## What a reader needs first

**Checkout, worktree, HEAD.** A git checkout is a directory holding the repository's files as of one commit, plus any changes made there since; git calls each such directory of a clone a worktree. The clone's first worktree is its main worktree; the others are linked worktrees made with `git worktree add`. HEAD is what a checkout stands on: a branch, such as `main`, or, when HEAD is detached, a commit named directly, with no branch. This design says "checkout" for the directory and "check out" only for the git action.

**Behind and ahead.** A checkout is behind main by the number of commits on `origin/main` that its HEAD lacks, and ahead by the number of commits its HEAD has that `origin/main` lacks. "Own commits" below means commits that are not on `origin/main`. `origin/<branch>` is the remote-tracking branch: this clone's record, from its last fetch or push, of the branch on GitHub; a plain `git fetch` keeps the record of a branch since deleted on GitHub until `git fetch --prune` removes it. A commit is pushed when some remote-tracking branch holds it after a `git fetch`: `git fetch`, then `git branch -r --contains <commit>` prints a name. The fetch brings this clone's record up to date, so a commit pushed from the other machine counts too. This is a definition for agents to apply, not a program's test. When the fetch fails, the agent treats the commit as pushed and its branch as having an open pull request, and so neither amends nor rebases it until a fetch succeeds; no program refuses the amend or the rebase.

**Moving a checkout forward.** Three git operations bring a checkout up to date, and they differ in what they risk:

- a fast-forward (`git merge --ff-only origin/main`) moves HEAD to `origin/main` when HEAD has no own commits, and rewrites no commit; it overwrites every tracked file main changed, and refuses rather than overwrite an uncommitted change to a tracked file or an untracked file (one git neither tracks nor ignores) at a path main adds; a file git ignores is overwritten;
- a rebase (`git rebase origin/main`) replays a branch's own commits on top of main, giving each replayed commit a new hash, unless the branch already sits on top of main, when nothing changes; git drops an own commit whose change main already holds;
- a merge (`git merge origin/main`) adds a merge commit joining the branch and main when each has commits the other lacks, fast-forwards when only main has new commits, and does nothing when main has none the branch lacks. A topic branch never takes a merge from main; a conflict with main is cleared by a new pull request (step 8).

**Frozen-head and fix-round.** Both are project-terms the glossary defines. Decision 4 changes when a head commit is frozen: from when its pull request is open, not from when it is pushed, until the pull request merges or is closed (not yet in force: approval-walk on CLAUDE.md). While frozen it is never amended or rebased, and never force-pushed except when merge-lane-2 asks for the force-push (decision 18), because merge-lane-2 commissions its review against that commit. The glossary's frozen-head entry says "once pushed" and CLAUDE.md says a head commit "becomes a frozen-head the moment it is pushed"; the glossary changes in the Build item "Agent-homes detached at main", and CLAUDE.md in the approval-walk on CLAUDE.md that the agent-seats cold-read-improvement and fleet-restart-at-login are preparing (Corrections).

**The two machines.** The Mac and ned-box each have their own clone of the repository. A branch made in one clone reaches the other through GitHub: pushed from one, fetched by the other.

**Scratchpad.** Claude Code gives each agent-session a temporary directory of its own, its scratchpad: under `/private/tmp/claude-501/` on the Mac and `/tmp/claude-1000/` on ned-box. The operating system can empty these directories.

**The hooks and the launch-time sync.** The freshness hook is `scripts/checkout-freshness-catch-up.py`, a Claude Code Stop hook, run when a turn of an agent-session ends normally (not after an interrupted turn), on the checkout that holds the agent-session's working directory. The session-location write guard, the force-push guard and the edit warning hook below are Claude Code hooks too; a Codex run gets none of them, only the git hooks. The launch-time sync is `sync_working_branch_with_main` in `nc-systems/handoff/handoff-supervisor.py`: before each agent-session it starts or resumes, though not when it adopts an agent-session already running, the handoff-supervisor runs it on the agent-seat's agent-home. It fast-forwards the agent-home when it is strictly behind with no own commits, no uncommitted tracked change and no git operation in progress, and otherwise leaves it, with the reason in its `branch sync:` line. It also leaves an agent-home that is on a branch, and its `branch sync:` line says the agent-home is on a branch (not yet built: Build, agent-homes detached at main).

## What a checkout's HEAD can be, and what each program does

The freshness hook acts on the checkout that holds the agent-session's working directory, which is normally the agent-home; it sees a topic worktree only while the agent-session's working directory is there, as after Claude Code's EnterWorktree tool. So in the normal arrangement it never examines a topic branch, and the rows below from `unpushed` on apply only to an agent-session started by hand inside a topic worktree; for those rows the hook keeps its behaviour on main, less its rebase step (decision 3) and with a new pull request in place of a hand-merge (Build, new pull request in place of a hand-merge). It fetches from GitHub at most every 300 seconds for each checkout (`DEFAULT_FETCH_INTERVAL_SECONDS`). It sorts a checkout with `head_state`, except that a checkout on `main` is handled as a reference checkout and a detached one by `move_detached_checkout_forward`. It tells the agent through `additionalContext` and the user through `systemMessage`. It tells the agent about a branch only when the branch is behind `origin/main`, once for each commit `origin/main` stands at (`drift_facts`).

After its Build item, the freshness hook gives an agent-facing-message about a checkout it left alone again when main moves or when the reason changes (not yet built: Build, freshness hook). A second agent-session in the same agent-home is not told to reread after the first one's fast-forward. It moves no branch except `main` in the reference checkout, and besides that fast-forwards only a detached checkout (not yet built: Build, freshness hook, which deletes `rebase_never_pushed_branch`). Its `timeout` in `.claude/settings.json` is set above the sum of its slowest steps; when Claude Code stops the hook at that limit, that turn's agent-facing-messages are lost (not yet built: Build, freshness hook; today the hook has no `timeout` entry).

| State | Example | Freshness hook |
|---|---|---|
| on `main` | the reference checkout | fast-forwarded when it has no own commits, no uncommitted tracked change and no git operation in progress; otherwise left, and the user told once per reason |
| detached, no own commits, no uncommitted tracked change, no operation in progress | an agent-home at an old main commit | fast-forwarded, and the agent told what changed and to reread CLAUDE.md and any listed skill; when git refuses, the agent told why, and a refusal that does not name an untracked file is also reported to the user once |
| detached, with own commits, an uncommitted tracked change, or an operation in progress | an agent-home where an agent committed by mistake | left; the agent told why, and told to carry the work to a topic worktree: finish or abort the rebase, merge, cherry-pick or revert in progress, if any; commit the uncommitted changes with `git add -A && git commit -m '<what>'`; then `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> HEAD`, and in the agent-home `git fetch && git checkout --detach origin/main`; files git ignores stay in the agent-home. No branch is left pointing at the carried commits; an agent-home still on a branch is the launchers' case (Build, agent-homes detached at main) (not yet built: Build, freshness hook) |
| no own commit on any remote-tracking branch (`unpushed`) | a topic branch with two commits, no copy on GitHub | left; the agent may rebase the branch onto `origin/main`, and need not (not yet built: Build, freshness hook; today the hook rebases it) |
| own commits pushed under another branch's name (`pushed-history`) | a branch cut at a pull request's pushed head commit to make a fix-round | left; the agent told not to rebase or amend those commits, and that a fix is a new commit on top (`PUSHED_HISTORY_ADVICE`) |
| HEAD equals `origin/<branch>` (`pushed`) | a pull request's branch under review | left; the agent told not to rebase or amend the branch, and that a fix is a new commit on top, pushed once (`LEAVE_IT_ADVICE`) |
| ahead of `origin/<branch>` (`pushed-with-local-commits`) | a fix-round commit not yet pushed | left; told as for `pushed` (`LEAVE_IT_ADVICE`) |
| behind its remote-tracking branch (`behind-remote`) | another agent pushed a fix-round commit to this branch | left; told as for `pushed` (`LEAVE_IT_ADVICE`); `head_state`'s description tells the agent to fast-forward to `origin/<branch>` before working there |
| diverged from its remote-tracking branch (`diverged-from-remote`) | the branch was amended after it was pushed; or a commit was made here while another agent pushed one | left; told as for `pushed`, and reported to the user ("A rewritten frozen-head" below) |
| `unknown` | git did not run, or could not say whether the branch's commits are on a remote-tracking branch | left; the agent told to check `git status` (`UNKNOWN_ADVICE`) |

The hook makes no GitHub call. The hook reaches `behind-remote` only when the branch is also behind `origin/main`; git's own refusal of a non-fast-forward push covers the cases the hook does not see.

At every turn's end the freshness hook also checks the checkout for two things an agent must not do, and reports each to the user. Like the rows from `unpushed` on, these checks reach a topic branch only in an agent-session started by hand inside its topic worktree.

- **A merge from main into the checkout's branch** (`merges_from_main`). A topic branch never takes a merge from main (step 8). Today the hook re-merges each such merge's two parents with `git merge-tree` and reports only a merge whose parents re-merge cleanly, so that an allowed hand-merge goes unreported; after its Build item it reports every merge from main into a topic branch, and tells the agent to clear a conflict with a new pull request instead (not yet built: Build, new pull request in place of a hand-merge). When a git command the check needs fails, the hook reports a failure, not a forbidden merge, to the agent and to the user, naming the command and git's error and saying the repository may be damaged; the agent runs `git fsck` and reports what it finds before pushing again (not yet built: Build, new pull request in place of a hand-merge).
- **A rewritten frozen-head** (`head_state`'s `diverged-from-remote`). The hook reports every `diverged-from-remote` branch to the user, whether or not it has an open pull request, and asks GitHub nothing. Most often `origin/<branch>` advanced under commits made here, which is no rewrite; the user tells the two apart from the report. A rewrite force-pushed within the same turn leaves HEAD equal to `origin/<branch>`, the `pushed` state, and is not reported; a rewrite made from the other machine's clone is not reported either. The force-push guard is the check on rewriting a frozen-head.

Other programs that act on a checkout's state:

- `scripts/obsolete-file-edit-warning-hook.py`, the edit warning hook, is the only other program that calls `head_state`; after each Edit or Write of a file inside the checkout that holds the agent-session's working directory, it warns when `origin/main` changed the file since the checkout's merge base with `origin/main`, with an agent-facing-message for each state. It says nothing about a file in any other checkout, so it is silent for an edit in a topic worktree made from the agent-home. Its agent-facing-messages give no rebase instruction and point an agent in an agent-home to a topic worktree (not yet built: Build, freshness hook), and name a new pull request, not a hand-merge, for a conflict with main (not yet built: Build, new pull request in place of a hand-merge).
- `.claude/hooks/session-location-write-guard.py`, the session-location write guard, registered for Edit, Write and NotebookEdit, uses its own `head_state_of`. It refuses such a call into the checkout that holds the agent-session's working directory while HEAD is detached, unless a rebase, merge, cherry-pick or revert is in progress or git ignores the file, and refuses one into the reference checkout; both refusals are user-blocks: each lets one call through when `.location-write-approved` holds the user's quoted approval. A write made by a Bash command is not checked. Its refusal in an agent-home names the command that makes a topic worktree, `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> origin/main`, and so does `docs/agents/seat-first-prompt.md` (not yet built: Build, agent-homes detached at main).
- `scripts/force-push-with-open-pull-request-guard-hook.py`, the force-push guard, registered for Bash, refuses `git push --force` or `--force-with-lease` to a branch that GitHub says has an open pull request (`open_pull_request_for_branch`). It lets the push through with an agent-facing-message when a `gh` call fails or takes longer than 10 seconds (`GH_TIMEOUT_SECONDS`, within a budget of 20 seconds for the whole run, `PROBE_BUDGET_SECONDS`), and lets every command through when its shell parser is missing or fails (`parser_unavailable_hook_output`). A push inside an ssh command, and a push of several branches in one command, are outside its scope. Its refusal says that if merge-lane-2 asked for the force-push, the agent may run the command again prefixed with `CLAUDE_MERGE_LANE_ASKED_FOR_THIS_REWRITE=1` (`ESCAPE_HATCH_VARIABLE`); the guard reads the prefix from the command itself, the agent writes it there, and the guard does not check that merge-lane-2 asked.
- The freshness hook does not run for a subagent: it is registered for Stop only, not for SubagentStop. A subagent's worktree is cut from `origin/main` as of the clone's last fetch, a conflict with main is refused when the subagent pushes (step 4), and the dispatching agent's own hook does not see the subagent's worktree.

## How a change reaches main

1. **Make a topic worktree from `origin/main`.** One feature or one bugfix per topic branch, which may take several commits. After a successful `git fetch`, `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> origin/main` makes the branch and its worktree together, from any checkout. Then work in the topic worktree: run git and test commands there (start each with `cd <worktree> &&`, or use `git -C <worktree>`), because a command run from the agent-home acts on the agent-home; `python3 scripts/run-all-test-suites.py` names the runner by a relative path, so without the `cd` it runs the agent-home's copy against the agent-home, unless given `--checkout <worktree>`. The agent-home holds no topic work. A Claude Code hook, the worktree location hook, refuses an agent's `git worktree add` that makes a new branch (`-b` or `-B`) at a path outside `~/Projects/nedschorus/.claude/worktrees/`, and one whose directory name begins with `agent-`, saying such names belong to subagent worktrees, which the cleaner removes after an hour; it also refuses Claude Code's EnterWorktree tool when the agent-session runs from an agent-home; each refusal names the command above. A detached worktree may be made anywhere (not yet built: Build, worktree location hook). Nothing makes a topic branch start at `origin/main`: GHI [Topic-branch base enforcement: a branch-creation script and a gh pr create check that refuses an undeclared carry of another PR's commits](https://github.com/nedschorus/nedschorus/issues/238) proposes a script and a check, unbuilt.
2. **Work.** No program moves the topic branch (not yet built: Build, freshness hook; today the freshness hook rebases a never-pushed topic branch while the agent-session's working directory is in its worktree). An agent may rebase a never-pushed branch onto `origin/main`, and need not: a conflict with main is refused at the push, unless the check cannot run or is skipped (step 4), and a merge without conflicts that breaks a tested behaviour is caught by merge-lane-2's test of the head commit merged onto main (step 6).
3. **Run the selective test run before pushing,** in the topic worktree: `git fetch`, then `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`. CLAUDE.md asks for this; no program runs it or checks it. The author's own run finds a failure before merge-lane-2's run would, and saves a review round, which is worth asking for but not worth a hook that slows every push.
4. **Push** with `git push -u origin <topic>`. The pre-push hook runs `scripts/branch-conflict-check.py` against main and refuses a push to `origin` that conflicts (`scripts/git-client-side-hooks-pre-push-conflict-check.py`). When the check cannot run or gives no answer, the push goes through, and `git push --no-verify` skips it. Until a pull request is open, the agent may still rewrite and force-push the branch (not yet in force: approval-walk on CLAUDE.md).
5. **Open the pull request.** The head commit is now a frozen-head (not yet in force: approval-walk on CLAUDE.md), and the force-push guard protects the branch.
6. **merge-lane-2 tests and reviews.** This step's program is not yet in the repository: the Build item "merge-lane-2's test program" adds and names it, and merge-lane-2's seat-brief names that program (not yet built: Build, merge-lane-2's test program); today merge-lane-2 does the test by hand. On ned-box, for every pull request that changes a recorded input of any test suite, merge-lane-2 runs that program; the program asks `scripts/run-all-test-suites.py` which suites those are, and a suite with no recording yet, such as one the pull request adds, always runs. The program builds `wt/pr<N>-merged` at `origin/main` with `git merge --no-ff <head commit>`, never pushed, and runs `scripts/pull-request-head-test-run.py --checkout <that worktree>`. A conflict with main stops that merge before any review is commissioned; how merge-lane-2 then tells the author is settled with merge-lane-2 in that Build item. A test run that fails, or that ends without a verdict, blocks the merge; merge-lane-2 reruns it once, then tells the user why it cannot get a verdict, and that pull request waits while the others proceed. A failure merge-lane-2 or the user judges not worth fixing is cleared by a separate pull request that deletes the test, or skips it with its reason and a GHI that tracks it; the blocked pull request is then rerun, not cancelled. merge-lane-2 commissions the reviews the head commit needs and decides which findings block. When main moves with a change to a recorded input of any test suite before the merge, merge-lane-2 rebuilds the merged worktree on the new main and reruns the tests. After a merge, when main's tree matches the tested tree, merge-lane-2 runs nothing more; when it differs, merge-lane-2 runs the suites whose recorded inputs changed between the tested tree and main; the daily full test run on both machines is the backstop for anything those selections miss. When a run after a merge fails, merge-lane-2 tells the user and the author of the pull request it merged, and merges nothing else until main passes, except a pull request that merge-lane-2 or the user names as the fix in a comment on it. When the daily full test run fails, merge-lane-2 tells the user and keeps merging; the failing suite then blocks only the pull requests whose own tests select it.
7. **Fix-round.** Findings that hold are answered by a fix-round: one commit on top of the frozen-head, pushed once, written by a forked subagent; findings that do not hold are answered with the reason. When the fix is made on a branch cut at the pushed head commit under another name, the `pushed-history` state, the commit reaches the pull request with `git push origin HEAD:<the pull request's branch>`.
8. **Conflict.** When `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`, or GitHub reports a conflict that git does not, the author makes a new topic branch from current `origin/main`, applies the pull request's change to it with the conflict resolved, opens a new pull request whose description links the old one, and closes the old pull request with a comment linking the new one; if main deleted or replaced what the branch changes, the author closes the pull request with a comment naming what replaced it and carries only what main still lacks. Merging main into a topic branch is never allowed. When the conflict is found as a fix-round commit is pushed, the fix goes into the new pull request instead. When a pull request comes to conflict with main after its review, merge-lane-2's merge onto main fails, the author makes the new pull request, and merge-lane-2 tests and reviews it from the start (not yet built: Build, new pull request in place of a hand-merge; today the author hand-merges main into the branch, as the report of `scripts/branch-conflict-check.py` says).
9. **Merge.** `scripts/merge-gate.sh` checks that an approving review covers the head commit, that GitHub's merge state allows the merge, and that no review or comment arrived since merge-lane-2 last read them, then prints the merge command pinned to the head commit with `--match-head-commit`. merge-lane-2 runs it, as a merge commit, never a squash. Two gaps are known: `scripts/merge-gate.sh` does not check that the test run of step 6 ran or passed, and a review that arrives between `scripts/merge-gate.sh`'s check and the merge is not seen.
10. **Clean up.** `scripts/clean-worktrees.py`, the cleaner, runs daily at 06:30 on both machines, and at each session-handoff. Its rules ask nothing of GitHub. This step states the cleaner as its Build item makes it; of its rules below, only the subagent worktree's hour, the deletion of a fully merged branch with no worktree, and the removal with `--force` and its output are built (not yet built: Build, cleaner). Today the cleaner acts only on worktrees under `~/Projects/nedschorus/.claude/worktrees/`, ignores locks, removes a vacant worktree there whose branch has no own commits at its next run whatever it holds, keeps one with own commits, and deletes a branch only when it is fully merged. After its Build item it covers every worktree of the clone except the reference checkout and any worktree locked with `git worktree lock`, which it lists with its lock reason and never removes; it covers branches anywhere in the clone, and reports dead registrations.
    - Every agent-home is locked: at the start of every run, before any rule, the cleaner locks with `git worktree lock`, reason "agent-home", every worktree at `~/agents/<name>` for which the handoff-supervisor keeps a state file, `~/.claude/handoffs/<name>-supervisor-state.json`; a worktree already locked stays as it is, and when a lock fails the cleaner stops before removing anything and reports why. A worktree elsewhere under `~/agents/` with no state file, such as a misplaced one, stays unlocked. An agent-seat that keeps another worktree on purpose locks it itself; merge-lane-2 locks `wt/main` (the merge-lane-2 row above).
    - Each unlocked worktree falls under the first of the next three rules that fits it, and is removed only if it is vacant, that is, no process has its working directory inside it (`worktree_vacancy_keep_reason`).
    - A subagent worktree, named `agent-<id>`, with no own commits, is removed when it is quiet (`agent_worktree_quiet_keep_reason`: neither the subagent's transcript nor the worktree's `.git` file written for an hour), whatever it holds.
    - A topic worktree with no uncommitted, untracked or ignored file (the disposable files `.DS_Store` and `__pycache__` aside, `DISPOSABLE_JUNK_BASENAMES`) and no own commits is removed once it has been quiet for an hour, measured from the newest of the worktree directory's modification time, its `.git` file's and its git index's; the cleaner reads those times at each run, so nothing records anything. The hour keeps a topic worktree made just before another agent-seat's session-handoff from being removed before its first edit. Such a removal loses no work, since the worktree is empty and its branch sits at `origin/main`; an agent that finds its topic worktree gone remakes it with the same `git worktree add` command.
    - Any other worktree, a subagent worktree with own commits included, is removed once nothing in it has changed for 30 days, whatever it holds. The 30 days count from the newest of: the modification time of each file a removal would discard and of each directory in the worktree (a deleted or added file changes its directory's), the worktree's `.git` file and git index, and the committer date of its branch tip, or of HEAD when HEAD is detached. The cleaner reads git with `--no-optional-locks`, so its own reads do not refresh the index and reset the clock. Its branch is deleted with it, merged or not.
    - A branch that no worktree has checked out is deleted when it is fully merged into `origin/main` (`branch_refs_with_no_worktree_fully_on_main`), or when it is more than 30 days old, its age measured from the newer of its tip's committer date and its newest reflog entry, the last time the branch was made or moved in this clone.
    - Before deleting an unmerged branch, or removing a detached worktree whose HEAD has own commits, whichever run does it, the cleaner appends the branch name or the worktree's path, the machine, its tip's hash and each own commit's subject to `nedlern@ned-box:/home/nedlern/nedschorus-logs/clean-worktrees/deleted-branches.log` in the log-store, over ssh from the Mac; when that line cannot be written, the branch or worktree is kept, the failure appears in the handoff-supervisor's `worktree cleanup:` line at the next session-handoff, and the next run tries again. While ned-box cannot be reached, the Mac deletes no unmerged branch. `git branch <name> <tip hash>` brings the commits back while git still holds them, and that window may be zero: git's garbage collection may prune them at its next run, because it prunes an object nothing refers to once the object file is older than its grace period of two weeks (`gc.pruneExpire`), and an object file is as old as the commit's arrival in this clone. A commit that GitHub, or the other machine's clone, still holds is not lost with this clone's copy. Otherwise only the clone's backups hold it: Time Machine on the Mac, whose schedule this design has not checked, and Timeshift on ned-box, which takes a snapshot every 10 minutes (`/etc/cron.d/timeshift-10min`), keeps each for about 24 hours, and beyond that keeps the daily, weekly and monthly snapshots its settings name, 7, 5 and 12 (`/etc/timeshift/timeshift.json`). The cleaner keeps no other copy.
    - Removal is `git worktree remove --force`, and the cleaner's output names the files a removal discards, at most 10 and then a count of the rest (`DISCARDED_FILES_NAMED_AT_MOST`). Uncommitted changes to tracked files and untracked files survive in the work-snapshot that `scripts/uncommitted-work-snapshot-hook.py` kept, if it kept one: it is listed in the initial-agent-instructions of the owning agent-seat's next agent-session, within the limits `nc-systems/handoff/uncommitted-work-snapshots-across-crashes-design.md` states, and deleted ten days after that first listing if nobody restores it. Files git ignores, such as walk-documents and walk-minutes (terms of `.claude/skills/skills-glossary.md`), survive only where a backup, a transcript or a copy shipped to the log-store caught them, which `scripts/find-deleted-path-across-backups.py` searches.
