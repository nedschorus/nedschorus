## What a reader needs first

**Checkout, worktree, HEAD.** A git checkout is a directory holding a copy of the repository's files at one commit; git calls each such directory of a clone a worktree. The clone's first worktree is its main worktree; the others are linked worktrees made with `git worktree add`. HEAD is what a checkout stands on: a branch, such as `main`, or, when HEAD is detached, a commit named directly, with no branch. This design says "checkout" for the directory and "check out" only for the git action.

**Behind and ahead.** A checkout is behind main by the number of commits on `origin/main` that its HEAD lacks, and ahead by the number of commits its HEAD has that `origin/main` lacks. "Own commits" below means commits that are not on `origin/main`. `origin/<branch>` is the remote-tracking branch: this clone's record, from its last fetch or push, of the branch on GitHub. A commit is "on GitHub" when some remote-tracking branch holds it (`git branch -r --contains <commit>` prints a name).

**Moving a checkout forward.** Three git operations bring a checkout up to date, and they differ in what they risk:

- a fast-forward (`git merge --ff-only origin/main`) moves HEAD to `origin/main` when HEAD has no own commits, and rewrites no commit; it overwrites every tracked file main changed, and refuses rather than overwrite an uncommitted change to a tracked file or a file git neither tracks nor ignores at a path main adds; a file git ignores is overwritten;
- a rebase (`git rebase origin/main`) replays a branch's own commits on top of main, giving them new commit hashes;
- a merge (`git merge origin/main`) adds a merge commit joining the branch and main when the branch has own commits, and fast-forwards when it has none.

**Frozen-head and fix-round.** Both are project-terms the glossary defines. This design changes when a head commit is frozen: from when its pull request is open, not from when it is pushed, until the pull request merges or is closed. While frozen it is never amended, rebased or force-pushed, because merge-lane-2 commissions its review against that commit. The glossary's frozen-head entry and CLAUDE.md still say "once pushed"; the glossary changes in the Build's agent-home sweep, and CLAUDE.md in the approval-walk on CLAUDE.md that the agent-seats cold-read-improvement and fleet-restart-at-login are preparing (Corrections).

**The two machines.** The Mac and ned-box each have their own clone of the repository. Git branches pass between them only through GitHub.

**Scratchpad.** Claude Code gives each agent-session a temporary directory of its own, its scratchpad: under `/private/tmp/claude-501/` on the Mac and `/tmp/claude-1000/` on ned-box. The operating system can empty these directories.

**The hooks.** The freshness hook is `scripts/checkout-freshness-catch-up.py`, a Claude Code Stop hook, run when a turn of an agent-session ends normally (not after an interrupted turn), on the checkout that holds the agent-session's working directory. The write guard, the force-push guard and the obsolete-file warning below are Claude Code hooks too; a Codex run gets none of them, only the git hooks. The launch-time sync is `sync_working_branch_with_main` in `nc-systems/handoff/handoff-supervisor.py`: before each agent-session it starts or resumes, the handoff-supervisor runs it on the agent-seat's agent-home. It fast-forwards the agent-home when it is strictly behind with no own commits, no uncommitted tracked change and no git operation in progress, and otherwise leaves it, with the reason in its `branch sync:` line. A checkout on a branch it leaves, with that reason (not yet built: Build, agent-home sweep).

## What a checkout's HEAD can be, and what each program does

The freshness hook acts on the checkout that holds the agent-session's working directory, which is normally the agent-home; it sees a topic worktree only while the agent-session's working directory is there, as after Claude Code's EnterWorktree. So in the normal arrangement it never examines a topic branch, and the rows below from `unpushed` on apply only to an agent-session working inside a topic worktree. It fetches from GitHub at most every 300 seconds for each checkout (`DEFAULT_FETCH_INTERVAL_SECONDS`). It sorts a checkout with `head_state`, except that a checkout on `main` is handled as a reference checkout and a detached one by `move_detached_checkout_forward`. It tells the agent through `additionalContext` and the user through `systemMessage`. A note to the agent about a checkout it left alone is told again when main moves or when the reason changes (not yet built: Build, freshness hook). The hook moves no branch except `main` in the reference checkout; besides that it fast-forwards only a detached checkout (not yet built: Build, freshness hook, which deletes its rebase step). Its `timeout` in `.claude/settings.json` is set above the sum of its slowest steps; when Claude Code stops the hook at that limit, that turn's notes are lost (not yet built: Build, freshness hook).

| State | Example | Freshness hook |
|---|---|---|
| on `main` | the reference checkout | fast-forwarded when it has no own commits, no uncommitted tracked change and no git operation in progress; otherwise left, and the user told once per reason |
| detached, no own commits, no uncommitted tracked change, no operation in progress | an agent-home at an old main commit | fast-forwarded, and the agent told what changed and to reread CLAUDE.md and any listed skill; when git refuses, the agent told why, and a refusal that does not name an untracked file is also reported to the user once |
| detached, with own commits, an uncommitted tracked change, or an operation in progress | an agent-home where an agent committed by mistake | left; the agent told why, and told to carry the work to a topic worktree: `git worktree add -b <topic> <path> HEAD` carries the commits, uncommitted files are copied across, and then `git checkout --detach origin/main` returns the agent-home to main (not yet built: Build, freshness hook) |
| never pushed (`unpushed`) | a topic branch with two commits, no copy on GitHub | left; the agent may rebase the branch onto `origin/main`, and need not (not yet built: Build, freshness hook) |
| pushed history under a new name (`pushed-history`) | a branch cut at a pull request's pushed head commit to make a fix-round | left; the agent told that, if the pull request is open, those commits are frozen |
| pushed, and HEAD equals its remote-tracking branch (`pushed`) | a pull request's branch under review | left; the agent told that, if this branch has an open pull request, its head commit is frozen (not yet built: Build, freshness hook) |
| pushed, with commits on top that are not on GitHub (`pushed-with-local-commits`) | a fix-round commit not yet pushed | left; the agent told that, if this branch has an open pull request, the commits on GitHub are frozen, and that the commits not on GitHub may be amended, or rebased with `git rebase -i origin/<branch>` (not yet built: Build, freshness hook) |
| behind its remote-tracking branch (`behind-remote`) | another agent pushed a fix-round commit to this branch | left; the agent told to run `git merge --ff-only origin/<branch>` (not yet built: Build, freshness hook) |
| diverged from its remote-tracking branch (`diverged-from-remote`) | the branch was amended after it was pushed; or a commit was made here while another agent pushed one | left; see "A rewritten frozen-head" below |
| `unknown` | git did not run, or could not say whether the branch's commits are on a remote-tracking branch | left; the agent told to check `git status` (`UNKNOWN_ADVICE`) |

The routine messages say "if this branch has an open pull request" rather than asking GitHub; only the rewrite report below asks GitHub. The hook reaches `behind-remote` only when the branch is also behind `origin/main`; git's own refusal of a non-fast-forward push covers the cases the hook does not see.

At every turn's end the freshness hook also checks the checkout for two things an agent must not do, and reports each to the user:

- **A merge from main into the checkout's branch** whose two parents re-merge without a conflict (`merges_from_main`). A merge whose parents conflict when re-merged is not reported; that covers the allowed hand-merge, and also a merge over a file main deleted, which step 8 forbids and which nothing reports. A hand-merge that GitHub demanded although git can merge the parents cleanly is reported as forbidden; when that report reaches the user, the author explains that GitHub demanded the hand-merge, and the hook is fixed then.
- **A rewritten frozen-head** (`head_state`'s `diverged-from-remote`). The hook first asks whether a commit that this branch once held locally is missing from HEAD: whether some commit in `HEAD..origin/<branch>` appears in the branch's own reflog (`git reflog <branch>`). If none does, nothing this clone pushed was rewritten: `origin/<branch>` advanced under commits made here, and the agent is told to rebase those commits onto `origin/<branch>`. If one does, the hook asks GitHub (`gh pr list --state open --head <branch>`) and reports the rewrite to the user only when the branch has an open pull request, since a rewrite before a pull request opens is allowed. When either question cannot be answered, the hook tells the agent it could not check and why, and reports nothing (not yet built: Build, freshness hook).

Other programs that act on a checkout's state:

- `scripts/obsolete-file-edit-warning-hook.py` is the only other program that calls `head_state`; after each Edit or Write of a file inside the checkout that holds the agent-session's working directory, it warns when the file is older than main's copy, with advice by state. It says nothing about a file in any other checkout, so it is silent for an edit in a topic worktree made from the agent-home. Its advice gives no rebase instruction and points an agent in an agent-home to a topic worktree (not yet built: Build, freshness hook).
- `.claude/hooks/session-location-write-guard.py`, registered for Edit, Write and NotebookEdit, uses its own `head_state_of`. It refuses such a call into the checkout that holds the agent-session's working directory while HEAD is detached, unless a rebase, merge, cherry-pick or revert is in progress or git ignores the file, and refuses one into the reference checkout; both refusals are user-blocks: each lets one call through when `.location-write-approved` holds the user's quoted approval. A write made by a Bash command is not checked. Its refusal in an agent-home names the command that makes a topic worktree, `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> origin/main`, and so does `docs/agents/seat-first-prompt.md` (not yet built: Build, agent-home sweep).
- `scripts/force-push-with-open-pull-request-guard-hook.py`, registered for Bash, refuses `git push --force` or `--force-with-lease` to a branch that GitHub says has an open pull request (`open_pull_request_for_branch`). When GitHub cannot be asked within its 20-second budget, it lets the push through with a note. Its refusal says that if merge-lane-2 asked for the force-push, the agent may run the command again prefixed with `CLAUDE_MERGE_LANE_ASKED_FOR_THIS_REWRITE=1` (`ESCAPE_HATCH_VARIABLE`); the agent sets the variable itself, and the guard does not check that merge-lane-2 asked.
- No freshness check runs for a subagent: the freshness hook is registered for Stop only, not for SubagentStop. A subagent's task is short, its branch is cut from current main or is a pushed fix-round branch, and the agent that dispatched it receives the hook's notes at its own turn's end.

## Who may move what

| Action | Allowed when | Enforced by |
|---|---|---|
| Fast-forward a checkout to `origin/main` | it has no own commits, no uncommitted tracked change and no git operation in progress | the freshness hook does it for the reference checkout and a detached checkout, the launch-time sync for an agent-home, and `fast_forward_seat_checkout` for ghi-info's checkout; an agent does it with `git merge --ff-only origin/main` |
| Rebase a branch | the branch has no open pull request and no other branch is built on it; or its commits that are not on GitHub, with `git rebase -i origin/<branch>`. A rebase onto `origin/main` rewrites every own commit of the branch, pushed ones included | nothing stops it; the freshness hook reports a rewrite of a branch with an open pull request to the user, only while the agent-session's working directory is in that branch's checkout, and never for a branch made under another name (`pushed-history`) |
| Amend a commit | the commit is not on GitHub, or its branch has no open pull request | as for Rebase |
| Merge main into a topic branch | only the hand-merge `scripts/branch-conflict-check.py` asks for, or one GitHub asks for when it reports a conflict that git does not | the freshness hook reports a merge whose parents re-merge cleanly, only while the agent-session's working directory is in that branch's checkout |
| Push | after the suites the change can affect pass, when the push does not conflict with main; a fix-round is pushed once | the pre-push hook refuses a push that conflicts with main; nothing runs the tests or counts the pushes |
| Force-push | never to a branch with an open pull request; closing the pull request without merging ends the frozen-head rule for its branch | the force-push guard, which lets the push through when GitHub does not answer within 20 seconds, or when the agent sets `CLAUDE_MERGE_LANE_ASKED_FOR_THIS_REWRITE=1` |
| Merge to main | merge-lane-2 after review, pinned to the reviewed head commit, or an agent-seat the user deputizes in that agent-seat's own agent-session, as rule R13 of `docs/nedschorus-wiki/nedschorus-fleet-git-worktree-working-model.md` says | GitHub's branch protection, which lets only the accounts `nedlern` and `ned-review-merge` push to main and requires one approving review (that page's R12); `scripts/merge-gate.sh` checks the conditions in step 9 and prints the pinned merge command, which uses the `ned-review-merge` credential, but nothing makes a merger run it |

## How a change reaches main

1. **Make a topic worktree from `origin/main`.** One feature or one bugfix per topic branch, which may take several commits. After a successful `git fetch`, `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> origin/main` makes the branch and its worktree together, from any checkout. Then work in the topic worktree: run git and test commands there (`cd` into it, or `git -C <worktree>`), because a command run from the agent-home acts on the agent-home. The agent-home holds no topic work. A Claude Code hook refuses an agent's `git worktree add` whose path is outside `~/Projects/nedschorus/.claude/worktrees/`, and Claude Code's tool for entering a new worktree when the agent-session runs from an agent-home; its refusal names the command above (not yet built: Build, worktree-place hook). Nothing enforces the base: GHI [Topic-branch base enforcement: a branch-creation script and a gh pr create check that refuses an undeclared carry of another PR's commits](https://github.com/nedschorus/nedschorus/issues/238) proposes a script and a check, unbuilt.
2. **Work.** No program moves the topic branch. An agent may rebase a never-pushed branch onto `origin/main`, and need not: a conflict with main is refused at the push (step 4), and a merge without conflicts that breaks a tested behaviour is caught by merge-lane-2's test of the head commit merged onto main (step 6).
3. **Run the selective test run before pushing,** in the topic worktree: `git fetch`, then `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`. CLAUDE.md asks for this; no program runs it or checks it. The author's own run finds a failure before merge-lane-2's run would, and saves a review round, which is worth asking for but not worth a hook that slows every push.
4. **Push** with `git push -u origin <topic>`. The pre-push hook runs `scripts/branch-conflict-check.py` against main and refuses a push to `origin` that conflicts (`scripts/git-client-side-hooks-pre-push-conflict-check.py`). When the check cannot run or gives no answer, the push goes through, and `git push --no-verify` skips it. Until a pull request is open, the agent may still rewrite and force-push the branch.
5. **Open the pull request.** The head commit is now a frozen-head, and the force-push guard protects the branch.
6. **merge-lane-2 tests and reviews.** On ned-box, for every pull request that changes a file other than Markdown, merge-lane-2 runs a program in the repository, which Build item "merge-lane-2's test program" adds and names, and merge-lane-2's seat-brief names that program (not yet built). The program builds `wt/pr<N>-merged` at `origin/main` with `git merge --no-ff <head commit>`, never pushed, and runs `scripts/pull-request-head-test-run.py --checkout <that worktree>`. A conflict with main stops that merge before any review is commissioned; how merge-lane-2 then tells the author is settled with merge-lane-2 in that Build item. A failing test run blocks the merge. merge-lane-2 commissions the reviews the head commit needs and decides which findings block. When main moves with a change to a file other than Markdown before the merge, merge-lane-2 rebuilds the merged worktree on the new main and reruns the tests; after each merge it runs every suite on main.
7. **Fix-round.** Findings that hold are answered by a fix-round: one commit on top of the frozen-head, pushed once, written by a forked subagent; findings that do not hold are answered with the reason. When the fix is made on a branch cut at the pushed head commit under another name, the `pushed-history` state, the commit reaches the pull request with `git push origin HEAD:<the pull request's branch>`.
8. **Conflict.** When `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`, or GitHub reports a conflict that git does not: if main deleted or replaced what the branch changes, the pull request, if there is one, is closed, and what main still lacks is carried on a new topic branch; otherwise the author hand-merges main into the branch, with the frozen-head as first parent, plus at most one ordinary commit for an edit the resolution forces, pushed once. When the branch conflicts at the moment a fix-round commit is pushed, the pre-push hook refuses the push until the hand-merge is made. When a pull request comes to conflict with main after its review, merge-lane-2's merge onto main fails, the author clears the conflict with a hand-merge in a fix-round, and merge-lane-2 runs the tests and the review again.
9. **Merge.** `scripts/merge-gate.sh` checks that an approving review covers the head commit, that GitHub's merge state allows the merge, and that no review or comment arrived since merge-lane-2 last read them, then prints the merge command pinned to the head commit with `--match-head-commit`. merge-lane-2 runs it, as a merge commit, never a squash. Two gaps are known: `scripts/merge-gate.sh` does not check that the test run of step 6 ran or passed, and a review that arrives between the gate's check and the merge is not seen.
10. **Clean up.** `scripts/clean-worktrees.py` runs daily at 06:30 on both machines, and at each session-handoff. It covers every worktree of the clone except the reference checkout and any worktree locked with `git worktree lock`, which it lists with its lock reason and never removes; it covers branches anywhere in the clone, and reports dead registrations. Its rules ask nothing of GitHub (not yet built: Build, cleaner).
    - Every agent-home is locked: the launchers lock it at every launch, and the cleaner's pull request locks every existing agent-home on both machines as a step at its merge, before the wider rule first runs. An agent-seat that keeps another worktree on purpose locks it itself; merge-lane-2's program locks the `wt/main` worktree it builds.
    - A topic worktree with no uncommitted, untracked or ignored file (disposable files such as `__pycache__` aside) and no own commits is removed once it has been quiet for an hour, if it is vacant, that is, no process has its working directory inside it (`worktree_vacancy_keep_reason`). The hour keeps a topic worktree made just before another agent-seat's session-handoff from being removed before its first edit.
    - Any other unlocked worktree, a subagent worktree with a commit outside `origin/main` included, is removed once nothing in it has changed for 30 days, whatever it holds, if it is vacant. The 30 days count from the newest of: the modification time of each file a removal would discard and of each directory in the worktree (a deleted or added file changes its directory's), the worktree's `.git` file and git index, and its branch tip's committer date. Its branch is deleted with it, merged or not.
    - A branch that no worktree has checked out is deleted when it is fully merged into `origin/main` (`branch_refs_with_no_worktree_fully_on_main`), or when its tip's committer date is more than 30 days old.
    - Before deleting an unmerged branch, whichever run deletes it, the cleaner appends the branch name, its tip's hash and each commit's subject to `~/.claude/daily-clean-worktrees.log` on that machine; `git branch <name> <tip hash>` brings the branch back while git still holds its commits. Git's garbage collection may prune them at its next run, because commits older than its two-week grace period are pruned once nothing refers to them; after that only the clone's backups hold them.
    - A subagent worktree, named `agent-<id>`, with no own commits, is removed when it is vacant and quiet (`agent_worktree_quiet_keep_reason`: neither the subagent's transcript nor the worktree's `.git` file written for an hour), whatever it holds.
    - Removal is `git worktree remove --force`, and the cleaner's output names each file a removal discards. Uncommitted changes to tracked files and new files survive in the work-snapshot that `scripts/uncommitted-work-snapshot-hook.py` kept, if it kept one: it is listed in the initial-agent-instructions of the owning agent-seat's next agent-session, and deleted ten days after that first listing if nobody restores it. Files git ignores, such as walk-documents and walk-minutes, survive only where a backup or a transcript caught them, which `scripts/find-deleted-path-across-backups.py` searches.
