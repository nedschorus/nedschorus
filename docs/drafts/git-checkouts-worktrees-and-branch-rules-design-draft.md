# Design of record: the project's git checkouts, worktrees and branch rules

This design states how the project keeps each git checkout current with main, what an agent may do to a branch on its way to main, and how a change reaches main. It cites code by file and function or constant name. Where two places disagree, it says so: a description shown to be stale is listed under "Corrections", and a disagreement only the user can settle is a "Question for the user". Nothing here is built yet beyond what main already does.

## What a reader needs first

**Checkout, worktree, HEAD.** A git checkout is a directory holding a copy of the repository's files at one commit; git calls each such directory of a clone a worktree. The clone's first worktree is its main worktree; the others are linked worktrees made with `git worktree add`. HEAD is what a checkout stands on: a branch, such as `main`, or, when HEAD is detached, a bare commit. This design says "checkout" for the directory and "check out" only for the git action.

**Behind and ahead.** A checkout is behind main by the number of commits on `origin/main` that its HEAD lacks, and ahead by the number of commits its HEAD has that `origin/main` lacks. "Own commits" below always means commits that are not on `origin/main`; a branch's commits beyond its remote branch, `origin/<branch>`, are called "local commits".

**Moving a checkout forward.** Three git operations bring a checkout up to date, and they differ in what they risk:

- a fast-forward (`git merge --ff-only origin/main`) moves HEAD to main's newest commit when HEAD has no own commits, and rewrites no commit; it overwrites every tracked file main changed, but git refuses rather than overwrite an uncommitted change to a tracked file, or an untracked file at a path main adds;
- a rebase (`git rebase origin/main`) replays a branch's own commits on top of main, giving them new commit hashes;
- a merge (`git merge origin/main`) adds a merge commit joining the branch and main.

**Frozen-head and fix-round.** Both are project-terms the glossary defines: a head commit becomes a frozen-head the moment it is pushed, and a fix-round answers review findings with one commit on top of it.

**The two machines.** The Mac and ned-box each have their own clone of the repository. Git branches pass between them only through GitHub.

**Scratchpad.** Claude Code gives each agent-session a temporary directory of its own, its scratchpad: under `/private/tmp/claude-501/` on the Mac and `/tmp/claude-1000/` on ned-box. The operating system can empty these directories.

**The freshness hook and the launch-time sync.** The freshness hook is `scripts/checkout-freshness-catch-up.py`, run at the end of each turn of an agent-session. The launch-time sync is `sync_working_branch_with_main` in `nc-systems/handoff/handoff-supervisor.py`, run by the handoff-supervisor just before it starts an agent-session, both when the agent-seat starts and after each session-handoff.

## The kinds of checkout

| Kind | Where | HEAD | What keeps it current | What removes it |
|---|---|---|---|---|
| Reference checkout | the clone's main worktree: `/Users/el/Projects/nedschorus` on the Mac, `/home/nedlern/Projects/nedschorus` on ned-box | `main` | a fast-forward each time `scripts/launch-claude-mac` or `scripts/launch-claude-ubuntu` starts an agent-seat (through `checkout-freshness-catch-up.py --reference-pull`), and `fast_forward_reference_checkout` in the freshness hook at the end of each turn of an agent-session in any checkout of the clone | never removed |
| Agent-home | `~/agents/<agent-seat>`, made by `git worktree add -b <agent-seat> origin/main` in the two launchers | designed to be the seat-branch named after the agent-seat; in practice often detached, or a topic branch (Question A) | the launch-time sync, and the freshness hook while an agent-session works in it | never removed |
| Worktree under the reference checkout | `<reference>/.claude/worktrees/<name>` | a topic branch | the freshness hook while an agent-session works in it | `scripts/clean-worktrees.py`, the only worktrees it considers (`classify`) |
| Worktree under an agent-home, or beside it | `~/agents/<agent-seat>/.claude/worktrees/<name>`, or a sibling directory such as `/Users/el/agents/wt-<topic>` | a topic branch | the freshness hook while an agent-session works in it | its author, by hand; no program |
| Scratchpad worktree | an agent-session's scratchpad | detached or a branch | the freshness hook while an agent-session works in it | its author, by hand; when the operating system empties the scratchpad, the directory goes and a dead registration stays, which the cleaner reports (working model R25) |
| merge-lane-2's review worktrees | on ned-box, in merge-lane-2's scratchpad: `wt/pr<N>-head`, detached at a pull request's head commit, and `wt/pr<N>-merged`, the head merged onto `origin/main` | detached | rebuilt by merge-lane-2 when main moves | merge-lane-2, by hand; a scheduled remover is planned in GHI [Before a seat is retired, report what still cites the paths the retirement removes](https://github.com/nedschorus/nedschorus/issues/226) |
| A program's own worktree or clone | worktrees made by `scripts/daily-full-test-run-of-main.py`, `scripts/ghi-issue-write.py` and `scripts/pull-request-mutation-testing-survivors.py`; a separate local clone made by `scripts/sanity-check-attacks.py` | detached | — | the program that made it, in a `finally` block; one left by a killed program has no remover |
| ghi-info's checkout | `~/agents/ghi-info` on ned-box | the branch `ghi-info` | `fast_forward_seat_checkout` in `scripts/ghi-info-ask.py`, run by the ask that holds the lock | never removed |

Every checkout of the Mac's clone and of ned-box's clone runs the git hooks from the reference checkout's `scripts/git-client-side-hooks/`, because each clone's local git configuration sets `core.hooksPath` there. A separate clone, such as the one `scripts/sanity-check-attacks.py` makes, does not inherit that setting.

## What a checkout's HEAD can be, and what each program does

The freshness hook acts on the checkout that holds the agent-session's working directory, fetches from GitHub at most every 300 seconds (`DEFAULT_FETCH_INTERVAL_SECONDS`), and does nothing unless the checkout is behind `origin/main` (`drift_facts`). It sorts a checkout with `head_state`, except that a checkout on `main` is handled as a reference checkout and a detached one by `move_detached_checkout_forward`. It tells the agent through `additionalContext` and the user through `systemMessage`; a note to the agent about a checkout it left alone is told once per update of main (the `last_told` record keys on the branch and main's newest commit).

| State | Example | Freshness hook | Launch-time sync |
|---|---|---|---|
| on `main` | the reference checkout | fast-forwarded when it has no own commits, no uncommitted tracked change and no git operation in progress; otherwise left, and the user told once per reason | fast-forwarded when strictly behind with no own commits, no uncommitted tracked change and no git operation in progress; otherwise left, with the reason in its `branch sync:` line |
| detached, no own commits, no uncommitted tracked change, no operation in progress | an agent-home parked at an old main commit | fast-forwarded, and the agent told what changed and to reread CLAUDE.md and any listed skill; when git refuses, the agent told why, and a refusal that does not name an untracked file is also reported to the user once | as for `main` |
| detached, with own commits, an uncommitted tracked change, or an operation in progress | an agent-home with an uncommitted edit, or mid-rebase | left; the agent told why and what to do | as for `main` |
| never pushed (`unpushed`) | a topic branch with two local commits, no copy on GitHub | rebased onto `origin/main` when it has no uncommitted tracked change, no operation in progress and a readable `git status`; when git refuses before starting, the agent told; on a conflict the rebase is aborted and the agent told the files; when the abort fails, the tree is left mid-rebase and the user told | as for `main`; a branch with own commits is reported, never moved |
| pushed history under a new name (`pushed-history`) | a branch cut at a pull request's pushed head commit to make a fix-round | left; the agent told not to rebase or amend those commits | as for `main` |
| pushed, and HEAD equals its remote branch (`pushed`) | a pull request's branch under review | left; the agent told not to rebase or amend it, and to cut its next topic from `origin/main` | as for `main` |
| pushed, with local commits on top (`pushed-with-local-commits`) | a fix-round commit not yet pushed | left; told as for `pushed` (see Question J) | as for `main` |
| behind its remote branch (`behind-remote`) | another agent pushed a fix-round commit to this branch | left; told as for `pushed` (see Question G) | as for `main` |
| diverged from its remote branch (`diverged-from-remote`) | the branch was amended after it was pushed; or a local commit was made while another agent pushed one | left; the user told the pushed head commit was rewritten | as for `main` |
| `unknown` | git did not run, or could not say whether the branch's commits are on a remote branch | left; the agent told to check `git status` (`UNKNOWN_ADVICE`) | as for `main` |

At every turn's end, before anything else, the freshness hook also checks for two things an agent must not do, and reports each to the user: a merge from main into a working branch whose two parents re-merge without a conflict (`merges_from_main`), and divergence from the branch's remote branch, reported as a rewritten pushed head commit (`head_state`'s `diverged-from-remote`). A merge whose parents conflict when re-merged is not reported; that covers the allowed hand-merge, and also a merge over a file main deleted, which step 8 below forbids and which nothing reports.

Other programs that act on a checkout's state, each with its own test:

- `scripts/obsolete-file-edit-warning-hook.py` is the only other program that calls `head_state`; after each Edit or Write it warns when the edited file is older than main's copy, with advice by state (`NEVER_PUSHED_ADVICE`, `PUSHED_ADVICE`).
- `.claude/hooks/session-location-write-guard.py`, registered for Edit, Write and NotebookEdit, uses its own `head_state_of`. It refuses a write into the agent-session's own checkout while HEAD is detached, unless a rebase, merge, cherry-pick or revert is in progress or git ignores the file, and refuses a write into the reference checkout; either refusal lets one write through when `.location-write-approved` holds the user's approval. It does not see git commands, so `git switch -c <branch>` still runs: that is the way out of a detached checkout holding uncommitted work, after which the agent commits on the new branch.
- `scripts/force-push-with-open-pull-request-guard-hook.py`, registered for Bash, refuses `git push --force` or `--force-with-lease` to a branch that GitHub says has an open pull request (`open_pull_request_for_branch`). When GitHub cannot be asked within its 20-second budget, it lets the push through with a note. Its refusal says that if merge-lane-2 asked for the force-push, the agent may run the command again prefixed with `CLAUDE_MERGE_LANE_ASKED_FOR_THIS_REWRITE=1` (`ESCAPE_HATCH_VARIABLE`); the agent sets the variable itself, and the guard does not check that merge-lane-2 asked.

## Who may move what

| Action | Allowed when | Enforced by |
|---|---|---|
| Fast-forward a checkout | it has no own commits, no uncommitted tracked change and no git operation in progress | the freshness hook and the launch-time sync, which do it themselves |
| Rebase a branch | it has never been pushed, and none of its commits is on GitHub under another name | the freshness hook, which does it itself; nothing stops an agent's own rebase |
| Amend a commit | it has never been pushed (for a local commit on a pushed branch, see Question J) | nothing stops it; the freshness hook reports the divergence to the user once the amended branch differs from its remote branch of the same name, and misses an amend of commits pushed under another branch name |
| Merge main into a working branch | only the hand-merge `scripts/branch-conflict-check.py` asks for, including when GitHub reports a conflict that git does not | the freshness hook reports a merge whose parents re-merge cleanly |
| Push | after the suites the change can affect pass, when the push does not conflict with main, and once per fix-round | the pre-push hook refuses a push that conflicts with main; nothing runs the tests or counts the pushes |
| Force-push | never to a frozen-head (see Question D) | the force-push guard, for a branch with an open pull request only |
| Merge to main | merge-lane-2 after review, pinned to the reviewed head commit, or an agent-seat the user deputizes in that agent-seat's own session (working model R13) | `scripts/merge-gate.sh` prints the pinned merge command; GitHub's branch protection admits two accounts, `nedlern` and `ned-review-merge`, and requires one approving review (working model R12) |

## How a change reaches main

1. **Cut a topic branch from `origin/main`.** One feature or one bugfix per branch, which may take several commits. `git checkout -b <topic> origin/main`, or `git worktree add -b <topic> <path> origin/main`, works from any checkout. Nothing enforces the base: GHI [Topic-branch base enforcement: a branch-creation script and a gh pr create check that refuses an undeclared carry of another PR's commits](https://github.com/nedschorus/nedschorus/issues/238) proposes a script and a check, unbuilt.
2. **Work, and keep the branch current.** While the branch has never been pushed, the freshness hook rebases it onto main at a turn's end when the tree is clean; mid-work the tree is usually dirty, so the branch can fall behind until the agent commits.
3. **Run the selective test run before pushing:** `git fetch`, then `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`. CLAUDE.md asks for this; no program runs it.
4. **Push.** The pushed head commit is now a frozen-head. The pre-push hook runs `scripts/branch-conflict-check.py` against main and refuses a push that conflicts (`scripts/git-client-side-hooks-pre-push-conflict-check.py`). When the check itself cannot run, the push goes through.
5. **Open the pull request.** From now on the force-push guard also protects the branch.
6. **merge-lane-2 tests and reviews.** On ned-box, for every pull request that changes code, merge-lane-2 builds `wt/pr<N>-merged` at `origin/main` with `git merge --no-ff <head commit>`, never pushed, and runs `scripts/pull-request-head-test-run.py --checkout` on it; a conflict with main stops that merge before any review is commissioned. It then commissions the reviews the head commit needs and decides which findings block. When main moves with a code change before the merge, it rebuilds the merged worktree on the new main and reruns the tests; after each merge it runs every suite on main. A pull request that changes only prose gets no test run. This procedure lives in scripts in merge-lane-2's scratchpad (merge-lane-2's answer, 2026-10-09), not in the repository (Question B).
7. **Fix-round.** A review with findings starts a fix-round, one commit on top of the frozen-head, pushed once, written by a forked subagent. When the fix is made on a branch cut at the pushed head commit under another name, the `pushed-history` state, the commit reaches the pull request with `git push origin HEAD:<the pull request's branch>`.
8. **Conflict.** When `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`: if main deleted or replaced what the branch changes, the pull request is closed and what main still lacks is carried on a new branch; otherwise the author hand-merges main into the branch, with the frozen-head as first parent, plus at most one ordinary commit for an edit the resolution forces. When the branch conflicts at the moment a fix-round commit is pushed, the pre-push hook refuses the push until the hand-merge is made.
9. **Merge.** `scripts/merge-gate.sh` checks that an approving review covers the head commit, that GitHub's merge state allows the merge, and that no review or comment arrived since merge-lane-2 last read them, then prints the merge command pinned to the head commit with `--match-head-commit`. merge-lane-2 runs it. The gate does not check that tests ran.
10. **Clean up.** `scripts/clean-worktrees.py` removes a worktree under `<reference>/.claude/worktrees/` once it is merged (no commit outside `origin/main`), vacant (`worktree_vacancy_keep_reason`: no process has its working directory inside it) and, for a worktree the Agent tool made for a subagent, named `agent-<id>`, quiet (`agent_worktree_quiet_keep_reason`: neither the subagent's transcript nor the worktree's `.git` file written for an hour). Removal is `git worktree remove --force`, which discards any uncommitted, untracked or ignored files, each named in the report. It also deletes every branch fully merged into `origin/main` that no worktree has checked out (`branch_refs_with_no_worktree_fully_on_main`); no name is exempt, so a seat-branch is deleted whenever its agent-home is detached or on another branch. It runs daily at 06:30 on both machines, and at each session-handoff.

## Questions for the user

**Question A: does an agent-home rest on its seat-branch, or detached at main?** The documents say an agent-home is a worktree on its seat-branch: the glossary's agent-home entry, and `docs/agents/seat-first-prompt.md`, which tells the agent to stop if HEAD is detached. In practice the agent-homes of the agent-seats MD-skills and cold-read-research on the Mac are detached, put there by their own agents' `git checkout origin/main`, and MD-skills has no seat-branch: the cleaner's branch sweep (step 10) deletes a seat-branch whenever its agent-home is not on it.

- Shape 1, the seat-branch, as the documents say. Costs: the cleaner must exempt seat-branches; the launch-time sync must recreate a missing seat-branch and check it out; the freshness hook's detached message must say to switch back, and must tell an agent-home from other detached checkouts (scratchpad and review worktrees), which it cannot today. GHI [pull-request skill: how a change reaches main — durable-file disposition, the description, and topic-branch creation](https://github.com/nedschorus/nedschorus/issues/236) proposes cutting each topic branch from the seat-branch after fast-forwarding it; GHI 238's design measured that route on 2026-09-02 and dropped it as unsafe, because `git merge --ff-only origin/main` answers "Already up to date" when the branch is ahead, so stray commits carry into the next topic.
- Shape 2, detached at main as the resting state. The agent-home stays detached at main's newest commit, which the freshness hook and the launch-time sync now keep current; the write guard already refuses edits there; all work happens in topic branches cut with `git checkout -b <topic> origin/main` or in worktrees made with `git worktree add -b`. Costs: the glossary's agent-home entry, `docs/agents/seat-first-prompt.md`, the two launchers (`git worktree add --detach`) and GHI 236's procedure change; an agent that commits on the detached HEAD by mistake is told to make a branch, as today.

Recommendation: Shape 2. It matches how the live agent-homes already behave, it needs no exemption in the cleaner, and it rests on GHI 238's measurement rather than on the route that measurement dropped.

**Question B: merge-lane-2's merged-onto-main test lives outside the repository.** CLAUDE.md says merge-lane-2 "runs the same selection on the head commit merged onto main before merging", and step 6 shows it does. But the procedure lives in scripts in merge-lane-2's scratchpad, which a session-handoff can lose, and merge-lane-2's seat-brief (`nedlern@ned-box:~/agents/merge-lane-2/CLAUDE.local.md`) describes only the older worktree detached at the head. Recommendation: move the helper that builds and refreshes `wt/pr<N>-merged` into the repository as a program merge-lane-2 runs, and update its seat-brief to name it, so that the procedure survives a session-handoff.

**Question C: who rebases a never-pushed branch.** The freshness hook rebases it when the tree is clean. The initial-agent-instructions the handoff-supervisor gives an agent-session after a session-handoff also say "If this branch has never been pushed, rebase it onto origin/main before your first substantive action" (`BRANCH_STATE_INSTRUCTION`), and the obsolete-file warning, which fires after an edit, when the tree is dirty and the hook cannot rebase, says to commit and run `git rebase origin/main`. Recommendation: `BRANCH_STATE_INSTRUCTION` stops telling the agent to rebase and says the hook rebases a clean never-pushed branch at a turn's end; the warning keeps its instruction, because it fires exactly when the hook cannot act.

**Question D: what "frozen" means.** CLAUDE.md and the glossary freeze a head commit the moment it is pushed, and the freshness hook agrees. The force-push guard refuses a rewrite only while the branch has an open pull request. Recommendation: pushed, everywhere; the force-push guard refuses a force-push to any branch that exists on GitHub, keeping merge-lane-2's escape, so that a branch pushed before its pull request is opened is protected too.

**Question E: which worktrees are removed.** `scripts/clean-worktrees.py` considers only worktrees under `<reference>/.claude/worktrees/`. On the Mac on 2026-10-09, 24 worktrees under the agent-home of the agent-seat merge-lane-backlog and five scratchpad worktrees had no remover. Extending the cleaner meets cases no current test answers: ghi-info's checkout and merge-lane-2's `wt/main` are level with main and vacant between uses, so "merged and vacant" would remove them; a review worktree of a pull request closed without merging is never "merged"; the vacancy test cannot see a subagent working in a worktree, and the quiet test covers only `agent-<id>` worktrees; and `--force` discards uncommitted files. Recommendation, open in part: extend the cleaner to worktrees under agent-homes only, with the quiet test applied to every worktree it removes, and leave scratchpad, review and program worktrees to their owners; the user decides whether removal may discard uncommitted files, or must keep any worktree that holds them.

**Question F: subagents.** The freshness hook is registered for Stop only, not for SubagentStop (where `scripts/absence-claim-locator-reminder-hook.py` runs), so a subagent working in a worktree of its own is never told that main moved. A fix-round runs in a forked subagent; its branch is pushed and is never rebased, so for a fix-round only the telling matters. Two things are not known: whether a SubagentStop payload's `cwd` is the subagent's worktree or the parent's agent-home, as the cleaner's docstring says of an Agent-tool subagent; and whether the hook's output, which names its event `Stop`, is accepted on SubagentStop. Recommendation: register the freshness hook for SubagentStop only after a test shows which checkout the payload names; misbehaviour reports still go to the user's `systemMessage`.

**Question G: a branch behind its remote branch.** The `behind-remote` state text says "fast-forward to it before working here", but the advice given is to leave the branch alone, and nothing fast-forwards it; the hook reaches this state only when the branch is also behind `origin/main`. Recommendation: the hook fast-forwards such a branch to `origin/<branch>` when it has no local commits beyond `origin/<branch>` (which `behind-remote` already means) and no uncommitted tracked change, since no commit is rewritten; and it checks for this state whether or not the branch is behind `origin/main`.

**Question H: three questions merge-lane-2's review left open on PR [A detached checkout with no work of its own is moved forward to main, at launch and at each turn's end](https://github.com/nedschorus/nedschorus/pull/1110).**

- The reason a detached checkout is not moved can change after the agent acts: the agent commits away an uncommitted tracked change, and git then refuses over an untracked file. The `last_told` record keys on the branch and main's newest commit, so the new reason is not told until main moves, and a refusal over an untracked file is never told to the user. Recommendation: key the record on the reason too, so that a new reason is told at once.
- Two agent-sessions of the same agent-seat can share one checkout, and a move run by one changes files under the other. The cleaner's vacancy test cannot tell them apart: it always finds the hook's own agent-session in the checkout. Open, no recommendation: the design has no test that tells another agent-session from this one.
- The freshness hook has no `timeout` in `.claude/settings.json`, so Claude Code's default limit applies, which this design has not checked. In one run the hook can fetch twice (20 seconds each), re-merge each merge commit twice (60 seconds each), and fast-forward or rebase two checkouts (up to 120 seconds each). Recommendation: set a timeout above that total, so that the hook is never stopped part-way through a move.

**Question I: the pre-push test run.** CLAUDE.md asks every agent to run the selective test run before pushing; no program runs it, and GHI [Move mechanical agent chores into programs and hooks](https://github.com/nedschorus/nedschorus/issues/1036) row 1 proposes the pre-push hook run it. merge-lane-2's merged-onto-main test run (step 6) covers every code pull request before merge, though the merge gate does not check it. Recommendation: keep the instruction and leave it unenforced; the author's own run finds a failure one review round sooner, which is worth asking for but not worth a hook that slows every push.

**Question J: amending a local commit on top of a pushed head commit.** In the `pushed-with-local-commits` state, the hook tells the agent "Do not rebase or amend it", which also forbids amending the top commit, though that commit has never been pushed and no review covers it. Recommendation: allow amending only commits that are not on GitHub, since rewriting them changes nothing anyone has seen; the pushed commits beneath stay frozen.

## How this design changes, and what it does not cover

The design is updated in the same pull request as any change to a rule it states. It does not cover the main-gatekeeper of GHI [main-gatekeeper — the single check-in gate](https://github.com/nedschorus/nedschorus/issues/3), which is not in use, or the design-to-main state machine, which has its own design. On landing, it moves to `docs/issues/1121-git-checkouts-worktrees-and-branch-rules-design.md`, beside the GHI-MD of GHI [One design of record for the project's git checkouts, worktrees and branch rules](https://github.com/nedschorus/nedschorus/issues/1121).
