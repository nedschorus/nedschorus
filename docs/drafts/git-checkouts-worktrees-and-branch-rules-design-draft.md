## What a reader needs first

**Checkout, worktree, HEAD.** A git checkout is a directory holding the repository's files as of one commit, plus any changes made there since; git calls each such directory of a clone a worktree. The clone's first worktree is its main worktree; the others are linked worktrees made with `git worktree add`. HEAD is what a checkout stands on: a branch, such as `main`, or, when HEAD is detached, a commit named directly, with no branch. This design says "checkout" for the directory and "check out" only for the git action.

**Behind and ahead.** A checkout is behind main by the number of commits on `origin/main` that its HEAD lacks, and ahead by the number of commits its HEAD has that `origin/main` lacks. "Own commits" below means commits that are not on `origin/main`. `origin/<branch>` is the remote-tracking branch: this clone's record, from its last fetch or push, of the branch on GitHub; a plain `git fetch` keeps the record of a branch since deleted on GitHub until `git fetch --prune` removes it. A commit is pushed when some remote-tracking branch holds it after a `git fetch`: `git fetch`, then `git branch -r --contains <commit>` prints a name. The fetch brings this clone's record up to date, so a commit pushed from the other machine counts too. This is a definition for agents to apply, not a program's test. When the fetch fails, the agent treats the commit as pushed and its branch as having an open pull request, and so neither amends nor rebases it until a fetch succeeds; no program refuses the amend or the rebase.

**Moving a checkout forward.** Three git operations bring a checkout up to date, and they differ in what they risk:

- a fast-forward (`git merge --ff-only origin/main`) moves HEAD to `origin/main` when HEAD has no own commits, and rewrites no commit; it overwrites every tracked file main changed, and refuses rather than overwrite an uncommitted change to a tracked file or an untracked file (one git neither tracks nor ignores) at a path main adds; a file git ignores is overwritten;
- a rebase (`git rebase origin/main`) replays a branch's own commits on top of main, giving each replayed commit a new hash, unless the branch already sits on top of main, when nothing changes; git drops an own commit whose change main already holds;
- a merge (`git merge origin/main`) adds a merge commit joining the branch and main when each has commits the other lacks, fast-forwards when only main has new commits, and does nothing when main has none the branch lacks.

**Frozen-head and fix-round.** Both are project-terms the glossary defines. Decision 4 changes when a head commit is frozen: from when its pull request is open, not from when it is pushed, until the pull request merges or is closed (not yet in force: approval-walk on CLAUDE.md). While frozen it is never amended or rebased, and never force-pushed except when merge-lane-2 asks for the force-push (decision 18), because merge-lane-2 commissions its review against that commit. The glossary's frozen-head entry says "once pushed" and CLAUDE.md says a head commit "becomes a frozen-head the moment it is pushed"; the glossary changes in the Build item "Agent-homes detached at main", and CLAUDE.md in the approval-walk on CLAUDE.md that the agent-seats cold-read-improvement and fleet-restart-at-login are preparing (Corrections).

**The two machines.** The Mac and ned-box each have their own clone of the repository. A branch made in one clone reaches the other through GitHub: pushed from one, fetched by the other.

**Scratchpad.** Claude Code gives each agent-session a temporary directory of its own, its scratchpad: under `/private/tmp/claude-501/` on the Mac and `/tmp/claude-1000/` on ned-box. The operating system can empty these directories.

**The hooks and the launch-time sync.** The freshness hook is `scripts/checkout-freshness-catch-up.py`, a Claude Code Stop hook, run when a turn of an agent-session ends normally (not after an interrupted turn), on the checkout that holds the agent-session's working directory. The session-location write guard, the force-push guard and the edit warning hook below are Claude Code hooks too; a Codex run gets none of them, only the git hooks. The launch-time sync is `sync_working_branch_with_main` in `nc-systems/handoff/handoff-supervisor.py`: before each agent-session it starts or resumes, though not when it adopts an agent-session already running, the handoff-supervisor runs it on the agent-seat's agent-home. It fast-forwards the agent-home when it is strictly behind with no own commits, no uncommitted tracked change and no git operation in progress, and otherwise leaves it, with the reason in its `branch sync:` line. It also leaves an agent-home that is on a branch, and its `branch sync:` line says the agent-home is on a branch (not yet built: Build, agent-homes detached at main).

## What a checkout's HEAD can be, and what each program does

The freshness hook acts on the checkout that holds the agent-session's working directory, which is normally the agent-home; it sees a topic worktree only while the agent-session's working directory is there, as after Claude Code's EnterWorktree tool. So in the normal arrangement it never examines a topic branch, and the rows below from `unpushed` on apply only to an agent-session working inside a topic worktree. It fetches from GitHub at most every 300 seconds for each checkout (`DEFAULT_FETCH_INTERVAL_SECONDS`). It sorts a checkout with `head_state`, except that a checkout on `main` is handled as a reference checkout and a detached one by `move_detached_checkout_forward`. It tells the agent through `additionalContext` and the user through `systemMessage`. It tells the agent about a branch only when the branch is behind `origin/main`, once for each commit `origin/main` stands at (`drift_facts`).

After its Build item, the freshness hook gives an agent-facing-message about a checkout it left alone again when main moves or when the reason changes (not yet built: Build, freshness hook). It moves no branch except `main` in the reference checkout, and besides that fast-forwards only a detached checkout (not yet built: Build, freshness hook, which deletes `rebase_never_pushed_branch`). Its `timeout` in `.claude/settings.json` is set above the sum of its slowest steps, with the number of merge commits `merges_from_main` re-merges in one turn bounded so that the sum is finite; when Claude Code stops the hook at that limit, that turn's agent-facing-messages are lost (not yet built: Build, freshness hook; today the hook has no `timeout` entry).

After its Build item, the routine agent-facing-messages say "if this branch has an open pull request" rather than asking GitHub, and only the rewrite report below asks GitHub (not yet built: Build, freshness hook; today no message says so and the hook makes no GitHub call). The hook reaches `behind-remote` only when the branch is also behind `origin/main`; git's own refusal of a non-fast-forward push covers the cases the hook does not see.

At every turn's end the freshness hook also checks the checkout for two things an agent must not do, and reports each to the user:

- **A merge from main into the checkout's branch** whose two parents re-merge without a conflict (`merges_from_main`). A merge whose parents conflict when re-merged is not reported; that covers the allowed hand-merge, and also a merge over a file main deleted, which step 8 forbids and which nothing reports. A merge whose re-merges both fail to run is reported as forbidden today (`merge_parents_conflict` counts an error as no conflict); after its Build item the hook tells the agent it could not check that merge, and why, instead (not yet built: Build, freshness hook). A hand-merge that GitHub demanded although git can merge the parents cleanly is reported as forbidden; when the user asks the author about such a report, the author explains that GitHub demanded the hand-merge, and the fix of the hook goes on the freshness hook's task list then.
- **A rewritten frozen-head** (`head_state`'s `diverged-from-remote`). Today the hook reports every `diverged-from-remote` branch to the user, whether or not it has an open pull request; after its Build item the hook works as the rest of this item says (not yet built: Build, freshness hook). The hook first asks whether a commit that this branch once held locally is missing from HEAD: whether some commit in `HEAD..origin/<branch>` appears in the branch's own reflog (`git reflog <branch>`). If none does, the hook finds no sign that this clone's pushed commits were rewritten: most likely `origin/<branch>` advanced under commits made here, and the agent is told to rebase those commits onto `origin/<branch>`. If one does, the hook asks GitHub (`gh pr list --state open --head <branch>`) and reports the rewrite to the user only when the branch has an open pull request, since a rewrite before a pull request opens is allowed (not yet in force: approval-walk on CLAUDE.md). When either question cannot be answered, the hook tells the agent it could not check and why, and reports nothing. Three rewrites are not reported: one whose reflog entry has expired, after 30 days by git's default for an entry no longer reachable from the branch (`gc.reflogExpireUnreachable`), or whose branch was deleted, which deletes its reflog; one made from the other machine's clone; and one force-pushed within the same turn, which leaves HEAD equal to `origin/<branch>`, the `pushed` state. The force-push guard is the check for the last.

Other programs that act on a checkout's state:

- `scripts/obsolete-file-edit-warning-hook.py`, the edit warning hook, is the only other program that calls `head_state`; after each Edit or Write of a file inside the checkout that holds the agent-session's working directory, it warns when `origin/main` changed the file since the checkout's merge base with `origin/main`, with an agent-facing-message for each state. It says nothing about a file in any other checkout, so it is silent for an edit in a topic worktree made from the agent-home. Its agent-facing-messages give no rebase instruction and point an agent in an agent-home to a topic worktree (not yet built: Build, freshness hook).
- `.claude/hooks/session-location-write-guard.py`, the session-location write guard, registered for Edit, Write and NotebookEdit, uses its own `head_state_of`. It refuses such a call into the checkout that holds the agent-session's working directory while HEAD is detached, unless a rebase, merge, cherry-pick or revert is in progress or git ignores the file, and refuses one into the reference checkout; both refusals are user-blocks: each lets one call through when `.location-write-approved` holds the user's quoted approval. A write made by a Bash command is not checked. Its refusal in an agent-home names the command that makes a topic worktree, `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> origin/main`, and so does `docs/agents/seat-first-prompt.md` (not yet built: Build, agent-homes detached at main).
- `scripts/force-push-with-open-pull-request-guard-hook.py`, the force-push guard, registered for Bash, refuses `git push --force` or `--force-with-lease` to a branch that GitHub says has an open pull request (`open_pull_request_for_branch`). It lets the push through with an agent-facing-message when a `gh` call fails or takes longer than 10 seconds (`GH_TIMEOUT_SECONDS`, within a budget of 20 seconds for the whole run, `PROBE_BUDGET_SECONDS`), and lets every command through when its shell parser is missing or fails (`parser_unavailable_hook_output`). A push inside an ssh command, and a push of several branches in one command, are outside its scope. Its refusal says that if merge-lane-2 asked for the force-push, the agent may run the command again prefixed with `CLAUDE_MERGE_LANE_ASKED_FOR_THIS_REWRITE=1` (`ESCAPE_HATCH_VARIABLE`); the guard reads the prefix from the command itself, the agent writes it there, and the guard does not check that merge-lane-2 asked.
- The freshness hook does not run for a subagent: it is registered for Stop only, not for SubagentStop. A subagent's task is short, its branch is cut from current main or is a pushed fix-round branch, and the agent that dispatched it receives the hook's agent-facing-messages at its own turn's end.

## How a change reaches main

1. **Make a topic worktree from `origin/main`.** One feature or one bugfix per topic branch, which may take several commits. After a successful `git fetch`, `git worktree add -b <topic> ~/Projects/nedschorus/.claude/worktrees/<topic> origin/main` makes the branch and its worktree together, from any checkout. Then work in the topic worktree: run git and test commands there (start each with `cd <worktree> &&`, or use `git -C <worktree>`), because a command run from the agent-home acts on the agent-home; `python3 scripts/run-all-test-suites.py` names the runner by a relative path, so without the `cd` it runs the agent-home's copy against the agent-home, unless given `--checkout <worktree>`. The agent-home holds no topic work. A Claude Code hook, the worktree location hook, refuses an agent's `git worktree add` whose path is outside `~/Projects/nedschorus/.claude/worktrees/`; it also refuses Claude Code's EnterWorktree tool when the agent-session runs from an agent-home; each refusal names the command above (not yet built: Build, worktree location hook). Nothing makes a topic branch start at `origin/main`: GHI [Topic-branch base enforcement: a branch-creation script and a gh pr create check that refuses an undeclared carry of another PR's commits](https://github.com/nedschorus/nedschorus/issues/238) proposes a script and a check, unbuilt.
2. **Work.** No program moves the topic branch (not yet built: Build, freshness hook; today the freshness hook rebases a never-pushed topic branch while the agent-session's working directory is in its worktree). An agent may rebase a never-pushed branch onto `origin/main`, and need not: a conflict with main is refused at the push, unless the check cannot run or is skipped (step 4), and a merge without conflicts that breaks a tested behaviour is caught by merge-lane-2's test of the head commit merged onto main (step 6).
3. **Run the selective test run before pushing,** in the topic worktree: `git fetch`, then `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`. CLAUDE.md asks for this; no program runs it or checks it. The author's own run finds a failure before merge-lane-2's run would, and saves a review round, which is worth asking for but not worth a hook that slows every push.
4. **Push** with `git push -u origin <topic>`. The pre-push hook runs `scripts/branch-conflict-check.py` against main and refuses a push to `origin` that conflicts (`scripts/git-client-side-hooks-pre-push-conflict-check.py`). When the check cannot run or gives no answer, the push goes through, and `git push --no-verify` skips it. Until a pull request is open, the agent may still rewrite and force-push the branch (not yet in force: approval-walk on CLAUDE.md).
5. **Open the pull request.** The head commit is now a frozen-head (not yet in force: approval-walk on CLAUDE.md), and the force-push guard protects the branch.
6. **merge-lane-2 tests and reviews.** This step's program is not yet in the repository: the Build item "merge-lane-2's test program" adds and names it, and merge-lane-2's seat-brief names that program (not yet built: Build, merge-lane-2's test program); today merge-lane-2 does the test by hand. On ned-box, for every pull request that changes a file other than Markdown, merge-lane-2 runs that program. The program builds `wt/pr<N>-merged` at `origin/main` with `git merge --no-ff <head commit>`, never pushed, and runs `scripts/pull-request-head-test-run.py --checkout <that worktree>`. A conflict with main stops that merge before any review is commissioned; how merge-lane-2 then tells the author is settled with merge-lane-2 in that Build item. A failing test run blocks the merge. A failure merge-lane-2 or the user judges not worth fixing is cleared by a separate pull request that deletes the test, or skips it with its reason and a GHI that tracks it; the blocked pull request is then rerun, not cancelled. merge-lane-2 commissions the reviews the head commit needs and decides which findings block. When main moves with a change to a file other than Markdown before the merge, merge-lane-2 rebuilds the merged worktree on the new main and reruns the tests; after each merge it runs every suite on main.
7. **Fix-round.** Findings that hold are answered by a fix-round: one commit on top of the frozen-head, pushed once, written by a forked subagent; findings that do not hold are answered with the reason. When the fix is made on a branch cut at the pushed head commit under another name, the `pushed-history` state, the commit reaches the pull request with `git push origin HEAD:<the pull request's branch>`.
8. **Conflict.** When `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`, or GitHub reports a conflict that git does not: if main deleted or replaced what the branch changes, the pull request, if there is one, is closed, and what main still lacks is carried on a new topic branch; otherwise the author hand-merges main into the branch, with the frozen-head as first parent, plus at most one ordinary commit for an edit the resolution forces, pushed once. When the branch conflicts at the moment a fix-round commit is pushed, the pre-push hook refuses the push until the hand-merge is made. When a pull request comes to conflict with main after its review, merge-lane-2's merge onto main fails, the author clears the conflict with a hand-merge in a fix-round, and merge-lane-2 runs the tests and the review again.
9. **Merge.** `scripts/merge-gate.sh` checks that an approving review covers the head commit, that GitHub's merge state allows the merge, and that no review or comment arrived since merge-lane-2 last read them, then prints the merge command pinned to the head commit with `--match-head-commit`. merge-lane-2 runs it, as a merge commit, never a squash. Two gaps are known: `scripts/merge-gate.sh` does not check that the test run of step 6 ran or passed, and a review that arrives between `scripts/merge-gate.sh`'s check and the merge is not seen.
10. **Clean up.** `scripts/clean-worktrees.py`, the cleaner, runs daily at 06:30 on both machines, and at each session-handoff. Its rules ask nothing of GitHub. This step states the cleaner as its Build item makes it; of its rules below, only the subagent worktree's hour, the deletion of a fully merged branch with no worktree, and the removal with `--force` and its output are built (not yet built: Build, cleaner). Today the cleaner acts only on worktrees under `~/Projects/nedschorus/.claude/worktrees/`, ignores locks, removes a vacant worktree there whose branch has no own commits at its next run whatever it holds, keeps one with own commits, and deletes a branch only when it is fully merged. After its Build item it covers every worktree of the clone except the reference checkout and any worktree locked with `git worktree lock`, which it lists with its lock reason and never removes; it covers branches anywhere in the clone, and reports dead registrations.
    - Every agent-home is locked: the launchers lock it at every launch, and the cleaner's pull request locks every existing agent-home on both machines as a step at its merge, before the wider rule first runs. An agent-seat that keeps another worktree on purpose locks it itself; merge-lane-2's test program locks the `wt/main` worktree it builds.
    - Each unlocked worktree falls under the first of the next three rules that fits it, and is removed only if it is vacant, that is, no process has its working directory inside it (`worktree_vacancy_keep_reason`).
    - A subagent worktree, named `agent-<id>`, with no own commits, is removed when it is quiet (`agent_worktree_quiet_keep_reason`: neither the subagent's transcript nor the worktree's `.git` file written for an hour), whatever it holds.
    - A topic worktree with no uncommitted, untracked or ignored file (the disposable files `.DS_Store` and `__pycache__` aside, `DISPOSABLE_JUNK_BASENAMES`) and no own commits is removed once it has been quiet for an hour. The hour keeps a topic worktree made just before another agent-seat's session-handoff from being removed before its first edit.
    - Any other worktree, a subagent worktree with own commits included, is removed once nothing in it has changed for 30 days, whatever it holds. The 30 days count from the newest of: the modification time of each file a removal would discard and of each directory in the worktree (a deleted or added file changes its directory's), the worktree's `.git` file and git index, and the committer date of its branch tip, or of HEAD when HEAD is detached. The cleaner reads git with `--no-optional-locks`, so its own reads do not refresh the index and reset the clock. Its branch is deleted with it, merged or not.
    - A branch that no worktree has checked out is deleted when it is fully merged into `origin/main` (`branch_refs_with_no_worktree_fully_on_main`), or when its tip's committer date is more than 30 days old.
    - Before deleting an unmerged branch, or removing a detached worktree whose HEAD has own commits, whichever run does it, the cleaner appends the branch name or the worktree's path, its tip's hash and each own commit's subject to `~/.claude/daily-clean-worktrees.log` on that machine; when that line cannot be written, the branch or worktree is kept, the failure is reported, and the next run tries again. `git branch <name> <tip hash>` brings the commits back while git still holds them, and that window may be zero: git's garbage collection may prune them at its next run, because it prunes an object nothing refers to once the object file is older than its grace period of two weeks (`gc.pruneExpire`), and an object file is as old as the commit's arrival in this clone. A commit that GitHub, or the other machine's clone, still holds is not lost with this clone's copy. Otherwise only the clone's backups hold it: Time Machine on the Mac, whose schedule this design has not checked, and Timeshift on ned-box, which takes a snapshot every 10 minutes (`/etc/cron.d/timeshift-10min`), keeps each for about 24 hours, and beyond that keeps the daily, weekly and monthly snapshots its settings name, 7, 5 and 12 (`/etc/timeshift/timeshift.json`). The cleaner keeps no other copy.
    - Removal is `git worktree remove --force`, and the cleaner's output names the files a removal discards, at most 10 and then a count of the rest (`DISCARDED_FILES_NAMED_AT_MOST`). Uncommitted changes to tracked files and untracked files survive in the work-snapshot that `scripts/uncommitted-work-snapshot-hook.py` kept, if it kept one: it is listed in the initial-agent-instructions of the owning agent-seat's next agent-session, within the limits `nc-systems/handoff/uncommitted-work-snapshots-across-crashes-design.md` states, and deleted ten days after that first listing if nobody restores it. Files git ignores, such as walk-documents and walk-minutes (terms of `.claude/skills/skills-glossary.md`), survive only where a backup, a transcript or a copy shipped to the log-store caught them, which `scripts/find-deleted-path-across-backups.py` searches.

## How this design changes, and what it does not cover

The design is updated in the same pull request as any change in this repository to a rule it states; a change to a rule it states that is made outside the repository, such as to GitHub's branch protection, to git's or Claude Code's behaviour, or to a seat-brief, is brought into the design by the agent that notices it, in a pull request of its own. It does not cover the main-gatekeeper of GHI [main-gatekeeper — the single check-in gate](https://github.com/nedschorus/nedschorus/issues/3), which is not in use, or the design-to-main state machine, which has its own design. On landing, it moves to `docs/issues/1121-git-checkouts-worktrees-and-branch-rules-design.md`, beside the GHI-MD of GHI [One design of record for the project's git checkouts, worktrees and branch rules](https://github.com/nedschorus/nedschorus/issues/1121).
