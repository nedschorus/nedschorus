# Design: canary tests, when one is required, who runs it, and where it lives

Status: draft after its /cold-read, for the user's approval-walk. Everything under "Open questions" is undecided; everything else is proposed for approval. Nothing here is built.

## What a canary test is

A canary test runs a real outside program, such as Codex, Claude Code, git, cron or launchd, with throwaway inputs, to check whether behaviours of that program that the project's code relies on hold at the version installed on the machine that day: behaviours that the project's own tests replace with a test double or never run. A test of the project's code shows that the code does what we meant if the outside program behaves as we assume; a canary test shows whether the outside program behaves so. The canary runner gives its result as one of three hashtags: #canary_pass, #canary_fail, or #canary_no_answer when the run gave no answer. The author's report on a pull request may use two more, #canary_fail_elsewhere and #canary_unchecked, which only the author gives (see "When a canary test is required").

A canary test is a kind of contract test, the standard name for a test that a real outside program still behaves as the project's test doubles assume. It is neither a canary release, which sends a new version to a few users first, nor a canary token, a planted decoy secret; the fake credential files a canary test plants are called planted files. The design uses four terms, which the glossary is to list as the project-terms canary-test, scheduled-canary-test, one-shot-canary-test and canary-runner, and which this draft writes unhyphenated until it does: canary test, for both kinds; scheduled canary test and one-shot canary test, the two kinds (below); and canary runner, the script that runs both.

Example: PR [Cold-read cells: the Codex reviewer can write a report outside its checkout, and a missing report says why](https://github.com/nedschorus/nedschorus/pull/1200) relies on Codex's `--add-dir` making one more directory writable without lifting the deny entries that the permission profile places on credential files. The test suite of `nc-systems/cold-read/cold-read-codex-cell.py` runs a test double in place of Codex, which cannot show that. So before the merge an agent wrote a random string into planted files `probe.token` and `.env` in a new temporary directory, and `inside-added-dir.token` in a second one, ran `codex exec` twice with `--add-dir` pointing at the second, once under the credential-denying profile and once under `--sandbox workspace-write` as a control, and got PASS: the profile run never showed the string and could still write into the added directory, and the control run did show it. The run log is in the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/canary-temp-2026-10-12-codex-add-dir/codex-canary-run-transcript.txt`, and the result is the pull request's [comment of 2026-10-12](https://github.com/nedschorus/nedschorus/pull/1200#issuecomment-6130641752).

What exists today: canary tests run by hand, as PR 1200's was, with their results in pull request comments or a GHI-MD (GHI [The Codex review cell's commands run writable and without credential denials, because `codex exec review` drops the cell's permission profile](https://github.com/nedschorus/nedschorus/issues/804) records its measurement); one kept and scheduled, `nc-systems/handoff/uncommitted-work-snapshot-hook-real-claude-session-weekly-owner-check.py`, run weekly; and two test suites that run a live check only when given `--canary`, `scripts/session-statusline-command-test.py` and `nc-systems/handoff/tests/handoff-supervisor-successor-prompt-test.py`. Nothing says when a canary test is owed, how one runs, or where its files go. This design settles that.

## When a canary test is required

A change needs a canary test when both hold:

- the change makes the project's code newly rely on a behaviour of an outside program, such as honouring a flag, denying a read, firing a hook, or running a scheduled job; or changes how the code calls that program in a way that the behaviour it relies on could change; or depends on the text or format of the program's output; and
- no test in the repository runs that outside program for real in a way that checks that behaviour. Such a test counts, and is better than a canary test, because it runs again with every test run.

A change that neither newly relies on such a behaviour, nor changes the call in a way that behaviour could turn on, nor depends on the program's output, such as an edit to a prompt passed to an existing `codex exec` call, needs none.

The canary test runs the exact command the code uses, on each machine the code runs on. The author runs it before asking for the merge, and posts its result on the pull request as a comment that begins with one of five hashtags (see "How a result is reported"):

- #canary_pass: the behaviour holds;
- #canary_fail: the behaviour does not hold; the pull request then carries a commit that fixes the code or drops the reliance, and after a fix the author runs the canary test again and posts a new comment;
- #canary_fail_elsewhere: the canary test passes on one machine the code runs on but fails on another, such as one where another version of the outside program is installed; the author fixes the code, or asks the user;
- #canary_no_answer: the run gave no answer, because the outside program was signed out, a passing fault struck, or the test could not run; it is never a pass, and the author runs the canary test once more and then tells the user the cause;
- #canary_unchecked: the behaviour cannot be checked before a merge, such as one that shows only after a reboot, a login or an upgrade, or cannot be checked safely, because the run would use a real credential or change real shared state; the comment gives the reason, and merge-lane-2 judges it. A change to real shared state that an unsandboxed canary test declares and undoes, as "Writing an unsandboxed canary test" says, does not make a canary test unchecked; whether a credential limited to a place that holds nothing but test objects does is open question 12.

The latest comment counts. A pull request reviewer who finds such a dependence unchecked in code that CLAUDE.md's review scope covers asks for one, as a finding that blocks the merge; in an `-nbd` file, only when one of CLAUDE.md's four kinds of blocking finding for such a file applies.

When a scheduled canary test already checks the behaviour, the change needs no new canary test, but when the change touches the code that the scheduled canary test protects, the author runs that scheduled canary test by name before asking for the merge and reports the result on the pull request.

Until the canary runner is built, a canary test runs by hand, as PR 1200's did, and is reported the same way (open question 1).

## The two kinds

**A scheduled canary test** checks a behaviour of an outside program, as the project configures and calls it, that must keep holding, so that an upgrade of the outside program that breaks it shows in the next daily full test run that runs it. Example: the permission profiles the project builds for Codex with `codex_credential_denying_permission_profile_arguments` in `nc-systems/cold-read/cold-read-cell-common.py`, which the Codex cold-read-cells, the Codex sanity-check-cells and the Codex pull request reviewer `scripts/code-review-codex-cell.py` rely on, and which a Codex upgrade could change. A scheduled canary test is a test suite in the repository, and the daily full test run, `scripts/daily-full-test-run-of-main.py`, runs it on ned-box only until the check of GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) or the maintenance job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058) reads the Mac's daily record; from then on, on each machine the canary test's file declares. Until then nothing reads the Mac's record, so a failure there would reach no one.

**A one-shot canary test** answers one question about an outside program at one version, for one change, and is not kept in the repository. Its program, its run log and its result are kept in the log-store for 30 days, and then deleted. Example: a canary test showing that a flag does not do what a change assumed, after which the change takes another route.

When the behaviour a canary test checked must keep holding for the change to stay correct, the canary test is a scheduled canary test, and the change's author adds it in the same pull request. PR 1200's canary test ran before this design, and under it would have been a scheduled canary test; one of the first two scheduled canary tests, named under "Where canary tests live, and their names", asks its question again. A canary test stays one-shot when the change does not come to rely on the behaviour, or the change runs once, such as a migration.

A canary test of either kind is sandboxed unless the user approves it as an unsandboxed canary test (see "Writing an unsandboxed canary test"); what makes a canary test sandboxed is open question 10.

## Who runs it, and how

Every canary test, of either kind, is a program: one Python file that runs the outside program and prints what it checks. It runs through one repository script, the canary runner, which is not built yet and whose file name is chosen when it is. The canary runner is given the program's path, its kind, for a one-shot canary test its subject, and a timeout.

The canary test's program:

- prints the outside program's version before anything else, such as the output of `codex --version`, so that a later failure can be tied to an upgrade;
- prints each command it runs and that command's standard output and standard error, because the canary runner sees only what the program prints;
- opens, in its own code, no credential file except the planted files the canary runner made (below; how an unsandboxed canary test reaches a place that holds nothing but test objects is open question 12); what the outside program itself opens is what some canary tests check;
- when it has an answer, ends with a last standard-output line that is exactly `#canary_pass` or `#canary_fail`, and exits 0 with `#canary_pass` or 1 with `#canary_fail`.

The canary runner:

1. makes a new temporary directory for the run, and in it a throwaway home directory with planted files, each holding a random string of its own: one at each credential location that `codex_credential_denying_permission_profile_arguments` denies, `.ssh/`, `.config/nedschorus/`, `.config/gh/` and the sign-in files of Claude Code, Codex and agy, the third agent-binary, and `canary.token` and `.env` in the throwaway home directory, so that a string that shows in the run log names the file it leaked from;
2. starts the program in a process group of its own, with `HOME` set to the throwaway home directory, `TMPDIR` to a directory inside the run's temporary directory, and `CODEX_HOME` and `CLAUDE_CONFIG_DIR` to the real directories in the user's real home, such as `/home/nedlern/.codex` and `/home/nedlern/.claude` on ned-box, so that Codex and Claude Code reach their real sign-in;
3. writes the program's standard output and standard error, in the order printed, to the run log; the result is the program's last standard-output line when that line is `#canary_pass` with exit 0, or `#canary_fail` with exit 1; any other ending, such as no hashtag line, other text on that line, or an exit code that does not match, and a run stopped at its timeout, gives #canary_no_answer; at the timeout it stops the whole process group;
4. writes the run's files to the log-store on ned-box, over ssh when it runs on the Mac: for a one-shot canary test, the program, the run log and a result file into the canary test's directory (below); for a scheduled canary test, the run log into the test's run-log directory (below);
5. deletes the run's temporary directory, and exits 0 for #canary_pass and 1 for #canary_fail; it exits 2 for #canary_no_answer, or when the run could not be made, its files could not be written, or the temporary directory could not be deleted, printing which, with the result when there was one. When the run's files could not be written, it keeps the run's temporary directory, minus the throwaway home directory, and prints the one command that copies it to the log-store; the author runs that command once ned-box answers.

`codex_credential_denying_permission_profile_arguments` takes every path it denies from the home directory, through constants its module sets when it is loaded, so under the throwaway home directory it would deny only the planted files and leave the real `~/.ssh` and `~/.config/gh` readable by the Codex under test. The canary runner therefore passes that module the real home directory, and the module builds the deny list from both home directories. The list limits only the commands Codex runs, not Codex itself, so Codex still reads its own sign-in. `CODEX_HOME` pointed at the real directory also gives Codex the machine's real `config.toml`. On the Mac, Claude Code may keep its sign-in in the macOS Keychain rather than under `CLAUDE_CONFIG_DIR`; that is unchecked.

A temporary directory the program makes outside `TMPDIR` is the program's own to delete. A throwaway home directory does not stop a program from opening a real path; the canary test's own code opens no credential file except the planted files, and the outside program it runs, such as Codex or Claude Code, reads its own real sign-in, as it does in real use.

An agent working inside Codex, whether an agent-session, or a cold-read-cell, sanity-check-cell or pull request reviewer whose agent-binary is `codex`, runs the canary runner outside Codex's sandbox, because that sandbox would otherwise wrap the outside program under test, and everything that program starts, and change what the canary test sees; a canary test of a sandbox must start the outside program with the sandbox settings the test chooses. One rule lets the canary runner out: a `.rules` file in `~/.codex/rules/` on each machine, which the user adds, holds `prefix_rule(pattern=["<the canary runner's full path>", "run"], decision="allow")`, which matches that program only, with any arguments after `run`. The canary runner and everything it starts then run outside the sandbox, so the hole is only as small as the canary runner keeps it, by three limits:

- its `run` command accepts only the name of a scheduled canary test, and refuses any other argument;
- it runs that file as committed on main, never a working copy an agent could have edited; how a scheduled canary test not yet on main, or the code it protects as a pull request changes it, is run before the merge is open question 14;
- the canary runner itself runs from a copy agents cannot edit; how that copy is made is not settled yet.

A one-shot canary test is not on main, so the `run` command refuses it, and an agent inside Codex runs one by hand (how, and whether it still runs through the canary runner, is open question 13), after the user approves that canary test once, before its first run; a later run of the same file needs no new approval (see "Writing an unsandboxed canary test" for when the approval ends, and open question 10 for whether a one-shot canary test that makes no outside change needs one). Before anything uses the rule, one test, run once at the user's word, checks it: started from inside Codex, the canary runner must read a planted file that Codex's sandbox denies; another program must stay inside the sandbox; and the canary runner must refuse an extra argument, a file not on main, and an edited copy.

A Claude Code agent starts the canary runner directly. No Claude Code settings file on ned-box or on the Mac turns Claude Code's sandbox on, though on the Mac a default sandbox that allows the home directory is not ruled out. If a machine turns Claude Code's sandbox on, its hole is settled then, as Codex's is above.

Once the canary runner exists, nothing else runs a canary test, except that an agent inside Codex runs a one-shot canary test by hand.

## Writing an unsandboxed canary test

An unsandboxed canary test is a canary test that runs outside the agent-binary's sandbox, after the user approved it once before its first run; open question 10 asks whether this definition is replaced, because under it every canary test is unsandboxed. Its changes need not be undone perfectly, only enough that nothing it did causes a lasting conflict or issue. Follow these rules while writing it, not after a failed run.

1. Declare every outside change before you write the code. An outside change is anything the test changes beyond the run's temporary directory, which the canary runner makes for it: a file, an environment variable or setting, a change made through an API call or a web service, or a message. A call that only reads changes nothing and is not declared, and neither is anything inside the run's temporary directory, which the canary runner deletes after the run. In the test file, list each outside change with its class, its undo, and any residue the undo leaves with the reason that residue is harmless. The user approves this list, and the canary runner refuses to run an unsandboxed canary test whose file has no such list.
2. Classify each outside change. Restorable: its prior state can be saved and put back, such as a setting read before it is written, or an object created and then deleted. Compensable: it cannot be removed, but a further call cancels its effect, such as revoking a token, closing an issue the test opened, or a cancellation message after a test message. Irreversible: someone or something outside the project may act on it before an undo can run.
3. Make no irreversible change. A message to anyone or anywhere outside the project is irreversible, so send messages only to places the project owns and only the project's agents and the user read, with the label from rule 7 in the text. Where a service has a test mode that still exercises what the canary test checks, use it.
4. Register each undo on a last-in-first-out cleanup stack, such as Python's `contextlib.ExitStack`, so it runs even when the test fails: for a restorable setting or file, just before the change; for a created object, as soon as the service returns its identifier.
5. For a restorable change, save the prior value first; if the thing did not exist, the undo deletes it. Restore only what the test changed, so another agent's change made meanwhile survives.
6. Delete or cancel what the test created by the identifier the service returned, never by name or age alone. The one search-based deletion allowed is rule 9's, and only in a place that holds nothing but test objects.
7. Label every object and message the test creates with `nedschorus-canary-test`, the test's name, and the run's identifier, which the canary runner gives the test, in a field a script can search.
8. Do remote work only in a place that holds nothing but test objects, such as a dedicated test repository; how the test reaches that place under the throwaway home directory is open question 12.
9. At its start, the test removes its own leftovers from an earlier run, found by the label and its own name, in such a place. This also catches an object whose creation failed before the service returned its identifier, so rule 4 never registered its undo.
10. Every undo tolerates "already gone", and every undo is attempted even after one fails. Residue the list declares is accepted; an undo that fails outright is printed by name and makes the test end with `#canary_fail`, so the user sees what was left; open question 11 asks whether a failed undo is reported otherwise, because `#canary_fail` elsewhere means that the behaviour does not hold.
11. Do not count on a snapshot of Timeshift, the system snapshot tool installed on ned-box, to undo anything: by default Timeshift leaves home directories out, and restoring one would also undo every other agent's work since the snapshot.

The user's approval ends when the test's file, or repository code it imports, changes, or when the test makes an outside change its list does not declare.

## Where canary tests live, and their names

**Scheduled:** one file in the repository, the canary test's program, in the `tests/` directory of the system whose code relies on the behaviour, beside that system's other test suites, or in `scripts/` when that code is a program in `scripts/`, named `<the outside program>-<the behaviour>-canary-test.py`. The file declares, in constants, its time limit and the machines it runs on. With four changes to the test runner and one to an installer, none made yet, it runs as follows:

- the test runner, `scripts/run-all-test-suites.py`, starts each file whose name ends `-canary-test.py` through the canary runner, outside the test runner's signal sandbox, one at a time, with the time limit the file declares as the canary runner's timeout, even below `TEST_SUITE_TIMEOUT_FLOOR_SECONDS`, 600 seconds, the floor of the test runner's own time limit for a suite;
- the test runner skips such a file in a selective run, such as the one before a push, unless the run names it, and says so; the daily full test run runs it;
- the test runner skips such a file on a machine the file does not declare, and says so;
- the test runner gains an option to run named suites only, with which the author runs a scheduled canary test by name before the merge;
- `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py` gives ned-box's cron jobs a PATH, as it gives the Mac's launchd jobs, so that a canary test run by the daily full test run finds `claude`, `agy` and `codex`.

The first two scheduled canary tests check how Codex applies the permission profile that `codex_credential_denying_permission_profile_arguments` builds to keep Codex's commands away from credential files, because Codex is upgraded outside the project and nothing else checks either behaviour again; neither file exists yet:

- `nc-systems/cold-read/tests/codex-add-dir-credential-deny-canary-test.py` checks that the report directory the Codex cold-read-cell, `nc-systems/cold-read/cold-read-codex-cell.py`, adds with `--add-dir` still leaves every credential file the profile denies unreadable; PR 1200 checked this by hand once, on codex-cli 0.159.3;
- `scripts/codex-exec-review-profile-after-review-canary-test.py` checks that the profile the Codex pull request reviewer, `scripts/code-review-codex-cell.py`, places after the word `review` in its `codex exec review` command still applies; GHI 804 measured on codex-cli 0.156.0 that a profile placed before that word is dropped.

The daily full test run runs both on ned-box.

The canary runner writes the log of every run of a scheduled canary test, whether the daily full test run started it or an author ran it by name before a merge, to `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/scheduled/<machine>/<YYYY-MM-DD>T<HHMMSS>-<suite path with each / as __>.txt`, where `<machine>` is the machine that ran it, ned-box for now, and the date and time are in America/Los_Angeles at the run's start; the log's first line is the full hash of the commit it ran at. For example, a run on ned-box at 03:15:07 on 2026-11-02 writes `canaries/scheduled/ned-box/2026-11-02T031507-nc-systems__cold-read__tests__codex-add-dir-credential-deny-canary-test.py.txt`. These logs exist because the daily full test run's record names each suite that failed, not each that passed, and keeps each suite's output only in `/var/tmp/nedschorus-daily-full-test-run-of-main/logs/` on ned-box, which the next day's run replaces; without them, nothing would show what a failed canary test printed on its previous run, such as the outside program's version. The test's program is already in the repository, so each run keeps one file, not a directory.

**One-shot:** a directory in the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/one-shot/<YYYY-MM-DD>-<subject>/`, where the date is the date in America/Los_Angeles when the run started, as the daily full test run dates its records, and the subject names the outside program and the behaviour, such as `2026-10-12-codex-add-dir`; a second run with the same date and subject adds `-2`, then `-3`. The directory holds the canary test's program, its run log and its result file. Deletion goes by the date in the name alone: no database table, and no index file. PR 1200's directory, `canaries/canary-temp-2026-10-12-codex-add-dir/`, keeps its name and is deleted by the same rule.

## How a result is reported

**One-shot:** the author posts the result on the pull request that needed it, or, for a change with no pull request, on the GHI that asked for it, as a comment that begins with the result's hashtag and gives the machine, the outside program's version, what was run and what was seen, in a table when there is a control run, and cites the run log in the log-store. The comment stands on its own: the run log is deleted after 30 days, and the comment is what remains. PR 1200's comment of 2026-10-12 is the example to follow.

**Scheduled, before its merge:** the author runs the new scheduled canary test by name on each machine it applies to and posts the results as for a one-shot canary test.

**Scheduled, after its merge:** the daily full test run's record, `nedlern@ned-box:/home/nedlern/nedschorus-logs/daily-full-test-runs/<machine>/<YYYY-MM-DD>.txt`, like any other test suite. The test runner prints a FAIL line for a canary test whose canary runner exits with any code but 0, and the line gives that exit code, which stands for a result hashtag. Exit 1 is #canary_fail: the outside program, or the project's way of calling it, no longer behaves as the code relies on; whoever investigates compares the run log with the previous one, including the version line, before saying which. Exit 2 is #canary_no_answer, or files not written, and says nothing about the outside program: whoever investigates reads the cause the canary runner printed, runs the test once more, and then reports the cause to the user. When `codex` refuses to run under cron because it is signed out or has reached its usage limit, the canary test's program prints that cause and no hashtag line, so the run is #canary_no_answer, exit 2, not #canary_fail. Who carries a failed canary test on either machine to the user is open question 2.

## How a canary test is removed

Each one-shot canary test's directory, and each scheduled canary test's run log, is deleted once more than 30 days have passed since the date in its name, by a scheduled job on ned-box, run daily and listed in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`. It deletes each `canaries/one-shot/<date>-*` directory, each old `canaries/canary-temp-<date>-*` directory, and each `canaries/scheduled/<machine>/<date>T*` file more than 30 days old, and prints what it deleted, because deleting by a date in a name needs no agent. A scheduled canary test is removed like any test suite, in a pull request that says why the behaviour no longer matters.

## Build

1. The pull request that adds the first two scheduled canary tests, `nc-systems/cold-read/tests/codex-add-dir-credential-deny-canary-test.py` and `scripts/codex-exec-review-profile-after-review-canary-test.py`, also builds the canary runner, makes the five changes listed under "Where canary tests live, and their names", and makes `codex_credential_denying_permission_profile_arguments` build its deny list from both home directories ("Who runs it, and how"); from its merge, the daily full test run runs both canary tests on ned-box, and the canary test a change needs no longer runs by hand, except a one-shot canary test that an agent inside Codex runs.
2. Before an agent inside Codex uses the canary runner, the user adds the `.rules` file's rule on that machine and the one test of the rule under "Who runs it, and how" passes.
3. Whoever builds the check of GHI 1206 or the maintenance job of GHI 1058, whichever first reads the Mac's daily record, also turns on the Mac's scheduled canary tests.
4. The pull request of Build step 1 also adds the scheduled job under "How a canary test is removed".

## Open questions

1. **Until the canary runner is built.** The canary runner is built in the pull request of Build step 1, and running by hand the canary test a change needs ends when that pull request merges. Recommendation: from the day this design is approved until that merge, a change that needs a canary test gets one run by hand, reported as a one-shot result; an agent inside Codex runs it after the user approves that canary test once, before its first run, as "Who runs it, and how" says.
2. **Who tells the user when a scheduled canary test fails.** Today merge-lane-2 reads ned-box's newest daily record at each session start, and no other channel carries a failed record to the user; no one reads the Mac's. GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) plans that channel. Recommendation: on the Mac, the check of GHI 1206 or the maintenance job of GHI 1058, whichever first reads the Mac's record; until then scheduled canary tests run on ned-box only, as "The two kinds" says.
3. **What deletes the one-shot directories and the scheduled run logs.** Decided: see "How a canary test is removed".
4. **The weekly real Claude session check and the status line `--canary` suite.** Decided 2026-10-27: `nc-systems/handoff/uncommitted-work-snapshot-hook-real-claude-session-weekly-owner-check.py`, a weekly scheduled job that starts `claude` itself and ends with `VERDICT: PASSED` or `VERDICT: FAILED`, and `scripts/session-statusline-command-test.py`, which runs its live check only when given `--canary` and a status line payload captured by hand, stay as they are until the canary runner exists; then the canary runner's builder asks the user, for each, whether it becomes a scheduled canary test.
5. **Canary tests of cron and launchd.** Folded into open question 9.
6. **How an unsandboxed canary test's list of outside changes is written.** How the list is written in the test file, and how the canary runner reads it; with it, how the canary runner tells an unsandboxed canary test from a sandboxed one, and how it gives the test the run's identifier that rule 7 asks for; settled when the canary runner is built.
7. **How the user's approval of an unsandboxed canary test is recorded.** How the canary runner checks the approval and the imported code; settled when the canary runner is built.
8. **How an undeclared outside change is noticed.** The canary runner can check some things, such as whether branches moved, and any agent that notices one reports it to the user; settled when the canary runner is built.
9. **Leftovers of a test killed before its undo ran.** What removes the leftovers of a test killed before its undo ran, whether they are remote objects or changes on the machine, such as a job in the real user's crontab or launchd, which the start-of-run cleanup of rule 9 does not search; for example, whether a small janitor on ned-box deletes labelled leftovers older than a day; settled when the first test that leaves such leftovers is written. The starting point for a canary test of cron or launchd: the canary runner runs one program and waits for it, while cron and launchd run a job later, outside that program, and in the real user's crontab or launchd whatever the home directory is; so such a test installs a throwaway job that writes a file, writes the job's identity to a file in the run's temporary directory before installing it, and waits for the file within a wait shorter than its timeout; the canary runner removes the job named in that file after the program ends or is stopped; a job that fires at login is loaded to run at once; and `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py --check` reports a job left behind.
10. **What makes a canary test sandboxed.** On 2026-10-19 the user proposed two kinds of canary test, sandboxed by default and unsandboxed with his permission, and approved the eleven rules under "Writing an unsandboxed canary test". The definition under "Writing an unsandboxed canary test", a canary test that runs outside the agent-binary's sandbox, fits every canary test: the canary runner and everything it starts run outside Codex's sandbox through the `.rules` file's rule, and no settings file on ned-box or on the Mac turns Claude Code's sandbox on. Two readings fit the user's words. By what the test changes: a sandboxed canary test makes no outside change, as rule 1 defines one, and needs no approval; an unsandboxed one declares at least one, and needs the user's approval before its first run; a one-shot canary test that an agent inside Codex runs by hand and that makes no outside change then needs no approval from the user. By where the test runs: a sandboxed canary test runs inside a sandbox the canary runner starts for it, such as the sandbox that `credential_sandbox_prefix` in `nc-systems/cold-read/cold-read-agy-cell.py` builds for agy, bwrap on ned-box and sandbox-exec on the Mac, and an unsandboxed one does not; every one-shot canary test run by hand from inside Codex is then unsandboxed. Recommendation: by what the test changes, so the definition reads "An unsandboxed canary test is a canary test whose file declares at least one outside change (rule 1); it runs only after the user approved it once before its first run." The user drew the line by effect on 2026-10-19 ("the sandbox is just a bunch of files"), the eleven rules he approved sort outside changes, and the canary runner can refuse a test whose file declares an outside change without approval, without building and testing a second sandbox around Codex and Claude Code.
11. **What a failed undo reports.** Rule 10 makes a test whose undo failed end with `#canary_fail`, which everywhere else in this design means that the outside program's behaviour does not hold, and whose exit 1 sends whoever investigates to compare the outside program's versions; a failed undo says nothing about the outside program. Step 5 of the canary runner already reports its own failed clean-up without changing the result: a temporary directory it could not delete gives exit 2, with the result printed. Recommendation: a failed undo is reported the same way: the test prints each undo it could not do, by name, and its last line still says whether the behaviour held; the canary runner exits 2 and prints that an undo failed, so the user sees what was left; how the test tells the canary runner is settled with open question 6. A failed undo also ends the user's approval of the test, because what it left is an outside change the list does not declare, and on 2026-10-19 the user said that a test that "does something that is hard to fix or hard to recover from" would have to be approved again, while doubting that "bad" could be defined well enough for that.
12. **How an unsandboxed canary test reaches a test-only place.** The user's message of 2026-10-19 counts API calls, web services and messages among the changes an unsandboxed canary test may make and undo, and rules 3, 8 and 9 send such work to a place that holds nothing but test objects, such as a dedicated test repository. But the canary runner sets `HOME` to the throwaway home directory, whose credential files are planted, so `gh` there has no real sign-in; the test's own code opens no credential file except the planted files (item 26 of approval-walk md-skills-seat-open-decisions-2026-10-15, approved 2026-10-19; its walk-minutes are `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/md-skills-seat-open-decisions-2026-10-15-minutes.md`); and #canary_unchecked covers a run that "would use a real credential or change real shared state". Recommendation: an unsandboxed canary test's list of outside changes also names each credential the test needs, one whose only access is the test-only place, such as a GitHub token for the dedicated test repository alone; the user approves the credential with the list; the canary runner passes it to the test in an environment variable, so the throwaway home directory and the planted files stay, and no credential the project's own work uses reaches the test. #canary_unchecked then covers a canary test that would need any other real credential, or change shared state outside a test-only place.
13. **How an agent inside Codex runs a one-shot canary test.** "Who runs it, and how" gives the canary runner a one-shot canary test's path and subject, but its `run` command, the only one the `.rules` rule lets out of Codex's sandbox, refuses anything but the name of a scheduled canary test; and "by hand" does not say whether such a run still gets the throwaway home directory, the planted files, the deny list built from both home directories and the run's files in the log-store, which only the canary runner provides. Recommendation: the canary runner has a second command for a one-shot canary test, which the rule does not match; an agent inside Codex starts that command through Codex's request to run a command outside its sandbox, which the user approves before the canary test's first run, so the run gets everything the canary runner gives a scheduled canary test; "by hand" means only that the user's approval, not the rule, lets the run out.
14. **How a scheduled canary test is run before its merge.** "When a canary test is required" has the author run a scheduled canary test by name before the merge of a change to the code it protects, and "How a result is reported" has the author run a new scheduled canary test before its own merge; but the `run` command runs a file only as committed on main, so it cannot run a new scheduled canary test, and it runs main's copy of the protected code, not the pull request's. Recommendation: before the merge, the author runs the pull request's copy of the scheduled canary test through the canary runner's one-shot command of open question 13, and reports the result as for a one-shot canary test; the `run` command keeps its limit to main, and runs scheduled canary tests only for the daily full test run.
