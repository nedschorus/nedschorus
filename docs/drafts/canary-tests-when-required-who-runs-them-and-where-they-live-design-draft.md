# Design: canary tests, when one is required, who runs it, and where it lives

Status: draft after its /cold-read, for the user's approval-walk. Everything under "Open questions" is undecided, and so is the name "canary test" itself (open question 1); everything else is proposed for approval. Nothing here is built.

## What a canary test is

A canary test runs a real outside program, such as Codex, Claude Code, git, cron or launchd, with throwaway inputs, to check whether behaviours of that program that the project's code relies on hold at the version installed on the machine that day: behaviours that the project's own tests replace with a test double or never run. A test of the project's code shows that the code does what we meant if the outside program behaves as we assume; a canary test shows whether the outside program behaves so. Its verdict is PASS, FAIL, or no verdict when the run gave no answer.

Example: PR [Cold-read cells: the Codex reviewer can write a report outside its checkout, and a missing report says why](https://github.com/nedschorus/nedschorus/pull/1200) relies on Codex's `--add-dir` making one more directory writable without lifting the deny entries that the permission profile places on credential files. The test suite of `nc-systems/cold-read/cold-read-codex-cell.py` runs a test double in place of Codex, which cannot show that. So before the merge an agent wrote a random string into planted files `probe.token` and `.env` in a new temporary directory, and `inside-added-dir.token` in a second one, ran `codex exec` twice with `--add-dir` pointing at the second, once under the credential-denying profile and once under `--sandbox workspace-write` as a control, and got PASS: the profile run never showed the string and could still write into the added directory, and the control run did show it. The run log is in the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/canary-temp-2026-10-12-codex-add-dir/codex-canary-run-transcript.txt`, and the result is the pull request's [comment of 2026-10-12](https://github.com/nedschorus/nedschorus/pull/1200#issuecomment-6130641752).

What exists today: canary tests run by hand, as PR 1200's was, with their results in pull request comments or a GHI-MD (GHI [The Codex review cell's commands run writable and without credential denials, because `codex exec review` drops the cell's permission profile](https://github.com/nedschorus/nedschorus/issues/804) records its measurement); one kept and scheduled, `nc-systems/handoff/uncommitted-work-snapshot-hook-real-claude-session-weekly-owner-check.py`, run weekly; and two test suites that run a live check only when given `--canary`, `scripts/session-statusline-command-test.py` and `nc-systems/handoff/tests/handoff-supervisor-successor-prompt-test.py`. Nothing says when a canary test is owed, how one runs, or where its files go. This design settles that.

## When a canary test is required

A change needs a canary test when both hold:

- the change makes the project's code newly rely on a behaviour of an outside program, such as honouring a flag, denying a read, firing a hook, or running a scheduled job, or changes how the code calls that program in a way that the behaviour it relies on could change; and
- no test in the repository runs that outside program for real in a way that checks that behaviour.

A change that does neither, such as an edit to a prompt passed to an existing `codex exec` call, needs none.

The requirement is met when the canary test's verdict is PASS, or when it is FAIL and the change no longer relies on the behaviour. A run with no verdict meets nothing. The author runs the canary test before asking for the merge. A pull request reviewer who finds such a dependence unchecked in code that CLAUDE.md's review scope covers asks for one, as a finding that blocks the merge; in an `-nbd` file, only when CLAUDE.md's three blocking kinds apply.

When a permanent canary test already checks the behaviour, the change needs no new canary test, but when the change touches the code that the permanent canary test protects, the author runs that permanent canary test by name before asking for the merge and reports the result on the pull request.

Until the canary runner is built, a canary test runs by hand, as PR 1200's did, and is reported the same way (open question 2).

## The two kinds

**A permanent canary test** checks a behaviour of an outside program, as the project configures and calls it, that must keep holding, so that an upgrade of the outside program that breaks it shows in the next daily full test run that runs it. Example: the permission profiles the project builds for Codex with `codex_credential_denying_permission_profile_arguments` in `nc-systems/cold-read/cold-read-cell-common.py`, which the Codex cold-read-cells, the Codex sanity-check-cells and the Codex pull request reviewer `scripts/code-review-codex-cell.py` rely on, and which a Codex upgrade could change. A permanent canary test is a test suite in the repository, and the daily full test run, `scripts/daily-full-test-run-of-main.py`, runs it on each machine it applies to.

**A one-shot canary test** answers one question about an outside program at one version, for one change, and is not kept in the repository. Its program, its run log and its verdict are kept in the log-store for 30 days, and then deleted. Example: a canary test showing that a flag does not do what a change assumed, after which the change takes another route.

When the behaviour a canary test checked must keep holding for the change to stay correct, the canary test is permanent, and the change's author adds it in the same pull request. PR 1200's canary test ran before this design; under it, its question would be permanent, and open question 7 proposes it as the first permanent canary test. A canary test stays one-shot when the change does not come to rely on the behaviour, or the change runs once, such as a migration.

## Who runs it, and how

Every canary test, of either kind, is a program: one Python file that runs the outside program and prints what it checks. It runs through one repository script, the canary runner, which is not built yet and whose file name is chosen when it is. The canary runner is given the program's path, its kind, for a one-shot canary test its subject, and a timeout.

The canary test's program:

- prints the outside program's version before anything else, such as the output of `codex --version`;
- prints each command it runs and that command's output, so that the run log shows what was run and what was seen;
- never opens a real credential file or directory; it reads only the planted files the canary runner made (below);
- ends by printing `VERDICT: PASS` or `VERDICT: FAIL` as the last line of its standard output, and exits 0 on PASS and 1 on FAIL.

The canary runner:

1. makes a new temporary directory for the run, and in it a throwaway home directory with planted files: at each credential location that `codex_credential_denying_permission_profile_arguments` denies, `.ssh/`, `.config/nedschorus/`, `.config/gh/` and the sign-in files of Claude Code, Codex and agy, and as `canary.token` and `.env` in the throwaway home directory, a file holding a random string of its own, so that a string that shows in the run log names the file it leaked from;
2. starts the program in a process group of its own, with `HOME` set to the throwaway home directory and `TMPDIR` to a directory inside the run's temporary directory, and with Codex and Claude Code reaching their real sign-in files in the way open question 5 settles;
3. writes the program's standard output and standard error, in the order printed, to the run log; the verdict is the program's last standard-output line when that line is `VERDICT: PASS` with exit 0, or `VERDICT: FAIL` with exit 1; anything else, or a run stopped at its timeout, is no verdict; at the timeout it stops the whole process group;
4. writes the run's files to the log-store on ned-box, over ssh when it runs on the Mac: for a one-shot canary test, the program, the run log and a verdict file into the canary test's directory (below); for a permanent canary test, the run log as open question 8 settles;
5. deletes the run's temporary directory, and exits 0 on PASS and 1 on FAIL; it exits 2 when the run could not be made, gave no verdict, its files could not be written, or the temporary directory could not be deleted, printing which, with the verdict when there was one. When the run's files could not be written, it keeps the run's temporary directory, minus the throwaway home directory, and prints the one command that copies it to the log-store; the author runs that command once ned-box answers.

A temporary directory the program makes outside `TMPDIR` is the program's own to delete. A throwaway home directory does not stop a program from opening a real path; the program's rules above are what keep a canary test away from real credentials, and the outside program reads its own sign-in files as it does in the project's real use.

An agent working inside Codex, whether an agent-session, or a cold-read-cell, sanity-check-cell or pull request reviewer whose agent-binary is `codex`, runs the canary runner outside Codex's sandbox, because that sandbox would otherwise wrap the outside program under test and change what the canary test sees; a canary test of a sandbox must start the outside program with the sandbox settings the test chooses. One rule in Codex's execpolicy `.rules` files on each machine, which the user adds, lets the canary runner's command run outside Codex's sandbox; whatever program the canary runner is handed runs there too, so the rule confines the command, not the code that runs. How that rule is written is open question 3, and how a Claude Code agent-session leaves its own sandbox to run the canary runner is open question 4. Once the canary runner exists, nothing runs a canary test any other way.

## Where canary tests live, and their names

**Permanent:** one file in the repository, the canary test's program, in the test directory of the system whose code relies on the behaviour, beside that system's other test suites, named `<the program that relies on the behaviour>-<the behaviour>-canary-test.py`; the first, for example, would be `nc-systems/cold-read/tests/cold-read-codex-cell-credential-deny-canary-test.py`, which does not exist yet. How the test runner, `scripts/run-all-test-suites.py`, starts it is open question 6.

**One-shot:** a directory in the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/one-shot/<YYYY-MM-DD>-<subject>/`, where the date is the date in America/Los_Angeles when the run started, as the daily full test run dates its records, and the subject names the outside program and the behaviour, such as `2026-10-12-codex-add-dir`; a second run with the same date and subject adds `-2`, then `-3`. The directory holds the canary test's program, its run log and its verdict file. Deletion goes by the date in the name alone: no database table, and no index file. PR 1200's directory, `canaries/canary-temp-2026-10-12-codex-add-dir/`, keeps its name and is deleted by the same rule.

## How a result is reported

**One-shot:** the author posts the result on the pull request that needed it, or, for a change with no pull request, on the GHI that asked for it, as a comment that says PASS, FAIL or NO VERDICT, the machine, the outside program's version, what was run and what was seen, in a table when there is a control run, and cites the run log in the log-store. The comment stands on its own: the run log is deleted after 30 days, and the comment is what remains. PR 1200's comment of 2026-10-12 is the example to follow.

**Permanent, before its merge:** the author runs the new permanent canary test by name on each machine it applies to and posts the results as for a one-shot canary test.

**Permanent, after its merge:** the daily full test run's record, `nedlern@ned-box:/home/nedlern/nedschorus-logs/daily-full-test-runs/<machine>/<YYYY-MM-DD>.txt`, like any other test suite. A FAIL line there for a canary test means the suite exited nonzero: exit 1 is a FAIL verdict, and exit 2 means no verdict, or files not written. A FAIL verdict means the outside program, or the project's way of calling it, no longer behaves as the code relies on; whoever investigates compares the run log with the previous one, including the version line, before saying which. Who carries a failed canary test on either machine to the user is open question 9.

## How a canary test is removed

A one-shot canary test's directory is deleted once more than 30 days have passed since the date in its name, by the mechanism open question 10 settles. A permanent canary test is removed like any test suite, in a pull request that says why the behaviour no longer matters.

## Open questions

1. **The name.** "Canary" means other things in software engineering: a canary release sends a new version to a few users first, and a canary token is a planted decoy secret, which is how GHI 804 used the word for its planted files. The standard term for this design's permanent kind is a contract test, a test run on a schedule that checks a real outside service still behaves as the project's test doubles assume; its one-shot kind is what the standard vocabulary calls a learning test. Recommendation: the project-term outside-program-contract-test, in the glossary, with the two kinds as permanent and one-shot outside-program-contract-tests, the canary runner named for it, and the log-store directory `outside-program-contract-tests/`. The alternative is to keep the word as the project-term canary-test, hyphenated, in the glossary. Until the user rules, this draft says "canary test", and the planted files are called planted files.
2. **Until the canary runner is built.** Recommendation: from the day this design is approved, a change that needs a canary test gets one run by hand, at the user's word for an agent inside Codex, reported as a one-shot result; the rest of "Who runs it, and how" applies from the day the canary runner lands.
3. **The one rule in Codex's execpolicy `.rules` files.** `codex exec --help` names the files (its `--ignore-rules` flag skips "user or project execpolicy `.rules` files"); where they live, and which form of rule lets the canary runner's command, and only that command, start outside the sandbox, has not been measured. Recommendation: measure it once, before the canary runner is built, by a canary test run by hand at the user's word, as in open question 2.
4. **A Claude Code agent-session and its own sandbox.** A Claude Code agent-session's commands also run in a sandbox. Recommendation: on ned-box, the agent-session runs the canary runner as `ssh nedlern@ned-box '<the canary runner's command>'`, the route the project already uses to run a command outside the sandbox; on the Mac, by a rule measured as in open question 3.
5. **The real sign-in files under a throwaway home directory.** Codex and Claude Code find their sign-in files under the home directory unless an environment variable points elsewhere: `CODEX_HOME` for Codex, `CLAUDE_CONFIG_DIR` for Claude Code (which `scripts/clean-worktrees.py` reads). On the Mac, Claude Code may keep its sign-in in the macOS Keychain rather than a file; that is unchecked. Two further facts bear on it: `codex_credential_denying_permission_profile_arguments` builds its deny entries from the home directory (`pathlib.Path.home()`), so under a throwaway home directory it denies the planted files and not the real ones; and pointing `CODEX_HOME` at the real directory also gives Codex the machine's real `config.toml`. Recommendation: point `CODEX_HOME` and `CLAUDE_CONFIG_DIR` at the real directories, build the deny entries under the throwaway home directory as the profile run does, and check by a canary test, reading planted files only, that the outside program still runs.
6. **How the test runner runs a permanent canary test.** Today `scripts/run-all-test-suites.py` runs every `*-test.py` file directly, judges it by its exit code alone, runs suites at once up to the core count, sets no per-suite timeout, and runs each inside its signal sandbox (bwrap on Linux, sandbox-exec on macOS), in which bwrap, and so Codex's Linux sandbox, cannot start; a selective run also runs a suite with no recording yet or whose last run failed. It has no option to run one suite by name. Recommendation: the test runner starts each file whose name ends `-canary-test.py` through the canary runner, outside its signal sandbox, one at a time, with the timeout and the machines the file declares in constants; skips it, saying so, in a selective run and on a machine it does not apply to; and gains an option to run named suites. The daily full test run runs them; on ned-box, through cron, whose PATH lacks `~/.local/bin`, so the canary runner looks there for `claude`, as the weekly check does.
7. **The first permanent canary test.** Recommendation: the Codex permission profiles, with PR 1200's `--add-dir` case and the profile placement after `review` that GHI 804 measured, because every reviewer whose agent-binary is `codex` relies on them and Codex upgrades itself; one file per behaviour, beside the code that relies on it.
8. **Where a permanent canary test's run logs are kept.** The daily full test run's record names a failed suite, not a passed one, and comparing an outside program's version before and after a FAIL needs earlier run logs. Recommendation: the canary runner writes each run's log to `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/permanent/<machine>/<YYYY-MM-DD>T<HHMMSS>-<suite path with each / as __>.txt`, with the commit it ran at as its first line, deleted after 30 days by the job of open question 10.
9. **Who tells the user when a permanent canary test fails.** Today merge-lane-2 reads ned-box's newest daily record at each session start, and no other channel carries a failed record to the user; no one reads the Mac's. GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) plans that channel. Recommendation: the first permanent canary test that runs on the Mac waits for GHI 1206's channel; until then permanent canary tests run on ned-box only.
10. **What deletes the one-shot directories and the permanent run logs.** Recommendation: a scheduled job on ned-box, run daily and listed in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, that deletes each `canaries/one-shot/<date>-*` directory, each old `canaries/canary-temp-<date>-*` directory, and each `canaries/permanent/<machine>/<date>T*` file more than 30 days old, and prints what it deleted, because deleting by a date in a name needs no agent. The alternative is a job of the daily maintenance step of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058), which an agent-session runs.
11. **The weekly real Claude session check and the two `--canary` suites.** `nc-systems/handoff/uncommitted-work-snapshot-hook-real-claude-session-weekly-owner-check.py` checks a real Claude Code behaviour, but runs with the real home directory, starts `claude` itself, ends with `VERDICT: PASSED` or `VERDICT: FAILED`, and runs weekly as its own scheduled job; the two suites above run their live checks only when given `--canary`. Recommendation: leave all three as they are until the canary runner exists; then the canary runner's builder brings to the user whether each becomes a permanent canary test.
12. **Canary tests of cron and launchd.** The canary runner runs one program and waits for it; cron and launchd run a job later, outside that program, and in the real user's crontab or launchd whatever the home directory is. Recommendation: such a canary test installs a throwaway job that writes a file, writes the job's identity to a file in the run's temporary directory before installing it, and waits for the file within a wait shorter than its timeout; the canary runner removes the job named in that file after the program ends or is stopped; a job that fires at login is loaded to run at once; and `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py --check` reports a job left behind.
