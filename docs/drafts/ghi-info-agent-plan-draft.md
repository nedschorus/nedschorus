# ghi-knowledge-agent — plan for the user's walk

*(The name is provisional and is walk item 2. The user called `ghi-knowledge-agent` "pretty good", 2026-08-07 — not yet a ruling.)*

**This agent is an instance of a class the project already designed.** [26-dynamic-agent-team-model.md](../issues/26-dynamic-agent-team-model.md) (pair of [nedschorus#26](https://github.com/nedschorus/nedschorus/issues/26)) defines **domain-knowledge agents**: long-lived domains, and "the GHIs" is the first domain that document lists; short tasks (answer a question, maintain the domain); lifecycle active / idle / exited, with exited-by-default and on-demand spawn as the fallback until idle-wake is verified; and the ruling that the expert's real asset is *its curated domain files, which a fresh spawn loads in seconds*. This plan is that class's first concrete build, and its decisions should land consistent with that document or explicitly revise it.

**Lifecycle refinement (user, 2026-08-07):** a headless resume-per-question agent has no idle state — it is active only while taking a turn, and otherwise exited: what persists between turns is a session id, its transcript, and its curated files, not a process. "Idle" describes a live process waiting — an interactive session, or a watcher/shadow agent monitoring other agents (who might themselves be idle) — and knowledge agents are probably not that kind. For this class, § 26's exited-by-default fallback is therefore the design, not a fallback. Whether 26-dynamic-agent-team-model.md's lifecycle line is revised to say so lands with this plan. The agent-roster question on [nedschorus#45](https://github.com/nedschorus/nedschorus/issues/45) (open question 3) will want this agent's name and cold-start instructions once ruled.

A dedicated agent that holds this project's GitHub issues in context. Another agent, before filing or editing an issue, asks it which issues they should read, and gets an answer. Replaces the gate direction rejected at [ghi-gatekeeper-plan-draft.md](ghi-gatekeeper-plan-draft.md): nothing is gated, because unmediated access was never the problem. The two problems are that an agent about to write does not know what related issues already exist, and that issues get written carelessly. This plan addresses the first; the second stays with the `ghi-write` skill ([ghi-write-skill-draft.md](ghi-write-skill-draft.md)).

## The shape, as understood

Your direction, restated for confirmation at item 1:

- One long-lived agent per project, whose job is knowing the issue set — not writing issues, not deciding routing.
- An asking agent invokes a prompt that resumes it, poses the question, and reads the answer when it exits.
- The answer is a set of issues the asker should read, not a summary that replaces reading them.
- Cheap enough to sit in front of every file-or-edit, since that is where it is meant to fire.

## The verified precedent

NM (`~/Projects/nedsmessenger`) already runs this pattern, and its mechanics are the reference implementation, verified 2026-08-07 at `adapter/adapter.py:379` (`ask_claude`):

- `claude -p <prompt> --output-format stream-json --verbose --permission-mode bypassPermissions --model <model>`, plus `--resume <session-id>` when a session already exists for that conversation.
- One persisted session id per conversation; the first call omits `--resume` and injects history instead.
- The answer is read off the exit stream by the caller.
- Unattended authentication uses a long-lived `CLAUDE_CODE_OAUTH_TOKEN`, because an interactive login expires with no human to refresh it.
- Three watchdogs kill a stuck run — idle silence, a silent in-flight tool call, and a total-runtime backstop — so a hung agent cannot block its caller forever.

## Open questions, each with its item

- **Item 3 is the load-bearing one.** A resumed session's context only grows: every question and answer stays in it, so the agent needs recycling on the same terms as any long-lived session, and its knowledge is only as fresh as its last read of the issue set. "Keeps the issues in context" therefore needs a stated refresh discipline and a stated recycle behavior, or the agent silently answers from a stale picture — the failure that is hardest to notice, because a confident wrong answer looks like a right one. Two mechanisms are on the table (user, 2026-08-07), and they compose rather than compete:
  - **Incremental refresh each run** — possible, verified 2026-08-07: issues are listable by update time (`gh issue list --state all --search "sort:updated-desc" --json number,updatedAt`) and filterable to a window (`--search "updated:>2026-08-06"` returned exactly the one issue touched since). So "read everything that changed since my last look, then answer" is one call. GitHub documents `updated` as moving on body edits and comments alike; that claim is verified at build.
  - **An ingest program** — reads all of a project's issues and produces the best form for a knowledge agent to load (the user suggested JSON). This is the § 26 curated-domain-file ruling made concrete: the durable asset that survives recycling is the file, not the session; a fresh spawn loads it in seconds, and the incremental query is then only the delta since the file was built. Form (JSON vs MD), owner (the agent maintains its own file vs a separate program), and refresh cadence are item 3's decisions.
- Whether the asker passes the issue text it intends to write, or only a subject line — the more the agent sees, the better it can match, and the more it costs.
- Whether "which issues should I read" and "is this a duplicate" are one question or two.

## Format, extraction, and the cross-reference question (discussion opened 2026-08-07, being walked)

Raised by the user mid-walk, with a scale bound: this project is expected to stay under ~10,000 issues (projects with 100K+ exist; the bigger the issue set, the harder to understand efficiently). Three questions, with the positions taken to the walk:

1. **Best ingestion format — JSON?** Position: curation decides value, format barely does. An agent reads well-structured MD at least as well as JSON, and MD is denser per token; JSON/JSONL earns its place only where a *program* consumes the file (delta bookkeeping, diffing). The real design decision is what each issue's entry keeps — number, title, state, updated time, one-line summary, outbound references — not the syntax around it.
   *processed 2026-08-07 → REVISED then ruled: MD, for human readability and grepability. Condensation is not needed to fit — a 1M-token context holds ~3000 issues with little condensation, and that window is what this design spends (user: "instead of building a vector or graph DB of the GHIs, we're just using a modern agent" — the ruled framing). Summaries, cross-references, and a two-or-three-level information architecture remain helpful as organization, not as compression. Clarified: "big issues" meant MANY issues; complex individual issues are their own difficulty.*
2. **Is extraction faster or more reliable than querying GitHub live?** Position: the extract's value is neither speed nor reliability — it is *whole-set awareness*. Live search only returns what the asker thought to search for; a curated index the agent holds whole is what lets it answer with issues nobody thought to look for. Delta refresh (verified, `updated:>`) keeps the extract cheap. At today's ~45 issues everything fits trivially; near the 10K bound a one-line-per-issue index strains one context, so tiering (open vs closed) is the named growth point, not built now.3. **A GHI graph — and does the job flip from answering queries to maintaining cross-references?** Position: the graph is derivable by a program (parse `#n` references from bodies; GitHub's own cross-reference timeline events are the backlinks — verify the API shape at build). The job does not flip; it doubles, and [26-dynamic-agent-team-model.md](../issues/26-dynamic-agent-team-model.md) already names both tasks for this class: *answer a question, maintain the domain*. Maintenance = keeping cross-references current so the corpus navigates itself from any entry point; answering = the pre-write moment, which link-following cannot serve because the issue being written does not exist yet and has no links. Small, well-linked issues are themselves the scale mitigation the user's 100K observation points at.
   *processed 2026-08-07 → approved: the agent maintains cross-links and answers questions. The user's surrounding model confirmed with it: any agent may create, edit, or close issues — the how is `ghi-write`'s business, nothing is gated — and revisions are body edits, not comments; every GitHub-side change (edit, comment, close) moves the issue's updated time, so the delta feed carries them all to this agent. One build-time verification rides: that close and label changes move `updated` as body edits and comments do.*

## The MD side of the pair — open, raised 2026-08-07

Issues link to MDs (the MD-GHI pair is the project's own convention), and nothing yet keeps that boundary sound. The user named two gaps: linked MDs are not kept up to date when their issue moves, and nothing ensures an MD backlinks the correct GHI(s). One caveat makes this structural: **MD edits are invisible to the issue delta** — they land as git commits and touch no issue's updated time, so the agent needs two delta feeds: `updated:>` for the GitHub side, git log since last run for the MD side. Candidate position for the walk: **link integrity in both directions joins the maintenance task** (GHI→MD references resolve; MD→GHI backlinks exist and are correct), but MD *content* freshness is flag-not-fix — the agent reports "issue #n changed, its pair MD untouched since" rather than rewriting the MD, staying out of authorship the way it stays out of routing.

**Coupling discussion (2026-08-07).** The user leans loosely coupled: the meat is typically in the MD, which goes through many passes irrelevant to the GHI's task-tracking aspect — which is the pair convention's existing split (GHI carries state, MD carries substance, joined by links). Factual state, verified against origin/main after fetch (2026-08-07; a first check against a stale checkout missed `docs/founding/`, landed by the handoff session that day): NC has **one kind of MD file** — repository files under `docs/`, grepable, queue-promotable to the in-repo wiki (`docs/wiki/`); a github.com `blob/main/` URL is the web view of a pushed repo file, not a second store. GitHub's wiki feature is enabled on the repo but unused, and no documents live GitHub-side except **issue bodies and comments** — markdown text, but the convention's state surface, not documents. The blur that does exist: substantial issue-*only* bodies (nedschorus#13's commission is a live specimen — meaty body, no pair MD), which sit past the convention's "issue-only when lean" line. The user's don't-have-both-kinds instinct maps onto a candidate rule for `ghi-write` routing: issue bodies stay lean; when a body grows substantial working material, that is the trigger to split it into a pair MD.

**Who performs the lean-split (discussion 2026-08-07, direction set by the user; refined same day).** The agent that took the body over the limit does the summary and split — or the re-summary and re-split when a paired issue's body has regrown — because it holds the substance context a rewrite needs. But **no agent is asked to count words**: the length check is a script's job, run after the write. The chosen mechanism is post-write correction — the write lands untouched, the script measures it, and an over-limit writer is told immediately to summarize and split now. The user picked post-over-pre deliberately: it is the simplest and safest form because it does not disturb the writing step. (Mechanically both are available in Claude Code: issue writes go through the `gh` CLI as shell commands, which tool hooks can see before and after — post-tool-hook field shapes and the Codex equivalent are verify-at-build.) Where the split needs corpus breadth — what to link — the writer asks this knowledge agent, the ask-before-writing flow already designed. The knowledge agent's maintenance sweep runs the same length script as the drift backstop: a body found over the limit after the writer's session is gone is flagged, and the next writing agent corrects it as part of its edit. No new agent role is created. The threshold, the script, the hook wiring, and the split procedure ride to the `ghi-write` walk.

**The write-path tool question (user, 2026-08-07: is there an update-GHI tool Claude uses — or should we make one?).** Factual state: Claude Code has no built-in issue tool — in this project issue writes are `gh` CLI calls through the shell, which is why hooks were the mechanism under discussion. An official GitHub MCP server exists with issue-update tools (check at adoption; Codex also runs MCP servers — verify there), but it performs generic writes carrying none of NC's checks. The alternative is making one: a small project script wrapping the issue write, which carries the length check and the teaching reply itself — no hook wiring in any runtime, identical behavior from Claude and Codex, and the post-write-correction choice becomes the tool's own reply ("written; body is over the limit — summarize and split now"). This is not the rejected gate re-entering: `gh` stays usable, nothing blocks; it is a helper the `ghi-write` skill teaches, reviving the useful non-gate slice of the superseded gatekeeper plan (teaching replies, mechanical checks) without enforcement. Position taken to the walk: make the script, skip the MCP server.

*Write-time integration direction (user, 2026-08-07, post-walk).* The hook **rewrites instead of refusing**: PreToolUse `updatedInput` replaces the agent's `gh issue create/edit` arguments with the project tool invocation and executes it — agents keep their trained behavior entirely; nothing is asked of them (verified 2026-08-07: `updatedInput` replaces the arguments the tool runs; command-hook timeout defaults to 600s, per-hook configurable — an in-path model turn fits; combining `updatedInput` with `additionalContext` is undocumented, verify at build). The tool then consults `ghi-info` with the **actual draft body** — resolving the old open question of what the asker passes — and routes by its judgment: **too similar** (duplicate, overlapping, or conflicting with an existing GHI) → the write is refused with a reconsider-and-read teaching reply, the soft block; **related but compatible** → the write proceeds and the reply (or injected context) tells the writer to familiarize itself with the related GHIs in case other changes follow; **unrelated** → plain write. Conditions recorded: fail-open — `ghi-info` unreachable means the write proceeds unchecked (the never-blocks ladder holds); the tool's reply must not confuse an agent that believes it ran `gh` (mimic or extend `gh` output, and/or announce the substitution via context — verify at build); the latency of a model turn per issue write is accepted at issue-write frequency. Layering: the skill's ask-first step stays as the *efficiency* path (find the EDIT target before drafting a duplicate body); the hook check is the *correctness* backstop that makes a skipped ask survivable. Lineage: this is the superseded acknowledgment scheme's smarter successor — similarity judged by `ghi-info`, not self-attested flags.*

*The comment case (user, 2026-08-07): rewrite is impossible there, so the hook refuses and teaches.* A comment cannot be mechanically rewritten into the body edit the convention wants — where the content lands in the body, and what it supersedes, is judgment only the commenting agent holds. So `gh issue comment` gets the deny-and-teach treatment, not `updatedInput`: the refusal arrives at the moment of action carrying the instruction — integrate this into the issue body by edit; or, if it is a genuinely new event (instance outcome, completion, ruling challenge — the convention's legitimate comment class), resubmit through the tool's comment verb, which requires naming the event kind. The forced classification is the point: only the author knows which case it is, and the retry attaches that judgment. Cost accepted: one lost turn per attempt. The user's skepticism that a CLAUDE.md line would be obeyed is the project's own documented finding (nedschorus#13: the convention recurred as a failure despite being written down — instructions in memory lose to training; instructions at the moment of action do not); the CLAUDE.md line stays as ambient documentation, the hook is the enforcement. `gh issue delete` (where available) is denied flat with close-instead teaching — the record is append-forward, closure is the end state, deletion is not part of the workflow.*

*Close, comments, and cleanup (user, 2026-08-07).* **Close is a state, not a comment**: GitHub issues carry open/closed state with a state reason (completed / not planned), the change is a timeline event the delta feed picks up, and `gh issue close` passes through the hook untouched. **Close-instead-of-delete ratified**: marking closed is simpler and safer; the record stays append-forward. **The allowed-comment catalog is deliberately iterated**: it starts at the three ruled event kinds (instance outcome, completion, ruling challenge) and grows only by explicit ruling — whether "completion" collapses into close-with-reason is a detail for the `ghi-write` walk. **Old-closed-GHI cleanup**: the dead weight lands first on `ghi-info`'s context and reader attention, not on GitHub — so cleanup begins at the mirror layer, cheap and reversible: tier the corpus (open issues near-raw, closed as one-line entries, dead ones dropped from the mirror entirely) before touching GitHub at all. The user's when-is-relative point recorded as the aging clock: age is measured in project activity, not calendar time — a dormant project's issues do not age; an active project's do. A GitHub-side purge (export to a repo file, then delete) is a far rung with its trigger being the mirror tiering itself no longer sufficing; until then GitHub keeps everything and the mirror curates.*

*Open/closed grep default, encoded in file layout (user, 2026-08-07: be specific enough for Python, not prompts — closed GHIs are useful maybe 1 in 50 greps).* The mirror is **two files, split by state**: `issues-open.md` (near-raw) and `issues-closed.md` (tiered one-line entries). The default is then not an instruction anyone must remember but a path: routine relatedness checks grep the open file; the closed file joins the grep in two named cases — an **absence claim** (a "no issue covers X" receipt is invalid unless both files were searched: the closed file is exactly where was-tried-and-rejected lives) and an explicit **precedent hunt**. Both conditions are observable, so the rule is procedure, not judgment. The script maintains the split mechanically — close moves an entry from one file to the other at delta refresh. General principle recorded: wherever a workflow default can be expressed in file layout or code instead of prompt text, it is.*

*Time-blindness and how the record compensates (user, 2026-08-07: AIs, ghi-info included, do not understand time or progress — they cannot tell relevant-now from relevant-before; help is needed).* Recorded with three legs, two of which the project's conventions already provide by construction: (1) **the revision convention keeps reading surfaces current** — because clarifications edit the body rather than stack comments, an issue body is its latest truth by construction, and supersession is written explicitly (a SUPERSEDED marker naming the successor) at the moment of the change by the agent that knows, never inferred later by one that cannot; (2) **state encodes the coarsest now-vs-before** — the open/closed file split just ruled is the primary temporal filter, ahead of any timestamp. (3) What remains genuinely temporal, the script makes legible rather than asking the agent to infer: each mirror entry carries its updated time plus a computed **activity-relative freshness** (how much of the project has moved since this issue last did — the user's aging clock made a number), and the supersession marker is a mechanically sweepable pattern, so two open issues claiming the same ground without one naming the other is a flaggable defect — the same conflict class the write-time check already catches. Boundary held: no script decides whether an old ruling still binds — that stays with writers editing the record when direction changes, and with the user.*

*Context policy and the recycle trigger (user, 2026-08-07).* **ghi-info is 100% focused on open GHIs**: the cold start loads `issues-open.md` only; closed issues enter a turn solely by grep on demand. Closed GHIs are retained on GitHub indefinitely at sane volumes — retention pressure was already routed to mirror tiering, not deletion. The genuinely new problem this names: a *resumed session's context drifts* — the mirror updates every turn, but previously loaded issues that have since closed linger in context as if open, and the agent cannot notice on its own. Mechanisms set, crude by design because the user's decisive observation is that a refresh is fast and cheap so recycling can err eager: (1) the wrapper's state file counts closes since the session was born and a small threshold forces clear-and-reload (the user's "1000 closed" shape, scaled to project size; a config constant tuned in live use); (2) the wrapper **post-checks every answer against the closed file** — a returned pointer to a closed issue is filtered out with a note before the asker sees it, which both repairs the answer immediately and, as a rate, is the user's 20%-of-matches staleness signal driving recycle; (3) the transcript-size recycle from the invocation design remains. Whichever trigger fires first wins; all three are script-observable, none is the agent's judgment.*

*Hard-vs-soft raised (user, 2026-08-07): with the tool in place, why not a hard block? Position taken to the walk: soft, with the audited override — because a hard block makes the tool a single point of failure for the whole issue workflow (a tool bug, or any `gh` capability the tool does not wrap yet, halts every issue write until fixed), and the project's own floor warns that absolutes backfire in unforeseen conditions. The override is not a hole: ca3d603's lane is one audited use per marker, consumed on use. Hardening trigger, named: the audit showing the override used to dodge the tool rather than for genuine breakage.*
