# Restarting a handoff-supervisor onto main's code when it will not restart itself

A running handoff-supervisor keeps the code it started with, because its process reads its Python code once, when it starts. At each session-handoff that launches a successor without consulting the user, the handoff-supervisor restarts itself on main's code, as the handoff-system's nc-architecture-overview, `docs/nedschorus-wiki/nedschorus-handoff-architecture-overview.md`, says, and then the next such session-handoff is enough.

The restart program, `python3 ~/Projects/nedschorus/nc-systems/handoff/handoff-supervisor-restart-onto-main-code-by-relaunch-from-reference-checkout.py <seat>`, is for a handoff-supervisor that is running and will not restart itself: one whose code predates that restart; one that runs from a checkout other than the reference-checkout `~/Projects/nedschorus`, such as a Mac agent-seat launched from its agent-home, since the restart fast-forwards the checkout the handoff-supervisor runs from and fails whenever that checkout cannot be fast-forwarded to main, as when its seat-branch holds commits of its own; or one whose restart failed for a reason other than its checkout. The agent-seat being restarted runs the program itself, on the machine it runs on, and on ned-box through `ssh nedlern@ned-box '<command>'`, because the Bash sandbox cannot signal the handoff-supervisor. The program's docstring says what the agent-seat does before and after running it, what the program does, how each failure leaves the agent-seat, and what it cannot handle.

When neither a handoff-supervisor nor an agent-session of the agent-seat runs, the restart program does not apply: `scripts/recover-crashed-seats.py`, which brings back an agent-seat whose handoff-supervisor is gone, is the tool for that agent-seat.

When the successor's initial-agent-instructions say the handoff-supervisor did not restart because the reference-checkout cannot be fast-forwarded to main, do not run the restart program, since its first step fails the same way: tell the user, and once that checkout is fixed, the next session-handoff that launches a successor without consulting the user restarts the handoff-supervisor.
