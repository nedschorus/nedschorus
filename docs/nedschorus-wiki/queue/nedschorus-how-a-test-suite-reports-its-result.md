# How a test suite reports its result

This page says how an nc-test-suite in this repository tells the test runner, `scripts/run-all-test-suites.py`, whether it passed, and what the test runner prints. Read it before you write an nc-test-suite, or a program that reads the test runner's output. The test runner's module docstring, at the top of the file, holds its complete rules; this page is the short version of the parts an nc-test-suite's author needs, and a program that reads the test runner's output needs the docstring's OUTPUT and EXIT sections as well. The last section, on canary tests, describes rules the user has decided for programs not yet built, which that docstring does not cover.

The project glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`, defines an nc-test-suite. On this page a test case is one test inside an nc-test-suite.

## What counts as an nc-test-suite

The test runner runs only files that git tracks, so commit a new nc-test-suite, or `git add` it, before you expect it to run. A full test run, which is the test runner started without `--only-suites-whose-recorded-inputs-changed-since` or `--only-suites-named`, runs every nc-test-suite, except one that gets a `NOT RUN` line, unless the test run is stopped or ends early, as the last paragraph of the next section says; `--stop-at-first-failing-suite` stops it once an nc-test-suite fails, and `--run-time-limit-seconds-not-counting-admission-waits` once the test run's time limit has passed. Run with `--only-suites-whose-recorded-inputs-changed-since <commit>`, as the test run at a pull request's nc-head-commit is, the test runner runs only the nc-test-suites its docstring's selection rules pick, and prints a `SELECTED` or `NOT SELECTED` line for each nc-test-suite it considered: every nc-test-suite, or, with `--only-suites-named`, the ones named. Where nc-test-suites run in nc-test-sandboxes, on Linux with bwrap, such a test run without `--only-suites-named` also leaves out each picked nc-test-suite that `SUITES_RUN_WITHOUT_ANY_SANDBOX`, a dict in `scripts/run-all-test-suites.py`, lists, and prints for it, in place of its `SELECTED` line, a line opening `NO-SANDBOX SUITE LEFT OUT OF SELECTIVE TEST RUN` with the command that runs it by hand.

The test runner runs each nc-test-suite as a script, `<python> -u <path>` or `sh <path>`. It does not run pytest or unittest's test discovery. So an nc-test-suite that uses Python's `unittest` must itself run its test cases and exit nonzero when one fails: `unittest.main()` does both, while after `unittest.main(exit=False)` or `unittest.TextTestRunner().run()` the nc-test-suite must exit nonzero itself; a file that only defines `test_` functions for pytest runs none of them and exits 0, which the test runner reports as a pass. No nc-test-suite in the repository uses pytest.

## Pass or fail: the exit code, not the output

An nc-test-suite passes when its process exits with code 0. It fails when it exits with any other code, when a signal kills it, when it runs past its per-suite time limit, which the docstring's PER-SUITE TIMEOUT section sets, or, where nc-test-suites run in cgroup scopes, when the kernel kills one of its processes at its memory ceiling, even if the nc-test-suite then exits 0; the docstring's MEMORY CEILING section says where that is. Two nonzero ends are exceptions, and count as neither a pass nor a fail. An nc-test-suite killed because the test run was stopped counts as stopped: the line the test runner prints for it opens `FAIL` and says `killed when the run was stopped by`, and in a test run that reaches its `SUMMARY:` line it is left out of the list of failed nc-test-suites and counted as stopped. An nc-test-suite whose bwrap failed after the test runner started it, before the nc-test-suite started, gets a `NOT RUN` line, as the last paragraph of this section says.

The test runner reads no text an nc-test-suite prints to decide whether it passed. On Linux it reads each test case line, a line that opens with the word `PASS`, `FAIL` or `ok` after any spaces, only to time and record that test case; a line that opens `PASSED` is not a test case line. nc-test-suites print success in several wordings, such as "all cases passed" or "OK", so no wording can be trusted. An nc-test-suite that finds a failure must exit nonzero: printing its own "FAIL" and exiting 0 is reported as a pass.

The exit-code page, `docs/nedschorus-wiki/nedschorus-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, asks more of a test file than the test runner checks today: exit 1 when a test case fails and 2 when it could not run, and print a verdict line as the last line of standard output. The form of that verdict line is not decided yet, and until the test runner is changed to read it, the test runner treats every nonzero exit code alike, so exit 2 fails an nc-test-suite just as exit 1 does.

The test runner prints a line opening `PASS`, `FAIL` or `NOT RUN` as each nc-test-suite finishes, with `, <n> skipped` inside its parentheses when the nc-test-suite printed `SKIP` lines, then each nc-test-suite that failed or got a `NOT RUN` line, again with its log file, then every `SKIP` line, and ends with a line opening `SUMMARY:`. A `NOT RUN` line is for an nc-test-suite whose bwrap, the program that builds its nc-test-sandbox, failed after the test runner had started it and before it started the nc-test-suite: no test case ran, so the nc-test-suite counts as neither a pass nor a fail, and the test run goes on to its `SUMMARY:` line. A test run stopped by SIGTERM, SIGHUP or SIGINT before its last nc-test-suite ended, or one the test runner ended early because it could not prepare an nc-test-suite's nc-test-sandbox before starting bwrap for it, could not start the command that runs an nc-test-suite, bwrap where there is one, could not write an nc-test-suite's log file or its run record, or could not admit an nc-test-suite to start, as the docstring's ADMISSION section describes, prints no `SUMMARY:` line; it prints a line opening `run-all-test-suites: not run to the end` instead. A test run stopped because it passed the time limit that `--run-time-limit-seconds-not-counting-admission-waits` sets prints such a line and then its `SUMMARY:` line. A test run stopped by `--stop-at-first-failing-suite` prints a line opening `stopped at the first failing suite,` and then its `SUMMARY:` line. A test run that could not start, such as one given a directory that is not the top directory of a checkout, prints a line opening `run-all-test-suites: not run —` and exits 2 or 3 before any nc-test-suite starts; one given an option the test runner does not accept, or a value it refuses, such as `-j 0`, prints a `usage:` line and a line opening `run-all-test-suites: error:` and exits 2. A test runner killed by any other signal, SIGKILL among them, prints nothing more. The docstring of `scripts/run-all-test-suites.py` describes the output under OUTPUT and gives every exit code under EXIT.

## Skipped test cases: the `SKIP` line

An nc-test-suite sometimes cannot run one of its test cases, for example because a tool the test case needs is not installed. It then prints one line for that test case and goes on with the other test cases. Print a line that opens with `SKIP` and a space, then gives the test case and the reason; the test runner checks only that `SKIP` is followed by a whitespace character, such as a space or a tab, so the second space and the colon in the example below are optional. A line that opens any other way, such as `SKIP:`, is not counted, and neither is a skip made with unittest's own skip. `scripts/test-suites-source-scan-for-skipped-case-prints-run-all-test-suites-cannot-count-test.py` fails on a call of `.skipTest(`, `unittest.skip(`, `unittest.skipIf(` or `unittest.skipUnless(`, though not on `raise unittest.SkipTest(...)` or a `skip` imported from `unittest`, and on a `print(`, `echo` or `printf` followed directly by text that opens `SKIP` without a space right after it, even where the printed line would be counted, as with `print("SKIP", name)`, though not on such text after a prefix such as `r`, a triple quote or a flag such as `-e`; a `SKIP` line printed any other way, such as through `sys.stdout.write`, it does not see. When the machine itself is the cause, its platform or what is installed on it, put `[this machine cannot run it]` right after `SKIP` and its spaces; the test runner reads the mark only there, and its docstring says what the mark changes. Print one line per skipped test case. Example: `SKIP  [this machine cannot run it] the hand-run command's lock case: /usr/bin/flock is missing; it exists on Linux only`.

The test runner counts every line of an nc-test-suite's output that matches the regular expression `^SKIP\s`, and shows a count that is not 0 on the line it prints for the nc-test-suite. A test run that reaches its `SUMMARY:` line also prints each counted line again, with its nc-test-suite, near the end of its output, and the sum on the `SUMMARY:` line. A skipped test case never changes whether the nc-test-suite passed: an nc-test-suite that skips every test case and exits 0 is reported as a pass. The test runner counts lines, so a line that names several test cases counts as one.

GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) proposes replacing the `SKIP` line with `SKIPPED test case "<name>"; reason: <reason>`, printed by one shared function, in which a test case that cannot apply on this machine gets a reason opening `not on this platform:` rather than the mark `[this machine cannot run it]`, and changing the test runner's pattern to match. Until that change is merged, print the `SKIP` line, with the mark where the machine is the cause.

## Where the report and the logs are kept

A test run writes its whole report to `test-run-report.txt` in its log directory, which the first line of the report names after `; logs in `, beside one log file per nc-test-suite it started; a test run that could not start, and ended before the first line of its report, writes neither. Unless `--log-dir` names another directory, the log directory is under the system temp directory. On Linux a later test run that uses the same `--lock-file` deletes such a directory once two days have passed since the test run ended; on macOS the test runner does not delete it, and it never deletes a directory that `--log-dir` names. Copy anything you need to cite within those two days.

`scripts/scheduled-full-test-run-of-main.py` runs every nc-test-suite on main once a day on each machine, ned-box and the Mac, at the times `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` gives; a Mac run missed while the Mac sleeps starts when it wakes. It writes one record per machine and day to `nedlern@ned-box:/home/nedlern/nedschorus-logs/scheduled-full-test-runs-of-main/<machine>/<YYYY-MM-DD>.txt`, where `<machine>` is `ned-box` or `mac` and the date is the date in America/Los_Angeles when the run started. The record holds the run's failures and counted `SKIP` lines; the docstring of `scripts/scheduled-full-test-run-of-main.py` lists all it holds. The whole report, `test-run-report.txt`, and the nc-test-suites' log files stay on the machine that ran them, in `<system temp directory>/nedschorus-scheduled-full-test-run-of-main/logs`, which the record names and each scheduled full test run replaces.

## An nc-test-suite that measures something

An nc-test-suite that measures something, such as a duration or how often a hook's reminder is right, prints the number and the threshold, and passes or fails against the threshold, which its author may set by judgement, saying why in a comment beside it. Work whose result is a number with no pass or fail is not an nc-test-suite; it is a check, and reports as the exit-code page, `docs/nedschorus-wiki/nedschorus-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, says.

## Canary tests: decided, not yet built

A canary test runs a real outside program that the project does not write, such as `codex` or `gh`, to check that it still behaves the way our code relies on. It is a kind of contract test; it is not a canary release, the software-engineering sense of "canary". The user decided the rules below in approval-walks (user-ruled 2026-10-19 to 2026-10-26). No canary test, and no canary runner, the program that will run one, exists yet.

A scheduled canary test is kept in the repository and runs in the scheduled full test run; a one-shot canary test runs once, for a single change. A scheduled canary test lives in the `tests/` directory of the nc-system whose code relies on the outside program's behaviour, or in `scripts/` when a program there relies on it, and is named `<outside program>-<behaviour>-canary-test.py` (user-ruled 2026-10-20).

A canary test is one Python file. Its last line of standard output is exactly `#canary_pass`, and it exits 0, when the outside program behaved as relied on; or exactly `#canary_fail`, and it exits 1, when the outside program did not. The canary runner, not the canary test, gives the third result, `#canary_no_answer`, which means the canary test could not tell: when the last line of standard output is anything else, when the exit code does not match the line, or when the canary test runs past its time limit and the canary runner kills its whole process group. So a canary test that finds it cannot check, for example because the outside program is logged out, prints neither hashtag, whatever its exit code, and its result is `#canary_no_answer`. The canary runner logs standard output and standard error together, but takes the result from standard output alone (user-ruled 2026-10-23).

The extra line is what tells "the outside program failed the check" apart from "the canary test could not give an answer": an exit code alone reports both as a fail.

The canary runner exits 0 for `#canary_pass` and 1 for `#canary_fail`; it exits 2, saying why, for `#canary_no_answer`, and also when it could not write to the log-store or delete its run directory, the directory it makes for each run to hold a throwaway home directory with planted fake credential files, even after a pass or a fail (user-ruled 2026-10-19). In the scheduled full test run's record, a `FAIL` line for a canary test gives the canary runner's exit code: exit 1 is `#canary_fail`, and exit 2 says nothing about the outside program (user-ruled 2026-10-25).

The canary runner writes the log of every run of a scheduled canary test, scheduled or by name before a merge, to `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/scheduled/<machine>/<YYYY-MM-DD>T<HHMMSS>-<suite path with each / as __>.txt`, where `<machine>` is ned-box for now, with the date and time in America/Los_Angeles at the run's start, and the full hash of the commit it ran at as the log's first line (user-ruled 2026-10-26). Scheduled canary tests run on ned-box only until the check GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) proposes, or the maintenance-job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058), reads the Mac's record; from then on each runs on the machines its file declares in a constant, and on any other machine the test runner skips it, saying so (user-ruled 2026-10-25 and 2026-10-26). A one-shot canary test's Python file, run log and result go to `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/one-shot/<YYYY-MM-DD>-<subject>/`, where `<subject>` names what the canary test checks, the date is the date in America/Los_Angeles at the run's start, and a second run with the same date and subject adds `-2`, a third `-3` (user-ruled 2026-10-19 and 2026-10-20). Each scheduled canary test's log, and each one-shot canary test's directory, is deleted once more than 30 days have passed since its date (user-ruled 2026-10-20 and 2026-10-26).

Today's test runner judges every file it runs by its exit code, as above, and on ned-box, in its nc-test-sandbox, an outside program such as `gh` or `codex` has no login and, by default, no network. The test runner is to start each file whose name ends `-canary-test.py` through the canary runner, outside the nc-test-sandbox, one at a time, under the time limit the file declares in a constant (user-ruled 2026-10-26). That change to the test runner is made in the pull request that commits the first scheduled canary test, and no canary test is committed before it (user-ruled 2026-10-20).
