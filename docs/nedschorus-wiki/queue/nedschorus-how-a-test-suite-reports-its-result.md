# How a test suite reports its result

This page says how an nc-test-suite in this repository tells the test runner, `scripts/run-all-test-suites.py`, whether it passed, and what the test runner prints. Read it before you write an nc-test-suite, or a program that reads the test runner's output. The test runner's module docstring, at the top of the file, holds its complete rules; this page is the short version of the parts an nc-test-suite's author needs. The last section, on canary tests, describes rules the user has decided for programs not yet built, which that docstring does not cover.

The project glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`, defines an nc-test-suite. On this page a test case is one test inside an nc-test-suite.

## What counts as an nc-test-suite

The test runner runs only files that git tracks, so commit a new nc-test-suite, or `git add` it, before you expect it to run. A full test run, which is the test runner started without `--only-suites-whose-recorded-inputs-changed-since` or `--only-suites-named`, runs every nc-test-suite. Run with `--only-suites-whose-recorded-inputs-changed-since <commit>`, as the test run at a pull request's nc-head-commit is, the test runner runs only the nc-test-suites its docstring's selection rules pick, and prints a `NOT SELECTED` line for each of the others.

The test runner runs each nc-test-suite as a script, `<python> -u <path>` or `sh <path>`. It does not run pytest or unittest's test discovery. So an nc-test-suite that uses Python's `unittest` must itself call `unittest.main()`, and, when it calls `unittest.main(exit=False)`, must exit nonzero itself when a test case fails; a file that only defines `test_` functions for pytest runs none of them and exits 0, which the test runner reports as a pass. No nc-test-suite in the repository uses pytest.

## Pass or fail: the exit code alone

An nc-test-suite passes when its process exits with code 0. It fails when it exits with any other code, when a signal kills it, or when it runs past its time limit, which the docstring's PER-SUITE TIMEOUT section sets.

The test runner reads no text an nc-test-suite prints to decide whether it passed. The test runner reads test case lines such as `PASS`, `FAIL` or `ok` only to time and record each test case. nc-test-suites print success in several wordings, such as "all cases passed" or "OK", so no wording can be trusted. An nc-test-suite that finds a failure must exit nonzero: printing its own "FAIL" and exiting 0 is reported as a pass.

The exit-code page, `docs/nedschorus-wiki/nedschorus-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, asks more of a test file than the test runner checks today: exit 1 when a test case fails and 2 when it could not run, and print a verdict line as the last line of standard output. The form of that verdict line is not decided yet, and until the test runner is changed to read it, the test runner reads every nonzero exit code as a fail.

The test runner prints a line opening `PASS`, `FAIL` or `NOT RUN` as each nc-test-suite finishes, then each nc-test-suite that failed or got a `NOT RUN` line, again with its log file, then every `SKIP` line, and ends with a line opening `SUMMARY:`. A `NOT RUN` line is for an nc-test-suite whose bwrap, once the test runner had started it, failed before starting the nc-test-suite's process: no test case ran, so the nc-test-suite counts as neither a pass nor a fail, and the test run goes on to its `SUMMARY:` line. A test run stopped by a signal, or one the test runner ended early because it could not prepare an nc-test-suite's nc-test-sandbox before starting bwrap for it, could not start an nc-test-suite's process, or could not admit an nc-test-suite to start, as the docstring's ADMISSION section describes, prints no `SUMMARY:` line; it prints a line opening `run-all-test-suites: not run to the end` instead. The docstring of `scripts/run-all-test-suites.py` gives every line's exact form, under OUTPUT, and every exit code, under EXIT.

## Skipped test cases: the `SKIP` line

An nc-test-suite sometimes cannot run one of its test cases, for example because a tool the test case needs is not installed. It then prints one line for that test case and goes on with the other test cases. Print a line that opens with `SKIP` and a space, then gives the test case and the reason; the test runner checks only that opening, so the second space and the colon in the example below are optional. Any other form, such as `SKIP:` or unittest's own skip, is not counted, and `scripts/test-suites-source-scan-for-skipped-case-prints-run-all-test-suites-cannot-count-test.py` fails on it. When the machine itself is the cause, its platform or what is installed on it, put `[this machine cannot run it]` right after `SKIP` and its spaces; the test runner reads the mark only there, and its docstring says what the mark changes. Print one line per skipped test case. Example: `SKIP  [this machine cannot run it] the hand-run command's lock case: /usr/bin/flock is missing; it exists on Linux only`.

The test runner counts every line of an nc-test-suite's output that matches the regular expression `^SKIP\s`, and shows the count and each line as the section above says. A skipped test case never changes whether the nc-test-suite passed: an nc-test-suite that skips every test case and exits 0 is reported as a pass. The test runner counts lines, so a line that names several test cases counts as one.

GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) proposes replacing the `SKIP` line with `SKIPPED test case "<name>"; reason: <reason>`, printed by one shared function, and changing the test runner's pattern to match. Until that change is merged, print the `SKIP` line.

## Where the results are kept

Every test run writes its whole report to `test-run-report.txt` in its log directory, which the test runner's first output line names, beside one log file per nc-test-suite. Unless `--log-dir` names another directory, the log directory is under the system temp directory and is deleted two days after the test run ends, so copy anything you need to cite before then.

`scripts/scheduled-full-test-run-of-main.py` runs every nc-test-suite on main once a day on each machine, ned-box and the Mac, at the times `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` gives; a Mac run missed while the Mac sleeps starts when it wakes. It writes one record per machine and day to `nedlern@ned-box:/home/nedlern/nedschorus-logs/scheduled-full-test-runs-of-main/<machine>/<YYYY-MM-DD>.txt`, where `<machine>` is `ned-box` or `mac` and the date is the date in America/Los_Angeles when the run started. The record holds the run's failures and counted `SKIP` lines; the docstring of `scripts/scheduled-full-test-run-of-main.py` lists all it holds. The full report and the nc-test-suites' log files stay on the machine that ran them, in `<system temp directory>/nedschorus-scheduled-full-test-run-of-main/logs`, which the record names and the next day's run replaces.

## An nc-test-suite that measures something

An nc-test-suite that measures something, such as a duration or how often a hook's reminder is right, prints the number and the threshold, and passes or fails against the threshold, which its author may set by judgement, saying why in a comment beside it. Work whose result is a number with no pass or fail is not an nc-test-suite; it is a check, and reports as the exit-code page, `docs/nedschorus-wiki/nedschorus-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, says.

## Canary tests: decided, not yet built

A canary test runs a real outside program that the project does not write, such as `codex` or `gh`, to check that it still behaves the way our code relies on. It is a kind of contract test; it is not a canary release, the software-engineering sense of "canary". The user decided the rules below in approval-walks (user-ruled 2026-10-19 to 2026-10-26). No canary test, and no canary runner, the program that will run one, exists yet.

A canary test is one Python file. Its last line of standard output is exactly `#canary_pass`, and it exits 0, when the outside program behaved as relied on; or exactly `#canary_fail`, and it exits 1, when the outside program did not. The canary runner, not the canary test, gives the third result, `#canary_no_answer`, which means the canary test could not tell: when the last line of standard output is anything else, when the exit code does not match the line, or when the canary test runs past its time limit and the canary runner kills it. So a canary test that finds it cannot check, for example because the outside program is logged out, prints neither hashtag, whatever its exit code, and its result is `#canary_no_answer`. The canary runner logs standard output and standard error together, but takes the result from standard output alone (user-ruled 2026-10-23). The canary runner writes the log of every run of a canary test kept in the repository, scheduled or by name before a merge, to `nedlern@ned-box:/home/nedlern/nedschorus-logs/canaries/scheduled/<machine>/<YYYY-MM-DD>T<HHMMSS>-<suite path with each / as __>.txt`, where `<machine>` is ned-box for now, with the date and time in America/Los_Angeles at the run's start, and the full hash of the commit it ran at as the log's first line (user-ruled 2026-10-26).

The extra line is what tells "the outside program failed the check" apart from "the canary test could not give an answer": an exit code alone reports both as a fail.

Today's test runner judges every file it runs by its exit code alone, as above, and in its nc-test-sandbox an outside program such as `gh` or `codex` has no network and no login. The test runner is to start each file whose name ends `-canary-test.py` through the canary runner, outside the nc-test-sandbox, one at a time, under the time limit the file declares in a constant (user-ruled 2026-10-26). That change to the test runner is made in the pull request that commits the first canary test kept in the repository, and no canary test is committed before it (user-ruled 2026-10-20).
