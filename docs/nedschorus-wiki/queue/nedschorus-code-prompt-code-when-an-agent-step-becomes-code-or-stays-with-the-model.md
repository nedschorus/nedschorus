# Code-prompt-code: when a step given to an agent becomes code, and when it stays with the model

This page is for an agent that writes agent-instructions, such as a `CLAUDE.md` line, a skill step, an `-instructions.md` file or the prompt a program gives a subagent, or that writes a tool-message-to-agent, such as a hook's refusal or a script's error. A step is one piece of work that such a text gives to one actor; a sentence that gives out three pieces of work holds three steps. The actor is most often the model, meaning the agent that follows the text, and sometimes a person, such as the user when a text tells him to run a command on his Mac. For each step, the page says how to decide whether code should take it over, or whether it should stay with the model or the person. That split is what code-prompt-code (CPC) programs are built on. The glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`, says what code-prompt-code is, and `docs/nedschorus-wiki/nedschorus-ai-native-software-development-objective.md` says why the project builds that way. The terms cold-read-fast-read, mechanization-adversarial-prompt and walk-document are in the skills glossary, `.claude/skills/skills-glossary.md`.

## Where to look

The user has most often asked for code about a text that adds or changes agent-instructions, a one-line edit as often as a whole new file, and about an approval-walk item that proposes such a text; give those texts the closest look. The agent-seat cold-read-research searched the transcripts from July to October 2026 and found 107 messages in which the user asked or said that what an agent had shown him could be code, a script or code-prompt-code. By cold-read-research's later classification, 84 of the 107 answered an approval-walk item. Of the 64 of the 107 sent on or after 2026-10-15, 45 answered a turn that a word match marked as adding instructions: the turn held words such as "add a rule", "new line" or "insert a step", or named `CLAUDE.md`, an `-instructions.md` file, a skill or a brief. These are pointers to where to look, not a way to decide: since 2026-10-15 that word match fired on 1,277 turns, and only 45 of them, 3.5%, drew such a request, against 2.8% of all the turns the user answered. Of the heuristics cold-read-research tested on a text's surface, such as its length, its numbered lines or its verbs, none with enough matches to judge was followed by such a request on more than about 7% of the texts it matched. Whether a step should be code is judged step by step. The figures are in two reports: `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/cold-read-research/cpc-trigger-research-2026-10-28/cpc-trigger-research.md` and, for the 84, section 3 of `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/cold-read-research/cpc-trigger-research-2026-10-28/cpc-question-measurement-2026-10-29.md`.

A tool-message-to-agent gives an agent steps just as a Markdown file does, and fewer checks reach it. One put to the user as an approval-walk item gets a cold-read-fast-read, whose Question 4 asks which of its steps code could do. One that an agent adds to a `.py` file gets a reminder from `nc-systems/general-tools/python-edit-changed-tool-message-to-agent-strings-check-reminder-hook.py`, with the message's cold-read-fast-read command, only when the hook finds it: the hook reads only edits made with the Edit, MultiEdit or Write tool outside test files, misses messages built in ways it does not look for, and lists at most 20 messages per edit. One written into a `.sh` file gets no reminder. A pull request reviewer gives the English of such a message no finding, by `CLAUDE.md`'s review scope, except a finding that the message names a file, a flag or a script that does not work as the message says. So the agent that writes a tool-message-to-agent is the one sure to go through its steps as this page says, whether or not a cold-read-fast-read also does. In the 11 days from 2026-10-18 to 2026-10-28, a string match found such text added to `.py` or `.sh` files in 68 merged pull requests, by section 4 of the second report above; 9 of the 10 hits cold-read-research checked by hand were real tool-messages-to-agent.

## The split

The mechanization-adversarial-prompt, `docs/agents/sanity-checker-mechanization-adversarial-prompt.md`, draws the line this project uses, in its two bullets beginning "The model handles" and "Code handles". In short: the model keeps what needs judgment, such as understanding ambiguous intent and drafting open-ended content; code takes work where variability adds nothing, such as validation, parsing, calculation, state transitions, sequencing and formatting contracts. The prompt's bullets have the full lists. Its overall question, "what here relies on an LLM following English instructions, or on a human remembering to do something, where code could do the job?", is asked of each step through four questions, Encode, Constrain, Externalize and Verify; Verify is asked of every step, even one whose judgment stays with the model, because code may still check what the model produces. Every cold-read-fast-read and cold-read-full-run asks that overall question as its Question 4, so to have a fresh reader go through a text step by step, run `nc-systems/cold-read/cold-read-fast-read.py --target <file>` on it and judge each item of its Question 4 section against the four cases below.

When a step moves into code, the program does the normal case and hands every other case it detects back to the agent, with a tool-message-to-agent saying what failed, as the principle in [Move mechanical agent chores into programs and hooks](https://github.com/nedschorus/nedschorus/issues/1036) says. A case that a fixed rule settles without judgment can count as part of the normal case: the first example's program, asked to open a pull request that is already open, records that pull request's link instead of handing the case back. `CLAUDE.md` allows the program a retry only for a passing fault, one that clears by itself, on an operation safe to repeat, with a limit on attempts, and only when the rule the third case below quotes allows it. What is left in the text for the agent is then three things: when to run the program, unless a hook runs it; the judgment the program cannot make; and what to do with what the program hands back, which can be one line, such as "If a command refuses or fails, do what it prints.", when the program's tool-messages-to-agent say what to do.

When the answer for a step is code and the program does not exist yet, the text keeps the step until the program merges, as rung 6 of `docs/nedschorus-wiki/nedschorus-enforcement-ladder.md` says of a do-or-not-do rule. The pull request that adds the program also takes the step out of the text, or cuts it down to what is left for the agent, because `CLAUDE.md` has each pull request carry every document it would otherwise break. What the ladder calls a governing principle is not such a step: the ladder keeps it as text for good.

## When code is the wrong answer

Asked of a text, the mechanization-adversarial-prompt's overall question nearly always finds something: cold-read-research gave Question 4's wording to 65 texts of 80 words or more from the transcripts, and every answer named at least two numbered items; of 5 answers it checked by hand, all 5 named a step code could do, and 4 were worth suggesting. So before you propose code for a step, check it against these four cases:

- **The step needs judgment.** Deciding whether a review finding still holds, or which findings belong in one pull request, needs judgment, and the decision stays with the model. Code can still take the work around the decision: as in the first example below, it can carry the order of such steps, record each decision and check its form.
- **The step works reliably, costs little, and fails loudly.** In the mechanization-adversarial-prompt's words, such a step "is not a finding": code could do it, but would not pay for itself, so the step stays where it is. For a new step, judge it by a step like it already in use.
- **The code would be a guard, a validation, a retry or a workaround that `CLAUDE.md`'s rule does not allow.** The rule allows one only when "the failure has happened, as a citation from the user, an agent or a machine shows, or concrete evidence shows it is foreseeable within the next 30 days; and it would lose or damage work, stop work beyond the task that failed, or go unnoticed until it does one of those." When it does not, leave the guard out, from the text as well as from code, as the third example below did.
- **The text gives no step that code could take.** This case is about a whole text, before you go through its steps: a summary or a definition gives no one work to do. Of 20 approval-walk items since 2026-10-15 that cold-read-research judged by hand, each matched by the word match above and none drawing a request for code, 16 were summaries, definitions, judgment calls, or proposals already made in code, and 3 or 4 proposed steps that code could do.

A step that code already does needs no line in the text beyond when to run that code.

The first case decided this page's own design. The surface heuristics above predicted the user's requests only weakly, at best about twice as often as the 2.8% of all turns, so this page teaches the judgment with examples, and Question 4 of the cold reads puts the question to each text, instead of a hook that would tell an agent from a text's surface when to think of code.

## Examples from this project

### The prompt for answering a pull request's non-blocking findings

After merge-lane-2 merges a pull request, it can send the author non-blocking findings to follow up. A hook hands the author a brief, which `build_follow_up_request_forked_subagent_brief` in `scripts/pull-request-follow-up-request-after-merge-finding-answers-and-next-step.py` builds; the brief's last lines are the prompt a subagent follows to answer the findings. The earlier version of that prompt, below, is saved at `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/prime-intellect/cpc-page-follow-up-brief-before-and-after-from-cold-read-research-2026-10-29.md`, from a build that never reached main, in which the program had an earlier name; in both versions, "Program:" stands for the command that runs the program with the pull request's number.

The earlier version gave the subagent five numbered items to carry out in order, with a loop over topics; each "topic branch" in it is an nc-topic-branch:

> For the subagent, in your own worktree:
> 1. Check each finding against origin/main; leave out any that no longer holds, and any that would change a design or decision of the user's, ending your report with a question to him on each of these.
> 2. Group the findings you take on by topic: one pull request per topic.
> 3. For each topic, Program: start-topic-branch <topic-branch>
>    Make the change with its tests, and commit.
>    Write follow-up-pull-request-title-and-description.md at your worktree's root: the title, a blank line, then the description. Do not commit it.
>    Program: open-pull-request --handled-finding-numbers <n>[,<n>...]
> 4. For each finding you leave out, Program: record-finding-leave-out-reason <n> --reason "<why>"
> 5. Program: finish-follow-up-request-and-print-merge-lane-2-message
>    Send the message it prints to merge-lane-2 with SendMessage.

The user asked "could this be more code prompt codey?", and on 2026-10-28 approved the following one-line version as item 2.1 of cold-read-research's approval-walk cold-read-research-carried-items-2026-10-28, whose walk-document, copied to the log-store, is `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/cold-read-research-carried-items-2026-10-28.md`:

> For the subagent, in your own worktree: Program: next-step. Do what it prints, then run Program: next-step again, until it prints "Done".

On main, the brief ends with that line and one more: "If a command refuses or fails, do what it prints." Before them come the findings, a line saying what "Program:" means, and lines for the author on dispatching the subagent.

`next-step` fetches origin, reads what the program has recorded about which findings each nc-topic-branch took on and which findings have an answer, and prints only what comes next and what to do about it. For an nc-topic-branch whose findings have no pull request yet, it prints, in part:

> Next: topic branch <topic-branch> takes on findings <n> and <n>, which have no pull request yet.
> On that branch, make the change with its tests, and commit, unless you have.
> [...]
> Then run: python3 scripts/pull-request-follow-up-request-after-merge-finding-answers-and-next-step.py <number> open-pull-request

There are no finding numbers to type. When nothing is left to do, the output of `next-step` begins "Done:". The prompt can be one line because each output of `next-step` says in full what to do next, such as the one that opens "Next: judge findings <n> and <n>, which have no answer yet".

What moved into code: the order of the steps, the loop over topics, working out from the program's record which findings still need an answer, and the finding numbers that `open-pull-request` used to be given. Code also gained a fetch of origin, which the earlier version lacked. What stayed with the model: judging whether a finding still holds or needs the user's decision, grouping the findings by topic, which the program then records and prints back as each nc-topic-branch's findings, writing the change and its pull request description, and sending merge-lane-2 the message the program prints, which a program cannot send.

### The conflict check before a push

On 2026-09-23, the agent-seat whose agent-home was `/Users/el/agents/merge-lane` on the Mac put to the user, as item 2.1 of an approval-walk, a new `CLAUDE.md` sentence for every agent to follow:

> Before you push a branch, and whenever you read that its pull request conflicts with main, run `scripts/branch-conflict-check.py --pull-request <n>` from the branch's checkout, leaving out `--pull-request` before the pull request exists, and do what its VERDICT line says: exit 0 is clean, 1 is a conflict to merge by hand, 2 is no answer.

The user answered: "2.1 sounds reasonable, but this looks like it should be a script, not a prompt" (line 278 of `nedlern@ned-box:/home/nedlern/nedschorus-logs/agent-session-files-by-machine/mac/projects/-Users-el-agents-merge-lane/7807f5bd-d1ee-4609-aefd-ea669f68ce67.jsonl`). The same day, commit 3a1c60029, "A pre-push hook refuses to push a branch that conflicts with main", made `scripts/git-client-side-hooks/pre-push` run the conflict check, through `scripts/git-client-side-hooks-pre-push-conflict-check.py`, on each branch pushed to origin other than main. Remembering to run the conflict check before a push, and reading its exit code, moved into code. From the conflict check, the hook hands back two cases: a refusal when the conflict check reports a conflict, and, when the conflict check cannot give an answer, lines telling the agent to run `scripts/branch-conflict-check.py` by hand, while the push goes through; the hook on main also runs other checks. `CLAUDE.md` keeps one sentence: "When `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`, do what its report says." `scripts/branch-conflict-check.py` now also chooses how to clear a conflict: its report says whether to replace the pull request, merge main into the branch or rebase the branch, with the commands to run. Resolving the conflicting changes, and carrying out the report, stay with the agent.

### A hook's refusal message, and the retry left out

On 2026-10-17, the agent-seat agent-instructions-editor put to the user, as item 10 of the approval-walk agent-instructions-editor-every-open-decision-2026-10-15, whose walk-document is `nedlern@ned-box:/home/nedlern/agents/agent-instructions-editor/docs/walk/agent-instructions-editor-every-open-decision-2026-10-15.md`, a new tool-message-to-agent for the guard now at `.claude/guard-hooks/session-location-write-guard.py` to print when git failed while the guard checked a write from a detached HEAD. The message refused the write, then told the agent to run `git status` and tell four situations apart; its second to fourth lines read:

> Run git status: it says whether a rebase, merge, cherry-pick or revert is stopped here.
> If git status fails too: tell the user what it printed; until git works in this checkout, this guard refuses every write from a detached HEAD here.
> If an operation is stopped here: try the write again, because this guard checks again on every call. [...]

The user asked "could this be CPC?" (line 5984 of `nedlern@ned-box:/home/nedlern/nedschorus-logs/agent-session-files-by-machine/ned-box/projects/-home-nedlern-agents-agent-instructions-editor/fd3dde6d-34c5-4198-9aa4-1209e4d8b1a6.jsonl`). The agent's answer proposed moving the telling apart into the guard: when git failed, the guard would check again by itself and act on the second answer, and only when git failed both times would the agent get the new message, shrunk to three lines. The same answer named the cost, a retry and a test for each outcome, against a failure nobody had yet seen, and recommended leaving the retry out until one was seen. The user's answer, at lines 6003 to 6039 of the same file, asked for a likely failure, not only a seen one, as the condition for building a retry, and said that "there isn't much reason to guard against quickly and easily corrected failures like the one you just cited, as long as the agent will notice that error." Commit 6d6ad8bb4 wrote that answer into the `CLAUDE.md` rule the third case above quotes. Neither the refusal message nor the retry was built. The guard's design changed instead: when git cannot answer, the guard on main lets the write go ahead and prints a note saying it could not check the write, which tells the agent to switch to a new branch before committing when its checkout is on a detached HEAD with nothing stopped, and to tell the user. Telling the four situations apart was dropped rather than moved into code: with the write let through, no step needs it.
