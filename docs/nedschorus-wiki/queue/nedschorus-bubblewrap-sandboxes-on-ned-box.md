# Bubblewrap sandboxes on ned-box

Read this page before you write a program that starts a bubblewrap sandbox (`bwrap`) on ned-box, or before you run one program inside the sandbox of another, such as the test runner `scripts/run-all-test-suites.py` inside an agent's sandbox. It says why a second bubblewrap sandbox cannot start inside a first on ned-box, how the test runner copes with that, and, for each program on main that starts a sandbox, what the sandbox shows, what it hides and how the agent inside reaches its login file.

Every `file:line` citation is to main at commit `b14a66236ef1fa7797e1de6f1c4f8837d39c041b`; a later change to a cited file can move or change the line. Each fact is marked **Observed**, with the date and the command; **Code**, for what the cited code does, read and not run; or **Documented**, for what a docstring, a GHI-MD or a configuration file's comment claims. Every observation on this page was made on ned-box on 2026-11-11 between 02:03 and 02:08 UTC, from an agent-session's shell that was not itself inside a sandbox, except the one dated 2026-10-10. The commands, their full output and the scripts they ran are in `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/prime-intellect/bubblewrap-sandboxes-wiki-page-observations-2026-11-11/observations.md`, whose numbered items this page cites as "observation N".

## A second bubblewrap sandbox cannot start inside a first

- **Observed** (observation 1): `sysctl` prints `kernel.apparmor_restrict_unprivileged_userns = 1` and `kernel.unprivileged_userns_clone = 1`. bubblewrap is version 0.11.1, at `/usr/bin/bwrap`, and is not setuid; the AppArmor profile `/etc/apparmor.d/bwrap-userns-restrict` exists for it.
- **Observed** (observations 2 and 3): `bwrap --ro-bind / / --dev /dev --proc /proc -- sh -c 'echo single-ok'` prints `single-ok` and exits 0. The same command with a second `bwrap` inside the first prints `bwrap: No permissions to create a new namespace, likely because the kernel does not allow non-privileged user namespaces` and exits 1.
- **Documented**: that profile's header comment says bwrap may make user namespaces but "its children do not have capabilities, blocking bwrap from being able to be used to arbitrarily by-pass the user namespace restrictions". That is why a process inside the first sandbox cannot make the new user namespace a second sandbox needs. The same limit was observed on 2026-10-10, when a Docker container failed the same way: `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/prime-intellect/benchmark-sandbox-nesting-probe-2026-10-10.md`.
- **Observed** (observation 6): Codex's own sandbox hits the same limit. `codex sandbox -- sh -c 'echo codex-sandbox-ok'` (codex-cli 0.159.3) works alone; inside `bwrap` it prints the same "No permissions to create a new namespace" line and exits 1. That was bare `codex sandbox`, not one of this project's Codex launchers below.

So on ned-box a program that starts a bubblewrap sandbox fails when it runs inside another program's bubblewrap sandbox: the test runner, unless told it is already inside one; an agy cold-read-cell; the Gemini launcher; agy for one prompt; and every command a Codex model runs.

## The test runner inside another program's sandbox

- **Code**: the test runner reads the environment variable `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX`, whose name is its constant `SIGNAL_SANDBOX_INSIDE_VARIABLE` (`scripts/run-all-test-suites.py:823`). When the variable is set, `signal_sandbox()` returns no command prefix and no reason (`scripts/run-all-test-suites.py:2545-2546`), so the test runner starts no sandbox and runs every suite inside whatever sandbox the test runner itself was started in. The test runner sets the variable inside every sandbox it starts (`scripts/run-all-test-suites.py:2556-2557`), so a test runner that a suite starts never tries to nest.
- **Code**: without the variable, the test runner tries `bwrap ... true` once before any suite runs, and when that fails raises `SignalSandboxCouldNotStart` (`scripts/run-all-test-suites.py:2558-2566`); the test runner then stops with exit 2 rather than run the suites unconfined (docstring, `scripts/run-all-test-suites.py:160-163`).
- **Observed** (observation 7): `signal_sandbox()`, called inside `bwrap --dev-bind / / --unshare-pid --proc /proc`, raised `SignalSandboxCouldNotStart` with bwrap's "No permissions to create a new namespace" text; inside the same bwrap with `--setenv RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX 1` it returned the empty prefix.
- **Observed** on 2026-10-10 (the probe record cited above): the test runner, started with `--only-suites-whose-recorded-inputs-changed-since HEAD~1` inside one bwrap with `--unshare-pid --die-with-parent --proc /proc --setenv RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX 1`, printed "SUMMARY: 15 passed, 0 failed, 15 total" and exited 0.

A program that starts a bubblewrap sandbox and runs the test runner inside it therefore sets `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX=1` in that sandbox, and that sandbox is then all that confines the suites. **Documented** in GHI [Each test suite on ned-box runs in its own throwaway test environment, and suites start by free CPU and memory instead of waiting for a machine-wide lock](https://github.com/nedschorus/nedschorus/issues/1374), under "The machine lock" and "Records (point 4)": a test runner nested this way takes the machine-wide test-run lock, as on a machine without bwrap, and its report has no CPU or memory figures for its suites.

## Suites that fail inside a bubblewrap sandbox

**Code**: the dict `SUITES_RUN_WITHOUT_ANY_SANDBOX` (`scripts/run-all-test-suites.py:849-876`) maps each suite that cannot work inside the test runner's sandbox to the reason. When the test runner starts the sandboxes itself, it runs these suites outside any sandbox (`scripts/run-all-test-suites.py:3049-3050`) and names each in its report with the reason. When the test runner runs inside another program's sandbox, these suites run inside that sandbox like every other suite, and the dict's reason says why they fail there. At the pinned commit the dict names seven suites:

- Five fail because bwrap cannot start inside bwrap. `nc-systems/cold-read/tests/cold-read-agy-cell-real-sandbox-test.py` and `nc-systems/general-tools/tests/agy-print-prompt-run-in-empty-home-sandbox-real-sandbox-test.py` start the real bwrap of the program each tests; `scripts/run-all-test-suites-test-sandbox-escape-test.py` builds the test runner's sandboxes itself; `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py` and `scripts/run-all-test-suites-overlapping-runs-real-process-test.py` start the test runner, whose suites run in bwrap.
- `scripts/mac-request-from-ned-box-forced-command-test.py` runs the real `ssh`, which refuses its root-owned configuration files because inside the sandbox's user namespace they show as owned by nobody. **Observed** (observations 4 and 5): inside `bwrap --ro-bind / / --dev /dev --proc /proc`, `stat` shows `/etc/ssh/ssh_config` as owned by `nobody` (outside, `root`), and `ssh -G localhost` prints `Bad owner or permissions on /etc/ssh/ssh_config.d/20-systemd-ssh-proxy.conf` and exits 255; outside, it exits 0.
- `scripts/recover-crashed-seats-started-tmux-server-lands-in-user-systemd-manager-cgroup-without-xdg-runtime-dir-real-process-test.py` starts a tmux server in a scope of the user's systemd, whose session bus the test runner's sandbox hides by making `/run` an empty tmpfs. Whether this suite fails inside another program's sandbox depends on whether that sandbox hides `/run` too; that has not been observed.

Read the dict for the current suites and reasons; this list is the dict at the pinned commit. **Code**: a test runner given `--only-suites-whose-recorded-inputs-changed-since` without `--only-suites-named`, where the test runner starts the sandboxes itself, leaves these suites out of its selection and prints the command that runs each by hand (docstring, `scripts/run-all-test-suites.py:640-650`).

## Programs on main that start a sandbox

### The test runner, and the programs that use its sandbox

- **Paths**: `scripts/run-all-test-suites.py` builds the sandbox. `scripts/run-suite-in-signal-sandbox.py`, which runs one suite or one mutant, and `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py` call its `signal_sandbox()` (`scripts/run-suite-in-signal-sandbox.py:541`, `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py:1514`).
- **Where the settings live**: the bwrap arguments every suite shares are `TEST_SANDBOX_BWRAP_ARGUMENTS_SHARED_BY_EVERY_SUITE` (`scripts/run-all-test-suites.py:803-822`); `bwrap_arguments_for_one_suites_test_sandbox()` (`scripts/run-all-test-suites.py:2768`) adds each suite's own. The three dicts that say which sandbox a suite gets are read from the checkout under test (docstring, `scripts/run-all-test-suites.py:177-186`).
- **What the sandbox shows and hides**: the sandbox is the suite's nc-test-sandbox; the glossary's entry for that term points to the test runner's docstring under "THE SIGNAL SANDBOX IS ALSO EACH SUITE'S NC-TEST-SANDBOX" (`scripts/run-all-test-suites.py:113-163`), which says what a suite sees. **Observed** (observation 8), inside the shared arguments alone, without each suite's additions: process 1 is `bwrap`; the home directory holds only `~/.gitconfig`, `~/.local/bin/ruff`, `~/.local/lib` and the directories above one log-store file, as `TEST_SANDBOX_HOME_PATHS_SHOWN_READ_ONLY` (`scripts/run-all-test-suites.py:761-770`) lists; `/run` holds only an empty `user` directory; and `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX` is 1.
- **Login file**: no agent runs inside, and no login file is there. The home directory is an empty tmpfs apart from the paths above, and no environment variable that `TEST_SUITE_CREDENTIAL_ENVIRONMENT_VARIABLE_PATTERNS` (`scripts/run-all-test-suites.py:794-797`) matches reaches a suite.
- **Code**: `scripts/run-suite-in-signal-sandbox.py` refuses a suite that `SUITES_RUN_WITHOUT_ANY_SANDBOX` names (`scripts/run-suite-in-signal-sandbox.py:528-530`), and before the suite starts confirms, inside the sandbox, that process 1 is bwrap (`scripts/run-suite-in-signal-sandbox.py:183`).

### The agy cold-read-cell

- **Path**: `nc-systems/cold-read/cold-read-agy-cell.py`.
- **Where the settings live**: `credential_sandbox_prefix()` (`nc-systems/cold-read/cold-read-agy-cell.py:198-229`), built from the lists `CREDENTIAL_DIRECTORIES`, `CREDENTIAL_FILE_NAME_PATTERNS` and `REVIEWER_PROGRAM_LOGIN_FILES` (`nc-systems/cold-read/cold-read-cell-common.py:63-77`).
- **What the sandbox shows and hides** (**Code**): called with no writable paths, as this program calls it, bwrap binds the whole file system read-write (`--dev-bind / /`), mounts an empty tmpfs over each credential directory that exists (`~/.config/nedschorus`, `~/.config/gh`, `~/.ssh`), and binds `/dev/null` over each file named `*.token` or `.env` found at launch under the home directory and the repository, and over Claude's and Codex's login files. The network is shared. The docstring says a credential file made after launch, or one outside the home directory and the repository, is not hidden (`nc-systems/cold-read/cold-read-agy-cell.py:81-86`).
- **Login file**: agy reads its own login under `~/.gemini/`, which the sandbox leaves readable and writable. **Observed** (observation 9), inside this prefix: `~/.claude/.credentials.json` and `~/.codex/auth.json` read as empty, `~/.config/gh` holds no files, `~/.gemini/antigravity-cli/antigravity-oauth-token` is readable, and `~/.gemini` is writable.
- **Code**: with no `bwrap` on PATH the program refuses before agy starts (`nc-systems/cold-read/cold-read-agy-cell.py:252-261`).

### The Gemini launcher

- **Path**: `scripts/run-gemini-task-from-brief.py`.
- **Where the settings live**: the same `credential_sandbox_prefix()`, called with writable paths and a network switch (`scripts/run-gemini-task-from-brief.py:126-129`).
- **What the sandbox shows and hides** (**Code**): because the launcher always passes writable paths, bwrap binds the whole file system read-only (`--ro-bind / /`), adds a private `/dev`, and binds read-write only the report file and, with `--sandbox workspace-write`, the checkout and each `--writable-root` (`nc-systems/cold-read/cold-read-agy-cell.py:215-220`). Without `--network` it adds `--unshare-net` (`nc-systems/cold-read/cold-read-agy-cell.py:221-222`). The credential directories and files are hidden as in the agy cold-read-cell.
- **Login file**: **Observed** (observation 9), inside this prefix with no writable paths: the agy login file is readable, Claude's and Codex's login files read as empty, and `~/.gemini` is not writable (`touch` there is refused). What agy does when it must refresh its login and cannot write `~/.gemini` has not been observed.

### agy for one prompt, in an empty home directory

- **Path**: `nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py`.
- **Where the settings live**: `empty_home_sandbox_prefix()` (`nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py:84-99`).
- **What the sandbox shows and hides** (**Code**): only `/usr` and `/etc`, read-only; a private `/dev`, `/proc`, `/tmp` and `/run`, with `/run/systemd/resolve` bound in when it exists, so that host names resolve; the agy binary, read-only at `/run/agy-bin/agy`, off PATH; a fresh empty working directory; and process, IPC and host-name namespaces of its own. The network is shared.
- **Login file**: `~/.gemini` is the only part of the home directory there, bound read-write. **Observed** (observation 9): `ls -A ~` inside lists only `.gemini`; the agy login file is readable and `~/.gemini` writable.

### The Codex launchers

- **Paths**: `scripts/run-codex-task-from-brief.py`; `nc-systems/cold-read/cold-read-codex-cell.py`; and `scripts/code-review-codex-cell.py`, which `scripts/merge-lane-code-review-codex-cell-run-on-pull-request-head.py` runs on a pull request.
- **Where the settings live**: none of them calls `bwrap` itself. Each passes Codex a named permission profile through `-c` options built by `codex_credential_denying_permission_profile_arguments()` (`nc-systems/cold-read/cold-read-cell-common.py:172-195`): `codex-task-no-credentials`, extending `:read-only`, or `:workspace` with `--sandbox workspace-write` (`scripts/run-codex-task-from-brief.py:93-94`); `cold-read-no-credentials`, extending `:workspace`, with the network on (`nc-systems/cold-read/cold-read-codex-cell.py:170-176`); and `code-review-no-credentials`, extending `:read-only` (`scripts/code-review-codex-cell.py:456`, `scripts/code-review-codex-cell.py:654-655`).
- **What the sandbox shows and hides** (**Code**): the profile denies each credential directory that exists, each reviewer program's login file that exists, and, on Linux, each credential-named file found at launch; on Linux with `:workspace` it also makes `/tmp` and `$TMPDIR` read-only. **Documented** (`scripts/code-review-codex-cell.py:163-168`): Codex runs each of the model's commands through a `codex-linux-sandbox` child process, which execs `bwrap`.
- **Login file**: **Documented** (`nc-systems/cold-read/cold-read-codex-cell.py:89-93`, `nc-systems/cold-read/cold-read-cell-common.py:70`): the Codex program reads its login outside the profile, which governs only the model's commands, so denying `~/.codex/auth.json` to those commands leaves Codex logged in.

### Claude Code's own sandbox: off

**Observed** (observation 10): neither `.claude/settings.json` on main nor `~/.claude/settings.json` on ned-box has a `sandbox` key, and `~/.codex/config.toml` on ned-box has no line that names a sandbox. So the agent-seats' `claude` commands on ned-box run outside any bubblewrap sandbox, and a program they start may start one.

### The benchmark pilot's sandbox: designed, not built

GHI [A pilot of three past bug fixes, redone by agents on the code as it stood before each fix, to learn whether a benchmark of agent-instructions and hooks can be built from the project's history](https://github.com/nedschorus/nedschorus/issues/1505) specifies, under "Step 1: the sandbox probe" (`docs/issues/1505-a-pilot-of-three-past-bug-fixes-redone.md:31-45`), one bubblewrap sandbox for each invocation of `claude -p`. Its private home directory holds copies of `~/.claude/CLAUDE.md` and `~/.claude/settings.json`, and the real `~/.claude/.credentials.json` is bound in for reading and writing, so that a login refresh inside the sandbox updates the one file every agent-seat uses. The sandbox sets `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX`, and Claude Code's own sandbox stays off. All of this is **Documented** only: at the pinned commit no program on main builds this sandbox, and no record of the probe was found in the log-store on 2026-11-11, so none of it has been observed. Once the probe has run, this section is checked against the probe's record and rewritten from it.
