# Bubblewrap sandboxes on ned-box

Read this page before you write a program that starts a bubblewrap sandbox (`bwrap`) on ned-box, or before you run one program inside the sandbox of another, such as the test runner `scripts/run-all-test-suites.py` inside a sandbox that another program starts around an agent, like the one GHI 1505's pilot plans for `claude -p`. It says why a second bubblewrap sandbox cannot start inside a first on ned-box, how the test runner copes with that, and, for each program on main that starts a sandbox, what the sandbox shows, what it hides and, where an agent runs inside, how that agent reaches its login file.

Every `file:line` citation is to main at commit `b14a66236ef1fa7797e1de6f1c4f8837d39c041b`; a later change to a cited file can move or change the line. Every fact on the page carries one of three marks:

- **Observed**: seen on ned-box. ## A second bubblewrap sandbox cannot start inside a first

- **Observed** (observation 1): `sysctl` prints `kernel.apparmor_restrict_unprivileged_userns = 1` and `kernel.unprivileged_userns_clone = 1`. bubblewrap is version 0.11.1, at `/usr/bin/bwrap`, and is not setuid; the AppArmor profile `/etc/apparmor.d/bwrap-userns-restrict` exists for it.
- **Observed** (observations 2 and 3): `bwrap --ro-bind / / --dev /dev --proc /proc -- sh -c 'echo single-ok'` prints `single-ok` and exits 0. The same command with a second `bwrap` inside the first prints `bwrap: No permissions to create a new namespace, likely because the kernel does not allow non-privileged user namespaces` and exits 1.
- **Documented**: that AppArmor profile's header comment says bwrap may use user namespaces but "its children do not have capabilities, blocking bwrap from being able to be used to arbitrarily by-pass the user namespace restrictions"; the profile its children run under, `unpriv_bwrap`, allows `userns` and denies every capability (`/etc/apparmor.d/bwrap-userns-restrict`, lines 68 and 79). Which kernel check refuses the second sandbox was not established; turning the sysctl off to test it needs root and was not tried. The rule this page relies on is the observed one: on ned-box, as it is set up, a bwrap started inside a bwrap fails.
- **Observed** on 2026-10-10 (`nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/prime-intellect/benchmark-sandbox-nesting-probe-2026-10-10.md`): bwrap run inside a Docker container on ned-box also failed, with a different message, `bwrap: Creating new namespace failed: Operation not permitted`, both with Docker's default profile and with AppArmor and seccomp turned off for the container. A container is therefore no way around the limit; whether the same kernel setting causes that failure was not shown.
- **Observed** (observation 6): Codex's own sandbox hits the same limit. `codex sandbox -- sh -c 'echo codex-sandbox-ok'` (codex-cli 0.159.3) works alone; inside `bwrap` it prints the same "No permissions to create a new namespace" line and exits 1. That was bare `codex sandbox`, not one of this project's Codex launchers below; that the launchers' runs fail the same way inside another sandbox is inferred from this observation and from the **Documented** fact, under "The Codex launchers", that Codex runs each of the model's commands through `bwrap`.

So on ned-box a program that starts a bubblewrap sandbox fails when it runs inside another program's bubblewrap sandbox. The test runner, and the two programs that use its sandbox, `scripts/run-suite-in-signal-sandbox.py` and `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py`, can be told that they already run inside one, as the next section says. The agy cold-read-cell launcher (`nc-systems/cold-read/cold-read-agy-cell.py`), the Gemini task launcher (`scripts/run-gemini-task-from-brief.py`) and agy for one prompt (`nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py`) cannot, and neither can Codex for the model's commands; run each of them outside any bubblewrap sandbox.

## The test runner inside another program's sandbox

- **Code**: the test runner reads the environment variable `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX`, whose name is its constant `SIGNAL_SANDBOX_INSIDE_VARIABLE` (`scripts/run-all-test-suites.py:823`). When the variable has a non-empty value, `signal_sandbox()` returns an empty command prefix, and `None` in place of the reason it otherwise gives for running unconfined (`scripts/run-all-test-suites.py:2545-2546`): the test runner starts no sandbox, checks nothing about the sandbox it is in, and runs every nc-test-suite inside whatever sandbox the test runner itself was started in. An empty value counts as unset.
- **Code**: the test runner sets the variable to `1` inside every sandbox it starts (`scripts/run-all-test-suites.py:2556-2557`), so a test runner that an nc-test-suite starts inherits it and does not try to nest, unless the nc-test-suite removes the variable from the child's environment, as `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py` does on purpose (lines 162, 186 and 199-201).
- **Code**: without the variable, and with `bwrap` on PATH, the test runner tries `bwrap ... true` once before any nc-test-suite runs, and when that fails raises `SignalSandboxCouldNotStart` (`scripts/run-all-test-suites.py:2558-2566`); the test runner then stops with exit 2 rather than run the nc-test-suites unconfined. With no `bwrap` on PATH it runs the nc-test-suites unconfined and the report says why (`scripts/run-all-test-suites.py:2553-2555`).
- **Code**: `scripts/run-suite-in-signal-sandbox.py`, which runs one nc-test-suite or one mutant, is stricter. Started inside another sandbox, it runs the nc-test-suite only when the variable is exactly `1` (`scripts/run-suite-in-signal-sandbox.py:189-192`) and `/proc/1/comm` there reads `bwrap` (`scripts/run-suite-in-signal-sandbox.py:141-146` and `183-186`), that is, when the outer sandbox has a PID namespace of its own and mounts a fresh `/proc` (`bwrap --unshare-pid --proc /proc`); otherwise it refuses.
- **Code**: `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py` gets its sandbox from the same `signal_sandbox()` (`scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py:1514`), so the variable stops it, too, from trying to nest; what else it does inside another sandbox was not read for this page.
- **Observed** (observation 7): `signal_sandbox()`, called inside `bwrap --dev-bind / / --unshare-pid --proc /proc`, raised `SignalSandboxCouldNotStart` with bwrap's "No permissions to create a new namespace" text; inside the same bwrap with `--setenv RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX 1` it returned the empty prefix.
- **Observed** on 2026-10-10 (the 2026-10-10 record cited above), with the test runner of that date, before the nc-test-sandbox and its admission merged on 2026-10-15: the test runner, started with `--only-suites-whose-recorded-inputs-changed-since HEAD~1` and a private lock file inside one bwrap with `--unshare-pid --die-with-parent --proc /proc --setenv RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX 1`, printed "SUMMARY: 15 passed, 0 failed, 15 total; 5 cases skipped in 3 suites" and exited 0. The test runner at the pinned commit has not been run nested this way.

A program that starts a bubblewrap sandbox and runs the test runner inside it must therefore do three things:

- Set `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX=1` in that sandbox. None of the programs under "Programs on main that start a sandbox" below sets it in its own sandbox, so a model that runs the test runner inside one of them gets exit 2.
- Give that sandbox a PID namespace of its own (`bwrap --unshare-pid`). **Documented** (`scripts/run-all-test-suites.py:107-111`): the test runner's own sandbox puts each nc-test-suite in a PID namespace so that an nc-test-suite's signals reach only the processes it started, never the agent-seats, which run as the same account. With the variable set, the outer sandbox is all that confines the nc-test-suites, and the test runner does not check that it has a PID namespace.
- Decide which test-run lock the nested test runner takes. **Documented** in the GHI-MD of GHI [Each test suite on ned-box runs in its own throwaway test environment, and suites start by free CPU and memory instead of waiting for a machine-wide lock](https://github.com/nedschorus/nedschorus/issues/1374), in the bullets "The machine lock" and "Records (point 4)" of its Outcome (`docs/issues/1374-each-test-suite-on-ned-box-runs-in.md:64-65`): a nested test runner takes the lock, as on a machine without bwrap, and its report has no CPU or memory figures for its nc-test-suites. **Code**: the lock is the file `~/.claude/.run-all-test-suites.lock` (`scripts/run-all-test-suites.py:987`) as the outer sandbox shows it, so it is shared with the rest of the machine only when that sandbox shows the real `~/.claude`: inside a sandbox with a private home directory, the nested test runner takes a lock no other test run sees, and does not wait for them; and with the default `--wait-for-lock-seconds 0`, a test runner that finds the lock held exits 3 at once (docstring, `scripts/run-all-test-suites.py:33-36`). To share the lock, bind the real lock file into the sandbox, or pass `--lock-file` with a path both sides see; pass `--wait-for-lock-seconds` to wait instead of exiting 3.

## nc-test-suites that cannot work inside a bubblewrap sandbox

**Code**: the dict `SUITES_RUN_WITHOUT_ANY_SANDBOX` (`scripts/run-all-test-suites.py:849-868`) maps each nc-test-suite that cannot do its job inside its nc-test-sandbox to the reason. The test runner reads it from the checkout under test, and from its own file only when that checkout has none (docstring, `scripts/run-all-test-suites.py:182-186`). When the test runner starts the sandboxes itself, it runs these nc-test-suites outside any sandbox (`scripts/run-all-test-suites.py:3049-3050`) and names each in its report with the reason (`scripts/run-all-test-suites.py:4144-4148`). When the test runner runs inside another program's sandbox with the variable set, it has no outside to put them in, so these nc-test-suites run inside that sandbox like every other nc-test-suite. At the pinned commit the dict names seven nc-test-suites:

- Five cannot do their job because bwrap cannot start inside bwrap. `nc-systems/cold-read/tests/cold-read-agy-cell-real-sandbox-test.py` and `nc-systems/general-tools/tests/agy-print-prompt-run-in-empty-home-sandbox-real-sandbox-test.py` start the real bwrap of the program each tests; `scripts/run-all-test-suites-test-sandbox-escape-test.py` builds nc-test-sandboxes itself; `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py` and `scripts/run-all-test-suites-overlapping-runs-real-process-test.py` start a second test runner and need it to run its own nc-test-suites in bwrap.
- `scripts/mac-request-from-ned-box-forced-command-test.py` runs the real `ssh`, which refuses its root-owned configuration files because inside the sandbox's user namespace they show as owned by nobody. **Observed** (observations 4 and 5): inside `bwrap --ro-bind / / --dev /dev --proc /proc`, `stat` shows `/etc/ssh/ssh_config` as owned by `nobody` (outside, `root`), and `ssh -G localhost` prints `Bad owner or permissions on /etc/ssh/ssh_config.d/20-systemd-ssh-proxy.conf` and exits 255; outside, it exits 0.
- `scripts/recover-crashed-seats-started-tmux-server-lands-in-user-systemd-manager-cgroup-without-xdg-runtime-dir-real-process-test.py` starts a tmux server in a scope of the user's systemd, whose D-Bus session bus the nc-test-sandbox hides by making `/run` an empty tmpfs.

**Code**: inside another program's sandbox, some of these nc-test-suites print SKIP instead of failing. `scripts/run-all-test-suites-test-sandbox-escape-test.py:318`, `scripts/run-all-test-suites-overlapping-runs-real-process-test.py:113` and `scripts/recover-crashed-seats-started-tmux-server-lands-in-user-systemd-manager-cgroup-without-xdg-runtime-dir-real-process-test.py:41` skip every case when the variable is set. `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py:272-274` skips its killed-run cases when bwrap cannot start, and still runs its signal-helper cases, which have not been run inside another sandbox. The two agy real-sandbox nc-test-suites and the ssh nc-test-suite have no such skip, so a nested test runner that runs any of them is expected to report it failed and exit 1. Nothing on main leaves them out of a nested test run; a caller that wants a nested test run without them names the nc-test-suites it wants with `--only-suites-named`. No nc-test-suite was run inside a sandbox for this page.

**Code**: a test runner given `--only-suites-whose-recorded-inputs-changed-since` without `--only-suites-named` leaves out of its selection each of these nc-test-suites the selection would have picked, and prints the command that runs it by hand, only when the test runner starts the sandboxes itself (docstring, `scripts/run-all-test-suites.py:640-650`; code, `scripts/run-all-test-suites.py:3813-3816` and `4189-4194`). Inside another program's sandbox, a selective test run selects these nc-test-suites like any other.

The list above is the dict at the pinned commit; read the dict in the checkout under test for the current nc-test-suites and reasons.

## Programs on main that start a sandbox

The programs below were found at the pinned commit by `git grep` for `bwrap` in files other than tests, and for the callers of `codex_credential_denying_permission_profile_arguments()`, the one builder of the Codex launchers' permission profiles. A program that starts a sandbox some other way would not have been found.

### The test runner, and the programs that use its sandbox

- **Paths**: `scripts/run-all-test-suites.py` builds the sandbox. `scripts/run-suite-in-signal-sandbox.py` and `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py` call its `signal_sandbox()` (`scripts/run-suite-in-signal-sandbox.py:541`, `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py:1514`).
- **Where the sandbox settings are**: the bwrap arguments every nc-test-suite shares are `TEST_SANDBOX_BWRAP_ARGUMENTS_SHARED_BY_EVERY_SUITE` (`scripts/run-all-test-suites.py:803-822`); `bwrap_arguments_for_one_suites_test_sandbox()` (`scripts/run-all-test-suites.py:2768`) adds each nc-test-suite's own, among them the checkout under test as a copy-on-write overlay. The three dicts that say which sandbox an nc-test-suite gets are read from the checkout under test (docstring, `scripts/run-all-test-suites.py:177-186`).
- **What the sandbox shows and hides**: the sandbox is the nc-test-suite's nc-test-sandbox. The glossary's entry for that term points to the test runner's docstring under "THE SIGNAL SANDBOX IS ALSO EACH SUITE'S NC-TEST-SANDBOX" (`scripts/run-all-test-suites.py:113-163`), which says what an nc-test-suite sees. **Observed** (observation 8), inside the command prefix `signal_sandbox()` returns, which is the shared arguments plus the variable set to `1`, without each nc-test-suite's additions: process 1 is `bwrap`; `find ~ -maxdepth 3` lists only `~/.gitconfig`, `~/.local/bin/ruff`, `~/.local/lib` and the first directories of the path to the one log-store file, as `TEST_SANDBOX_HOME_PATHS_SHOWN_READ_ONLY` (`scripts/run-all-test-suites.py:761-770`) lists them; `/run` holds only `user`, in which the shared arguments mount an empty tmpfs at `/run/user/<uid>` (`scripts/run-all-test-suites.py:808-811`); and `RUN_ALL_TEST_SUITES_INSIDE_SIGNAL_SANDBOX` is 1. A real nc-test-suite's sandbox also shows the checkout under test and the other paths each nc-test-suite's additions bind.
- **Login file**: no agent runs inside, and no login file is there. The home directory is an empty tmpfs apart from the paths above and the checkout, and no environment variable that `TEST_SUITE_CREDENTIAL_ENVIRONMENT_VARIABLE_PATTERNS` (`scripts/run-all-test-suites.py:794-797`) matches reaches an nc-test-suite.
- **Code**: `scripts/run-suite-in-signal-sandbox.py` refuses an nc-test-suite that `SUITES_RUN_WITHOUT_ANY_SANDBOX` names (`scripts/run-suite-in-signal-sandbox.py:528-530`), reading the dict from the `scripts/run-all-test-suites.py` beside itself (`scripts/run-suite-in-signal-sandbox.py:101-106`).

### The agy cold-read-cell launcher

- **Path**: `nc-systems/cold-read/cold-read-agy-cell.py`.
- **Where the sandbox settings are**: `credential_sandbox_prefix()` (`nc-systems/cold-read/cold-read-agy-cell.py:198-229`), built from the lists `CREDENTIAL_DIRECTORIES`, `CREDENTIAL_FILE_NAME_PATTERNS` and `REVIEWER_PROGRAM_LOGIN_FILES` (`nc-systems/cold-read/cold-read-cell-common.py:63-77`).
- **What the sandbox shows and hides** (**Code**): this program calls the function without `writable_paths`, whose default is `None`, and for `None` bwrap binds the whole file system read-write (`--dev-bind / /`). It mounts an empty tmpfs over each credential directory that exists (`~/.config/nedschorus`, `~/.config/gh`, `~/.ssh`), and binds `/dev/null` over each regular file named `*.token` or `.env` that a scan at launch finds under the home directory and the checkout the program runs from, and over Claude's and Codex's login files that exist at launch. The scan follows no symbolic link, stays on one file system and skips directories it cannot read (`nc-systems/cold-read/cold-read-cell-common.py:106-170`). It has no PID namespace of its own, and the network is shared. **Documented** (`nc-systems/cold-read/cold-read-agy-cell.py:81-86`): a credential file made after launch, or one outside the home directory and the repository, is not hidden.
- **Login file**: agy reads its own login under `~/.gemini/`, which this sandbox leaves readable and writable. **Observed** (observation 9), inside a sandbox started with this prefix: `~/.claude/.credentials.json` and `~/.codex/auth.json` read as empty, `~/.config/gh` holds no files, `~/.gemini/antigravity-cli/antigravity-oauth-token` is readable, and `~/.gemini` is writable.
- **Code**: with no `bwrap` on PATH the program refuses before agy starts (`nc-systems/cold-read/cold-read-agy-cell.py:252-261`).

### The Gemini task launcher

- **Path**: `scripts/run-gemini-task-from-brief.py`.
- **Where the sandbox settings are**: the same `credential_sandbox_prefix()`, called with a list of writable paths and its `network` argument, true only when the launcher is given `--network` (`scripts/run-gemini-task-from-brief.py:126-129`).
- **What the sandbox shows and hides** (**Code**): for a list, even an empty one, bwrap binds the whole file system read-only (`--ro-bind / /`), adds a private `/dev`, and binds read-write each path in the list (`nc-systems/cold-read/cold-read-agy-cell.py:215-220`). The launcher's list always holds the report file and, with `--sandbox workspace-write`, the checkout and each `--writable-root`. Without `--network` the launcher adds `--unshare-net` (`nc-systems/cold-read/cold-read-agy-cell.py:221-222`). The credential directories and files are hidden as in the agy cold-read-cell launcher, and there is no PID namespace of its own.
- **Login file**: **Observed** (observation 9), inside a sandbox started with `credential_sandbox_prefix(writable_paths=[])`, the read-only part of the launcher's prefix without the report file and directories: the agy login file is readable, Claude's and Codex's login files read as empty, and `~/.gemini` is not writable (`touch` there is refused). What agy does when it must refresh its login and cannot write `~/.gemini` has not been observed.

### agy for one prompt, in a home directory that holds only `~/.gemini`

- **Path**: `nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py`.
- **Where the sandbox settings are**: `empty_home_sandbox_prefix()` (`nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py:84-99`).
- **What the sandbox shows and hides** (**Code**): `/usr` and `/etc`, read-only, with `/bin`, `/lib`, `/lib64` and `/sbin` as symbolic links into `/usr`; `~/.gemini`, read-write; a private `/dev`, `/proc`, `/tmp` and `/run`, with `/run/systemd/resolve` bound in when it exists, so that host names resolve; the agy binary, read-only at `/run/agy-bin/agy`, off PATH; a fresh empty working directory; and PID, IPC and UTS (host name) namespaces of its own. The network is shared.
- **Login file**: `~/.gemini` is the only part of the home directory there, bound read-write. **Observed** (observation 9): `ls -A ~` inside lists only `.gemini`; the agy login file is readable and `~/.gemini` writable.

### The Codex launchers

- **Paths**: `scripts/run-codex-task-from-brief.py`; `nc-systems/cold-read/cold-read-codex-cell.py`; `scripts/code-review-codex-cell.py`, which `scripts/merge-lane-code-review-codex-cell-run-on-pull-request-head.py` runs on a pull request; and `scripts/sanity-check-adversarial-prompts.py`.
- **Where the sandbox settings are**: none of them calls `bwrap` itself. Each passes Codex a named permission profile through `-c` options built by `codex_credential_denying_permission_profile_arguments()` (`nc-systems/cold-read/cold-read-cell-common.py:172-195`): `codex-task-no-credentials`, extending `:read-only`, or `:workspace` with `--sandbox workspace-write` (`scripts/run-codex-task-from-brief.py:93-94`); `cold-read-no-credentials`, extending `:workspace`, with the network on (`nc-systems/cold-read/cold-read-codex-cell.py:170-176`); `code-review-no-credentials`, extending `:read-only` (`scripts/code-review-codex-cell.py:456`, `scripts/code-review-codex-cell.py:654-655`); and the sanity-check's profile, extending `:workspace`, with the network on (`scripts/sanity-check-adversarial-prompts.py:765-768`). `scripts/run-codex-task-from-brief.py` turns the network on only with `--network`. A launcher can also make a directory writable with Codex's `--add-dir` option, as the cold-read Codex launcher does for its report (`nc-systems/cold-read/cold-read-codex-cell.py:189-190`).
- **What the sandbox shows and hides**: **Documented** (`scripts/code-review-codex-cell.py:114-119` and `141-148`, `nc-systems/cold-read/cold-read-codex-cell.py:70-80`): `:read-only` lets the model's commands read the file system and write nowhere; `:workspace` also lets them write the checkout Codex is given with `-C` and each directory added with `--add-dir`. **Code**: the profile denies each credential directory that exists, each agent-binary's login file that exists, and, on Linux, each file named `*.token` or `.env` found at launch; on Linux with `:workspace` it also makes `/tmp` and `$TMPDIR` read-only. **Documented** (`nc-systems/cold-read/cold-read-codex-cell.py:77-80`): a directory added with `--add-dir` is writable even inside that read-only `/tmp`. **Documented** (`scripts/code-review-codex-cell.py:163-168`): Codex runs each of the model's commands through a `codex-linux-sandbox` child process, which execs `bwrap`.
- **Login file**: **Documented** (`nc-systems/cold-read/cold-read-codex-cell.py:89-93` and the comment at `nc-systems/cold-read/cold-read-cell-common.py:70`): the codex agent-binary reads its login outside the profile, which governs only the model's commands, so denying `~/.codex/auth.json` to those commands leaves Codex logged in.
- **Observed** (observation 10): `~/.codex/config.toml` on ned-box has no line containing the word "sandbox". That search does not rule out a permission setting under another key, and a Codex invocation with another `CODEX_HOME` reads another `config.toml`.

- **Observed** (observation 11): `/etc/claude-code/` does not exist, and no `.claude/settings.local.json` in an agent-home under `/home/nedlern/agents/` or in `/home/nedlern/Projects/nedschorus/` mentions `"sandbox"`. ### The benchmark pilot's sandbox: designed, not built

GHI [A pilot of three past bug fixes, redone by agents on the code as it stood before each fix, to learn whether a benchmark of agent-instructions and hooks can be built from the project's history](https://github.com/nedschorus/nedschorus/issues/1505) specifies, under "Step 1: the sandbox probe" (`docs/issues/1505-a-pilot-of-three-past-bug-fixes-redone.md:31-45`), one bubblewrap sandbox for each invocation of `claude -p`, with a process namespace of its own and the network open. It shows the case tree and its bare `origin` repository, read and write; the instruction package under test, which GHI 1505 calls an arm, and the system's programs, read only; a private temporary directory; and a private home directory, which holds copies of `~/.claude/CLAUDE.md`, of `~/.claude/settings.json` with Remote Control and cross-session messages turned off, and of the programs that settings file runs. Other checkouts, the log-store, other agent-sessions' transcripts and GitHub's credentials are absent. The real `~/.claude/.credentials.json` is bound in for reading and writing, so that a login refresh inside the sandbox updates the one file every agent-seat uses.
