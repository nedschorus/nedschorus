# Fast, parallel reviews of pull requests

How this project keeps the review of a pull request short, and which parts of the review run side by side. It is for any agent-seat that reviews, merges or authors a pull request. Terms are the project glossary's, `docs/nedschorus-wiki/nedschorus-glossary.md`, and, for cold-read-fast-read, the skills glossary's, `.claude/skills/skills-glossary.md`. Which content a pull request reviewer gives findings on, and which findings block a merge, the -nbd rule included, is the `CLAUDE.md` bullet that begins "Reviewing a pull request — review scope", called the review scope rule below and not restated here; rule 2 below narrows it for one kind of finding, and rule 3 adds a check merge-lane-2 runs itself. Each program named below says in its docstring, or for `scripts/merge-gate.sh` in its header comment, what it does, except where the section Open work says the docstring is out of date; this page says how the programs fit and why the rules around them exist.

## Why reviews were slow

On 2026-10-02 the user asked why reviews were slow when the code base is tiny and the pull requests are small. Of the 40 most recently opened pull requests that had merged by 16:00Z that day, half merged within 18 minutes of opening and three quarters within 1.2 hours. The list came from `gh pr list --repo nedschorus/nedschorus --state merged --limit 40 --json createdAt,mergedAt`, run at 16:00Z on 2026-10-02, which lists by opening time; run on a later day, the same command returns a later set of pull requests. The quartiles are Python's `statistics.quantiles`.

The slow quarter had three causes, none of them the size of the change:

- **merge-lane stopped.** A usage limit stopped merge-lane-2: no pull request merged between 04:49Z and 15:37Z on 2026-10-02, nearly eleven hours.
- **Repeated review rounds of the whole pull request.** A review round here is everything run on one head commit of a pull request: its reviewers, its Codex review and its head test run. PR [The instruction-file guard protects the files the user reviews, by where they sit](https://github.com/nedschorus/nedschorus/pull/852) merged after four review rounds, 37 hours after it opened; its last fix-round changed one agent-facing-message. At 16:00Z that day PR [The Bash guards' shell reader reads a command substitution inside double quotes as commands](https://github.com/nedschorus/nedschorus/pull/886) was in its fourth review round, and PR [A cold-read-record shipment prints shipped: only when the store holds its own files](https://github.com/nedschorus/nedschorus/pull/912) had drawn requested changes on two head commits; both were still open, and both merged later that day.
- **Each approval asked as its own question.** Merges waited for the user to approve agent-instructions that the pull requests handed agents, and each was put to him as its own question, so each merge waited for his next look.

The rules below cut the repeated review rounds and gather the approvals into one sitting. They do nothing about a usage limit.

## The rules

These rules are user-rulings of 2026-10-02. Rule 1 is given as merge-lane-2's seat-brief, `nedlern@ned-box:/home/nedlern/agents/merge-lane-2/CLAUDE.local.md`, stated it on 2026-10-16: merge-lane-2 manages the reviews, commissions the reviewers, decides which findings block, and merges, but reads no code for defects itself and adds no findings of its own to a review. Where the seat-brief now differs from this page, the seat-brief governs merge-lane-2.

### 1. The reviewers match the risk

Each pull request gets one of three sets of reviewers:

- **Prose only**, content on which the review scope rule has reviewers say nothing: no reviewer. merge-lane-2 checks that the pull request changes nothing else.
- **Tests and text only**: a change made only of tests, of printed text, comments and docstrings, or of shell commands and code blocks in Markdown that the review scope rule has reviewers review, in any mix. It gets the Codex review, `scripts/code-review-codex-cell.py`, and the head test run, and no Claude reviewer. The head test run is `scripts/pull-request-head-test-run.py`, which merge-lane-2 runs on the pull request's head commit merged with main.
- **Everything else**, such as any other change to a program or a script, and always a change to `.claude/hooks/`, to `.claude/settings.json`, or to a program that `.claude/settings.json` registers as a hook, the Bash guards among them: one Claude reviewer, a fresh-agent, beside the Codex review and the head test run. The Bash guards are the hooks `.claude/settings.json` registers on Bash tool calls.

A pull request gets the largest set any of its changes needs. The Claude reviewer is the slowest and costliest step, so it goes where a defect costs most. A hook runs inside every Claude Code agent-session of every agent-seat, on each tool call its matcher names, so a defect in a hook reaches every agent-seat as soon as the change merges, and can stop all their work at once.

**After a fix-round, only the commits pushed since the last reviewed head commit are reviewed**, with the set of reviewers those commits need, and the check whose blocking result ended the previous review round is run again: a review on the new commits, or the head test run on the new head commit merged with main. The whole pull request is reviewed again, with the set it needs, when the new commits include a hand-merge of main, or when the author rewrote the branch's history, which leaves no range of new commits to review. The earlier commits were reviewed at the frozen-head and are unchanged, and a reviewer of the new commits who sees that they break earlier code reports that too, as the review scope rule says. A hand-merge brings in main's changes, which no reviewer has yet read beside this branch's. The check that blocked runs again because its earlier result described the previous head commit, not the new one.

### 2. When a finding about the shared shell reader blocks

The Bash guards share one reader of shell commands, the shared shell reader, a parser built on tree-sitter-bash, in `nc-systems/general-tools/shell-command-tree-sitter-bash-reader-common.py`. PR [Bash guards read commands with tree-sitter-bash, through one shared shell module](https://github.com/nedschorus/nedschorus/pull/1237) added it and deleted the hand-written reader that `scripts/synthetic-keystroke-guard-hook.py` held before. A reviewer's report that the shared shell reader misreads a shell construct is a finding, which blocks the merge, only when replaying the commands agents really typed changes a guard's verdict, or when evidence shows the construct is one agents commonly type. A construct a reviewer constructed, by hand or by generating commands at random, is a non-blocking finding. merge-lane-2 adds it to the one GitHub issue that collects such constructs for the shared shell reader, by editing that issue's GHI-MD with the edit-GHI operation, and does not send it to the author as a follow-up. A construct moves from that issue to a pull request only when a real command an agent ran, recorded in a transcript, uses it. Rule 2 does not cover a finding that the reader or a guard hides one of its own failures or reports one as success; such a finding needs no citation, as `CLAUDE.md` says.

Shell syntax has a great many constructs, so a reviewer can keep building one more that the reader gets wrong; without a stopping rule, the review rounds do not end. The replay measures what agents actually type: PR [The Bash guards' shell reader reads a command substitution inside double quotes as commands](https://github.com/nedschorus/nedschorus/pull/886), which tested the hand-written reader before PR 1237 replaced it, replayed every distinct pair of command and working directory in the Claude Code transcripts, 59,199 from the Mac and 21,431 from ned-box, through the guards at main and at the pull request's head commit; its description gives the counts and its outline of the method. Transcripts from both machines are mirrored under `/home/nedlern/nedschorus-logs/transcripts/` on ned-box. Rule 2 applies to the Bash guards the `CLAUDE.md` rule that begins "Propose a guard, validation, retry or workaround only when you can cite the failure it defends against".

### 3. Agent-instructions pending approval go to the user in one approval-walk

Agent-instructions that a pull request adds or changes need the user's approval before it merges. merge-lane-2 gathers them from every open pull request into one approval-walk, still with one decision per item, instead of putting each to him as its own question at a different time. The merges then wait for one sitting of his, not for one look per question. An agent-facing-message that is not agent-instructions, such as an error, a refusal or a warning, needs no approval from the user; instead, merge-lane-2 runs each cold-read-fast-read command that `scripts/pull-request-review-plan.py` prints for the pull request's agent-facing-messages, runs one itself on any new or changed agent-facing-message the program does not list, such as one in a shell script, and sends the reports to the author. It holds the merge until, for each such agent-facing-message, the latest report shows the fresh-reader neither misread nor struggled with it, or the author gives a reason the wording must stand and the user accepts it. This hold is merge-lane-2's own, not a reviewer's finding.

### 4. Fewer tokens, and fewer suites run

- **merge-lane-2's task list keeps only open tasks.** A finished task is removed from the task list of merge-lane-2's agent-session, not kept as history, because every task kept is carried in the agent-session's context and a finished one spends tokens on nothing.
- **A head test run runs only the suites test selection picks**, through the `--only-suites-whose-recorded-inputs-changed-since` option of `scripts/run-all-test-suites.py`. The runner records which files and which git calls each suite reads, and picks a suite when one of them changed; its docstring lists the other cases that pick a suite, among them a change to the runner, to `.claude/hooks/` or to `.claude/settings.json`, which picks every suite. Since PR [Test selection sets aside git calls that see no file or run on another repository](https://github.com/nedschorus/nedschorus/pull/945), a recorded git call on one of two allowlists, calls that read no file of the checkout and calls on another repository, no longer picks a suite. The daily full run of main, `scripts/daily-full-test-run-of-main.py`, still runs every suite and writes its result to the log-store, so a suite test selection wrongly skipped is run on main by the next daily run that completes; the daily run blocks no merge, and its record catches nothing until someone reads it.

## What runs in parallel

merge-lane-2 starts these for every open pull request together, so the slowest one, not their sum, sets the wait:

- the conflict check, `scripts/branch-conflict-check.py`, which takes seconds;
- the Claude reviewer, for each pull request whose set of reviewers includes one;
- the Codex review, for each pull request that is not prose only, run through `scripts/merge-lane-code-review-codex-cell-run-on-pull-request-head.py`, a step of the per-pull-request program the head test runs bullet below names; the Codex reviews of different pull requests run side by side, and within one pull request the head test run starts after its Codex review: on ned-box on 2026-10-02, seven Codex reviews ran together in about nine minutes, through the helper that program later replaced.

Meanwhile authors run the fix-rounds of other pull requests; an author's own fix-round starts only after merge-lane-2 posts a changes-requested review on that pull request, as `CLAUDE.md` says. The author dispatches a forked subagent for the fix-round, in a git worktree of its own, so the author keeps working in the author's own checkout while the subagent fixes and pushes.

Three things wait their turn:

- **The head test runs' suites.** For each pull request, `scripts/merge-lane-pull-request-worktrees-reviewer-brief-codex-review-and-head-tests-run-without-merge.py` runs the Codex review and then the head test run, `scripts/pull-request-head-test-run.py` on the pull request merged with main, and merge-lane-2 may run it for several pull requests at the same time, but their suites still wait their turn. On ned-box, where `scripts/run-all-test-suites.py` runs each suite in a test sandbox built with bwrap, every test run on the machine shares one admission, which starts a suite only while the machine's CPU and memory allow. Where suites do not run in a test sandbox, as on the Mac, `scripts/run-all-test-suites.py` allows one test run per machine at a time, because overlapping test runs there share machine state and were measured to drop test cases silently while both reported a pass. Either way the suites waiting to start form the queue to keep short; rule 4's test selection keeps it short.
- **The user's approvals**, which rule 3 gathers into one sitting.
- **merge-lane-2's own work**: the cold-read-fast-read of rule 3, deciding which findings block, the review it posts, and the merge.

PR [merge-lane: move the merge helpers into scripts/, and retarget stacked pull requests before a merge](https://github.com/nedschorus/nedschorus/pull/1161) moved merge-lane-2's helpers from the log-store into `scripts/`. The helpers run the test runner, the head test run program, the Codex review and `scripts/merge-gate.sh` from a worktree at main, never the pull request's own copies, so a pull request cannot change those tools to pass its own review. The head test run still runs the pull request's own test suites, which is why rule 1 has a reviewer read every change to a test.

Last, `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py` merges each pull request. The merge program first runs `scripts/merge-gate.sh`, which refuses, among the cases its header comment lists, on a missing approving review, and pins the merge to the head commit the newest approving review covered. merge-lane-2 posts the approving review from the merge account, the GitHub account `ned-review-merge`; GitHub refuses an approval from a pull request's author, so on a pull request that account opened the approving review comes from the GitHub account `mac-claude`. The user's approval of agent-instructions under rule 3 is a different approval. When the gate passes, the merge program retargets each open pull request stacked on the merging branch to that branch's base branch, because the merge deletes the branch and GitHub closes every open pull request whose base branch is deleted.

## Open work

`scripts/pull-request-review-plan.py`, from PR [pull-request-review-plan: compute a pull request's review tier, fix-round delta and brief facts](https://github.com/nedschorus/nedschorus/pull/943), states for one pull request its set of reviewers under rule 1, the review round, a fix-round's new commits, and the changed agent-facing-messages. It differs from rule 1 in three ways, and until it is changed, rule 1 governs:

- Its names for the three sets, `seat-alone`, `seat-and-codex` and `full-reviewer`, and its docstring date from when merge-lane-2 read pull requests' code itself.
- It gives the Codex review to every fenced code block in Markdown, where the review scope rule has reviewers review only those a pull request's description asks for.
- It treats a change to any Python string constant as text, though a string constant that is never printed, such as a regular expression or a path, changes behavior and belongs to Everything else.
