# PR reviewer instructions

This file's text is pasted whole into the prompt of every commissioned PR reviewer: Claude's, and Codex's, whose prompt `scripts/code-review-codex-cell.py` builds. `CLAUDE.md` also holds the review-scope section below as one of its bullets. `scripts/pr-reviewer-instructions-copies-test.py` fails when the two copies differ, so change both together.

## Review scope: code findings block the merge; prose gets none, apart from the exceptions below

Code needs PR reviewers. Prose is reviewed before the PR.

- **Code is reviewed skeptically, hunting for defects, and its findings block the merge.** Review the code the pull request changes. If you notice that the change breaks other code, in the same file or another, that break is a finding too. A file of any type other than markdown is reviewed this way: source code, such as a script, a test or a hook; settings, such as `.claude/settings.json` or `.gitignore`; data, such as a JSON or YAML file a test reads; and any other file. A docstring is treated as code, and so is a comment that says what a piece of code does or why the code does it: a finding says where the docstring or the comment and the code it describes disagree. A comment that tells a program what to do, such as a script's `#!` first line or `# noqa`, is code. Every other comment, such as one that only cites a user-ruling or a pull request, is prose, and so are a message the code prints and a prompt the code hands to an agent. A pull request reviewer gives such a comment, message or prompt no finding, remark or question, with one exception: a finding may say that a message or a prompt names a file, a flag or a script that does not work as the message or the prompt says, such as a marker file a guard no longer reads, a flag the named script does not accept, or a script the message or the prompt places in this repository that is not there. Such a finding blocks the merge. Code that fills in the placeholders of a message or a prompt, or copies a prompt's text from another file, is code and is reviewed; the English of the message or the prompt is not. A finding about code may name a markdown file the change breaks, such as a `CLAUDE.md` line that quotes output the code no longer prints.
- **A markdown file is prose, whole, the shell commands inside included.** A pull request reviewer says nothing about a markdown file, with two exceptions: a finding about code may name a markdown file the change breaks, as the code bullet above says; and when the pull request's description names a markdown file and asks for a review of the code or shell commands inside that file, review the ones the pull request changes as code and say nothing about the English around them.
- **A file whose name ends with the -nbd suffix, just before any extension, is nice-but-dirty code, as the project glossary defines it, and only three kinds of finding on it block the merge.** Review the file as code, but a finding on it blocks the merge only when it shows one of these: the code damages other systems or data, or blocks other work; the code hides one of its own failures, reports one as success, or reports one where neither an agent nor the user will see it; or deleting the file, or reverting the pull request that added it, would leave something broken. A failing test still blocks. Every other finding on the file is advice, and does not block. A file without the suffix, which the pull request adds or changes, and which needs code from an -nbd file in order to work, is a finding that blocks: that file is nice-but-dirty too, so it must be renamed with the suffix, or stop depending on the -nbd file. A test whose only job is to test an -nbd file is named `<name>-nbd-test.py` and is exempt from this rule.

## A pull request that fixes a defect

A defect is a flaw in a program, or in agent-instructions, that makes or would make the program, or the agent following them, do the wrong thing. A case fix is a change that fixes only the case in front of the author. A workaround is code that copes with a cause instead of removing it. `scripts/merge-gate.sh` reads the first link after `#follow_up` on each `#root_cause_not_fixed` line, and refuses a link that is not a GitHub GHI or pull request, or that names a GHI closed as not planned, a pull request closed without merging, or this pull request. You judge only what needs judgment. The pull request's description is outside the review scope above, so the findings below are not exceptions to it; a defect in the code is still a code finding. An older `Root cause:`, `Root cause not fixed:` or `No defect fixed.` line counts as the hashtag line it stands for. Take these steps in order.

1. Decide whether the pull request fixes a defect that is on main. If it does, the description must carry, for each such defect, a `#root_cause` line or a `#root_cause_not_fixed` line. A `#root_cause` line gives the root cause, as `CLAUDE.md` defines it, and what in the change removes it. A `#root_cause_not_fixed` line gives the root cause and why it stays, or says it was not found.
2. If it does, and such a line is missing or the description says `#no_defect_fixed`, report one finding that blocks the merge, saying the description needs the line. Writing the right line, in place of any `#no_defect_fixed`, settles the finding; no new commit is needed.
3. A defect that a fix-round fixes in this pull request's own earlier commits needs no `#root_cause` or `#root_cause_not_fixed` line, and the description keeps the hashtag it had. The author's fix-round says whether the finding is one case of a wider pattern, as the review asks.
4. If you can show that a cause of the defect is still in the code after this change, report a finding that blocks the merge, unless the description already settles it as step 6 or step 8 says. Name the cause, where it is, and the change that would remove it. For example, a caller still passes the bad input, or each place does by hand what nothing shared does for all of them.
5. If you reported that finding, ask of this pull request's fix, which is then a case fix, and of each workaround in this pull request, one at a time: would it still be needed after the change that removes the cause?
6. For each one whose answer is yes, a `#root_cause_not_fixed` line whose `#follow_up` links a GHI or pull request for that change settles the finding. Check that the link is for that change.
7. For each one whose answer is no, the finding blocks until the author drops it and removes the cause. When the cause is in a design, the design is changed first.
8. One exception: a case fix or workaround that ends an outage may stay though the answer is no. An outage is something agents or the user rely on that does not work. Its `#root_cause_not_fixed` line names what is down, links the follow-up, and says what will show the case fix or workaround can go.
9. When a `#root_cause_not_fixed` line says the cause was not found, check that its `#follow_up` link is for a GHI that looks for the cause. If it is not, report a finding that blocks the merge.
10. If a `#root_cause` line names no root cause, or one the change does not remove, and you cannot show where a cause is, report a finding that does not block. Do the same when you only suspect a deeper cause and cannot say where it is.
11. When your prompt lists merged pull requests whose `#root_cause_not_fixed` line links to a GHI this pull request closes, or to this pull request, look at each case fix or workaround they added that is still in the code. For each one this change makes useless, this pull request removes it, or this pull request's description links, after `#follow_up`, an open GHI for removing it. If neither, report a finding that blocks the merge. `scripts/merge-gate.sh` does not read that link, so check yourself that the GHI is open.
