# sanity-check

## When used

After the document's full /cold-read has run and the changes its findings produced are committed, and before the document is merged into main. If the document's current text has had no full /cold-read, run one first. Only by a deliberate decision, yours or the user's: never wired into automation, and a revision of an already-checked document earns no automatic rerun. Only on a document that directs work, a design, a specification, a skill or a plan; never on one that only reports what happened. The agent that opens a pull request carrying such a document with no sanity-check behind it may say so in the description, as a note; a reviewer never raises it, and it is never a gate. A full run is six sanity-check-cells, three sanity-check-attacks on each of two runtimes, the `claude` CLI and the `codex` CLI, each a full model run at xhigh reasoning effort taking tens of minutes; say so when you suggest it. A run can be smaller: `--attack` selects a subset, and without a sanity-check-request the two fresh-eyes cells are skipped.

## Glossary headwords this skill uses

A **sanity-check-attack** is one stance the instrument takes on the document, run as its own prompt: the cut-attack asks what should be deleted, the mechanization-attack asks which English instruction should be code, and the fresh-eyes-attack builds an independent design from the sanity-check-request, never from the document. The runner's manual calls an attack an audit; they are one thing. A **sanity-check-cell** is one fresh agent running one sanity-check-attack on one runtime. A **sanity-check-request** is the file you write for the fresh-eyes-attack: a problem statement plus off-limits and read-first lists. A **sanity-check-record** is the directory one run leaves behind. All four are defined in `docs/nedschorus-wiki/nedschorus-glossary.md`; this section only tells you how they are used here.

## What to do

1. Read the runner's manual: `scripts/sanity-check-attacks.py --print requester`. It is authoritative for how the runner behaves. This skill repeats the parts you act on, and where the two differ, on keeping the sanity-check-record (step 7), this skill governs.
2. Commit the document first, so the provenance line each report opens with names the text the cells read; on a dirty worktree it names a commit that does not.
3. Write the sanity-check-request as the manual's section "Writing the problem statement" says. Its problem statement is extracted from the document's committed text at that commit: what the system must accomplish, never how the document does it, and none of the names the document coined. Its off-limits list must name the document's own paths, which is not a leak. Save the file outside the worktree, in the session scratchpad the harness gives you, and copy it into the sanity-check-record when the run ends, so a later reader can see what the fresh-eyes cells were asked. Without the file the fresh-eyes cells are skipped; with the flag pointing at a file that does not exist, the run refuses to start.
4. Run `scripts/sanity-check-attacks.py --target <path> [--context <path> ...] --problem-statement <sanity-check-request path>` as a background task. The flag is named for the statement but takes the whole request file. `--context` names documents the target cites that a reader needs open beside it; the cut and mechanization cells receive them, the fresh-eyes cells never do, since they read only what the request's read-first list names. The `--attack` values are cut, mechanization and fresh-eyes, the attack names without their suffix. Arm the Monitor tool on the runner's output for these lines. `saved:` means a report landed; read it now. `FAILED:` means a cell produced no report. `SKIPPED:` means a fresh-eyes cell had no request. `WARNING:` has six sources: a model that could not run, failed, or produced no review, which the runner records and you note; a quoted span found in no tracked file, which you look for in git history before trusting the quote; a cell that modified the worktree, which you inspect and, if the change is the cell's, revert; and a stray write at a cell's own report path that the runner overwrote, which needs nothing. `LEAK-WARNING:` names a coined design name found in the request or in an instruction file the CLIs inject; a hit on the off-limits paths is expected and needs nothing, any other hit you weigh at triage. While the run is in progress change nothing in the worktree, the sanity-check-record included: the write detector compares against a baseline and cannot tell your edit from a cell's.
5. Reports land in the sanity-check-record, `sanity-check-records/<date>-<target-stem>/`, gitignored, one per cell that saved, named `<attack>-<runtime>`. A rerun lands in a fresh directory with a `-2`, `-3` suffix, so one sanity-check can own several; all of them are its record. Read each report as it arrives and keep your judgments provisional until every launched cell has saved or failed. When a cell fails, rerun its attack alone once with `--attack`; if it fails again, triage that attack from the other runtime's report, and if both runtimes failed, the attack is unreviewed and `dispositions.md` says so.
6. Triage, after the run ends. Follow up every `WARNING:` line and every `LEAK-WARNING:` outside the off-limits paths. Settle a hedged claim about code by reading the code. Deduplicate the two reports for each attack: the same finding from both runtimes is one finding, and where they disagree it is one finding carrying both readings. Judge cut-attack and mechanization-attack findings by what their prompts ask for, which is more than deletion and more than code: a cut names what is lost and what elsewhere goes stale; a mechanization names a mechanism, which may constrain, externalize or verify rather than replace, and its prompts-to-code table is walked row by row. The fresh-eyes-attack returns two independent designs, one per runtime; compare each with the original on its merits. A worry, trap or failure mode a fresh design raises that the original never addresses is a candidate finding; a substantive difference between the designs is a question, walked like a finding; the stronger parts of either can feed a best-of-both proposal, walked as a finding. Findings are candidate design changes, and none is applied without the user's ruling.
7. Walk the surviving findings and questions with /walk-me-through (`.claude/skills/walk-me-through/`), one at a time, most important first. For each, propose the fix, not a restatement of the finding, and the user rules (user-ruled 2026-09-04, recorded on https://github.com/nedschorus/nedschorus/issues/263). Record every warning followed up, every failed cell, and every finding or question set aside, with the reason, in `dispositions.md` beside the reports. Triage is complete when every `WARNING:`, every followed-up `LEAK-WARNING:`, every finding and every question has been ruled on or set aside with a stated reason. Keep the sanity-check-record after the work it served lands: review records are logs (user-ruled 2026-08-25), and logs belong in the log-store on ned-box, which the runner does not yet ship to, so the record stays where it was made until a shipper exists. The runner's manual and closing line still say to delete it; the ruling governs.
8. Commit the ruled changes on the topic-branch, if any were ruled, and name every sanity-check-record directory in the pull request description as `sanity-check-records/<name>` on the machine that ran it.

## The user's review criteria

From the walk of 2026-08-10, recorded in the sanity-checker brief: "asking to simplify is like asking to optimize without context." Name the criterion a finding is judged on. This project's criteria, in the order the attack prompts apply them: simpler to operate, then simpler to understand, then simpler to build or maintain; mechanical guarantees over trained habit; a detector with no consumer is cost without value; never trade a deterministic script that does the job for probabilistic agent behavior.

## What it is not

It is not the cold read. /cold-read reviews prose for a fresh reader; this instrument attacks what the document does. They are separate instruments by ruling (2026-08-17), and this one runs second. The attack prompts are `docs/agents/sanity-checker-cut-attack-prompt.md` and its mechanization and fresh-eyes siblings. The three attacks are fixed in the runner; the fourth planned on https://github.com/nedschorus/nedschorus/issues/121 is registered there when it lands, and this skill's counts change with it.
