# Draft engineering rules — agent-loop discipline (awaiting the boss's drain)

Four rule candidates from the agent-native testing walk (`nc-queue/2026-07-28-sdlc-skill-set-coverage-and-app-skill-pile.md` §6a item 4, boss-walked 2026-07-30). Drafted for the extraction-walk lane; wording follows the absolutes-are-deadly audit (no bare always/never).

**1. Fix-loop ladder.** An edit-check-fix loop on one artifact records theory, action, and result from its first round. A second fix round begins with root-cause analysis over the recorded first round — not a second unexamined theory. When the third round fails to clear all checks, the loop stops: the reset is a scope-widening root-cause analysis (function → file → subsystem → harness → environment → instructions) by a fresh-narrow + broad-expert pair, with prior theories handed over labeled as failed conjectures — evidence, not starting points. Why: with roughly 95% per-cycle diagnostic reliability, non-convergence by round 3 is itself strong evidence the theory is wrong, and each further cycle accretes complexity; continuing has negative expected value.

**2. The loop counter is code, outside the loop.** The agent inside a loop does not count its own cycles — its context is contaminated by its theory, and it reliably fails to notice its own anchoring. The harness counts iterations per artifact and enforces the ladder. Why: rule 1 is worthless if the tripwire depends on the judgment it exists to interrupt. **OPEN DESIGN POINT (boss-flagged 2026-07-30): where the counter lives is not settled.** Under one-shot creators, round 2 is a different agent in a different session, so the cycle count must be attributed across sessions to the *change*, not the agent. Candidate homes: the change's append-only attempt history (the cops decision-23 shape), carried on the task record, the PR, or the claims ledger. The home must be named before this rule is admitted; until then it is a discipline, not a mechanism.

**3. Mismatch verdicts before edits.** When a check disagrees with reality, the resolution records one verdict before anything is edited: code wrong / expectation wrong (with a reason about intent, not "measurement said so") / design silent (a new claim exists — name and stamp it) / instrument wrong / environment wrong. Why: the last two verdicts are the ones a looping agent cannot reach from inside its frame, and silent expectation-editing converts an evidence system into an echo of past measurements. Named example (the daemon incident): agents repeatedly "fixed" daemon code without success because the running process was never reloaded — the code being edited was not the code executing; the mismatch verdict was *environment wrong*, unreachable from inside the code-editing frame, and a reach proof on the fix (does the changed line execute in the failing run?) exposes it on attempt one.

**4. Creators are retained for interrogation.** A one-off creator agent's session ID is recorded **until its work clears checks or 30 days elapse, whichever comes first** (boss-ruled 2026-07-30: process mutation makes older transcripts diminishing-returns, so the interrogation window rides inside the existing 30-day drop discipline rather than fighting it). When a checker finds a problem, the creator may be resurrected and interrogated with the blameless framing — the goal is to learn whether its instructions or knowledge were confusing, incorrect, or lacking, and the findings land in the shared boot context (design text, skill prompts, wiki, CLAUDE.md). Why: the creator's context is the only record of the generative reasoning; asked casually it produces an apology, asked blamelessly it produces information; and a boot-context patch corrects every future agent that would have inherited the same error.

**5. The fixer is a third agent — never the writer, never the reviewer (boss-ruled 2026-07-31).** The agent that fixes code cannot be the agent that wrote it (its context assumes its own code is right — the same poisoning that makes creators one-shot) nor the agent that reviewed it (it would grade its own homework on re-review, and its findings may themselves be wrong). Fixing is done by a fresh one-shot agent with a constructed context — the design, the code, the tests when they exist, and the complete findings batch — briefed to trust none of them: verify each finding against the code, verify the code against the design, apply rule 3's five verdicts (the reviewer may be wrong; the design may be silent), and make the improvements as one coherent change, never per-finding patches (donor cost specimen: per-finding fixers cost more than all tasks combined). A finding that contradicts the approved design goes to the boss to rule which governs. The writer stays available to the fixer as an interrogable evidence source (rule 4), nothing more. Why: a wrong finding implemented is a new defect whose provenance looks like diligence; only a party with no stake in either the code or the findings can adjudicate between them.
