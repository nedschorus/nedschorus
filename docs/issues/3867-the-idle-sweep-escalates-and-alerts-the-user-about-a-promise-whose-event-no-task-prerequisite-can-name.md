# The idle sweep escalates and alerts the user about a promise whose event no task prerequisite can name

The idle sweep, `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py` with `scripts/agent-seat-idle-sweep-verdicts-print.py`, treats a promise to act after an event as not acted on until the agent-seat makes a TaskCreate or TaskUpdate call that sets a task's `metadata.prerequisites`, or a TaskUpdate call with `addBlockedBy`. A task's `prerequisites` can name only three kinds of event, `pr_merged`, `issue_closed` and `approval_walk_item_decided`. So when a promise waits on any other event, such as a pull request being marked ready, another agent-seat sending a link, or the user's answer in chat, the agent-seat cannot do what the sweep asks, short of taking the promise back. The sweep then nudges it, escalates, and writes the user a user-alert that is false. On 2026-11-17 this cost the user four false user-alerts about merge-lane-2, and cost merge-lane-2 a turn for each nudge and escalation.

The program's design is GHI [Tasks raise themselves when their prerequisites are met, and agent-seats left idle with something to do are woken](https://github.com/nedschorus/nedschorus/issues/940), `docs/issues/940-tasks-raise-themselves-when-their-due-time-passes.md`; this GHI reports a defect in the program built from that design.

## Root cause

Line numbers are those of main at commit 2c3781f0f.

The check that decides "not acted on" is `task_calls_settling_promise_messages`, in `scripts/agent-seat-idle-sweep-headless-judge-wake-messages-send-and-user-alerts-write.py`, lines 454 to 471, called at lines 859 to 868. A wait on which a rule 2 message was sent ends there only when, after each such message, the agent-seat has made at least one TaskCreate or TaskUpdate call per sentence the message named, on distinct tasks, each of which sets a non-empty `metadata.prerequisites` or, on TaskUpdate, a non-empty `addBlockedBy`. Which calls count is decided by `sets_prerequisites_or_blocked_by`, in `scripts/agent-seat-idle-sweep-verdicts-print.py`, lines 544 to 556. Nothing else the agent-seat does ends such a wait: by design, a tool call does not (lines 853 to 858), "nothing to do" does not (lines 882 to 886), and a reply in text does not. So the wait runs on to the escalation and the user-alert, in `due_step`, from line 909.

The same filter decides whether a new promise counts as backed. `open_tasks_with_prerequisites_or_blocked_by`, in `scripts/agent-seat-idle-sweep-verdicts-print.py`, lines 527 to 538, gives the judge only open tasks that carry `prerequisites` or `blockedBy`. `code_reading_of_sentence`, lines 559 to 574, settles a promise to act after an event as unbacked without asking the judge when no such task exists. A task whose description names the event, with `prerequisites` null, is never seen. So each fresh promise merge-lane-2 made in its reply was flagged again, and its message went on the open wait (lines 889 to 898).

The kinds `prerequisites` can hold are fixed in `scripts/agent-seat-due-task-raise-hook.py`, `CONDITION_KINDS` at lines 227 to 230 and `APPROVAL_WALK_ITEM_KIND` at line 232. None names a pull request being marked ready, a message arriving from another agent-seat, or the user's answer in chat. GHI 940's § More kinds of prerequisite, § Phase 2 of More kinds of prerequisite, lists the deferred kinds, and none of these three is among them.

The root cause is the mismatch between the two: the sweep's rule for a promise to act after an event, and its nudge text ("Record it as a task whose prerequisites name the event, or tell the user you take the promise back"), assume every awaited event can be named in `prerequisites`, and the due-task raise hook's kinds cannot name these. Which side to change is the owner's decision. The two candidates are: add `prerequisites` kinds that can name these events, of which a pull request's draft state and the user's next message are things code can read; or have the sweep credit something an agent-seat can record when no kind fits, such as a task whose description names the event, which today it does not. This GHI proposes neither.
