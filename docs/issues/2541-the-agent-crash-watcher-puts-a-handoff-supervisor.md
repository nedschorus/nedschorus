# The agent-crash-watcher puts a handoff-supervisor back on an unsupervised agent-seat whose session-handoff is waiting

## What is wrong

A `claude` that a person starts by hand in an agent-home, rather than through a launcher, runs with no handoff-supervisor. When it writes its session-handoff, nothing acts on it: no handoff-supervisor stops the agent-session or starts the successor. Today a person recovers this state with `scripts/resupervise-seat.py <seat>`, run on the Mac: it refuses unless the session-handoff is waiting (its `restart-counter` not yet consumed) and no handoff-supervisor is alive, retires the agent-seat's tmux session, and runs the launcher, whose handoff-supervisor starts the successor from the waiting session-handoff. For an agent-seat on ned-box, `--machine ubuntu` runs steps 1 to 4 on ned-box over ssh, as `resupervise-seat.py <seat> --prepare-only`, and then `scripts/launch-claude-ubuntu` on the Mac, because that launcher is a Mac-side program. Only a person runs it, and only once he has noticed the state.

The agent-crash-watcher, `nc-systems/handoff/handoff-agent-crash-watcher.py`, runs every minute on ned-box and assesses every agent-seat with `assess_seat()` from `scripts/recover-crashed-seats.py`, but never runs `resupervise-seat.py` (no line of it names that program, on main at 78716fd58). For this state `assess_seat()` returns the verdict `refuse` before it reads the session-handoff: the tmux session is alive and no handoff-supervisor is confirmed by `ps`, or, outside tmux, a process works in the agent-home. The watcher at most shows the user a refusal notice, and only for an agent-seat it saw running earlier in the boot.

## Why it matters

The agent-session has done its part, a session-handoff, and the successor that would carry the work on never starts until a person notices. The project builds code-prompt-code: detecting a waiting session-handoff, no live handoff-supervisor lock and a running `claude`, then running one program, needs no judgment. The session-handoff writer, `nc-systems/handoff/handoff-write-and-check-supervisor.py`, cannot do it: the handoff-system's nc-architecture-overview, `docs/nedschorus-wiki/nedschorus-handoff-architecture-overview.md`, says under its invariants that the writer starts nothing, because the program that starts a successor must be the one that ends the agent-session. `resupervise-seat.py` keeps to that invariant, since it starts a handoff-supervisor, which ends the agent-session and starts the successor, as `recover-crashed-seats.py` does when the watcher runs it today.

## What to build

In the agent-crash-watcher on ned-box, a check of each agent-seat for three facts read by code: a waiting session-handoff that does not carry `dont-restart`; no live handoff-supervisor; and a running `claude` working in the agent-home. Each fact is read by a function that a program already uses, so that the watcher and the programs it runs cannot disagree: `handoff_is_waiting()` of `scripts/resupervise-seat.py`, or `waiting_handoff_verdict()` of the records reader the watcher already uses, whichever the builder shows agrees with `resupervise-seat.py`'s refusal; and `seat_supervisor_confirmed_by_ps()` of `scripts/recover-crashed-seats.py`, which confirms with `ps` the process the supervisor lock names. When all three hold on two runs at least `CRASH_CONFIRMATION_SECONDS` apart, the watcher does on ned-box what the restart program `nc-systems/handoff/handoff-supervisor-restart-onto-main-code-by-relaunch-from-reference-checkout.py` does in its steps 5 and 6: it runs `scripts/resupervise-seat.py <seat> --prepare-only`, which retires the agent-seat's tmux session and with it the unsupervised `claude` in that session, then `scripts/recover-crashed-seats.py <seat>`, which starts the handoff-supervisor on ned-box under the user's systemd manager and opens the agent-seat's window on the Mac; the handoff-supervisor then starts the successor from the session-handoff. It records the decision in `handoff-agent-seat-died-without-session-handoff-restart-watcher-decisions.jsonl`, as it records a restart, and counts it against `RESTART_LIMIT_SECONDS` as a restart. A `claude` running outside a tmux session is not ended by `--prepare-only`, so `recover-crashed-seats.py` refuses while it runs; the watcher then shows the user a notice naming the process. Every failure becomes a notice with its own text, since the existing notices say the agent-session stopped without a session-handoff. Tests go in `nc-systems/handoff/tests/handoff-agent-crash-watcher-test.py`.

## Open questions

- The watcher's docstring calls an agent-seat down with a waiting session-handoff "a state only he should restart from", and `WAITING_HANDOFF_NOTICE_TEMPLATE` says the watcher does not start a successor from a waiting session-handoff because it is the agent's own request. That case differs from this one, where the `claude` is still running and wrote the session-handoff itself, but the builder brings the user the change, with that recorded line, before building.
- Where the check sits in the watcher: the watcher acts today only on an agent-seat it saw running earlier in the boot, and an unsupervised agent-seat is never seen running, because `assess_seat()` returns `seat-already-running` only when a handoff-supervisor is confirmed. The builder decides whether this check runs for every agent-seat, and says why.

The questions below came from a cold-read-fast-read of this GHI-MD on 2026-11-13 and were checked against main at 8de6c7acc on 2026-11-14. They are open; none changes what the sections above decide.

- Which function reads the third fact, a running `claude` working in the agent-home? What to build names a reader for the first two facts only. Readers already exist: `seat_directory_occupied()` and `processes_rooted_in_seat_directory()` in `scripts/recover-crashed-seats.py`, which `assess_seat()` uses, and `directory_occupancy_keep_reason()` in `scripts/resupervise-seat.py`, which reads `lsof` instead.
- Does the watcher tell apart, before it acts, a `claude` running outside a tmux session, rather than after `recover-crashed-seats.py` refuses? `assess_seat()` already takes the two cases down different paths: with the tmux session alive it refuses to touch it; with none alive it refuses because `seat_directory_occupied()` finds a process in the agent-home. Both return the same verdict, `refuse`, so the watcher would need `tmux_session_alive_anywhere()` of `scripts/recover-crashed-seats.py`, or a verdict of its own, to tell them apart. Telling them apart before acting would show the notice without retiring anything first.
- Does a failed recovery count against `RESTART_LIMIT_SECONDS`? The watcher's docstring counts a failed restart attempt, and `RESTART_LIMIT_SECONDS` is 3600, so counting a failed recovery of this kind leaves the agent-seat out of automatic recovery for an hour.
- What does each new notice say, and does the program owner also get a task? The watcher's docstring sends a failure an agent can fix to a task on the agent-seat's list and on the list of `AGENT_CRASH_WATCHER_PROGRAM_OWNER_AGENT_SEAT_NAME`, and gives an agent-seat that recovery keeps refusing its tasks once until it is seen running again. What to build makes every failure a notice instead, so a failure that persists would show the user a notice on every invocation of the watcher, once a minute, unless notices are limited the same way, once per refusal until the agent-seat is seen running again.
- Which reader decides that the session-handoff is waiting? `handoff_is_waiting()` of `scripts/resupervise-seat.py` and `waiting_handoff_verdict()` of `nc-systems/handoff/agent-seat-state-records-reader.py` disagree today in two cases. For a session-handoff that carries `ask-user-before-restart`, `handoff_is_waiting()` says it is waiting, while `waiting_handoff_verdict()` returns `seat-asked-to-be-consulted`. For a session-handoff whose `session-handoff-sequence-number` cannot be read, `handoff_is_waiting()` says it is not waiting, while `waiting_handoff_verdict()` returns `refuse`.
- Low priority: does the watcher take a work-snapshot of the agent-seat's worktrees before it retires the tmux session? Retiring the tmux session ends the `claude` while its worktrees may hold uncommitted changes. The by-hand path takes none today: no line of `scripts/resupervise-seat.py` names a work-snapshot. `refresh_work_snapshot()` in `nc-systems/handoff/uncommitted-work-snapshots.py` writes one for a worktree.
- Do the watcher and the restart program share one function for steps 5 and 6? Step 5 of `nc-systems/handoff/handoff-supervisor-restart-onto-main-code-by-relaunch-from-reference-checkout.py` does more than run `resupervise-seat.py <seat> --prepare-only`: it then lists the processes working in the agent-home again and ends each one that step 2 also listed and that is not a tmux server. What to build leaves that out.

The questions below came from a cold-read-fast-read of this GHI-MD on 2026-11-14, `nedlern@ned-box:/home/nedlern/nedschorus-logs/cold-read-records/2541-ghi-md-copy-2026-11-14/cold-read-fast-read.md`, and were checked against main at 3ad27d7f6 on 2026-11-14. They are open; none changes what the sections above decide.

- What keeps the watcher from acting on a session-handoff that asks the user before a restart? `dont-restart`, which the first fact names, is the retired name of `ask-user-before-restart`: `nc-systems/handoff/session-handoff-field-names-common.py` keeps it as `LEGACY_DONT_RESTART_FIELD`, and `nc-systems/handoff/handoff-write-and-check-supervisor.py` writes both names. Both readers read either name through `read_ask_user_before_restart_reason_from_session_handoff_fields()` of `nc-systems/handoff/handoff-supervisor.py`, but `handoff_is_waiting()` still says such a session-handoff is waiting, and `resupervise-seat.py --prepare-only` prints that it carries `ask-user-before-restart` and goes on to retire the tmux session. The restart program reads the field itself once the session-handoff is written and stops before its step 4 when the field is set, because a new handoff-supervisor would wait for an answer on a terminal nobody watches.
- Could the watcher end a `claude` running outside a tmux session itself, instead of showing the user a notice? The restart program's `end_process()` takes a process ID and its command line, checks that the process ID still names that command, and ends the process with SIGTERM and, after `PROCESS_END_GRACE_SECONDS` (20), SIGKILL. The restart program ends only processes it listed earlier, in its step 2; the watcher reads the third fact on two invocations at least `CRASH_CONFIRMATION_SECONDS` apart.
- Does the watcher confirm that the successor starts? `recover-crashed-seats.py` waits, in `wait_for_the_seat_to_come_up()`, up to `SEAT_COMES_UP_DEADLINE_SECONDS` (120) for a handoff-supervisor to appear and still run after a settle interval; nothing in What to build waits for the successor itself. The restart program's step 7 waits up to `SUCCESSOR_REPLY_WAIT_LIMIT_SECONDS` (5 minutes) for a new transcript in the agent-seat's project folder under `~/.claude/projects` to hold a reply from the successor. Each invocation of the watcher holds an exclusive lock, and an invocation that finds the lock held exits at once, so a 5-minute wait inside the watcher would skip the next invocations for every agent-seat.
- What does the watcher do when `resupervise-seat.py --prepare-only` exits 1? `resupervise-seat.py` exits 1 both when it refuses before changing anything, as when the session-handoff is no longer waiting or a handoff-supervisor is alive, and when retiring the tmux session fails, which can happen after the tmux session was already killed on one tmux server. The restart program's step 5 runs the command through `run_with_one_retry()`, which after a failure ends the processes left in the agent-home and runs the command once more. What to build makes the failure a notice and does not say whether `recover-crashed-seats.py` still runs after it.
- What does the watcher keep between its two sightings, and must the session-handoff be the same on both? For the crashes it restarts today, the watcher keeps only `first_seen_crashed_at`, the time of the first sighting. An unsupervised `claude` keeps working after it writes its session-handoff, and can write a newer one between the sightings; `resupervise-seat.py`'s docstring says that anything the agent did after writing the session-handoff is lost when its agent-session ends.
- What happens when a person runs `resupervise-seat.py` by hand while the watcher acts on the same agent-seat? `CRASH_CONFIRMATION_SECONDS` is 50. Neither `scripts/resupervise-seat.py` nor `scripts/recover-crashed-seats.py` takes a lock of its own: a search of the first for `lock` finds only a docstring line about the handoff-supervisor's lock, and a search of the second for `flock` and `fcntl` finds nothing. With `--machine ubuntu`, `resupervise-seat.py` runs `--prepare-only` on ned-box and then `scripts/launch-claude-ubuntu` from the Mac, and no handoff-supervisor runs between the two. Both programs refuse when a handoff-supervisor is already alive, and `recover-crashed-seats.py` looks for one twice, but what follows when both retire the tmux session and both start a handoff-supervisor has not been traced (unverified).

## Provisional additions (not yet vetted by the user)

- fleet-restart-at-login, 2026-11-14, on the open question of which reader decides that the session-handoff is waiting: the watcher imports `handoff_is_waiting()`, so that it agrees with `resupervise-seat.py`'s refusal by construction.
- fleet-restart-at-login, 2026-11-14, on the open question of whether the watcher and the restart program share one function for steps 5 and 6: one shared function that both programs call, so that the watcher's steps cannot drift from the restart program's.
- fleet-restart-at-login, 2026-11-14, on the open question of what keeps the watcher from acting on a session-handoff that asks the user before a restart: the watcher leaves such an agent-seat alone before it runs `--prepare-only`, as it already leaves alone the verdict `seat-asked-to-be-consulted`, and as the restart program stops before its step 4.
