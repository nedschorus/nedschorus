## The two commits

- **last known good commit**: the commit the branch `last-known-good` on origin points to. The program of part 1 moves the branch, only forward, to a commit of main on which ned-box's full test run, every nc-test-suite, passed. The agent-homes, the reference-checkouts and merge-lane-2's review tools follow it, except the canary's agent-home; part 2 says which checkouts still run newer code, and why.
- **release candidate**: main's newest commit, `origin/main`. Every merge moves it. The next full test run tests it, and when that test run passes, the program of part 1 moves `last-known-good` to it.

This design uses both as SDLC-terms, in plain words, and neither becomes a project-term, as the user decided in item 25. Neither is in `docs/nedschorus-wiki/nedschorus-sdlc-terms.md` today. Search receipt: `git grep -l -i "last-known-good\|last known good\|release candidate\|release-candidate"` over `scripts`, `nc-systems`, `.claude` and `docs` on origin/main 45e082bc0, 2026-11-04, found only `docs/cross-project/nedschorus-ai-native-software-development-notes.md`, which uses "release candidate" in its general sense, and ghi-guide-agent, asked 2026-11-04, found no GHI that names either.

The release candidate is not a branch of its own. Main already moves only forward, one tested merge at a time, so "the failed one plus the fix" is main's next commit after the fix merges. No branch or checkout that holds work moves backwards; a fix may still be a `git revert` of the breaking pull request, merged as a pull request of its own. Nothing but the promotion in part 1 moves `last-known-good`.

## Design

### 1. The last known good commit, and how it moves

The last known good commit is the commit the branch `last-known-good` on origin points to, so that an ordinary `git fetch origin` brings the branch to every clone whose fetch refspec is `+refs/heads/*:refs/remotes/origin/*`, as the reference-checkout's on ned-box is, and git shows it as `origin/last-known-good`; the user chose the branch over a ref outside `refs/heads/` in item 18. Only one program moves it, by a fast-forward push, and only after a passing full test run on ned-box.

A new program, `scripts/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.py`, runs on ned-box under cron every 5 minutes. Its entry in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` replaces ned-box's entry for `scripts/scheduled-full-test-run-of-main.py`; the Mac's entry stays. As the installer's docstring, "RETIRING A JOB", requires, the build runs `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py --remove --job scheduled-full-test-run-of-main` on ned-box before its pull request merges, so cron does not also start the old daily run, and `--install` after it merges, then `--check`, which reports a job installed that the table does not name. Each invocation, in order:

1. Takes the program's own lock, a lock file beside its state file. A scheduled invocation takes it without waiting and exits 0 when another invocation holds it; a `--start-now` invocation waits for it.
2. Reads its state file, `~/.local/state/nedschorus/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.json`: for the last full test run, its commit, start, end, exit code, record path and failing nc-test-suites; how many full test runs in a row failed at that commit; the last time an nc-test-suite was seen running on ned-box; the window of the last start; a passing commit not yet promoted, with the time and reason its push last failed; and the time `last-known-good` last moved. A missing file counts as empty, as on the first invocation after the build; an empty file's last time an nc-test-suite was seen running counts as the time of this invocation, so the first full test run waits 20 quiet minutes like any other. A file that exists but cannot be read or parsed is reported, and the invocation exits nonzero without changing it, because treating it as empty would forget the window's start and the failure count.
3. Fetches origin.
4. When the state file holds a passing commit not yet promoted: when `origin/last-known-good` already holds that commit, clears the passing commit from the state file; otherwise retries its push as in step 8. A failed retry is recorded, and the invocation goes on to step 5, so a push that keeps failing does not stop later full test runs.
5. Records whether an nc-test-suite is running now, as part 3 says.
6. Decides whether a full test run is due and ned-box is quiet, as part 3 says; exits 0 when not. A `--start-now` invocation skips this step.
7. Records the window of this start in the state file, then runs `scripts/scheduled-full-test-run-of-main.py`, changed as listed below, which fetches origin, tests origin/main's newest commit in a detached worktree, and writes its record.
8. Writes the full test run's result to the state file, and sets the last time an nc-test-suite was seen running to the time the full test run ended. When that program exited 0 and its record names commit C, C is the passing commit not yet promoted, and the program pushes C to `refs/heads/last-known-good` without force: it creates the branch at C when origin has none, and otherwise pushes only when `origin/last-known-good` is an ancestor of C. C is promoted even when main has moved past C during the full test run; the next window's full test run tests main's newer commit. The push fails, rather than moving the branch backwards, when the branch moved to a later commit in the meantime, which only a push from outside this program can do. When the push fails, the program records C and the push's error in the state file, then exits nonzero. After a push that worked, it clears the passing commit not yet promoted and records the time `last-known-good` moved.

Every failure to fetch, push, read or write the state file, or to read an admission slot file or a run record, prints its reason and exits nonzero, so cron's output file, `~/.claude/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.log` on ned-box, where the other cron jobs' output files are, keeps it. A push that has failed is also in the state file, so the notice of part 5 names it.

**Changes to `scripts/scheduled-full-test-run-of-main.py`.** It gains an option, named in the build as item 25 says, that leaves `--record-inputs-with-strace` out, for part 3. On both machines, its record's name becomes `<YYYY-MM-DD>-<HHMM>.txt`, from the Los Angeles date and time the full test run started, so that each full test run, a `--start-now` one included, keeps a record of its own. For each failing nc-test-suite it copies the log to the log-store beside the record, so the notice of part 5 can name a log the next full test run does not delete.

**The user's own start.** The same program with `--start-now` waits for the program's lock instead of exiting, skips the window and the quiet test, tests origin/main's newest commit even when the last full test run passed or failed twice at that commit, and promotes as in step 8 when the full test run passes. Its start, when it has taken the lock, counts as the start of the window it then falls in, so the scheduled full test run of that window does not also start; when that window's scheduled full test run has already started, the user's waits for it to end and then runs. He runs it from his Mac as `ssh nedlern@ned-box 'python3 ~/Projects/nedschorus/scripts/full-test-run-of-main-in-a-quiet-gap-and-last-known-good-promotion.py --start-now'`, or tells an agent to.

Only ned-box's full test run promotes. The Mac's daily full test run stays as it is and writes its own record: the Mac sleeps, so a promotion that waited for it could wait for days, and the test cases that run only on macOS are few (on 2026-11-04 ned-box's record skipped 4 test cases as macOS only, 3 in `scripts/recover-crashed-seats-test.py` and 1 in `scripts/run-all-test-suites-signal-sandbox-test.py`, of 10 test cases it skipped in all).

The promotion push of `refs/heads/last-known-good` goes through the pre-push hook like any other branch push; its conflict check and revert check find it clean, because the commit it pushes is already on main.

### 2. Which commit agent-seats run on, and which commit they start branches from (question 1)

**Branches start from origin/main, the release candidate, as today.** Work changes the candidate: a fix for a failed candidate must be built on it, since the next candidate is "the failed one plus the fix". `scripts/merge-gate.sh` refuses a pull request that is `BEHIND`, so a branch cut from the last known good commit would have to take in main before it could merge anyway, and the head test run tests it merged with main. The checkout-freshness hook keeps rebasing a never-pushed nc-topic-branch onto origin/main.

**What an agent runs comes from the last known good commit.** Three checkout-sync steps change their target from origin/main to origin/last-known-good, for checkouts that hold no commits that origin/main lacks:

- `launch_time_git_sync` fast-forwards a strictly behind agent-home to origin/last-known-good before an agent-session starts, and fast-forwards the reference-checkout to origin/last-known-good before the handoff-supervisor restarts itself.
- The checkout-freshness hook's step 5b fast-forwards a detached checkout with no commits that origin/main lacks to origin/last-known-good. Its step 4, for the agent-home's seat-branch alone, when the seat-branch is never-pushed and holds no commits that origin/main lacks, fast-forwards the seat-branch to origin/last-known-good in place of rebasing it onto main; any other never-pushed branch, such as an nc-topic-branch cut a moment ago, still rebases onto origin/main.
- The checkout-freshness hook's step 6 fast-forwards the reference-checkout to origin/last-known-good, so the git client-side hooks, the cron jobs and the handoff-supervisors run the last known good commit's code. The glossary entry for reference-checkout, "which stays on `main`", changes to say the reference-checkout stays at the last known good commit.

A fast-forward never moves a checkout backwards. An agent-home that is at a newer commit of main when this is built, as most will be, stays where it is, running that newer code, until the last known good commit passes it. The glossary entry for launch-time-git-sync, which says it fast-forwards to `origin/main`, changes to match. Each agent-session runs the checkout-freshness hook from its own checkout, so a checkout follows origin/last-known-good from the first turn end at which the checkout holds the build's commit.

So "runs on the last known good commit" holds, once the last known good commit passes them, for the agent-homes and the reference-checkouts. It does not hold for the canary's agent-home, for a pushed branch, which the checkout-freshness hook never moves, or for a subagent in a worktree of its own, cut from origin/main, which still runs that worktree's hooks through `$CLAUDE_PROJECT_DIR` until GHI 2408 is built. **GHI 2408's one copy per machine is kept at the last known good commit**, not at main, as the user decided in item 20. A branch that changes a hook or a skill still tests it from its own checkout, as GHI 2408's requirement says.

**The canary.** One setting names the agent-seats whose agent-home follows origin/main instead: a file in the repository, `nc-systems/handoff/handoff-canary-agent-seats-whose-agent-home-follows-main.json`, holding a JSON list of agent-seat names. The canary file holds `["cold-read-research"]` (item 22). Whether the setting moves to the agent-seat record of GHI 972 is under Deferred-decisions. The three checkout-sync steps read the file as origin/main holds it, `git show origin/main:<path>`, so a change to the list acts once it merges, without waiting for a promotion. The canary runs its hooks, skills and agent-instructions from main's newest commit, as every agent-seat does today. Its git client-side hooks still come from its machine's reference-checkout, at the last known good commit.

When a candidate breaks the canary badly enough that it cannot work, the user takes its name out of the canary file, in a pull request or by asking an agent to. `launch_time_git_sync` records, in a state file on the machine, each agent-home it synced to origin/main as a canary's. At the agent-seat's next agent-session start, finding the name gone from the file and the agent-home in that record, it checks out origin/last-known-good, detached, in the agent-home, when the agent-home holds no commits that origin/main lacks and no uncommitted tracked change, and drops the agent-home from the record; otherwise it leaves the agent-home as it is and says why, as it does today. That moves a checkout back, never anyone's work, which stays on the branches the canary pushed.

**Windows.** The day has four windows of 6 hours, starting 00:00, 06:00, 12:00 and 18:00 Los Angeles time. Each window gets at most one scheduled full test run. A full test run is due in a window when none has started in it yet, unless the last one tested origin/main's present commit and passed, in which case there is nothing new to test. So a failed full test run is tried once more in the next window even when main has not moved, which clears a transient failure. After two failed full test runs in a row at the same commit, none is due at that commit again; the next one starts once main moves, which it does when the fix merges.

**Quiet.** In this design, "ned-box is quiet" means that no nc-test-suite has been seen running on ned-box for 20 minutes. Each invocation, every 5 minutes, records whether an nc-test-suite is running now. One is running when any of the 64 admission slot files, in the admission directory `~/.claude/.run-all-test-suites.lock.test-suite-admission/`, is held, which the program tests by taking each with a non-blocking flock and releasing it at once, or when a run record in `~/.claude/.run-all-test-suites.lock.runs/` names a runner process that is still alive, its process id and start ticks both matching `/proc`, so a process id the kernel reused for another program does not count. The runner's records name each runner's process id and start ticks but no end time, so the program samples instead of reading an end. The second test catches a test run whose nc-test-suites all wait for admission and hold no slot. Neither test sees an nc-test-suite run as a program on its own, outside `scripts/run-all-test-suites.py`. While a full test run holds the program's lock, invocations exit at step 1 and take no sample, so step 8 sets the last time an nc-test-suite was seen running to the full test run's end. A short nc-test-suite that starts and ends between two samples is missed, so ned-box can be judged quiet a few minutes early. This test is not GHI 2381's quiet test, which asks only whether the no-sandbox nc-test-suites' shared lock is free, and not the low CPU, memory and token use GHI 2353 looks for.

**A busy day with no gap.** When ned-box has not been quiet by 5 hours into a window, the program starts the full test run anyway. A full test run still going at that time holds the program's lock, so the invocation exits at step 1 and no second full test run starts beside it. The full test run's nc-test-suites share ned-box through the runner's admission: an nc-test-suite starts only while CPU use is under 90% and over 10 GB of memory is free, at most 64 at once, every nc-test-suite at CPU weight 10 against the agent-seats' 100 (the runner's docstring, "ADMISSION"). A pull request's test run that starts beside it waits for admission as its nc-test-suites already do beside other test runs; on 2026-11-02 a full test run took 7,945 seconds on such a day. So, while no full test run is still going at the next window's 5-hour deadline, two scheduled full test runs start at most 11 hours apart: one at the start of a window, the next at the 5-hour deadline of the window after.

**Strace.** Only the first full test run started in each Los Angeles date passes `--record-inputs-with-strace`, as the daily one does today; the others record with the audit hook alone, because strace costs ned-box too much CPU to run more often (the runner's docstring, "RECORDED INPUTS"). The user decided in item 34: "The 00:00 full test run with `--record-inputs-with-strace` runs even when main has not moved; the other full test runs of the day are skipped when main has not moved since the last full test run and that run passed."

Under open question 4, GHI 2381's own quiet-gap program is not built, and this part runs the no-sandbox nc-test-suites in its place.

### 5. merge-lane-2's head test run and its merges (question 4)

- The head test run keeps testing the `pr<n>-merged` worktree, the next release candidate's tree, with its nc-test-suites selected since the merge base as today, less the listed nc-test-suites of part 4.
- A merge moves only main, the release candidate. merge-lane-2 never waits for the last known good commit and never moves it.
- Merges go on while the candidate's last full test run failed: the fix merges as one more pull request, and the next full test run tests the candidate with the fix. Stopping all merges would hold every agent-seat's pull requests for one nc-test-suite's failure.
- `scripts/merge-gate.sh` keeps its exit codes and reads no test record for its verdict. It gains one notice on stderr, through the channel GHI 2381's part 4 designs, so there is one notice and not two. The notice is built from the promotion program's state file. When the last full test run failed, the notice names each failing nc-test-suite, its log in the log-store, the commit range from the last known good commit to the commit tested, and the pull requests merged in that range, read from main's first-parent merge commits, listing first the pull requests whose changed files appear among a failing nc-test-suite's recorded inputs, since those are the likeliest causes. When a promotion push has failed, the notice names the commit and the push's error. When the last fast check of part 4 failed, the notice names that failure too, as item 12 says; what it shows for the failure is under Deferred-decisions. The notice also says how long ago `last-known-good` last moved, from the state file's time of the last promotion.
- merge-lane-2's review tools, which `scripts/merge-lane-pull-request-worktrees-reviewer-brief-codex-review-and-head-tests-run-without-merge.py` checks out at main's newest commit today, in the worktree it names `review-tools-at-main` and passes as `--review-tools-worktree-at-main`, move to the last known good commit, as the user decided in item 21. ### 6. Where a failed full test run goes

The full test run's record is written as part 1 says. The promotion program does not move the last known good commit. The merge-gate.sh notice of part 5 shows the failure at merge-lane-2's next merge. merge-lane-2 sends the follow-up to an author and records that it sent the follow-up with the promotion program's `--record-follow-up-sent`, which writes the time into the state file, so later notices say the follow-up was sent and when; this takes the place of the `--record-follow-up-sent` of GHI 2381's part 2 program, which open question 4 leaves unbuilt. A failure merge-lane-2 cannot place goes where GHI 2381's part 4 sends it. That notice takes the place of the reading of the newest daily record at the start of each merge-lane-2 agent-session that `scripts/scheduled-full-test-run-of-main.py`'s docstring describes, and that docstring paragraph changes to name the notice.

The promotion program also writes a user-alert, with `nc-systems/general-tools/user-alerts-pending-and-claimed-files-write-claim-release-and-delete-common.py`, when a full test run fails for the second time in a row at the same commit, when a push of `last-known-good` fails, and when two invocations in a row fail for any other reason. Each failure is alerted once. The alert names the failure and, for a failed full test run, what the notice of part 5 names.
