# GHI-MD kind: design line daily maintenance-job, in which an agent rates each changed GHI-MD and lists for the user each file whose front matter disagrees with its rating, and each close call

Each day, a maintenance-job reads every GHI-MD in `docs/issues/` that has changed since the job last read it. One agent gives each file one of three ratings, by the four rules below: design, not a design, or close call, the last for a file it cannot decide. The job lists each close call, and each file whose rating and front matter disagree: a design without the line `kind: design` in its front matter, or a file with that line that the agent rates not a design. The list goes to the user as an approval-walk, and an agent carries out what he decides. The job itself edits no file in the repository; it writes only its own record in the log-store. That record keeps the user's decisions, so a file he has decided on is listed again only when its text changes after his decision.

## Why

A GHI-MD that is a design is meant to carry `kind: design` in its front matter, so that programs and agents can tell a design from a placeholder, a bug report or a list of work. The /ghi-write skill's instruction acts only at the moment a GHI-MD is written, and three things make the line wrong later:

- An agent writing a design can forget the instruction to add the line.
- A placeholder or a bug report can grow into a design in later edits, and nobody adds the line then.
- A design can be dropped or declined and keep its line, although the four rules no longer count it a design.

The user asked, with his answer to item 2.1.1, "Do we need a maintenance item to do this occasionally?", as item 2.1.2's page records, and, in the agent-session that ran the approval-walk, judged that "a few extra checks a day might help and have no real cost".

## The four rules

The agent rates a file by these rules, which item 2.1.1's page stated from the boundary the sort drew, and which the user approved there:

1. A design lays out how something will be built, with parts and decisions, complete enough to build from.
2. A complete proposal the user has not decided on yet counts as a design. A file that offers a choice of fixes does not.
3. A design that has been built still counts. A design that was dropped or declined does not.
4. A record of user-rulings, a list of rules or working notes, for something whose mechanism is still open, does not count as a design.

A `status:` line in the front matter, a sentence stating the file's status, or `-design` in its file name, is a hint only, as it was for the sort. The job rates by these four rules, which the user approved for it, and not by the /ghi-write skill's shorter definition of a design.

## What the job does

The job is built as code-prompt-code: code does every step below except the rating of step 3, which is the job's only prompt, given to one agent that the code starts. Code finds the changed files, leaves out the files the user has decided on whose text has not changed, reads each file's front matter, compares the front matter with the agent's rating, keeps the record, and writes the list for the approval-walk. The user asked for this on 2026-10-27, with his answer to item 2.2 of the same approval-walk, as its walk-minutes record: "can this be cpc?"

1. **Find the changed files.** The job takes the files that `git diff --name-only <that commit> origin/main -- docs/issues/` lists, where `<that commit>` is the commit its previous invocation read, and keeps only the `.md` files directly in `docs/issues/`, supporting documents included, as the sort rated them. A deleted file is not rated. A renamed file is rated under its new name, and step 2 compares texts, so the user's decision on the old name still holds while the text is unchanged. The first invocation reads from 675b99013, the commit the sort read, and treats the user's approval of the sort in item 2.1.1 as his decision on each of the sort's 161 files, as they stood at 675b99013, so that the sort's hard calls are not put to him a second time. Like the sort, the job leaves out `docs/issues/queue/`, `docs/issues/archived/` and every file that is not a `.md` file.
2. **Leave out the decided files whose text has not changed.** A file whose text is the same as the text the record keeps for the user's last decision on it is not listed again. The comparison leaves out the front matter's `kind:` line, so that the line that pull request 2038 added, or that an agent adds or removes when it carries out a decision, does not by itself list the file again. Because the comparison leaves that line out, a decision that is never carried out would never list the file again, so on each invocation code also compares each decided file's `kind:` line, at the commit the invocation reads, with the user's recorded decision, and lists each file where they disagree.
3. **Rate each file.** The agent reads each remaining file and rates it design, not a design, or close call, by the four rules, with a one-line reason. A file to which two rules give different answers, such as a design declined and later built, is a close call.
4. **Compare the rating with the front matter.** The job lists each close call; each file rated design whose front matter has no `kind: design` line; and each file with that line that the agent rates not a design. A file with no front matter counts as having no `kind: design` line. A file whose front matter has a `kind:` line with another value is listed, because the /ghi-write skill gives a GHI-MD no `kind:` line but `kind: design`. A file whose rating and front matter agree is not listed.
5. **Hand the list to the user.** The job's agent-session, which GHI 1058's section "How a daily job is handed to the user and tracked (decided)" provides, puts the list to the user as an approval-walk, one file to an item, each with the agent's rating, its reason and a recommendation; for a close call, the agent recommends the rating it leans to. A file whose item the user has not answered is listed again by the next invocation. On a day with nothing listed, the job says so in one line.
6. **Carry out what the user decides.** An agent makes the change the user decides on each file, adding or removing the `kind: design` line. The job itself edits no file in the repository.
7. **Keep the record.** The job keeps, in the log-store, the commit on main its invocation read and, for each file the user decided on, his decision and a text of the file for step 2 to compare with.

When the rating agent fails, or rates only some of the files, the job reports which files it did not rate and why, and never treats a file it did not rate as one whose front matter agrees with its rating. A file it did not rate is rated by a later invocation, even after the job records a later commit as read, so the job keeps such files apart from the list step 1 makes, and item 7 of the Deferred-decisions leaves to the build where.

## Deferred-decisions

The build settles each of these.

1. Where in the log-store the job keeps the commit it last read and the user's decisions, and whether this job uses the shared record of the last commit read that the fifth job on GHI 1058's list and GHI 1064 plan.
2. Which text the record keeps for a decision: the file as the user decided on it, or the file once the pull request carrying out the decision has merged. Either way, carrying out a decision must not by itself list the file again, an edit made between the decision and the merge must still be rated, and a decision that needs no change, or whose pull request is closed without merging, must still leave a text to compare with.
3. Which agent carries out the user's decisions, what starts that agent once the approval-walk ends, and how it changes a filed GHI-MD's front matter: with the edit-GHI operation once for each file, or in one pull request for the day's decisions.
4. Which checkout the job runs in, how the job brings `origin/main` up to date before step 1, and that every file is read, rated and compared at the one commit the job records as read.
5. What the rating agent is given besides the file and the four rules: whether it sees the file's `kind:` line, and whether it is given the sort's finer cases from its summary, on bug reports, experiments and pilots, and supporting documents, or files as examples.
6. How many files one invocation rates, whether in one agent's reading or one for each file, and how the cost of one invocation is kept small, to be measured on the first invocations.
7. Where the job keeps the files it did not rate, the time limit after which a rating that has not finished counts as failed, how a failed rating is retried, and what the job does when the agent fails on a file on several days in a row.
8. What an invocation does when step 1's command fails, or the record cannot be read or written: in each case the job reports the failure, and never reports a day with nothing listed.
9. How the per-file answers of one approval-walk set the day's state file of GHI 1058's design, what the job's agent-session does on a day with nothing listed, and at which point the job records the commit it read, so that a file whose item is unanswered, or whose decision has not yet been carried out, is not dropped from later invocations.
