# A read-only web server on ned-box renders Markdown files as web pages on the LAN, for approval-walk item pages and other pages agents publish to claude.ai that only show text

This is a design, and this file is its GHI-MD, filed with `scripts/ghi-issue-write.py`. It proposes a small read-only web server on ned-box that renders Markdown files kept on ned-box as web pages, for the user's browser on the LAN. Its first use is the approval-walk item page, which today is a private claude.ai page; its second is any other page an agent would publish to claude.ai that only shows text and takes no input from the user. Nothing is built yet. The next action: the agent-seat that builds this, agent-instructions-editor unless the user names another, puts the open questions below to the user in an approval-walk and writes each of his user-rulings into this GHI-MD, changing the design where a user-ruling adds work; then it builds the two pull requests under "Building it".

## What the server does

1. **A link is a file's path.** `http://ned-box.local:8766/<path>` shows the file `/home/nedlern/<path>` on ned-box, with `<path>` percent-encoded in the link, when that file is a regular file of one of these kinds, and nothing else:
   - a walk-document: a file whose path starts `/home/nedlern/agents/` or `/home/nedlern/Projects/nedschorus/.claude/worktrees/` and ends `/docs/walk/<name>.md`, at any depth between, so an approval-walk run in an agent-home or in any topic-worktree under those two directories is served alike;
   - a walk-document the log-store keeps, `/home/nedlern/nedschorus-logs/walk/<name>.md`;
   - a page in the log-store's new directory `/home/nedlern/nedschorus-logs/agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/`, not in a subdirectory of it, ending in `.md` or `.html`.

   In the directories that hold walk-documents, a name ending `-minutes`, `-draft`, `-suggestions` or `-dispositions` is another of the approval-walk's files, not its walk-document, and is not served. The path is checked after its `..` parts and symbolic links are resolved; any other path gets 404, whatever the method, except a missing walk-document under a checkout, which point 2 covers.
2. **A walk-document whose checkout is gone is shown from the log-store.** When the path names a walk-document under a checkout and no file is there, as when the checkout was removed after the approval-walk closed, the server shows `/home/nedlern/nedschorus-logs/walk/<name>.md`, under a line saying that this is the copy `scripts/walk-files-ship.py` shipped to the log-store, which may predate the last revision, since the shipper adds to a walk-document's copy but never replaces it. When the log-store has no such copy either, it answers 404 saying that neither file exists.
3. **An item is a place on the page.** The whole walk-document is one page, and each item's start gets an anchor named for its number, such as `#item-4` or `#item-4.1`, placed before the HTML of the Markdown block that starts on that line, which markdown-it-py's tokens give; an opening that names several items, such as `Items 5 and 6 of 9`, gets one anchor for each. A walk-document whose items the module cannot find is still shown, with anchors only where it finds them. The server finds the starts with the /walk-me-through skill's shared module, `nc-systems/skills/walk-me-through/walk-me-through-approval-walk-minutes-and-walk-document-item-finder-common.py`: `item_unit_spans` for each running count that starts an item, and `item_opening_lines` for each item's opening under a heading shared by several items. An item's link ends with its anchor, so the browser opens the page at that item. The page's title is the walk-document's file name without `.md`. The server loads that module and the Markdown parser module from its checkout by path on every request, as the hooks do, so a change to how they find items reaches the server without a restart.
4. **It renders Markdown with markdown-it-py,** through the project's one shared parser module, `nc-systems/general-tools/markdown-commonmark-parser-with-tables-common.py`, as GHI [Replace the hand-written parsers in the project's hooks and scripts with real parsers](https://github.com/nedschorus/nedschorus/issues/1196) requires: CommonMark with tables, and raw HTML passed through so that HTML comments in walk-documents stay hidden. No new library is added. Each Markdown page is a UTF-8 HTML document with a viewport meta element, so that it reads on a phone, and one short inline stylesheet that follows the browser's light or dark setting. A Markdown page in `agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/` takes its title from its first heading, or its file name when it has none. An `.html` page in `agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/` is sent as its bytes, unchanged, as `text/html; charset=utf-8`.
5. **A Markdown page that is open follows its file.** Every answer is built from the file as it is on disk, with `Cache-Control: no-store` and a `Last-Modified` header. Each Markdown page carries a few lines of script that send a HEAD request for the page's own link every 5 seconds and reload the page at the same anchor when `Last-Modified` changes. When a HEAD request fails or answers anything but 200, the script keeps the page, shows a line at its top saying that the page can no longer be checked and may be out of date, and keeps asking; the line goes when a request succeeds again. So an agent's revision of an item reaches a page the user already has open, and there is nothing to publish or republish. An `.html` page does not follow its file; the user reloads it.
6. **It only reads, and says what failed.** On an allowed path it answers GET and HEAD, and every other method with 405. A file over 5 MB, a file that cannot be read, a Markdown file that is not UTF-8, and a failure to load the shared modules or to render, each get 500, with the error as the page. Each connection times out after 30 seconds. It has no authentication, because a link the user clicks carries no token: any device that can reach port 8766 from the LAN subnet `10.0.1.0/24` can read the files it serves. That is why it serves only walk-documents and `agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/`, and not walk-minutes, transcripts or anything else in the log-store or the agent-homes.
7. **It runs on ned-box as the service of GHI [A small HTTP service with SQLite on ned-box keeps one record of every agent-seat on both machines](https://github.com/nedschorus/nedschorus/issues/972) is designed to run,** taking from that design three rules: a systemd user service of `nedlern`, which starts at boot because lingering is on and restarts 10 seconds after it stops; a `ufw` rule that admits its port from the LAN only, here `sudo ufw allow from 10.0.1.0/24 to any port 8766 proto tcp comment 'markdown page server from LAN'`; and links that name the host `ned-box.local`, because on the Mac `ned-box` is only an ssh alias, which a browser cannot resolve. It listens on port 8766; that service is designed to take 8765. The program is Python's standard `http.server.ThreadingHTTPServer`, run from ned-box's reference-checkout, under the unit `ned-box-markdown-and-html-file-read-only-web-server.service`, whose `Restart=always` restarts it after any exit. When its own program file changes, it stops taking new connections, lets the requests in progress finish, and exits, and systemd starts the new code.

## How approval-walks change

- **Which items get a server link.** `walk_document_item_page_url_on_ned_box_read_only_web_server_or_none(walk_document_path, item_number)`, a new function in the /walk-me-through module above, returns the item's server link when the file is a walk-document the server serves and the machine is ned-box, and returns nothing otherwise, as on the Mac. It and the server use one path check and one anchor function in that module, so the links it builds are the paths the server serves. An item whose function returns a link gets a server link and is never published. Every other item, such as every item of an approval-walk on the Mac until the user decides open question 1, gets a claude.ai page as today. An item that already has a claude.ai `#item_page` line, as in an approval-walk open when this change merges, keeps it and is republished as today; its later items get server links. At close, nothing is deleted, claude.ai pages included, since an agent-session cannot delete them.
- **The link form.** The walk-minutes line keeps its form, `#item_page item N of M <link>`, with the server's link: `#item_page item 4 of 9 http://ned-box.local:8766/agents/<agent-seat>/docs/walk/<name>.md#item-4`. The hooks' pattern, `ITEM_PAGE` at [line 157 of the short-answer hook](https://github.com/nedschorus/nedschorus/blob/beb9524e4fff3d50b897bafb7380771a05846f7f/nc-systems/skills/walk-me-through/walk-me-through-user-short-answer-to-approval-walk-item-expanded-into-instructions-user-prompt-submit-hook.py#L157), already accepts any link, so no hook changes how it reads the line.
- **The skill.** The build changes line 32 of the /walk-me-through skill to say: when an item first comes up, run `python3 nc-systems/skills/walk-me-through/walk-me-through-item-page-server-link-record-in-walk-minutes.py <walk-document> <N>`, a new program that, when the function returns a link, appends the item's `#item_page` line to the walk-minutes itself and prints `recorded`, and otherwise prints `publish`, and that prints the server link of a page in `agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/` when given that page's path; on `recorded`, publish nothing; on `publish`, publish the page as today. A revision of an item with a server link is the edit the skill already makes to the walk-document. When the user says a page does not open, show the item in full, word for word as the walk-document has it. The close step no longer deletes item pages. Line 88, on resuming after a session-handoff, republishes only claude.ai pages.
- **The hooks.** Two prompts change, with the code that fills them in. `NO_PAGE_TEMPLATE` at [line 235 of the Stop hook that refuses a question asked outside the approval-walk's items](https://github.com/nedschorus/nedschorus/blob/beb9524e4fff3d50b897bafb7380771a05846f7f/nc-systems/skills/walk-me-through/walk-me-through-agent-question-to-user-outside-approval-walk-items-refusal-stop-hook.py#L235) appends the `#item_page` line itself for each item that lacks one and whose function returns a link, and says which lines it added, and keeps "publish its page first" for the rest. The O answer's instruction at [line 253 of the short-answer hook](https://github.com/nedschorus/nedschorus/blob/beb9524e4fff3d50b897bafb7380771a05846f7f/nc-systems/skills/walk-me-through/walk-me-through-user-short-answer-to-approval-walk-item-expanded-into-instructions-user-prompt-submit-hook.py#L253) says to republish the page only when its link is a claude.ai link. The tests that quote those prompts change with them.

A tunnel carries the traffic but not the name `ned-box.local`, which only the LAN resolves, so that work also gives the links a second host name.

## When the Mac cannot reach ned-box

When only the server cannot be reached, because it is down, the `ufw` rule is missing or `ned-box.local` does not resolve, a server link does not open, while the agent-seat's window still works: the item was shown in full there when it first came up, and the agent shows it in full again when the user says the page does not open. When the Mac has no route to ned-box at all, the user reaches ned-box's agent-seats, if at all, through Claude Code Remote Control, where the same holds. When ned-box is down, its agent-seats are down too, so no approval-walk there can go on. No fallback is added.

## Alternatives not chosen

- **One page per item.** The server could cut each item out of the walk-document, with a second cut for an item under a heading shared with others, as the hooks do. One page with an anchor per item needs neither cut, and the user can scroll to the items around it.
- **HTML files on the Samba share, with no server.** The Mac mounts ned-box's home directory as `/Volumes/nedhome` over Samba. A script could render each Markdown file to an HTML file in the log-store, linked as `file:///Volumes/nedhome/...`. It needs no running program, but every revision needs a render, an open page does not follow the file, and an iPad cannot open a `file:///Volumes` link at all.
- **Pages served by the service of GHI [A small HTTP service with SQLite on ned-box keeps one record of every agent-seat on both machines](https://github.com/nedschorus/nedschorus/issues/972).** That service is not built: its GHI-MD says "Build-slice 1 is merged; the next action is build-slice 2", which builds the service; on 2026-10-29 nothing on ned-box listened on its port 8765 (`ss -ltn`), and no file on main has `agent-seat-database` in its path. Its design also refuses, with 401, every request that lacks a known token, which a link clicked in a browser cannot send. Once both are running, merging them into one program is a change either GHI's build can propose.
- **The pool of 32 reused claude.ai pages per agent-seat that task #121, "Walk item + build: a pool of 32 reused Artifact pages per agent-seat for walk item pages" proposed.** It leaves at most 32 pages per agent-seat on claude.ai instead of one per item, but they stay there.

## Open questions

1. **Approval-walks on the Mac.** An agent-seat on the Mac keeps its walk-document in its own `docs/walk/` on the Mac until the approval-walk closes, where this server cannot read it, so the Mac keeps claude.ai item pages under this design. Should a program instead copy the walk-document to ned-box each time it changes, so that the Mac's approval-walks use the server too?

The cold read of this design found eight more decisions the user may want to make himself; under his 2026-10-28 ruling that a GHI needs only a cold read, they are put to him here, each with the design's choice and the case against it, and the design stands as written until he answers.

2. **No authentication.** Any device on the LAN subnet can read every walk-document under the agent-homes and topic-worktrees, and every page in `agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/`, by its path. Against: walk-documents are private claude.ai pages today, and a guest's or an appliance's device on his Wi-Fi could read them; a token or a narrower set of paths would close that, at the cost of links that need more than a click.
3. **`.html` pages are served as they are, scripts included.** Against: an agent's HTML then runs in his browser from a ned-box address; serving only `.md` removes that, at the cost of pages that need more than Markdown.
4. **One page per walk-document, not one per item.** Against: he sees the other items on the page, including later ones not yet put to him; a page per item, cut as the hooks cut items, shows only the item asked.
5. **A new `CLAUDE.md` rule sends every page that only shows text to `agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/`, not only item pages.** Against: it changes what every agent-seat does beyond approval-walks, such pages cannot be read away from the LAN, and Mac agents need ssh for each; it could wait until approval-walks have used the server for a while.
6. **Nothing is deleted at close, claude.ai pages included.** Against: this gives up deleting the claude.ai pages that Mac approval-walks and approval-walks already open still make.
7. **An open page reloads itself when its file changes.** Against: the text can change under him while he reads; a line saying "this item changed, reload" would leave the reload to him.
8. **A walk-document whose checkout is gone is shown from the log-store's copy, which may be older.** Against: a copy that may be out of date invites a decision on old text; a 404 would not.
9. **No fallback when the server cannot be reached.** Against: every approval-walk on ned-box then depends on a new service and a `ufw` rule, and when either fails he finds out only when a link does not open; keeping a claude.ai page as well would be a fallback, at the cost of the pages this design exists to stop making.

## Building it

1. **The server, in a pull request that changes no agent's behaviour:** the server program, `nc-systems/general-tools/ned-box-markdown-and-html-file-read-only-web-server.py`, with its tests; its unit file, `nc-systems/general-tools/ned-box-markdown-and-html-file-read-only-web-server.service`; and `walk_document_item_page_url_on_ned_box_read_only_web_server_or_none` with the program that records it, `nc-systems/skills/walk-me-through/walk-me-through-item-page-server-link-record-in-walk-minutes.py`, with tests. Nothing calls the function yet.
2. **Install and check.** Once ned-box's reference-checkout holds the merged commit, the building agent-seat creates `/home/nedlern/nedschorus-logs/agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/`, links the unit file into `~/.config/systemd/user/`, runs `systemctl --user enable --now ned-box-markdown-and-html-file-read-only-web-server.service`, and asks the user to run the `ufw` rule above with `sudo` on ned-box. It then writes a short walk-document of two items in its own `docs/walk/`, fetches the link that program records for its item 2 with `curl --fail --max-time 10`, and asks the user to open the same link on his Mac or iPad and say whether the page shows the item. When any of these steps fails, it tells the user what failed, with the command's output, and the second pull request waits until the failure is fixed.
3. **The approval-walk changes, in a second pull request:** the skill and hook changes above, with their tests, and one sentence in `CLAUDE.md`: a page that only shows text and is not an approval-walk item page, which an agent would publish to claude.ai, goes in `/home/nedlern/nedschorus-logs/agent-written-pages-for-the-user-served-by-ned-box-read-only-web-server/` instead, named `<agent-seat>-<subject>-<date>.md` so that two agent-seats do not write one file, written over ssh from the Mac, and the user is given its server link; a page that takes input from the user stays on claude.ai. The skill and `CLAUDE.md` are files the instruction-file guard protects, so their new wording goes to the user for approval before the pull request is opened.
4. **Then** agent-instructions-editor closes task #121, "Walk item + build: a pool of 32 reused Artifact pages per agent-seat for walk item pages", and the outcome is recorded here.

## Deferred-decisions

- Relative links and images inside a served Markdown file, to be settled from the first pages agents serve.
- Two items with the same number in one walk-document, such as an item and its revision, to be settled in the build from how the finder module reports them.
- Whether the server also listens on IPv6, to be settled in the build from whether the Mac's browser reaches `ned-box.local` over IPv6.
- What brings ned-box's reference-checkout to a merged commit, to be settled in the build from how the reference-checkout is kept on main today.
- How the server notices that its own program file changed, and how long it waits for requests in progress before it exits, to be settled in the build.
