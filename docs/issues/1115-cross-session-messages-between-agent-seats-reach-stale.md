# One message queue for messages between agent-seats, kept in the nc-shared-database, with SendMessage as the nudge

Agent-seats message each other with Claude Code's SendMessage tool, which delivers only to an agent-session that is running: on the same machine by the agent-seat's name, and to the other machine over Remote Control. When the recipient is between agent-sessions, at a session-handoff, or stopped, SendMessage leaves the message at an offline Remote Control entry, the row that ListAgents keeps for a Claude Code session whose Remote Control connection has ended, and reports success; an entry left behind by an agent-session that ended and is not resumed never reconnects, so the message is never read. This GHI-MD holds the design of the fix: every message between agent-seats goes into one message queue, a table in the nc-shared-database, until its recipient takes it and marks it done or failed; SendMessage stays as the nudge that tells a running recipient a message waits. In this GHI-MD, a nudge is always that one-line SendMessage.

## The failure this design fixes

SendMessage's reply to a send left at an offline entry carries `"success": true`, and its text ends "it is offline right now — delivery is queued until that machine reconnects)". Eleven such replies are in merge-lane-2's transcripts on ned-box, `nedlern@ned-box:/home/nedlern/.claude/projects/-home-nedlern-agents-merge-lane-2/*.jsonl`, from 2026-10-06 to 2026-10-31: eight to cold-read-research, two to ned-box-helper, one to agent-instructions-editor. When the entry is one that an ended agent-session left, the message is lost, and the sender learns so only by reading the text of a reply that reports success. GHI [Seat mailboxes across machines and runtimes](https://github.com/nedschorus/nedschorus/issues/749) records the same loss for messages to Mac agent-seats, ten of which waited in a file for a person to forward them.

## Which package

The question is which package can hold messages that agent-seats on two machines put in and take out. Three candidates, looked up on 2026-11-04:

| | persist-queue | litequeue | A table in the nc-shared-database |

| Maintenance | [repository](https://github.com/peter-wangxu/persist-queue) last pushed 2026-01-08, 28 open GitHub issues and pull requests, marked "Development Status :: 4 - Beta" | [repository](https://github.com/litements/litequeue) last pushed 2026-07-31; versions 0.10 and later refuse a database of version 0.9 until it is migrated by hand | this project's |

| Several processes, several machines | its owner, in GitHub issue [132](https://github.com/peter-wangxu/persist-queue/issues/132): "multiprocessing is not supported and verified for both file and sqlite queues"; in GitHub issue [148](https://github.com/peter-wangxu/persist-queue/issues/148), a queue on two machines "requires an external database like mysql or postgresql". Implement a proxy that runs on the database machine" ([useovernet.html](https://www.sqlite.org/useovernet.html)) |
| Fits the nc-shared-database file | creates its own tables, `ack_queue_<name>`, and stores each message as one pickled value, so SQL cannot select by recipient or sender; each recipient would need a queue of its own | owns "one fixed `Queue` table per database file" and refuses a file with other tables ([\_\_init\_\_.py](https://github.com/litements/litequeue/blob/main/src/litequeue/__init__.py)), so it needs a database file per recipient, outside the nightly backup and the generation ID of GHI [A small HTTP service with SQLite on ned-box keeps one record of every agent-seat on both machines](https://github.com/nedschorus/nedschorus/issues/972) | one more table in the backed-up database |
| Install | not installed on ned-box; `/usr/bin/python3`, which runs the service, is marked externally managed, so `pip install` is refused; apt has 1.0.0 | requires Python 3.12 or newer: ned-box has 3.14.4, the Mac's Apple Python is 3.9; not in apt | nothing to install |

Each package keeps its queue in a SQLite file that only processes on one machine may open, so neither can hold a queue that both machines use; a program on ned-box would have to open the file for both, which is what the nc-shared-database service already is. The two parts that are hard across machines are already built there: a program on either machine reaches the service over HTTP, and the local events file on each machine holds every write until the service stores it, even while ned-box is unreachable (GHI 972, condition 1). Taking a message out still needs ned-box, with any store kept on ned-box. Message brokers that run a server on each machine, such as NATS or RabbitMQ, were set aside in GHI 749, § 1, as a service to install, supervise and diagnose on two machines. The queue itself is then one table and a few SQL updates in the service, with litequeue's rules copied. The design adds no package.

## Design

### The rules

The rules are litequeue's claim rules, [docs/message_claim_ids.md](https://github.com/litements/litequeue/blob/main/docs/message_claim_ids.md), with one recipient per message. Where this design adds or changes a rule, the rule says so and names its source.

- A message is **waiting** (litequeue's READY), **taken** (litequeue's LOCKED), **done** or **failed**.
- **Take** is litequeue's `pop()`, repeated: it takes one recipient's waiting messages oldest first, up to 5 in one take (this design's limit, so that one hand-over stays short), marks each taken and adds 1 to its claim ID. Before it does, the service returns to waiting each of that recipient's messages taken more than 60 minutes ago, as litequeue's `retry_expired(threshold_seconds=3600)` does.
- A take made when a new agent-session of the recipient starts first returns to waiting every message of that recipient still taken. An agent-seat runs one agent-session at a time, and the new one does not hold what the old one took. This rule is persist-queue's: `SQLiteAckQueue` does the same when its one consumer restarts.
- **Done** and **failed**, litequeue's `done()` and `mark_failed()`, change a message only when it is taken and the claim ID given is its current one; otherwise they change nothing, so a stale claim, such as one an ended agent-session held, cannot settle a later delivery.
- A take that would hand a message over a sixth time marks it failed instead, with the reason "handed over five times and never settled". This rule is Amazon SQS's: a queue moves a message to its dead-letter queue after its `maxReceiveCount` receives ([redrive policy](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-dead-letter-queues.html)).
- The ID of a message an agent or program queues is the ID of the event that queued it, so a message the local events file sends twice is stored once, as litequeue's idempotency key does.

### Where the messages are kept

In a new table of the nc-shared-database, proposed name `agent_seat_message`: message ID, sender, with its seat ID when the sender is an agent-seat, recipient agent-seat by its seat ID, so a name reused after a retirement does not inherit the old messages, kind, summary, body, queued at, status, claim ID, taken at, the ID of the agent-session that took it, settled at, and the reason given for a failure. Settled messages stay in the table; at a few messages per agent-seat per day it grows by kilobytes. The sender is an agent-seat's name or, for a program that is not an agent-seat, the program's name. The kind is one of a fixed list that the service and the program of § Sending, step 2, share: `message` for any message no other kind fits, `pull-request-follow-up-request`, `pull-request-fix-round-finished-report`, `wake-message`, `account-change-notice`, `review-findings-nudge` and `agent-seat-message-failed-notice`. The service creates the table when it starts and the table is missing, since the database file already exists by then.

An agent or program writes to the queue only through events, written with `write_event_to_local_events_file_and_start_sender` in `nc-systems/nc-shared-database/nc-shared-database-local-events-file-common.py` like the service's other events, so a write on a machine that cannot reach ned-box waits there until the service stores it, in the order written. Three new operations, proposed names `agent-seat-message-queued`, `agent-seat-message-done` and `agent-seat-message-failed`. A take must return the messages at once, so it is a direct request, proposed `POST /agent-seat-messages/take`, and needs ned-box. Every request a hook or the program makes waits at most 2 seconds, the time the local events file's sender waits; an answer that is not a success is treated like no answer, and its status is named wherever no answer is reported.

When the service applies an `agent-seat-retired` event, it marks failed every waiting or taken message to that agent-seat, with the reason "recipient retired". When a message is marked failed, the service itself, in the same transaction, queues a message of kind `agent-seat-message-failed-notice`, sent by the service, to the failed message's sender, naming its ID, recipient, summary and the reason. No nudge goes with it; the sender's hooks hand it over at its next prompt, turn end or agent-session. When that sender is a program or a retired agent-seat, or the failed message is itself such a notice, the service writes a user-alert instead.

### Sending

1. The sending agent writes the message (judgment).
2. It runs the `add-message` subcommand of one program, proposed name `nc-systems/nc-shared-database/nc-shared-database-agent-seat-message-queue-add-message-or-mark-handed-over-message-done-or-failed.py`, with the recipient's agent-seat name, a kind, a summary of at most 200 characters, and the body on standard input. Code refuses, with exit status 2 and what to correct, an unknown kind, a longer summary, an empty body, a recipient missing from the list of agent-seats that step 3 of this list describes while the service answers, and a send with no sender. Code then writes the event, and waits up to 10 seconds for the service to store it. Code prints the message ID and the exact nudge to send, a single line in one fixed format naming the message ID, the sender and the summary. The nudge says that the message is handed over at the recipient's next prompt or turn end once the service holds it; when the service did not store it within the 10 seconds, the program also says so to the sender, with the reason the local events file's sender gives.
3. The list of agent-seats is the agent-seats not retired, from `GET /agent-seats` when the service answers, and otherwise from the copy of its last such answer that the program keeps on this machine, together with this machine's own agent-seats in its local events file.
4. The agent sends the nudge with SendMessage to the recipient's entry in ListAgents. A nudge that reaches an offline entry loses nothing.

The sender is the agent-seat named by `NEDSCHORUS_HANDOFF_SUPERVISOR_AGENT_NAME`, which the handoff-supervisor sets in every agent-session it launches. A program that is not an agent-seat passes `--from <its name>`, which the program refuses when that variable names an agent-seat.

A PreToolUse hook on SendMessage, proposed name `.claude/guard-hooks/nc-shared-database-agent-seat-message-queue-send-message-tool-call-missing-queued-message-id-refusal-hook.py`, acts in an agent-session whose `NEDSCHORUS_HANDOFF_SUPERVISOR_AGENT_NAME` is set. It refuses a SendMessage to an agent-seat unless its message is a nudge: one line in the fixed format, whose message ID this machine's local events file holds as an `agent-seat-message-queued` event to that agent-seat from this agent-seat. Its refusal gives the `add-message` command to run. A SendMessage is to an agent-seat when its `to`, without the short identifier ListAgents shows in brackets after the name, such as `[74e8b9]` in `merge-lane-2 [74e8b9]`, is in the list of § Sending, step 3, which the hook reads without ned-box. A SendMessage to a subagent or to any other name passes. The eleven lost messages become a rule that code enforces.

### How a recipient learns a message waits

The recipient is the agent-seat named by `NEDSCHORUS_HANDOFF_SUPERVISOR_AGENT_NAME`. The hooks below act only when the agent-session's ID, from the hook's input, is the one in `NEDSCHORUS_HANDOFF_SUPERVISOR_SESSION_ID`, which the handoff-supervisor sets beside the agent-seat's name; a `claude` started inside the agent-session inherits both variables but has a session ID of its own, so it takes nothing. One hook program, proposed name `nc-systems/nc-shared-database/nc-shared-database-agent-seat-message-queue-waiting-messages-hand-over-hook-on-session-start-user-prompt-submit-and-stop-events.py`, takes the recipient's messages and hands each over whole: its sender, time, kind, summary, body, how many times it has been handed over, and the exact command that marks it done, with its message ID and claim ID filled in. Before a take, it sends this machine's unsent done and failed events of the recipient and makes no take while any is still unsent, saying which, so a take never overtakes the recipient's own settling. A take that finds nothing, such as at a nudge that arrived before the service stored its message, leaves the message for the next turn end.

- **Starting**: as a SessionStart hook, in additionalContext. At startup, a new agent-session, which the hook input's `source` field tells from the others, the take first returns the agent-seat's taken messages, by § The rules. At resume, `/clear` and compaction, the take takes only waiting messages, and also returns, with their current claim IDs and no new claim, the messages this same agent-session took and has not settled, which the service knows because each take records the agent-session's ID; so a compaction does not lose a message from the agent's context. When the service cannot be reached, the hook says so and why.
- **Running, at a prompt**: as a UserPromptSubmit hook, in additionalContext. A nudge reaches an idle recipient as a prompt, so the message is handed over with the nudge. When the service cannot be reached, the hook says so only when the prompt is a nudge.
- **Running, at a turn end**: as a Stop hook, by blocking the stop with the messages as the reason, so the agent goes on to them. A busy recipient gets a message here. The Stop hook blocks only when the take returned a message, so it blocks again only for messages that arrived or came back since the last take. When the service cannot be reached, the Stop hook lets the turn end.

A message whose nudge reached an offline entry waits for the recipient's next prompt, turn end or agent-session; open point 5 asks the user whether GHI [Tasks raise themselves when their due time passes or their prerequisite is met](https://github.com/nedschorus/nedschorus/issues/940)'s idle sweep should wake an idle agent-seat for it.

The recipient then settles each message (judgment), with the program of § Sending, step 2: `done <message ID> <claim ID>` once it has acted on the message or recorded it in a task; `failed <message ID> <claim ID> --reason <text>` when it cannot act on it, such as a message meant for another agent-seat. A message left taken returns to waiting after 60 minutes, or at the agent-seat's next agent-session, and is handed over again with its count, which reminds the recipient and shows it is a repeat.

### Mac agent-seats while ned-box is unreachable

- **Sending** works: the event waits in the Mac's local events file and reaches the service when ned-box answers again; the `add-message` subcommand says that the recipient cannot see the message until then. The nudge is still sent.
- **Receiving** waits: no Mac agent-seat can take a message, a message from another Mac agent-seat included, until ned-box answers. Settling is written at once and reaches the service later, since done and failed are events.
- Nothing pages the user for it: GHI 972's 10-minute sending job, its build-slice 3, opens a page when a queued row is more than an hour old, but on the Mac "skips the page when ned-box does not answer ssh, since a ned-box that is down is plain to see".

### Cases the design accepts

- A restore of the nc-shared-database from a backup, GHI 972, condition 4, loses the takes made since the backup, which are not events. Messages settled since then are handed over again, with their counts, and a recipient's done for an earlier claim changes nothing.
- A message to a recipient retired after the sender's list was saved is answered 422 by the service; GHI 972's sending job lists it as a rejected row on its page.
- Delivery is at least once, as in litequeue and SQS: a message whose take answer was lost, or whose recipient acted on it and stopped before marking it done, is handed over again, with its count, after 60 minutes or at the next agent-session. Whether to act again is the recipient's judgment.
- While ned-box is unreachable, a machine that has never saved the service's list knows only its own agent-seats. The `add-message` subcommand then queues a message to a name in no list, saying that the name is unchecked; a wrong name is answered 422 when ned-box answers, and GHI 972's sending job lists the row on its page. The refusal hook lets a SendMessage to such a name through, since it cannot tell the name from a subagent's.

### What else the queue carries

Every SendMessage from an agent-seat to an agent-seat, since the refusal hook in § Sending sees to that. Among them, kinds the project sends today or has designed:

- merge-lane-2's follow-up requests after a merge, kind `pull-request-follow-up-request`. Today `nc-systems/general-tools/pull-request-follow-up-request-from-merge-lane-2-message-save-and-forked-subagent-brief-hand-over-user-prompt-submit-hook.py` reads the `#follow_up_request` block from a cross-session message's text, which will hold only a nudge. The hand-over hook program instead passes each message of this kind to `save_follow_up_request_and_clear_answers_when_its_findings_changed()` of `scripts/pull-request-follow-up-request-after-merge-finding-answers-and-next-step.py`, and adds the brief its `build_follow_up_request_forked_subagent_brief()` writes, as the follow-up request hook does today; that hook is then removed.
- An author's message to merge-lane-2 at the end of a fix-round, kind `pull-request-fix-round-finished-report`, which `scripts/pull-request-fix-round-author-brief-from-blocking-findings-and-one-commit-every-finding-answered-check.py` builds; the build has that program queue the message itself and print only the nudge.
- The idle sweep's wake messages and its notice of a change of logged-in account, kinds `wake-message` and `account-change-notice`, GHI 940, and the nudge to an author whose review findings are unanswered, kind `review-findings-nudge`, GHI [Nudge the author of a pull request whose review findings have gone unanswered for hours](https://github.com/nedschorus/nedschorus/issues/1203). Neither job is built, and both send from processes that are not agent-seats, which the refusal hook does not act in. Each can queue its texts when its own design adopts the queue; the user decided on 2026-10-30 that a wake is a cross-session message from a supervising job, and that route stays, as the nudge.
- Messages to Mac agent-seats that merge-lane-2 keeps in a file for a person to forward, as GHI 749 records; merge-lane-2 can queue them instead.

### Not in this design

- Removing the old offline Remote Control entries: no `claude` command lists, archives or deletes them, and the user dropped archiving them by hand.
- Changing GHI 940's or GHI 1203's designs, which their own authors write; open point 5 asks the user about the one change GHI 940 would need.
- Agent-seats that run Codex rather than Claude Code: none runs today, and the hooks are Claude Code's.

## Open for the user

1. **No new package.** Recommended: keep the messages in a table of the nc-shared-database, with litequeue's rules copied into a few SQL updates in the service, because each package's SQLite file can be opened by processes on one machine only, persist-queue's owner says it is not supported across processes, and litequeue will not share the backed-up database file. The alternative: litequeue in its own database file per recipient agent-seat on ned-box, opened only by the service, installed in a virtual environment that the service's systemd unit names, with its files outside the nightly backup.
2. **Every SendMessage from an agent-seat to an agent-seat goes through the queue, and a hook refuses one that is not a nudge.** Recommended, because agents that did not read a reply reporting success have lost eleven messages, and an instruction would rely on the same reading. One alternative: the hook queues the whole message itself, with kind `message`, and replaces the SendMessage's text with the nudge, so the agent's step stays one SendMessage; this rests on Claude Code letting a PreToolUse hook change a tool's input, which the build would first have to test, and the agent would not choose a kind. The other: an instruction alone, with SendMessage still allowed to carry a message whole.
3. **A message between two Mac agent-seats waits while ned-box is unreachable.** Recommended, because CLAUDE.md says to leave a step that needs ned-box until ned-box is back, and a second path for that case would bring back the loss this design removes. The alternative: the nudge carries the whole message while ned-box is unreachable, and the recipient marks the queued copy done when it arrives.
4. **This design replaces GHI 749.** GHI 749, not yet approved, proposes mailbox files on ned-box written over the Mac's file-sharing mount, and a Stop hook that wakes an idle agent-session. Recommended: close GHI 749 as superseded when this design is approved; its Codex half serves no agent-seat, since none runs Codex.
5. **The idle sweep of GHI 940 wakes an agent-seat for which a message waits, or which holds a message taken more than 60 minutes ago.** The service would add a request that counts them, since a take would claim the messages for the sweep. Recommended, because otherwise a message whose nudge reached an offline entry waits until the recipient's next prompt, turn end or agent-session, which for an idle agent-seat can be hours. If he approves, the agent-seat reboot-test, which writes GHI 940, adds that to GHI 940's rules.
6. **The build waits for GHI 972's build-slices 2 and 3.** Their install steps, the tokens, the `ufw` rule and enabling the service, are his to run or approve, and on 2026-11-04 the service was inactive, so messages keep being lost until then. Recommended: wait, because without the running service and the "agent-seat seen" fill the refusal hook would let through the very sends it exists to stop, and the hand-over hooks would find nothing to take. The alternative: build the table, the program and the hand-over hooks now, since each already handles a service it cannot reach, and turn the refusal hook on only once the service answers and the fill has run.
