# Approval-walk item pages the user answers on, from the Claude app on the iPad or the Mac, with each answer recorded in the walk-minutes by code

This is a design, a GHI-MD the user approved on 2026-11-05 and not yet filed. It becomes the new title and text of GHI [Agents put each question for the user on a page that pops up on his Mac, and hold the dialog with him there](https://github.com/nedschorus/nedschorus/issues/1186), whose earlier design, a question page that a monitor on the Mac popped open, the user deferred on 2026-10-19; the section "What is decided" cites his decisions. Filing waits until merge-lane-2 lifts its pause on new pull requests, because edit-GHI opens a pull request. Nothing is built yet. Build-slice 0, a short trial that merges no code, began on 2026-11-07: a press on the page reached the agent-session as a comment sent to Claude but started no turn, which steps 3 and 4 of "How an answer travels" rest on; the paragraph "Build-slice 0's trial of 2026-11-07" there gives the facts. The next action: the user decides how the design goes on from that result, before any code is written.

## Why

An approval-walk shows the user one item at a time in the agent-session's chat, and the item's last line links to the item page, a private claude.ai page holding the same item. Today he reads the page and then types his answer, such as A or D, into the chat. He wants to answer on the page itself.

- On 2026-10-19 he deferred GHI 1186's earlier design, "we can defer the pop-up thing, perhaps indefinitely", because "I've started using remote control a lot, and so I'm not using my Mac because I'm on an iPad" (item 1 of reboot-test's approval-walk reboot-test-questions-owed-to-the-user-2026-10-19).
- On 2026-10-28, in agent-instructions-editor's agent-session: "I love the item pages. The problem was that when I changed accounts they all became inaccessible, and that we ran into a limit of 100 new artifacts".
- On 2026-10-29, in prime-intellect's agent-session: "I thought we have a task or GHI to build our own md to html thing and server, so we have complete control." That became GHI [A read-only web server on ned-box renders Markdown files as web pages on the LAN, for approval-walk item pages and other pages agents publish to claude.ai that only show text](https://github.com/nedschorus/nedschorus/issues/2175), which he approved for his home network only on 2026-10-30 (item 11.1 of fleet-restart-at-login's approval-walk `ghi-972-agent-seat-database-service-design-mac-task-lists-fallback-decision-and-cold-read-findings-approval-walk-2026-10-29`).
- On 2026-11-01, in the same approval-walk, he wrote: "I do not want stuff to be self contained. I want them visible in walks." and "And ideally actionable". He then approved its item 16.3.5: pause GHI 2175's build, and write one design for answerable item pages that open on the iPad away from home, starting from GHI 1186's claude.ai page without its Mac pop-up, and choosing between claude.ai and a ned-box server. This file is that design.

## Constraints

- **The pages open where he works:** the Claude app on the iPad through Claude Code's Remote Control, away from home included, and the Claude app or a browser on the Mac.
- **No pop-ups.** Nothing opens a page on his screen by itself; he opens an item page from its link.
- **Account changes and deleted pages break pages.** A claude.ai page belongs to the account Claude Code on ned-box is logged in to. When he switched accounts on 2026-10-29 and again on 2026-11-04, the item pages stopped opening, and on 2026-11-01 the page an approval-walk used was deleted, so its link broke. Whatever is built, the chat stays complete: each item is shown in full in the agent's message, and an answer typed in the chat always works.
- **Code records the answer.** A press of a button on the page reaches the walk-minutes through the program that records typed answers today, `nc-systems/skills/walk-me-through/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close.py`, called by code, never by an agent restating the answer.

## Hosting: claude.ai, not a ned-box server

| | claude.ai item page | ned-box web server |
|---|---|---|
| Opens on the iPad away from home | yes | only through a tunnel, such as Tailscale, which nothing has set up |
| Tells the agent-session at once that he answered | not shown: in build-slice 0's trial of 2026-11-07, a press calling `sendToClaude`, below, reached the agent-session as a comment but started no turn | no supported way: a program would have to start a turn in a running agent-session |
| Knows who pressed | yes: the platform stamps the comment's author | needs a login of its own |
| Survives an account change | no: the agent publishes the page again under the new account, at a new link, as "After an account switch" says; the chat still works | yes |

The design uses claude.ai. A ned-box server would keep working through an account change, but it cannot wake the agent-session, so an answer on it would wait for the agent-session's next turn, and it needs a tunnel and a login of its own. GHI [Switch the agent-seats to another Claude account when the current account reaches its weekly usage limit](https://github.com/nedschorus/nedschorus/issues/1201) plans to switch among his three accounts each time one reaches its weekly limit, so a switch may come every two or three days; each one breaks the open item page until the agent publishes it again. GHI 2175 stays paused. The trial of 2026-11-07 did not show the wake this comparison counts for claude.ai, so the user is asked whether the hosting he decided still holds; until he answers, it stands.

## How an answer travels

The Artifact tool's runtime capabilities, contract 0.2.96, read on 2026-11-01 and again on 2026-11-05 in the type definitions `comments.d.ts` that Claude Code's built-in `artifact-capabilities` skill ships, outside this repository, offer one channel that, as those type definitions describe it, wakes an agent-session: the `comments` capability's `sendToClaude`; the trial paragraph below says what a press did in practice. A page that declares `capabilities: {comments: {}}` may call `sendToClaude({anchor, text})` from the viewer's own button press. It posts a comment thread as the viewer, and the platform sends it to the agent-sessions that watch the artifact; an agent-session watches an artifact it has published, or one it names to the ArtifactComments tool's `watch` action, and only a main agent-session, not a subagent, can watch. It works only for an editor of the artifact, which the user is as its owner, and the first such write on an artifact asks his consent once; if he declines, the type definitions say the call rejects `forbidden` for the rest of that page load, which build-slice 0 checks, and the page says to answer in the chat. A call that cannot reach an agent-session rejects `claude_unavailable` and posts nothing. `canSendToClaude()` tells the page beforehand whether it can go through: `available`, `writers_only`, `no_session` or `off`. The other capabilities do not fit: `db` keeps answers that the agent-session must poll with the ArtifactData tool, which wakes nothing, as GHI 1186's earlier watcher did by reading an undocumented route with Claude Code's login token; `room` reaches only the views open at that moment, and keeps nothing.

**Build-slice 0's trial of 2026-11-07.** fleet-restart-at-login's agent-session `79bd8b1d-030c-4cf9-a0f9-587e4bb485ee` published a test page at https://claude.ai/artifact/SgQHELViiS4KyRsEP64PAa with the `comments` capability at 22:32 UTC, and the ArtifactComments tool's status then showed the page's watch "connected, armed by a publish, auto-replies armed". At 22:41:53 UTC the user pressed A on the page from the Claude app; the agent-session had ended its last turn at 22:37:37. The press posted a comment thread, `6994bcc0-72bc-4c05-ba01-88891e8f5e68`, anchored at the page's `#item` element, with the text `#item_page_answer item 1 of 1: A (trial)`, which the ArtifactComments tool's read lists as from "the user (owner), posted by the artifact, sent to you". The press started no turn, and nothing put its text before the agent: the agent-session's next turn began when the user typed "Done." at 22:41:59, that turn's prompt held only "Done.", and the agent found the press by reading the page's comments with the ArtifactComments tool, then replied in the thread and resolved it. Claude Code's record of the page's comments, written in the transcript after that read, lists the thread as sent at 22:41:53. Two facts limit what the trial shows: the user typed six seconds after his press, and a background agent's notification that arrived at 22:38:23, while the agent-session was waiting, started no turn either, though such notifications at 22:34:25 and 22:37:31 had each started one within a second; so the trial does not tell apart a press that never starts a turn from an agent-session that was starting no turns for any event in those minutes. The records are in `nedlern@ned-box:/home/nedlern/.claude/projects/-home-nedlern-agents-fleet-restart-at-login/79bd8b1d-030c-4cf9-a0f9-587e4bb485ee.jsonl`, lines 1029 and 1052 (the publish and the watch), 1063 to 1068 and 1132 to 1136 (the two notifications that started turns), 1152 to 1161 (the last turn's end, the notification, and "Done."), 1165 (the comment read) and 1180 (Claude Code's comment record). Steps 3 and 4 below assume a press starts a turn; until the user decides how the design goes on, a press waits for the agent to read the page's comments in a turn that something else started, and a page built as step 1 says keeps its buttons and text field disabled after the press until the agent republishes it in that turn.

1. **The page.** A new item page builder, written in build-slice 1, makes the page the agent publishes: the item's text, and below it the answers he types today, as buttons, A approve, AO approve as obvious, Aa approve after an advisor check, D disapprove, Z defer and E explain, and a text field for a short typed reply, with a Send button that sends it. An item with parts gets the buttons once per part, except Z, because `check` takes no Z for a part, and a Send button that sends every part's answer at once, such as `1 a 2 d`; an item with options also gets O2 and O3, which choose its second or third option; and an item that asks no decision gets one button, Next, which sends `next`, recorded by `check --moved-on-no-decision`. The builder reads which of these the item has, parts, options or no decision, from the item in the walk-document, through `nc-systems/skills/walk-me-through/walk-me-through-approval-walk-minutes-and-walk-document-item-finder-common.py`, not from the agent, and prints the publish call's arguments, `capabilities: {comments: {}}` included, with the link on the walk-minutes' last `#item_page` line as the page to update; when the approval-walk has no `#item_page` line yet, the call publishes a new page. After a press the page disables its buttons and text field until it is republished, so a double press sends once. Each republish updates the approval-walk's one page in place, so it adds no new artifact toward the limit of 100 he hit. On load the page calls `canSendToClaude()`. When it answers `available`, the buttons and text field are enabled; otherwise they are disabled, and the page says to answer in the chat. When a press rejects, nothing was posted, so the page enables its buttons and text field again and says to press again or answer in the chat.
2. **A press.** Pressing D on item 16.3.5 of 25 calls `sendToClaude` with the text `#item_page_answer item 16.3.5 of 25: D`, anchored at the item's heading; a typed reply sends `#item_page_answer item 16.3.5 of 25: <his words>`. The item number lets code refuse an answer, from a page left open, for an item that is no longer waiting.
3. **The wake.** The ned-box agent-session that published the page watches it: a publish arms the watch and its comment replies when comment auto-replies, which the ArtifactComments tool's description names but whose setting is not documented, are on for that agent-session; build-slice 0 finds where they are turned on, and the agent-seat's settings turn it on, with a test that fails when it is off. The design assumed that the comment starts a turn in that agent-session, which Remote Control shows on the iPad; in the trial of 2026-11-07, with auto-replies armed, the comment started no turn.
4. **The record.** This step holds only if build-slice 0 shows that a comment turn runs UserPromptSubmit hooks. In the trial of 2026-11-07 there was no comment turn, so no UserPromptSubmit hook could see the press, and the thread id came from the ArtifactComments tool's read, not from a turn. The walk-me-through UserPromptSubmit hook, `nc-systems/skills/walk-me-through/walk-me-through-user-short-answer-to-approval-walk-item-expanded-into-instructions-user-prompt-submit-hook.py`, learns one more form: a turn that is an artifact comment sent to Claude, on the page the walk-minutes' last `#item_page` line names, whose text starts `#item_page_answer item <N> of <M>:`. When N is an item the walk-minutes' last `#next_to_present` line names, and the words after the colon read as one answer to the hook's existing parser, such as `D`, `1 a 2 d` or `next`, the hook runs `check` itself, with the answer's flag and a new flag, `--user-reply-from-item-page-comment-thread <page link> <thread id>`, taking the thread id from the comment turn, where build-slice 0 finds it, which writes the answer into the walk-minutes as `page <link>, thread <id>, answered <answer> with "<his words>" at <time>`, never as typed words. An E, pressed or typed on the page, is not recorded by `check`: the hook hands the agent the same instruction as an E typed in the chat, to run the explain skill on the item. When `check` leaves nothing for the agent to judge, the hook runs `close` too, and hands the agent what `close` printed with step 5's instruction, the reply line and the builder command for the next item; otherwise it hands the agent what `check` printed and the `close` command to run once the agent has judged it, as for a typed answer. When `check` refuses, the hook records nothing and hands the agent the refusal, to reply in the thread. Words that do not read as an answer, such as a question, reach the agent as an ordinary prompt from the page; the agent replies in the thread, and the item stays waiting. When N is not a waiting item, the hook records nothing and tells the agent which item is waiting. When N is an item that the page builder recorded as approving a guarded-file, the hook records nothing and tells the agent to ask for the answer in the chat, as the section "Approvals of guarded-files" says.
5. **The reply on the page.** The agent replies into the thread with the ArtifactComments tool in one line, such as "Recorded: item 16.3.5 disapproved; item 16.3.5.1 is next", resolves the thread, and republishes the page with the next item. The answer is already recorded, so an agent-session that ends before this step loses only the reply; its successor republishes the page with the next item when it resumes, as the walk-me-through skill says, and the hook of the section "After an account switch" asks it to when the agent-session id is recorded.

## After an account switch

A page made under one Claude account stops opening once Claude Code on ned-box is logged in to another. Each ned-box agent-session can read, without a model, which account it runs under: Claude Code keeps the account's fixed id, `oauthAccount.accountUuid` in `~/.claude.json`, beside its login, as read on ned-box on 2026-11-05.

1. **Publishing records the account.** Every publish of an item page records its `#item_page` line through the check program's subcommand of the section "Failures", which reads the account id from `~/.claude.json` itself and writes it beside the page's link, so no agent writes the line or the id by hand. If build-slice 0 shows that a new agent-session does not hear presses on a page its predecessor published, the subcommand also writes the id of the agent-session that published the page.
2. **A hook compares.** A hook, written in build-slice 3, runs at each turn of the agent-session and at its start. It compares the logged-in account with the one recorded for the waiting item's page. When they differ, it tells the agent to publish the waiting item's page again, under the new account, at a new link, because the old page belongs to the old account; to record the new link in the walk-minutes' `#item_page` line, which step 4 then reads; and to put the new link in the item's closing line in its next message. When the agent-session id is recorded, the hook also compares it with the current agent-session's id; when only the agent-session differs and an item is waiting, it tells the agent to publish that item's page again at the same link, and asks at each turn until the publish has recorded the `#item_page` line again with the current agent-session's id. If build-slice 0 shows that a watch with the ArtifactComments tool alone makes the new agent-session hear presses, the hook asks for that watch instead of a publish, and for the `#item_page` line to be recorded again through the same subcommand after it, which is what stops the asking. When both the account and the agent-session differ, the hook takes the account path: a new link.
3. **Example.** The agents run under his first account, and item 4 of an approval-walk is waiting, its page open on his iPad. He switches to his second account. At the agent's next turn, or when it restarts, the hook finds that the account differs from the one recorded for item 4's page, and the agent publishes item 4 again and gives the new link. Had he kept the account, and the agent-session handed off to a successor instead, the successor's hook would find a different agent-session id at its start, and the successor would publish item 4's page again at the same link, so that its buttons reach the successor.

An agent waiting for his answer has no turn until something wakes it, so the old link stays broken until then; an answer typed in the chat still works, and in that turn the hook has the agent publish the page of the item that is then waiting, the next one, under the new account. A job running a light agent every minute was weighed and set aside: it costs a model call each minute and needs a job to run it, while the hook costs nothing while the account stays the same.

## Deleting pages

Agents do not delete item pages. The hook `.claude/guard-hooks/claude-code-artifact-tool-claude-ai-page-delete-refusal-hook.py` refuses every Artifact tool delete of a claude.ai page and nothing else, so no confirmation dialog for a delete reaches the user; walk items, walk-documents and files are not affected. Old pages stay in his claude.ai gallery until he deletes them himself. This design changes nothing there.

## Failures

- **Answered twice.** Whichever answer arrives first is recorded, and moves the `#next_to_present` line on. A page answer arriving second names an item no longer waiting, so step 4 refuses it and the agent says so in the thread. A typed answer arriving second answers the next item, as a typed answer does today; the agent's message after the page answer shows that next item, so he answers it having seen it, unless he typed before that message arrived. That last case is a risk this design accepts, as the chat already does when he types ahead.
- **No agent-session is listening.** After a session-handoff or a crash, the successor may not hear presses on the page; build-slice 0 checks this. If it does not, the hook of the section "After an account switch" has the successor publish the page again at the same link, or watch it if a watch alone is enough. Until then `canSendToClaude()` answers `no_session`, and the page tells him to answer in the chat.
- **The page breaks.** When a publish to the approval-walk's page is refused because the page is gone, the agent publishes a new page and records its link with a new subcommand of the check program, which writes and checks the `#item_page` line that step 4 reads from then on. After an account switch the page does not open until the agent publishes it again, as the section "After an account switch" says; until then he answers in the chat.
- **The comment does not reach the hook.** Build-slice 0 checks this. If a comment turn starts no UserPromptSubmit hook, step 4 moves to a hook that does see it; if none does, the page shows the item only, and he answers in the chat as today. The trial of 2026-11-07 met this case: the press started no turn, so no hook saw it. Taking the fallback would remove the answer on the page that he asked for, so the choice goes to him first.

## Approvals of guarded-files

An item that approves a new version of a guarded-file, such as a hook, CLAUDE.md or a skill, puts the user's words into `.walk-approved`, and checks such as `scripts/search-user-messages-in-transcripts.py` compare them with his typed words in the transcript. A button press, or words typed in the page's text field, reaches the agent as a comment, not as words typed in the chat, so those checks would not find it. Such an item's page therefore disables its buttons and text field and asks for the answer in the chat, and step 4's hook refuses a page answer for that item. Typing A, AO or Aa in the chat stays on every item. The page builder decides which items these are, by testing the paths the item's change touches, read from the item in the walk-document, with the instruction-file guard's own test for a guarded-file, and records its verdict for the item beside the page's link, which step 4's hook reads instead of judging again.

## The build-slices

Approval-walks run in a main agent-session, which is the only kind that can watch a page; a subagent does not present items to the user. Each build-slice is one pull request that leaves main working, except build-slice 0, which merges no code. No pull request is opened while merge-lane-2's pause on new pull requests holds.

0. **The trial.** On one test page published from a ned-box agent-session: a button calling `sendToClaude` from the Claude app on the iPad starts a turn in that agent-session; the turn's text is captured; and a UserPromptSubmit hook is shown to run on that turn. The trial also records whether comment auto-replies are on for agent-seat agent-sessions, what a declined consent makes `sendToClaude` reject, whether a running agent-session sees an account switch in `~/.claude.json` at its next turn, whether a second agent-session hears a press on a page the first one published, whether a watch with the ArtifactComments tool alone, without a publish, makes the second agent-session hear presses, and whether an agent-session whose context is compacted keeps its watch. Its results are written into this GHI-MD. Results so far, from the trial of 2026-11-07 that the section "How an answer travels" describes: the press posted its comment thread and the thread was sent to Claude, but no turn started, so there was no turn text to capture and no UserPromptSubmit hook to show; the publishing agent-session's watch showed auto-replies armed. Not yet checked: whether a press starts a turn in an agent-session that is starting turns for other events, what a declined consent makes `sendToClaude` reject, whether a running agent-session sees an account switch, whether a second agent-session hears a press, whether a watch alone is enough, and whether a compacted agent-session keeps its watch.
1. **The page and the record.** A new item page builder, `walk-me-through-answerable-item-page-html-builder.py`, to be written in the directory `nc-systems/skills/walk-me-through/`, which GHI [Approval-walk item page publisher copying linked files into the page as timestamped copies, so short repository and log-store paths open on the iPad](https://github.com/nedschorus/nedschorus/issues/2168)'s publisher would use too; the hook's new form, its refusal for guarded-file items included; and `check`'s new flag; with tests that feed the hook the comment turn build-slice 0 captured. The trial of 2026-11-07 captured no comment turn, because the press started none.
2. **The skill.** The walk-me-through skill's paragraph on publishing item pages says to publish them with `capabilities: {comments: {}}`, and to reply in and resolve the thread after a page answer. This is an instruction change, which goes to the user before it is made.
3. **The account switch and the new agent-session.** Recording the account at each publish, and, if build-slice 0 shows a successor does not hear presses, the publishing agent-session's id too; and the hook of the section "After an account switch", with a test that feeds the hook a changed account id and, when the agent-session id is recorded, one that feeds it a changed agent-session id. The walk-me-through skill says today to republish an item's page to the link its `#item_page` line records, when the item changes and when a successor resumes the approval-walk; with this build-slice, both sentences change to say that after an account switch the page is published at a new link and the `#item_page` line is updated, and the successor's sentence changes to say that the hook asks the successor for the publish, or the watch. This is an instruction change too, which goes to the user before it is made. This build-slice does not wait on build-slices 1 and 2.

## Deferred-decisions

- Whether the approval check accepts a page answer for an item that approves a guarded-file, which needs the transcript checks to read answers that arrive as comments: proposed after build-slice 0, as fleet-restart-at-login's task #482.
- Where the account id, the agent-session id and the guarded-file verdict are written beside a page's link: in the `#item_page` line, which changes the parser of step 4's hook with it, or in a line of their own; and where the check program's subcommand and the hook read the agent-session id from.
- Whether a page answer can carry his words with a button's answer, such as D and a reason, and whether an item with parts gets a text field per part.
- What the hook does with a page answer whose M differs from the walk-minutes' count.
- How `check` is given his words for `<his words>`, and what it records there for a button press.
- Whether the page calls `canSendToClaude()` again after load, so that a page opened while no agent-session watched it enables its buttons once one does.
- Whether a PostToolUse hook on the Artifact tool writes the `#item_page` line after each publish, instead of the agent running the check program's subcommand.
- How the walk-document marks the paths an item's change touches, so that the page builder reads them rather than guessing from the item's prose.
- The name of the check program's subcommand that writes and checks the `#item_page` line.
- What the page shows, and what the agent replies in the thread, after the last item of an approval-walk is answered.
- How the page's buttons and text field are enabled again after a page answer that `check` refuses, or words that do not read as an answer, since neither moves the approval-walk on.
