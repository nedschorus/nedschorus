# Failures no agent is watching go first to an agent; a window opens on the user's Mac only when that agent needs him or no agent can run

This is a design. None of its pieces is built. It replaces a design of 2026-10-13 for a queue of messages to the user, which the user set aside that day in the fleet-restart-at-login agent-seat. Version 4: version 1 was rewritten after a Claude review and a Codex review, version 2 after a cold-read-full-run of six reviewers, and version 3 after a sanity-check; the records are listed at the end.

## The problem

Programs that run with no agent watching, chiefly the scheduled jobs in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, report their failures into log files that no program reads to the user. On origin/main at c2723d96 that file declares six jobs: `transcript-mirror-to-log-store` (both machines, every minute), `log-store-session-dialogs-refresh` (ned-box, every 10 minutes), `daily-full-test-run-of-main` (both, 03:30), `daily-clean-worktrees` (both, 06:30), `handoff-agent-seat-died-without-session-handoff-restart-watcher` (ned-box, every minute; below, the crash restart watcher) and `weekly-uncommitted-work-snapshot-hook-real-claude-session-owner-check` (both, weekly; below, the weekly work-snapshot owner check). Each appends its output to a log under `~/.claude/`. The daily full test run and the weekly work-snapshot owner check also write records to the log-store, and the crash restart watcher also opens notice windows on the user's Mac.

- `scripts/daily-full-test-run-of-main.py`, when it cannot write its record (around lines 479 to 497), prints "Tell the user what the line above says" and exits nonzero. It runs from cron and launchd, so no agent reads that instruction, and neither does the user.
- `scripts/clean-worktrees.py` exits 1 when a removal or a deletion fails. On 2026-10-13, `/home/nedlern/.claude/daily-clean-worktrees.log` on ned-box held eight FAILED lines nobody had seen: six for worktrees git lists as locked, which Claude Code locks while an agent works in them, and two for one branch that git would not delete, on two days.
- `scripts/transcript-mirror-to-log-store.py --failures-only` prints only FAILED lines, into a log nobody reads.
- Nothing tells the user when Claude is logged out or at its usage limit on a machine, or when ned-box cannot be reached, except an agent that happens to notice.
- The crash restart watcher is the one program with a route: it opens a notice window on the user's Mac with `scripts/open-mac-window-from-ned-box.py` when it cannot or will not restart an agent-seat, and when its own run fails. Three of its six notices tell the user to ask an agent to investigate.

The daily maintenance step of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) and the nightly test report of GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) have a route to the user that he decided on 2026-10-12, a hook at his first prompt of the day, not yet built. Their due jobs are not failures, and this design leaves them on that route. The nightly test report also reports a failed test run and a failed weekly work-snapshot owner check record to the user.

A survey of the eight running agent-seats on both machines on 2026-10-13 found no other route.

## What the user asked for

The user, on 2026-10-13, in the fleet-restart-at-login agent-seat: "when things go wrong I really want an agent to be the first line of defense, not me personally." "Right now when HW is down or can't log in, or run out of tokens I need to know, and I may want to work with some agent to do some investigation if what's wrong isn't obviious." "a -p agent can easily be wrapped to have a discussion with it, if it's still around to resume or continue." "I don't want to see the escalation agent unless it's needed because it will take screen space that's not needed 99% of the time. So I'd like to be able to close it in iterm2, and have it pop up when necessary."

## The design in one paragraph

When a scheduled job on ned-box fails, the wrapper that runs it records the failure in an incident file and starts nothing. The incident handler, a scheduled job every minute on ned-box, first gives the job one more chance: it waits for the next run of a job that runs every few minutes, or reruns any other job once, and closes the incident if that run passes. Only a failure that persists starts the escalation agent: one headless `claude -p` conversation, in a worktree of the project so that the project's hooks apply, given the escalation policy. The escalation agent investigates, fixes what the policy lets it fix or files a task or a pull request, and returns a verdict and a summary as structured output, which the incident handler writes into the incident file. A `claude -p` conversation ends by itself when its answer is done. Only for the verdict `user-needed` does the incident handler open a window on the user's Mac, running `claude --resume <session id>` on ned-box, so he arrives in a conversation with the agent that did the groundwork. Closing that window ends the resumed conversation, not the incident; the window tells him how to reopen it. The incident handler also checks every hour that Claude is logged in and under its usage limit, and the Mac checks that ned-box answers; each opens a notice window once per outage. The Mac's own jobs are covered only if open question 4 says so.

## The escalation policy

| Case | Detected by | First responder | What the agent may do itself | When a window opens on the user's Mac | What the window shows |
|---|---|---|---|---|---|
| A scheduled job on ned-box fails, and fails again on its next run or its one rerun | the wrapper, from the job's exit code | escalation agent | read the job's output, its log and its run record; clear what the job's own documentation says is safe to clear; file a task for the agent-seat named as the job's owner; open a pull request for a code defect | the agent's verdict is `user-needed`: the cause is unknown, the fix needs a decision only the user makes, or the job's first run after a fix the agent recorded also failed | the agent's summary, the command to reopen the window, then the resumed conversation |
| The crash restart watcher cannot or will not restart an agent-seat | the watcher | today the watcher's own notice window; see open question 3 | | | |
| Claude is logged out on ned-box | the Claude health check | none: no agent can run | nothing | at once, once per outage | the command to log in on ned-box, and how many incidents are `waiting` |
| Claude is at its usage limit, or fails some other way, on ned-box | the Claude health check | none | nothing | at once, once per outage | Claude's own output, including when a limit resets, and how many incidents are `waiting` |
| ned-box does not answer ssh from the Mac | the ned-box reachability check, on the Mac | none | nothing | after three failed checks in a row, once per outage; again when ned-box answers | the time of the first failed check and ssh's last error |

## The pieces

- **Run record.** The wrapper writes every run's start time and exit code, passed or failed, to a run record for the job, under `~/.local/state/nedschorus/unattended-failure-escalation/` on ned-box, where the crash restart watcher keeps its own state.
- **Incident file.** One file per incident, in the same directory, named `<job name>-<time of the first failure>`. It holds the job's `name` in the scheduled-jobs table, which is the incident's key; the exit code and the failing run's whole output; for each repeat, its time, exit code and first lines of output; the state; the verdict, the summary and, for `fix-pending`, the fix's kind and reference; the session id, process id and process start time of its `claude -p` conversation; and whether its window has been shown, and when. A finished incident's file is copied to the log-store.
- **One program writes incident files**, under one lock: the wrapper, the incident handler and the verdict command all call it, and so does the crash restart watcher if open question 3 is approved. The escalation agent never writes the file itself.
- **States.** Each state is one exact string: `waiting`, `being-handled`, `handled`, `fix-pending`, `user-needed`. A failure whose key has an incident in any state but `handled` appends a repeat to that incident instead of starting a new one, so a job that fails every minute makes one incident. A repeat appended while the incident is `being-handled` returns it to `waiting` only when the verdict is `handled`; after `fix-pending` or `user-needed` the repeat is recorded and the verdict stands.
- **Fix confirmation.** The incident handler holds a `fix-pending` incident until the job's first run that started after the fix took effect, for a pull request after the merge reached the clone the job runs from, and reads that run in the run record: exit 0 sets `handled`, a failure sets `user-needed`. A pull request closed without merging sets `user-needed`. A run that exits 0 only because an earlier run held the job's lock does not confirm a fix (open question 6).
- **The wrapper.** `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py` writes each wrapped job's cron line to run the job through the wrapper, which runs the job, appends its output to the job's log as now, writes the run record, and reports a nonzero exit to the incident program. The scheduled-jobs table marks the jobs that are not wrapped with `wrapped: false`: the crash restart watcher and the incident handler. A failure of the wrapper or of the incident handler opens a notice window directly, once per distinct error, as the crash restart watcher's run-failed notice does. The table's `lines_of_job` matches a cron line by `/<program file name>` (origin/main), so a wrapped line still matches its job; build-slice 3 tests that the wrapper's own file name is never a job's program.
- **A nonzero exit must mean a failure.** Three programs exit nonzero when nothing failed, and are changed in build-slice 1. The transcript mirror and `log-store-session-dialogs-refresh` exit 0 instead of `EXIT_LOCKED = 3` when an earlier run holds their lock. `clean-worktrees.py` keeps a worktree that git lists as locked, prints that it kept it, and exits 0 for that case. The daily full test run's `EXIT_ANOTHER_DAILY_RUN_HOLDS_THE_LOCK = 6` stays a failure, since it fires only when a run from a day earlier still holds the lock. Whether a red nightly test run is an incident is open question 5.
- **The incident handler**, a scheduled job every minute on ned-box. It exits 0 at once if another run holds its lock. For each `waiting` incident whose job has not yet had its one more chance, it waits for the next scheduled run of a job whose schedule is `*` or `*/N`, and reruns any other job once through the wrapper unless the table marks it `rerun_on_failure: false` (the daily full test run and `daily-clean-worktrees`); a run that exits 0 sets `handled`. Before it starts any conversation it runs the Claude health check, and on failure it stops, leaving incidents `waiting`. Otherwise, for each incident still failing, it sets `being-handled`, records the conversation's session id (passed with `--session-id`), process id and start time, and runs `claude -p --output-format json --json-schema <verdict schema>`, with the escalation policy, the incident file and a time limit. The schema holds `verdict` (one of `handled`, `fix-pending`, `user-needed`), `summary`, and for `fix-pending` the fix's kind and reference. At the time limit the handler kills the conversation's process group, as the weekly work-snapshot owner check does (lines 157 to 169). A timeout, a nonzero exit or output that does not match the schema sets `user-needed`, with what went wrong in the summary. A later run that finds an incident `being-handled` past the time limit kills that process group if the same process is still alive, then takes the incident up again.
- **Where the conversation runs.** The incident handler adds a worktree from origin/main at `<clone>/.claude/worktrees/unattended-failure-escalation-<incident>` and locks it while the incident is open, so the project's hooks in `.claude/settings.json`, such as the force-push guard and the instruction-file guard, apply to the escalation agent. `scripts/recover-crashed-seats.py` counts only directories under `~/agents` as agent-seats, so it never takes this worktree for one, and build-slice 1's change to `clean-worktrees.py` keeps a locked worktree. A code fix is made in that worktree. For the conversation the handler sets `CLAUDE_CODE_TASK_LIST_ID=nedschorus-<owner>-tasks`, composed as `scripts/launch-claude-ubuntu` composes it, so a task the agent files goes on the job owner's task list.
- **The escalation policy** is a tracked file in `nc-systems/unattended-failure-escalation/`, approved by the user word for word in build-slice 2: what the agent may fix itself, what it must bring to the user, and what its summary holds. The incident handler hands it to each conversation.
- **The window.** For `user-needed`, the incident handler opens a window on the Mac with `scripts/open-mac-window-from-ned-box.py`, running a small script on ned-box. That script first marks the incident's window as shown, then prints the summary and the command to reopen the window from a Terminal on the Mac, `ssh -t nedlern@ned-box <that script>`, which opens the newest `user-needed` incident, and then runs `claude --resume <session id>` in the incident's worktree; it waits for Enter if `claude --resume` fails. When the window has not marked itself shown, the next run of the incident handler tries again, so a window the opener reported as "may not have opened" is not opened twice. While the incident stays `user-needed`, the window opens again once a day (open question 7). In the resumed conversation, the agent records a new verdict with the verdict command, `<verdict command> <incident> <verdict> --summary <text>`, which goes through the incident program and its lock; only that ends `user-needed`.
- **The Claude health check** runs inside the incident handler, before any conversation and otherwise once an hour, under the handler's lock. It runs `claude auth status --json` first, which uses no tokens; `loggedIn: false` is the logged-out case. Otherwise it sends one short `claude -p` request on the model the escalation agent uses, and takes a nonzero exit, unparseable output or `is_error` as a failure, showing Claude's own output. A failure opens a notice window once per outage, recorded in the handler's state; an outage counts as announced only once its window has opened. A pass after a failure clears the outage.
- **The ned-box reachability check**, a scheduled job on the Mac every five minutes, runs `ssh` to ned-box with a short time limit. After three failures in a row it opens a notice window on the Mac with `scripts/open-iterm-window-running-command`, once per outage, recorded in a state file on the Mac, and a second window when ned-box answers again.

## Where it is written down

- The scheduled-jobs file's header and the installer's docstring say that a wrapped job's failure goes to the escalation agent, that a nonzero exit must mean a failure, and what `wrapped`, `rerun_on_failure` and `owner` mean.
- Each job in the scheduled-jobs table gets an `owner` field naming the agent-seat that owns it; the installer's `--check` reports an `owner` that names no agent-seat of the machine running the job, or a retired one.

## Open questions

1. **Names and new system-terms.** A name check on 2026-10-13 against `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md` judged "escalation" alone too vague and proposed the system name `unattended-failure-escalation`. This document names the pieces "escalation agent", "escalation policy", "incident handler", "incident file", "run record", "verdict command" and "wrapper". Recommend the system name; recommend that only "escalation agent", "escalation policy" and "incident" become system-terms of `unattended-failure-escalation`, in a new system glossary, and the rest stay plain words; and that the user approves each term, after a name check of each program's file name, before any code or instruction file uses them. "Incident handler" replaces "drainer", which collides with the project's queue-drain.
2. **What the agent may fix without asking.** Recommend starting as narrow as the table says and widening it as incidents show what is safe.
3. **The crash restart watcher's notices.** Three of its six notices ask the user to ask an agent to investigate. Recommend the watcher writes an incident for those three, through the incident program, when Claude works, so an agent looks first, and keeps its own notice window for when Claude does not.
4. **The Mac's own failures.** An agent on ned-box cannot run commands on the Mac: ned-box's key to the Mac only opens windows. Recommend the Mac runs the same incident handler for its own jobs, with its own incident directory, and pauses only the Mac's transcript mirror while the reachability check records ned-box down, since that mirror then fails every minute for that reason alone.
5. **A red nightly test run and a failed weekly owner check.** Both already reach the user through the decided route of the nightly test report, linked above. Recommend that the daily full test run and the weekly work-snapshot owner check exit 0 once their record is written, whatever its verdict, so only a failure of the run itself is an incident and no failure reaches the user twice.
6. **A run that skipped because an earlier run held the lock.** It must not confirm a fix. Two ways: the wrapper records the skip as its own outcome in the run record, which needs the job to say so in its output; or the job keeps a distinct exit code that the scheduled-jobs table lists as "skipped, not a failure". Recommend the second, because the wrapper then needs no parsing.
7. **A `user-needed` incident the user closes without answering.** Recommend the window reopens once a day until the first-prompt hook of the daily maintenance step, linked above, is built, and after that the hook shows a daily line instead, the route the user chose for items that are not urgent.
8. **Several incidents with one cause.** A full disk could fail six jobs at once and open six windows. Recommend at most one window open at a time, the others waiting until it is closed.
9. **A job that stops running, and failures just after a reboot.** Both reviewers' independent designs detect a job that has not run when it should, and ignore failures in the first minutes after a reboot. Neither case has happened. Recommend neither for now; the run record makes the first cheap to add later.

## Verified, and not verified

- Verified on ned-box on 2026-10-13: a `claude -p` conversation can be continued with `claude -p --resume <session id>` and remembers the text it was first given. A sanity-check cell ran `claude -p --json-schema` on ned-box and got validated structured output back.
- Not verified: that an interactive `claude --resume <session id>` opens that same conversation in a window, and that `claude -p` started from cron keeps its session; build-slice 2 checks both first. The weekly work-snapshot owner check runs `claude -p` from cron, but with `--no-session-persistence`, and its first run is still to come.
- Not verified: the output of `claude auth status --json` when logged out, beyond a sanity-check cell's report of its `loggedIn` field.
