# Failures no agent is watching go first to an agent; a window opens on the user's Mac only when that agent needs him or no agent can run

This is a design. None of its pieces is built. It replaces a design of 2026-10-13 for a queue of messages to the user, which the user set aside that day in the fleet-restart-at-login agent-seat. Version 3: version 1 was rewritten after a Claude review and a Codex review, and version 2 after a cold-read-full-run of six reviewers; the records are listed at the end.

## The problem

Programs that run with no agent watching, chiefly the scheduled jobs in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, report their failures into log files that no program reads to the user. On origin/main at c2723d96 that file declares six jobs: `transcript-mirror-to-log-store` (both machines, every minute), `log-store-session-dialogs-refresh` (ned-box, every 10 minutes), `daily-full-test-run-of-main` (both, 03:30), `daily-clean-worktrees` (both, 06:30), `handoff-agent-seat-died-without-session-handoff-restart-watcher` (ned-box, every minute; below, the crash restart watcher) and `weekly-uncommitted-work-snapshot-hook-real-claude-session-owner-check` (both, weekly; below, the weekly work-snapshot owner check). Each appends its output to a log under `~/.claude/`. The daily full test run and the weekly work-snapshot owner check also write records to the log-store, and the crash restart watcher also opens notice windows on the user's Mac.

- `scripts/daily-full-test-run-of-main.py`, when it cannot write its record (around lines 479 to 497), prints "Tell the user what the line above says" and exits nonzero. It runs from cron and launchd, so no agent reads that instruction, and neither does the user.
- `scripts/clean-worktrees.py` exits 1 when a removal or a deletion fails. On 2026-10-13, `/home/nedlern/.claude/daily-clean-worktrees.log` on ned-box held eight FAILED lines nobody had seen: six for worktrees git lists as locked, which Claude Code locks while an agent works in them, and two for one branch that git would not delete, on two days.
- `scripts/transcript-mirror-to-log-store.py --failures-only` prints only FAILED lines, into a log nobody reads.
- Nothing tells the user when Claude is logged out or at its usage limit on a machine, or when ned-box cannot be reached, except an agent that happens to notice.
- The crash restart watcher is the one program with a route: it opens a notice window on the user's Mac with `scripts/open-mac-window-from-ned-box.py` when it cannot or will not restart an agent-seat, and when its own run fails. Three of its six notices tell the user to ask an agent to investigate.

The daily maintenance step of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) and the nightly test report of GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) have a route to the user that he decided on 2026-10-12, a hook at his first prompt of the day, not yet built. Their due jobs are not failures, and this design leaves them on that route.

A survey of the eight running agent-seats on both machines on 2026-10-13 found no other route.

## What the user asked for

The user, on 2026-10-13, in the fleet-restart-at-login agent-seat: "when things go wrong I really want an agent to be the first line of defense, not me personally." "Right now when HW is down or can't log in, or run out of tokens I need to know, and I may want to work with some agent to do some investigation if what's wrong isn't obviious." "a -p agent can easily be wrapped to have a discussion with it, if it's still around to resume or continue." "I don't want to see the escalation agent unless it's needed because it will take screen space that's not needed 99% of the time. So I'd like to be able to close it in iterm2, and have it pop up when necessary."

## The design in one paragraph

When a scheduled job on ned-box fails, the wrapper that runs it writes an incident file and starts nothing. The incident handler, a scheduled job every minute on ned-box, takes a lock, and for each incident that is waiting runs one headless `claude -p` conversation, the escalation agent, given the escalation policy. The escalation agent investigates, fixes what the policy lets it fix or files a task or a pull request, writes a summary into the incident file, and ends its answer with one verdict line. A `claude -p` conversation ends by itself when its answer is done. Only for the verdict `user-needed` does the incident handler open a window on the user's Mac, running `claude --resume <session id>` on ned-box, so he arrives in a conversation with the agent that did the groundwork. Closing that window ends the resumed conversation, not the incident; the window tells him how to reopen it. Two health checks cover what no agent can handle, Claude logged out or at its usage limit, and ned-box unreachable; each opens a notice window once per outage. The Mac's own jobs are covered only if open question 4 says so.

## The escalation policy

| Case | Detected by | First responder | What the agent may do itself | When a window opens on the user's Mac | What the window shows |
|---|---|---|---|---|---|
| A scheduled job on ned-box fails | the wrapper, from the job's exit code | escalation agent | read the job's output and log; rerun the job once, except the daily full test run and `clean-worktrees.py --remove`; clear what the job's own documentation says is safe to clear; file a task for the agent-seat named as the job's owner; open a pull request for a code defect | the agent's verdict is `user-needed`: the cause is unknown, the fix needs a decision only the user makes, or the failure came back after a fix the agent recorded | the agent's summary, the command to reopen the window, then the resumed conversation |
| The crash restart watcher cannot or will not restart an agent-seat | the watcher | today the watcher's own notice window; see open question 3 | | | |
| Claude is logged out on ned-box | the Claude health check | none: no agent can run | nothing | at once, once per outage | Claude's own output, the command to log in on ned-box, and how many incidents are `waiting-for-claude` |
| Claude is at its usage limit on ned-box | the Claude health check | none | nothing | at once, once per outage | Claude's own output, including when the limit resets, and how many incidents are `waiting-for-claude` |
| ned-box does not answer ssh from the Mac | the ned-box reachability check, on the Mac | none | nothing | after three failed checks in a row, once per outage; again when ned-box answers | the time of the first failed check and ssh's last error |

## The pieces

- **Incident file.** One file per incident, under `~/.local/state/nedschorus/unattended-failure-escalation/incidents/` on ned-box, where the crash restart watcher keeps its own state. It holds the incident's key, the machine, the exit code and the failing run's whole output; for each repeat, its time, exit code and first lines of output; the state; the escalation agent's summary; the session id of its `claude -p` conversation; and the date a window last opened. A finished incident's file is copied to the log-store.
- **Key.** The key is the job's `name` in the scheduled-jobs table. The file is named `<key>-<time of the first failure>`.
- **States.** Each state is one exact string: `waiting`, `being-handled`, `handled`, `fix-pending`, `user-needed`, `waiting-for-claude`. A failure whose key has an incident in any state but `handled` appends a repeat to that incident instead of starting a new one, so a job that fails every minute makes one incident. A repeat appended while the incident is `being-handled` returns it to `waiting` once that conversation ends, so the repeat is looked at. At a `fix-pending` incident's recheck time, the incident handler sets `handled` if no repeat was appended after the fix was recorded, and `user-needed` if one was. Incidents that are `waiting-for-claude` return to `waiting` when the Claude health check passes.
- **Verdict line.** The escalation agent ends its answer with exactly one of `VERDICT: handled`, `VERDICT: fix-pending <task or pull request> <recheck time>` and `VERDICT: user-needed`, and the incident handler sets the state of the same name.
- **The wrapper.** `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py` writes each wrapped job's cron line to run the job through the wrapper, which runs the job, appends its output to the job's log as now, and writes or appends to the job's incident when the job exits nonzero. The wrapper and the incident handler each take one lock for each change to an incident file. The crash restart watcher, the incident handler and the two health checks are not wrapped. A failure of the wrapper or of the incident handler opens a notice window directly, once per distinct error, as the crash restart watcher's run-failed notice does.
- **A nonzero exit must mean a failure.** Four programs exit nonzero when nothing failed, and are changed in build-slice 1. The transcript mirror and `log-store-session-dialogs-refresh` return `EXIT_LOCKED = 3`, and the daily full test run returns `EXIT_ANOTHER_DAILY_RUN_HOLDS_THE_LOCK = 6`, when an earlier run still holds their lock: each exits 0 instead while the earlier run is younger than a few of its periods, and after that prints that the earlier run looks stuck and exits nonzero. `clean-worktrees.py` keeps a worktree that git lists as locked, prints that it kept it, and exits 0 for that case. The daily full test run also exits with the test runner's code when tests fail (line 504); whether a red nightly run is an incident is open question 5.
- **The incident handler**, a scheduled job every minute on ned-box. It exits 0 at once if another run holds its lock. Before it runs any agent it runs the Claude health check; on failure it sets `waiting` incidents to `waiting-for-claude` and stops. Otherwise it handles each `waiting` incident in turn: it sets `being-handled` and runs `claude -p --output-format json`, which gives the session id, with the escalation policy, the incident file and a time limit. At the limit it kills the conversation's process group, as the weekly work-snapshot owner check does (lines 157 to 169). A timeout, a nonzero exit or a missing verdict line sets `user-needed`, with what went wrong in the summary. An incident left `being-handled` by an incident handler that died is taken up again after the time limit.
- **The escalation policy** is a tracked file in `nc-systems/unattended-failure-escalation/`, approved by the user word for word in build-slice 2: what the agent may fix itself, what it must bring to the user, how it writes its summary, and the verdict line it must end with. The incident handler hands it to each conversation. Each conversation runs in a working directory under `~/.local/state/nedschorus/unattended-failure-escalation/`, outside `~/agents`, so that `scripts/recover-crashed-seats.py`, which counts every `~/agents/<name>` that has a Claude project directory as an agent-seat (`list_agent_seat_names_with_agent_session_records`), never takes it for one. A code fix is made in a worktree the agent cuts from the main checkout, as any agent does.
- **The window.** For `user-needed`, the incident handler opens a window on the Mac with `scripts/open-mac-window-from-ned-box.py`, running a small script on ned-box that prints the summary and the command to reopen this window from a Terminal on the Mac, `ssh -t nedlern@ned-box '<that script> <incident>'`, and then runs `claude --resume <session id>` in the working directory; the script waits for Enter if `claude --resume` fails. When the opener exits nonzero, the incident keeps a mark and the next run tries again, as the crash restart watcher does for its notices. While the incident stays `user-needed`, the window opens again once a day. The state leaves `user-needed` only when the resumed conversation, with the user, writes a new verdict.
- **The Claude health check** is one program that owns its state file under a lock; an hourly scheduled job on ned-box and the incident handler both call it, and while any incident is `waiting-for-claude` the incident handler calls it every minute. It runs one short `claude -p` request on the model the escalation agent uses. A failure opens a notice window once per outage, showing Claude's own output; an outage counts as announced only once its window has opened. A pass after a failure clears the outage.
- **The ned-box reachability check**, a scheduled job on the Mac every five minutes, runs `ssh` to ned-box with a short time limit. After three failures in a row it opens a notice window on the Mac with `scripts/open-iterm-window-running-command`, once per outage, recorded in a state file on the Mac, and a second window when ned-box answers again.

## Where it is written down

- The scheduled-jobs file's header and the installer's docstring say that a wrapped job's failure goes to the escalation agent, and that a nonzero exit must mean a failure.
- A program outside the scheduled jobs that runs with no agent watching reports a failure by the same route; CLAUDE.md's rule on reporting a failure gets one sentence saying so.
- Each job in the scheduled-jobs table gets an `owner` field naming the agent-seat that owns it, for the tasks the escalation agent files.

## Build-slices

1. The four programs that exit nonzero when nothing failed are changed as above, with tests that cause each case.
2. First, a test by hand: start `claude -p` from cron with session persistence and resume that conversation in a window on the Mac. If either step fails, stop and bring the result to the user. Then the incident file, the wrapper's reporting, the incident handler, the Claude health check and the escalation policy, on ned-box, with tests using a fake `claude` and a fake `scripts/open-mac-window-from-ned-box.py`, including a repeat that arrives while a run is `being-handled` and a repeat during `fix-pending`.
3. The installer change on ned-box only, the `owner` field, and a trial with a real failing job: a trial job installed from the branch with `--job`, removed with `--remove --job` after one verdict.
4. The hourly Claude health check job, and the ned-box reachability check on the Mac.
5. The Mac's own incidents, if open question 4 is approved.
6. The crash restart watcher's change, if open question 3 is approved.

Each build-slice is one pull request with its tests.

## Open questions

1. **Names and new system-terms.** A name check on 2026-10-13 against `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md` judged "escalation" alone too vague and proposed the system name `unattended-failure-escalation`. This document names the pieces "escalation agent", "escalation policy", "incident handler", "incident file" and "wrapper", which would be system-terms of `unattended-failure-escalation`, in a new system glossary. Recommend the system name, and that the user approves each term, after a name check of each program's file name, before any code or instruction file uses them. "Incident handler" replaces "drainer", which collides with the project's queue-drain.
2. **What the agent may fix without asking.** Recommend starting as narrow as the table says and widening it as incidents show what is safe.
3. **The crash restart watcher's notices.** Three of its six notices ask the user to ask an agent to investigate. Recommend the watcher writes an incident for those three when Claude works, so an agent looks first, and keeps its notice window for when Claude does not.
4. **The Mac's own failures.** An agent on ned-box cannot run commands on the Mac: ned-box's key to the Mac only opens windows. Recommend the Mac runs the same incident handler for its own jobs, with its own incident directory, and runs no agent while the reachability check records ned-box down, because the Mac's transcript mirror then fails every minute for that reason alone.
5. **A red nightly test run.** The daily full test run exits nonzero when tests fail, and the nightly test report, linked above, reports test failures to the user by its decided route. Recommend the daily full test run exits 0 once its record is written, whatever the tests' verdict, so test failures go by the nightly test report's route and only a failure of the run itself is an incident.

## Verified, and not verified

- Verified on ned-box on 2026-10-13: a `claude -p` conversation can be continued with `claude -p --resume <session id>` and remembers the text it was first given.
- Not verified: that an interactive `claude --resume <session id>` opens that same conversation in a window, and that `claude -p` started from cron keeps its session; build-slice 2 checks both first. The weekly work-snapshot owner check runs `claude -p` from cron, but with `--no-session-persistence`, and its first run is still to come.
- Not verified: Claude Code's exact messages for a lapsed login and for a usage limit; the health check shows Claude's own output, so it does not depend on them.
