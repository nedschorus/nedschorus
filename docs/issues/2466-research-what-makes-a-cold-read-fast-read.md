# Research what makes a cold-read-fast-read slow, and which reader instructions earn their findings

A cold-read-fast-read, `nc-systems/cold-read/cold-read-fast-read.py`, took a median of 196 seconds when this GHI was filed, and approval-walks wait on it between items. The user asked how to cut that time, and how to tell which of the reader's instructions produce findings worth keeping. The research is done, and the user ruled on its results in an approval-walk that closed on 2026-11-06: the fast read is to run two readers in parallel, Sonnet and Gemini Flash as a custom agent, and four smaller changes go with it. Those rulings, and the builds and the recount still to come, are under "Rulings" below. One part is not yet decided: readers naming the instruction behind each finding, sketched under "Readers naming the instruction behind each finding". ## The questions, and what answered each

The research asked five questions. Its report, by cold-read-research and measured on ned-box, is `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/cold-read-research/ghi-2466-fast-read-speed-research-2026-11-02/report.md`, with its data in `data/` beside it.

1. **Where the time goes.** Answered by the research, not ruled on. In four timed reads of a one-sentence target the median read took 154 seconds. Start-up is about 8 seconds of it, so the roughly 2 minutes of fixed cost is not start-up. About 100 seconds is the Gemini reader's agent loop under agy: 15 to 33 model requests, most of them driving tool calls the prompt does not ask for, such as `git log` or reading `cold-read-fast-read.py`. A further 16 to 79 seconds is the cell on Opus that answers the report's Question 4, "What should be code", which `cold-read-fast-read.py` runs after the main reader, not beside it.
2. **Ready readers.** Answered by the research, not ruled on. A pool of readers started early would save at most the 8 seconds of start-up. One reader reused or cleared between reads keeps the earlier read in its conversation or session store, so it is not fresh. Neither is worth building. The research found a larger freshness fault instead: 111 of 290 production fast reads (38%) had opened another read's report under `cold-read-records/`. Item 1 below is the user's ruling on it.
3. **Reader models.** Ruled on in items 2, 2.2 and 12 below: a five-run bake-off was run against a corrected answer key, and the user chose two readers in parallel.
4. **Which instructions earn their findings.** Not ruled on. The research wrote a design sketch, under "Readers naming the instruction behind each finding" below. It still waits for an approval-walk item.
5. **How to call a fresh reader.** Settled for the fast read by item 12: Sonnet through the existing claude cell, and Gemini Flash through agy as a custom agent. The `GEMINI_API_KEY` on ned-box is on Google's paid tier and bills by the token: its errors name a paid-tier quota, and it hit a monthly spending cap on 2026-10-25. Fast reads do not use it; they sign in to the user's Gemini Ultra subscription. A cloud agent was not measured. The research also proposed calling Gemini directly through its REST API on a new key from a project with no billing; no ruling was made on that.

The answer key of item 17.3.3.1 of fleet-restart-at-login's approval-walk ghi-972-agent-seat-database-service-design-mac-task-lists-fallback-decision-and-cold-read-findings-approval-walk-2026-10-29 (walk-document `/home/nedlern/agents/fleet-restart-at-login/docs/walk/ghi-972-agent-seat-database-service-design-mac-task-lists-fallback-decision-and-cold-read-findings-approval-walk-2026-10-29.md` on ned-box), which this GHI-MD once offered as the test for questions 3 and 5, was not used. ## Readers naming the instruction behind each finding

This is the research's design sketch for question 4, from its report's section "Question 4: readers naming the instruction behind each finding (design sketch only)". The user has not ruled on it.

At launch, code puts an id on each instruction sentence of the fast-clarify prompt, `[i1]` to `[iN]`, as the function `sentence_id_markup` in `nc-systems/cold-read/cold-read-fast-read.py` already does for the target's sentences, so the prompt text the user ruled on is not edited. The prompt gains one sentence: end each finding with the id of the instruction that made you raise it, such as `[i3]`. Code checks that each finding carries one id, and that the id exists. The agent's triage already records each finding's fate in the `cold-read-triage.md` of each cold-read-record, kept in the log-store under `nedlern@ned-box:/home/nedlern/nedschorus-logs/cold-read-records/`, in lines such as "- Q2.1 (…): applied" and "- Q2.2 (…): declined"; the log-store held 503 such files when the research counted. A script joins the two by finding number and tallies kept against dropped findings for each instruction id. After a month it lists the instructions that produced no kept finding.

Three limits. With item 12's two readers in parallel, a finding number such as Q2.1 no longer names one finding, so the join needs the reader's name as well. A read of a walk draft has no triage file, so the walk-me-through skill would need to record one line per finding there too. And instructions that stop false alarms, such as "a subject it never takes up is not a gap", raise no findings, so they can be judged only by removing one and counting false findings over the same documents. The judgment steps are the reader's tagging and the agent's triage; everything else is code.
