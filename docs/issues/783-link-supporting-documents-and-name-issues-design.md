# How the ghi-write-tool names an issue and links its GHI-MD and supporting files

This design says how the ghi-write-tool, `scripts/ghi-issue-write.py`, tells an issue's one GHI-MD from the issue's supporting documents, how the issue is titled and its GHI-MD's file name chosen, and how the issue's body links both. It replaced this issue's earlier GHI-MD, which stated the problem only; PR [GHI-MD edit for issue 783: How the ghi-write-tool names an issue and links its GHI-MD and supporting files](https://github.com/nedschorus/nedschorus/pull/887) landed this design and removed that file, whose last text is `git show 5620543b:docs/issues/783-an-issue-has-one-ghi-md-and-many.md`.

§ The user-rulings lists what the user has decided. The mechanics that carry those decisions out are this design's own; the user reviewed the choices among them in the approval-walks that § The user-rulings lists, and § Open questions lists what is still his to decide.

The problem, in one paragraph. The tool treats every file named `<number>-*` directly in `docs/issues/`, or directly in a system's directory under `nc-systems/`, as the issue's GHI-MD; only a design whose code has landed, in a system's `docs/` directory, is found by its `issue:` line instead. So the tool cannot tell an issue's GHI-MD from the issue's supporting documents, never links a supporting document stored anywhere else, and can link a file shared by several issues from one of those issues at most. The tool also cuts the words of an issue's file name from the first eight words of the file's first heading, which the user called a bad name.

## What the tool does today

Measured on origin/main, 2026-10-01.

- **Which files belong to an issue.** `ghi_md_paths_for_issue` lists the files on main whose file name begins `<number>-` and which sit directly in `docs/issues/` or directly in `nc-systems/<system>/`, and, since the commits [The ghi-write tool finds a landed design in its system's docs/, filed by its issue: line](https://github.com/nedschorus/nedschorus/commit/c0582dc3) and [ghi-write tool fix round 1: an edit adding a landed design's issue: line counts the design, and create sees a moved design](https://github.com/nedschorus/nedschorus/commit/fcefed36) (made at the MD-skills agent-seat, approval-walk ghi-224-migration-order-and-open-questions-2026-09-30, item 3), a landed design: a file under `nc-systems/` in a `docs/` directory, named `*-design.md` with no number, whose front matter `issue:` line links the issue (`landed_design_relative_path`, `issue_number_in_frontmatter`). `writable_relative_path` accepts the same three places. Any other file is never found, and a file serves one issue at most.
- **The body.** `links_body` writes one link per file found, sorted by full path, each labelled with the file's base name, and nothing else.
- **The file name.** create-GHI lands the file as `docs/issues/<number>-<slug>.md`, where `slug`, today's code's word for what this design calls the name, is the first heading's first eight words (`SLUG_WORD_LIMIT = 8`).
- **The title.** create-GHI files the issue under the file's first heading, its first line opening with `#`. edit-GHI retitles the issue from the first heading only when the edit changed that heading and the issue has at most one filed GHI-MD (`title_follows_heading_in_this_edit`). A first heading about to become a title is refused when it carries a date or a file path.
- **The `issue:` line.** create-GHI and edit-GHI write an `issue:` line into the front matter of the file they land, citing the issue by its title as a link. Some closed issues' files carry no `issue:` line, such as `docs/issues/8-adversarial-package-review.md`.
- **Designs moved out.** Four designs sit directly in a system's directory with no number and no `issue:` line: `nc-systems/cold-read/cold-read-design.md`, `nc-systems/cold-read/cold-read-grid-cell-failure-handling-design.md`, `nc-systems/handoff/handoff-design.md` and `nc-systems/main-gatekeeper/main-gatekeeper-design.md`. The tool finds none of them for any issue. No design sits yet in a `docs/` directory.
- **A move that renames.** edit-GHI finds the path a moved file came from by the file's base name. A file moved and renamed is not matched: the tool lands it as a new file, leaves main's old copy, and tells the author to land the removal.

## The design

Every refusal this design adds is a hard-block, exit 64.

### One GHI-MD per issue, found by its `issue:` line

The tool takes as an issue's GHI-MD the file on main whose front matter `issue:` line links that issue, in a place a GHI-MD may sit (§ Where a GHI-MD may sit). This generalises what the tool already does for a landed design, `issue_number_in_frontmatter`, to every place. create-GHI and edit-GHI write the line, as they do today. The tool reads the issue number from the link's URL, and only from a URL of the repository the tool runs against, `https://github.com/<repository>/issues/<number>`, where `<repository>` is the tool's `--repo` value, `nedschorus/nedschorus` by default; a line linking anywhere else counts as no `issue:` line, and the tool reports it.

- **None found.** The tool reports that the issue has no GHI-MD on main and leaves the title alone. The body is handled in § What the body links.
- **More than one found.** The tool reports every path, links each one first in path order, and leaves the title alone. Nothing is guessed.
- **An `issue:` line outside the places a GHI-MD may sit**, such as a copy under `docs/drafts/`. The file is not taken as the GHI-MD; the tool reports the path.

When a file given to edit-GHI carries a number at the start of its file name and an `issue:` line linking a different issue, the operation stops with a hard-block, exit 64, naming both numbers and telling the author to correct the wrong one. When the search of main meets such a file, the tool uses the `issue:` line, reports the mismatch, and carries on.

edit-GHI takes the issue number from the given file's `issue:` line only. A file with no `issue:` line is refused, exit 64, with instructions: a supporting document lands in an ordinary pull request, and the next hourly rebuild updates the bodies; a file meant to take the place of an issue's GHI-MD does so through an edit of the GHI-MD. So edit-GHI never turns a supporting document into a second GHI-MD.

create-GHI refuses, exit 64, a file that carries an `issue:` line or an `issue-marker:` line: such a file is a filed GHI-MD, or a copy of one, and edit-GHI is the operation for it. Two cases are not refused. In the first, as today, the issue the `issue:` line links is still being filed, its body still create-GHI's placeholder, and the run resumes. The second is new: the file given is that issue's GHI-MD as main holds it and the issue's body is already its links, and the run reports that the filing is finished and exits 0 (§ Rebuilding every hour); a copy elsewhere is refused. The refusal text that tells an author to file material as a new issue by copying it under a name with no number gains the instruction to remove the `issue-marker:` line from the copy as well as the `issue:` line.

### The issue marker

Each issue has one issue marker, `ghi-<number>-<16 random hexadecimal characters>`, apart from the state, which the tool reports, in which main holds several GHI-MDs for the issue. The number shows a reader which issue the issue marker identifies; the random part makes a match by accident practically impossible, so a search for the issue marker matches the files given it, copies of those files, and any file that quotes the whole issue marker. Documentation, this design included, shows the issue marker with its random part elided, `ghi-783-…`, and never a whole issue marker, so no document is taken for a supporting document of an issue it only describes; a test builds the whole issue marker strings it needs at run time, so none sits in a file on main. A document that cites by path a file whose file name carries the issue marker quotes the whole issue marker and is linked too; such a file is cited from the GHI-MD.

- **Where it is kept.** The GHI-MD's front matter carries it on an `issue-marker:` line beside the `issue:` line. A GHI-MD keeps its issue marker when it moves or is renamed.
- **A GHI-MD without its issue marker.** Whenever edit-GHI runs on a GHI-MD that has no `issue-marker:` line, such as a new file taking the place of a deleted GHI-MD, edit-GHI writes the line and the issue's body links the file. The issue marker it writes is the issue's existing issue marker, the one § Which issue marker is the issue's gives, read from main's history when the issue has no GHI-MD on main, so an issue keeps one issue marker for life and every file already carrying it stays linked; only an issue that has no issue marker gets a fresh one.
- **How create-GHI makes it, and how a rerun finds it again.** create-GHI makes the random part before it files the issue and writes that part into the issue's placeholder body, beside the ghi-md-pairing-key. Once GitHub returns the issue's number the issue marker is whole, and create-GHI writes the `issue:` and `issue-marker:` lines into the file it lands. A rerun of an interrupted filing finds its issue by the ghi-md-pairing-key, as today, and takes the random part from that issue's placeholder body, so it lands the file the first run would have landed. A filing in flight when the build merges has no random part in its placeholder; its rerun makes one and writes it into the placeholder first. Once the filing has finished and the body is links, the random part is no longer in the body. A rerun then compares each GHI-MD on main with what its source would become if create-GHI landed it under that GHI-MD's number with that GHI-MD's issue marker, both front matter lines added as create-GHI adds them (`refuse_if_already_landed_on_main`).
- **Which issue marker is the issue's.** The one on its GHI-MD's `issue-marker:` line. While main holds several GHI-MDs for the issue, a state the tool reports (§ One GHI-MD per issue), each one's issue marker counts when the tool links files, and `mark-supporting-document` refuses the issue (§ Supporting documents). When the issue has no GHI-MD on main, its issue markers are read from main's history, so a deleted GHI-MD's supporting documents stay linked: every issue marker on an `issue-marker:` line of a file whose front matter `issue:` line linked the issue, in any commit on main, counts, so the result does not depend on whether files were removed, or their `issue:` lines removed or changed, in one commit or several. A file that carried no `issue-marker:` line, such as one removed before the build, gives none. An issue that never had a GHI-MD with an `issue-marker:` line has no issue marker. A string of the issue marker's pattern whose random part differs from each of the issue's issue markers, or whose issue has no issue marker, is not the issue's issue marker: the tool reports each file carrying it and does not link the file.
- **Data, not a citation.** The issue marker is read by the tool. CLAUDE.md's rule against citing an issue by a bare number or GUID does not reach it; a writer who means to cite an issue links it by title, and never writes its issue marker in prose.

### Supporting documents and how they carry the issue marker

A supporting document is any file on main, a picture or a data file included, other than the issue's GHI-MD, that carries the issue's issue marker in its text content or in its file name. A file can carry several issues' issue markers, and an issue can have many supporting documents.

- **A Markdown file** carries the issue markers on a front matter line, in a front matter block `mark-supporting-document` creates when the file has none, `supports-issues: ghi-783-…, ghi-790-…`. A GHI-MD can carry a `supports-issues:` line carrying other issues' issue markers, and is then a supporting document of those issues; a GHI-MD whose `supports-issues:` line carries its own issue's issue marker is linked once, as the GHI-MD.
- **Another text file** carries the issue marker anywhere in its text content. `mark-supporting-document` writes it as a comment line, `supports-issues: ghi-783-…`, at the top of the file, after a shebang line (`#!`), a Python encoding declaration and an XML declaration when the file has them, in the comment syntax of the file's type: `#` for Python, shell, YAML and TOML, `//` for JavaScript and TypeScript, `<!-- -->` for HTML and XML. One comment line holds every issue marker the file carries, separated by commas, as the front matter line does. The type is read from the file's extension, or from its shebang line when it has no extension.
- **Any file, a binary one included,** can carry the issue marker in its file name, such as `ghi-783-…-answer-times.png`. The author puts it there when choosing the file name.
- **An image's embedded metadata** may carry the issue marker for a reader. The search does not rely on it: the search reads the text content only of the files git treats as text, passing `-I` to `git grep`, which otherwise reports a binary file whose bytes match; and many image tools compress or strip metadata when they save. A file git treats as binary is found by its file name alone.
- **A file that can carry the issue marker in neither place**, such as a JSON file whose format another program fixes and whose file name the author does not choose, is not linked; the GHI-MD cites it in its text.

A copy of a file carries the issue marker and is linked too. A copy of a GHI-MD outside the places a GHI-MD may sit, such as one under `docs/drafts/`, is therefore linked as a supporting document of its issue, though it is not taken as the GHI-MD. A file in `docs/issues/queue/` or `docs/issues/archived/` is linked when it carries the issue marker, and not otherwise.

The tool writes the issue marker. `mark-supporting-document <path> <number>…` looks up each issue's issue marker on its GHI-MD's `issue-marker:` line on main, or, while the issue is still being filed and its GHI-MD is on create-GHI's pull request, in the issue's placeholder body, and writes it into the file at `<path>` in the author's checkout, in the form for the file's type; `mark-supporting-document --remove <path> <number>…` takes out the given issues' issue markers from the line the operation writes, the line when none is left, and the front matter block when nothing is left in it; at least one number is required either way. When any number given is refused, the operation refuses the whole request and changes nothing. The operation:
- refuses a closed issue's number, saying: "GHI <number> is closed, and a closed issue's description is never rebuilt, so the file would never be linked.";
- refuses a number whose issue has no issue marker on main or in a placeholder body, telling the author, when the issue's GHI-MD was deleted, to give the issue a GHI-MD through edit-GHI first, which writes the issue's issue marker into it; a number whose issue has more than one GHI-MD on main, listing every path and telling the author to leave the issue one GHI-MD first; and a number that belongs to a pull request, or to nothing;
- reports an issue marker already present, or already absent, and changes nothing for it; an issue marker carried in the file's name, or elsewhere in its text content, it reports and leaves, for the author to remove by hand;
- refuses, exit 64, a binary file, telling the author to carry the issue marker in the file's name; a text file whose comment syntax the operation does not know, such as JSON, with the same instruction or the GHI-MD's text as the alternative; a Markdown file whose front matter opens with `---` and never closes; a `supports-issues:` line whose value, inside its comment syntax, is anything other than issue markers separated by commas, and a file with two such lines; and a file of agent-instructions: a `SKILL.md`, `CLAUDE.md`, `CLAUDE.local.md`, `AGENTS.md`, an `-instructions.md` or `-prompt.md` file, and any file `.claude/hooks/instruction-file-guard.py` guards. The GHI-MD cites such a file in its text instead.

The operation renames nothing and lands nothing: the author commits the changed file with the rest of the work, because a new supporting document usually lands in the author's own pull request. Which issues a file supports is the author's call.

### Names and titles

- **The author gives the name.** The author writes the GHI-MD as `<name>.md`, and create-GHI lands it as `docs/issues/<number>-<name>.md`. The tool no longer cuts a name from the first heading, and `SLUG_WORD_LIMIT` is deleted.
- **A GHI-MD with no number.** A GHI-MD that moves beside its code is named `<name>.md` there: the move drops the number and keeps the name, so the name of a GHI-MD with no number is its file name without `.md`, and the issue's title does not change.
- **The checks.** create-GHI refuses, with a hard-block, exit 64, a name that:
  - is not 3 to 9 words;
  - is not lowercase letters and digits joined by single hyphens;
  - has a first word made only of digits, such as `2026-summary-of-reviews`, which the tool would read as an issue number; `3d-graphics-export` passes;
  - carries a date in the form the check PR [GHI titles name the work](https://github.com/nedschorus/nedschorus/pull/829) built for the first heading recognizes, which moves to the name; a file path cannot pass the character check;
  - is already the name of another GHI-MD on main, or the title of another issue, open or closed.
  The refusal says which check failed and how to fix the name. edit-GHI runs the same checks when the GHI-MD's name differs from its name on main, and none when the name is unchanged. Two filings that both pass the checks before either creates its issue, and choose the same name, are not caught.
- **What a program cannot check.** That the name names the work in full words, without abbreviations, status, ruling, provenance, or a date in a form the check does not recognize, is the author's to meet; the /ghi-write skill is to say so (§ What the build changes outside the tool). A name changes only when the user asks for it; the skill is to say that too, because nothing in a file records whether the user asked.
- **The title is the name, set on main.** The title is the name as written, hyphens included: this issue's title becomes `link-supporting-documents-and-name-issues-design`. create-GHI files the issue under the name. After that, only `relink-and-retitle-issues` sets the title, from the name of the GHI-MD on main, when the two differ. edit-GHI does not set the title, so an edit whose pull request is closed unmerged leaves the title as it was. The `issue:` line cites the issue under its title. edit-GHI writes the GHI-MD's name as the text of the `issue:` line, so the pull request that renames a GHI-MD also brings its `issue:` line to the name, which is the title once the rebuild has run; the tool reads only the line's URL, so a line whose text lags breaks nothing.
- **A title is a name.** A title, like a file name, is a name, so CLAUDE.md's rule that a hyphenated phrase in prose marks a project-term does not reach it.
- **The first heading is free text.** It no longer sets the title, so `heading_changed_in_this_edit`, `title_follows_heading_in_this_edit`, `issue_title_after_this_edit` and `sync_title_on_heading_change` are deleted, and `refuse_heading_with_date_or_file_path` becomes the name's date check. `validate` and `validate_edit` still require a first heading, because a GHI-MD opens with one; their refusal says so instead of calling the heading the title. `refuse_if_filing_is_in_flight` compares the name of the file given to create-GHI, not the file's first heading, with the titles of issues still being filed.

### What the body links

The body of a link-only-GHI is, in order:

1. the link to the GHI-MD, found as above;
2. one link per supporting document, every file on main other than the GHI-MD that carries the issue's issue marker in its text content or its file name, sorted by path.

Each link's text is the file's path in the repository, with Markdown's brackets escaped, so two files with the same base name in different directories are told apart, and each link's address percent-encodes every segment of the path, keeping the slashes between segments and encoding `(` and `)` too, so a path holding `#`, `)` or a space still opens its file. Nothing else is in the body, and nothing is kept by hand: the list is computed from main at every write. Not linked: a file only on an unmerged branch, whose link would not open, and a file in the log-store on ned-box, which GitHub cannot link; the GHI-MD cites either kind in its text.

The tool finds both kinds of file from origin/main with two reads: `git grep -I` for `issue:` lines and for strings of the issue marker's pattern, `ghi-`, a number, `-` and 16 hexadecimal characters, in the text content of the files git treats as text, and `git ls-tree -r -z --name-only`, whose paths arrive unquoted, for the same pattern in each path's last segment, its file name. Of the strings found, the tool links each file by the issue marker it carries; a string that carries an issue's number but whose random part matches none of that issue's issue markers is reported (§ The issue marker). Another issue's issue marker is not a fault and is not reported. An `issue:` line counts only in a file's front matter block, so the tool reads the front matter of each file `git grep` finds with such a line and drops a match outside the block. The issue marker counts anywhere in a text file, Markdown included, as the user ruled; a document that only describes an issue does not carry it, because documentation shows the issue marker with its random part elided (§ The issue marker). For an issue with no GHI-MD on main, a third read, of main's history, finds the issue marker (§ The issue marker).

The tool writes the body only over a body it wrote, its list of links or create-GHI's placeholder, as `relink_body_from_main` does today, and leaves a prose body as it stands. When no GHI-MD is on main:
- a placeholder body stays, because the filing has not finished and its GHI-MD is still on a pull request;
- a list of links, when the issue has at least one supporting document, is rebuilt from the supporting documents alone, so a dead link to a deleted GHI-MD drops out, and the tool reports that the issue has no GHI-MD;
- when there is no supporting document either, the body is left as it stands and the tool reports it, so no body is written empty.

### Rebuilding every hour

A new operation, `relink-and-retitle-issues`, rebuilds the body and sets the title of each open issue it is given. It skips a closed issue, changing neither the body nor the title, as the user ruled (§ Closing an issue), and reports a closed issue given on the command line. Every form fetches origin/main first. It has two forms:
- `relink-and-retitle-issues <number>…` for the issues given;
- `relink-and-retitle-issues --all-open` for every open issue; a run that stops partway, for example on GitHub's rate limit, is run again whole.

Each run is idempotent: an issue whose body and title already match is left untouched. The title is set whether the body is links or prose, and only to a name that passes the checks edit-GHI runs on a changed name (§ Names and titles); a GHI-MD renamed by an ordinary pull request, such as a `git mv` in a repository-layout migration, to a name that fails them leaves the title as it was, and the run reports the issue. A GHI-MD on main with no `issue-marker:` line, or with one that does not hold one issue marker of its own issue, leaves its issue as it stands, body and title, so no link is dropped, and the run reports the issue; the next edit-GHI run on that GHI-MD writes the line back (§ The issue marker). A number that belongs to no issue of this repository is reported and skipped. The run carries on with the rest after each report, and exits 1 at the end when it reported anything, so a failure reaches whoever reads its output. A state that persists, such as an issue with two GHI-MDs, is reported at every hourly run until someone fixes it.

A scheduled job runs `relink-and-retitle-issues --all-open` every hour, on ned-box only, so two machines never edit one issue at once: one row, `hourly-relink-and-retitle-issues`, in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, writing its output to a log. Every merge is covered within the hour, whoever made it and however, and nothing needs to be told that a merge happened. merge-lane-2 reads that log at the start of each session and brings each reported failure to the user.

Before the build starts, the agent that builds this design confirms, with `ssh nedlern@ned-box gh auth status`, that the `gh` login on ned-box, under which the scheduled job runs, can edit issue titles and bodies; if that login cannot, the build stops and asks the user.

create-GHI, rerun by an author on a GHI-MD on main whose issue body the rebuild has already turned into links, reports that the filing is finished and exits 0, instead of refusing the file as already filed. The /ghi-write skill's rerun after a merge becomes the fallback for the body when the hourly run has not yet come; a title waits for the next `relink-and-retitle-issues` run.

### Closing an issue

A closed issue is frozen: no program changes its body or its title, apart from pinning its links once. Before an issue is closed, each link in its body to main, `https://github.com/nedschorus/nedschorus/blob/main/<path>` or `https://github.com/nedschorus/nedschorus/tree/main/<path>`, is rewritten to the same path at one commit, the commit at closing, `https://github.com/nedschorus/nedschorus/blob/<commit>/<path>` or `…/tree/<commit>/<path>`, with any line anchor kept; GitHub calls such a link a permalink. This is done whether the body is a list of links or prose; only the links' addresses change, so a prose body keeps its text. A pinned link to a file that the commit at closing holds keeps opening after the file moves, is renamed or is deleted, and shows the file as it stood when the issue closed; a link already dead at that commit stays dead.

After that, nothing rebuilds the issue. `relink-and-retitle-issues` skips it however it is invoked, and a rerun of edit-GHI or create-GHI leaves its body and title alone. So its links and its title stay as they were at closing, even when its GHI-MD is later edited, moved or renamed, and a file marked later with the issue's issue marker is not linked from it. § Open questions asks which program pins the links, which commit is the commit at closing, and what a reopened issue gets.

### Moves, renames and deletions

- **A GHI-MD moves or is renamed.** Its `issue:` and `issue-marker:` lines move with it, so the tool finds the file at its new path. edit-GHI, given a file whose `issue:` line links an issue whose GHI-MD main holds at a different path, looks at that other path in the author's checkout:
  - the file is gone from the checkout: the author moved or renamed the GHI-MD, and edit-GHI removes main's old copy in the same commit, after today's conflict check on the moved-from path (`refuse_on_conflict`, exit 66), which refuses when main changed that path since the author's checkout started from it;
  - the file is still in the checkout: two files carry the line, and edit-GHI refuses, exit 64, telling the author to remove the `issue:` and `issue-marker:` lines from the copy, or to delete the original if the GHI-MD is moving.
  When main holds more than one file with that issue's `issue:` line, edit-GHI removes nothing and refuses, exit 64, listing every path.
- **A supporting document moves, is renamed or is deleted.** The next hourly rebuild rebuilds the body of every open issue whose issue marker the file carried. An issue marker in the file's text content moves with it; a file that carried the issue marker in its file name keeps it only if the new file name keeps it, which the author sees to. A deleted file drops out of the body, except the last link of an issue with no GHI-MD, which stays and is reported (§ What the body links).
- **A GHI-MD is deleted.** The rebuild follows § What the body links: the body keeps the supporting documents' links, and the tool reports that the issue has no GHI-MD. The title stays.

### Where a GHI-MD may sit

A GHI-MD sits directly in `docs/issues/` from filing until its code lands, and then where the file naming page puts a design whose code has landed: the `docs/` directory of the directory its code is in, at any depth under `nc-systems/`. The tool accepts a GHI-MD there only when it is a design, named `*-design.md` with no number (`landed_design_relative_path`), because the file naming page moves only designs beside their code; a GHI-MD there that is not a design is refused, exit 64, telling the author that the file belongs in `docs/issues/`. `writable_relative_path` still accepts `nc-systems/<system>/` directly, where the four designs moved out so far sit, so main-gatekeeper's design, `nc-systems/main-gatekeeper/main-gatekeeper-design.md`, is found there by its `issue:` line until the migration of GHI [Rationalize the repository layout: group components by owning system under nc-systems/, and a hook dispatcher](https://github.com/nedschorus/nedschorus/issues/224) moves it. That design has no `issue:` line today; the pull request that lands the user's review of it, branch `main-gatekeeper-specification-becomes-ghi-3-ghi-md`, writes the line. A move keeps both front matter lines, and so the file stays the issue's GHI-MD.

A landed design is revised only to fix a flaw found in it, and only after human review (the file naming page, as changed by PR [A landed design is revised only to fix a flaw, after human review](https://github.com/nedschorus/nedschorus/pull/860)). The tool does not enforce that; the /ghi-write skill is to say it for edit-GHI on a landed design (§ What the build changes outside the tool).
