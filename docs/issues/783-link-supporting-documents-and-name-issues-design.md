# How the ghi-write-tool names an issue and links its GHI-MD and supporting files

This design says how the ghi-write-tool, `scripts/ghi-issue-write.py`, tells a GHI's one GHI-MD from the GHI's supporting documents, how the GHI is titled and its GHI-MD's file name chosen, and how the GHI's body links both. It replaced this GHI's earlier GHI-MD, which stated the problem only; PR [GHI-MD edit for issue 783: How the ghi-write-tool names an issue and links its GHI-MD and supporting files](https://github.com/nedschorus/nedschorus/pull/887) landed this design and removed that file, whose last text is `git show 5620543b:docs/issues/783-an-issue-has-one-ghi-md-and-many.md`.

§ The user-rulings lists what the user has decided. The mechanics that carry those decisions out are this design's own; the user reviewed the choices among them in the approval-walks that § The user-rulings lists.

The problem, in one paragraph. The tool treats every file named `<number>-*` directly in `docs/issues/`, or directly in a system's directory under `nc-systems/`, as the GHI's GHI-MD; only a design whose code has landed, in a system's `docs/` directory, is found by its `issue:` line instead. So the tool cannot tell a GHI's GHI-MD from the GHI's supporting documents, never links a supporting document stored anywhere else, and can link a file shared by several GHIs from one of those GHIs at most. The tool also cuts the words of a GHI's file name from the first eight words of the file's first heading, which leaves names cut off mid-thought, the names the one name change for the open GHIs replaces (§ The user-rulings).

## What the tool does today

Measured on origin/main, 2026-10-01.

- **Which files belong to a GHI.** `ghi_md_paths_for_issue` lists the files on main whose file name begins `<number>-` and which sit directly in `docs/issues/` or directly in `nc-systems/<system>/`, and, since the commits [The ghi-write tool finds a landed design in its system's docs/, filed by its issue: line](https://github.com/nedschorus/nedschorus/commit/c0582dc3) and [ghi-write tool fix round 1: an edit adding a landed design's issue: line counts the design, and create sees a moved design](https://github.com/nedschorus/nedschorus/commit/fcefed36) (made at the MD-skills agent-seat, approval-walk ghi-224-migration-order-and-open-questions-2026-09-30, item 3), a design in its code's `docs/` directory: a file under `nc-systems/` in a `docs/` directory, named `*-design.md` with no number, whose front matter `issue:` line links the GHI (`landed_design_relative_path`, `issue_number_in_frontmatter`). `writable_relative_path` accepts the same three places. Any other file is never found, and a file serves one GHI at most.
- **The body.** `links_body` writes one link per file found, sorted by full path, each with the file's base name as its link text, and nothing else.
- **The file name.** create-GHI lands the file as `docs/issues/<number>-<slug>.md`, where `slug`, today's code's word for what this design calls the name, is the first heading's first eight words (`SLUG_WORD_LIMIT = 8`).
- **The title.** create-GHI files the GHI under the file's first heading, its first line opening with `#`. edit-GHI retitles the GHI from the first heading only when the edit changed that heading and the tool finds at most one file for the GHI (`title_follows_heading_in_this_edit`). A first heading about to become a title is refused when it carries a date or a file path.
- **The `issue:` line.** create-GHI and edit-GHI write an `issue:` line into the front matter of the file they land, citing the GHI by its title as a link. Some closed GHIs' files carry no `issue:` line, such as `docs/issues/8-adversarial-package-review.md`.
- **Designs moved out.** Four designs sit directly in a system's directory with no number and no `issue:` line: `nc-systems/cold-read/cold-read-design.md`, `nc-systems/cold-read/cold-read-grid-cell-failure-handling-design.md`, `nc-systems/handoff/handoff-design.md` and `nc-systems/main-gatekeeper/main-gatekeeper-design.md`. The tool finds none of them for any GHI. No design sits yet in a `docs/` directory.
- **A move that renames.** edit-GHI finds the path a moved file came from by the file's base name. A file moved and renamed is not matched: the tool lands it as a new file, leaves main's old copy, and tells the author to land the removal.

## The design

Every refusal this design adds is a hard-block, exit 64.

### One GHI-MD per GHI, found by its `issue:` line

The tool takes as a GHI's GHI-MD the file on main whose front matter `issue:` line links that GHI, in a place a GHI-MD may sit (§ Where a GHI-MD may sit). This generalises what the tool already does for a design in its code's `docs/` directory, `issue_number_in_frontmatter`, to every place. create-GHI and edit-GHI write the line, as they do today. The tool reads the GHI number from the link's URL, and only from a URL of the repository the tool runs against, `https://github.com/<repository>/issues/<number>`, where `<repository>` is the tool's `--repo` value, `nedschorus/nedschorus` by default; a line linking anywhere else counts as no `issue:` line, and the tool reports it.

- **None found.** The tool leaves the title alone. The body is handled in § What the body links, which says when the state is reported.
- **More than one found.** The tool reports every path, links each one first in path order, and leaves the title alone. Nothing is guessed. A file whose `issue:` line sits outside the places a GHI-MD may sit, as in the next case, is not counted.
- **An `issue:` line outside the places a GHI-MD may sit**, such as a copy under `docs/drafts/`. The file is not taken as the GHI-MD; the tool reports the path.

When a file given to edit-GHI carries a number at the start of its file name and an `issue:` line linking a different GHI, the operation stops with a hard-block, exit 64, naming both numbers and telling the author to correct the wrong one. When the search of main meets such a file, the tool uses the `issue:` line, reports the mismatch, and carries on.

edit-GHI takes the GHI number from the given file's `issue:` line, with one exception. A file with no `issue:` line, named `<number>-<name>.md` directly in `docs/issues/`, whose GHI is open and has no GHI-MD on main, is taken as the GHI's new GHI-MD: edit-GHI writes its `issue:` line and its `issue-marker:` line (§ The issue marker) and runs the name checks on its name as on a changed name. Any other file with no `issue:` line is refused, exit 64, with instructions: a supporting document lands in an ordinary pull request, and the next rebuild updates the bodies; a file meant to take the place of a GHI-MD still on main does so through an edit of that GHI-MD. So edit-GHI never turns a supporting document into a second GHI-MD.

create-GHI refuses, exit 64, a file that carries an `issue:` line or an `issue-marker:` line: such a file is a filed GHI-MD, or a copy of one, and edit-GHI is the operation for it. Two cases are not refused. In the first, as today, the GHI the file's number names is still being filed, its body still create-GHI's placeholder, and the run resumes. The second is new: the file given is that GHI's GHI-MD as main holds it and the GHI's body is already its links, and the run prints that the filing is finished and exits 0 (§ Rebuilding when main moves); a copy elsewhere is refused. The refusal text that tells an author to file material as a new GHI by copying it under a name with no number gains the instruction to remove the `issue-marker:` line from the copy as well as the `issue:` line.

### The issue marker

A GHI that has had a GHI-MD since the build has one issue marker, `ghi-<number>-<16 random hexadecimal characters>`, for life; a GHI that never had a GHI-MD with an `issue-marker:` line has none. The GHI's one GHI-MD carries it. The number shows a reader which GHI the issue marker identifies; the random part makes a match by accident practically impossible, so a search for the issue marker matches the files given it, copies of those files, and any file that quotes the whole issue marker. Documentation, this design included, shows the issue marker with its random part elided, `ghi-783-…`, so no document is taken for a supporting document of a GHI it only describes; a test builds the whole issue marker strings it needs at run time, so none sits in a file on main. The one exception is a citation of a file whose file name carries the issue marker: the path holds the whole issue marker, so the citing document is linked from the GHI too. Cite such a file from the GHI-MD, or from another document that belongs among the GHI's supporting documents.

- **Where it is kept.** The GHI-MD's front matter carries it on an `issue-marker:` line beside the `issue:` line. A GHI-MD keeps its issue marker when it moves or is renamed.
- **A GHI-MD without its issue marker.** Whenever edit-GHI runs on a GHI-MD that has no `issue-marker:` line, or whose line does not hold its own GHI's issue marker, such as a new file taking the place of a deleted GHI-MD or a GHI-MD copied from another GHI's as a template, edit-GHI writes the GHI's issue marker into the line, and once the pull request merges the GHI's body links the file when the body is the tool's list of links and the GHI is open. The issue marker it writes is the GHI's existing one, as § Which issue marker is the GHI's gives, so every file already carrying it stays linked; only a GHI that has no issue marker gets a fresh one.
- **How create-GHI makes it, and how a rerun finds it again.** create-GHI makes the random part before it files the GHI and writes that part into the GHI's placeholder body, beside the ghi-md-pairing-key. Once GitHub returns the GHI's number the issue marker is whole, and create-GHI writes the `issue:` and `issue-marker:` lines into the file it lands. A rerun of an interrupted filing finds its GHI by the ghi-md-pairing-key, as today, and takes the random part from that GHI's placeholder body, so it lands the file the first run would have landed. A filing in flight when the build merges has no random part in its placeholder; its rerun makes one and writes it into the placeholder first. Once the filing has finished and the body is links, the random part is no longer in the body. A rerun then compares each GHI-MD on main with what the file given to the rerun would become if create-GHI landed that file under that GHI-MD's number with that GHI-MD's issue marker, both front matter lines added as create-GHI adds them (`refuse_if_already_landed_on_main`).
- **Which issue marker is the GHI's.** The one on its GHI-MD's `issue-marker:` line, when the number inside it is the GHI's number and the line holds that one issue marker and nothing else. When no GHI-MD on main has such a line, because the GHI-MD was deleted or its line lost or changed, the issue marker is read from main's history, so the GHI's supporting documents stay linked: the issue marker on a valid `issue-marker:` line, of a file in a place a GHI-MD may sit whose front matter `issue:` line linked the GHI, in any commit on main. The result does not depend on whether files were removed, or their `issue:` lines removed or changed, in one commit or several. The history read needs the whole of main's history: in a shallow clone the tool reports that it cannot read the history and exits 1, rather than taking the GHI for one with no issue marker. A file that carried no `issue-marker:` line, such as one removed before the build, gives none. A string of the issue marker's pattern whose random part differs from the GHI's issue marker, or whose GHI has no issue marker, is not the GHI's issue marker: the tool reports each file carrying it and does not link the file.
- **Data, not a citation.** The issue marker is read by the tool. CLAUDE.md's rule against citing a GHI by a bare number or GUID does not reach it; a writer who means to cite a GHI links it by title, and never writes its issue marker in prose, apart from a file path that carries it.

### Supporting documents and how they carry the issue marker

A supporting document is any file on main, a picture or a data file included, other than the GHI's GHI-MD, that carries the GHI's issue marker in its text content or in its file name. A file can carry several GHIs' issue markers, and a GHI can have many supporting documents.

A design is never only a supporting document. Every design is the GHI-MD of its own GHI, or a design beside its code; a design may also be a supporting document of other GHIs that depend on it. A design that exists only as a supporting document under another GHI's number, with no GHI of its own, is not allowed; the migration brings the one such file to the user (§ Getting there). A design that belongs to no GHI and sits under no other GHI's number, such as `nc-systems/cold-read/cold-read-design.md`, stays as it is.

- **A Markdown file** carries the issue markers on a front matter line, `supports-issues: ghi-783-…, ghi-790-…`. In a Markdown file with no `supports-issues:` line, `mark-supporting-document` adds one as the last line of the front matter, creating the front matter when the file has none; when the line exists, wherever it sits, the new issue marker joins it after a comma. The rebuild counts an issue marker found anywhere in the file's text. A GHI-MD can carry a `supports-issues:` line carrying other GHIs' issue markers, and is then a supporting document of those GHIs; a GHI-MD whose `supports-issues:` line carries its own GHI's issue marker is linked once, as the GHI-MD.
- **Another text file** carries the issue marker anywhere in its text content. `mark-supporting-document` writes it as a comment line, `supports-issues: ghi-783-…`, at the top of the file, after a shebang line (`#!`), a Python encoding declaration and an XML declaration when the file has them, in the comment syntax of the file's type: `#` for Python, shell, YAML and TOML, `//` for JavaScript and TypeScript, `<!-- -->` for HTML and XML. One comment line holds every issue marker the operation has written into the file, separated by commas, as the front matter line does; an issue marker the author put elsewhere in the file's text is not on that line. The type is read from the file's extension, or from its shebang line when it has no extension.
- **Any file, a binary one included,** can carry the issue marker in its file name, such as `ghi-783-…-answer-times.png`. The author puts it there when choosing the file name.
- **An image's embedded metadata** may carry the issue marker for a reader. The search does not rely on it: the search reads the text content only of the files git treats as text, passing `-I` to `git grep`, which otherwise reports a binary file whose bytes match; and many image tools compress or strip metadata when they save. A file git treats as binary is found by its file name alone.
- **A file that can carry the issue marker in neither place**, such as a JSON file whose format another program fixes and whose file name the author does not choose, is not linked; the GHI-MD cites it in its text.

A copy of a file carries the issue marker and is linked too. A copy of a GHI-MD outside the places a GHI-MD may sit, such as one under `docs/drafts/`, is therefore linked as a supporting document of its GHI, though it is not taken as the GHI-MD. A file in `docs/issues/queue/` or `docs/issues/archived/` is linked when it carries the issue marker, and not otherwise.

The tool writes the issue marker. `mark-supporting-document <path> <number>…` looks up each GHI's issue marker as § Which issue marker is the GHI's gives, from main or main's history, or, while the GHI is still being filed and its GHI-MD is on create-GHI's pull request, in the GHI's placeholder body, and writes it into the file at `<path>` in the author's checkout, in the form for the file's type; `mark-supporting-document --remove <path> <number>…` takes out the given GHIs' issue markers from the line the operation writes, the line when none is left, and the front matter block when nothing is left in it; at least one number is required either way. When any number given is refused, the operation refuses the whole request and changes nothing. The operation:
- refuses a closed GHI's number, saying: "GHI <number> is closed, and a closed GHI's description is never rebuilt, so the file would never be linked." and, on a line of its own, "Do not mark this file for a closed GHI. If the work continues in an open GHI, mark the file for that GHI; otherwise leave the file unmarked.";
- for a GHI whose GHI-MD is on main but has no issue marker in main, main's history or a placeholder body, such as a GHI whose filing was still in flight when the migration ran, makes the GHI a fresh issue marker and writes it on the `issue-marker:` line of the GHI-MD in the author's checkout as well, so the author's pull request carries both files, and carries on;
- refuses a number whose GHI has no GHI-MD on main yet because its filing has not finished, saying: "Nothing was marked: GHI <number>'s filing has not finished, so its GHI-MD is not on main yet." and, on a line of its own, "Run this command again after GHI <number>'s GHI-MD has merged."; and refuses a number that belongs to a pull request, or to nothing;
- prints that an issue marker is already present, or already absent, and changes nothing for it; an issue marker carried in the file's name, or elsewhere in its text content, it reports and leaves, for the author to remove by hand;
- refuses, exit 64, a binary file, telling the author to carry the issue marker in the file's name; a text file whose comment syntax the operation does not know, such as JSON, with the same instruction or the GHI-MD's text as the alternative; a Markdown file whose front matter opens with `---` and never closes; a `supports-issues:` line whose value, inside its comment syntax, is anything other than issue markers separated by commas, and a file with two such lines; and a file of agent-instructions: a `SKILL.md`, `CLAUDE.md`, `CLAUDE.local.md` or `AGENTS.md`, and any file whose name ends in `-instructions.md` or `-prompt.md`. The GHI-MD cites such a file in its text instead. A design and a wiki page are marked like any other Markdown file: the operation changes only their front matter, and the pull request that carries the change is reviewed as any change to such a file is.

The operation renames nothing and lands nothing: the author commits the changed file with the rest of the work, because a new supporting document usually lands in the author's own pull request. Which GHIs a file supports is the author's call.

### Names and titles

- **The author gives the name.** The author writes the GHI-MD as `<name>.md`, and create-GHI lands it as `docs/issues/<number>-<name>.md`. The tool no longer cuts a name from the first heading, and `SLUG_WORD_LIMIT` is deleted.
- **A GHI-MD with no number.** A GHI-MD that moves beside its code is named `<name>.md` there: the move drops the number and keeps the name, so the name of a GHI-MD with no number is its file name without `.md`, and the GHI's title does not change.
- **The checks.** create-GHI refuses, with a hard-block, exit 64, a name that:
  - is not 3 to 9 words, a word being one piece between hyphens, so `link-supporting-documents-and-name-issues-design` is 7 words;
  - is not lowercase letters and digits joined by single hyphens;
  - has a first word made only of digits, such as `2026-summary-of-reviews`, which the tool would read as a GHI number; `3d-graphics-export` passes;
  - carries a date in the form the check PR [GHI titles name the work](https://github.com/nedschorus/nedschorus/pull/829) built for the first heading recognizes, which moves to the name; a file path cannot pass the character check;
  - is already the name of another GHI-MD on main, or the title of another GHI, open or closed.
  The refusal says which check failed and how to fix the name. edit-GHI runs the same checks when the GHI-MD's name differs from its name on main, or when the GHI has no GHI-MD on main, and none when the name is unchanged. Two filings that both pass the checks before either creates its GHI, and choose the same name, are not caught.
- **What a program cannot check.** That the name names the work in full words, without abbreviations, status, ruling, provenance, or a date in a form the check does not recognize, is the author's to meet; the /ghi-write skill is to say so (§ What the build changes outside the tool). A name changes only when the user asks for it; the skill is to say that too, because nothing in a file records whether the user asked.
- **The title is the name, set on main.** The title is the name as written, hyphens included: this GHI's title becomes `link-supporting-documents-and-name-issues-design`. create-GHI files the GHI under the name. After that, only `relink-and-retitle-issues` sets the title, from the name of the GHI-MD on main, when the two differ. edit-GHI does not set the title, so an edit whose pull request is closed unmerged leaves the title as it was. The `issue:` line cites the GHI under its title. edit-GHI writes as the text of the `issue:` line the title the GHI will have once the rebuild has run: the GHI-MD's name when the GHI is open and the name passes the checks, otherwise the GHI's current title, since a closed GHI's title never changes. So the pull request that renames a GHI-MD also brings its `issue:` line to the name; the tool reads only the line's URL, so a line whose text lags breaks nothing.
- **A title is an identifier.** A title, like a file name, identifies rather than describes, so CLAUDE.md's rule that a hyphenated phrase marks a project-term or a system-term does not reach it.
- **The first heading is free text.** It no longer sets the title, so `heading_changed_in_this_edit`, `title_follows_heading_in_this_edit`, `issue_title_after_this_edit` and `sync_title_on_heading_change` are deleted, and `refuse_heading_with_date_or_file_path` becomes the name's date check. `validate` and `validate_edit` still require a first heading, because a GHI-MD opens with one; their refusal says so instead of calling the heading the title. `refuse_if_filing_is_in_flight` compares the name of the file given to create-GHI, not the file's first heading, with the titles of GHIs still being filed. Before the build's pull request merges, the builder confirms that no filing is in flight, no open GHI's body being create-GHI's placeholder, and finishes any that is, so no filing straddles the change.

### What the body links

The body of a link-only-GHI is, in order:

1. the link to the GHI-MD, found as above;
2. one link per supporting document, every file on main other than the GHI-MD that carries the GHI's issue marker in its text content or its file name, sorted by path.

Each link's text is the file's path in the repository, with Markdown's backslashes and brackets escaped, so two files with the same base name in different directories are told apart, and each link's address percent-encodes every segment of the path, keeping the slashes between segments and encoding `(` and `)` too, so a path holding `#`, `)` or a space still opens its file. A path holding a line break cannot be a link's text; the tool reports the file and does not link it. Nothing else is in the body, and nothing is kept by hand: the list is computed from main at every write. Not linked: a file only on an unmerged branch, whose link would not open, and a file in the log-store on ned-box, which GitHub cannot link; the GHI-MD cites either kind in its text.

The tool fetches origin/main once, takes the commit it points at, and reads that commit, so every read sees one state of main. It finds both kinds of file with two reads: `git grep -I` for `issue:` lines and for strings of the issue marker's pattern, `ghi-`, a number, `-` and 16 hexadecimal characters, in the text content of the files git treats as text, and `git ls-tree -r -z --name-only`, whose paths arrive unquoted, for the same pattern in each path's last segment, its file name. Of the strings found, the tool links each file by the issue marker it carries; a string that carries a GHI's number but whose random part matches none of that GHI's issue markers is reported (§ The issue marker). Another GHI's issue marker is not a fault and is not reported. An `issue:` line counts only in a file's front matter block, so the tool reads the front matter of each file `git grep` finds with such a line and drops a match outside the block. The issue marker counts anywhere in a text file, Markdown included, as the user ruled; a document that only describes a GHI does not carry it, because documentation shows the issue marker with its random part elided (§ The issue marker). For a GHI with no GHI-MD on main, a third read, of main's history, finds the issue marker (§ The issue marker).

The tool writes the body only over a body it wrote, its list of links or create-GHI's placeholder, recognised by its shape as `relink_body_from_main` does today, with `is_derived_body` changed to accept link text with escaped brackets, and leaves a prose body as it stands. When GitHub refuses a body as too long, the tool reports the GHI and leaves its body as it stands. When no GHI-MD is on main:
- a placeholder body stays, because the filing has not finished and its GHI-MD is still on a pull request; this is not reported;
- a list of links, when the GHI has at least one supporting document, is rebuilt from the supporting documents alone, so a dead link to a deleted GHI-MD drops out, and the tool reports that the GHI has no GHI-MD;
- when there is no supporting document either, the body is left as it stands, so no body is written empty; the tool reports it when the body is a list of links, and not when the body is prose, since an open GHI with a prose body and no file on main is a state the build accepts (§ Getting there).

### Rebuilding when main moves

A new operation, `relink-and-retitle-issues`, rebuilds the body and sets the title of each open GHI it is given. It skips a closed GHI, changing neither the body nor the title, as the user ruled (§ Closing a GHI), and prints a line for a closed GHI given on the command line. Every form fetches origin/main first. It has two forms:
- `relink-and-retitle-issues <number>…` for the GHIs given;
- `relink-and-retitle-issues --all-open` for every open GHI; a run that stops partway, for example on GitHub's rate limit, is run again whole.

Each run is idempotent: a GHI whose body and title already match is left untouched. The title is set whether the body is links or prose, and only to a name that passes the checks edit-GHI runs on a changed name (§ Names and titles); a GHI-MD renamed by an ordinary pull request, such as a `git mv` in a repository-layout migration, to a name that fails them leaves the title as it was, and the run reports the GHI. A GHI-MD on main with no `issue-marker:` line, or with one that does not hold one issue marker of its own GHI, leaves its GHI as it stands, body and title, so no link is dropped, and the run reports the GHI; the next edit-GHI run on that GHI-MD writes the GHI's issue marker back (§ The issue marker). A number that belongs to no GHI of this repository is reported and skipped. The run carries on with the rest after each report. Its exit status says only whether it did its work: it exits 0 when it did, every report printed as a line of its output, and 1 on an operating failure, as the tool's exit table already says, so a failure reaches whoever reads its exit status and a report never reads as a failure. A state that persists, such as a GHI with two GHI-MDs, is reported at every run that does work, until someone fixes it.

A scheduled job runs every 5 minutes, on ned-box only, so no two copies of the job run at once: one job entry, `relink-and-retitle-issues-when-main-moves`, in the `jobs` list of `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`. Each run fetches origin/main and first pins closed GHIs (§ Closing a GHI), whether or not main has moved. It then compares the commit main points at with the commit its last run that did work recorded; when main has not moved, the run exits there, writing nothing more. When main has moved, it runs `relink-and-retitle-issues --all-open`, then records the commit. Its output goes to the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/relink-and-retitle-issues-when-main-moves.log`, each run that does work opening with a line that carries its start time and main's commit. The report of every run that does work also lists every concerns file on main, a file named `<number>-<name>-concerns-*.md` beside a GHI's GHI-MD, which the ghi-write-tool writes when ghi-info finds that a draft may conflict with one of the user's rulings, and which a reviewer may write for any concern about the GHI. For each GHI that has one, the run starts a concerns agent-session, `concerns-<number>`, which brings all of that GHI's concerns to the user together, and opens its window on the user's Mac, only when no `concerns-<number>` agent-session exists yet on ned-box; while one waits, every report lists it, such as "GHI 783: concerns waiting in agent-session concerns-783". That agent-session is specified in its own GHI, still to be filed, not here. While the job runs, other writers can still edit the same GHI: an author's rerun of create-GHI or edit-GHI, or a one-GHI run of `relink-and-retitle-issues`. Each computes the body and the title from main, so writers that read the same main write the same body; a write from an older main stays until the next run that does work, after the next merge. Normally every merge is covered within five minutes, whoever made it and however, and nothing needs to be told that a merge happened; while ned-box is down, or the job fails, merges wait, and the failure is in the log. merge-lane-2 reads the newest report, that of the last run that did work, at the start of each agent-session and brings each report in it to the user; a state that persists is in every such report, and one a later run no longer reports needs no action.

A second scheduled job, `daily-issue-marker-upkeep`, runs once a day on ned-box and reuses the migration's code. A file that carries a string of a GHI's issue marker pattern whose random part differs from the issue marker on that GHI's GHI-MD, such as one left behind when someone changed a GHI-MD's `issue-marker:` line by hand, it re-marks with the GHI's current issue marker, all such files in one pull request that merge-lane-2 reviews like any other; anything that needs a choice, such as a GHI that has gained a second file claiming to be its GHI-MD, it reports for the user to decide, as the migration asks the user. File changes go through a pull request, so once a day keeps them to one pull request a day; reporting already happens every five minutes.

Before the build starts, the builder confirms that the `gh` login the scheduled job will use on ned-box can edit GHI titles and bodies: `ssh nedlern@ned-box gh api repos/nedschorus/nedschorus --jq .permissions` must show `push` or `triage` true. If that login cannot, the build stops and asks the user. After the build's pull request merges, the builder runs `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py` on ned-box, in the reference clone the job runs from, once that clone holds the merge, and reads the report of the first run that does work; a run that fails for the scheduler's environment, such as a `gh` login cron cannot see, is a failure to fix before the build counts as done.

create-GHI, rerun by an author on a GHI-MD on main whose GHI body the rebuild has already turned into links, prints that the filing is finished and exits 0, instead of refusing the file as already filed. A rerun on the author's original unnumbered file, `<name>.md`, after the filing has finished does the same: it prints that the filing is finished, names the GHI and the merged file, tells the author to delete the unnumbered file and to use edit-GHI on the merged file from now on, and exits 0. The /ghi-write skill's rerun after a merge becomes the fallback for the body when the scheduled run has not yet come; a title waits for the next `relink-and-retitle-issues` run.

### Closing a GHI

A closed GHI is frozen: no program changes its body or its title, apart from pinning its links once. However the GHI was closed, by an agent following the /ghi-write skill's `Close:` step, by GitHub when a merged pull request's description closes it, or by the user in the browser, the scheduled job of § Rebuilding when main moves pins it: on every run, whether or not main has moved, it searches GitHub for closed GHIs whose body still holds a link to main, and in each one it rewrites each link to main, `https://github.com/<repository>/blob/main/<path>` or `https://github.com/<repository>/tree/main/<path>`, where `<repository>` is the tool's `--repo` value, to the same path at one commit, the main commit the pinning run reads, at most five minutes after the GHI closed, `https://github.com/<repository>/blob/<commit>/<path>` or `…/tree/<commit>/<path>`, with any line anchor kept; GitHub calls such a link a permalink. This is done whether the body is a list of links or prose; only the links' addresses change, so a prose body keeps its text. A pinned link to a file that the commit at closing holds keeps opening after the file moves, is renamed or is deleted, and shows the file as it stood when the GHI closed; a link already dead at that commit stays dead. The search finds only the closed GHIs that still need pinning, so the job keeps no record of which it pinned, and a rebuild that read a GHI while it was open and wrote main's links back after the pin is pinned again by the next run.

After that, nothing rebuilds the GHI. `relink-and-retitle-issues` skips it however it is invoked, and a rerun of edit-GHI or create-GHI leaves its body and title alone. So its links and its title stay as they were at closing, even when its GHI-MD is later edited, moved or renamed, and a file marked later with the GHI's issue marker is not linked from it. A GHI that is reopened needs nothing special: the next run that does work rebuilds its body from main, which replaces the pinned links, and the first run after it closes again pins them again.

### Moves, renames and deletions

- **A GHI-MD moves or is renamed.** Its `issue:` and `issue-marker:` lines move with it, so the tool finds the file at its new path. edit-GHI, given a file whose `issue:` line links a GHI whose GHI-MD main holds at a different path, looks at that other path in the author's checkout:
  - the file is gone from the checkout: the author moved or renamed the GHI-MD, and edit-GHI removes main's old copy in the same commit, after today's conflict check on the moved-from path (`refuse_on_conflict`, exit 66), which refuses when main changed that path since the author's checkout started from it;
  - the file is still in the checkout: two files carry the line, and edit-GHI refuses, exit 64, telling the author to remove the `issue:` and `issue-marker:` lines from the copy, or to delete the original if the GHI-MD is moving.
  When main holds more than one GHI-MD for that GHI, edit-GHI removes nothing and refuses, exit 64, listing every path.
- **A supporting document moves, is renamed or is deleted.** The next rebuild rebuilds the body of every open GHI whose issue marker the file carried and whose body is the tool's list of links; a prose body stays as it stands. An issue marker in the file's text content moves with it; a file that carried the issue marker in its file name keeps it only if the new file name keeps it, which the author sees to. A deleted file drops out of the body, except when the GHI has no GHI-MD and no supporting document is left: then the body stays as it stands, dead links included, and is reported (§ What the body links).
- **A GHI-MD is deleted.** The rebuild follows § What the body links: the body keeps the supporting documents' links, and the tool reports that the GHI has no GHI-MD. The title stays.

### Where a GHI-MD may sit

A GHI-MD sits directly in `docs/issues/` from filing. A GHI-MD that is a design moves, once its code lands, where the file naming page puts a design whose code has landed: the `docs/` directory of the directory its code is in, at any depth under `nc-systems/`. Any other GHI-MD stays in `docs/issues/`. The tool accepts a GHI-MD in a `docs/` directory under `nc-systems/` only when it is a design, named `*-design.md` with no number (`landed_design_relative_path`), because the file naming page moves only designs beside their code; a GHI-MD there that is not a design is refused, exit 64, telling the author that the file belongs in `docs/issues/`. `writable_relative_path` still accepts `nc-systems/<system>/` directly, where the four designs moved out so far sit, so main-gatekeeper's design, `nc-systems/main-gatekeeper/main-gatekeeper-design.md`, is found there by its `issue:` line until the migration of GHI [Rationalize the repository layout: group components by owning system under nc-systems/, and a hook dispatcher](https://github.com/nedschorus/nedschorus/issues/224) moves it. That design has no `issue:` line today; the pull request that lands the user's review of it, branch `main-gatekeeper-specification-becomes-ghi-3-ghi-md`, writes the line. A move keeps both front matter lines, and so the file stays the GHI's GHI-MD.

A design whose code has landed, wherever the file sits, is revised only to fix a flaw found in it, and only after human review (the file naming page, as changed by PR [A landed design is revised only to fix a flaw, after human review](https://github.com/nedschorus/nedschorus/pull/860)). The tool does not enforce that; the /ghi-write skill is to say it for edit-GHI on a design whose code has landed (§ What the build changes outside the tool).
