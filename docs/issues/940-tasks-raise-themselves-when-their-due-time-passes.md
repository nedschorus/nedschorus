# Tasks raise themselves when their due time passes or their prerequisite is met

## Why

An agent often promises to act later: "I'll report when PR 927 merges", "I'll hold until the review is in". A promise backed only by a task on the agent-seat's task list still depends on the agent remembering to look at the list at the right moment, and nothing makes it look. Over 30 days of agent messages to the user, measured for GHI [A project style guide: words to avoid, a mechanical checker, and a check on unbacked promises](https://github.com/nedschorus/nedschorus/issues/14), 592 first-person promises were found and only 47.0% were backed by a task, a reminder or a background job in the same response. A memory is no backing either: nothing forces an agent to read one.

A rule holds when something fires at the moment the rule applies. This GHI gives a task that something: a prerequisite that a program checks, and two checkers that raise the task to its agent-seat when the prerequisite is met. To raise a task is to put it in front of its agent with the reason, so the agent acts on it now. The user approved the first version of this design on 2026-10-02; § The idle sweep, § Decided, records his later rulings.

## What to build

1. **One optional field in a task's `metadata`.** Every agent-seat's tasks are JSON files `~/.claude/tasks/nedschorus-<seat name>-tasks/<id>.json`, and a task may carry a `metadata` object; 57 of the 1,065 task files on the user's Mac carried one on 2026-10-02. Claude Code's TaskCreate and TaskUpdate tools both take a `metadata` argument, so an agent sets the field with the task tools, never by editing the files:
   - `prerequisites`: a list of conditions a program can check, all of which must hold. The first two kinds are `{"pr_merged": <pull request number>}` and `{"issue_closed": <issue number>}`, both in the repository nedschorus/nedschorus. A prerequisite on another task stays in the task's existing `blockedBy` field.

   A task is raised when its `prerequisites` all hold. A task whose `blockedBy` tasks are still open is not raised. A task without `prerequisites`, but with `blockedBy` tasks that have all completed, is raised once. A task with neither is a plain task, reviewed by the periodic approval-walks that put an agent-seat's open items to the user, as now. Until 2026-10-27 a task could also carry a due time, `due_utc`, and the field was named `waits_on`; PR [Agent-seat tasks drop due times, and waits_on is renamed prerequisites](https://github.com/nedschorus/nedschorus/pull/2012) dropped the due time and renamed the field, and the idle check names once any open task that still carries either old key.

2. **The idle check, built first.** A Stop hook runs at the end of each of the agent's turns, reads the agent-seat's own task list, and raises every open task whose prerequisites are met, so the agent acts on the task before it goes idle. The hook hands the agent its text as the Stop hook's `additionalContext`, not as a refusal of the stop, and Claude Code continues the conversation so the agent reads it: the text names each raised task and why, then tells the agent to give a task it cannot act on yet new `prerequisites`, or, for a task it waits on, `addBlockedBy`.
   - Conditions that need a network call, such as whether a pull request merged, are checked at most once every few minutes, each with a short timeout; between checks, the last answer stands.
   - The hook records what it raised, and when it last made each network check, in a state file of its own for the agent-seat. A task is raised once when its conditions come to hold, so the hook cannot keep the agent from stopping turn after turn; a raised task the agent leaves open is raised again only after the agent changes its `prerequisites` or its `blockedBy`, and then only when the new conditions all hold and the new `blockedBy` tasks have all completed.
   - A fault prints one line on stderr naming it and exits 1, which Claude Code records as a non-blocking error, so a hook error never stops the agent's turn from ending; a condition the hook could not ask GitHub about, at a stop that raises a task, is named in the raise text instead.

3. **The idle sweep.** A scheduled job, installed through `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` like the jobs already there, runs on ned-box every minute. It looks for an agent-seat that is idle while it has something to do, idle after a promise or an announced action that nothing backs, or stopped at a usage limit. The idle check cannot reach such an agent-seat, because an idle agent ends no turns. § The idle sweep, below, says how the job finds one and how it wakes it, and carries GHI 14's promise check.

GHI [Relaunch stopped agent-seats with open tasks daily](https://github.com/nedschorus/nedschorus/issues/936) also reads agent-seat task lists on a schedule, to relaunch agent-seats that stopped; the idle sweep and that GHI's job may share one reader of the task files.

## The idle sweep

### Why

Two incidents of 2026-10-29 and 2026-10-30, both in reboot-test's agent-session 222a1661-826e-4213-834e-439b45884194 (transcript `nedlern@ned-box:/home/nedlern/.claude/projects/-home-nedlern-agents-reboot-test/222a1661-826e-4213-834e-439b45884194.jsonl`):

- **A turn that ended on an announced action.** On 2026-10-30 at 17:14:34Z the agent ended a turn on "I'm starting the PR 1633 work now.", about PR [GHI-MD edit for issue 1571: The Bash guards replay reads a stored file of distinct recorded command pairs, reuses main's readings and reads many commands in each new process](https://github.com/nedschorus/nedschorus/pull/1633), without a tool call. Eight Stop hooks ran, and none of them stopped it. The agent-seat sat idle until the user noticed, at 17:38:48Z, 24 minutes later. GHI [A project style guide: words to avoid, a mechanical checker, and a check on unbacked promises](https://github.com/nedschorus/nedschorus/issues/14) records this incident against its announced-action check, which is not built.
- **Ready work held for 19 hours.** At 22:54Z on 2026-10-29 the handoff threshold hook put off the agent-session's handoff while a subagent ran, told the agent to start no new subagents until a later message, and then went silent. That message could never come, because of two defects in the hook: it counted a subagent that had finished as still running, and its 65% ceiling compares only the current context, which compaction kept at 24%. ned-box-helper's task #165, which fixes the hook's reading of a subagent whose last notice is interim, and reboot-test's task #369, "Handoff threshold hook: the 65% ceiling compares only current context", fix the defects. Ready work waited until the user asked about it at about 18:00Z on 2026-10-30.

Each defect has its own fix. This sweep is the backstop for the defects nobody has found yet: an agent-seat that sits idle with something to do is found within minutes, whatever left it idle, and is woken unless the judge of § Who decides finds it cannot act now.

The first incident is also the kind GHI [A project style guide: words to avoid, a mechanical checker, and a check on unbacked promises](https://github.com/nedschorus/nedschorus/issues/14) designed its promise check for, its item 3. The user asked for the two to be one design, on 2026-10-30, at item 1 of reboot-test's approval-walk reboot-test-idle-agent-seat-wake-route-2026-10-30: "I think we've got some other system that is looking for false promises or promises not met that potentially could use a similar design. This design sounds better than the unmet promises design. So take a look and probably roll these both into one design. I think they're basically they're either false, unrealized promises or potentially accidental idols or even purposeful idols." ("idols" is his dictation of "idles".) § Promises and announced actions, below, is that design: the promise check runs inside this job, on an agent-seat found idle, instead of as a Stop hook at the end of every turn.

He also proposed treating zero token spend in an agent-session's transcript as the sign that it is truly idle, with a cheap model deciding whether to nudge.

### How the job tells an agent-seat is idle

Code decides, from facts on disk; no model runs unless rule 2 or rule 5 of § Who decides applies to an idle agent-seat. An agent-seat is idle when all of these hold:

- Its current agent-session's transcript, `~/.claude/projects/<project folder>/<session id>.jsonl`, and every transcript under that agent-session's `subagents/` directory, gained no record that spent tokens (an `assistant` record with `usage`) in the last 5 minutes.
- Its last turn ended: the last record of the agent-session's own transcript is the `turn_duration` system record, or a later record that is not a request to the model.
- No approval-walk item is waiting on the user: no walk-minutes file in the agent-seat's `docs/walk/` folder has a last `#next_to_present` line other than `#next_to_present none, closed`.

Code also reads from the transcript what the agent-seat is waiting on, and since when: each background command it started (a tool call with `run_in_background`) with no completion notice after it, and each subagent it started that has not yet given its final report. A subagent counts as running from its start until its final report.

### Who decides, and what is sent

For each idle agent-seat, code applies these rules in order, and the first that applies settles the case, except that when rule 2's judge finds every matched sentence backed, rules 3 to 5 decide it:

1. **A usage limit**: the last record of the agent-seat's transcript is Claude's usage-limit record. The job runs the step **a session limit**, below, and nothing else.
2. **A promise or an announced action**: a message that ended one of the agent-seat's turns since the job last checked it holds a sentence that GHI 14's phrase lists match. A check is a run of the job that found the agent-seat idle. The headless agent-session below judges the sentence, as § Promises and announced actions says.
3. **A handoff put off**: a handoff deferral marker file, `~/.claude/handoffs/<session id>-handoff-deferred`, exists for the agent-session, and nothing is found running. Code decides: wake, with code's text "Your handoff was put off at <time> and nothing is running now. Is now a good time to hand off?", which a headless agent-session sends as written.
4. **Nothing to do**: nothing is found running, no handoff deferral marker file exists, and no open task is one that nothing holds, that is, none is one whose `blockedBy` tasks, if any, are all completed or deleted, as the idle check counts them, and whose `prerequisites`, if any, all hold, which code asks GitHub as the idle check does, at most once every few minutes for each condition. Code decides: no wake.
5. **Anything else**: the headless agent-session below judges it.

Rule 1 comes before rule 4 because a usage limit stops an agent in the middle of its work, whether or not a task records that work, and the user ruled an extra wake harmless on 2026-10-18 ("If it's already awake who cares", in GHI 1152's GHI-MD). Rule 2 comes before rule 4 because an agent that promised something and recorded no task is the case the promise check exists for.

To judge, at rules 2 and 5, and to send a text code wrote, the job starts a headless agent-session on Sonnet, `claude -p --model sonnet`, with only the SendMessage, ListAgents and ToolSearch tools allowed, as in the canary test under § How the message reaches the agent-seat; for rule 2, § Promises and announced actions says what it is given and what it sends. For rule 5, code hands it the agent-seat's last message, its open tasks that nothing holds, any handoff deferral marker file, what code found it waiting on and for how long, the agent-seat's name and tmux session, by which it picks the one ListAgents entry to write to, and which step this is. The headless agent-session judges whether the agent-seat could act now. If it could, it sends the agent-seat a short message saying what it saw. The message names each background command and subagent that has not yet finished or reported, with how long it has run, and asks whether it is taking longer than expected, such as "Your test-suite run started 25 minutes ago and has not finished. Is it taking longer than expected?". With nothing running, it asks what is going on, such as "You said "I'm starting the PR 1633 work now" 6 minutes ago and have made no tool call since. What's going on?". If it could not, it sends nothing. Its last output is JSON that code checks and logs, whether it sent a message and why, as `{"sent": false, "reason": "a subagent started 3 minutes ago is still running"}`. After a verdict not to send, code asks again about that agent-seat only when it next spends tokens and goes idle again, or 15 minutes later, whichever comes first. Each headless agent-session is stopped after 5 minutes; one that fails or is stopped is reported to the user.

Code keeps a log of each message sent and each verdict, with its time, in the log-store, and decides from it which step comes next:

- **nudge**: the first message about this wait, as above.
- **escalate**: when the agent-seat is idle again 15 minutes after a nudge, even if it answered the nudge, code fills X into the user's words and the headless agent-session sends that text as written: "You've given this X minutes, please check; if not sure, hand off". X is the number of minutes since the agent-seat first went idle in this wait, as in "You've given this 20 minutes, please check; if not sure, hand off".
- **tell the user**: when the agent-seat is idle again 15 minutes after an escalation, the job tells the user, once, instead of the agent-seat. After telling the user, the job sends nothing more about the agent-seat until it spends tokens and goes idle again, which starts the steps over.
- **a session limit**: when rule 1 applies, the job runs none of the steps above. Claude Code writes the limit as an `assistant` record with `"apiError": "usage_limit_reached"`, whose `quotaLimits` object carries `resetsAt`, the reset time in Unix seconds; its text, such as "You've hit your session limit · resets 1am (America/Los_Angeles)", is for people, and code does not read it. One rule covers every kind of limit, with no 5-hour or weekly case: the limit has ended when `resetsAt` passes, or when the account logged in on that machine, `oauthAccount.accountUuid` in `~/.claude.json`, differs from the account code recorded when it first saw the limit record, whichever comes first. A missing account, as in the middle of a switch, is not a change. At the job's first run after the limit has ended, the headless agent-session sends one short message that code wrote, with no judgment asked of it. Code logs the agent-seat, the limit record and why it ended, and sends no second wake for the same limit record. If the agent-seat is still idle 5 minutes after the wake, code skips rule 1 for that limit record from then on, so rules 2 to 5 decide the case at the next run, starting from the nudge. Switching the agent-seats to another account is GHI [Switch the agent-seats to another Claude account when the current account reaches its weekly usage limit](https://github.com/nedschorus/nedschorus/issues/1201), and this job does not do it; it only notices that the account changed, whether the switch was made by hand or by that GHI's switcher. Whether a cross-session message sent after a limit ends resumes the agent-seat is tested at the first such wake after the job is built, and recorded in GHI 1152.

### Promises and announced actions

This is GHI 14's promise check, its item 3, moved into this job. The kinds of sentence and what backs each are GHI 14's; what changes is when the check runs and who judges.

**What code picks out.** At rule 2, code reads each message that ended one of the agent-seat's turns since the job last checked that agent-seat, and matches its sentences against two phrase lists from GHI 14's measurements: the promise phrases its item 3 lists, such as "I'll bring you X", "I'll report when…", "Noted", "I'll hold", "from now on" and "say the word and I'll …", and the announced-action phrases at the top of `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/announced-action-not-executed-measurement-2026-10-19/measure_announced_actions.py`. The job's module in the repository holds the one copy of each list, each phrase tagged with its kind of sentence below; GHI 14's item 3 and the script are only where the lists start. The lists only choose which sentences are checked. A sentence they miss is seen only when rule 5 applies and the sentence is in the agent-seat's last message, which the judge is handed; and a sentence they match by mistake costs at most one Sonnet call.

**What code settles, and what the headless agent-session judges.** Code settles two cases without a model. A promise or a hold is unbacked when no task created or updated in the sentence's turn or after it carries `prerequisites` or `blockedBy`; when one does, the headless agent-session judges whether it names the sentence's event. A sentence tagged conditional on the user, such as "say the word and I'll …", is not raised, because the user has the next move, and neither is one tagged negative, such as "I won't merge it yet", as Decided point 7 keeps. For every other matched sentence, code hands the headless agent-session, beside what § Who decides lists, the sentence with its time and kind, the tool calls the agent-seat made in that turn and after it, each task those calls created or updated with its `prerequisites` and `blockedBy`, and each hook or test file they changed. It answers, as JSON that code checks, backed or unbacked for each sentence, by GHI 14's rules:

- **An announced action**, such as "Next I'm starting the pull request", is backed when a tool call in the same turn, before or after the sentence, or a later one does the action, or a background task it started is still running.
- **A promise to act after an event**, such as "I'll report when PR 927 merges", is backed by a task whose `prerequisites` or `blockedBy` name the event, so the idle check raises it.
- **A standing rule**, such as "from now on" or "Noted", is backed by the hook or test that enforces it, or by a task to build one together with a proposal to the user; a memory never backs it.
- **A hold**, such as "I'll hold", is backed by a task whose `prerequisites` name what releases the hold.

Code writes one message covering every unbacked sentence, one line for each from its kind's text, and a second headless agent-session, with no judgment asked of it, sends that message as written:

- an announced action: "You said "<the sentence>" <N> minutes ago and have not done it. Do it now, or tell the user why not."
- a promise to act after an event: "You promised "<the sentence>". Record it as a task whose prerequisites name the event, or tell the user you take the promise back."
- a standing rule: "You said "<the sentence>". Back it with the hook or test that enforces it, or a task to build one and a proposal to the user, or tell the user you take it back."
- a hold: "You said "<the sentence>". Record a task whose prerequisites name what releases the hold, or tell the user you are no longer holding."

When every matched sentence is backed, rules 3 to 5 decide the case.

**Once each.** Code logs each sentence it has raised, by the transcript record that holds it and the sentence's text, and never raises it again, so the check cannot keep an agent from going idle; the same words in a later message are a new sentence. The message is the nudge of § Who decides: it starts a wait, and if the agent-seat stays idle the escalation and telling the user follow as for any other wait.

**What this gives up.** A Stop hook would have raised an unbacked sentence the moment the turn ended; this job raises it once the agent-seat has been idle 5 minutes, at the next run of the job. In return, the judge sees each sentence with its whole turn and what followed, so it can tell a promise from a passing phrase, and an agent that is waiting for its own background work, which was 76% of the stops after an announced action in GHI 14's measurement of 2026-10-19, is not sent a promise message while that work runs. A turn whose agent-seat keeps working is checked at the next idle stretch, with every turn-ending message since the last check.

### How the message reaches the agent-seat

The message is a cross-session message, sent with SendMessage, Claude Code's own tool for messages between agent-sessions. Nothing types into a terminal or a tmux window, so nothing can land in the middle of what the user is typing. A cross-session message wakes an idle agent-session, which then processes it: GHI [Claude turn/start and turn/steer equivalents: inject a message into an idle session, steer an active turn](https://github.com/nedschorus/nedschorus/issues/37), which had found an injected message left unprocessed until a keystroke, was closed on 2026-09-18 because Claude Code's own messaging had started to work, agent-seats wake on each other's messages every day, and the canary test below shows it. On 2026-10-30 a headless Haiku agent-session started this way listed all nine agent-seats on ned-box, each with its tmux pane and whether it was busy or idle, and delivered a message into reboot-test's agent-session.

The canary test of Decided point 2, under § The idle sweep, passed on ned-box on 2026-10-31. An interactive agent-session, `claude --model haiku` in the tmux session canary-wake and the folder `/home/nedlern/agents/canarybox`, ended its first turn at 02:09:43Z and sat idle. At 02:10Z a headless agent-session, `claude -p --model sonnet --allowedTools=SendMessage,ListAgents,ToolSearch`, started in the same folder, picked the idle agent-session's entry `canarybox-61 [1bd527]` from ListAgents and sent it a cross-session message as `canarybox-1f`: "Canary wake test from a headless Sonnet session: you have been idle; reply with the single word awake." At 02:10:04Z the idle agent-session's transcript gained the message as a user record, and at 02:10:05Z it took a new turn and answered "awake". Nothing was typed into its terminal. The record is `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/reboot-test/canary-idle-wake-cross-session-message-2026-10-31/`: a README, the idle agent-session's transcript and its tmux pane. The test shows that a cross-session message from a headless agent-session wakes an idle interactive agent-session. It did not test an agent-seat, since the idle agent-session was a throwaway one idle for 21 seconds, nor how code finds an idle agent-seat; nor an agent-session stopped at its session limit, woken after the reset; nor an agent-session on the Mac.

Three limits remain:

- A cross-session message reaches the other machine only while the receiving agent-session's Remote Control is connected, as GHI [Seat mailboxes across machines and runtimes](https://github.com/nedschorus/nedschorus/issues/749) records, so the Mac's agent-seats get a job running on the Mac. ned-box comes first.
- A message can go to an old offline entry that Remote Control left in the list of agent-sessions, instead of the running agent-session, as GHI [Save a message that SendMessage queues to an offline Remote Control entry, and deliver it later or have the sender resend it](https://github.com/nedschorus/nedschorus/issues/1115) records. On 2026-10-30, ListAgents showed three entries named prime-intellect: the running agent-session on ned-box and two Remote Control entries, from 3 and 18 days before. The headless agent-session therefore writes only to the entry ListAgents shows as interactive, with the agent-seat's name and tmux session, such as `prime-intellect [9cbc4b] · interactive · tmux prime-intellect:@0.%0`, and never to a Remote Control entry; code cannot pick the entry itself, because ListAgents is a tool only an agent-session can call and `claude agents --json` does not give the entry's ref. When the headless agent-session's own transcript shows a SendMessage call, code looks a minute later for that message in the agent-seat's transcript, comparing it with the text code wrote where code wrote it, and tells the user when it is not there.
- Each headless agent-session costs one Sonnet call: one judges at rule 2 or 5, and one sends each text code wrote, so a promise found unbacked costs two; on most runs the job makes none, because code finds no idle agent-seat or settles the case itself.

This job replaces the 3-hourly wake of GHI [Wake an agent-seat when its 5-hour session limit resets](https://github.com/nedschorus/nedschorus/issues/1152), which is not built, and also wakes an agent-seat whose 5-hour session limit has reset.

### Settled with the design, from the evidence

- **The order of the rules** in § Who decides: a usage limit first, then a promise, then a handoff put off, then nothing to do. The reasons are under the rules.
- **Reading the limit**: from the record's `resetsAt` and the logged-in account, never its text, so no time-zone or clock-time parsing is needed.
- **The Mac**: the job's entry in `scheduled-jobs-on-each-machine.json` gains a `mac` key in its own pull request after the job has woken an agent-seat on ned-box, and an agent-seat on the Mac runs `nc-systems/general-tools/install-scheduled-jobs-on-this-machine.py --install` there and records the first Mac wake. The program is the same on both machines and reads only its own machine's transcripts and task lists, since cross-session messages stay on one machine.
- **No more canary tests before the build.** The canary test of Decided point 2 passed. The cases it left untested, a real agent-seat, an agent-seat after a reset, and the Mac, are left to the job's first runs, and each first case is recorded when it happens: the first wake of a real agent-seat here, the first wake after a reset in GHI 1152, and the first Mac wake here. A wrong entry or a message that did not arrive will be caught: code looks for the message in the agent-seat's transcript a minute later and tells the user when it is not there.
- **GHI 1152 stays open**, with `kind: design`, until its Next action records the first wake after a reset on each machine.
- GHI [Console text-insertion + stuck/waiting-state detection (operator tooling; captured from the comms backlog)](https://github.com/nedschorus/nedschorus/issues/27) measured a Monitor tool inside an agent-session waking it with no keystroke. This job does not use it, because it runs inside each agent-session, which the user said clutters the agent-session, preferring a message from a supervising program (2026-10-30, item 5.2.2.7 above), and the cross-session message has passed its own canary test.

### Decided

The user ruled on points 1 to 6 in reboot-test's approval-walk reboot-test-idle-agent-seat-wake-route-2026-10-30 (walk-minutes: `nedlern@ned-box:/home/nedlern/agents/reboot-test/docs/walk/reboot-test-idle-agent-seat-wake-route-2026-10-30-minutes.md`), and on points 7 and 8 in the approval-walk each names.

1. **The route** (user-ruled 2026-10-30, item 1): a supervising scheduled job sends a cross-session message, with SendMessage, from one headless agent-session, as above. It replaces GHI 1152's 3-hourly in-session wake, which is not built.
2. **A canary test before the build** (user-ruled 2026-10-30, item 1): an idle agent-session gets a cross-session message from a headless agent-session, and its transcript is checked for a new turn, before the job is built. It passed on 2026-10-31, as § How the message reaches the agent-seat records.
3. **One design with GHI 14's promise check** (user-ruled 2026-10-30, item 1): this idle sweep and GHI 14's check on unbacked promises are one design, which § Who decides and § Promises and announced actions give.
4. **The numbers** (user-ruled 2026-10-30, item 2): an agent-seat counts as idle after 5 minutes with no token spent; the job runs every minute; 15 minutes from the nudge to the escalation and 15 more before the user is told, once; X counts from when the agent-seat first went idle.

#### What to add

Each new `prerequisites` kind's key names are chosen in the pull request that builds it, and that pull request adds the kind to phase 1's TaskCreate hook text, which otherwise tells agents to record no other kind.

1. **An approval-walk item as a condition.** A new `prerequisites` kind names an approval-walk and an item number, and is met when the walk-minutes record the user's answer to that item. The prerequisite is met when the `close` step of `nc-systems/skills/walk-me-through/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close.py` has recorded the item's outcome, after its `check` step wrote the answer; the program knows the approval-walk's name, the item and the answer. 2. **A task on another agent-seat's list as a condition.** A new `prerequisites` kind names an agent-seat and a task id, and is met when that task is completed. The task may be on either machine; the log-store's copies make both readable from ned-box.
3. **Telling what waits on a finished task.** A task can record what waits on it: a pull request, a GHI, an approval-walk item, or a task on another agent-seat's list. When the task is completed, the agent-seat responsible for the waiting thing is told, by the delivery of GHI 1203 described above: the author agent-seat of the pull request, the agent-seat that runs the approval-walk, or the agent-seat whose task waits. Today `blocks` names only tasks on the same list, and nothing tells anyone else.
4. **Prerequisites that will never be met.** A task now waits in silence, for good, when its prerequisite is cancelled rather than finished: a pull request closed without merging never meets `pr_merged`; an approval-walk item the user disapproved or deferred out of the approval-walk would never meet item 1's condition; a task on another agent-seat's list that was deleted would never meet item 2's condition; and a `blockedBy` task that was deleted stops holding the task, by the idle check's design, so a task that also has `prerequisites` is raised as if its blocker were done, a task with neither is never raised, and in both cases nothing says the blocker was deleted. In each case the waiting task's agent-seat is told, by the delivery of GHI 1203 described above, that the prerequisite was cancelled, naming it, so the agent re-plans the task. A GHI closed as not planned meets `issue_closed` today, the same as one closed as completed, because the idle check compares only the GHI's state with CLOSED.
5. **Further improvements** the user adds go in § Provisional additions until he vets them.
