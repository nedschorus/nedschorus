# Tasks raise themselves when their due time passes or their prerequisite is met

## Why

An agent often promises to act later: "I'll report when PR 927 merges", "I'll hold until the review is in". A promise backed only by a task on the agent-seat's task list still depends on the agent remembering to look at the list at the right moment, and nothing makes it look. Over 30 days of agent messages to the user, measured for GHI [A project style guide: words to avoid, a mechanical checker, and a check on unbacked promises](https://github.com/nedschorus/nedschorus/issues/14), 592 first-person promises were found and only 47.0% were backed by a task, a reminder or a background job in the same response. A memory is no backing either: nothing forces an agent to read one.

A rule holds when something fires at the moment the rule applies. This issue gives a task that something: a prerequisite that a program checks, and two checkers that raise the task to its agent-seat when the prerequisite is met. To raise a task is to put it in front of its agent with the reason, so the agent acts on it now. The user approved this design on 2026-10-02.

## What to build

1. **One optional field in a task's `metadata`.** Every agent-seat's tasks are JSON files `~/.claude/tasks/nedschorus-<seat name>-tasks/<id>.json`, and a task may carry a `metadata` object; 57 of the 1,065 task files on the user's Mac carried one on 2026-10-02. Claude Code's TaskCreate and TaskUpdate tools both take a `metadata` argument, so an agent sets the field with the task tools, never by editing the files:
   - `prerequisites`: a list of conditions a program can check, all of which must hold. The first two kinds are `{"pr_merged": <pull request number>}` and `{"issue_closed": <issue number>}`, both in the repository nedschorus/nedschorus. A prerequisite on another task stays in the task's existing `blockedBy` field.

   A task is raised when its `prerequisites` all hold. A task whose `blockedBy` tasks are still open is not raised. A task without `prerequisites`, but with `blockedBy` tasks that have all completed, is raised once. A task with neither is a plain task, reviewed by the periodic approval-walks that put an agent-seat's open items to the user, as now. Until 2026-10-26 a task could also carry a due time, `due_utc`, and the field was named `waits_on`; PR [Agent-seat tasks drop due times, and waits_on is renamed prerequisites](https://github.com/nedschorus/nedschorus/pull/2012) dropped the due time and renamed the field, and the idle check names once any open task that still carries either old key.

2. **The idle check, built first.** A Stop hook runs at the end of each of the agent's turns, reads the agent-seat's own task list, and raises every open task whose prerequisites are met, so the agent acts on the task before it goes idle. The hook hands the agent its text as the Stop hook's `additionalContext`, not as a refusal of the stop, and Claude Code continues the conversation so the agent reads it: the text names each raised task and why, then tells the agent to give a task it cannot act on yet new `prerequisites`.
   - Conditions that need a network call, such as whether a pull request merged, are checked at most once every few minutes, each with a short timeout; between checks, the last answer stands.
   - The hook records what it raised, and when it last made each network check, in a state file of its own for the agent-seat. A task is raised once when its conditions come to hold, so the hook cannot keep the agent from stopping turn after turn; a raised task the agent leaves open is raised again only after the agent changes its `prerequisites` or, for a task raised because its `blockedBy` tasks completed, its `blockedBy`, and then only when the new conditions all hold or the new `blockedBy` tasks have all completed.
   - A fault prints one line on stderr naming it and exits 1, which Claude Code records as a non-blocking error, so a hook error never stops the agent's turn from ending; a condition the hook could not ask GitHub about, at a stop that raises a task, is named in the raise text instead.

3. **The idle sweep.** A scheduled job, installed through `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` like the jobs already there, runs on ned-box every minute. It looks for an agent-seat that is idle while it has something to do. The idle check cannot reach such an agent-seat, because an idle agent ends no turns. § The idle sweep, below, says how the job finds one and how it wakes it.

GHI 14's promise check, its item 3, is narrowed to depend on this issue in an edit of the same day: a promise passes when the same turn created or updated a task with a due time or a checkable prerequisite.

GHI [Relaunch stopped agent-seats with open tasks daily](https://github.com/nedschorus/nedschorus/issues/936) also reads agent-seat task lists on a schedule, to relaunch agent-seats that stopped; the idle sweep and that issue's job may share one reader of the task files.

### How the job tells an agent-seat is idle

Code decides, from facts on disk; no model runs while every agent-seat is busy or has nothing to do. An agent-seat is idle when all of these hold:

- Its current agent-session's transcript, `~/.claude/projects/<project folder>/<session id>.jsonl`, and every transcript under that agent-session's `subagents/` directory, gained no record that spent tokens (an `assistant` record with `usage`) in the last 5 minutes.
- Its last turn ended: the last record of the agent-session's own transcript is the `turn_duration` system record, or a later record that is not a request to the model.
- No approval-walk item is waiting on the user: no walk-minutes file of the agent-seat's has a last `#next_to_present` line other than `#next_to_present none, closed`.

Code also reads from the transcript what the agent-seat is waiting on, and since when: each background command it started (a tool call with `run_in_background`) with no completion notice after it, and each subagent it started that has not yet given its final report. A subagent counts as running from its start until its final report.

### Who decides, and what is sent

Code decides two cases without a model: a handoff deferral marker file under `~/.claude/handoffs/`, with nothing found running, means wake; no open task that nothing holds, and no such marker file, means no wake. For any other idle agent-seat, the job starts one headless agent-session on Sonnet, `claude -p --model sonnet`, with only the SendMessage tool allowed. Code hands it the agent-seat's last message, its open tasks that nothing holds, any handoff deferral marker file, what code found it waiting on and for how long, the one ListAgents entry to write to, and which step this is. The headless agent-session judges whether the agent-seat could act now. If it could, it sends the agent-seat a short message saying what it saw. The message names each background command and subagent that has not yet finished or reported, with how long it has run, and asks whether it is taking longer than expected, such as "Your test-suite run started 25 minutes ago and has not finished. Is it taking longer than expected?". With nothing running, it asks what is going on, such as "You said "I'm starting the PR 1633 work now" 6 minutes ago and have made no tool call since. What's going on?", or "Your handoff was put off at 22:54Z and nothing is running now. Is now a good time to hand off?". If it could not, it sends nothing. Each headless agent-session is stopped after 5 minutes; one that fails or is stopped is reported to the user.

Code keeps a log of each message sent, with its time, in the log-store, and decides from it which step comes next:

- **nudge**: the first message about this wait, as above.
- **escalate**: when the agent-seat is idle again 15 minutes after a nudge, even if it answered the nudge, the headless agent-session is told to send the user's words, with X filled in: "You've given this X minutes, please check; if not sure, hand off". X is the number of minutes since the agent-seat first went idle in this wait, as in "You've given this 20 minutes, please check; if not sure, hand off".
- **tell the user**: when the agent-seat is idle again 15 minutes after an escalation, the job tells the user, once, instead of the agent-seat. After telling the user, the job sends nothing more about the agent-seat until it spends tokens and goes idle again, which starts the steps over.
- **a session limit**: when the agent-seat's last turn ended on Claude's session-limit message, which names the reset time, such as "You've hit your session limit · resets 1am (America/Los_Angeles)", the job runs none of the steps above. A few minutes after that reset time, the headless agent-session sends one short message, with no judgment asked of it, and the steps start over if the agent-seat is still idle 5 minutes later. Whether a cross-session message sent after a reset resumes the agent-seat is tested when the job is built.

### How the message reaches the agent-seat

The message is a cross-session message, sent with SendMessage, Claude Code's own tool for messages between agent-sessions. Nothing types into a terminal or a tmux window, so nothing can land in the middle of what the user is typing. A cross-session message wakes an idle agent-session, which then processes it: GHI [Claude turn/start and turn/steer equivalents: inject a message into an idle session, steer an active turn](https://github.com/nedschorus/nedschorus/issues/37) records this in its outcome of 2026-09-18, and agent-seats wake on each other's messages every day. On 2026-10-30 a headless Haiku agent-session started this way listed all nine agent-seats on ned-box, each with its tmux pane and whether it was busy or idle, and delivered a message into reboot-test's agent-session.

The canary test of Decided point 2, under § The idle sweep, passed on ned-box on 2026-10-31. An interactive agent-session, `claude --model haiku` in the tmux session canary-wake and the folder `/home/nedlern/agents/canarybox`, ended its first turn at 02:09:43Z and sat idle. At 02:10Z a headless agent-session, `claude -p --model sonnet --allowedTools=SendMessage,ListAgents,ToolSearch`, started in the same folder, picked the idle agent-session's entry `canarybox-61 [1bd527]` from ListAgents and sent it a cross-session message as `canarybox-1f`: "Canary wake test from a headless Sonnet session: you have been idle; reply with the single word awake." At 02:10:04Z the idle agent-session's transcript gained the message as a user record, and at 02:10:05Z it took a new turn and answered "awake". Nothing was typed into its terminal. The record is `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/reboot-test/canary-idle-wake-cross-session-message-2026-10-31/`: a README, the idle agent-session's transcript and its tmux pane. The test shows that a cross-session message from a headless agent-session wakes an idle interactive agent-session. It did not test an agent-seat, since the idle agent-session was a throwaway one idle for 21 seconds, nor how code finds an idle agent-seat; nor an agent-session stopped at its session limit, woken after the reset; nor an agent-session on the Mac.

Three limits remain:

- Cross-session messages stay on one machine, so the Mac's agent-seats need a job running on the Mac; GHI [Seat mailboxes across machines and runtimes](https://github.com/nedschorus/nedschorus/issues/749) records the limit. ned-box comes first.
- A message can go to an old offline entry that Remote Control left in the list of agent-sessions, instead of the running agent-session, as GHI [Cross-session messages between agent-seats reach stale offline Remote Control entries instead of the live agent-session](https://github.com/nedschorus/nedschorus/issues/1115) records. On 2026-10-30, ListAgents showed three entries named prime-intellect: the running agent-session on ned-box and two Remote Control entries, from 3 and 18 days before. Code therefore picks the entry ListAgents shows on this machine, by its name and its ref, such as `prime-intellect [2c0a77]`, looks a minute later for a new message from the headless agent-session in the agent-seat's transcript, and tells the user when there is none.
- Each agent-seat found idle costs one Sonnet call; on most runs the job makes none, because code finds no idle agent-seat.

This job replaces the 3-hourly wake of GHI [Wake an agent-seat when its 5-hour session limit resets](https://github.com/nedschorus/nedschorus/issues/1152), which is not built, and also wakes an agent-seat whose 5-hour session limit has reset.

1. **The route** (user-ruled 2026-10-30, item 1): a supervising scheduled job sends a cross-session message, with SendMessage, from one headless agent-session, as above. It replaces GHI 1152's 3-hourly in-session wake, which is not built.
2. **A canary test before the build** (user-ruled 2026-10-30, item 1): an idle agent-session gets a cross-session message from a headless agent-session, and its transcript is checked for a new turn, before the job is built. It passed on 2026-10-31, as § How the message reaches the agent-seat records.
3. **One design with GHI 14's promise check** (user-ruled 2026-10-30, item 1): this idle sweep, as this section describes it, and GHI 14's check on unmet promises are to be joined into one design. That design is not yet written; until it is, this section is the idle sweep's design.
4. **The numbers** (user-ruled 2026-10-30, item 2): an agent-seat counts as idle after 5 minutes with no token spent; the job runs every minute; 15 minutes from the nudge to the escalation and 15 more before the user is told, once; X counts from when the agent-seat first went idle.
5. **What the message says** (user-ruled 2026-10-30, item 2): the headless agent-session still decides whether to send; the message names each background command and subagent that has not finished or reported, with how long it has run, and asks whether it is taking longer than expected. A subagent counts as running from its start until its final report.
6. **The model** (user-ruled 2026-10-30, rider on item 2): the headless agent-session runs on Sonnet, `claude -p --model sonnet`, not Haiku. Each message it sends costs the agent-seat a full turn on its own model, which costs far more than the Sonnet call, so a judge that sends fewer needless messages saves more than the difference; and the calls are rare, since code decides the plain cases.

## More kinds of prerequisite, in two phases

The user asked on 2026-10-24, in prime-intellect's approval-walk prime-intellect-open-decisions-for-the-user-2026-10-22-2, for a separate GHI in which the tasks that wait on a pull request, a GHI or an approval-walk item, or that it enabled, are pointed out once it is completed: "It only matters if they're complete ... At item 6.2 of the same approval-walk he decided that the work goes in this GHI instead, in two phases: phase 1 for tasks on the agent-seat's own list, then phase 2 for the rest.

### Phase 1: tasks on the agent-seat's own list

Phase 1 is done: pull request [Due-task hook: after each TaskCreate, tell the agent how to record what the task waits on](https://github.com/nedschorus/nedschorus/pull/1914) built it and merged on 2026-10-24. A PostToolUse hook on TaskCreate, `scripts/agent-seat-due-task-prerequisites-recording-reminder-after-task-create-hook.py`, tells the agent to record what the new task waits on: a pull request or a GHI in `metadata.waits_on`, since renamed `prerequisites`, and a task on its own list with TaskUpdate's `addBlockedBy`. The idle check, `scripts/agent-seat-due-task-raise-hook.py`, now also raises, once, an open task with no `prerequisites` whose `blockedBy` tasks all exist and have completed, as § What to build, item 1, says.

### Phase 2: approval-walk items, other agent-seats' tasks, telling what waits on a finished task, and prerequisites that will never be met

Phase 2 starts now that phase 1 is done.

#### What already covers part of the request

- Phase 1 covers a pull request merging, a GHI closing and a task on the agent-seat's own list completing, raised by the idle check as § What to build, item 1, says. Phase 2 does not propose them again. Before phase 1 they went unused: on 2026-10-24, none of the 710 task files on ned-box (`grep -l '"waits_on"' ~/.claude/tasks/*/*.json`) and none of the 261 Mac task files in the log-store's copy (`grep -l '"waits_on"' /home/nedlern/nedschorus-logs/agent-session-files-by-machine/mac/tasks/*/*.json`) carried `waits_on`.
- The idle check reads only its own agent-seat's task list, named by the environment variable `CLAUDE_CODE_TASK_LIST_ID`, so `blockedBy` and `waits_on` can name nothing on another agent-seat's list.
- Each machine keeps its own task lists, at `~/.claude/tasks/nedschorus-<agent-seat>-tasks/<id>.json`. `scripts/transcript-mirror-to-log-store.py` copies both machines' lists into the log-store every minute, under `/home/nedlern/nedschorus-logs/agent-session-files-by-machine/mac/tasks/` and `.../ned-box/tasks/`, so a program on ned-box can read every agent-seat's tasks, one minute late. The copies are never written back.
- How a finding reaches another agent-seat is already decided, in GHI [Nudge the author of a pull request whose review findings have gone unanswered for hours](https://github.com/nedschorus/nedschorus/issues/1203), § "How the nudge works" (user-rulings of 2026-10-14 and 2026-10-15): a busy agent-seat is told by a Stop hook in its own agent-session, as the idle check tells it; an idle one by a cross-session message, with a test that a running agent-session received it; nothing types into its tmux window; when the agent-seat cannot be reached, or runs on the Mac, the user is told. GHI [Seat mailboxes across machines and runtimes](https://github.com/nedschorus/nedschorus/issues/749) and GHI [Cross-session messages between agent-seats reach stale offline Remote Control entries instead of the live agent-session](https://github.com/nedschorus/nedschorus/issues/1115) record the limits of cross-session messages. This section reuses that delivery and decides nothing new about it.

#### What to add

Each new `prerequisites` kind's key names are chosen in the pull request that builds it, and that pull request adds the kind to phase 1's TaskCreate hook text, which otherwise tells agents to record no other kind.

1. **An approval-walk item as a condition.** A new `prerequisites` kind names an approval-walk and an item number, and is met when the walk-minutes record the user's answer to that item. The answer is written by the `close` step of `nc-systems/skills/walk-me-through/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close.py`, which knows the approval-walk's name, the item and the answer. The walk-minutes of an approval-walk still running sit untracked in the checkout of the agent-seat that runs it, and on 2026-10-24 the log-store's `walk/` directory held no copy of the walk-minutes of prime-intellect-open-decisions-for-the-user-2026-10-22-2 (`ls /home/nedlern/nedschorus-logs/walk | grep 2026-10-22-2` printed nothing), so another agent-seat, or the other machine, cannot read the answer there yet.
2. **A task on another agent-seat's list as a condition.** A new `prerequisites` kind names an agent-seat and a task id, and is met when that task is completed. The task may be on either machine; the log-store's copies make both readable from ned-box.
3. **Telling what waits on a finished task.** A task can record what waits on it: a pull request, a GHI, an approval-walk item, or a task on another agent-seat's list. When the task is completed, the agent-seat responsible for the waiting thing is told, by the delivery above: the author agent-seat of the pull request, the agent-seat that runs the approval-walk, or the agent-seat whose task waits. Today `blocks` names only tasks on the same list, and nothing tells anyone else.
4. **Prerequisites that will never be met.** A task now waits in silence, for good, when its prerequisite is cancelled rather than finished: a pull request closed without merging never meets `pr_merged`; an approval-walk item the user disapproved or deferred out of the approval-walk would never meet item 1's condition; a task on another agent-seat's list that was deleted would never meet item 2's condition; and a `blockedBy` task that was deleted stops holding the task, by the idle check's design, so a task that also has `prerequisites` is raised as if its blocker were done, a task with neither is never raised, and in both cases nothing says the blocker was deleted. In each case the waiting task's agent-seat is told, by the delivery above, that the prerequisite was cancelled, naming it, so the agent re-plans the task. A GHI closed as not planned meets `issue_closed` today, the same as one closed as completed, because the idle check compares only the GHI's state with CLOSED.
5. **Further improvements** the user adds go in § Provisional additions until he vets them.

#### Open questions for the user

1. **Where item 3 is recorded.** `waits_on` holds only what a task waits on. Does what waits on a task get a `metadata` field of its own, or is it derived by reading every other `prerequisites` list that names the task, which works only for things that have task lists? And which agent-seat is told when the waiting thing is a GHI, since a GHI names no agent-seat?
2. **Who looks.** Either each agent-seat's idle check reads the other lists it needs, from the log-store's copies, at the end of each turn; or one program on ned-box reads every list and tells each agent-seat, which is the idle sweep of § What to build, item 3; or the program that finishes the thing, such as the merge program `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py` or the approval-walk's `close` step, tells the waiting agent-seats at once. The third catches nothing finished outside those programs, such as a GHI closed in the GitHub web page or a pull request closed there.
3. **How the approval-walk answer is published.** For item 1 to work across agent-seats and machines, the `close` step could write a record of each answer to the log-store at once, or the walk-minutes could be shipped to the log-store after each answer. Which one?
4. **How a Mac agent-seat is told.** A program on ned-box can read the Mac's lists but has no agreed route into a Mac agent-session; GHI 1203 tells the user in that case. Is that right here too, or does each Mac agent-seat's own idle check do the reading?
5. **Which cancellations count.** Is a GHI closed as not planned a cancelled prerequisite under item 4, or met, as today? Is an approval-walk item deferred once still waiting, or cancelled? When one of a task's several `prerequisites` is cancelled, is the agent-seat told at once, or only once the others hold?
