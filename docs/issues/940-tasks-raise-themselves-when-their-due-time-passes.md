# Tasks raise themselves when their due time passes or their prerequisite is met

## Why

An agent often promises to act later: "I'll report when PR 927 merges", "I'll hold until the review is in". A promise backed only by a task on the agent-seat's task list still depends on the agent remembering to look at the list at the right moment, and nothing makes it look. Over 30 days of agent messages to the user, measured for GHI [A project style guide: words to avoid, a mechanical checker, and a check on unbacked promises](https://github.com/nedschorus/nedschorus/issues/14), 592 first-person promises were found and only 47.0% were backed by a task, a reminder or a background job in the same response. A memory is no backing either: nothing forces an agent to read one.

A rule holds when something fires at the moment the rule applies. This issue gives a task that something: a due time or a prerequisite that a program checks, and two checkers that raise the task to its agent-seat when the time passes or the prerequisite is met. To raise a task is to put it in front of its agent with the reason, so the agent acts on it now. The user approved this design on 2026-10-02.

## What to build

1. **Two optional fields in a task's `metadata`.** Every agent-seat's tasks are JSON files `~/.claude/tasks/nedschorus-<seat name>-tasks/<id>.json`, and a task may carry a `metadata` object; 57 of the 1,065 task files on the user's Mac carried one on 2026-10-02. Claude Code's TaskCreate and TaskUpdate tools both take a `metadata` argument, so an agent sets these fields with the task tools, never by editing the files. A task may carry either field, both, or neither:
   - `due_utc`: an ISO 8601 time in UTC from which the task should be started, or looked at again.
   - `waits_on`: a list of conditions a program can check, all of which must hold. The first two kinds are `{"pr_merged": <pull request number>}` and `{"issue_closed": <issue number>}`, both in the repository nedschorus/nedschorus. A prerequisite on another task stays in the task's existing `blockedBy` field.

   A task is raised when its due time has passed, or when its `waits_on` conditions all hold; a task carrying both is raised when both hold, and once at its due time if a condition still does not hold, naming that condition, so its agent can chase it. A task whose `blockedBy` tasks are still open is not raised. A task with neither field, but with `blockedBy` tasks that have all completed, is raised once. A task with neither field and no such `blockedBy` is a plain task, reviewed by the periodic approval-walks that put an agent-seat's open items to the user, as now.

2. **The idle check, built first.** A Stop hook runs at the end of each of the agent's turns, reads the agent-seat's own task list, and raises every open task that is due, so the agent acts on the task before it goes idle. Claude Code lets a Stop hook refuse the stop with a reason; the reason names each raised task and why, and the agent's turn continues.
   - Due times are read from the task files, with no network call, so the check costs nothing on most turns.
   - Conditions that need a network call, such as whether a pull request merged, are checked at most once every few minutes, each with a short timeout; between checks, the last answer stands.
   - The hook records what it raised, and when it last made each network check, in a state file of its own for the agent-seat. A task is raised once for its due time and once when its conditions come to hold, so the hook cannot keep the agent from stopping turn after turn; a raised task the agent leaves open is raised again only by its next due time.
   - Every fault is silence: a hook error never stops the agent's turn from ending.

3. **The hourly sweep.** A scheduled job, installed through `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` like the jobs already there, runs on each machine, reads the task lists of the agent-seats on that machine, and checks due times and `waits_on` conditions as the idle check does. Its purpose is the agent-seat that is idle, which the idle check cannot reach because an idle agent ends no turns. Two questions are open: how the job tells that an agent-seat is idle, and how it reaches an idle agent-seat. The handoff-supervisor launches agent-sessions but does not type into a running one, and `scripts/synthetic-keystroke-guard-hook.py` refuses synthetic keystrokes, so no route exists yet.

GHI 14's promise check, its item 3, is narrowed to depend on this issue in an edit of the same day: a promise passes when the same turn created or updated a task with a due time or a checkable prerequisite.

GHI [Relaunch stopped agent-seats with open tasks daily](https://github.com/nedschorus/nedschorus/issues/936) also reads agent-seat task lists on a schedule, to relaunch agent-seats that stopped; the hourly sweep and that issue's job may share one reader of the task files.

### Phase 2: approval-walk items, other agent-seats' tasks, telling what waits on a finished task, and prerequisites that will never be met

Phase 2 starts now that phase 1 is done.

#### What already covers part of the request

- Phase 1 covers a pull request merging, a GHI closing and a task on the agent-seat's own list completing, raised by the idle check as § What to build, item 1, says. Phase 2 does not propose them again. Before phase 1 they went unused: on 2026-10-24, none of the 710 task files on ned-box (`grep -l '"waits_on"' ~/.claude/tasks/*/*.json`) and none of the 261 Mac task files in the log-store's copy (`grep -l '"waits_on"' /home/nedlern/nedschorus-logs/agent-session-files-by-machine/mac/tasks/*/*.json`) carried `waits_on`.
- The idle check reads only its own agent-seat's task list, named by the environment variable `CLAUDE_CODE_TASK_LIST_ID`, so `blockedBy` and `waits_on` can name nothing on another agent-seat's list.
- Each machine keeps its own task lists, at `~/.claude/tasks/nedschorus-<agent-seat>-tasks/<id>.json`. `scripts/transcript-mirror-to-log-store.py` copies both machines' lists into the log-store every minute, under `/home/nedlern/nedschorus-logs/agent-session-files-by-machine/mac/tasks/` and `.../ned-box/tasks/`, so a program on ned-box can read every agent-seat's tasks, one minute late. The copies are never written back.
- How a finding reaches another agent-seat is already decided, in GHI [Nudge the author of a pull request whose review findings have gone unanswered for hours](https://github.com/nedschorus/nedschorus/issues/1203), § "How the nudge works" (user-rulings of 2026-10-14 and 2026-10-15): a busy agent-seat is told by a Stop hook in its own agent-session, as the idle check tells it; an idle one by a cross-session message, with a test that a running agent-session received it; nothing types into its tmux window; when the agent-seat cannot be reached, or runs on the Mac, the user is told. GHI [Seat mailboxes across machines and runtimes](https://github.com/nedschorus/nedschorus/issues/749) and GHI [Cross-session messages between agent-seats reach stale offline Remote Control entries instead of the live agent-session](https://github.com/nedschorus/nedschorus/issues/1115) record the limits of cross-session messages. This section reuses that delivery and decides nothing new about it.

#### What to add

Each new `waits_on` kind's key names are chosen in the pull request that builds it, and that pull request adds the kind to phase 1's TaskCreate hook text, which otherwise tells agents to record no other kind.

1. **An approval-walk item as a condition.** A new `waits_on` kind names an approval-walk and an item number, and is met when the walk-minutes record the user's answer to that item. The answer is written by the `close` step of `nc-systems/skills/walk-me-through/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close.py`, which knows the approval-walk's name, the item and the answer. The walk-minutes of an approval-walk still running sit untracked in the checkout of the agent-seat that runs it, and on 2026-10-24 the log-store's `walk/` directory held no copy of the walk-minutes of prime-intellect-open-decisions-for-the-user-2026-10-22-2 (`ls /home/nedlern/nedschorus-logs/walk | grep 2026-10-22-2` printed nothing), so another agent-seat, or the other machine, cannot read the answer there yet.
2. **A task on another agent-seat's list as a condition.** A new `waits_on` kind names an agent-seat and a task id, and is met when that task is completed. The task may be on either machine; the log-store's copies make both readable from ned-box.
3. **Telling what waits on a finished task.** A task can record what waits on it: a pull request, a GHI, an approval-walk item, or a task on another agent-seat's list. When the task is completed, the agent-seat responsible for the waiting thing is told, by the delivery above: the author agent-seat of the pull request, the agent-seat that runs the approval-walk, or the agent-seat whose task waits. Today `blocks` names only tasks on the same list, and nothing tells anyone else.
4. **Prerequisites that will never be met.** A task now waits in silence, for good, when its prerequisite is cancelled rather than finished: a pull request closed without merging never meets `pr_merged`; an approval-walk item the user disapproved or deferred out of the approval-walk would never meet item 1's condition; a task on another agent-seat's list that was deleted would never meet item 2's condition; and a `blockedBy` task that was deleted stops holding the task, by the idle check's design, so a task that also has a due time or a `waits_on` is raised as if its blocker were done, a task with neither is never raised, and in both cases nothing says the blocker was deleted. In each case the waiting task's agent-seat is told, by the delivery above, that the prerequisite was cancelled, naming it, so the agent re-plans the task. A GHI closed as not planned meets `issue_closed` today, the same as one closed as completed, because the idle check compares only the GHI's state with CLOSED.
5. **Further improvements** the user adds go in § Provisional additions until he vets them.

#### Open questions for the user

1. **Where item 3 is recorded.** `waits_on` holds only what a task waits on. Does what waits on a task get a `metadata` field of its own, or is it derived by reading every other `waits_on` that names the task, which works only for things that have task lists? And which agent-seat is told when the waiting thing is a GHI, since a GHI names no agent-seat?
2. **Who looks.** Either each agent-seat's idle check reads the other lists it needs, from the log-store's copies, at the end of each turn; or one program on ned-box reads every list and tells each agent-seat, which is the hourly sweep of § What to build, item 3; or the program that finishes the thing, such as the merge program `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py` or the approval-walk's `close` step, tells the waiting agent-seats at once. The third catches nothing finished outside those programs, such as a GHI closed in the GitHub web page or a pull request closed there.
3. **How the approval-walk answer is published.** For item 1 to work across agent-seats and machines, the `close` step could write a record of each answer to the log-store at once, or the walk-minutes could be shipped to the log-store after each answer. Which one?
4. **How a Mac agent-seat is told.** A program on ned-box can read the Mac's lists but has no agreed route into a Mac agent-session; GHI 1203 tells the user in that case. Is that right here too, or does each Mac agent-seat's own idle check do the reading?
5. **Which cancellations count.** Is a GHI closed as not planned a cancelled prerequisite under item 4, or met, as today? Is an approval-walk item deferred once still waiting, or cancelled? When one of a task's several `waits_on` conditions is cancelled, is the agent-seat told at once, or only once the others hold?
