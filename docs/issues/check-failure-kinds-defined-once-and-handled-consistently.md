# One shared list of the kinds of check failure, used by reviewers, authors and test writers, and a daily check that each kind is handled the same way

The user asked for this GHI on 2026-10-18, in item 19 of the approval-walk `md-skills-seat-open-decisions-2026-10-15`, after two independent searches found that a failing check can mean several different things and that agents handle each one differently. The walk-minutes record his request: `nedlern@ned-box:/home/nedlern/nedsnodes-logs/walk/md-skills-seat-open-decisions-2026-10-15-minutes.md`, the bullets dated 2026-10-18.

## The problem

The project's checks are its nc-test-suites, the pull request reviewers, the merge gate, merge-lane-2's head test run, the guard hooks, the git client-side hooks, the cold-read grid, `scripts/branch-conflict-check.py`, the canary tests, and the prerequisite checks that GHI [Check every prerequisite of the fleet's programs before an agent-session starts](https://github.com/nedschorus/nedschorus/issues/1055) plans. Their outcomes are not just pass or fail. Between them they produce nine kinds of non-pass outcome, listed below. Some kinds now have a definition in one place, as the section "What other GHIs and pages already define" says, but nothing defines them as a set, names the cases no page covers, such as a test already failing on main or a test that fails at random, or checks that agents handle each kind the same way.

The evidence is in four reports, two by Codex and two by Claude subagents, which searched independently, and in their combined summary, all in `nedlern@ned-box:/home/nedlern/nedsnodes-logs/analysis/canary-cases-and-failure-kinds-2026-10-18/` (`summary.md`, `failure-kinds-codex.md`, `failure-kinds-claude.md`, `canary-trawl-codex.md`, `canary-trawl-claude.md`). The cases below come from them; each was checked again on 2026-11-20.

**The same kind handled differently.**
- A test already failing on main was ignored, merged over, rerun, filed as a GHI or fixed at the root, depending on the agent. On 2026-10-14 the test `scripts/run-codex-task-from-brief-test.py` got three of those handlings from three agent-seats; merge-lane-2 then filed GHI [The Codex task runner's deadline test case fails on a busy machine, because a scan of the whole home directory runs before the deadline starts](https://github.com/nedschorus/nedschorus/issues/1323).
- A Mac test case noted as "also fails on main" was pushed over in four pull requests, starting with PR [Claude Code Bash hook: remind the agent to run both citation checks when a git push sends a branch that changes a Markdown file](https://github.com/nedschorus/nedschorus/pull/1354), and fixed only in PR [Bash guards replay: a checkout named through a symlink is removed by git, not deleted as unregistered](https://github.com/nedschorus/nedschorus/pull/1452).
- A failure called "a flake" in PR [handoff dialog: each subagent's task and report as a third voice; ned-box keeps every session's complete dialog current in the log-store](https://github.com/nedschorus/nedschorus/pull/1188) was a deterministic defect, GHI [The signal sandbox test's fake bwrap fails when its status descriptor number is 10 or more, so the test fails at random](https://github.com/nedschorus/nedschorus/issues/1233), which had held six unrelated pull requests.
- Non-blocking findings sometimes got a follow-up pull request or a written decline, as in PR [Fast-read reminder: the marked-as-read note and stderr line say only what is true, mutant M6 is killed, and every registered hook's constants are scanned for citations](https://github.com/nedschorus/nedschorus/pull/1593), and sometimes nothing visible, as in PR [run-all-test-suites.py: kill a suite past a time limit sized from its recorded duration](https://github.com/nedschorus/nedschorus/pull/1560).
- Two reviewers gave the same finding different merge consequences in PR [The cold-read-cells read the frozen copy, which is what freezing meant](https://github.com/nedschorus/nedschorus/pull/636).

**The same kind called by different words.**
- A finding that need not be fixed before the merge was called "advice", "does not block", "non-blocking finding", "follow-up" and "findings that do not block". The four finding categories of GHI 2522, below, now give it one set of names.
- "Could not answer" and "no" are kept apart by `scripts/run-all-test-suites.py` (its `NOT RUN` line, and exit 2 against exit 1) and by the cold-read grid ("a run that produced no report is not a review that found nothing"), but the docstring of `nn-systems/handoff/uncommitted-work-snapshot-hook-scheduled-check-that-real-claude-session-is-recorded-as-owner.py` says that a lapsed claude login or a network outage "is a failed check", and the program writes it as `VERDICT: FAILED`.
- `docs/nedsnodes-wiki/nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md`, in its bullet "When the program fails open", requires a program that lets an act through unchecked to say that the act was not checked; the failure-kinds reports found guard hooks that fail open silently on bad input.

**Why it matters.** When the kinds are not defined as a set, an agent decides each case alone, from its own reading. A real defect labelled "flaky" stays unfixed and holds other pull requests; a "could not answer" read as a pass merges unchecked work; a non-blocking finding with no follow-up is lost. The user cannot see from the records which of these happened.

## What other GHIs and pages already define

This GHI does not define again what these define; its list points to them and adds only the kinds and the handling they leave out.
- `docs/nedsnodes-wiki/nedsnodes-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md` sets what a program's exit code means: 0 yes, 1 no, 2 could not answer, and, in its section "Hooks", what a Claude Code hook and a git hook do when a check could not answer. GHI [Bring every program, test, help text and unbuilt design into line with the wiki page on how a program reports success, failure and findings with its exit code](https://github.com/nedschorus/nedschorus/issues/2476) brings every program into line with it. That GHI changes what each program exits with; this GHI says what an agent does with each kind of outcome, across programs, reviews and test runs, and checks that it was done.
- Section 2 of `docs/nedsnodes-wiki/queue/nedsnodes-goals-and-philosophy-founding-statement-and-agent-working-principles.md`, a page in the wiki queue not yet approved, puts every finding in one of four categories, by when it is fixed: must fix now, fix next, fix during maintenance, and file an improvement, a feature or a change. GHI [Implementing the project's goals and philosophy: every finding sorted into four categories, checked claims kept with their evidence, and one standard in every agent's instructions](https://github.com/nedschorus/nedschorus/issues/2522) carries that work, and `docs/agents/pr-reviewer-instructions.md` already has merge-lane-2 give each review finding one of the four categories. The categories say when a finding is fixed; this GHI's kinds say what a non-pass outcome is, such as a defect of the change, a failure already on main or a check that could not answer. A kind and a category answer different questions, and a finding has one of each.
- GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) defines how a skipped test case is printed and reported. `scripts/test-suites-source-scan-for-skipped-case-prints-run-all-test-suites-cannot-count-test.py` already fails when an nc-test-suite prints a skip the test runner cannot count.
- GHI [A test result relayed from one agent-seat to another without its exit code can hide a crash as a pass](https://github.com/nedschorus/nedschorus/issues/1235) is one case of kind 4 below read as a pass; it is fixed under its own GHI.
- GHI [Every refusal and warning a program hands an agent says why and what to do instead](https://github.com/nedschorus/nedschorus/issues/956) covers the wording of a program's message; this GHI covers only which kind each outcome is.

## The proposed list of kinds

The kind names below are plain prose; only the two under Proposed terms are proposed as project-terms. "Decides" names who or what sets the kind for a given case. Where a page above already defines a kind, its row points there. A finding of kind 1 also gets a finding category, which says when it is fixed; the other kinds are outcomes that are not findings about the change.

| # | Kind | Definition | Leads to | Decides |
|---|---|---|---|---|
| 1 | Finding about the change | The check ran and found a real problem in this change: a defect it introduces, or an improvement it should make. A test that fails on the head, passes on main and fails again on a rerun of the head is a kind 1 finding. | The finding category merge-lane-2 gives it, as section 2 of the goals and philosophy page defines. A must-fix-now finding is fixed before the merge. A finding in category 2, 3 or 4 gets the follow-up pull request, task or GHI its category names, or a leave-out reason recorded with `scripts/pull-request-follow-up-request-after-merge-finding-answers-and-next-step.py`'s `record-finding-leave-out-reason`. | The reviewer or the check reports it; merge-lane-2 gives it its category. |
| 2 | Already failing on main | The same test fails on main without this change. | Never merged over; cleared by a separate pull request that fixes, deletes or skips the test, with a GHI tracking it. | Code, from the head test run's record compared with the daily full test run of main: failing on main too is kind 2. merge-lane-2 decides only a case the records do not settle. |
| 3 | Fails at random | The check fails, then passes on one rerun of the same commit, and passed on main. | The failing log is cited in a pull request comment; the pull request may merge on the passing rerun; a GHI at the second sighting. Never put down to machine load without evidence: two failures so labelled were real defects. | Code, from the same records and the rerun; merge-lane-2 runs the one rerun. `scripts/run-all-test-suites.py` adds every failing test case to `test-case-failure-history.jsonl`, in its `--recorded-inputs-directory`, by default `~/.cache/nedsnodes-test-suite-recorded-inputs/` on the machine that ran it; the runner prints a second sighting when it records one, and whoever runs it files the GHI. |
| 4 | Could not answer | Exit 2, as the exit-code page defines it; for an nc-test-suite, also the test runner's `NOT RUN`. | Never a pass; the cause named; a cause the user can clear, such as a lapsed login or a usage limit, told to the user. Whether the pull request may merge with the gap named is open question 1. | The check's exit code, or the test runner's `NOT RUN` line. |
| 5 | Let through unchecked | A hook whose check could not answer let the act go ahead, as the exit-code page's section "Hooks" allows. | The program says so where the agent will see it, as the tool-message page's bullet "When the program fails open" requires. | The program's author, at build time; what the agent then does is open question 5. |
| 6 | Skipped | A test case chose not to run, as GHI 1206 defines. | Printed and reported as GHI 1206 plans; whether a skip holds a merge is GHI 1206's to settle. | The test writer. |
| 7 | Question | A matter for a decision, not a defect. | Answered before the merge. | The reviewer raises it; where it goes is open question 3. |
| 8 | False alarm | The finding does not hold. | The author says why in a reply on the finding; when the check is a program, its cause is fixed so it does not recur. | The author answers; merge-lane-2 accepts or rejects the answer. |
| 9 | Outside program changed | A program the project calls but does not write behaved differently from what the code assumes, now or after an upgrade. | A fix whose description has a `#root_cause` line naming the outside program, and a canary test where the canary design asks for one. | Open question 6. |

The canary design, `docs/drafts/canary-tests-when-required-who-runs-them-and-where-they-live-design-draft.md` on branch `canary-tests-when-required-who-runs-them-and-where-they-live-design-topic-branch`, not yet on main, splits kinds 4 and 9 further for canary tests (wrong only on the other machine, wrong only after an upgrade or at a reboot, a false pass from probing the wrong command), using this list's names.

## Where the list lives

One wiki page holds the table above with one real example of each kind, and points to the pages above for the kinds they define. Its proposed name, `docs/nedsnodes-wiki/nedsnodes-kinds-of-check-failure.md`, is still to be checked against `docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md`. The kinds' names are also kept once as data, a file or a constant that the programs below read, and an nc-test-suite test fails when the page's table and that data differ. Each proposed term the user approves gets a project glossary entry pointing to the page. The page also lists the words the evidence above found used for a kind, such as "flake", "flaky", "advice", "does not block" and "non-blocking finding", which an nc-test-suite test refuses in an instruction file.

## Which files must use the list

- `docs/agents/pr-reviewer-instructions.md`: a reviewer names the kind of each finding; merge-lane-2 gives its category afterwards, as today.
- `.claude/skills/pull-request-review-write/SKILL.md` and `scripts/merge-lane-pull-request-reviewer-review-post-and-read-back.py`: the kind is a field of each review comment beside `finding_category`, and the program refuses a value not in the list, as it already refuses a category not in `FINDING_CATEGORIES`.
- `scripts/run-all-test-suites.py` and `scripts/scheduled-full-test-run-of-main.py`: their summary lines name kind 4, and kinds 2 and 3 from the comparison the table gives, where a run's records can tell them; the runner prints a second sighting of a failing test case.
- `nn-systems/handoff/uncommitted-work-snapshot-hook-scheduled-check-that-real-claude-session-is-recorded-as-owner.py`: it reports a lapsed login or a network outage as kind 4, not as a failed check. Its exit code changes under GHI 2476; this GHI changes only what the record calls the outcome.
- The guard hooks that fail open silently: they say so (kind 5), and the message gives the command that runs the check by hand. An nc-test-suite test sends malformed input to every registered guard hook and fails on one that lets the act through without saying so.
- merge-lane-2's seat-brief, which is outside the repository: whoever merges the wiki page sends merge-lane-2 the page's path, and merge-lane-2 updates its seat-brief itself.

## The consistency check

A daily maintenance-job among those of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058). It reads the pull requests merged since its last run (descriptions, reviews, comments), the head test run records and daily full test run records in the log-store, and `test-case-failure-history.jsonl`. When GHI [Pull requests, their reviews and approval-walks held as one state machine over one schema and one store, so code tracks their state and agents are handed only the steps that need judgment](https://github.com/nedschorus/nedschorus/issues/2505) is built, it reads that store instead of the pull requests' text. What the merge gate can see before a merge it checks there instead, as it already checks the `#root_cause` line: a kind 2 failure with no GHI or separate pull request named, and a kind 4 `NOT RUN` line or exit 2 in the head test run's record that merge-lane-2's approving review does not name. The daily check reports to the user, and to merge-lane-2, what got past or cannot be seen at the merge, each case where:
- a test failing on a pull request's head also failed on main that day, and the pull request merged without a GHI or a separate pull request for it (kind 2);
- the same test failed on two pull requests' heads, or failed and then passed on one commit, with no GHI after the second sighting (kind 3);
- a kind 1 finding in category 2, 3 or 4 has, after the grace period of open question 4, no later pull request citing it, no task or GHI holding it, and no recorded leave-out reason;
- a "Not checked", "not run" or "Codex review not run" line in a pull request is not named in merge-lane-2's approving review (kind 4);
- an instruction file uses a word for a kind that the wiki page does not list.

It would have caught the already-failing-on-main, fails-at-random and non-blocking-finding cases above. It cannot judge false alarms or outside-program changes; for those it checks only that a finding left unfixed has a reply, or a `False alarm:` or `Outside program changed:` line in the description, and merge-lane-2 judges the content. The steps that need judgment are: a reviewer naming a finding's kind, merge-lane-2 giving its category, merge-lane-2 judging a false alarm or an outside-program change, and a case of kind 2 or 3 the records do not settle. Everything else, the consistency check and the merge gate's checks included, is code.

## Proposed terms

Each stays plain prose until the user approves it; approved, it takes the hyphenated form.
- check failure kind: one of the nine kinds of non-pass outcome listed in this GHI, each with a defined consequence.
- already failing on main: a failure that also happens on main without the change under test.
