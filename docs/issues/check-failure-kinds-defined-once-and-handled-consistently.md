# One shared list of the kinds of check failure, used by reviewers, authors and test writers, and a daily check that each kind is handled the same way

The user asked for this GHI on 2026-10-18, in item 19 of the approval-walk `md-skills-seat-open-decisions-2026-10-15`, after two pairs of independent searches found that a failing check can mean several different things and that agents handle each one differently. The walk-minutes record his request: `nedlern@ned-box:/home/nedlern/nedsnodes-logs/walk/md-skills-seat-open-decisions-2026-10-15-minutes.md`, the bullets dated 2026-10-18. The title keeps the words of his request, "kinds of check failure"; some kinds below, such as a question or a skipped test case, are not failures but are handled in the same list.

## The problem

The project's checks include its nc-test-suites, the pull request reviewers, the merge gate `scripts/merge-gate.sh`, the head test run, the guard hooks, the git client-side hooks, the cold-read grid, `scripts/branch-conflict-check.py`, the canary tests, and the prerequisite checks that GHI [Check every prerequisite of the fleet's programs before an agent-session starts](https://github.com/nedschorus/nedschorus/issues/1055) plans. The head test run is the run, by `scripts/merge-lane-pull-request-head-test-run-on-merged-worktree.py` and `scripts/pull-request-head-test-run.py`, of the nc-test-suites a pull request's change selects, other than those that run the real claude program, on its nc-head-commit merged onto main. A canary test runs a real outside program, such as Codex or git, to check that a behaviour the project's code relies on is still there; when one is required is proposed by the canary design, a draft not yet on main, named under Deferred-decisions.

A check that answers no on purpose, such as a guard hook refusing an act, `scripts/branch-conflict-check.py` finding a conflict or a scheduled check reporting what it found, is the check working: the agent does what its tool-message-to-agent says. This GHI adds to that only where the no is about a pull request's change (kind 1 below) or does not hold (kind 8). All the outcomes it handles are listed below: eight kinds of outcome other than a pass, and one kind of cause. Some already have a definition in one place, as the section "What other GHIs and pages already define" says, but nothing defines them as a set, names the cases no page covers, such as a test case already failing on main or a flaky test, or checks that agents handle each kind the same way.

The evidence is in four reports, two by Codex and two by Claude subagents, which searched in two independent pairs, and in their combined summary, all in `nedlern@ned-box:/home/nedlern/nedsnodes-logs/analysis/canary-cases-and-failure-kinds-2026-10-18/` (`summary.md`, `failure-kinds-codex.md`, `failure-kinds-claude.md`, `canary-trawl-codex.md`, `canary-trawl-claude.md`). The cases below come from them.

**The same kind handled differently.**
- A test said to be already failing on main was ignored, merged over, rerun, filed as a GHI or fixed at the root, depending on the agent. On 2026-10-14 the nc-test-suite `scripts/run-codex-task-from-brief-test.py`, which one agent-seat called "already fails on main", got three different handlings from three agent-seats: one moved on, one fixed it at the root, and merge-lane-2 filed GHI [The Codex task runner's deadline test case fails on a busy machine, because a scan of the whole home directory runs before the deadline starts](https://github.com/nedschorus/nedschorus/issues/1323).
- A Mac test case noted as "also fails on main" was left failing by four pull requests, starting with PR [Claude Code Bash hook: remind the agent to run both citation checks when a git push sends a branch that changes a Markdown file](https://github.com/nedschorus/nedschorus/pull/1354), and fixed only in PR [Bash guards replay: a checkout named through a symlink is removed by git, not deleted as unregistered](https://github.com/nedschorus/nedschorus/pull/1452).
- A failure called "a flake, not caused by this pull request" in PR [handoff dialog: each subagent's task and report as a third voice; ned-box keeps every session's complete dialog current in the log-store](https://github.com/nedschorus/nedschorus/pull/1188) was not filed then. It was a defect in the test, filed later, after more sightings, as GHI [The signal sandbox test's fake bwrap fails when its status descriptor number is 10 or more, so the test fails at random](https://github.com/nedschorus/nedschorus/issues/1233), whose GHI-MD lists the head test runs of nine pull requests it failed.
- Non-blocking findings sometimes got a follow-up pull request or a written decline, as in PR [Fast-read reminder: the marked-as-read note and stderr line say only what is true, mutant M6 is killed, and every registered hook's constants are scanned for citations](https://github.com/nedschorus/nedschorus/pull/1593); `failure-kinds-claude.md`, written on 2026-10-18, found no later pull request citing those of PR [run-all-test-suites.py: kill a suite past a time limit sized from its recorded duration](https://github.com/nedschorus/nedschorus/pull/1560).
- Two reviewers gave the same finding different merge consequences in PR [The cold-read-cells read the frozen copy, which is what freezing meant](https://github.com/nedschorus/nedschorus/pull/636).

**The same kind called by different words.**
- A finding that need not be fixed before the merge was called "advice", "does not block", "non-blocking finding", "follow-up" and "findings that do not block". The four finding categories of GHI 2522, below, now give it one set of names.
- "Could not answer" and "no" are kept apart by `scripts/run-all-test-suites.py` (its `NOT RUN` line) and by the cold-read grid ("a run that produced no report is not a review that found nothing"), but the docstring of `nn-systems/handoff/uncommitted-work-snapshot-hook-scheduled-check-that-real-claude-session-is-recorded-as-owner.py`, the owner check, says that a lapsed claude login or a network outage "is a failed check", and the program writes it as `VERDICT: FAILED`.
- `docs/nedsnodes-wiki/nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md`, the tool-message page, in its bullet "When the program fails open", requires a program that detects that it could not run its check and lets the act through to say that the act was not checked and what the agent does about it; the failure-kinds reports found guard hooks that fail open silently on malformed input.

**Why it matters.** When the kinds are not defined as a set, an agent decides each case alone, from its own reading. A failure put down to chance and filed nowhere stays unfixed and keeps other pull requests from merging; a "could not answer" read as a pass merges unchecked work; a non-blocking finding with no follow-up is lost. No program reports to the user how each of these cases was handled.

## What other GHIs and pages already define

This GHI does not define again what these define. Its list points to them, and it adds the kinds they leave out, the handling of every kind, and a check of the handling.
- `docs/nedsnodes-wiki/nedsnodes-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, the exit-code page, sets what a program's exit code means: 0 yes, 1 no, 2 could not answer, with the different codes of Claude Code hooks and git hooks in its section "Hooks". GHI [Bring every program, test, help text and unbuilt design into line with the wiki page on how a program reports success, failure and findings with its exit code](https://github.com/nedschorus/nedschorus/issues/2476) brings every program's exit code into line with it; this GHI says what an agent does with each kind of outcome.
- Section 2 of `docs/nedsnodes-wiki/queue/nedsnodes-goals-and-philosophy-founding-statement-and-agent-working-principles.md`, the goals and philosophy page, in the wiki queue and not yet approved, puts every finding in one of four numbered categories: 1, must fix now; 2, fix next; 3, fix during maintenance; and 4, file an improvement, a feature or a change. GHI [Implementing the project's goals and philosophy: every finding sorted into four categories, checked claims kept with their evidence, and one standard in every agent's instructions](https://github.com/nedschorus/nedschorus/issues/2522) carries that work, and `docs/agents/pr-reviewer-instructions.md` already has merge-lane-2 give each review finding one of the four categories. A category says what is done with a finding and by when; a kind says what an outcome is. This GHI gives a category to the outcomes the table below calls findings; the others are handled as their rows say.
- GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) defines how a skipped test case is printed and reported. `scripts/test-suites-source-scan-for-skipped-case-prints-run-all-test-suites-cannot-count-test.py` already fails when an nc-test-suite prints a skip the test runner cannot count.
- GHI [Two test cases that fail on a busy machine and pass on rerun: a stop while the last cell saves its report, and a stop while a relaunch is prepared](https://github.com/nedschorus/nedschorus/issues/1112), closed, was filed for two test cases that failed in head test runs and passed on rerun; this GHI makes such a filing the rule at the second sighting.
- GHI [A test result relayed from one agent-seat to another without its exit code can hide a crash as a pass](https://github.com/nedschorus/nedschorus/issues/1235) records one case of a test file that crashed part-way, which the exit-code page counts as could not answer, relayed as a pass; whether to act on it is that GHI's to decide.
- GHI [Every refusal and warning a program hands an agent says why and what to do instead](https://github.com/nedschorus/nedschorus/issues/956) covers the wording of a tool-message-to-agent.
- GHI [Sanity-check-cells return their reports as a JSON object checked against a schema, so the runner stops guessing from prose whether a text is a report](https://github.com/nedschorus/nedschorus/issues/2007) and GHI [ghi-guide-agent answers with a JSON object checked against a schema, so its callers stop sorting its prose replies](https://github.com/nedschorus/nedschorus/issues/2159) make other agents' replies schema-checked JSON; this GHI does the same for the kind of each review comment, through merge-lane-2's review file, and changes neither.

## The proposed list of kinds

Kind names are plain prose; the numbers below are only this GHI's shorthand. "Decides" names who or what puts a given outcome in its row.

| # | Kind | Definition | Leads to | Decides |
|---|---|---|---|---|
| 1 | Finding about the change | A real problem in a pull request's change: a defect it introduces, or an improvement it should make. For a failing test case, see "How the head test run classifies a failing test case" below. | A finding: merge-lane-2 gives it a category. A failing test case is category 1, must fix now. A finding in category 2, 3 or 4 is followed up as its category says, gets a leave-out reason, or is recorded as waiting for a user-ruling, each with `scripts/pull-request-follow-up-request-after-merge-finding-answers-and-next-step.py`. When merge-lane-2 accepts the author's answer that it is kind 8, it becomes kind 8 and loses its category. | The reviewer or the check reports it; code classifies a failing test case; merge-lane-2 gives the category. |
| 2 | Already failing on main | A test case that fails in the head test run also fails on the main commit that run merged onto, without the change. | The pull request waits, unless the answer to open question 2 lets a passing rerun clear it. merge-lane-2 files a GHI for the test case; whoever takes the GHI opens a separate pull request, whose description names the GHI, that fixes, deletes or skips the test case. After merging that pull request, merge-lane-2's merge program reruns the head test run of each open pull request whose last head test run record shows a kind 2 test case that GHI names. | Code. merge-lane-2 may judge that the change fails the test case in a different way, which makes it kind 1; it records that judgment through the head test run program, which writes it into the record. |
| 3 | Flaky test | A test case that exists on main, passes there, fails in the head test run and passes on one rerun of the same commit. Its cause, in the test, the code it tests, the machine's load or an outside program, is not yet known. | The head test run program posts the failing log's path in a pull request comment, and the pull request may merge on the passing rerun. At the second sighting, the same test case classified this way on a second commit, of any pull request, merge-lane-2 files a GHI to find the cause, and adds each later sighting to that GHI while it is open; a sighting after it closed counts as a first sighting. | Code. merge-lane-2 may judge that the change could have caused it, which makes it kind 1, recorded as for kind 2. |
| 4 | Could not answer | A check reached no answer, or no answer for part of what it was asked, as the exit-code page defines: exit 2 from a program that is not a hook, or a code above 2, which its section "A caller" reads as 2; exit 1 from a Claude Code hook, which its section "Hooks" gives a hook that broke; the test runner's `NOT RUN`; and a reviewer that could not review, such as a Claude reviewer's `COULD_NOT_REVIEW` verdict. A skipped test case is kind 6, not kind 4. | Never a pass for the check; whatever the check did find stands; the cause named; on ned-box, a cause only the user can clear, such as a lapsed login or a usage limit, written as a user-alert. Whether the pull request may merge with the gap named is open question 1. | The check's exit code, verdict or `NOT RUN` line. |
| 5 | Failed open | A hook's kind 4 outcome after which the act went ahead: a git hook after a check's exit 2, a Claude Code hook that exits 0 because the agent's next act depends on the check, or one that broke on an event where Claude Code lets the act go ahead, as the exit-code page's section "Hooks" says. | Kind 4's handling, except that the act has gone ahead. A hook that detects that its check could not run says so where the agent will see it, naming the check, as the tool-message page's bullet "When the program fails open" requires; a hook that broke cannot, and the user sees Claude Code's hook error notice instead, as the exit-code page says. Where the agent is told, the message says what it does, as that bullet requires; whether every such message gives the same instruction is open question 5. | The hook's author, at build time. |
| 6 | Skipped | A test case chose not to run, as GHI 1206 defines. | Printed and reported as GHI 1206 plans. A skip never changes a suite's verdict, as the test runner's docstring says. | The test writer. |
| 7 | Question | A matter for a decision, not a defect; or a suspected defect the reviewer cannot yet state as a finding. | Answered; where it goes, and whether the merge waits for the answer, is open question 3. | The reviewer raises it. |
| 8 | False alarm | A reported finding, or a check's refusal, that does not hold. | In a pull request, the author says why in a reply on the finding or in a pull request comment, and merge-lane-2 accepts or rejects the answer. When the check is a program, the author fixes the cause of this false alarm, in the same pull request or a later one, unless merge-lane-2 accepts that the cause is a pattern the check cannot avoid. Outside a pull request, the agent that met it says so to the agent-seat that owns the check; open question 7 asks about one hook. | The author answers; merge-lane-2 accepts or rejects the answer. |
| 9 | Outside program changed | A cause, not an outcome: a program the project calls but does not write changed its behaviour, such as in an upgrade, so code that matched it no longer does. Code that never matched it is a defect of the code, handled as any other. | The outcome it shows as, of any kind above, is handled as its row says; the head test run program never writes kind 9, which the author argues in a reply. The fix's description also has a `#root_cause` line naming the outside program's change, or, when the project can only work around it, a `#root_cause_not_fixed` line whose `#follow_up` names a GHI that removes the workaround when it can, as `docs/agents/pr-reviewer-instructions.md` defines those lines; and a canary test where the canary design asks for one. | Open question 6. |

**How the head test run classifies a failing test case.** For each nc-test-suite with a failing test case, `scripts/pull-request-head-test-run.py` runs the suite once on the main commit the run merged onto, and once more on the same commit as the head test run. The rules apply in this order. If the test case fails on main, it is kind 2, even when it fails there only at random. If the rerun or the run on main could not answer, it is kind 4. Otherwise, if it fails again on the rerun, or does not exist on main, it is kind 1; if it passes on the rerun and exists on main, it is kind 3. A flaky test case the pull request adds is therefore kind 1, the author's to fix.

## Where the list lives

One wiki page holds the table above, the classification just described, and one real example of each kind, and points to the pages above for the kinds they define. Its proposed name, `docs/nedsnodes-wiki/nedsnodes-kinds-of-check-failure.md`, is still to be checked against `docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md`. The kinds' names are kept once in a data file that every program writing or reading a kind reads, and an nc-test-suite fails when the names in the page's table and in the data file differ.

## Which files must use the list

- `docs/agents/pr-reviewer-instructions.md` and `.claude/skills/pull-request-review-write/SKILL.md`: each review comment is a finding or a question (kind 1 or 7). Kinds 8 and 9 are argued in the author's replies.
- `scripts/merge-lane-pull-request-reviewer-review-post-and-read-back.py`: merge-lane-2's review file, which restates every reviewer's findings, gives each comment its kind, finding or question, and a category for a finding only; the program refuses any other kind and writes the kind into the posted comment's opening mark, beside the category mark it writes today. The two programs that read those marks, `scripts/pull-request-fix-round-author-brief-from-blocking-findings-and-one-commit-every-finding-answered-check.py` and the follow-up program above, change in the same pull request to read the new mark and a question with no category.
- `scripts/pull-request-head-test-run.py`: it reruns each failing nc-test-suite once and runs it once on main, classifies each failing test case as described above, and writes the kind's name into its record; it posts the kind 3 comment; and, for a kind 2 test case or a second sighting, it looks for an open GHI naming the test case and prints the facts its GHI-MD needs: the test case, the commits, the log paths and the pull requests it failed.
- `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py`, merge-lane-2's merge program: the rerun of waiting pull requests in kind 2's row.
- `scripts/merge-gate.sh`, which reads no head test run record today: it refuses a merge while there is no readable head test run record of the pull request's nc-head-commit, and while the last such record shows a kind 1 or kind 2 test case, except that the pull request that fixes, deletes or skips a kind 2 test case, and names its GHI in its description, is not refused for other kind 2 test cases; and while it shows a kind 4 test case, unless the answer to open question 1 allows it.
- The owner check: its record says could not answer for a lapsed login or a network outage, it writes a user-alert for a lapsed login on ned-box, and it exits 2, as the exit-code page requires its output and its code to agree.
- The guard hooks that fail open silently: each says so. An nc-test-suite sends input that is not the JSON a hook expects to every hook under `.claude/guard-hooks/` that `.claude/settings.json` registers, and fails on one that neither refuses nor tells the agent in `additionalContext` that its check did not run, as the exit-code page's section "Hooks" asks of a guard that could not check. The git client-side hooks are brought to the exit-code page's rule for a check's exit 2 under GHI 2476.
- merge-lane-2's seat-brief, which is outside the repository: merge-lane-2 proposes to the user any change it needs, as a seat-brief change needs his approval.

## The consistency check

A daily maintenance-job among those of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058) reports what got past the merge gate or cannot be seen there, each case once, by the route GHI 1058 sets for a maintenance-job to reach the user:
- a pull request merged although its last head test run record shows a kind 2 test case it does not name the GHI of, or a kind 4 test case that open question 1's answer does not allow;
- a test case classified as kind 2, or with a second sighting as kind 3, that no GHI names a day later, other than one closed before the classification;
- a kind 2 GHI still open when the grace period of open question 4 ends, while a pull request waits on it;
- a finding in category 2, 3 or 4 with no follow-up, no leave-out reason and no record of waiting for a user-ruling when the grace period of open question 4 ends;
- an accepted false alarm on a program's finding whose cause was not fixed, and not accepted as unavoidable, when that grace period ends;
- a fix argued as kind 9 whose description has neither a `#root_cause` nor a `#root_cause_not_fixed` line;
- a question merged with no reply, when open question 3's answer has the merge wait for one.

Kind 5 has no check yet, as Deferred-decisions says; kind 6 is checked by GHI 1206's daily check. The kind 2 and kind 3 rules read head test run records, so they see failures like those of GHI 1233, which are in such records, and not those of GHI 1323, which failed only in agents' own runs before a pull request opened.

The steps that need judgment are: a reviewer finding a problem or raising a question; merge-lane-2 giving a finding its category; merge-lane-2 judging that a kind 2 or kind 3 test case is kind 1 after all; an author answering a finding, including arguing kind 8 or 9, and merge-lane-2 accepting or rejecting the answer, including that a false alarm's cause is unavoidable; answering a question; writing the GHI-MD for a kind 2 or kind 3 test case; and the fix that a kind 2 GHI calls for. The classifying of each failing test case, the reruns, the kind 3 comment, the GHI lookup, the user-alerts, the merge gate's refusals and the consistency check are code.
