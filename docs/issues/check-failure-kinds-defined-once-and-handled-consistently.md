# One shared list of the kinds of check failure, used by reviewers, authors and test writers, and a daily check that each kind is handled the same way

The user asked for this GHI on 2026-10-18, in item 19 of the approval-walk `md-skills-seat-open-decisions-2026-10-15`, after two pairs of independent searches found that a failing check can mean several different things and that agents handle each one differently. The walk-minutes record his request: `nedlern@ned-box:/home/nedlern/nedsnodes-logs/walk/md-skills-seat-open-decisions-2026-10-15-minutes.md`, the bullets dated 2026-10-18.

## The problem

The project's checks are its nc-test-suites, the pull request reviewers, the merge gate `scripts/merge-gate.sh`, merge-lane-2's test run of a pull request's nc-head-commit (its head test run), the guard hooks, the git client-side hooks, the cold-read grid, `scripts/branch-conflict-check.py`, the canary tests, and the prerequisite checks that GHI [Check every prerequisite of the fleet's programs before an agent-session starts](https://github.com/nedschorus/nedschorus/issues/1055) plans. A check that answers no on purpose, such as a guard hook refusing an act or `scripts/branch-conflict-check.py` finding a conflict, is the check working: the agent does what its tool-message-to-agent says, and this GHI adds nothing to that. The other outcomes are not just pass or fail: the checks produce eight kinds of outcome that are neither a pass nor a deliberate refusal, and one kind of cause, all listed below. Some kinds already have a definition in one place, as the section "What other GHIs and pages already define" says, but nothing defines them as a set, names the cases no page covers, such as a test case already failing on main or a flaky test, or checks that agents handle each kind the same way.

The evidence is in four reports, two by Codex and two by Claude subagents, which searched in two independent pairs, and in their combined summary, all in `nedlern@ned-box:/home/nedlern/nedsnodes-logs/analysis/canary-cases-and-failure-kinds-2026-10-18/` (`summary.md`, `failure-kinds-codex.md`, `failure-kinds-claude.md`, `canary-trawl-codex.md`, `canary-trawl-claude.md`). The cases below come from them.

**The same kind handled differently.**
- A test already failing on main was ignored, merged over, rerun, filed as a GHI or fixed at the root, depending on the agent. On 2026-10-14 the nc-test-suite `scripts/run-codex-task-from-brief-test.py` got three different handlings from three agent-seats: one moved on, one fixed it at the root, and merge-lane-2 filed GHI [The Codex task runner's deadline test case fails on a busy machine, because a scan of the whole home directory runs before the deadline starts](https://github.com/nedschorus/nedschorus/issues/1323).
- A Mac test case noted as "also fails on main" was left failing by four pull requests, starting with PR [Claude Code Bash hook: remind the agent to run both citation checks when a git push sends a branch that changes a Markdown file](https://github.com/nedschorus/nedschorus/pull/1354), and fixed only in PR [Bash guards replay: a checkout named through a symlink is removed by git, not deleted as unregistered](https://github.com/nedschorus/nedschorus/pull/1452).
- A failure called "a flake, not caused by this pull request" in PR [handoff dialog: each subagent's task and report as a third voice; ned-box keeps every session's complete dialog current in the log-store](https://github.com/nedschorus/nedschorus/pull/1188) was filed nowhere. It was a defect in the test, GHI [The signal sandbox test's fake bwrap fails when its status descriptor number is 10 or more, so the test fails at random](https://github.com/nedschorus/nedschorus/issues/1233), whose GHI-MD lists the head test runs of nine pull requests it failed.
- Non-blocking findings sometimes got a follow-up pull request or a written decline, as in PR [Fast-read reminder: the marked-as-read note and stderr line say only what is true, mutant M6 is killed, and every registered hook's constants are scanned for citations](https://github.com/nedschorus/nedschorus/pull/1593), and sometimes, on 2026-10-18, nothing that a later pull request cited, as `failure-kinds-claude.md` records for PR [run-all-test-suites.py: kill a suite past a time limit sized from its recorded duration](https://github.com/nedschorus/nedschorus/pull/1560).
- Two reviewers gave the same finding different merge consequences in PR [The cold-read-cells read the frozen copy, which is what freezing meant](https://github.com/nedschorus/nedschorus/pull/636).

**The same kind called by different words.**
- A finding that need not be fixed before the merge was called "advice", "does not block", "non-blocking finding", "follow-up" and "findings that do not block". The four finding categories of GHI 2522, below, now give it one set of names.
- "Could not answer" and "no" are kept apart by `scripts/run-all-test-suites.py` (its `NOT RUN` line) and by the cold-read grid ("a run that produced no report is not a review that found nothing"), but the docstring of `nn-systems/handoff/uncommitted-work-snapshot-hook-scheduled-check-that-real-claude-session-is-recorded-as-owner.py`, the owner check, says that a lapsed claude login or a network outage "is a failed check", and the program writes it as `VERDICT: FAILED`.
- `docs/nedsnodes-wiki/nedsnodes-how-to-write-a-tool-message-to-agent-such-as-a-hook-refusal-or-script-error.md`, the tool-message page, in its bullet "When the program fails open", requires a program that lets an act through unchecked to say that the act was not checked; the failure-kinds reports found guard hooks that fail open silently on malformed input.

**Why it matters.** When the kinds are not defined as a set, an agent decides each case alone, from its own reading. A failure put down to chance and filed nowhere stays unfixed and keeps other pull requests from merging; a "could not answer" read as a pass merges unchecked work; a non-blocking finding with no follow-up is lost. Nothing reports to the user which of these happened.

## What other GHIs and pages already define

This GHI does not define again what these define. Its list points to them, and it adds the kinds they leave out, the handling of every kind, and the check that the handling happened.
- `docs/nedsnodes-wiki/nedsnodes-how-a-program-reports-success-failure-and-findings-with-its-exit-code.md`, the exit-code page, sets what a program's exit code means: 0 yes, 1 no, 2 could not answer, with the different codes of Claude Code hooks and git hooks in its section "Hooks". GHI [Bring every program, test, help text and unbuilt design into line with the wiki page on how a program reports success, failure and findings with its exit code](https://github.com/nedschorus/nedschorus/issues/2476) brings every program into line with it. That GHI changes what each program exits with; this GHI says what an agent does with each kind of outcome, across programs, reviews and test runs, and checks that it was done.
- Section 2 of `docs/nedsnodes-wiki/queue/nedsnodes-goals-and-philosophy-founding-statement-and-agent-working-principles.md`, the goals and philosophy page, in the wiki queue and not yet approved, puts every finding in one of four categories, by when it is fixed: must fix now, fix next, fix during maintenance, and file an improvement, a feature or a change. GHI [Implementing the project's goals and philosophy: every finding sorted into four categories, checked claims kept with their evidence, and one standard in every agent's instructions](https://github.com/nedschorus/nedschorus/issues/2522) carries that work, and `docs/agents/pr-reviewer-instructions.md` already has merge-lane-2 give each review finding one of the four categories. A category says when a kind 1 finding is fixed; a kind says what an outcome is.
- GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206) defines how a skipped test case is printed and reported. `scripts/test-suites-source-scan-for-skipped-case-prints-run-all-test-suites-cannot-count-test.py` already fails when an nc-test-suite prints a skip the test runner cannot count.
- GHI [A test result relayed from one agent-seat to another without its exit code can hide a crash as a pass](https://github.com/nedschorus/nedschorus/issues/1235) is one case of a test file that crashed part-way, which the exit-code page counts as could not answer, relayed as a pass; it is fixed under its own GHI.
- GHI [Every refusal and warning a program hands an agent says why and what to do instead](https://github.com/nedschorus/nedschorus/issues/956) covers the wording of a tool-message-to-agent; this GHI covers which kind each outcome is and what is done about it.

## The proposed list of kinds

The kind names below are plain prose; the rest of this GHI calls each kind by its number. "Decides" names who or what puts a given outcome in its row. Where a page above already defines a kind, its row points there. Only a kind 1 finding gets a finding category. Kinds 1 to 8 are outcomes; kind 9 is a cause, which shows as a kind 1, 2 or 4 outcome.

| # | Kind | Definition | Leads to | Decides |
|---|---|---|---|---|
| 1 | Finding about the change | The check found a real problem in this pull request's change: a defect it introduces, or an improvement it should make. A test case that fails on the nc-head-commit, passed on main and fails again on one rerun of the nc-head-commit is kind 1 unless the author shows it is kind 9. | The finding category merge-lane-2 gives it, as section 2 of the goals and philosophy page defines. A must-fix-now finding is fixed before the merge. A finding in category 2, 3 or 4 is followed up as its category says, or gets a leave-out reason recorded with `scripts/pull-request-follow-up-request-after-merge-finding-answers-and-next-step.py`'s `record-finding-leave-out-reason`. | The reviewer or the check reports it; merge-lane-2 gives it its category. |
| 2 | Already failing on main | The same test case, by nc-test-suite path and case name, fails on main without this change, on the same machine. | The pull request does not merge over it, and the merge gate refuses it while its head test run record shows kind 2. A separate pull request fixes, deletes or skips the test case, with a GHI tracking it, so that test case passes on its own head test run; whether a passing rerun of the nc-head-commit also clears it is open question 2. | Code: the program that runs the head test run compares each failing test case with the newest scheduled full test run of main on that machine, and, when that run is older than the pull request's merge base or has not finished, runs the failing nc-test-suite on the merge base itself. |
| 3 | Flaky test | A test case fails, then passes on one rerun of the same commit, and passed on main. Every flaky test case has a defect, in the test or in the code it tests. A rerun that could not answer is kind 4. | The program that made the rerun posts the failing log's path in a pull request comment, and the pull request may merge on the passing rerun. When the change touches the failing nc-test-suite's recorded inputs, the failure is kind 1 unless the author shows otherwise. A GHI is filed at the second sighting: the same test case classified as kind 3 on a second commit. | Code: the program that runs the head test run makes the one rerun, compares with main as for kind 2, and compares the pull request's diff with the recorded inputs `scripts/run-all-test-suites.py` keeps for each nc-test-suite. That runner adds every failing test case to `test-case-failure-history.jsonl` in its `--recorded-inputs-directory`, by default `~/.cache/nedsnodes-test-suite-recorded-inputs/` on the machine that ran it, except in runs given `--leave-recorded-inputs-and-failure-history-unchanged`, such as nc-mutation-testing runs. The head test run program prints a second sighting when it finds one; merge-lane-2 files the GHI. |
| 4 | Could not answer | The check reached no answer, as the exit-code page defines: exit 2 from a program that is not a hook, or a code above 2, which its section "A caller" reads as 2; exit 1 from a Claude Code hook, which its section "Hooks" gives a hook that broke; and, for an nc-test-suite, the test runner's `NOT RUN`. | Never a pass; the cause named; for a cause only the user can clear, such as a lapsed login or a usage limit, the program writes a user-alert. Whether the pull request may merge with the gap named is open question 1. | The check's exit code, or the test runner's `NOT RUN` line. |
| 5 | Failed open | A hook whose check could not answer let the act go ahead, as the exit-code page's section "Hooks" allows: a git hook after a check's exit 2, or a Claude Code hook that exits 0 because the agent's next act depends on the check. | The hook says so where the agent will see it, as the tool-message page's bullet "When the program fails open" and the exit-code page's section "Hooks" require, naming the check that did not run. | The hook's author, at build time; what the agent then does is open question 5. |
| 6 | Skipped | A test case chose not to run, as GHI 1206 defines. | Printed and reported as GHI 1206 plans. A skip never changes a verdict, as the test runner's manual says, so it never keeps a pull request from merging. | The test writer. |
| 7 | Question | A matter for a decision, not a defect. | Answered; where it goes, and whether the merge waits for the answer, is open question 3. | The reviewer raises it. |
| 8 | False alarm | A reported finding that does not hold. | The author says why in a reply on the finding, or, for a finding from a program, in a pull request comment. When the check is a program, its cause is fixed, unless the check matches a pattern that cannot avoid every false alarm, which the reply then says. | The author answers; merge-lane-2 accepts or rejects the answer. |
| 9 | Outside program changed | A program the project calls but does not write changed its behaviour, such as in an upgrade, so code that matched it no longer does. Code that never matched it is kind 1. | The row of the outcome it shows as says what keeps the pull request from merging; the author's reply on the finding or pull request comment names kind 9 and its evidence. The fix's description has a `#root_cause` line naming the outside program's change, or, when the project can only work around it, a `#root_cause_not_fixed` line with its `#follow_up`, as `docs/agents/pr-reviewer-instructions.md` defines; and a canary test where the canary design asks for one. | Open question 6. |

## Where the list lives

One wiki page holds the table above with one real example of each kind, and points to the pages above for the kinds they define. Its proposed name, `docs/nedsnodes-wiki/nedsnodes-kinds-of-check-failure.md`, is still to be checked against `docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md`. The kinds' names are also kept once in one data file, which every program that names a kind reads, and an nc-test-suite fails when the page's table and the data file differ, and exits 2 when either cannot be read.

## Which files must use the list

- `docs/agents/pr-reviewer-instructions.md` and `.claude/skills/pull-request-review-write/SKILL.md`: a reviewer gives each review comment kind 1 or kind 7; merge-lane-2 gives a kind 1 comment its category afterwards, as today.
- `scripts/merge-lane-pull-request-reviewer-review-post-and-read-back.py` and the Claude reviewer's schema, `scripts/merge-lane-pull-request-claude-reviewer-review-schema.json`: the reviewer's schema gains the kind for each comment, and the program's input carries it beside `finding_category`, which merge-lane-2 adds only to a kind 1 comment; the program refuses a kind other than 1 or 7, as it already refuses a category not in `FINDING_CATEGORIES`, and writes the kind into the posted comment's opening mark, as it writes the category, so the consistency check can read it back from GitHub.
- The program that runs merge-lane-2's head test run: it makes the one rerun, compares with main and with the recorded inputs, prints kind 1, 2, 3 or 4 for each failing nc-test-suite into the head test run record, posts the kind 3 comment, and prints a second sighting.
- The owner check: a lapsed login or a network outage is kind 4, so its record says could not answer, it writes a user-alert for a lapsed login, and it exits 2, as the exit-code page requires the output and the code to agree. Its exit code changes under GHI 2476; this GHI changes what its record says.
- The guard hooks that fail open silently: each says so (kind 5). An nc-test-suite sends malformed input to every registered guard hook and fails on one that exits 0 without refusing and without telling the agent that its check did not run.
- merge-lane-2's seat-brief, which is outside the repository: the author of the wiki page's pull request sends merge-lane-2 the page's path, and merge-lane-2 updates its seat-brief itself.

## The consistency check

The merge gate checks what it can see before a merge, as it already checks the `#root_cause` line: it refuses a pull request whose head test run record shows kind 2, and one whose record shows kind 4, as the answer to open question 1 says.

The consistency check, a daily maintenance-job among those of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058), reports what got past the merge or cannot be seen there. Each run reads the pull requests merged in the last 30 days, so a finding whose grace period ends after its pull request's first day is still checked: their descriptions, reviews and comments, with the kinds read back from the review comments' opening marks; the head test run records and scheduled full test run records in the log-store; and `test-case-failure-history.jsonl`. When GHI [Pull requests, their reviews and approval-walks held as one state machine over one schema and one store, so code tracks their state and agents are handed only the steps that need judgment](https://github.com/nedschorus/nedschorus/issues/2505) is built, it reads that store instead. It reports, as GHI 1058 says a maintenance-job reports to the user, each case where:
- a pull request merged while a test case that failed on its nc-head-commit also failed on main (kind 2);
- a test case has a second sighting in `test-case-failure-history.jsonl` and no GHI naming it opened after the first (kind 3);
- a kind 1 finding in category 2, 3 or 4 has, after the grace period of open question 4, no later merged or open pull request citing it, no task or GHI holding it, and no recorded leave-out reason;
- a kind 1 finding that was not fixed has neither a fix nor a reply arguing kind 8 or 9 that merge-lane-2 accepted;
- a kind 8 answer that merge-lane-2 accepted, on a finding from a program, has no later pull request or GHI citing it and does not say that the check cannot avoid every false alarm;
- a test case classified as kind 2 has no GHI naming it;
- a pull request merged with a kind 4 outcome in its head test run record that merge-lane-2's approving review does not name.

Of the cases above, it would have reported the test case of GHI 1233, whose failures are in head test run records, and the follow-ups of PR 1560 that no later pull request cited. It would not have seen the case of GHI 1323, which failed only in agents' own runs before a pull request opened, which no record it reads holds.

The steps that need judgment are: a reviewer finding a problem and giving its comment kind 1 or 7; merge-lane-2 giving a kind 1 finding its category; an author answering a finding, including arguing that it is kind 8 or 9, and merge-lane-2 accepting or rejecting the answer; answering a question; and writing the GHI-MD a second sighting or a kind 2 test case calls for. The classifying of kinds 1 to 4 from the records, the rerun, the run on the merge base, the second sighting, the kind 3 comment, the user-alerts, the merge gate's check and the consistency check are code.
