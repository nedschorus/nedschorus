# `scripts/merge-gate.sh` refuses a pull request whose standing instruction or prompt has no matching approval by the user or no cold-read-fast-read record

## What is wrong

merge-lane-2 holds a merge until the user has approved every prompt and every standing instruction the pull request hands an agent. The rule is in merge-lane-2's seat-brief, `nedlern@ned-box:/home/nedlern/agents/merge-lane-2/CLAUDE.local.md`, line 41. The texts it covers are the standing instructions CLAUDE.md lists, which are CLAUDE.md, the seat-briefs and every `-instructions.md` and `-prompt.md` file, together with each skill's `SKILL.md` and the prompts programs hand agents. Today that hold is kept by hand: merge-lane-2, or a subagent it dispatches, compares the committed text word for word with the text the user approved. Neither `scripts/merge-gate.sh` nor any other program merge-lane-2 runs before a merge makes that comparison, so a hand comparison that is skipped or misses a word lets text the user never saw reach every agent. Nothing at all asks that such a text has had a cold-read-fast-read: line 41 asks for one only for a message a program prints, such as an error or a refusal.

## What `scripts/merge-gate.sh` is to do

For each standing instruction a pull request adds or changes, and for each prompt a program in the pull request hands an agent, `scripts/merge-gate.sh` refuses the merge unless both of these hold for each passage the pull request adds or changes, as it will read once merged:

- a record of the user's approval holds that passage;
- a cold-read-record holds a cold-read-fast-read report and a frozen-copy that holds that passage.

Its refusal names each passage that failed, which of the two it lacks, and what to do: bring the passage to the user, or run the cold-read-fast-read on it. Both comparisons are code; no step inside `scripts/merge-gate.sh` needs judgment.

## What the design must settle

Each point below names the recommendation it starts from; the design may settle it otherwise, and its approval-walk puts each to the user.

1. **Which texts count, and in what pieces they are compared.** Recommendation: the standing instructions CLAUDE.md lists and each `SKILL.md`, found with the guard's `PROTECTED_BASENAMES` and `REUSABLE_PROMPT_SUFFIXES` rather than a second list, plus the prompts of point 4. A whole CLAUDE.md is never approved at once, so the comparison is of each passage the pull request adds or changes, found from its diff, as md-drift-lint's wiring finds changed lines. The design says what a passage is, such as a paragraph or a list item, and what a deletion needs: removing a passage changes what agents are told, so the recommendation is that a deletion needs the user's approval too, with no cold-read-fast-read. A seat-brief is outside `scripts/merge-gate.sh`: git does not track it, so no pull request carries it.
2. **Where `scripts/merge-gate.sh` finds the user's approval of a passage.** Recommendation: the walk-minutes answer line together with the walk-document's `#new` or `#new_if_d` line it approves, since the approval-walk answer program already writes the first and reads the second. A passage the user approved outside an approval-walk, such as an approval quoted in an agent-session that `scripts/search-user-messages-in-transcripts.py` finds, needs a record `scripts/merge-gate.sh` can read; the design says who writes it and in what form. Recommendation: the record carries the transcript's path, the time of the user's message and his words as quoted, and code confirms, with `scripts/search-user-messages-in-transcripts.py`, that he typed those words at that time, so a mistaken or invented approval does not pass. Deciding which of the user's words approve which passage needs judgment, and it is done once, by the agent that writes the record, not by `scripts/merge-gate.sh`.
3. **How far the merged passage may differ from the approved passage.** Recommendation: not at all. All three cases above were changes the user had to see. An agent whose pull request is refused judges whether the difference is an obvious-error-fix, as the project glossary defines it; the design says how such a fix is recorded so that `scripts/merge-gate.sh` lets it through with its reason, or whether every difference goes back to the user. A record of such a fix holds the approved passage, the merged passage and the reason, and `scripts/merge-gate.sh` confirms that the first matches an approval record and the second matches the merged file, so a reason written for one change cannot let a second one through. That judgment is the agent's, named in the design; `scripts/merge-gate.sh` only compares texts.
4. **Where a prompt a program hands an agent is kept so `scripts/merge-gate.sh` can read it.** A prompt is built in code and has no file of its own, and most fill placeholders, such as a branch name or a path, at run time. Recommendation: a test for each such program renders each prompt with fixed sample values, writes it to a committed file, and fails when the committed file and the rendered prompt differ, so `scripts/merge-gate.sh` compares the committed file like any other. The design says which programs this covers, starting from the prompts that [PR 2236: Agent-facing string collector: find text built in a local variable and returned or printed](https://github.com/nedschorus/nedschorus/pull/2236) marks, and whether the user approves the rendered sample or the template with its placeholders. Recommendation: rather than a list kept by hand, a test fails whenever a string `nc-systems/general-tools/python-source-agent-facing-string-collector-common.py` marks as a prompt has no committed rendered file, so a prompt added later cannot skip the comparison.
5. **Where `scripts/merge-gate.sh` reads the texts and the records.** It reads the pull request through GitHub today, and the approval records and cold-read-records are files on ned-box, in agent-homes and the log-store, not in the repository. Recommendation: it reads the merged text from the pull request's head commit, and looks for records as the approval-walk answer program does, in the checkout's `cold-read-records/` and the log-store's. When it cannot reach the log-store, it exits 2, could not run, never 1 or 0, because a record it could not look for is not a missing record.
6. **How this fits the cold-read skill's cold-read-full-run rule.** A standing instruction that takes a cold-read-full-run under `.claude/skills/cold-read/SKILL.md` step 2 ends with a cold-read-fast-read of the commit that carries out what the user decided in its approval-walk, in step 9; that cold-read-fast-read's record is the one `scripts/merge-gate.sh` finds, so no further read is asked for. Recommendation: when a text took a cold-read-full-run but its last revision has no cold-read-fast-read, `scripts/merge-gate.sh` refuses, as for any text without one, since the cold-read-full-run read an earlier text. The design confirms this against step 9.
7. **Where else the same comparisons run, and what they replace.** A refusal at merge time comes after the author's head commit is frozen. Recommendation: `scripts/pull-request-review-plan.py` runs the same two comparisons when the review is commissioned, and a missing cold-read-fast-read is started by code, as the approval-walk answer program already starts one, so the only step left to an agent is bringing a passage to the user. Once `scripts/merge-gate.sh` makes the comparison, line 41 of merge-lane-2's seat-brief no longer asks merge-lane-2 to make it by hand; the design lists that seat-brief change.
