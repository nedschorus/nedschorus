# The handoff-supervisor restarts itself on main's current code at each handoff

## What is wrong

Every agent-seat on ned-box runs its handoff-supervisor as `python3 /home/nedlern/Projects/nedschorus/nc-systems/handoff/handoff-supervisor.py`, from the reference-checkout. Python reads the program once, when the process starts, so a handoff-supervisor keeps the code it started with for every reincarnate-seat after, however far main moves on. Nothing restarts a running handoff-supervisor: `scripts/resupervise-seat.py` refuses when a handoff-supervisor is alive on the agent-seat, and `scripts/recover-crashed-seats.py` and `scripts/restart-live-seats-at-login.py` start handoff-supervisors that are not running. GHI [recover-crashed-seats: a recovered seat's supervisor runs from whichever checkout the recovery was run from, and stops at its next handoff once that checkout is removed](https://github.com/nedschorus/nedschorus/issues/659) already records that "a running supervisor keeps its code until it restarts", but asked for no change to it.

Seen on ned-box on 2026-10-27, by the agent-seat prime-intellect:

- `ps -eo pid,lstart,args` listed 8 handoff-supervisor processes, started between 2026-10-09 and 2026-10-22. prime-intellect's own, process 2948944, started on 2026-10-21. The handoff-supervisors on the Mac were not looked at; `ps -ww -eo pid,lstart,args | grep '[h]andoff-supervisor.py'`, run on the Mac, lists them.
- Commit 869067074 (2026-10-24, "handoff-supervisor: successor prompts bring the user's items in one approval-walk") made the initial-agent-instructions of each successor carry `ITEMS_NEEDING_THE_USER_IN_ONE_APPROVAL_WALK_INSTRUCTION`, which tells the successor to bring the user's open items in one approval-walk. prime-intellect's successor of 2026-10-27 was told instead to "Display them to the user", the text from before that commit, because its handoff-supervisor started on 2026-10-21.
- The reference-checkout itself is current: its reflog shows 23 fast-forwards to `origin/main` on 2026-10-26 alone, the last to 675b99013, the tip of `origin/main` on 2026-10-27. Which program makes them was not found. Only the processes that already loaded the code are behind.

## Why it matters

A change to the handoff-supervisor, or to a module it loads, reaches an agent-seat only when someone restarts that agent-seat's handoff-supervisor by hand, and on 2026-10-27 some agent-seats on ned-box had run for 18 days without one. Every merged fix to the handoff-system therefore waits, unseen, for days or weeks, while the agent that wrote it and the user believe it is in use. The 2026-10-27 successor shows the cost: an instruction the user asked for was missing from the initial-agent-instructions, and no program said so.

## What to build

1. **At each reincarnate-seat, the handoff-supervisor restarts itself on main's current code.** When a session-handoff arrives and the handoff-supervisor has stopped the retiring agent-session, but before it starts the successor, it fast-forwards the checkout it runs from to `origin/main`, then replaces its own process with a fresh start of `handoff-supervisor.py` from that checkout, by `os.execv`, so the process ID stays the same. The fresh process starts the successor, so every agent-seat runs current code from its next reincarnate-seat on.
2. **A one-time procedure, for the Mac and for ned-box, that restarts every handoff-supervisor running now**, so each one runs code that has part 1; until it has, a handoff-supervisor without part 1 never picks it up. Where the procedure can be a program, it is one.

## Constraints the build must meet

Each was checked against `nc-systems/handoff/handoff-supervisor.py` on main at 675b99013.

1. **The supervisor lock must accept its own process ID.** At startup, `main()` calls `claim_supervisor_lock()`, which takes an exclusive `flock` on `<handoff directory>/<agent-seat>-supervisor.lock` (`supervisor_lock_path()`) and then calls `refuse_old_code_supervisor()`. That function reads the process ID left in the lock file, asks `ps` for its command line, and raises "old-code supervisor … is running" when the command line runs `handoff-supervisor.py` with the same `--agent`; `main()` turns that into exit 4. After `os.execv`, the process ID in the lock file is the restarted process's own, and its command line matches, so as written the restarted handoff-supervisor refuses itself, exits 4, and the agent-seat has no handoff-supervisor. Part 1 must therefore make the startup treat a lock file holding its own `os.getpid()` as its own claim. Two more facts about the lock: Python opens files close-on-exec, so `os.execv` closes the locked file and releases the `flock`, and the restarted process can take it again; and `release_supervisor_lock()`, in the `finally` of `main()`, does not run on `os.execv`, so the lock file keeps the right process ID through the restart, and `--check` and `supervisor_liveness()` keep seeing a handoff-supervisor of that agent-seat. A comment on `refuse_old_code_supervisor()` says to delete it once no handoff-supervisor started before it is running; after part 2 has run on both machines, a later pull request may delete it.
2. **Where the restart sits.** Restart after `stop_session()` and before `carry_over_to_successor()`, while `state["consumed_counter"]` still holds the previous counter. The restarted process then finds the session-handoff unconsumed at startup, and its existing path for an unconsumed session-handoff (the block commented "Process an existing handoff before launching" in `supervise_sessions()`) writes the conversation-tail and starts the successor, as it does after a reboot. Two things the in-loop path does must not be lost on the way. `remove_finished_worktrees_at_handoff()` runs only on the in-loop path today, so call it before `os.execv`, or from the startup path for a restart. A session-handoff carrying `dont-restart` makes the in-loop path ask the user `restart? y/n` and the startup path ask again, so do not restart the process for a session-handoff that carries `dont-restart`. The builder confirms this placement, or chooses another and says why.
3. **The restarted process does not restart again for the same session-handoff, and restarts as usual at the next one.** Pass the restarted process a command-line flag saying that it was started by a restart. The flag is read at startup only: it stops a restart from the startup path for an unconsumed session-handoff, and the restarted process builds its own next restart, at a later session-handoff, without the flag. If the builder uses an environment variable instead, the restarted process removes it from `os.environ` at startup, so that neither its `claude` children nor its next restart inherit it.
4. **Build the restarted process's arguments from the settings, not from `sys.argv`.** Handoff-supervisors on ned-box were started with two argument lists: `--agent X --cd ~/agents/X` (prime-intellect, MD-skills and fleet-restart-at-login), and `--agent X --cd /home/nedlern/agents/X --handoff-dir /home/nedlern/.claude/handoffs --resume-session-id <id> --first-prompt-file /home/nedlern/.claude/handoffs/X-resume-recovery-prompt.md` (cold-read-improvement, merge-lane-2, reboot-test, agent-instructions-editor and ned-box-helper, started by a recovery). Passing `--resume-session-id` again would be wrong: at startup it marks a waiting session-handoff consumed and resumes the old transcript, so the successor would never start. `--first-prompt-file`, `--adopt-session-id` and `--adopt-process-id` also describe the original start only. Pass only what every reincarnate-seat needs, with the values the running process has: `--agent`, `--cd`, `--handoff-dir`, `--agent-command`, `--agent-update-timeout-seconds` and `--agent-append-system-prompt-file`, and the flag of constraint 3. The running process builds these arguments with its old code for the program main now holds, so these flag names become a contract: a later pull request that renames or removes one of them keeps the old name working, and part 1 adds a test that fails when `main()` stops accepting any of them.
5. **Replace the process; do not exit and relaunch.** Each handoff-supervisor is the last command of its tmux pane: `bash -c "trap ':' INT QUIT; …; python3 …/handoff-supervisor.py …"` for those started by `scripts/launch-claude-ubuntu`, and `sh -c "…; python3 …/handoff-supervisor.py …"` for those started by a recovery. When the handoff-supervisor exits, the pane's shell goes on to whatever follows it, and nothing starts a new handoff-supervisor. `os.execv` keeps the process, its terminal and its place in the pane. At the restart the retiring agent-session has already been stopped, so no `claude` process is left without a parent.
6. **A failed fast-forward or a failed restart is reported, and the handoff-supervisor carries on with the code already loaded in its process.** Reuse `launch_time_git_sync()`, which fast-forwards a checkout only when it is strictly behind `origin/main`, has no uncommitted tracked change and has no git operation in progress, and returns one line of report in every case. Run it on the checkout that holds the running `handoff-supervisor.py`. Restart when that line reports a fast-forward to main, and also when it reports the checkout current with main, because the running process may be older than the checkout. In every other case, and when `os.execv` raises, do not restart: print that line, or the error `os.execv` raised, on the handoff-supervisor's console and add it to the successor's initial-agent-instructions, as the launch-time-git-sync report already is, then start the successor from the in-loop path with the code already loaded. Because the report goes into every successor's initial-agent-instructions, a checkout that stays unable to fast-forward is reported to the agent at each reincarnate-seat until someone fixes the checkout. A successful restart needs only its console line.

Tests for each constraint go in the handoff-supervisor's tests in `nc-systems/handoff/`, with the failure injected where it cannot be caused for real: a lock file holding the test process's own process ID; a session-handoff carrying `dont-restart`; the restart flag present at startup and absent at the next session-handoff; argument lists of both kinds above; a checkout that cannot fast-forward; `os.execv` raising.

## Open questions

- **Which checkout a handoff-supervisor on the Mac runs from.** `scripts/launch-claude-mac` runs the `handoff-supervisor.py` of the checkout that holds the launcher (`REPOSITORY_ROOT`, the directory above `scripts/`). Run from an agent-home, that is a seat-branch, which `launch_time_git_sync()` leaves as it is when the branch has commits main lacks, so part 1 would keep that handoff-supervisor on its old code, the case GHI [recover-crashed-seats: a recovered seat's supervisor runs from whichever checkout the recovery was run from, and stops at its next handoff once that checkout is removed](https://github.com/nedschorus/nedschorus/issues/659) is about. The builder finds which checkout each handoff-supervisor on the Mac runs from, and brings the user the choice if any runs from somewhere other than the reference-checkout.
- **Whether part 2 interrupts work.** Restarting a handoff-supervisor while its agent-session is working stops that agent-session unless the procedure adopts it (`--adopt-session-id` and `--adopt-process-id`) or waits for its next session-handoff. The builder proposes which, and brings the user that choice before running part 2 on any agent-seat.
