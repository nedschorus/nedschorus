# Save each lesson where agents meet it at the moment it applies, and decide whether a store that recalls lessons by subject is worth building

## What is wanted

A lesson, here, is something an agent learned in one agent-session, usually from a correction by the user, that should change what later agents do. This GHI asks the user for two decisions:

1. **A rule an agent follows to choose where a lesson is saved**, so that a later agent meets the lesson before it acts. The proposed rule is under "The rule for choosing where a lesson goes", tested on the eight lessons agents tried to save into Claude Code's memory in four days.
2. **Whether to build a store that recalls lessons by subject**: lessons kept as entries in one store, each delivered by a hook when the agent's current tool call, file or reply matches the entry. The recommendation is not to build one now; the reasons, what would reopen the question, and the first measurable version are under "Whether to build a store that recalls lessons by subject".

Some lessons are already placed by hand; neither the rule nor a store exists. The next action is an approval-walk on both decisions.

## Why

- The instruction-file guard refuses every Edit, Write and NotebookEdit aimed at a Claude Code memory directory (`MEMORY_WRITE_DENY_MESSAGE` in `.claude/hooks/instruction-file-guard.py`), and no marker file lets one through. The user, on 2026-10-13 (walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/approved-action-re-ask-unpushed-commits-and-memory-refusal-2026-10-13-minutes.md`): "I blocked memory because memory works poorly, but not becaue I don't want agents to remember, but because I want them to save and recall not just save."
- Memory saves without recalling. Claude Code loads a memory directory's index, `MEMORY.md`, at the start of each agent-session; the text of a lesson is read only when an agent opens its file, and nothing puts the lesson in front of the agent at the moment it applies. The store does not reach every agent either. On ned-box the agent-seats under `~/agents/` aim their memory writes at one directory, `~/.claude/projects/-home-nedlern-Projects-nedschorus/memory/`, named after the reference checkout `/home/nedlern/Projects/nedschorus`: the eight refused writes below, from four agent-seats, all target that directory. Agent-seats on the Mac have a memory directory of their own on the Mac, and Codex reads neither.
- The refusal tells the agent to propose an edit where an agent would meet the lesson, and otherwise to drop the lesson. Nothing tells the agent how to choose that place, so each agent decides afresh, and a lesson whose place the agent cannot see is dropped. The first row of the table below is an example placed by hand.

## The rule for choosing where a lesson goes

The rule asks where the agent will be reading at the moment the lesson applies, and puts the lesson into that text. The general guide to where rules for agents are kept, which the user dropped on 2026-10-07 ("this guide doesn't look that useful, it's just a summary of claude's hooks"; walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/nedschorus-where-agent-rules-live-decision-guide-draft-2026-10-05-minutes.md`), also started from the moment a rule is needed, but then listed which Claude Code mechanism serves each kind of moment. This rule instead names the existing text the agent already reads before that action, and adds a mechanism only when no such text exists.

1. Split the lesson into its instructions, one per moment; an instruction that applies at two moments counts as two. Name each moment: a step of a skill, a program the agent runs, a tool call, a file it edits, or a message it writes. Drop an instruction that matters only to the current conversation.
2. Put each instruction in the first of these places that the agent reads before it takes the action the instruction changes:
   1. **The step of the skill** the agent follows at that moment.
   2. **The instruction that tells agents to take that action**, wherever it is: a bullet of CLAUDE.md, a wiki page, a seat-brief. A lesson about how to remove code to test a test goes beside the sentence that tells agents to do so.
   3. **The agent-facing-message of the program** the agent has just run, such as its error, its refusal or the line it prints, when the instruction is about what to do next with that program; or the description of a skill or of an agent definition under `.claude/agents/`, which the agent reads when choosing one. The user, on 2026-10-10: CLAUDE.md is "not a place to add rules that are specific to a skill or tool".
   4. **A new hook**, when the moment is a tool call, a file edit or a reply that a hook can recognise and none of the places above exists. A hook's added text reaches the agent only after the call it watches; an instruction that must change that call itself needs a refusal, used only where the wrong action does harm the hook can detect. CLAUDE.md's rule on guards applies: name the behaviour the hook answers.
   5. **The seat-brief**, when only one agent-seat meets the moment.
   6. **The glossary**, when the instruction is what a word means.
   7. **A new bullet in CLAUDE.md**, only when the moment comes in every kind of work, agents will otherwise tend to get it wrong, and none of the places above exists.
3. If no moment can be named, or no place in step 2 fits, nothing gives recall at the moment of use. An instruction about one subject's design can be kept in that subject's GHI-MD, where an agent meets it only when reading that GHI-MD or asking ghi-info about the subject. Otherwise ask the user where to save it.

## Whether to build a store that recalls lessons by subject

Such a store would hold each lesson with a trigger, such as a tool name and a pattern on the command, the file path or the agent's reply, and one hook would deliver the lesson when the trigger matches. GHI [Trigger-first instruction delivery (moved from nedlern#1972): delivery timing as a property of every instruction — step-2 CLAUDE.md design input + carried design and scan](https://github.com/nedschorus/nedschorus/issues/30) designs such a hook for the legacy project's CLAUDE.md rules; the design is not built. Its limits would carry over: added text reaches the agent only after the call that triggered it, Codex delivery is left open, and the design proposes a budget of 25 ms of added time per call, at the 99th percentile over 1,000 calls that match nothing.

- **For.** Adding a lesson would be one entry in a file instead of a hook with its own code, tests and pull request.
- **Against.** In the eight lessons above, no instruction needed a new hook, so the saving does not arise yet. A store is a second place to look for an instruction, beside the skill or program the instruction is about, and the two would drift apart. The hook runs on every tool call.
- **Recommendation.** Do not build the store now; place each instruction by the rule above.
- **What would reopen the question.** Proposed: three or more hooks added to `.claude/settings.json` in four weeks whose only job is to carry one lesson, found with `git log -p -- .claude/settings.json` and judged from the pull request that added each hook.
- **The first measurable version, if reopened.** GHI 30's hook, delivering after a completed call (PostToolUse) only, so serving only instructions about the agent's next action, with one entry per such instruction and a line in the log-store for each delivery. For each entry, define in advance what in a transcript counts as a moment the instruction applies and what counts as breaking it. Measure, from the transcripts of the four weeks before the entry and the four weeks after, the share of those moments where the instruction was broken; also the number of deliveries and the hook's added time per call. Judge the entries in the store when the trial starts, four weeks after it starts; keep the store if that share falls for most of them.
