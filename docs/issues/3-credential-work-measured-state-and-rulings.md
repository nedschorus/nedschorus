Written because these facts existed only in one conversation and two relay files, and this project's standing rule is durable artifacts for a reader with zero context. ## The three namespaces, and the trap in their names

Three different kinds of name are in play, and they cross over between machines:

| | Unix user | GitHub account | Commit author text¹ |
|---|---|---|---|
| Ubuntu box | `nedlern` | `ubuntu-claude` | `new-vp` |
| Mac | `el` | `nedlern` | `new-vp` |

The trap: **"nedlern" is the box's Unix user and the Mac's GitHub account** — two unrelated things sharing one name. Any sentence saying "nedlern did X" is ambiguous until it says which namespace. (The specification already warns that `NedLern` is a substring of `NedLerner`; this is a second naming trap of the same family.)

¹`new-vp` is a project-wide author string both machines' git config sets; it names the project era, not an actor, and is exactly the kind of value this paragraph warns about. The commit author field is testimony, not evidence: it is text anyone can set. Server-side attribution rests on the activity log's actor field, which comes from the credential that performed the write — and therefore names an *account*, never which agent or human used it; it is exact exactly when accounts are per-actor — the same principle by which the gatekeeper's `Gatekeeper-agent` trailer is recorded-not-verified.

Why one Unix user means one GitHub identity: `gh` keeps its token in the Unix user's home (`~/.config/gh/hosts.yml` on the box; the login keychain on the Mac), owner-only. Every process of one Unix user reads the same token by default (an environment variable can override per-process). Different Unix user, different token, and ordinary file permissions keep each from the other's — a boundary that holds against unprivileged users and, per the sudo finding below, not against this box's agents. This is the mechanism C2 builds on.

## Branch protection on `main`, as measured (live read, 2026-08-18)

- `restrictions.users` held exactly one entry, `nedlern` (the GitHub account), when first measured on 2026-08-18; since 2026-08-19 it holds **two: `nedlern` and `ned-review-merge`** (§ The account layout, built). `enforce_admins` is on; force-push and deletion blocked.
- `required_pull_request_reviews` is **null**. Protection restricts **who**, not **how**: a listed account can push straight to main with no pull request and no review. The activity log confirms this is exercised: over the API's returned history, 37 PR merges and **276 direct pushes** to main (the direct pushes stop cold at 2026-08-16T04:21 — the merge-lane seat's practice, formalized by the user's ruling a day later, 2026-08-17; since then the count is 277 with exactly **one** named non-PR write: `b24e376`, the gate's own first live check-in, user-authorized 2026-08-18 — which is the detector working, and what a legitimate non-PR write looks like: the payload commit on main explains itself. Zero *unexplained* non-PR writes — which is what *this* log can show; in the activity log a PR merged without review looks identical to a reviewed one. The pull request itself, though, carries a review slot the API answers — see the review-recording measurement below).
- **The footgun (join, never replace):** a pull-request merge is itself a push to main. If a future account is given the pusher role by *replacing* `nedlern` on that list rather than joining it, the merge-lane seat can no longer merge and the interim lane closes. New accounts go alongside — with the ordinary exception that rotation or compromise of an existing entry is exactly when it *should* come off the list.
- Consequence of who-not-how: the interim lane (defined fully in `CLAUDE.md`'s how-a-change-reaches-main bullet — small atomic PRs, one stream per PR, merges consolidated at the merge-lane seat, deputization as the ruled exception) is a convention enforced by agent behavior on the Mac, not by GitHub. On the box it is enforcement — see the experiment.

## The fence experiment (2026-08-18, merge-lane seat; closes R12 — the row in the git-infra seat's design document recording that the restriction had never been tested by a disallowed attempt; git-infra is another agent seat, like the merge-lane and gatekeeper seats named here)

The restriction had never been tested by a disallowed attempt — every prior claim rested on reading the configuration. The test: two throwaway branches cut from main's tip; one given protection identical to main's, one left unprotected as a control; a box agent (`ubuntu-claude`, write permission, not on the allowed list) pushed the same commit to both in the same minute.

- Protected branch: **refused** — `GH006: Protected branch update failed`.
- Unprotected control: accepted.

Same credential, same commit; only the protection differed, so the refusal is caused by the protection. The box's fence is now proven, not asserted: `ubuntu-claude` cannot write through the restriction. Cleanup verified; main untouched throughout.

**Second finding, proved by the same test: the activity log records only writes that succeeded.** The refused push left no entry at all. A quiet log means "nothing got through"; it can never mean "nobody tried." An attempted-but-refused bypass leaves nothing in the activity log; the one place we have verified it lands is client-side, in the attempting agent's own session transcript (the `GH006` text). (GitHub's separate org audit log was not examined and is not ruled out.)

## Detecting bypasses (user-ruled: wait, but keep the instruments)

A commit that skips the gate announces nothing — in the repository it sits on main looking normal; the instruments below are what can surface it. Two instruments exist:

1. **Today, no build needed:** GitHub's activity API lists writes to main with how each arrived (within the API's retention and pagination limits — an incomplete query looks like an empty result, so treat a quiet answer as from-a-completed-query or not at all). `gh api repos/nedschorus/nedschorus/activity --paginate -q '.[] | select(.ref=="refs/heads/main" and .activity_type!="pr_merge")'` lists exactly the non-PR writes. Limits: on the Mac every actor reads `nedlern`, so it proves *that*, never *which agent* (the box's `ubuntu-claude` is attributable); and per the fence finding it sees only successes.
2. **After activation, the better one:** commits the gate checks in carry trailer lines nothing else writes; scanning for trailer-less commits *from the activation point forward* (record that point as a commit id at activation, or the scan has no start) finds what went around. Useless before activation (nothing on main has trailers) and forgeable by an agent that knows of it — it catches accident, not determination. Its acceptance test was T12, retired 2026-08-10 with the then-deleted trailer-absence audit; reviving the scan revives T12's slot.

**The ruling (2026-08-18): build no detector until an actual problem is detected.** The interim record is consistent with zero bypasses. The logs and instruments above stay documented so a future problem can be seen at all — visibility, not prevention, is what the record-keeping is for.

## The box's sudo state, and the C2 ruling

Measured 2026-08-18: `/etc/sudoers.d/nedlern-nopasswd` grants the box's Unix user `nedlern` — which every box agent runs as — `NOPASSWD:ALL`. Verified live: an agent session can become root with no password. Root reads every user's files, so on this box a dedicated Unix user's credential is readable by any agent that goes looking, the root-owned deployed copy is editable, and the sudoers rule itself is rewritable.

Narrowing the rule was considered and rejected on evidence: the 30-day sudo journal shows agents doing real system administration (managing a local service called nm-adapter, sshd config, ufw, samba, timeshift — none of it nedschorus work). An allowlist wide enough for the observed work — arbitrary service management, config edits under /etc — is in practice wide enough to reach a credential (constrained root-owned wrappers could in principle thread this, at real build cost; nothing of the kind exists here). Moving nedschorus seats to a non-sudo Unix user would restore the boundary and remains open; that is the `fleet` seat's machinery (the launchers and the seat model), not this pile's.

**The ruling (user, 2026-08-18): C2 is not a hard boundary on this box, and that is accepted.** The specification's claim that C2 makes "agents never push" *impossible rather than instructed* is therefore withdrawn for this box — the specification amendment is owed, listed below. What the box actually has is the allow-list fence (proven above), which is enforcement at GitHub rather than at the Unix boundary.

Related: the box's agent token carries the `workflow` scope, which C4 says agent credentials must never hold. **Removal deferred (user-ruled 2026-08-19, at the merge-lane seat):** the repository has zero CI workflows so the scope currently governs nothing, `restrictions.apps` on main is empty so an Actions run cannot push to main anyway, and swapping a live credential under three working seats is real operational risk for hypothetical gain. Named revisit triggers, not "later": the first workflow added to the repository, or any secret added to repository or organization. Measured scope of the eventual fix: one credential — `ubuntu-claude` is the only live worker token; `mac-claude`, `mac-codex` and `ubuntu-codex` are accounts nothing authenticates as. All four workers are outside collaborators, so the classic-token route (`repo` scope alone) is the expected path when the trigger fires.

## What the box can and cannot do (measured)

The box is not powerless and the fence is not the gate: `ubuntu-claude` has 113 pushes to non-main branches, 10 branches created, and opened 6 of the last 40 PRs. It is stopped from writing main at all — direct push and PR merge alike; of those, the merge is the action the lane needs, and it is the same one the interim lane reserves to the merge-lane seat. "Safe" and "useless" come apart cleanly. The consequence worth stating: the fence concentrates main-writing power on the `nedlern` GitHub account — usable from the Mac, the web, or any host holding its credential — and every Mac agent today authenticates as that account, indistinguishable from the user in any server-side record — a state that is now one launcher line per seat away from fixed, per the GH_TOKEN demonstration below. That is the strongest practical argument for the Mac-side dedicated account (C3): GitHub is already willing to tell actors apart; the Mac never gives it anything to tell apart.

## The account layout, built (2026-08-19, merge-lane seat with the user)

No longer a plan. Done and read back the same day:

| account | org role | repo permission | on main's allow-list | authenticates |
|---|---|---|---|---|
| `nedlern` | owner (now the only one) | admin | yes | the user; every Mac seat except merge-lane |
| `ned-review-merge` | member | admin (granted directly) | yes | the merge-lane seat |
| `mac-claude`, `mac-codex`, `ubuntu-codex` | outside collaborator | write | no | nothing yet |
| `ubuntu-claude` | outside collaborator | write | no | every box seat |

`NedLerner` no longer exists: renamed to `ned-review-merge` (rename is UI-only, done by the user), demoted from org owner to member, granted repo admin directly, and added to the allow-list beside `nedlern`. Protection otherwise unchanged: `enforce_admins` on, force-push and deletion off, `required_pull_request_reviews` still null.

**A trap that bit, recorded for the next account:** repository admin held *by virtue of org ownership* vanishes silently on demotion — the account keeps pushing fine and only fails later on admin-level reads such as branch protection. Grant the repo permission directly before or immediately after demoting.

**Token mechanics that cost time:** a fine-grained token reaches only repositories owned by its resource owner — collaborator access does not come along; and an org-resource-owner token needs owner approval, which on this org's free plan is UI-only (the API endpoints 404). The merge seat's token (`ned-review-merge`, this repo only, expires 2027-08-20) verifies: reads protection (so `audit` works from it), reads and writes contents and PRs; refused on protection writes; carries no `workflow`, no `admin:*`.

**Consequence — enforcement is switchable now, not after any worker migration.** Relay 8's claim that C3 must come first was too pessimistic: GitHub forbids only the PR's *author* account from approving, and the PR boundary already has two identities — Mac seats author as `nedlern`, the merge seat reviews and merges as `ned-review-merge`. Turning on `required_pull_request_reviews` is one call, reversible by one call. The trade, stated because it is real: with `enforce_admins` on there is no override, so a lapsed merge-seat token or an unposted review means *nothing* merges until the user approves from his own account. Not done; the merge-lane seat holds it for the user's explicit word.

**Resolved same day, demonstrated rather than assumed: per-seat identity needs no Unix-user split.** A push from the Mac, from the Unix user whose keyring holds `nedlern`, with `GH_TOKEN` set to the `ned-review-merge` token and nothing else changed, landed in the activity log as `actor: ned-review-merge`. Per-process, keyring untouched, the ordinary configured credential helper (`gh auth git-credential` honours `GH_TOKEN`; the per-host override in `~/.gitconfig` routes github.com to it) — so this is what a normally-launched seat gets. Cleanup verified, main untouched. **Correction this forces on an earlier relay's conclusion:** Mac attribution does *not* wait on the Unix-user work; identity follows the environment variable, not the Unix user. C2's Unix split remains wanted only for what it actually provides — filesystem isolation of the credential — and is off the critical path for attribution. What attribution now costs: one token per account, one `GH_TOKEN` line in each seat's launcher. **Not done:** no launcher exports `GH_TOKEN` yet — the merge seat uses its token by hand — and that wiring belongs to the `fleet` seat, which owns the launchers.

## Review recording and the native enforcement lever (measured 2026-08-19, merge-lane seat)

GitHub records reviews per pull request, and the API answers the slot — so the record *can* distinguish a reviewed merge from an unreviewed one. Measured over the last twenty merged PRs: **eight carry a recorded review** (#91, #90, #88, #87 among recent ones); the rest carry none. Absence proves nothing, because filling the slot is optional. The deciding specimen is **#92**: the PR whose review demonstrated the case-folding bypass in the gate's own-source refusal — the sharpest find of the cycle, which changed the gate's code — carries zero recorded reviews; that finding survives only in a machine-local transcript, which is disposable.

**The enforcement lever already exists and needs no build:** main's `required_pull_request_reviews`, currently null. Turned on, GitHub itself refuses a merge without an approving review — no gate code, no trailer, no audit. **It cannot be turned on yet, and the blocker is C3:** GitHub does not let a PR's author approve their own PR, and today one account (`nedlern`) both opens and merges everything Mac-side. Flipping it now would deadlock the lane completely, and with `enforce_admins` on, nothing could override. So per-agent accounts are a *prerequisite for mechanical review enforcement*, not merely an attribution improvement — the strongest argument for C3 yet. **Verify before acting:** the self-approval restriction is GitHub product behavior, reported not tested; confirm it before anyone flips the setting, because getting it wrong locks main for every seat.

Meanwhile (user-ruled 2026-08-18, explicit stopgap): the merge-lane seat posts its review to the PR as a GitHub review before merging, stating whether an independent reviewer was used. A habit in that seat's machine-local instruction file, deleted when real enforcement lands.

This measurement is the kind of evidence a revisit of the declined slice 6 would weigh; whether it returns is the user's ruling, and nothing here presumes it.

## The guardian direction (user-set 2026-08-18; direction, not yet specification)

Where review-at-the-gate is heading, recorded so the reasoning survives:

- **Structure over instructions.** The merging agent is trustworthy by *position*, not by prompt: the design goal is that it authors nothing it merges, so it has no stake in promoting its own work. Today nothing enforces that goal — commit author text is testimony and every Mac actor is one account. **What makes it mechanical (measured 2026-08-19): two role accounts.** GitHub forbids a PR's author account from approving it, so one account that opens PRs and a different one that approves and merges is the entire requirement — one account more than today, and it does not grow with agent count. Honest limit: that enforces author≠approver at the *account* level; an agent that writes under the author account and approves under the merge account is invisible to it, which is what Unix-level credential separation later hardens, and what stays convention until then. Attribution is the goal that scales with actors, and accounts for it attach to seats or machines, which persist — never to agent instances, which do not (`ubuntu-claude` is the machine-level pattern already working). This is [nedschorus#31](https://github.com/nedschorus/nedschorus/issues/31) Part 2's author≠checker requirement (its section on what a gate cannot check: the one lever on review quality is that author and checker are different parties), arrived at independently by the user.
- **Script for the mechanical, agent for the judgment** — the pattern proven by the GHI (GitHub-issue) machinery — the project's issue tooling, a script plus the dedicated headless issue agent, and project doctrine as "code beats prompts." Checks a script can decide (paths touched, author≠merger, tests green, secrets) are never prompts.
- **Interactive, not headless** — the GHI agent is headless because its job is mechanical; a merge guardian's value is judgment, exactly where conversation must be possible: the user talking to it, and refused agents pleading their case to it rather than hunting for a way around. Refusals should be conversational rather than final — a refused agent argues its case to the guardian instead of hunting for a route around it. Open question for the real design: where pleading ends; an appeal loop needs a bound and a final authority or a refused check-in stays open forever.
- **Spawn-more fixes availability, not judgment.** Instances share instructions, model, and tendencies — different context and sampling vary the outputs, but the blind spots correlate, so spare bodies are not independent judgment. Cross-runtime diversity (a Codex leg) is the decorrelator — an optimization here, not a safety requirement, because of the next ruling.
- **The error standard (user-ruled): occasional bad merges are acceptable.** The user would err too, and judges the agents better at this call than himself — his stated risk assessment, recorded as such rather than as a measured fact; and a *pattern* of errors is corrected by amending the guardian's instructions and the submitting agents'. This works because merge-tier errors are mostly recoverable — the remedy is a revert through the same door — with named exceptions that stay judgment-worthy: a committed secret remains disclosed in history however fast the revert, and external effects (a deploy, a notification) do not un-happen. Mechanism guards the unrecoverable class: history rewrites are blocked by protection; the credential half is *in progress*, not handled — C2 is soft on the box by ruling, and the box token's `workflow` scope is still to be reissued. Patterns are only findable if errors are visible, which is what the record-keeping above is for.
- **Credential shape:** if any spawned guardian instance can merge, the credential belongs to the *role* — one dedicated account, on the allow-list alongside the existing entry (with the rotation exception above). Known limit, accepted: instances sharing the role credential are indistinguishable in any server-side record; fine for enforcement, a bound on attribution. Untested link, load-bearing for both this and Mac-side C2: the launcher wiring: exporting a per-seat `GH_TOKEN` in `scripts/launch-claude-mac` (per-seat *identity* is proven — see the demonstration above — so no Unix-user work is on this path; a different-Unix-user launch matters only if C2's filesystem isolation is later wanted on the Mac). The launchers belong to the `fleet` seat.
