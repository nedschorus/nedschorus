# The Bash guards replay reads a stored file of distinct recorded command pairs, reuses main's readings and reads many commands in each new process

The Bash guards replay, `nc-systems/general-tools/bash-guards-verdict-changes-between-two-git-refs-on-transcript-recorded-commands-check.py`, collects every Bash command recorded in both machines' transcripts and reads each one through every Bash guard twice: at main, and at a pull request's head commit. A full invocation of the replay takes one to two hours on a loaded ned-box. This GHI makes the replay cheap enough that every pull request it covers replays every recorded command: the replay reads a stored pairs file in the log-store instead of the transcripts, takes main's readings from a cache, and in its new-process mode reads a few hundred commands in each new process instead of one. A job in the daily step of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) adds each day's new pairs to that file.

## Why

The user decided on 2026-10-13 that every pull request that changes a Bash guard or the shell reader replays the recorded real commands of both machines, and that a changed verdict blocks the merge (item 3 of his reply in reboot-test's agent-session 13be3b1b-2966-4c0d-83ad-3d3738bc2df2, as PR [Bash guards: one committed script replays recorded real commands at two refs and blocks on a changed verdict](https://github.com/nedschorus/nedschorus/pull/1278) records). merge-lane-2 runs the replay for each such pull request. At one to two hours an invocation, as agent-seat reboot-test reported on 2026-10-16, each replay holds up the merge and takes a large share of ned-box's processors while it reads. By default the new-process mode also reads only a subset of the pairs, so most pairs are never read in that mode.

## What exists today

Measured on ned-box on 2026-10-16 with the replay's own `recorded_command_pairs()` and a count of the same transcripts:

- **What the replay reads.** Every `.jsonl` file under four directories: `~/.claude/projects` on the machine the replay runs on, and the log-store's `transcripts/mac/projects`, `transcripts/ned-box` and `transcripts/recovered`. On ned-box these are 16,970 files holding 362,090 Bash calls; reading them takes about 35 seconds. Each invocation reads all of them again; nothing is stored between invocations.
- **Duplicates are already removed.** The replay keeps each distinct pair of exact command text and working directory once, in the order first seen: 213,804 pairs. Keyed on the command text alone there would be 212,438, 0.6% fewer. Where each pair was first seen is not kept.
- **Nothing is cached.** Each invocation checks out main and the pull request's head commit as two worktrees and reads every pair at both, in three modes: in-process, with the guards' git and gh probes stubbed, on every pair; the search-file guard's `main()` with each pair's own working directory, on every pair; and new-process, by default only on the pairs that match `NEW_PROCESS_SUBSET_PATTERN` (a heredoc, a case terminator or `~`), 58,770 pairs, or on every pair with `--new-process-pairs all`. Main's readings are therefore read again by every invocation, though main's guards change far less often than the pull requests that are replayed.
- **How readings run in parallel.** Each mode at each ref is one step in a fresh Python interpreter, and the steps run one after another. Inside a step, a `ProcessPoolExecutor` of `--jobs` workers (by default the processor count minus one), at nice 15, reads tasks of 200 pairs each (`PAIRS_PER_TASK`).
- **One new process per command in new-process mode.** In new-process mode the shell reader, `nc-systems/general-tools/shell-command-tree-sitter-bash-reader-common.py`, starts a new Python process for every reading (`_simple_commands_in_a_new_process()`, which runs the reader with `--read-command-on-standard-input` on one command). The replay's comment puts this at about 50 times slower than reading in-process, and every guard that loads the reader reads through it, so one pair starts several processes. A hook takes the same path when the parser was installed only for a new process, so the new-process mode tests a path real hooks use.
- **What the transcripts record of the guards' verdict.** A Bash call that a PreToolUse hook refused has a tool result marked as an error whose text begins `PreToolUse:Bash hook error: ` followed by the refusal; the text does not name the hook. Context a PreToolUse hook added is recorded as an attachment of type `hook_additional_context` with `hookEvent` `PreToolUse`. Seen in ned-box's transcripts on 2026-10-16.

Search receipt: `scripts/ghi-info-ask.py --include-closed` on 2026-10-16, asked for a GHI about a stored file of pairs for the replay, cached main readings, batched new-process reads or a daily job that adds to such a file, found none. The nearest is GHI [Replace the hand-written parsers in the project's hooks and scripts with real parsers](https://github.com/nedschorus/nedschorus/issues/1196), whose provisional additions record replays as correctness evidence and say nothing of their cost.

## What is decided

The user approved the plan below with "y" in reboot-test's agent-session on 2026-10-16, after saying: "I suspect if you remove dups we can run them all, but the maint cycle will want to add new, non dups as they occur." Asked whether duplicates are matched by exact text alone or by the pair of command text and working directory, since two guards read the working directory and ignoring it would cut only 0.6%, the user answered on 2026-10-16: "Y, keep the directory".

- The replay runs on a corpus of distinct commands, deduplicated by the pair of exact command text and working directory: a log-store file holding each distinct pair once, with where it was first seen. The work below calls this file the stored pairs file, since the replay already calls each command with its working directory a pair, and keys each entry on the exact text of the command and its working directory, as the replay does today, for the reason step 1 gives.
- Every pull request the replay covers replays every pair in the file, with no sampling.
- Main's readings are cached, keyed on a hash of the shell reader's and the guards' files, so most pull requests pay only for the reading at their head commit.
- The new-process pass is batched: a few hundred commands in each new process.
- Merging near-duplicates, such as one command with a different path or hash, is left out: deduplicate by the pair of exact command text and working directory first, then measure.
- A job in the daily step adds the distinct pairs of new transcripts to the stored pairs file, as the eleventh job of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) says.

The measurement above shows that deduplication by the pair of command text and working directory was already in place (362,090 calls to 213,804 pairs), so the time the plan saves comes from the cache and the batching, not from removing duplicates. The first full invocation after the work below measures how much.

## The work

1. **The stored pairs file.** The log-store directory `nedlern@ned-box:/home/nedlern/nedschorus-logs/bash-guards-replay-stored-distinct-command-pairs/` holds the stored pairs file, `stored-distinct-command-pairs.jsonl`, with one JSON line per distinct pair of exact command text and working directory: the command, the working directory, and the transcript file, line number and time at which the pair was first seen. The key keeps the working directory because the force-push guard and the search-file guard's `main()` read it, so one command can get two verdicts in two directories; keeping it costs the 0.6% measured above. Beside that file, `transcript-read-positions.json` records how far each transcript file has been read, so an append reads only what is new. The replay reads the stored pairs file by default, as `--pairs-file` reads a pairs file today, and no longer reads the transcripts itself; today's `recorded_command_pairs()` stays in the replay script, which gains a mode that appends the new pairs to the stored pairs file, and the daily job runs that mode. The replay runs on ned-box, where the log-store is, as its default transcript directories already require. Every file in the directory is written to a temporary file and renamed into place, so a reader never sees a partial file.
2. **Batched new-process reads.** In the replay's new-process mode, the reader sends each command to a child process that reads one JSON request per line, in which a newline inside a command is escaped as JSON escapes it, and starts a fresh child after a number of commands set by a constant, as `PAIRS_PER_TASK` is, starting at a few hundred. A child that dies or runs past the per-pair timeout makes the reading of its current command a failed reading, which ends the replay with exit status 2 as a failed reading does today. Each request crosses the same JSON conversion, `_reader_output_to_json()` and `_reader_output_from_json()`, that the one-command path uses, so the replay still tests what a hook's new process does. A hook outside the replay keeps one process per command.
3. **Every pair in every mode.** Once batching works, `--new-process-pairs` defaults to `all`, and `NEW_PROCESS_SUBSET_PATTERN` and the `subset` choice are removed.
4. **The cache of main's readings.** `base-ref-readings-cache.jsonl`, in the same directory, holds the reading of each pair in each mode, keyed on the pair, the mode, and a hash of the content, at the base ref's commit, of every file that decides a reading: each file in the replay's `GUARDS`, every file those guards load from the repository, such as the shell reader and other `-common.py` modules, `.claude/settings.json`, and the replay script itself, whose reading functions and probe stubs are part of every verdict. The base ref is main for every pull request merge-lane-2 replays, but the key is the hash, not the ref's name. When the cache holds entries for the base ref's hash, the replay reads only the pull request's head commit, and reads at the base ref only the pairs the cache lacks, adding them. When it holds none, the replay reads the base ref in full and writes its entries under the new hash, removing the entries of older hashes.
5. **Tests**, in `nc-systems/general-tools/tests/bash-guards-verdict-changes-between-two-git-refs-on-transcript-recorded-commands-check-test.py`: the replay reads the stored pairs file; an append reads only lines added since the last append and adds only pairs not already present; a cache with a matching hash is used, and a change to one guard file makes the replay read main in full; batched new-process readings give the same rows as one process per command.
6. **The measurement.** The replay appends each full invocation's time for each mode, which it only prints today, to `full-invocation-times.jsonl` in the same directory. After steps 1 to 4, the first full invocation with every pair in every mode is recorded here in this GHI-MD, and its time sets the budget the daily job reports against, written to `full-invocation-time-budget.json` in the same directory; the daily job reports any full invocation that takes longer than the budget.
