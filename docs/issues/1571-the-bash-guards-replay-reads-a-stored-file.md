# The Bash guards replay reads a stored file of distinct recorded command pairs, reuses main's readings and reads many commands in each new process

The Bash guards replay, `nc-systems/general-tools/bash-guards-verdict-changes-between-two-git-refs-on-transcript-recorded-commands-check.py`, collects every Bash command recorded in both machines' transcripts and reads each one, with the working directory it ran in, through every Bash guard at two refs, main and a pull request's head commit, in three modes at each ref. This GHI makes that check a test suite that blocks the merge, cheap enough to cover every pair recorded up to the last time a guard pull request refreshed the check: a new test suite reads a stored pairs file in the log-store instead of the transcripts, and compares the pull request's readings with a baseline of main's readings committed to the repository, so main is not read again for each pull request. The replay script stays, for runs by hand and for writing the baseline. A job in the daily step of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) adds each day's new pairs to the stored pairs file.

## Why

The user decided on 2026-10-13 that every pull request that changes a Bash guard or the shell reader replays the recorded real commands of both machines, and that a changed verdict blocks the merge (item 3 of his reply in reboot-test's agent-session 13be3b1b-2966-4c0d-83ad-3d3738bc2df2, as PR [Bash guards: one committed script replays recorded real commands at two refs and blocks on a changed verdict](https://github.com/nedschorus/nedschorus/pull/1278) records). merge-lane-2 runs the replay by hand for each such pull request. On 2026-10-16 a full invocation took one to two hours on a loaded ned-box, as agent-seat reboot-test reported then, and the new-process mode read only a subset of the pairs. Commit aa700745 on main, "Bash guards replay: one long-running shell reader child per pool worker; every pair in new-process mode", cut a full invocation of every pair in every mode to 491 seconds on ned-box; merge-lane-2's walk-minutes record "the replay check now takes about 8 minutes, down from about 100" on 2026-10-17. What remains is that the check is run by hand, reads the transcripts and main again each time, and is not a test suite.

## What exists today

Measured on ned-box on 2026-10-16 with the replay's own `recorded_command_pairs()` and a count of the same transcripts. Since then, commit aa700745 on main has changed three things these bullets describe: the new-process mode now reads every pair, through one long-running child process per pool worker, and `--jobs` defaults to half the processors. Each bullet says which part is from before that commit.

- **What the replay reads.** Every `.jsonl` file under four directories: `~/.claude/projects` on the machine the replay runs on, and the log-store's `transcripts/mac/projects`, `transcripts/ned-box` and `transcripts/recovered`. On ned-box these are 16,970 files holding 362,090 Bash calls; reading them takes about 35 seconds. Each invocation reads all of them again; nothing is stored between invocations.
- **Duplicates are already removed.** The replay keeps each distinct pair of exact command text and working directory once, in the order first seen: 213,804 pairs. Keyed on the command text alone there would be 212,438, 0.6% fewer. Where each pair was first seen is not kept.
- **Nothing is cached.** Each invocation checks out main and the pull request's head commit as two worktrees and reads every pair at both, in three modes: in-process, with the guards' git and gh probes stubbed, on every pair; the search-file guard's `main()` with each pair's own working directory, on every pair; and new-process. Before commit aa700745 the new-process mode read by default only the 58,770 pairs that matched a heredoc, a case terminator or `~`; it now reads every pair. Main's readings are therefore read again by every invocation, though main's guards change far less often than the pull requests that are replayed.
- **How readings run in parallel.** Each mode at each ref is one step in a fresh Python interpreter, and the steps run one after another. Inside a step, a `ProcessPoolExecutor` of `--jobs` workers (by default half the processors since commit aa700745, the processor count minus one before it), at nice 15, reads tasks of 200 pairs each (`PAIRS_PER_TASK`).
- **One new process per command in new-process mode, before commit aa700745.** In new-process mode the shell reader, `nc-systems/general-tools/shell-command-tree-sitter-bash-reader-common.py`, starts a new Python process for every reading (`_simple_commands_in_a_new_process()`, which runs the reader with `--read-command-on-standard-input` on one command). The replay's comment then put this at about 50 times slower than reading in-process, and every guard that loads the reader reads through it, so one pair starts several processes. Commit aa700745 replaced this, in the replay only, with one long-running child process per pool worker. A hook takes the same path when the parser was installed only for a new process, so the new-process mode tests a path real hooks use.
- **What the transcripts record of the guards' verdict.** A Bash call that a PreToolUse hook refused has a tool result marked as an error whose text begins `PreToolUse:Bash hook error: ` followed by the refusal; the text does not name the hook. Context a PreToolUse hook added is recorded as an attachment of type `hook_additional_context` with `hookEvent` `PreToolUse`. Seen in ned-box's transcripts on 2026-10-16.

Search receipt: `scripts/ghi-info-ask.py --include-closed` on 2026-10-16, asked for a GHI about a stored file of pairs for the replay, cached main readings, batched new-process reads or a daily job that adds to such a file, found none. The nearest is GHI [Replace the hand-written parsers in the project's hooks and scripts with real parsers](https://github.com/nedschorus/nedschorus/issues/1196), whose provisional-additions record replays as correctness evidence and say nothing of their cost.

## What is decided

The user approved the plan below with "y" in reboot-test's agent-session on 2026-10-16, after saying: "I suspect if you remove dups we can run them all, but the maint cycle will want to add new, non dups as they occur." Asked whether duplicates are matched by exact text alone or by the pair of command text and working directory, since guards read the working directory and ignoring it would cut only 0.6%, the user answered on 2026-10-16: "Y, keep the directory".

- The replay runs on a corpus of distinct commands, deduplicated by the pair of exact command text and working directory: a log-store file holding each distinct pair once, with where it was first seen. The work below calls this file the stored pairs file.
- Every pair in the stored pairs file is read, with no sampling.
- The new-process pass reads many commands in each new process. Commit aa700745 has done this; step 2 says how.
- Merging near-duplicates, such as one command with a different path or hash, is left out.
- A job in the daily step adds the distinct pairs of new transcript lines to the stored pairs file, the eleventh job of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058); step 13 edits that job to match this design.

The user decided on 2026-10-18, at about 00:22Z, with "y" to item 11 of merge-lane-2's approval-walk merge-lane-2-everything-waiting-on-the-user-2026-10-15, that for every pull request that adds or changes a Bash guard, the replay's list of commands now refused or now allowed blocks the merge until the pull request's reviewer accepts each command on the list; a wrong entry goes back to the author, and an empty list blocks nothing. He gave reboot-test the design, to be judged by what is "good over the next 10,000 PRs". In approval-walk bash-guards-replay-check-which-pull-requests-and-how-it-blocks, on 2026-10-18 and 2026-10-19, he agreed to each recommendation below (walk-minutes nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/bash-guards-replay-check-which-pull-requests-and-how-it-blocks-minutes.md):

- **Where the check runs** (item 2): as an ordinary test suite under the test runner's recorded inputs, not as a step in merge-lane-2's review program alone. The test runner records the tracked files of the checkout that a suite and its child processes read, so a pull request that changes a guard, a tracked file a guard loads, the suite or the baseline selects the suite, without a list of guard names. It also selects the suite in the runner's other cases, such as a change to `.claude/settings.json`.
- **How main's readings are got** (item 3): from a baseline file committed to the repository, a golden file for a snapshot test. The cache of main's readings that this GHI-MD planned is dropped.
- **Where the reviewer's acceptance is kept** (item 4): in the merged baseline's diff, checked by merge-lane-2's review program against a record in the log-store that holds the changed commands' text.
- **What lives in the repository** (item 5): only the baseline, which names each pair by a plain SHA-256 hash of its command text and working directory, with no HMAC, and holds no command text, working directory or guard message. The stored pairs file and the records of changed commands stay in the log-store. The repository is public. A plain hash of a short command can be found by hashing guesses; the user accepted that, since a check on 2026-10-19 of all 221,278 recorded pairs for token-shaped text found only dummy values written for tests, so a guess can reveal only an ordinary command.
- **Which pull requests get the check** (item 6): every pull request that changes a Bash guard or any file a guard loads, such as the shell reader.
- **Guard names** (item 7): the seven Bash guards keep their directories and names.

The measurement above shows that deduplication by the pair of command text and working directory was already in place (362,090 calls to 213,804 pairs), so the time saved comes from the baseline and the batching, not from removing duplicates.

## The work

1. **The stored pairs file, to be built.** The log-store directory `nedlern@ned-box:/home/nedlern/nedschorus-logs/bash-guards-replay-stored-distinct-command-pairs/`, which does not exist yet, will hold `stored-distinct-command-pairs.jsonl`, with one JSON line per distinct pair of exact command text and working directory: the command, the working directory, and the transcript file, line number and time at which the append first met the pair. The file only grows at its end; nothing reorders, removes or rewrites its lines, so its first N lines are always the same N pairs. The key keeps the working directory because the force-push guard, the Markdown push reminder and the search-file guard read it, so one command can get two verdicts in two directories. Beside that file, `transcript-read-positions.json` records how far each transcript file has been read. The replay script gains an append mode, which reads with today's `recorded_command_pairs()` the transcript lines past each recorded position, adds the pairs not already in the file, and then updates the positions; the daily job runs that mode. The replay script and the suite read the stored pairs file instead of the transcripts by default; `--pairs-file` keeps its one-JSON-list format for hand runs. Everything runs on ned-box, where the log-store is.
2. **Done in commit aa700745: batched new-process reads.** In the replay's new-process mode, each pool worker keeps one long-running child process of the shell reader for its whole life, sends it one JSON request per line, and starts a new child at the next request after a failure. A child that dies or runs past the per-pair timeout makes the reading of its current command a failed reading, which ends the replay with exit status 2. Each request crosses the same JSON conversion, `_reader_output_to_json()` and `_reader_output_from_json()`, that the one-command path uses, so the replay still tests what a hook's new process does. A hook outside the replay keeps one process per command. The plan approved on 2026-10-16 said a few hundred commands per child; the commit keeps one child per worker instead.
3. **Done in commit aa700745: every pair in every mode.** `--new-process-pairs` defaults to `all`, and the subset choice is removed.
4. **Dropped: the cache of main's readings.** The committed baseline of step 5 replaces it, by the user-ruling of 2026-10-18 above.
5. **The baseline**, `nc-systems/general-tools/tests/bash-guards-verdict-baseline-on-transcript-recorded-commands.jsonl`, to be built. Its first line is a header with three fields: the guard-files hash, the number N of stored pairs it covers, which are the first N lines of the stored pairs file, and the main commit that the regeneration of step 7 fetched. The guard-files hash is the SHA-256 of the paths and contents of the Bash guards named in the checkout's `.claude/settings.json` and every tracked file of the checkout they load, which one shared function, used by the regeneration program and the suite, lists by loading each guard and reading which checkout files Python opened. Each further line is `[pair hash, mode, guard, decision, verdict hash]`, the guard being its repository-relative path, or `search-file main()` for that mode, for one reading whose decision is not a pass, sorted, written with `json.dumps(..., sort_keys=True)` so one set of readings always gives the same bytes. A pass is a reading whose decision is `"passed"`, `None` for the force-push guard, or `"silent"` with exit status 0 for the search-file guard's `main()`. The decision is the first element of the replay's row, such as `"refused"` or `"added context"`, and the verdict hash is the SHA-256 of the row's `json.dumps(..., sort_keys=True)`, so a change in a guard's probe calls or exit status changes the line without the line holding the probe text, which carries working directories. The pair hash is the SHA-256, in hexadecimal, of the UTF-8 bytes of `json.dumps([command, working directory], ensure_ascii=False)`, computed by one shared function. Measured on 2026-10-17 at main in one mode, 4,352 pairs got a reading that is not a pass from at least one guard, 4,517 lines; with a line per mode the file is expected at about twice that, about 2 MB, and the first regeneration measures it.
6. **The suite**, `nc-systems/general-tools/tests/bash-guards-verdict-baseline-on-transcript-recorded-commands-test.py`, to be built. It first computes the guard-files hash of the checkout and fails if it differs from the header's, printing that the guard files changed and the regeneration command of step 7 to run. Otherwise it reads the first N stored pairs at the checkout in all three modes and fails on any line that differs from the baseline, printing each difference by pair hash, mode and guard. It fails, never prints `SKIP`, when the stored pairs file is missing or holds fewer than N lines, and when a reading is a failed reading. On main the hash matches and N stays where the last guard pull request left it, so the daily full test run on main passes while the daily job adds pairs. The search-file guard's `main()` mode reads in a fixed directory holding `-v.txt` and `a.txt`, as the replay's in-process mode does, instead of each pair's own working directory, and the baseline is made with the same directory, so the readings do not depend on what is in a pair's working directory. The stored pairs file is added to `TEST_SANDBOX_HOME_PATHS_SHOWN_READ_ONLY` in `scripts/run-all-test-suites.py`, so the suite can read it inside the test sandbox. A guard that the pull request adds has no main reading, as PR [Bash guards replay: list and block on recorded commands a guard the pull request adds would refuse](https://github.com/nedschorus/nedschorus/pull/1627) makes the replay script treat it; every line it adds is a change. A guard the pull request removes takes its lines with it, and each removed line is a change to a pass.
7. **The regeneration program**, `nc-systems/general-tools/bash-guards-verdict-baseline-on-transcript-recorded-commands-regenerate.py`, to be built. It runs on ned-box outside the test sandbox. It fetches main, `git fetch origin main:refs/remotes/origin/main`, stops with exit status 2 when the fetch fails, and uses the one commit it fetched throughout. It reads at that main commit, in a worktree, the stored pairs that main's baseline does not cover, then reads every stored pair at the checkout, and rewrites the baseline with a new header. It stops with exit status 2 and writes nothing when a reading fails. It writes the verdict-baseline-changes record, `nedlern@ned-box:/home/nedlern/nedschorus-logs/bash-guards-replay-stored-distinct-command-pairs/verdict-baseline-changes/<blob>.jsonl`, named after the new baseline's git blob hash, as `git hash-object` computes it, since the commit that will hold the baseline does not exist yet. Each line of the record has a `kind`: `coverage-addition`, a baseline line of main's for a newly covered pair, or `change`, with the pair hash, mode, guard, command text, working directory, main's line and the checkout's line, either of which is absent for a pass. `--show <pair hash>` prints one pair's command and working directory for the author. `--branch <branch>` fetches that branch, regenerates in a ned-box worktree of it, removes the worktree, writes the record, and prints the path on ned-box of the new baseline, for an author on the Mac, who copies it with `scp`. A pull request may also regenerate the baseline with no guard change, to cover the pairs added since the last regeneration.
8. **The review program's check.** On a pull request whose baseline differs from main's, merge-lane-2's review program, `scripts/merge-lane-pull-request-worktrees-reviewer-brief-codex-review-and-head-tests-run-without-merge.py`, runs the regeneration program's `--verify-pull-request-head <commit>` mode. That mode finds the record by `git rev-parse <commit>:<baseline path>`, fails when the record is missing, and fails unless the pull request's baseline lines below the header equal main's baseline lines at the header's main commit, with the coverage additions added and each change applied: a change replaces main's line by the checkout's, adds the checkout's line when main's was a pass, and removes main's line when the checkout's is a pass. It also rereads, at that main commit, the stored pairs between main's covered count and the header's, and fails if any reading differs from the record's coverage additions. `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` then puts the changes into the reviewer's brief, which stays on ned-box. An empty changes list blocks nothing. An entry is wrong when the pull request's description does not say that the guard means to make that change; the description describes the change in words and never quotes a recorded command, since it is public, and the reviewer's finding names the pair hash, mode and guard only. For a wrong entry, the author reads the command with `--show`, then either fixes the guard and regenerates, or, when the change was intended, adds it to the description, and pushes one commit on top.
9. **A second guard pull request.** Two guard pull requests open at once both rewrite the header, so the second normally conflicts with main once the first merges, and `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`. As its report says, the second author resolves the conflict in the merge by taking main's baseline, then regenerates in one ordinary commit after the merge, and pushes the merge and that commit once; the new record covers only the second pull request's changes against the new main. If git merges the two baselines without a conflict, the suite still fails on the header's main commit or hash, and the author regenerates the same way.
10. **The Mac.** The Mac has no test sandbox and no log-store. The test runner gains a table of suites that need the log-store and run only on ned-box; on the Mac it reports such a suite as not selected, with that reason, instead of a `SKIP`, since a suite that prints `SKIP` is selected again at every later test run. A Mac author's guard pull request therefore reaches review without a regenerated baseline, and merge-lane-2's head test run on ned-box fails the suite. The author's fix-round runs `ssh nedlern@ned-box 'python3 ~/Projects/nedschorus/nc-systems/general-tools/bash-guards-verdict-baseline-on-transcript-recorded-commands-regenerate.py --branch <branch>'` against the frozen-head, copies the baseline it names with `scp nedlern@ned-box:<path> <baseline path>`, commits it, and pushes that one commit on top, as CLAUDE.md's fix-round allows.
11. **Tests**, each in the pull request that builds what it tests: in `nc-systems/general-tools/tests/bash-guards-verdict-changes-between-two-git-refs-on-transcript-recorded-commands-check-test.py` and the new programs' own test files. The replay reads the stored pairs file; an append reads only lines added since the last append and adds only pairs not already present; the suite fails on a changed line, on a changed guard-files hash, on a missing or short stored pairs file and on a failed reading, and passes on pairs past N; `--verify-pull-request-head` fails on a missing record and on a baseline that differs from the record.
12. **The measurement.** The test runner already records each suite's time and stops a suite that runs past its limit, 1,800 seconds for a suite with no passing run. The first passing run's time of the suite of step 6, and the regeneration program's time, which it prints, are recorded in this GHI-MD. A single-ref read of every pair in every mode is expected near half of commit aa700745's 491 seconds.
13. **GHI 1058's eleventh job.** An edit to GHI 1058's GHI-MD makes its eleventh job run step 1's append mode only, and removes its reading of new pairs at main and its cache, which step 4 drops.
