# The Bash guards replay reads a stored file of distinct recorded command pairs, reuses main's readings and reads many commands in each new process

The Bash guards replay, `nc-systems/general-tools/bash-guards-verdict-changes-between-two-git-refs-on-transcript-recorded-commands-check.py`, collects every Bash command recorded in both machines' transcripts and reads each one through every Bash guard twice: at main, and at a pull request's head commit. A full invocation of the replay takes one to two hours on a loaded ned-box. This GHI makes the replay cheap enough that every pull request it covers replays every recorded command, and makes the replay a test suite that blocks the merge: the replay reads a stored pairs file in the log-store instead of the transcripts, takes main's readings from a committed baseline file, and in its new-process mode reads a few hundred commands in each new process instead of one. A job in the daily step of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) adds each day's new pairs to that file.

## Why

The user decided on 2026-10-13 that every pull request that changes a Bash guard or the shell reader replays the recorded real commands of both machines, and that a changed verdict blocks the merge (item 3 of his reply in reboot-test's agent-session 13be3b1b-2966-4c0d-83ad-3d3738bc2df2, as PR [Bash guards: one committed script replays recorded real commands at two refs and blocks on a changed verdict](https://github.com/nedschorus/nedschorus/pull/1278) records). merge-lane-2 runs the replay for each such pull request. At one to two hours an invocation, as agent-seat reboot-test reported on 2026-10-16, each replay holds up the merge and takes a large share of ned-box's processors while it reads. By default the new-process mode also reads only a subset of the pairs, so most pairs are never read in that mode.

## What exists today

Measured on ned-box on 2026-10-16 with the replay's own `recorded_command_pairs()` and a count of the same transcripts. Since then, commit aa700745 on main, "Bash guards replay: one long-running shell reader child per pool worker; every pair in new-process mode", has done steps 2 and 3 below, so the new-process bullets here describe the replay before it:

- **What the replay reads.** Every `.jsonl` file under four directories: `~/.claude/projects` on the machine the replay runs on, and the log-store's `transcripts/mac/projects`, `transcripts/ned-box` and `transcripts/recovered`. On ned-box these are 16,970 files holding 362,090 Bash calls; reading them takes about 35 seconds. Each invocation reads all of them again; nothing is stored between invocations.
- **Duplicates are already removed.** The replay keeps each distinct pair of exact command text and working directory once, in the order first seen: 213,804 pairs. Keyed on the command text alone there would be 212,438, 0.6% fewer. Where each pair was first seen is not kept.
- **Nothing is cached.** Each invocation checks out main and the pull request's head commit as two worktrees and reads every pair at both, in three modes: in-process, with the guards' git and gh probes stubbed, on every pair; the search-file guard's `main()` with each pair's own working directory, on every pair; and new-process, by default only on the pairs that match `NEW_PROCESS_SUBSET_PATTERN` (a heredoc, a case terminator or `~`), 58,770 pairs, or on every pair with `--new-process-pairs all`. Main's readings are therefore read again by every invocation, though main's guards change far less often than the pull requests that are replayed.
- **How readings run in parallel.** Each mode at each ref is one step in a fresh Python interpreter, and the steps run one after another. Inside a step, a `ProcessPoolExecutor` of `--jobs` workers (by default the processor count minus one), at nice 15, reads tasks of 200 pairs each (`PAIRS_PER_TASK`).
- **One new process per command in new-process mode.** In new-process mode the shell reader, `nc-systems/general-tools/shell-command-tree-sitter-bash-reader-common.py`, starts a new Python process for every reading (`_simple_commands_in_a_new_process()`, which runs the reader with `--read-command-on-standard-input` on one command). The replay's comment puts this at about 50 times slower than reading in-process, and every guard that loads the reader reads through it, so one pair starts several processes. A hook takes the same path when the parser was installed only for a new process, so the new-process mode tests a path real hooks use.
- **What the transcripts record of the guards' verdict.** A Bash call that a PreToolUse hook refused has a tool result marked as an error whose text begins `PreToolUse:Bash hook error: ` followed by the refusal; the text does not name the hook. Context a PreToolUse hook added is recorded as an attachment of type `hook_additional_context` with `hookEvent` `PreToolUse`. Seen in ned-box's transcripts on 2026-10-16.

Search receipt: `scripts/ghi-info-ask.py --include-closed` on 2026-10-16, asked for a GHI about a stored file of pairs for the replay, cached main readings, batched new-process reads or a daily job that adds to such a file, found none. The nearest is GHI [Replace the hand-written parsers in the project's hooks and scripts with real parsers](https://github.com/nedschorus/nedschorus/issues/1196), whose provisional additions record replays as correctness evidence and say nothing of their cost.

## What is decided

The user approved the plan below with "y" in reboot-test's agent-session on 2026-10-16, after saying: "I suspect if you remove dups we can run them all, but the maint cycle will want to add new, non dups as they occur." Asked whether duplicates are matched by exact text alone or by the pair of command text and working directory, since two guards read the working directory and ignoring it would cut only 0.6%, the user answered on 2026-10-16: "Y, keep the directory".

- The replay runs on a corpus of distinct commands, deduplicated by the pair of exact command text and working directory: a log-store file holding each distinct pair once, with where it was first seen. The work below calls this file the stored pairs file, since the replay already calls each command with its working directory a pair, and keys each entry on the exact text of the command and its working directory, as the replay does today, for the reason step 1 gives.
- Every pull request the replay covers replays every pair in the file, with no sampling.
- The new-process pass is batched: a few hundred commands in each new process. Commit aa700745 has done this.
- Merging near-duplicates, such as one command with a different path or hash, is left out: deduplicate by the pair of exact command text and working directory first, then measure.
- A job in the daily step adds the distinct pairs of new transcripts to the stored pairs file, as the eleventh job of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) says.

The user decided on 2026-10-18, at about 00:22Z, with "y" to item 11 of merge-lane-2's approval-walk merge-lane-2-everything-waiting-on-the-user-2026-10-15, that for every pull request that adds or changes a Bash guard, the replay's list of commands now refused or now allowed blocks the merge until the pull request's reviewer accepts each command on the list; a wrong entry goes back to the author, and an empty list blocks nothing. He gave reboot-test the design, to be judged by what is "good over the next 10,000 PRs". In approval-walk bash-guards-replay-check-which-pull-requests-and-how-it-blocks, on 2026-10-18 and 2026-10-19, he agreed to each recommendation below (walk-minutes nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/bash-guards-replay-check-which-pull-requests-and-how-it-blocks-minutes.md):

- **Where the replay runs** (item 2): as an ordinary test suite under the test runner's recorded inputs, not as a step in merge-lane-2's review program alone. The test runner records every file a suite opens, so the suite is selected exactly when a guard, a file a guard loads, the suite or the baseline changes, and no program works out what the guards import.
- **How main's readings are got** (item 3): from a baseline file committed to the repository, a golden file for a snapshot test. The cache of main's readings that this GHI-MD planned is dropped.
- **Where the reviewer's acceptance is kept** (item 4): in the merged baseline's diff, checked by merge-lane-2's review program against a record in the log-store that holds the changed commands' text.
- **What lives in the repository** (item 5): only the baseline, which names each pair by a plain SHA-256 hash of its command text and working directory, with no HMAC; never command text. The stored pairs file and the records of changed commands stay in the log-store. The repository is public; a check on 2026-10-19 of all 221,278 recorded pairs for token-shaped text found only test fakes.
- **Which pull requests get the replay** (item 6): every pull request that changes a Bash guard or any file a guard loads, such as the shell reader.
- **Guard names** (item 7): the seven Bash guards keep their directories and names; the recorded inputs, not the names, select the pull requests.

The measurement above shows that deduplication by the pair of command text and working directory was already in place (362,090 calls to 213,804 pairs), so the time the plan saves comes from the baseline and the batching, not from removing duplicates. The first full invocation after the work below measures how much.

## The work

1. **The stored pairs file.** The log-store directory `nedlern@ned-box:/home/nedlern/nedschorus-logs/bash-guards-replay-stored-distinct-command-pairs/` holds the stored pairs file, `stored-distinct-command-pairs.jsonl`, with one JSON line per distinct pair of exact command text and working directory: the command, the working directory, and the transcript file, line number and time at which the pair was first seen. The key keeps the working directory because the force-push guard and the search-file guard's `main()` read it, so one command can get two verdicts in two directories; keeping it costs the 0.6% measured above. Beside that file, `transcript-read-positions.json` records how far each transcript file has been read, so an append reads only what is new. The replay reads the stored pairs file by default, as `--pairs-file` reads a pairs file today, and no longer reads the transcripts itself; today's `recorded_command_pairs()` stays in the replay script, which gains a mode that appends the new pairs to the stored pairs file, and the daily job runs that mode. The replay runs on ned-box, where the log-store is, as its default transcript directories already require. Every file in the directory is written to a temporary file and renamed into place, so a reader never sees a partial file.
2. **Done in commit aa700745: batched new-process reads.** In the replay's new-process mode, the reader sends each command to a child process that reads one JSON request per line, in which a newline inside a command is escaped as JSON escapes it, and starts a fresh child after a number of commands set by a constant, as `PAIRS_PER_TASK` is, starting at a few hundred. A child that dies or runs past the per-pair timeout makes the reading of its current command a failed reading, which ends the replay with exit status 2 as a failed reading does today. Each request crosses the same JSON conversion, `_reader_output_to_json()` and `_reader_output_from_json()`, that the one-command path uses, so the replay still tests what a hook's new process does. A hook outside the replay keeps one process per command.
3. **Done in commit aa700745: every pair in every mode.** Once batching works, `--new-process-pairs` defaults to `all`, and `NEW_PROCESS_SUBSET_PATTERN` and the `subset` choice are removed.
4. **Dropped: the cache of main's readings.** The committed baseline of step 5 replaces it, by the user's ruling on 2026-10-18 above.
5. **The baseline**, `nc-systems/general-tools/tests/bash-guards-verdict-baseline-on-transcript-recorded-commands.jsonl`, to be built. Its first line is a header: a hash of every file the guards load, the number of stored pairs covered, and the main commit whose readings it extends. Each further line is `[pair hash, mode, guard file, verdict]` for one verdict other than passed, the verdict as the replay's rows record it, sorted by pair hash, mode and guard, written with `json.dumps(..., sort_keys=True)` so one set of verdicts always gives the same bytes. The pair hash is the SHA-256 of `json.dumps([command, working directory])`, so every program computes the same hash. Measured on 2026-10-17 at main, 4,352 pairs get such a verdict from at least one guard, 4,517 lines, about 1.1 MB.
6. **The suite**, `nc-systems/general-tools/tests/bash-guards-verdict-baseline-on-transcript-recorded-commands-test.py`, to be built. It reads every covered pair at the checkout in all three modes and fails on any verdict that differs from the baseline. When the guard files hash to the header's value, only the pairs the header covers are compared, so the daily full test run on main passes as the daily job adds pairs; when the hash differs, every stored pair is compared, so a pull request that changes a guard must regenerate the baseline. On main the covered count stays where the last guard pull request left it until the next one. The search-file guard's `main()` mode reads in a fixed directory holding `-v.txt` and `a.txt`, as the replay's in-process mode does, instead of each pair's own working directory, and the baseline is made with the same directory, so no reading depends on the disk. The stored pairs file is added to `TEST_SANDBOX_HOME_PATHS_SHOWN_READ_ONLY` in `scripts/run-all-test-suites.py`, so the suite can read it inside the test sandbox. A guard that the pull request adds is read at the checkout only, as PR [Bash guards replay: list and block on recorded commands a guard the pull request adds would refuse](https://github.com/nedschorus/nedschorus/pull/1627) makes the replay script do; every refusal it gives is a change. A guard the pull request removes takes its baseline lines with it, and each removed line is a change to passed.
7. **The regeneration program**, `nc-systems/general-tools/bash-guards-verdict-baseline-on-transcript-recorded-commands-regenerate.py`, to be built. It runs on ned-box outside the test sandbox. It runs `git fetch origin main` and stops with exit status 2 when the fetch fails, so it never reads a stale main. It reads the uncovered pairs at `origin/main` in a worktree, then every pair at the checkout, and rewrites the baseline. It writes the verdict-baseline-changes record, `nedlern@ned-box:/home/nedlern/nedschorus-logs/bash-guards-replay-stored-distinct-command-pairs/verdict-baseline-changes/<blob>.jsonl`, named after the new baseline's git blob hash, since the commit that will hold the baseline does not exist yet. The record holds two lists: the coverage additions, which are main's own readings of new pairs, and the changes, each with the pair hash, command text, working directory, guard, verdict at main and verdict at the checkout. `--show <pair hash>` prints one pair's command and working directory for the author. `--branch <branch>` regenerates in a ned-box worktree of a pushed branch, writes the record, and prints the path on ned-box of the new baseline, for an author on the Mac, who copies it into the topic branch with `scp`. Once this program is on main, a Mac author runs `ssh nedlern@ned-box 'python3 ~/Projects/nedschorus/nc-systems/general-tools/bash-guards-verdict-baseline-on-transcript-recorded-commands-regenerate.py --branch <branch>'`.
8. **The review program's check.** On a pull request whose baseline differs from main's, merge-lane-2's review program runs the regeneration program's `--verify-pull-request-head <commit>` mode. That mode finds the record by `git rev-parse <commit>:<baseline path>`, fails when the record is missing, rereads the coverage additions at the main commit the header names, up to the header's covered count, and fails unless the baseline diff, its added and its removed lines, is exactly the coverage additions plus the changes. `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` then puts the changes list into the reviewer's brief, which stays on ned-box. An empty changes list blocks nothing. An entry is wrong when the pull request's description does not say the guard means to refuse or allow that command; the reviewer's finding names the pair hash and guard only, because the review is posted on a public repository. The author reads the command with `--show`, fixes the guard, regenerates, and pushes one commit on top.
9. **A second guard pull request.** Every regeneration rewrites the header line, so two guard pull requests open at once conflict on the baseline, and `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT` for the second once the first merges. The second author merges main, resolves the baseline by rerunning the regeneration program, and pushes the merge once; the new record covers only the second pull request's changes against the new main.
10. **The Mac.** The Mac has no test sandbox and no log-store. The test runner gains a table of suites that need the log-store and run only on ned-box; on the Mac it reports such a suite as not selected, with that reason, instead of a `SKIP`, since a suite that prints `SKIP` is selected again at every later test run.
11. **Tests**, in `nc-systems/general-tools/tests/bash-guards-verdict-changes-between-two-git-refs-on-transcript-recorded-commands-check-test.py` and the new programs' own test files: the replay reads the stored pairs file; an append reads only lines added since the last append and adds only pairs not already present; batched new-process readings give the same rows as one process per command; the suite fails on a changed verdict and passes on uncovered pairs while the guard hash matches; `--verify-pull-request-head` fails on a missing record and on a baseline diff that differs from the record.
12. **The measurement.** The replay appends each full invocation's time for each mode, which it only prints today, to `full-invocation-times.jsonl` in the log-store directory of step 1. After step 1, the first full invocation with every pair in every mode is recorded in this GHI-MD, and its time sets the budget the daily job reports against, written to `full-invocation-time-budget.json` in that directory; the daily job reports any full invocation that takes longer than the budget.
