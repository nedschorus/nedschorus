# The test runner `scripts/run-all-test-suites.py` reruns suites whose recorded inputs did not change, because it keeps one recording per suite for every branch and selects every suite that runs a content-reading git command on the checkout

## What this GHI asks for

A design, then a build, that stops the test runner, `scripts/run-all-test-suites.py`, from running an nc-test-suite in a selective test run when nothing the nc-test-suite reads has changed and its last run on those inputs passed. Two of the runner's selection reasons pick nc-test-suites that way today, and together they took 39% of the run-seconds of merge-lane-2's head test runs from 2026-11-01 to 2026-11-04 at 03:50Z, about three days. Run-seconds, in this GHI-MD, are the seconds each nc-test-suite ran, added up over the nc-test-suites the runs ran; nc-test-suites run side by side, so they are not the runs' wall-clock time.

### Reason 1: one recording per nc-test-suite, shared by every branch

The runner records the files each Python nc-test-suite reads while it runs, with a Python audit hook and, in a run given `--record-inputs-with-strace`, which the scheduled full test run gives, also with strace. It keeps that recording under `--recorded-inputs-directory`, keyed by the repository's root commit, one file per nc-test-suite, shared by every test run on the machine that uses the same directory: by default every clone and worktree, while merge-lane-2's head test runs use a directory of their own (the runner's docstring, section RECORDED INPUTS, and `recordings_directory_for`). Every test run not given `--leave-recorded-inputs-and-failure-history-unchanged` replaces the recordings of the Python nc-test-suites it ran; a shell nc-test-suite, a `*-test.sh` file, is never recorded. So when a test run on branch X records an nc-test-suite, a test run on branch Y that uses the same directory finds a recording whose file contents are X's. The runner then cannot tell what the nc-test-suite reads on Y, and selects it with the reason "its recording read another copy of <file> than the checkout holds, so what it reads here is unknown" (`selection_reason`).

Example: merge-lane-2's head test run of one pull request records `nc-systems/skills/explain/tests/explain-reply-cold-read-fast-read-test.py` while that pull request's copy of a cold-read file differs from main. The next head test run, of a pull request that touches nothing that nc-test-suite reads, selects it anyway. That nc-test-suite was selected this way 77 times in those three days.

Measured: this reason selected 24% of the head test runs' run-seconds, 122,534 run-seconds, in those three days.

The change to design: keep several recordings per nc-test-suite, each a file of its own, check them one by one, and do not select an nc-test-suite when any one of its passing recordings matches the checkout in everything it saw (the files it read, the paths it looked for, the directories it listed and, when it ran git on the checkout, the checkout's list of files) and none of that changed since COMMIT (a condition the user has since narrowed, as What the user has decided says), the commit the selective test run compares against (`--only-suites-whose-recorded-inputs-changed-since`).

### Reason 2: an nc-test-suite that runs a content-reading git command on the checkout is selected by every change

When an nc-test-suite runs a git command on the checkout that reads file contents, such as `git status`, `git diff` or `git clone` of the checkout, the runner selects it whenever any file differs, because git reads committed content from the object store, where neither recorder sees a working file (`selection_reason`, the reason "it runs git … on the checkout, which reads files no recorder here saw").

Measured: 749 runs of nc-test-suites and 75,745 run-seconds, 15% of the head test runs' run-seconds, in the same three days. They came from five nc-test-suites, among them `nc-systems/general-tools/tests/bash-guards-verdict-changes-between-git-refs-on-recorded-commands-check-test.py`, whose median run is 430 seconds; it ran in all 230 head test runs and used 17.5% of the CPU time of all nc-test-suites.

The options to weigh in the design, which can be combined:
1. Each such nc-test-suite runs git on a fixture repository it builds, instead of on the checkout, so it runs no content-reading git command on the checkout and Reason 2 no longer selects it. This helps only the nc-test-suites rewritten, and only where the fixture still holds what the test checks; an nc-test-suite that needs the real checkout stays selected by every change.
2. The recorder learns which paths a git command can read from its arguments, such as `git show <ref>:<path>` or a pathspec after `--`, and treats a whole-tree command such as `git status` as reading every tracked file, so an nc-test-suite running `git status` stays selected by every change; it does not help an nc-test-suite that clones the checkout, such as the bash-guards nc-test-suite above, which needs option 1.

### Part 1: several recordings per nc-test-suite

**Two checks of a recording against the checkout.** The design names the two halves of today's `selection_reason`, and keeps each half's rules as the runner's docstring states them today.

- A recording *matches the checkout* when every file it read has the same blob hash in the checkout, every path it looked for is present or absent as recorded, every directory it listed holds the recorded entries, and, when its run ran git on the checkout, the checkout's list of files has the recorded fingerprint.
- A recording is *unchanged since COMMIT* when none of the files it read differs between COMMIT and the checkout, no path it looked for was added or deleted, no directory it listed gained or lost an entry, and none of the git rules fires: a file was added or deleted since COMMIT and its run ran git on the checkout, or any file differs since COMMIT and its run ran a content-reading git command on the checkout.

A recording *passed* when its run exited 0 and skipped only cases marked `[this machine cannot run it]`, as `recorded_run_passed_and_skipped_only_cases_this_machine_cannot_run` says today; a *passing recording* is one that passed, and a *failing recording* one that did not.

A recording is *newer* than another when its `recorded_at` is later; between equal times, the one whose file name comes later in byte order is newer; a recording whose `recorded_at` is missing or unreadable is older than every other.

**The store.** Each nc-test-suite gets a directory of its own in place of its one file: `<recorded-inputs-directory>/<first 16 hex digits of the root commit>/<the nc-test-suite's path with each / written as __>/`, beside where its file is today. Each recording in the directory is a file named `<key>.json`, where the key is the first 16 hex digits of the SHA-256 of a JSON text, with sorted keys, of what the recording holds about its inputs: the files read with their blob hashes, each path looked for with whether it was there, the directories listed with their entries, the git commands run on the checkout, and the fingerprint when it ran git on the checkout. Two test runs of one nc-test-suite on the same inputs therefore write the same file name, and the later replaces the earlier. A file in the directory whose name ends in `.json` but that cannot be read or parsed, or whose format is not the current one, is not a recording: selection, saving and the other readers leave it out, eviction does not count it toward the 32, and nothing removes it. The lists of files only strace saw stay one per nc-test-suite, in `--suite-files-only-strace-saw-lists-directory`, unchanged; a test run that records with the audit hook alone adds the files on the list to the files its recording read, with their blob hashes in its checkout, as `recording_of` does today, so the match check covers them. A shell nc-test-suite is not recorded, as today, so it has no recording and step 2 of Selection selects it in every selective test run.

**Selection.** For each nc-test-suite, after the reasons that select every nc-test-suite, which stay as they are, in this order:

1. The nc-test-suite's own file, or a file on its list of files only strace saw, differs since COMMIT: SELECTED, with today's reason. Both are judged against COMMIT, as today, and not against a recording.
2. No recording, which includes a missing or empty directory: SELECTED, "no recording of its inputs on this machine yet".
3. A failing recording matches the checkout: SELECTED, even when a passing recording matches too. The reason names the newest such failing recording's `recorded_at` and gives today's detail of why its run did not pass, its exit or its count of unmarked skipped cases, opening "a recording of a run that did not pass matches the checkout" and not today's "its last recorded run", since a newer recording may have passed. A run that fails or is killed records only what it read before it stopped, so its recording matches at least the checkouts a passing one would; it stays the deciding recording until a test run on this checkout saves a newer outcome, as step 2 of Saving says. A passing and a failing recording therefore both match one checkout only when the failing run was on another checkout and read only files this checkout holds alike, so it could fail here too, or when a removal after a save that failed itself failed; in both the failure decides.
4. A recording that passed matches the checkout: NOT SELECTED, except that a recording made while the suite ran a content-reading git command on the checkout must also be unchanged since COMMIT. The selection line names that recording's `recorded_at` and commit, beside today's count of files read.
5. Otherwise SELECTED. When a passing recording matches the checkout, the reason is the first rule of unchanged since COMMIT that the newest such recording does not meet, worded as today. When none matches, the reason is "none of its <N> recordings matches the checkout; the newest: " followed by the first of today's reasons that a recording does not match the checkout that applies to the newest recording, passing or failing: it read another copy of a file, it looked for a path whose presence differs, it listed a directory whose entries differ, or it ran git on the checkout and was made on another set of files.

When more than one passing recording meets step 4's conditions, "that recording" in step 4 is the newest of them. Step 4's selection line reads "a passing recording of <recorded_at>, at commit <its first 12 hex digits>, matches the checkout; it read <N> files", followed by today's clause about git calls that read no file of the checkout when there is one; it does not say that no file differs since COMMIT, because under step 4 files may differ.

#open_question A recording made while the nc-test-suite ran a content-reading git command on the checkout, such as `git show HEAD:<path>`, does not hold the content git read from the object store. On a checkout that does not differ from COMMIT, such a recording made on another branch matches the checkout and is unchanged since COMMIT, so step 4 deselects the nc-test-suite though the content git reads here was never tested. Today's runner has the same gap. The user decides whether step 4 also requires such a recording to have been made at the checkout's own commit.

A recording that does not match the checkout plays no part in the decision: it was made on other inputs, so it says nothing about this checkout. Step 5 only names the newest one in its reason.

**Saving.** A test run that records an nc-test-suite creates the nc-test-suite's directory if it is missing, writes its recording to a temporary file of its own in the directory, whose name ends in `.tmp`, as `save_recording` does today, then takes the nc-test-suite's lock, which stays the file `<the nc-test-suite's path with each / written as __>.json.lock` beside the nc-test-suite's directory, as today, and while holding it does three things in this order:

1. Renames its recording into place.
2. Lists the directory again and removes every other recording in it that matches the checkout the test run recorded in, by every rule of the match check: the paths looked for, the directories listed and the fingerprint judged with the checkout's list of files the test run took at its start, and the files read judged with their blob hashes in that checkout, hashed now as `recording_of` hashes them today. Such a recording saw nothing that this checkout holds differently, so the new one records the newer outcome here. The last save on the same inputs wins, as with today's one file: a pass saved after a failure on the same inputs removes the failure, even when the passing run started first.
3. Eviction: when more than 32 recordings remain, removes the oldest, by the order under Two checks of a recording against the checkout, until 32 remain; the one just saved is never removed.

The test run leaves the nc-test-suite's file in today's format alone: a test run on a branch whose runner predates this design still reads and writes it, and this design's runner neither reads it nor counts it.

A test run that cannot save a recording removes, under the same lock, every recording of the nc-test-suite that matches the checkout and whose file still has the device, inode, modification time and size the test run read at its start, compared file by file as `remove_recording_if_unchanged` compares the one file today. A recording another test run saved meanwhile differs in those and records that test run's own outcome, so it stays, even when that run passed and this one failed; today's one file behaves the same way. Every listing or removal that fails, in step 2 or step 3 of Saving or after a save that failed, is reported in the test run's report as today's failed removal is, and the test run goes on; a failed removal after a successful rename does not make the report say the inputs were not recorded.

Selection takes no lock: a test run lists each directory once at its start and reads each file whose name ends in `.json` once, keeping each file's device, inode, modification time and size as `load_recording_and_identity` keeps them for the one file today, and a file removed between the listing and the read is skipped. A reader never sees a recording half written, because only the `.tmp` file is ever written and it is renamed into place. Selection and the starting order use what the test run read at its start, as today.

**Why 32.** A recording matters only while a checkout with its inputs is still tested. On merge-lane-2's store, the checkouts tested at once are main and the open pull requests: 9 pull requests were open on 2026-11-06, and merge-lane-2 ran head test runs on up to 78 distinct pull requests in a day (2026-10-31). The machine's default store also serves agent-seats' topic branches before they have a pull request. An nc-test-suite gains a recording only when a test run selects and runs it, so most nc-test-suites hold far fewer than 32. Today's default store held 300 recordings of about 4 KB each on average (`~/.cache/nedschorus-test-suite-recorded-inputs/c8652c93ef1c27e3/`, 2026-11-06), so a store of 32 recordings for each of those nc-test-suites would take about 40 MB. A week after pull request (1) merges, its author counts, over that week's head test runs of merge-lane-2, whose reports are kept at nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/merge-lane-2/merge-helpers/hr/pr*/stderr, the SELECTED lines whose reason opens "none of its 32 recordings matches the checkout", against all SELECTED lines, and records both counts in this GHI-MD. The count is rough: it includes selections no eviction caused, and misses eviction-caused ones when fewer than 32 recordings remained. More than 5% of selections is reason to raise the number and count again; whoever proposes a new number brings it to the user.

**Other readers of a recording.** The starting order, `suites_longest_recorded_first`, and each nc-test-suite's time limit, `suite_timeout_and_the_recorded_seconds_it_came_from`, use the newest recording, passing or failing, as each uses the one recording today; when it did not pass, both treat the nc-test-suite as they treat one with no passing recording today, so a run stopped at its time limit gives the next run today's longer limit. `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py` calls `runner.load_recording` in three places: `suites_for_file` chooses an nc-test-suite when any of its passing recordings read the file; `quick_mutation_pass_suites` and `default_mutant_timeout_seconds_from_test_suites_own_time_limits` use the newest recording, as they use the one recording today. The runner replaces `load_recording` with a function returning a list of every recording of the nc-test-suite, newest first, empty when there is none, and the build changes those three callers in the same pull request.

**Format.** `RECORDED_INPUTS_FORMAT_VERSION` goes from 5 to 6. A test run finds no recording in format 6 for any nc-test-suite at first, so each nc-test-suite is selected on each store until a run of it saves a passing recording that matches, as after every format change.

**Tests**, in `scripts/run-all-test-suites-test.py` except where a test names another file; the first test runs on a test fixture repository with two branches whose copies of one file differ:

- A test run on branch X, then one on branch Y, then a selective test run on each branch again: each nc-test-suite reading that file is NOT SELECTED on both branches.
- A passing recording, then a failing test run on the same inputs: the passing recording is gone, and the next selective test run selects the nc-test-suite.
- 33 recordings of one nc-test-suite: the oldest is removed and the new one stays.
- A save that fails removes the matching recordings the test run read at its start, and keeps one another test run saved meanwhile.
- Two test runs saving one nc-test-suite at once leave whole recordings, each named after its own inputs.
- A store holding only a format-5 file selects every nc-test-suite until a run of it saves a passing recording, and that save leaves the format-5 file in place.
- In `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors-test.py`: an nc-test-suite whose older passing recording, and not its newest, read the file is chosen for that file.

### What needs judgment and what is code in this proposal

Code: both checks of a recording, the store, the selection order, saving, step 2 of Saving's removal of recordings on the same inputs, eviction, the readers' choice of recording, and `ls-remote` in `GIT_COMMANDS_THAT_ONLY_LIST`.
