# Agents reuse what the project has already solved: shared helpers, one page of reusable components, and a reuse check before, during and after the build

Agents keep re-solving problems this project has already solved, because they do not know the solution exists or do not look for it. This GHI makes the solutions findable and checks for re-implementation at three moments: when an agent is briefed, when it writes a file, and when its pull request is reviewed.

## Why

- PR [Remind the agent to keep Markdown paragraphs on one line after an Edit or Write](https://github.com/nedschorus/nedschorus/pull/1106) took nine review rounds. For five of them the hook recognised Markdown with hand-written regular expressions, and each fix broke a neighbouring case. The standard parser, markdown-it-py, was installed on ned-box throughout; the rounds stopped once the hook used it.
- PR [Stop hook: tell the agent to fast-read documents it linked that have no cold-read-fast-read since their last change](https://github.com/nedschorus/nedschorus/pull/1109) copied two helpers that already existed, and its reviewers asked for the shared ones.
- Both trawls below found helpers that exist in three or four copies, where only some copies carry later fixes. One example: the list of environment variables that redirect git exists in four copies, and two of them strip only two of the six variables.
- Published work finds the same pattern. Agents "frequently disregard code reuse opportunities", and reviewers judged agents' pull requests more favourably than humans' ([More Code, Less Reuse, MSR 2026](https://arxiv.org/abs/2601.21276)). General advice in an instructions file barely changes what agents do, while a specific instruction such as "use X for Y" is followed ([ETH Zurich, 2026](https://arxiv.org/abs/2602.11988)).

The user asked for this on 2026-10-09 in agent-session fleet-restart-at-login: "we put to gether a wiki page with all these things, then have an agent check PRs to see if any of them should have been used", and asked for the whole project to be trawled for "components that can be and should be (at appropriate times) be reused", techniques included: test coverage tools, working with Codex and Gemini, a simple database instead of tags, and the reincarnation and daily cycles.

## What to build, in order

1. **Extract the duplicates first.** Where a helper exists in several copies, make one shared module and move every caller to it, taking the most complete copy's behaviour, with tests that cover each caller's use, so that a caller relying on a narrower copy shows up in the tests rather than on main. Start with the trawls' duplicates list. A page that points at three copies keeps the problem.
2. **One short wiki page of reusable components.** One row per problem, organised by what the agent is about to do ("read Markdown", "read an agent's transcript", "run git from a hook", "call Codex or Gemini", "keep state between runs", "schedule work daily"): the component to use, one example call, and the mistake it prevents. Techniques go on it as well as code: the reincarnation cycle, the daily step, a program-owned record instead of a marker in prose, the test runner's selection, mutation testing. The page stays short, linking to each system's own documentation for detail, so that a reviewer reads it whole.
3. **Before the build: the builder's brief.** Every prompt an agent writes to commission code from a subagent points to the page, as a specific instruction: before writing code that does one of these things, use the listed component.
4. **During the build: a hook.** Modelled on the new-shared-names reminder: after a write, when a changed file does something a page row covers, such as a new script that imports `re` and contains Markdown fence literals, or reads a JSONL transcript without the shared reader, the hook names the row and the component. Narrow mechanical patterns only; each comes from a re-implementation that was caught.
5. **After the build: a reviewer.** merge-lane-2 commissions one more cheap reviewer per pull request, given the page and the diff, with one question: does this change solve a listed problem without the listed component? It must name the existing component and say whether its contract fits. This is the backstop for what the brief and the hook miss, and the only check for techniques, such as the daily step or a program-owned record, which no pattern can detect.
6. **The loop.** Each re-implementation the reviewer catches adds a row to the page, and, where it can be matched mechanically, a pattern to the hook or a test that fails when a helper is defined twice. The page grows from real misses rather than from guesses.
7. **The tools are installed on both machines.** Libraries and tools are installed as item 8 of the ruling below says, and the daily check of GHI [Daily maintenance in one daily step, starting with a daily check of every wiki page](https://github.com/nedschorus/nedschorus/issues/1058) reports one that is missing.

## What is decided

The user ruled on the order above and the open questions on 2026-10-12 and 2026-10-13, in the approval-walk reusable-components-page-and-reuse-checks-2026-10-12 of agent-seat agent-instructions-editor; the walk-minutes, with his words, are at `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/reusable-components-page-and-reuse-checks-2026-10-12-minutes.md`. Where a ruling and a step above differ, the ruling holds.

1. **Where the page lives.** The page goes in `docs/nedschorus-wiki/`, named as `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md` says; the shared modules the page points to live in `nc-systems/general-tools/`. If GHI [One documentation tree in place of the wiki and the rest of docs, with Obsidian opened on it](https://github.com/nedschorus/nedschorus/issues/1066) moves the wiki, the page moves with it.
2. **What a row says, the page's size, and who changes the page.** The page has two levels: a short index of about nine groups, each named for the job the agent is about to start, and in each group up to about eight rows of the form "to do X, use Y", each with one example call, the mistake the row prevents, the row's origin, and a default where two components fit. The page holds under 80 rows in all. Any agent adds a row or a group in a pull request that cites the re-implementation the row would have prevented. A row is removed with its component. When the page is full, the agent asks the user which row to drop.
3. **Skills for procedures, and a search tool for the log-store.** A row holds one call; a procedure gets a skill, which the row links. Two skills are built: mutation testing a pull request with `scripts/pull-request-mutation-testing-survivors.py`; and searching the log-store, with one small program that searches the log-store's walk-minutes, cold-read-records and analyses together.
4. **The hook during the build.** After an Edit or Write of a `.py` or `.sh` file, a hook checks for narrow patterns, each taken from a re-implementation actually caught, and names the row to use, once per row per branch, as `scripts/new-shared-names-reminder-hook.py` does. The first patterns: a Markdown fence literal in a file that does not import `markdown_it`; a list of the variables that redirect git, such as `GIT_DIR`; `ps` called to find a process; and, once pytest is installed, a new `def check(` in a test suite.
5. **Checks that fail before review.** For the strongest rows, a test fails when a helper is defined twice, as `scripts/supervisor-file-names-defined-once-test.py` does, and ruff's banned-API rule refuses a call that a shared helper replaces. ruff is installed on the Mac and on ned-box.
6. **The reviewer after the build.** merge-lane-2 commissions a cheap reuse reviewer on each pull request that changes code, and a component the reviewer shows was missed blocks the merge. Two conditions come before the reviewer blocks anything: the reviewer's prompt is carefully constructed and tested; and research settles which other fast, cheap checks run at the same point, and which model runs them, Gemini being the user's guess. The research is under `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/pull-request-fast-cheap-checks-what-to-run-research-2026-10-12/`.
7. **How every agent learns about the page.** A path-specific rule in `.claude/rules/` for `.py` and `.sh` files holds the page's groups and the instruction to use the listed component. A Codex-only section of `AGENTS.md` holds the same groups and instruction, and the reviewer's rule that a missed component blocks. `docs/agents/pr-reviewer-instructions.md` gets one sentence linking the page, for Claude reviewers. `CLAUDE.md` gets one sentence: a brief that commissions code links the page and tells the subagent to use the listed components. A test keeps both lists of groups matched to the page.
8. **Where libraries live, and the Python version.** Pure-Python libraries go in the pinned requirements file, `nc-systems/general-tools/compiled-python-libraries-pinned-requirements.txt`, with each library's license recorded beside its pinned line, as compiled libraries do; python-crontab (LGPL-3.0), which replaces the hand-written crontab reader, goes there too. `vendor/` is not created. This follows approval-walk reboot-test-open-decisions-2026-10-14, item 2, user "Y" 2026-10-14 (walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/reboot-test-open-decisions-2026-10-14-minutes.md`, once that approval-walk closes): "Every outside library is then handled one way: one install path, one daily check, one file to change a version in." A program installs a missing library or tool itself and reports a failed install with what the install printed. Python 3.11 is the minimum on both machines. The program that installs from the pinned file, `nc-systems/general-tools/compiled-python-libraries-pinned-requirements-install-common.py`, checks the running Python first, in code that Python 3.9 can read; below 3.11 the program stops and tells the agent to tell the user which Python ran it, where that Python is installed, and the fix, which on the Mac is Homebrew's Python ahead of Apple's on the PATH. The program never changes the PATH.
9. **Which duplicates go first.** Two duplicates go first, each into its own shared module in `nc-systems/general-tools/`, in one pull request each, as the searches for duplicated code under `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/reusable-project-components-trawl-2026-10-09/` name them: the four git helper functions held by each of three hooks that check a Markdown file after an edit, and the list of six variables that redirect git, of which `nc-systems/handoff/handoff-supervisor.py` and `nc-systems/cold-read/cold-read-fast-read.py` strip only two. Every caller moves onto the module, with a test for each caller's use, and a test fails when the functions or the list are written out again.
