# Test suites that run without a sandbox leave per-change test runs unless the change edits a file they read, and run on main in a quiet gap

## What is wrong

This section describes ned-box as it was on 2026-11-03, before this design was built. On ned-box, Linux with bwrap, `scripts/run-all-test-suites.py` ran every nc-test-suite in its own nc-test-sandbox, except the ten listed in `SUITES_RUN_WITHOUT_ANY_SANDBOX` on 2026-11-03, which started bwrap themselves or ran the real ssh and so could not run inside one. When this GHI was filed on 2026-11-02 the list held nine, of which the GHI named eight. Those suites share one lock, the file named by `SUITES_RUN_WITHOUT_ANY_SANDBOX_LOCK_FILE_NAME` in the admission directory of the runner's lock file, and only one of them runs at a time among all runs that use the same lock file, the runner's default unless a run is given `--lock-file`. A test run that selected one of them starts its other suites, but that suite waits until no run, its own included, is running another. The ten were `nc-systems/cold-read/tests/cold-read-agy-cell-test.py`, `nc-systems/cold-read/tests/cold-read-fast-read-test.py`, `nc-systems/cold-read/tests/cold-read-grid-test.py`, `nc-systems/general-tools/tests/agy-print-prompt-run-in-empty-home-sandbox-test.py`, `nc-systems/skills/explain/tests/explain-reply-cold-read-fast-read-test.py`, `nc-systems/skills/walk-me-through/tests/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close-test.py`, `scripts/run-all-test-suites-cleanup-after-killed-runs-real-process-test.py`, `scripts/run-all-test-suites-test-sandbox-escape-test.py`, `scripts/run-all-test-suites-overlapping-runs-real-process-test.py` and `scripts/mac-request-from-ned-box-forced-command-test.py`.

Two independent analyses of the agent-sessions' transcripts and the runners' reports for 2026-10-31T00:00Z to 2026-11-02T00:00Z were made, one by Opus and one by Codex. The Opus analysis found:

- In the 226 author test runs that finished, the waits of each run's longest-waiting suite add up to 79.7 of the runs' 84.0 hours; in merge-lane-2's 139 head test runs, to 51.1 of 53.8 hours.
- 76% of the runners' once-a-minute "waits to start" lines in author runs, and 74% in head test runs, name this lock. It was held for 20.6 of the 29.6 hours that test runs covered.
- Each of these suites takes about a minute, but most selections include them.
- Taking them off per-change runs would save an estimated 49 to 88 pull-request hours and 105 to 210 agent-hours a week (Opus report, section 6, proposal 2).

The reports: `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/fleet-time-and-token-costs-2026-10-31-to-2026-11-02/opus/report.md` (section 2, "Top time costs", its paragraph "Why test runs are slow", and section 6, proposal 2) and `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/fleet-time-and-token-costs-2026-10-31-to-2026-11-02/codex/report.md`.

GHI [Each test suite on ned-box runs in its own throwaway test environment, and suites start by free CPU and memory instead of waiting for a machine-wide lock](https://github.com/nedschorus/nedschorus/issues/1374) replaced the old machine-wide lock with a sandbox and CPU admission for every other suite, and created this lock for the suites that cannot run in the sandbox, and pull request [Test runner admits a suite while machine CPU is under 90%, and every suite runs in one low-CPU-weight slice](https://github.com/nedschorus/nedschorus/pull/2350) raised the CPU limit for starting a suite and did not change this lock.

A third look, at the pre-push selective test runs of 2026-11-02 and 2026-11-03 (`nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/reboot-test/task-316-pre-push-time-budget-root-cause-2026-11-03/findings.md`), found 111 runs stopped at the 480-second budget the pre-push hook gives its selective test run, 71 on the first day and 40 on the second. In 67 of them the only suites left were no-sandbox ones, each waiting with the runner's line "another run is running a suite that has no sandbox, and that run holds the lock all such suites share". In the hours the findings file measured, 00:00 to 12:00 local time on 2026-11-02 and 00:00 to 05:00 and 09:00 to 12:00 on 2026-11-03, these suites held the lock for 2,300 to 3,300 of most hours' 3,600 seconds, and the longest single wait of any suite in any run on those days was 17,363 seconds.

A fourth look, ned-box-helper's test-time survey of 2026-11-03 and its verification (`nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/ned-box-helper/test-time-survey-2026-11-03/report.md` and `verification.md` beside it), counted 4,379 test runs from 2026-10-27 to 2026-11-03. In 563 of the 686 runs that selected a no-sandbox suite, that suite finished last; summed over those runs, the wait from their sandboxed suites' end to their own end came to about 50 hours a day. On 2026-11-03, a run of 203 suites finished its 194 sandboxed suites in 7 minutes, and its nine no-sandbox suites added 1.6 hours. Ten more pre-push runs stopped at 480 seconds waiting on the lock between 20:49Z and 21:42Z that day.

A related failure is outside this GHI: nc-mutation-testing's quick passes were stopped at 605 seconds on 2026-11-03 because the wait for CPU admission counts against each mutant's time limit, as the survey's verification records.

## What the user decided

On 2026-11-02 at about 00:55Z, in agent-instructions-editor's agent-session on ned-box, the user ruled, in his words: "We should really be careful about anything that locks the testing cycle for everybody. ... Obviously running the same tests is stupid unless there's a reason to run a test. But lock stuff really needs to be attacked. ... I would make all these changes, and I'd make them in the order of efficiency. I think you just said what I said, which is just run the eight lock holding suites completely separately. Or when their files change. Yes, and if that's not enough, maybe we run them four times a day or something. Or when we see we run them nightly, when we're almost positive there'll be a gap, or maybe we wait until things are really quiet and then run them during that gap. ... at some point there aren't anything queued up behind them ... if it did happen, we could stick one in." The user-ruling is recorded at line 35 of `/home/nedlern/agents/agent-instructions-editor/docs/walk/merge-lane-2-seat-brief-rewrite-without-history-2026-11-02-minutes.md` on ned-box. Another change he ordered at the same time, that each round's test suites run once, is GHI [Each round of a pull request runs its test suites once, and a push reuses a passing test run of the same tree](https://github.com/nedschorus/nedschorus/issues/2384).

So, with the two rulings of 2026-11-04 below:

1. Author test runs, the pre-push selective test run and merge-lane-2's head test run no longer run these suites as part of a run for one change, except a suite whose files the change edits.
2. A suite runs when its files change, in that change's own test run, which waits for the lock; part 1 says which files count.
3. They also run when ned-box is quiet, at a moment when no test run is waiting behind them.
4. If they have not run that day, they run at a fixed time; the design picks four times a day or nightly.

On 2026-11-04, in reboot-test's approval-walk, whose walk-document is `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/reboot-test-worktree-review-direction-2026-11-03.md` and whose walk-minutes are `reboot-test-worktree-review-direction-2026-11-03-minutes.md` in the same directory, the user made two more rulings on this GHI. On item 4.2, at line 71 of the walk-minutes, he approved reading "when their files change" as point 2 above says, in place of a test run of their own. On item 4.1, at line 62, he turned down the recommendation to leave the sandbox alternative out, in his words "Build what we need to test faster", and on item 4.2.1, at line 76, he approved keeping that rework, for catching breaks before the merge. The section "The sandbox alternative" below says what was built.

## Design

This design is built: parts 1, 2 and 4 by pull request [No-sandbox test suites leave per-change test runs and run on main in a quiet gap](https://github.com/nedschorus/nedschorus/pull/2684), merged 2026-11-06, with more tests for part 2 by pull request [Quiet-gap runner: tests for three untested paths](https://github.com/nedschorus/nedschorus/pull/2715), and part 1's rule for a suite whose files the change edits by pull request [Selective test run runs a no-sandbox suite when the change edits a file it reads, waiting for the lock](https://github.com/nedschorus/nedschorus/pull/3570). Where this section says what a program does, the program's docstring is the fuller account.

The user-ruling names eight suites; `SUITES_RUN_WITHOUT_ANY_SANDBOX` listed ten on 2026-11-03 and eight on 2026-11-13, and the design applies to whatever that list holds. This design calls the nc-test-suites on that list the no-sandbox suites, and writes "suite" for an nc-test-suite. The runner's behaviour in part 1 applies where the runner runs the other suites in nc-test-sandboxes, which is Linux with bwrap, ned-box's case, and where the no-sandbox suites' lock exists. Elsewhere, on the Mac and on Linux without bwrap, the whole run takes the machine's lock and part 1 changes nothing. Part 2 runs on ned-box alone; part 4's notice is printed by `scripts/merge-gate.sh` on any machine, and prints nothing where part 2's state file does not exist.

Steps that need judgment: none in the new code. Two steps keep an agent's judgment: an author deciding whether to run a left-out suite by hand before the merge, and merge-lane-2 deciding, from a failure notice, which merged pull request's author to ask about it.

### 1. Per-change test runs run a no-sandbox suite only when the change edits a file it reads

`scripts/run-all-test-suites.py` changes its selective run, a run given `--only-suites-whose-recorded-inputs-changed-since COMMIT` without `--only-suites-named`. Such a run runs a no-sandbox suite only when the change edits a file the suite reads: the suite's own file, a file its recording read, or a file only its last strace run saw. That suite waits for the no-sandbox suites' lock, and its `SELECTED` line names the file. Every other no-sandbox suite the selection would have picked, such as one with no recording or one selected because it runs git on the checkout, is left out, whatever else changed. The runner does this by default, so the pre-push selective test run, an author's test run and merge-lane-2's head test run all follow it with no change to those callers, and no selective caller can bring the lock back for every change by forgetting a flag. The user approved running a suite whose files the change edits in item 4.2 of reboot-test's approval-walk on 2026-11-04, as "What the user decided" says. A per-change run that runs such a suite can wait for the lock behind part 2's run, the daily full test run or nc-mutation-testing.

For each no-sandbox suite left out, the runner prints, in place of its `SELECTED` line, one line opening `NO-SANDBOX SUITE LEFT OUT OF SELECTIVE TEST RUN `, followed by the suite's path, the selection reason, and the command that runs it by hand: `python3 scripts/run-all-test-suites.py --only-suites-named <the suite's path>`. The `SUMMARY:` line adds a count of suites left out. A suite left out is never counted as failed or not run, so a selective run's exit 0 now means every suite it ran passed, and the `NO-SANDBOX SUITE LEFT OUT OF SELECTIVE TEST RUN ` lines say which no-sandbox suites the selection picked and the run did not run; suites the selection did not pick get their `NOT SELECTED` lines as before. A left-out suite prints neither a `FAIL ` nor a `NOT RUN ` line, so no program that picks those lines apart, such as `scripts/scheduled-full-test-run-of-main.py` and `scripts/mutation-testing-changed-lines-quick-or-full-pass-survivors.py`, needs a change.

Unchanged: a run with no selection option, such as the daily full test run of main, runs every suite; a run given `--only-suites-named` runs the named suites, narrowed by the selection option when that is given too; so nc-mutation-testing still runs a no-sandbox suite whenever its own selection picks that suite for a mutated file.

So a change to a file a no-sandbox suite is known to read, its own file, a file its recording read or a file its last strace run saw, is tested by that suite before the merge. A change to a file the suite reads that no recording shows, as for a suite with no recording yet, is not; part 2 tests it on main after the merge if the suite's recorded inputs changed since part 2's passing commit, and the daily full test run of main tests every no-sandbox suite each day. An author who wants a left-out suite's verdict before the merge runs the command the `NO-SANDBOX SUITE LEFT OUT OF SELECTIVE TEST RUN ` line prints. A per-change run takes the no-sandbox suites' lock only for a suite whose files the change edits; the other runs that take it are part 2's own run, any run with no selection option, such as the daily full test run of main, any run given `--only-suites-named` that names a no-sandbox suite, such as those hand runs, and nc-mutation-testing that runs a no-sandbox suite.

### 2. The no-sandbox suites' own run, on main, in a quiet gap

A new program, `scripts/no-sandbox-test-suites-run-on-main-in-a-quiet-gap.py`, runs on ned-box under cron every 10 minutes, from a new entry in `nc-systems/general-tools/scheduled-jobs-on-each-machine.json` with a `ned-box` key only and the output file `.claude/no-sandbox-test-suites-run-on-main-in-a-quiet-gap.log`. It keeps a state file, `~/.local/state/nedschorus/no-sandbox-test-suites-run-on-main-in-a-quiet-gap.json`, which holds two things: the passing commit, the last commit of main at which a run of the program passed; and the last run, the last run of the program that went past step 5 below or stopped before step 4. The last run holds its commit, or none when main could not be resolved; the passing commit it was compared with; its start and end times; its result, passed, failed or stopped; the reason, for a stopped run; each failing suite with the log-store copy of its log, for a failure; its record's path, when it wrote one; and the time a follow-up request was recorded for it, as part 4 says. The program writes the file whole, to a temporary file renamed into place.

Each run of the program does this, in order:

1. Takes its own lock, the state file's path with `.lock` added, without waiting. When another run of the program holds it, it exits 0.
2. Reads the state file. A file that is missing or cannot be read counts as having no passing commit and no last run.
3. Runs `git fetch origin` in the clone the program is in, with a 300-second time limit, and resolves `origin/main` to its full commit hash. When either fails, the run stops, as below, and the stop replaces the last run, whatever it was.
4. Exits 0 when no run is due. A run is due when there is no last run, when the last run was at another commit, when the last run stopped, or when it failed more than an hour ago. So a failure at one commit is tried again after an hour, which clears a failure that was a passing fault; a new commit on main is tested at the next firing whatever the last run's result; and a stopped run is tried again at the next firing, 10 minutes later, however many times it has stopped.
5. Checks that ned-box is quiet, in the user-ruling's sense that nothing is waiting behind the no-sandbox suites' lock. It takes that lock, the file the runner names `SUITES_RUN_WITHOUT_ANY_SANDBOX_LOCK_FILE_NAME` in its admission directory, `~/.claude/.run-all-test-suites.lock.test-suite-admission/`, without waiting, and releases it at once; when the lock is held, it exits 0. This sees only whether a suite holds the lock at that moment: not whether another run's suite is between two tries for it, nor whether one takes it before this run's runner starts. That is close enough: after part 1, few runs take the lock at all.
6. Makes a detached worktree at that commit, at `worktree-of-main` in a directory named for the program under the system temp directory. A worktree a killed run left there is removed first, with `git worktree remove --force`, then by deleting the directory, then with `git worktree prune`; if a runner of that killed run still uses it, its suites can fail. It runs the worktree's runner once, with `--log-dir` set to a `logs` directory beside the worktree, emptied first, with `--only-suites-named` and the no-sandbox suites listed in that worktree's `scripts/run-all-test-suites.py`, plus `--only-suites-whose-recorded-inputs-changed-since <the passing commit>` when there is one. The runner then runs each no-sandbox suite whose recorded inputs changed since the passing commit, and none when no such input changed. The runner has 60 minutes, counted from its start, its waits for the lock and for CPU admission included; past them its process group gets SIGTERM, then SIGKILL 60 seconds later.
7. Removes the worktree, then writes its record and the state file. The result is passed when the runner exited 0, and the commit becomes the passing commit; failed when it exited 1, with the suites its `FAIL ` lines name, each suite's log copied into the record's directory, and no suite named when it printed no `FAIL ` line; and stopped when the runner ran past its 60 minutes, or exited with any other code, with the reason. A stopped run's record keeps the runner's `FAIL ` lines, but no suite's log is copied.

A run that cannot finish, because the fetch, the worktree, the reading of the suite list or a write failed, records that as stopped in the state file where it can and prints the reason; one whose own lock file cannot be opened only prints the reason. A run that stops, at any step, exits 4, so cron's output file keeps it; a run that finished, whatever its suites did, or found no run due or a lock held, exits 0.

Each run whose runner ran writes one record to the log-store, at `nedlern@ned-box:/home/nedlern/nedschorus-logs/no-sandbox-test-suites-runs/<YYYY-MM-DD>/<HHMMSS>Z.txt`, named by the run's start in UTC, with each failing suite's log beside it as `<HHMMSS>Z-<the suite's path, with / as __>.log`. A record holds the commit tested, the passing commit it was compared with, when the run started and ended, the run's result, the reason for a stopped run, each failing suite with its log, and the runner's `FAIL `, `NOT RUN ` and `SUMMARY:` lines. When the record cannot be written, the run stops without one.

### 3. The fixed-time run is the daily full test run of main

`scripts/scheduled-full-test-run-of-main.py` already starts every day at 00:00 ned-box time, America/Los_Angeles, and runs every suite on main, the no-sandbox suites included. That covers point 4: the suites run every day at a fixed time, whether or not they ran in a quiet gap that day. So the design adds no second fixed-time job. The daily run can still end late on a busy ned-box, or test nothing on a day its fetch fails, as that day's record says. It leaves part 2's state file alone.

### 4. Where a failure goes

A failure in part 2's run is a failure on main, caught after the change merged. `scripts/merge-gate.sh` reads part 2's state file at every run, through part 2's program run with `--print-merge-gate-notice-of-last-failed-or-stopped-run`, and prints a notice on stderr, without changing its exit code, in three cases: the last run failed, naming each failing suite, the log-store copy of its log, the commit range from the passing commit to the commit tested, and the pull requests merged in that range, read from the merge commits on main's first-parent line in the checkout the gate runs from, or, when there is no passing commit yet, that there is no range; the last run stopped, naming the reason and, when the run wrote one, its record; or the state file exists but cannot be read. A missing state file, as before part 2's first run or on a machine without it, prints nothing. When part 2's program itself fails, the gate prints a line saying so, naming reboot-test as the program's owner, and goes on. The gate's header comment, which says the gate only gates, allows this notice. A refusal would stop every agent-seat's merges for one suite's failure, which is the lock on the testing cycle the user-ruling attacks.

merge-lane-2 runs the gate before every merge, so it sees a standing failure within one merge. The notice's last line tells it what to do: for a failure with a range, judge from the failing suites' logs and the merged pull requests which change most likely broke the suite, and send that pull request's author a follow-up request, as it does for a non-blocking finding: a message to the author's agent-seat holding the line `#follow_up_request pull request <number>` and the findings, which `nc-systems/general-tools/pull-request-follow-up-request-from-merge-lane-2-message-save-and-forked-subagent-brief-hand-over-user-prompt-submit-hook.py` hands to that agent-seat; for a failure it cannot place, a failure with no range, a stopped run or an unreadable state file, send the follow-up to reboot-test, which owns the runner. After sending, it runs part 2's program with `--record-follow-up-request-sent`, which writes the time into the state file's last run, a failed or stopped one; from then on the gate prints that run as one line naming the follow-up's time. The command refuses, with exit 2 and a message saying what to do, while a run of part 2 holds its lock, when the last run passed, and when the state file cannot be read; for an unreadable state file nothing can be recorded, and the notice repeats at every merge until part 2's next run replaces the file.

The recorded time belongs to that one run. Part 2's next run replaces the last run, at the next firing for a stopped run, after an hour for a failure, or at the next commit on main, so a standing failure comes back as a full notice, with a range that still starts at the passing commit, and merge-lane-2 sends another follow-up. A failure that part 2's hourly retry clears before merge-lane-2's next run of the gate is never shown; it stays in that run's record.

The user is not told of these failures directly today. The daily full test run writes its record to the log-store, but no seat-brief tells merge-lane-2 to read it. GHI [The daily full test runs tell the user about failures and about test cases that run nowhere or lack a tool, and every test suite prints a skipped test case in one format](https://github.com/nedschorus/nedschorus/issues/1206), which records that gap and is not yet built, is the planned path to the user.

### Tests

- The runner: a selective run runs a no-sandbox suite whose own file, a file its recording read, or a file only strace saw differs, and leaves out one selected for any other reason, such as having no recording, and prints the `NO-SANDBOX SUITE LEFT OUT OF SELECTIVE TEST RUN ` line with its command; `--only-suites-named` and a full run are unchanged; the exit code ignores a left-out suite.
- Part 2's program, each with a fake runner, a fake lock and a scratch repository: it exits 0 when its own lock or the no-sandbox lock is held; it exits 0 when no run is due, and runs again after a stop, after an hour past a failure, and when main moves; a pass moves the passing commit and a failure does not; a missing or unreadable state file counts as empty; a failed fetch exits nonzero and records a stop; the time limit stops the runner and records a stop.
- `scripts/merge-gate.sh`: the notice appears for a failure, a stop and an unreadable state file, and not for a missing one; for a failure or a stop it shrinks to one line after `--record-follow-up-request-sent`; the exit code is unchanged; the notice is gone after a passing run.

## Deferred-decisions

- Whether a pre-push selective test run that waits for the no-sandbox suites' lock behind part 2's run, the daily full test run or nc-mutation-testing stops at its 480-second budget often enough to act on, to be settled from the pre-push records of the month after part 1's rule for a suite whose files the change edits merges.
- Whether a follow-up recorded for a failed run should carry over when part 2's next run fails the same suite, to be settled when merge-lane-2 is seen sending a second follow-up for one standing failure.
- Whether a stopped run should be tried again less often than every 10 minutes when it keeps stopping, to be settled from the stops part 2's cron output file records.
- What part 2 does when `SUITES_RUN_WITHOUT_ANY_SANDBOX` is empty, since the runner refuses `--only-suites-named` with no name, to be settled when the last suite leaves that list.

## The sandbox alternative

The Opus report named a different fix: stub the bwrap of `nc-systems/cold-read/cold-read-agy-cell.py` and of `nc-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py` in the tests, or allow nested user namespaces, so that these suites run inside the nc-test-sandbox. The user ruled on 2026-11-04 to build it, as "What the user decided" says. Pull request [Six no-sandbox suites that start bwrap run in the nc-test-sandbox with a pass-through stand-in for bwrap](https://github.com/nedschorus/nedschorus/pull/2578), merged 2026-11-04, moved the six suites that started that bwrap into the nc-test-sandbox; for the two programs, a `-real-sandbox-test.py` suite holding one case with the real bwrap stays in `SUITES_RUN_WITHOUT_ANY_SANDBOX`. The list's other suites, those that start bwrap or the real ssh, tmux or claude themselves, each need a fix of their own and stay on it until one is built.

On 2026-12-06, a date on reboot-test's task list, reboot-test brings the user, for the suites still on the list, how many distinct failures on main part 2's records and the daily full test runs' records show since 2026-11-06, counting a failure of one suite once from the first run that shows it until a run passes it, beside the lock's measured waits from before the change, so he can decide whether any of them needs its own fix sooner.

## Why it matters

The lock made a test run that selected a no-sandbox suite wait for whichever run held it, and most selections included one, so it lay on the critical path of most pull requests. In the analyses' window, 2026-10-31T00:00Z to 2026-11-02T00:00Z, the Opus report counts 130 selective test runs, 102 of them by authors' pushes and 28 by `scripts/ghi-issue-write.py`, stopped at the pre-push hook's 480-second budget with no verdict, and the push went ahead without one; on 2026-11-02 and 2026-11-03, after that window, another 121 did, the third look's 111 and the fourth look's ten; in 67 of the 111, and in all ten, the suites still waiting were no-sandbox ones waiting for this lock.
