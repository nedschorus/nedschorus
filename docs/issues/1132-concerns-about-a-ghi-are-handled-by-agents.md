# Proposed improvements or changes to a GHI are handled by agents first, and reach the user only when they need him

## Problem

A reviewer of a GHI, or of the code a GHI describes, can find two kinds of thing: an improvement, such as something to remove, archive, simplify or add, and a possible problem. Reviews have tended to look only for problems and their fixes, although simplifying and removing what is obsolete do more for the project's health over time.

The first reviewer that records anything is ghi-guide-agent. Before an agent files or edits a GHI, the ghi-write-tool (`scripts/ghi-issue-write.py`) asks ghi-guide-agent whether an open GHI already covers the draft. ghi-guide-agent may answer instead that the draft may conflict with a user-ruling, because whether a user-ruling still applies is never ghi-guide-agent's to judge (GHI [Build ghi-guide-agent — the GHI knowledge agent](https://github.com/nedschorus/nedschorus/issues/46)).

Today, on main, the ghi-write-tool records that question as a comment on the GHI and adds the label `conflicts-with-a-ruling`, then lets the write go ahead (merged in PR [A ruling question from ghi-info no longer holds up the GHI write: the tool writes the issue and records the question on it](https://github.com/nedschorus/nedschorus/pull/983)). Nothing then reads the comment or acts on it, and every such question waits for the user, although most can be settled without him.

design-to-main settles findings like these inside a run (§ Reuse below), but it has no place for one raised outside a run, such as ghi-guide-agent's about a GHI that no run owns, or an overview writer's about the code it describes.

The user's direction, 2026-10-09: agents handle every proposed improvement or change they can, with at most 3 tries so that they never loop, and the user sees only what needs him. The full discussion is in the minutes `nedlern@ned-box:/home/nedlern/nedsnodes-logs/walk/concerns-files-design-explained-step-by-step-2026-10-09-minutes.md`.

## Example

An agent edits an invented closed GHI whose GHI-MD is `docs/issues/<n>-reopen-old-design-notes.md`. The user once ruled "closed GHIs are frozen", a user-ruling recorded in another GHI; both GHIs are invented for this example. ghi-guide-agent asks: "Does the ruling that closed issues are frozen still allow this edit?" The edit only fixes a broken link.

## The design

1. **Recording.** A reviewer writes one proposed-improvements-or-changes-file per review, beside the document it reviewed, or, for ghi-guide-agent, in the log-store (below), named `<document name>-proposed-improvements-or-changes-<source>-<date>.md`. The file lists everything that review found worth changing. Each entry is an improvement, saying what it would gain (simpler, smaller, an obsolete thing removed, a better way, a helpful addition), or a possible problem, saying what goes wrong and when. A second file from the same source on the same day gets `-2`, then `-3`, at the end of its name. Each entry has an ID, `E1`, `E2` and so on in its file, and its own state, written as one line under it: open, needs the user, or settled, with who settled it, how and when. The handler changes only those state lines, the try lines of rule 4 and the second agent's verdict lines, all through the program of rule 5 once that program is on main; it never rewrites an entry's text, and it changes no line of an entry it is not working on. For example:

   ```
   ## E1 — possible problem: the edit may break the user-ruling "closed GHIs are frozen"
   Goes wrong when: a closed GHI's decision changes without the user.
   State: settled, not worth doing — reboot-test handler, 2026-10-09T22:30Z: the edit only fixes a broken link.
   Try 1 — reboot-test handler, 2026-10-09T22:20Z: read the user-ruling and the diff; the ruling covers decisions, not links.
   Second agent: agrees that it is not worth doing, reboot-test handler, 2026-10-09T22:28Z
   ```
   - About a GHI-MD: ghi-guide-agent, through the ghi-write-tool, is the reviewer that writes them. Its files never reach main: the ghi-write-tool writes each to the log-store directory `nedlern@ned-box:/home/nedlern/nedsnodes-logs/ghi-guide-agent-proposed-improvements-or-changes/`, and the GHI-MD carries no line pointing to them. The handler settles each entry in that file, without a pull request; where rules 5 and 6 say a pull request marks an entry settled, the handler marks it in the file. Only the change an entry calls for reaches main, such as an edit of the GHI-MD through edit-GHI or a new GHI. A settled file stays in the log-store as a record of what ghi-guide-agent asked.
   - Beside an architecture overview: the overview's writer records what it notices in the code, adds one line under the overview's first heading pointing to these files, "This document has proposed improvements or changes: read every file in this folder whose name starts with `<overview name>-proposed-improvements-or-changes-`.", and starts the handler (rule 2). The file and that line reach main in the same pull request.
   - Other documents, such as designs, skills and other wiki pages, get no proposed-improvements-or-changes-files yet. This GHI closes only after the handler has run for a week; before it closes, an Outcome heading added to this GHI-MD records how many entries the handler settled and how many reached the user. ned-box-helper adds a task to its task list that waits on that close; `scripts/agent-seat-due-task-raise-hook.py` raises the task when the GHI closes, and ned-box-helper then puts the question to the user in an approval-walk.
2. **Who picks them up.** The writer that recorded the file, meaning the agent that ran the ghi-write-tool or the agent that wrote the overview, the nightly refresh included, dispatches a forked subagent at once, here called the handler, as CLAUDE.md already has an agent do for review findings. The handler settles what it can, and marks each entry that needs the user as needing the user. The agent-seat that owns the document brings those entries to the user in its next approval-walk. A document with no plain owner, such as a closed GHI-MD, is owned by the agent-seat that recorded the entries, or, when a subagent recorded them, by the agent-seat that dispatched it. Once a program exists that starts one handler per document (What must be built, item 4), the program takes this over.
3. **Several entries.** The handler reads every proposed-improvements-or-changes-file of the document before it acts. Dependent entries: it handles the one furthest upstream first, then checks the others again, since a change upstream may settle them; an entry the upstream change settled is settled in its own try, citing that change. Related entries, sharing one cause: one change, counted as one try for all of them. Independent entries: each on its own.
4. **Tries.** At most 3 for an entry or a group of related entries. Each try is recorded as one line under the entry it worked on, in the same file, saying what was tried, what was found, by whom and when; the tries spent on an entry are its try lines, with no other state. A try on a group of related entries is recorded under each of them. After the user has ruled on an entry, a line under it records his ruling, and its count starts again from that line.
5. **Not worth doing.** An entry is not worth doing when the problem is not real, or the improvement does not pay for itself. The handler must show this from the sources: in the example, the user-ruling's text and the edit's diff, showing the ruling governs changing a closed GHI's decision, not fixing its links. A second, independent agent must agree. The program `scripts/proposed-improvements-or-changes-file-entry-state-try-and-second-agent-verdict-lines-write.py`, which PR [GHI 1132 items 2 and 3: the handler's instructions, the second agent's prompt, and the program that writes an entry's State, Try and verdict lines](https://github.com/nedsnodes/nedsnodes/pull/3069) builds and which is not on main yet, runs the second agent through `claude -p`; the handler does not start it and does not copy its verdict. Until that pull request merges, the rule as first decided applies instead (Decided by the user): the handler starts the second agent as a new subagent and writes its verdict line itself. The second agent gets the entry's text and the sources the handler recorded on its try line, one per source: a path in this repository, a log-store path, `PR <number>` or `GHI <number>`; but not the handler's conclusion, so that it does not simply agree. The program reads the agent's last line, `VERDICT: agrees` or `VERDICT: disagrees`, and writes the verdict as one line under the entry: "Second agent: agrees (or disagrees) that it is not worth doing, <who>, <time>", where <who> is the handler that ran the program; when the last line is anything else, or the agent fails, or it has not finished after 1800 seconds, the program writes no verdict line, prints `FAILED:` with what came back and exits nonzero, and the entry stays open, so rule 6's maintenance job lists it once it has been open more than 7 days. A disagreement counts as a try, so the three-try limit still ends the loop; an entry that reaches the limit goes to the user, and when the second agent disagrees on an entry's third try, the program marks the entry "needs the user" itself; after a disagreement on an earlier try, the entry stays open and the handler may try again. When the second agent agrees, one pull request marks the entry settled as not worth doing, or, in a log-store file, the handler marks it there (rule 1). Without agreement the entry stays open, apart from that third-try case.
6. **Worth doing.** The handler makes the change now: a removal, an archiving, a simplification, an addition, or bringing the edit into line with the ruling. Removing or archiving is a change in its own right, not the side effect of a fix. The same pull request marks the entry settled. If the change is new work, it files a new GHI, and marks the entry settled with that GHI's link. If the entry is worth doing but cannot be done now, the entry stays open; it is the reminder, and no separate task is needed. A maintenance job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058) lists every entry open more than 7 days in its report.
7. **What reaches the user.** Only these, and nothing else:
   - a change that would alter a document the cold-read skill sends to a cold-read-full-run, in a way its step 9 sends to the user;
   - a question whether a user-ruling should change;
   - an entry still open after 3 tries.

   An entry of the first kind, whose change would alter a design, may go to him at once, without spending a try, as in design-to-main. Whatever reaches him comes as one report about the document, a file he reads in an approval-walk and not a GitHub comment, cold-read first, carrying the user-rulings already made on it so he is never asked twice, and taken one item at a time with the /walk-me-through skill. Until the program of What must be built, item 4, exists, the agent-seat that owns the document brings it to him in its next approval-walk. An entry that reached him and that he did not rule on stays "needs the user", and the agent-seat that owns the document brings it again at its next approval-walk. Deferred twice, it becomes a task on that agent-seat's task list, as a twice-deferred walk item does.

A file beside an overview is deleted in the ordinary pull request that settles its last open entry. The pointer line is removed only in the pull request that deletes the overview's last proposed-improvements-or-changes-file. While any such file remains, the line stays.

### The cold-read skill's wording that rule 7 uses

From `.claude/skills/cold-read/SKILL.md` on main, step 2, the documents that need a cold-read-full-run:

> "Wiki files, skills and their prompts, the files under `docs/agents/`, designs, including a GHI-MD that is a design, test designs, and design-contracts need a cold-read-full-run, and so does a change to one of them, with one exception: a change of at most one sentence, or a mechanical one applied by search and replace, such as a rename or a path, gets the cold-read-fast-read instead."

Step 9, which changes to them go to the user:

> "every change you applied that adds, alters or removes what a program or an agent does, must do or may do, or what the document decides or plans, and every finding you declined that would have made such a change. A finding step 7 deferred, and the line it added to `Deferred-decisions`, do not go to the user. An obvious-error-fix does not go to the user; nor does renumbering headings, steps or list items with every reference to them changed to match, nor adding an open question on its own line that starts with `#open_question` and says nothing about when or by whom it must be settled. When you cannot tell, it goes to the user."

In the example, the fix for the broken link changes no such document in such a way, and no user-ruling needs to change, so the entry never reaches the user.

## Reuse of design-to-main

The design takes these rules from `docs/design-to-main/design-to-main-state-machine.system.design.md` on main:

- §1: code routes and agents judge; "The state machine is code and holds no judgement." Rule 2's forked subagent is a stopgap until a program routes these files.
- §6.1: a reviewer's notes file, each material entry "a finding with a failure scenario"; the reviewer names the artifact at fault that is furthest upstream, "since whatever is downstream of it is rewritten from the corrected version anyway" (rules 1 and 3).
- §6.1 and §6.5: a reviewer and the arbitrator prove before they rule, and the arbitrator, ruling `advance` on a reviewer's reject, closes it as unfounded (rule 5, not worth doing).
- §6.6: the user is reached through one cold-read report, carrying prior user-rulings, delivered one item at a time, and only when he is needed (rule 7).
- §7: implementation-writes and test-writes have a ceiling of three, and "A resume from an investigation zeroes the six per-version counters", so every agent gets its chance again after the user steps in (rule 4).

**One difference:** design-to-main's ceilings vary by what is being revised, from one try for a contract-revision to three for a write. Here every entry gets 3, because an entry is smaller than a design-to-main artifact.
