# Cut cold-read-fast-read Gemini token cost

## Why

The cold-read-fast-read calls Gemini through the Antigravity command-line program, `agy`, and Gemini is now billed per token. On 2026-10-24 at 18:17 ned-box time, in agent-instructions-editor's agent-session `fd3dde6d-34c5-4198-9aa4-1209e4d8b1a6`, the user said: "I've been talking to Gemini. I think we're not optimizing its token cost thing correctly. I file a GHI on that." He gave no more detail then, so this GHI states the problem and what to measure; it does not choose a fix. At 19:58 ned-box time the same day, in the same agent-session, he asked: "Is it possible we are not using fresh gemini's - the less context we give them the faster and cheaper the fast cold read should be". The section Is each cold-read-fast-read a fresh Gemini answers the first half of his question from the measurements, and question 9 takes up the second half as a lever to test. Questions 10 and 11 hold what he added later that day: asking the strongest Gemini model, and which of his two Google billing routes pays. The cold-read-fast-read runs on each answer the walk-me-through check program checks during an approval-walk, on every agent-facing message merge-lane-2 reviews, in the explain skill, and whenever an agent gives a document a cold read, so its cost grows with the project's activity.

This GHI is about the money each cold-read-fast-read costs. The GHI [Improve the fast cold read: deterministic context rule, clerical restatement work moved into code, a measured shorter mode (from the 2026-09-07 assessment and task #57)](https://github.com/nedschorus/nedschorus/issues/284) is about how many defects the cold-read-fast-read finds; two of its steps also bear on cost, and this GHI links to them rather than repeating them.

## How a cold-read-fast-read reaches Gemini

- `nc-systems/cold-read/cold-read-fast-read.py` writes its prompt, `FAST_CLARIFY_PROMPT_TEMPLATE`, a copy of `.claude/skills/cold-read/prompts/fast-clarify-prompt.md`, to a temporary file, and `nc-systems/cold-read/cold-read-agy-cell.py` passes the text to `agy --add-dir <repository> --dangerously-skip-permissions --model gemini-3.8-flash-medium --effort medium --output-format text --print <prompt>`.
- The prompt embeds no file. It names files and tells the model to read them. Its first sentence is "Read {TARGET_PATH} in full …", so the cold-read-target's path, which differs on each invocation, is in the prompt's first line. The next sentence tells the model to read `CLAUDE.md` and `docs/nedschorus-wiki/nedschorus-glossary.md`, which are 10,878 and 21,835 bytes on main today, and the system glossaries where needed. The fixed instructions come after the cold-read-target's path.
- `agy` is an agent: it reads files, runs shell commands and fetches web pages with its own tools, and every tool call is a further request to Gemini that re-sends the whole conversation so far. `--add-dir` also loads the repository's `AGENTS.md`, 1,116 bytes.
- `~/.gemini/antigravity-cli/settings.json` on ned-box sets `"modelProvider": "gemini"`, and the agy cold-read-cell launcher gives agy the key in `~/.config/nedschorus/gemini-api.key` as `GEMINI_API_KEY`. agy's log does not name the API host it calls, so whether the Gemini API's caching and batch rules below apply to agy's requests has not been checked.
- agy prints no token counts, so the report's provenance line carries no `tokens=` field, as the docstring of `cold-read-agy-cell.py` says.

## What one cold-read-fast-read costs, measured on ned-box on 2026-10-24

agy keeps every conversation in a SQLite file under `~/.gemini/antigravity-cli/conversations/`, and each request to Gemini has a row in the file's `gen_metadata` table, whose protobuf message holds its token counts. There is no published schema, so the fields were identified by consistency: field 2 is input tokens not served from the cache, field 5 is input tokens served from the cache, and field 3 is output tokens; field 3 always equals field 9, thinking, plus field 10, response; and fields 2 and 5 together grow from one request to the next by about the size of the tool result in between. The scripts and their output are in `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/2026-10-24-gemini-fast-read-token-usage/`: `cold-read-fast-read-run-count-and-token-usage-per-day-from-agy-conversations.py` and its `-output.txt` for the totals below, and `agy-conversation-token-usage-per-model-request.py` and `agy-conversation-tool-call-arguments.py`, each with its output for the sample conversation, for one invocation's requests and tool calls. The prompt each request carries is not extracted by any of them: it is in the `step_payload` column of the conversation file's `steps` table, where the row with `idx` 0 holds the first message.

- The store held 501 conversations, the oldest created 2026-10-23 12:20. 403 of them are cold-read-fast-reads, recognised by "Question 1: What it says" in their first message, run between then and 2026-10-24 18:20, about 30 hours. The Mac's agy store was not examined, so cold-read-fast-reads run on the Mac are not in these numbers.
- Per cold-read-fast-read, the medians are 13 requests to Gemini, 78,389 input tokens not served from the cache, 249,978 input tokens served from the cache, and 14,743 output tokens. The largest invocation made 81 requests. Thinking is 4.69 million of the 5.82 million output tokens, about 80%.
- The first request of an invocation carries a median of 9,102 input tokens. A one-question agy call that reads no files, the blind-guess call in `.claude/agents/new-name-propose-and-check-fresh-agent.md`, carries about 6,860, so about 6,800 tokens are agy's own instructions and tool definitions, and about 2,300 are the fast-clarify prompt and `AGENTS.md`.
- The cache serves nothing to the first three requests of nearly every invocation: the first request got a cache hit in 5 of 403 invocations, the second in 2 of 295 and the third in 0 of 288, while the fourth got one in 269 of 288, and later requests almost always did. These first three requests, which read the cold-read-target, `CLAUDE.md` and the glossary, are paid at the full input price each time, although agy's 6,800-token preamble and the two fixed files are the same every time.
- In the sample conversation `c6545e75-23f5-47d2-9e24-0231b66974a3`, whose cold-read-record is `nedlern@ned-box:/home/nedlern/nedschorus-logs/cold-read-records/item14b-2026-10-24/`, the model made 34 requests. After reading `CLAUDE.md`, the glossary and the cold-read-target, it made 30 more tool calls: among them it read `scripts/checkout-freshness-catch-up.py` in ten `sed` pieces, ran `git grep` and `ls` several times, and fetched a Claude Code documentation page with `curl`. Each call re-sent the whole conversation, which grew from 12,000 to 80,000 tokens.

Prices for Gemini 3.8 Flash on the Gemini API's standard paid tier, per million tokens, until 2026-12-31, from the [pricing page](https://ai.google.dev/gemini-api/docs/pricing): input $0.75; output, thinking included, $3.75; input served from a cache $0.075; cache storage $0.50 per hour. All four double on 2027-01-01. The Batch API costs half as much.

At those prices the median cold-read-fast-read costs about $0.13: $0.059 for input not served from the cache, $0.019 for input served from it, and $0.055 for output. The 403 invocations on ned-box cost about $57 together: $22 for input not served from the cache, $12 for input served from it, and $22 for output. So output is about 40% of the cost, input not served from the cache about 40%, and the re-sent conversation that the cache serves about 20%.

How many cold-read-fast-reads run: the log-store holds 1,748 cold-read-records with a `fast-read.md`, written from 2026-10-18 to 2026-10-24, between 77 and 468 a day, counted with `find /home/nedlern/nedschorus-logs/cold-read-records -maxdepth 2 -name fast-read.md -newermt <day> ! -newermt '<day> 23:59:59'`. 729 of them are agent-facing messages, whose record names contain `agent-facing-message`, 198 are approval-walk items, and 17 are explain replies. A cold-read-fast-read of an approval-walk's `-draft` file writes its suggestions file beside that file and ships no cold-read-record, so the records undercount: 2026-10-23 has 261 records against 323 cold-read-fast-reads in ned-box's agy store. The same text is often read several times in a day as it is revised, for example the five records `nedlern@ned-box:/home/nedlern/nedschorus-logs/cold-read-records/item-6.1-v2-2026-10-24/` to `item-6.1-v6-2026-10-24/`, all from 2026-10-24.

## Is each cold-read-fast-read a fresh Gemini

It is fresh but not lean. Each attempt of `cold-read-fast-read.py`, in `run_one_fast_clarify_cell`, starts `cold-read-agy-cell.py` as a new process, and that launches `agy --print` with no option that resumes an earlier conversation, so each attempt is a conversation of its own in agy's store, which is why the store above holds one conversation per cold-read-fast-read. No reader carries anything over from an earlier read. What the reader is given is large, though: about 6,800 tokens of agy's own instructions and tool definitions come before the fast-clarify prompt; the prompt has the reader open `CLAUDE.md`, the glossary and the cold-read-target with tool calls; and every tool call re-sends the whole conversation. So the median read makes 13 requests and sends about 330,000 input tokens, 78,389 not served from the cache and 249,978 served from it, to review a cold-read-target whose median length is 220 words. That median is over the 1,772 cold-read-records written since 2026-10-18, counted on the copy marked with sentence ids that each record keeps, ids included, by `cold-read-target-word-count-quartiles-from-sentence-id-copies.py` in the analysis directory above, with its `-output.txt`; a quarter of the cold-read-targets are over 452 words.

## Gemini's caching rules

From [Context caching](https://ai.google.dev/gemini-api/docs/caching) and [explicit caching with generateContent](https://ai.google.dev/gemini-api/docs/generate-content/caching):

- Implicit caching is on by default for Gemini 2.5 and newer models and needs no setup. A request is served from the cache only when it starts with the same tokens as a recent request, at least 4,096 of them for Gemini 3.8 Flash. The page advises putting large content that does not change at the start of the prompt, and sending requests that start the same way within a short time of each other.
- Explicit caching stores chosen content for a time to live, one hour by default, billed per hour of storage. It is offered for Gemini 3 and 2.5 models through the `generateContent` API, not through the Interactions API. agy has no option for it, so using it means calling the Gemini API without agy.

## Questions to answer

1. Why do the first three requests of an invocation miss the cache, when agy's 6,800-token preamble is the same each time and is longer than the 4,096-token minimum? Four causes to check, each on its own: values in agy's own preamble that change per invocation, such as a date, a conversation id or the workspace path, before its 4,096th token; the cold-read-target's path in the first line of the fast-clarify prompt, which comes after agy's preamble; a delay before a new cache entry can serve requests; or agy's route to Gemini not caching at all.
2. Would putting the fixed text first help: the fast-clarify instructions before the cold-read-target's path, and `CLAUDE.md` and the glossary embedded in the prompt instead of read with tools? Several cold-read-fast-reads run each hour, often enough that a shared start could stay cached. If explicit caching is used instead, its storage is small beside the savings: 10,000 tokens kept for a day cost 10,000 × $0.50 per million per hour × 24 hours, $0.12.
3. How many requests does a cold-read-fast-read need? Most of a long invocation's cost is the conversation re-sent on each tool call. Step 1 of [the GHI on how many defects the fast cold read finds, linked under Why](https://github.com/nedschorus/nedschorus/issues/284), following each explicit reference once and no further, would cut tool calls. Would a cold-read-fast-read that gets the cold-read-target and the fixed files in its prompt, with no tools or only a few, find as many defects?
4. Can output be cut? Output is about 40% of the cost, and mostly thinking. Compare `--effort low` with medium on cost as well as on recall, which [the same GHI](https://github.com/nedschorus/nedschorus/issues/284) measured alone, and see whether the restatement can be shorter, item 3 of that GHI.
5. Can fewer cold-read-fast-reads run? For example, skip one when the text matches one already read. Reading only the changed sentences of a revised text would serve Question 1 of the fast-clarify prompt, the restatement, but not Questions 2 and 3, which look across the whole text, so it needs a design of its own.
6. Is a cheaper model good enough? The pricing page lists Gemini Flash-Lite models, which the project has not measured for the cold-read-fast-read. Here and in question 4, "good enough" means recall on the ghi-write defect list that [the GHI linked under Why](https://github.com/nedschorus/nedschorus/issues/284) measured with, run five or more times per arm as that GHI found necessary, compared with Gemini 3.8 Flash at medium.
7. Would the Batch API's half price suit a caller that does not wait for the answer? Batch results do not come back at once, and every caller named under Why waits for its report today, so this applies only to a caller that does not. It also means calling the Gemini API without agy.
8. Is the billing what this GHI assumes? Confirm in Google's console, on the usage page of the Gemini API key, that cold-read-fast-read tokens are billed to that key at the standard paid tier, and compare one day's charge with this GHI's estimate. A charge that does not match is also the first sign that agy's requests do not go through the public Gemini API, in which case the caching rules above may not apply to them.
9. Would one direct request to the Gemini API, with no agent loop, read as well for much less? This is the user's lever, quoted under Why. His words ask for less context. The measurements above show where the excess is: agy's preamble and the conversation re-sent on every tool call, about 330,000 input tokens a read, beside which the roughly 8,400 tokens of the glossaries are small. This question cuts the excess and keeps the glossaries. Each read would get the whole project glossary and the system glossaries, not only the entries the cold-read-target uses, so that the reader writes in the project's terms even where the cold-read-target does not; the user asked for that on 2026-10-24, through the agent that dispatched this edit. The lever goes further than questions 2 and 3: no agy, no tools, and so nothing re-sent. His model is a fork: build the reader's state once, from the fast-clarify prompt, `CLAUDE.md` and the glossaries, keep it, and start each read from that kept state with only the new cold-read-target added. Each read stays fresh, because no earlier cold-read-target is in it. Details the design must carry:
   - Explicit caching does what the fork needs. On [explicit caching with generateContent](https://ai.google.dev/gemini-api/docs/generate-content/caching), a program creates a `cachedContents` resource holding a `system_instruction` and `contents`, kept for its `ttl`, one hour unless set, with no minimum or maximum; each `generateContent` request names it in `cachedContent` and puts its own text in `contents`, and "Cached content is a prefix to the prompt." So the fixed text is stored once and each request adds one cold-read-target. The program must create the cache again when it has expired, and whenever `CLAUDE.md`, a glossary or the prompt changes on main, or reads go on using the old text. Storage costs $0.50 per million tokens per hour, so about 12,600 tokens kept for a day cost about $0.15.
   - Implicit caching does it only by chance. The [caching page](https://ai.google.dev/gemini-api/docs/caching) asks for large shared content at the start of the prompt and for requests "with similar prefix in a short amount of time"; it says neither how alike the prefix must be nor how long an implicit cache entry lasts, and it promises no saving. A byte-identical prefix of at least 4,096 tokens, the minimum for Gemini 3.8 Flash, is the most a program can do for it, and reads in quiet hours, such as overnight, would still miss.
   - The fixed text is about 12,600 tokens: the fast-clarify prompt, 5,848 bytes, with the cold-read-target's path moved out of its first line; `CLAUDE.md`, 10,878 bytes; the project glossary, 21,835 bytes; and the three system glossaries the project glossary names, 11,915 bytes together. That is estimated at 4 bytes a token; count it with the API's `countTokens` before relying on it.
   - The request must carry the copy of the cold-read-target marked with sentence ids, as agy is given today, because `attach_sentences_and_coverage` in `cold-read-fast-read.py` matches each restatement to its sentence by id.
   - Thinking stays at medium. On the [thinking page](https://ai.google.dev/gemini-api/docs/thinking), Gemini 3.8 Flash's `thinking_level` takes `low`, `medium` or `high`, medium by default, and thinking cannot be turned off; `max_output_tokens` counts thinking and cuts the answer off when reached, with the thinking still billed, so it is not a safe cap. `thinking_level` is the same setting as agy's `--effort`, which the user set to medium on 2026-09-07, so any change to it is question 4's to decide.
   - The program, not the model, writes the report: it writes the response text to the report path, and the rest of `cold-read-fast-read.py`, the one retry, the sentence coverage, the list of bare issue and pull request numbers, and the shipping of the cold-read-record, stays as it is. A request with no tools reads and writes no file, so on this path the credential sandbox in `cold-read-agy-cell.py` and its recovery of a review answered in chat, `stdout_is_a_review`, have nothing to do. The response's `usageMetadata`, with `promptTokenCount`, `cachedContentTokenCount`, `candidatesTokenCount` and `thoughtsTokenCount` on the [generateContent reference](https://ai.google.dev/api/generate-content), gives each read's token counts, which would fill the provenance stamp's `tokens=` field that agy leaves empty.

   What it would save, estimated: at the median, input not served from the cache costs $0.059 and input served from it $0.019 a read today. With explicit caching, a direct request would pay for about 12,600 cached tokens, $0.0009, plus a median cold-read-target of about 300 tokens at the full price, $0.0002, and its share of the day's storage, about $0.15. So input falls from about $0.078 to well under $0.01 a read. Output, $0.055 at the median and mostly thinking, is not cut by this lever directly; one request may think less than 13 did, which only measurement can show. The median read would cost about $0.06 or less instead of $0.13.

   What it gives up, measured against what the project wants from the reader: the glossary defines a fresh-reader as reading "the document and what it links", and the fast-clarify prompt has the reader follow the cold-read-target's references, search the repository for a bare file name, fetch linked web pages and report a reference that does not resolve. One request with no tools can do none of that, so the design must say for each how it is kept or that it is given up, and must rewrite the prompt's Question 2 bullets on references to match. The program can check that each repository path exists and that each bare file name matches exactly one file, and put the results in the request; that is new code, beside step 2 of [the GHI linked under Why](https://github.com/nedschorus/nedschorus/issues/284), which moved only the sentence ids and the coverage check into code. It can embed the repository files the cold-read-target names, one hop as that GHI's step 1 proposes, at a cost in tokens not served from the cache; that needs a size limit, because one named file can be large: `scripts/checkout-freshness-catch-up.py`, which the sample conversation above read, is 93,587 bytes. And it can fetch linked pages itself or leave them unread. The reader still knows the project's terms, because `CLAUDE.md` and the glossaries are in every request.

   How to test it: on ned-box, give both forms the same few cold-read-targets: the first version of the ghi-write skill, `cold-read-reviewer-test-cases/ghi-write-trio/ghi-write-first-draft-6a098f4.md`, which [the GHI linked under Why](https://github.com/nedschorus/nedschorus/issues/284) scored against `ghi-write-defect-list-2026-09-07.md` in the same directory, the ghi-write defect list question 6 names, and two or three agent-facing messages and approval-walk items from the cold-read-records. Run each form five or more times on each cold-read-target, as question 6 requires. Compare cost, from `usageMetadata` for the direct form and from the agy conversation store with the scripts in the analysis directory above for agy; wall time per read; recall on the ghi-write defect list; and, for the cold-read-targets that hold a reference that does not resolve, whether each form reports it. Check `cachedContentTokenCount` to confirm that each request is served the cached prefix. Run one hop of embedded files as a further form, if the first comparison shows the direct form worth having.
