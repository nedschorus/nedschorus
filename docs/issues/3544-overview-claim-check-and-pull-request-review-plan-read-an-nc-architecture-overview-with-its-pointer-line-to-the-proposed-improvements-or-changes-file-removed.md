# Overview claim check and pull request review plan: read an nc-architecture-overview with its pointer line to the proposed-improvements-or-changes-file removed

## Why

The claim-check program, `nc-systems/skills/overview-write/overview-write-architecture-overview-claim-check-by-fresh-agent.py`, checks an nc-architecture-overview's claims against the code with several fresh-agents. When it first writes claims to the overview's proposed-improvements-or-changes-file, it tells the writer to add a pointer line under the overview's first heading. In the form pull request [overview-write: the claim check appends to one proposals file per overview, outside the wiki; overview page's merge, handler and pointer-line rulings](https://github.com/nedschorus/nedschorus/pull/3406) gives it, that line reads "This document has proposed improvements or changes: read `<system>-architecture-overview-proposed-improvements-or-changes-entries.md` in `nc-systems/<system>/docs/`.". The page `docs/nedschorus-wiki/nedschorus-how-to-write-an-architecture-overview.md` says the line stands before the overview's seven sections and is not one of them.

Adding that line changes the overview's text, so its git blob changes. `scripts/pull-request-review-plan.py` lets an overview merge only when the newest claim-check report for the overview's blob at the pull request's head shows no claim ranked must fix, so the writer must run the whole claim check again for a line the program composed itself. That rerun costs several fresh-agents, and each rerun can also append new entries to the proposed-improvements-or-changes-file. In pull request 3406, adding the line to `docs/nedschorus-wiki/nedschorus-handoff-architecture-overview.md` needed a full rerun, which appended four claims ranked fix later, E56 to E59, to `nc-systems/handoff/docs/handoff-architecture-overview-proposed-improvements-or-changes-entries.md` (commit `d3d576b62` on that pull request's branch, head `a5434db17` on 2026-11-13).

## What is decided

The claim-check program and `scripts/pull-request-review-plan.py` both read the overview with the pointer line removed, whether or not the line is present, so that adding the line after the first check needs no second claim-check run.

After this change, the check runs on the overview's text as it will merge, less the pointer line; the rest of that ruling stands.

The option the user did not choose: the claim-check program writes the pointer line into the writer's checkout itself, before it computes the text it checks. It was set aside because the program would then edit the overview where the writer does not see it, and the writer might push that edit without reading it.

## Open questions

1. How the pointer line is found and removed. On pull request 3406's branch, the claim-check program builds the exact line with `overview_pointer_line_to_proposed_improvements_or_changes_file()` from the overview's path, and tests whether the line is present by an exact whole-line match, `pointer_line not in text.splitlines()`. Removing only that line leaves the blank lines around it, so the overview read with the line removed and the same overview without the line ever added can differ by a blank line. The removal must give the same text in both cases. Whoever builds this decides whether the line is removed only where the how-to page puts it, under the first heading, or wherever it stands; what is removed with it, such as the blank line after it; and what happens when it stands with no blank line beside it, or twice. A line that differs from the built line, such as one with a typing slip, is not removed: the check then reads it as overview text, while the claim-check program's closing instruction still says the line is missing. Question 3 covers catching that.
2. What key the reports are filed under. Both programs key a claim-check report by the overview's git blob, from `git rev-parse <revision>:<path>`: the claim-check program names each report `<overview blob>-<UTC time>.md`, and counts malformed reports by that prefix, and `scripts/pull-request-review-plan.py` looks reports up with `find_newest_architecture_overview_claim_check_report_path_and_result_for_overview_git_blob()`, which it imports from the claim-check program. After this change, both must compute the report key from the text with the pointer line removed, through one new function in the claim-check program, which the review plan already loads as a module. If the report key is the git blob hash of the text with the line removed, as `git hash-object --stdin` gives it, then for an overview that has no pointer line the report key equals today's blob, and existing reports stay valid; a test asserts that. Existing reports of an overview that already holds the line no longer match, so such an overview needs one more claim-check run after this lands. Whoever builds this also decides whether the report's `overview blob:` header line and the review plan's refusal message, which today name the git blob, name the report key instead or both.
3. What still checks that the pointer line is present when the overview's proposed-improvements-or-changes-file exists. Today only the claim-check program's closing instruction asks the writer to add the line; nothing at the merge gate refuses an overview without it. Candidate 5 of GHI [Architecture overview claim check and lint: steps the writer does by hand that code could take over](https://github.com/nedschorus/nedschorus/issues/3418) proposes that `scripts/md-drift-lint.py` check it. Removing the line from the checked text takes away the one thing that made a missing or mistyped line costly to notice, the changed blob, so an overview could merge without the line and nothing would say so. The review plan, which already finds the overview and its report, could instead refuse an overview whose proposed-improvements-or-changes-file exists and whose text lacks the exact built line. Whoever builds this decides whether either check is needed now, under CLAUDE.md's rule for guards, and if so builds it in the same pull request.
4. How this meets GHI [Overview claim check: judge again only new, changed or flagged claims, and keep a supported claim's verdict while its wording and cited files are unchanged](https://github.com/nedschorus/nedschorus/issues/2532). That design has code split the overview into claims, and keeps the review plan's lookup by overview blob unchanged. Whoever builds either reads the other first: the claims are split from the text with the pointer line removed, through the same function that gives the report key, and the review plan's lookup changes as question 2 says.
