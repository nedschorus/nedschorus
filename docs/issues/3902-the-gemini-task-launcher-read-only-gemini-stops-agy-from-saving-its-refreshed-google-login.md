# The Gemini task launcher's read-only `~/.gemini` stops agy from saving its refreshed Google login

## The defect

`scripts/run-gemini-task-from-brief.py` runs agy, the Antigravity command-line program that gives us Gemini, inside the sandbox that `credential_sandbox_prefix` in `nn-systems/cold-read/cold-read-agy-cell.py` builds. Because the launcher always passes writable paths, that function starts the Linux sandbox with `bwrap --ro-bind / /` and adds `--bind` only for the report file and, under `--sandbox workspace-write`, the checkout and each `--writable-root`. `~/.gemini` is therefore read-only in both modes; the launcher's own help says so ("not even its own state under ~/.gemini"). On macOS the same function denies every write outside those paths through `sandbox-exec`.

On ned-box agy keeps its Google login in the file `~/.gemini/antigravity-cli/antigravity-oauth-token` and rewrites that file every time it refreshes the access token, which lasts one hour. The keyring cannot be used on ned-box: agy's logs record `Failed keyring SaveToken, falling back to file when applicable: failed to unlock correct collection '/org/freedesktop/secrets/aliases/default'`, so the file is the only place a refreshed login is kept. Inside the launcher's sandbox that write must fail whenever agy's stored token expires while a task runs.

Why it matters: the launcher exists so that agents can hand Gemini tasks that run on the user's Google login rather than a billed API key. If agy treats the failed save as an error, a task that spans the token's expiry fails; if it only logs it, the task continues but every later run refreshes again from a stale file. Which of the two happens has not been observed.

## Evidence

Full findings, with the log excerpts and the commands used: `nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/prime-intellect/agy-gemini-login-refresh-writes-2026-11-18.md`. In short:

- The token file's stored expiry equals its modification time plus one hour, and agy's logs under `~/.gemini/antigravity-cli/log/` show a chain of runs on 2026-11-18, each loading the expiry the previous run's refresh wrote to the file.
- agy refreshes inside a process that is already running, not only at start-up: `~/.gemini/antigravity-cli/log/cli-20261118_163901.log` loaded the token at 16:39:01 with `expired=false`, logged `token refreshed` at 16:48:01.80, the moment the stored token expired, and the file's modification time is 16:48:01.808. So any launcher task that is running when the stored token expires needs the write, however short the task.
- No launcher run so far has refreshed inside the read-only sandbox: none of the 122 `*.run.log` files in the log-store contains `token refreshed`, `SaveToken`, `oauth-token` or `keyringAuth: loaded token`.
- The agy binary (a Go program with no source on disk) holds two messages for this failure: `failed to persist refreshed token: %w`, which returns the error, and `Failed to save refreshed token: %v`, which logs it. Which one the command-line login uses could not be told from the binary.
- A test that changes no credentials was tried on 2026-11-18: wait for the stored token to expire on its own, then run the launcher once on a trivial brief with no other agy process running. It was skipped because an agy cold-read cell, running under `bwrap --dev-bind / /`, refreshed the file first, at 16:48:01; the launcher was never run, so there is no exit status. agy cold-read cells run on ned-box much of the day, which makes a moment with none running at expiry rare.

## What to decide

Choose how agy, inside the launcher's sandbox, keeps a refreshed login. One option is to bind the directory `~/.gemini/antigravity-cli/`, or only the file `~/.gemini/antigravity-cli/antigravity-oauth-token`, writable in `credential_sandbox_prefix` whenever writable paths are given; `nn-systems/general-tools/agy-print-prompt-run-in-empty-home-sandbox.py` already binds all of `~/.gemini` writable. Binding only the file works only if agy rewrites it in place: a file bound on its own cannot be replaced by rename, as the launcher's help says of its report file, and whether agy writes in place or by rename is unknown (unverified). Any choice weighs giving a Gemini task write access to the user's Google login against the failure above. The fix must also be made to agree with GHI [Cold-read reviewer sandboxes deny a fixed list of credential directories instead of scanning the home directory for credential files in nn-systems/cold-read/cold-read-cell-common.py, and a daily check reports new credential files](https://github.com/nedsnodes/nedsnodes/issues/2990), which is changing how the same module family, `nn-systems/cold-read/cold-read-cell-common.py`, decides which credential paths a sandbox hides. If the test below shows agy only logs the failed save, the fix is still wanted, because each later run then refreshes from a stale file, but it is less urgent. Whether macOS is affected too depends on whether agy there saves its login to the Keychain or to this file (unverified).

## Next action

Whoever takes this up first runs a test to learn whether the failed save fails the task. Take the stored token's expiry as the token file's modification time plus one hour, so the credential file is never opened. About three minutes before that moment, run `scripts/run-gemini-task-from-brief.py -C <checkout> --brief <brief> -o <report> --sandbox read-only --network`, where the brief asks for work that lasts past the expiry, such as reading several large files in the checkout one after another before writing one sentence to the report. Then read `<report>.run.log` for `token refreshed`, `Failed to save refreshed token`, `failed to persist refreshed token` or `read-only file system`, and record the exit status. Other agy processes refreshing the file at the same moment do not spoil this test, because the sandboxed agy holds the copy of the token it loaded at start and must refresh and save that itself (unverified); the run log shows whether it did. Do not delete, edit or expire the token file to force the case. Then pick the fix, and add a test that checks the argument list `credential_sandbox_prefix` returns binds the chosen token path writable; such a test never touches the real login.
