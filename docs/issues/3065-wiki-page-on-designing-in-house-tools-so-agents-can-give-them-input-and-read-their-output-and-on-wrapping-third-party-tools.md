# Wiki page on designing in-house tools so agents can give them input and read their output, and on wrapping third-party tools

Agents write and change this project's command-line tools, hooks, scheduled jobs and nc-test-suites, but they often design them for a person at a terminal: a long text passed as a quoted argument, a wait with no deadline, a read of stdin that blocks until stdin is closed, help text that names an option but not its default. This GHI writes one wiki page, the hub page, that says how to design an in-house tool for agents, and when and how to wrap a third-party tool. Wrapping here means changing how agents use a third-party tool without changing the tool itself: a wrapper script that runs it, a hook that refuses or guides a call to it, or an MCP (Model Context Protocol) server that offers agents some of its operations. Two pages already on main cover parts of the subject, and the hub page links them rather than restating them: the page on exit codes, for what an in-house tool reports, and the tool-message-to-agent page, for how its messages are worded. This GHI also carries the pull requests, listed under What to build, that change in-house tools across the repository to follow the rules the user approves.

## What the hub page says, as proposed by the research

Each bullet is marked with where it stands: decided, with the entry above or the page it comes from; or proposed, with the Deferred-decision that puts it to the user. The hub page states a proposed bullet as a rule only after he approves it.

- **What an in-house tool is** (decided, entries 1 and 2): command-line tools that an agent or the user starts, hooks, scheduled jobs and nc-test-suites, with modules left out. Which kind a file is when it fits none of these, or two, is Deferred-decision 2.
- **`--help` is the manual** (decided, entry 5), in one format for every in-house tool (proposed, Deferred-decision 8), so an agent knows where to look and what it will find.
- **A usage error**, a tool called the wrong way, prints its error and usage line on stderr and exits 2 (decided, the page on exit codes), and also names the `--help` command (proposed, Deferred-decision 8). argparse prints the usage line and exits 2 by itself, and with `allow_abbrev=False` it stops taking a prefix of an option for the whole option (proposed, Deferred-decision 7).
- **Input an agent can give without guessing** (proposed, Deferred-decision 9): a long or multi-line text from a file, through an option such as `--body-file`; no read of stdin when stdin is a terminal, unless an option asks for it.
- **Output an agent can read** (proposed, Deferred-decision 9): bounded in size, with a count of what was left out; a `--json` option where a caller parses the output. The exit code and the streams follow the page on exit codes.
- **Time** (proposed, Deferred-decision 10): every wait has a deadline, or the tool's `--help` says why it waits without one, as a supervisor waiting for its agent-session does; a tool whose deadline passes exits 2 and says on stderr what it may already have changed. A tool that starts a long-running operation says whether it ran it synchronously, waiting for the end, or asynchronously; an asynchronous one names the command that reports the result.
- **Parallel work and shared state** (proposed, Deferred-decision 10): a pool of workers doing CPU-bound work is sized by `os.process_cpu_count()`, the CPUs the process may use, not `os.cpu_count()`, the machine's, and below Python 3.13, which added it, by `len(os.sched_getaffinity(0))` where that exists; two in-house tools that change one file or resource take one lock with one name; every step that may run twice is idempotent.
- **Wrapping a third-party tool** (proposed, Deferred-decision 11): a wrapper script or a hook first; an MCP server only to add context or to offer agents some of a third-party tool's operations, with a hook or a permission rule that removes agents' direct access to the operations the MCP server leaves out. A wrapper script exits 0, 1 or 2 as the page on exit codes says, for its own yes-or-no question: it turns each code of the third-party tool into that question's answer, and any code it cannot read as an answer, such as git's 128, into 2, and prints that code and the third-party tool's stderr.
- **Inviting changes** (proposed; the user decides it when he reviews the hub page in step 3): an agent that finds a rule wrong or missing proposes the change in a pull request that changes the hub page.
