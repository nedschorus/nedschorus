# Problem words and phrases: one page listing each word to avoid with why it is flagged and what to write instead, its checker, and a daily search of the transcripts for new rows

## Why

The user reads agents' messages cold, across many agents' terminals, and loses time to words he cannot pin down. On 2026-09-30, in the approval-walk explain-skill-draft-2026-09-29-2 of the agent-seat merge-lane-backlog, he directed a list of words agents should avoid, each with the reason and the word to write instead:

> "I have been thinking of having a 'bad' word list, an anti-glossary of sorts, words that should be avoided (and why). It, land, ... seem like good candidates"

He also named a second class, with a different reason and a different message to the agent:

> "agents saying they will remmember somethig, or will do something soon, but unless the todo soons are in a tasks list, or the remember somethings have some reminder or enforcmentt, those are 'bad' too - though for very different reasons - requiring very different 'error messages'."

He asked that the checker be mechanical and that each entry carry what to write instead ("Is the style guide checker mechnical - if so good - I assume each word has the prefered alternative?"), and that the list be measured from the transcripts before the list is written ("we might want to review our jsonls for additional 'bad words'"). He approved filing the work ("y", 2026-09-30).

The legacy system's list failed as text alone. The legacy list's page records that "under heavy context ... the model falls back to training priors", and the one class of wording the legacy system enforced with a hook at the moment of action, its postal softener guard (under Supporting documents), is the class that held, by the legacy GitHub issue nedlern/nedlern#1513, which this GHI-MD's first version cited. The user can open those legacy files; the agent-seats cannot. So this GHI builds the list and the checker that enforces the list together.

The list is one for the whole project, not one per nc-system as the glossaries are (user, 2026-10-01).

2. **A "Why it is flagged" column**, placed between Forms not flagged and Write instead. Each cell holds one sentence of reason, such as "carries five project meanings, so a reader cannot tell which one the writer meant" for `seat`, or "the project's word for this is merge" for `land`. The reason written for each of the 36 rows goes to the user in one approval-walk before the pull request that adds the column merges, because a change to a row of this table is never a cosmetic-change. The checker rejects a row whose Why it is flagged cell is empty, as it rejects other malformed rows today. The paragraph above the table that gives one reason for all rows, and the Markdown edit hook's opening lines that repeat it, are cut to what the column does not say. The checker, and the Markdown edit hook that formats its hits for the agent, report each hit with the row's Why it is flagged text and its Write instead text, as the user approved on 2026-10-05.

3. **Rows that turn a plain phrase into its glossary term.** A phrase in plain words that stands for one glossary term, such as "log store" for the log-store, gets a row whose Write instead cell is the glossary's term, as the rows listed under What exists today do. The rows come from item 4's daily search, which proposes a row when it finds the plain phrase used, more often than its threshold, for the term's meaning. Each term added to the project glossary, or to a system glossary listed at its top, since the search's last run gets its plain phrases counted from then on, so a new term's plain phrase reaches the search without anyone having to remember it. Each new row is the user's decision, like every other row.

4. **A daily search of agent-session transcripts and cold-read-records for new problem words** (user-approved 2026-10-05; daily, 2026-10-08), as one more maintenance-job of GHI 1058, whose GHI-MD gains the maintenance-job in an edit of its own. Its steps, divided by code-prompt-code:
   - **A model names the plain phrases** of each glossary term the job has not seen before, which on the first run is every term: code reads the terms from the project glossary and the system glossaries listed at its top, compares them with the terms the job's state file holds, and hands each new term with its definition to a model, which returns, as JSON, the plain phrases a writer would use for it. Code stores the phrases in the state file as candidates.
   - **Code counts**, with no model, over the agent-session transcripts and cold-read-records written since the job's last run, or over the last 30 days on its first run: the words and phrases the user asked the meaning of, or said confused him; the words cold-read-cells quoted as unclear; the plain phrases of glossary terms; and the seed candidates of item 5. The transcripts are those of both machines, read as the 2026-09-30 measurement script under Supporting documents reads them, which is where the counting code starts: the user's typed messages and the agent messages he sees, from interactive agent-sessions. Code keeps a running count per candidate in a state file of the job's own, so a word that recurs over days rises, and keeps counting every candidate, including one it holds back. Code holds back from the model a candidate that is a form an existing row flags or lists as not flagged; one the state file records as waiting for the user, approved, or declined by the user; and one the model judged not a problem, or whose proposed row code dropped, until its count has doubled since.
   - **A model judges** the candidates whose count exceeded a threshold that code applies, with the sentences in which the count found each: whether each is a problem word or phrase, and, for each that is, the row it proposes, returned as JSON whose schema holds the row's Word, its Forms flagged and Forms not flagged, its Why it is flagged sentence, its Write instead text, and its Applies to, one or more of the three values the column holds today. Code writes the row's Markdown from that JSON. When the model fails, returns nothing code can read, or runs past its time limit, the job reports the failure as GHI 1058 says for its jobs' failures, and the candidates wait for the next run.
   - **Code checks** each proposed row: it drops each proposed form that an existing row already flags or lists as not flagged, then drops the row when its Word was among those forms or no flagged form is left, when its forms match none of the sentences in which the count found the candidate, or when the checker's table parser rejects it. When two proposed rows share a form, code keeps the row of the candidate with the higher count, and the other candidate waits for the next run. When the checker cannot read the page, the job reports the failure as above and stops for the day.
   - **The user decides** each proposed row in the approval-walk of GHI 1058's section "How a daily job is handed to the user and tracked (decided)". At each run, code writes the rows the user approved since the last run into the page and opens one pull request for them, with the line `#no_defect_fixed` in its description; records each declined row in the job's state file so that the row is not proposed again; and keeps an approved row marked approved until its pull request merges. An approved row whose pull request could not be opened stays approved and goes into the next run's pull request. Each day the job asks GitHub, with `gh pr view`, for the state of every pull request the state file holds as open; when one closed unmerged, its rows go back to the user in the approval-walk with the pull request's link. When a pull request cannot be opened, its state cannot be read, or a `gh` call runs past its time limit, code reports the failure as above.

   The script's name is chosen when the maintenance-job is built, by the naming page `docs/nedsnodes-wiki/nedsnodes-how-to-choose-a-name-for-files-code-and-glossary-terms.md`.

5. **Seed candidates**, decided by the user or proposed already, beyond the rows on the page. A file in the repository holds them as strings, and item 4's job reads it each day and counts them as candidates, so the count, not the build, decides which ones agents still use. Today the job cannot read the legacy list, which is on the user's Mac and in a private repository, so an agent-seat on the Mac copies the legacy list's words into the file. They are: every word and phrase of the legacy list's sections Overloaded Words to Avoid and Deceptive Phrases That Hide Intent; and phrases that declare a fresh thing established, a class the user called "a 100% fail indicator" (user-ruled 2026-07-22, as this GHI-MD's first version records), such as "standing doctrine", "is now doctrine" and "established practice". The file's name is chosen when it is built, by the naming page.

6. **The checker's four places**, approved before 2026-10-05 and unchanged by it. **No model other than the writer rewrites the word at a hit; every hit goes back to the writer** (user-approved 2026-10-01, in the approval-walk glossary-names-for-ambiguous-project-words-2026-10-01; restated 2026-10-05). The writer is the one reader sure of the meaning it intended: bare "head" can be an nc-head-commit, a frozen-head or `HEAD`, and a rewriting model without the agent-session's context would guess. A guess shown to the user would also be text the writing agent never wrote and does not hold, so a sentence the user quotes back could not be found. A script cannot tell every "that" used as a pronoun from a joining "that", so the checker reports hits and the writer judges each one. Code, link targets, paths and text in double quotes are exempt, as today. The pronoun rows and the `or` row stay unchecked by any program, as the page says today, because the measurement finds them in most messages, and a refusal or a mark on nearly every message would teach agents to pass it without reading. Each place reports each hit with the row's Why it is flagged text and its Write instead text, as item 2 says. The checker runs at four places, each through a Claude Code hook except the last:
   - **A Markdown file**: the PostToolUse hook on the Write and Edit tools, built today. It skips files under `docs/walk/`, whose text the fourth place reads.
   - **A message to another agent**: a PreToolUse hook on the SendMessage tool refuses a send that holds a hit the writer has not yet been shown, so a listed word reaches the receiving agent only after its writer has seen the hit. The writer judges each hit: a word used in its ordinary English meaning, or in quoted text, stays. The hook's refusal text tells the agent this outright, in one instruction line: when the word at each hit is used in its ordinary English meaning or inside a quotation, send the same message again unchanged and it goes through (user-approved 2026-10-02; the line in the refusal text user-directed the same day). The hook records each hit it refused, as the flagged form with its sentence, in a state file of the agent-seat's own, and passes a send whose every hit it has refused before, so a writer who fixes one word and keeps another is not refused again for the one it kept. A send made by a program's headless sender, such as the one GHI 940's idle sweep starts to deliver a message whose text code wrote, is not refused, because no writer can judge its words and a refusal would fail the delivery.
   - **A message to the user**: a MessageDisplay hook marks the word on screen with its choices, such as "head (nc-head-commit, frozen-head or `HEAD`?)", without choosing one. The mark adds to the agent's words and removes none, and the transcript keeps the text without the mark, so a sentence the user quotes back, mark removed, is found in the transcript. A Stop hook tells the writing agent which listed words its message used, with each one's reason and suggestion. The message is the model's own output, and the user's rule above forbids any other model to rewrite it.
   - **A cold-read-target**: a section the cold-read-fast-read, `nn-systems/cold-read/cold-read-fast-read.py`, adds with no model, listing each hit in the cold-read-target under the rows whose Applies to holds "files": in its report, `cold-read-fast-read.md`, or, for a walk draft, in the suggestions file beside the draft, next to the section it already adds there for bare issue, pull request and task numbers. A cold-read-target with no hits gets the section with the line that there are none.

   When the checker fails, as when the page is missing or a row is malformed, each of the four places reports the error and does not block: the two tool hooks let the write or the send through and print the error to the agent, the MessageDisplay hook shows the message unmarked and the Stop hook prints the error to the agent, and the cold-read-fast-read writes the error in place of its section. The Markdown edit hook already exits this way on any error, because a hook that blocked on a bad page would block every agent's edits. The text each hook hands the agent follows CLAUDE.md's bullet on a tool-message-to-agent.

   **Checking further places is not pursued** (user-ruled 2026-10-02): no place of its own is added for tool-messages-to-agent outside the registered hooks, for reusable-prompts held in code, or for message texts written out in documents, by pattern or by a fast model, until a listed word in one of them is seen causing a mistake. The reason is a trial the agent-seat MD-skills ran on 2026-10-02: a pattern for dates, user-rulings and GHI numbers, over the module-level string constants of all 152 programs and tests on main, found 16 false positives in 26 hits outside the hooks, and each false positive sends an agent to judge text that was right. A Markdown file outside `docs/walk/` that holds such a prompt or message text is still checked by the first place when an agent writes the file with the Write or Edit tool.

   **The MessageDisplay hook, measured 2026-10-01 on Claude Code 2.1.287** (`nedlern@ned-box:/home/nedlern/nedsnodes-logs/seats/merge-lane-backlog/message-display-hook-live-test-2026-10-01.md`): the hook runs before the text is shown, once per batch of completed lines. The screen showed only the hook's output and never the original text, in an interactive test and in a headless test. The transcript, and what the model sees, keep the original text. The display waits for the hook: a hook that slept 3 seconds delayed the text by about 3 seconds, so the hook must be fast, and a test times it on a long message against the whole table. Claude Code's code also has a path that shows the original text first and rewrites the text when the hook returns; that path did not run in the test, and what selects that path is not measured. If that path runs, the mark appears a moment after the word instead of with the word.
