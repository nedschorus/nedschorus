# Problem words and phrases: one page listing each word to avoid with why it is flagged and what to write instead, its checker, and a daily search of the transcripts for new rows

## Why

The user reads agents' messages cold, across many agents' terminals, and loses time to words he cannot pin down. On 2026-09-30, in the merge-lane-backlog agent-seat's approval-walk explain-skill-draft-2026-09-29-2, he directed a list of words agents should avoid, each with the reason and the word to write instead:

> "I have been thinking of having a 'bad' word list, an anti-glossary of sorts, words that should be avoided (and why). It, land, ... seem like good candidates"

He also named a second class, with a different reason and a different message to the agent:

> "agents saying they will remmember somethig, or will do something soon, but unless the todo soons are in a tasks list, or the remember somethings have some reminder or enforcmentt, those are 'bad' too - though for very different reasons - requiring very different 'error messages'."

He asked that the checker be mechanical and that each entry carry its replacement ("Is the style guide checker mechnical - if so good - I assume each word has the prefered alternative?"), and that the list be measured from the transcripts before the list is written ("we might want to review our jsonls for additional 'bad words'"). He approved filing the work ("y", 2026-09-30).

The legacy system's list failed as text alone. The legacy list's page records that "under heavy context ... the model falls back to training priors", and the one class of wording the legacy system enforced at the moment of action, through its postal softener guard hook (under Supporting documents), is the class that held (the legacy GitHub issue nedlern/nedlern#1513, cited by this GHI's first version; that GitHub issue's title is not readable from the agent-seats' GitHub account). So this GHI builds the list and the checker that enforces the list together.

## What to build

1. **The rename.** The page becomes `docs/nedschorus-wiki/nedschorus-problem-words-and-phrases.md`, titled "Problem words and phrases", in one pull request that also changes every file on main that names the page's path, because the checker reads the page by that path and a citation of the old path would point at nothing. `git grep -n nedschorus-style-guide origin/main` lists them; on 2026-11-19 it listed `CLAUDE.md`, whose bullet `Read docs/nedschorus-wiki/nedschorus-style-guide.md.` points every agent to the page; the checker's `STYLE_GUIDE_PAGE_PATH` and its docstring; the hook's test; `docs/nedschorus-wiki/nedschorus-which-changes-need-the-users-approval.md`; `scripts/project-rename-repository-contents-rewrite-hack-test.py`, which uses the path in test data; and four GHI-MDs: `docs/issues/1043-the-style-guide-word-checker-misses-prose-and.md`, `docs/issues/1064-monthly-cold-read-full-run-of-every-important.md`, `docs/issues/1518-fixed-markers-list-every-literal-string-programs-and-prompts-match-with-its-readers-and-proposed-hashtag.md` and `docs/issues/1990-test-the-agent-instructions-files-a-vale-trial.md`. The scripts keep their names. The table keeps its heading "## Words to avoid", which the checker looks for. A citation of the old path that a later pull request brings back is reported by md-drift-lint, `scripts/md-drift-lint.py`, which reports every repository path a Markdown file cites that does not exist.

2. **A "Why it is flagged" column**, placed between Forms not flagged and Write instead. Each cell holds one sentence of reason, such as "carries five project meanings, so a reader cannot tell which one the writer meant" for `seat`, or "the project's word for this is merge" for `land`. The reason written for each of the 36 rows goes to the user in one approval-walk before the pull request that adds the column merges, because a change to a row of this table is never a cosmetic-change. The checker rejects a row whose Why it is flagged cell is empty, as it rejects other malformed rows today, and the paragraph above the table that gives one reason for all rows is cut to what the column does not say. The checker reports each hit with the row's Why it is flagged text and its Write instead text, as the user approved on 2026-10-05.

3. **Rows that turn a plain phrase into its glossary term.** A phrase in plain words that a glossary names with a term, such as "log store" for the log-store, gets a row whose Write instead cell is the glossary's term, as the six rows listed under What exists today do. The rows come from item 4's daily search, which proposes a row when it finds the plain phrase used for the term's meaning, and from any approval-walk that approves a new term, which also puts to the user a row for the plain phrase the term replaces. Each new row is the user's decision, like every other row.

4. **A daily search of the transcripts for new problem words** (user-approved 2026-10-05; daily, 2026-10-08), as one more job of GHI 1058, whose GHI-MD gains the job in an edit of its own. Its steps, divided by code-prompt-code:
   - **Code counts**, with no model, over the agent-session transcripts and cold-read-records written since the job's last run, or over the last 30 days on its first run: the words and phrases the user asked the meaning of, or said confused him; the words cold-read-cells quoted as unclear; the plain phrases of glossary terms, as item 3 says; and the candidates listed under item 5 that are not yet rows. Code drops every candidate an existing row already flags, and every candidate the job's state file records as proposed and waiting for the user, approved, declined by the user, or judged not a problem by the model at a count it has not since doubled. Code keeps a running count per candidate in the job's state file, so a word that recurs over days rises.
   - **A model judges** the candidates whose count passed a threshold that code applies: whether each is a problem word or phrase, and, for each that is, the row it proposes, with its forms, its Why it is flagged sentence and its Write instead text. When the model fails or returns nothing code can read, the job reports the failure as GHI 1058 says for its jobs' failures, and the candidates wait for the next run.
   - **Code checks** each proposed row with the checker's table parser, and drops a row the parser rejects or whose forms match none of the sentences in which the count found the candidate.
   - **The user decides** each proposed row in the approval-walk of GHI 1058's section "How a daily job is handed to the user and tracked (decided)". Code then writes each approved row into the page and opens its pull request, records each declined row in the job's state file so that the row is not proposed again, keeps an approved row marked approved until its pull request merges, and returns the row to the candidates when the pull request closes unmerged; when the pull request cannot be opened, code reports the failure as above.

   The 2026-09-30 measurement script under Supporting documents is where the counting code starts. The script's name is chosen when the job is built, by the naming page `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md`.

5. **Candidates already ruled or proposed**, beyond the rows on the page, which item 4's first run counts: the legacy list's overloaded words and deceptive phrases, where agents still use them; and the status-inflation class, "a 100% fail indicator" (user-ruled 2026-07-22, as this GHI's first version records), phrases that declare a fresh thing established, such as "standing doctrine", with siblings such as "is now doctrine" and "established practice". The list is one for the whole project, not one per system as the glossaries are (user, 2026-10-01).

6. **The checker's four places**, approved before 2026-10-05 and unchanged by it. **No model other than the writer rewrites a flagged word; every hit goes back to the writer** (user-approved 2026-10-01, in the approval-walk glossary-names-for-ambiguous-project-words-2026-10-01; restated 2026-10-05). Only the writer knows which meaning it intended: bare "head" is an nc-head-commit or `HEAD`, and a rewriting model without the agent-session's context would guess. A guess shown to the user would also be text the writing agent never wrote and does not hold, so a sentence the user quotes back could not be found. A script cannot tell every "that" used as a pronoun from a joining "that", so the checker flags candidates and the writer judges each one. Code and quoted text are exempt, as today. The checker runs at four places, each through a Claude Code hook except the last:
   - **A Markdown file**: the PostToolUse hook on the Write and Edit tools, built today.
   - **A message to another agent**: a PreToolUse hook on the SendMessage tool stops the first send of a message that holds a listed word, so the receiving agent never reads a listed word the writer has not judged. A send the agent repeats unchanged passes, because the writer judges each candidate: a word used in its ordinary English meaning, or in quoted text, stays. The hook's refusal text tells the agent this outright, in one instruction line: when each flagged word is used in its ordinary English meaning or inside a quotation, send the same message again unchanged and it goes through (user-approved 2026-10-02; the line in the refusal text user-directed the same day). The hook keeps a hash of each message it refused in a state file of the agent-seat's own, so it can tell an identical second send. A send made by a program's headless sender, such as the one GHI 940's idle sweep starts to deliver a message whose text code wrote, is not stopped, because no writer can judge its words and a refusal would fail the delivery.
   - **A message to the user**: a MessageDisplay hook marks the word on screen with its choices, such as "head (nc-head-commit or `HEAD`?)", without choosing one. The mark adds to the agent's words and removes none, and the transcript keeps the text without the mark, so a sentence the user quotes back, mark removed, is found in the transcript. A Stop hook tells the writing agent which listed words its message used. No hook can make the agent rewrite a message before the user reads the message, because the message is the model's own output.
   - **A document put to review**: a section of the cold-read-fast-read report, written by code with no model over the document the cold-read-fast-read reviews, placed beside the section the report already adds for bare GHI numbers in walk-documents (`nc-systems/cold-read/cold-read-fast-read.py`).

   When the page is missing or a row is malformed, each of the four places reports the parser's error and does not block: the two tool hooks let the write or the send through and print the error to the agent, the MessageDisplay hook shows the message unmarked and the Stop hook prints the error to the agent, and the cold-read-fast-read writes the error in place of its section. The Markdown edit hook already exits this way on any error, because a hook that blocked on a bad page would stop every agent's edits. The text each hook hands the agent follows CLAUDE.md's bullet on a tool-message-to-agent.

   **Checking further places is not pursued** (user-ruled 2026-10-02): program messages outside the registered hooks, prompts, and message texts written out in documents are not checked, by pattern or by a fast model, until a listed word in one of them is seen causing a mistake, because a trial the agent-seat MD-skills ran on 2026-10-02, a pattern for dates, rulings and GHI numbers over the module-level string constants of all 152 programs and tests on main, found 16 false positives in 26 hits outside the hooks, and each false positive sends an agent to change text that was right. A Markdown file that holds such a prompt or message text is still checked by the first place when an agent writes the file.

   **The MessageDisplay hook, measured 2026-10-01 on Claude Code 2.1.287** (`nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/merge-lane-backlog/message-display-hook-live-test-2026-10-01.md`): the hook runs before the text is shown, once per batch of completed lines. The screen showed only the hook's replacement and never the raw text, in an interactive test and in a headless test. The transcript, and what the model sees, keep the original text. The display waits for the hook: a hook that slept 3 seconds delayed the text by about 3 seconds, so the hook must be fast, and a test times it on a long message against the whole table. Claude Code's code also has a path that shows the raw text first and rewrites the text when the hook returns; that path did not run in the test, and what selects that path is not measured. If that path runs, the mark appears a moment after the word instead of with the word.

## The promise check, item 3 of this GHI's earlier versions, built under GHI 940 and not here

The promise check is not part of this GHI's build. GHI 940's GHI-MD cites this section as GHI 14's item 3, its number before this rewrite. GHI 940's § Promises and announced actions builds the promise check in GHI 940's idle sweep, a job that each minute looks for agent-seats that have stopped working and judges what to send them, and says when the promise check runs, who judges and what message the agent gets. That section judges "by GHI 14's rules", which this section keeps until GHI 940's GHI-MD holds them itself:

A promise phrase in an agent's message (the measured forms: "I'll bring you X", "I'll report when…", "Noted", "I'll hold", "from now on", "going forward", "from here on", "I'll carry …", "I'll pick up …", "I won't … until …" and "I'll … when/once <an event>") passes only when the agent backed the promise with the trigger that will make it happen (user-approved 2026-10-02); the measured form "say the word and I'll …" is conditional on the user and is never raised. The principle: a rule names the trigger that enforces it, because a rule with no trigger depends on an agent remembering it.
- **A promise to act later, or after an event**: passes when a task's `prerequisites` or `blockedBy` name the event, so GHI 940's due-task check, `scripts/agent-seat-due-task-raise-hook.py`, raises the task when the event happens. A task with neither does not pass, because nothing makes it fire.
- **A standing rule** ("from now on…", "going forward", "from here on", "Noted"): passes only when backed by the hook or test that enforces it, or by a task to build one together with a proposal to the user. A memory entry never passes: nothing forces an agent to read the entry when the rule applies.
- **A hold** ("I'll hold"): passes with a task whose `prerequisites` name what releases the hold.
- **An announced action**: a sentence saying the agent is doing, or is about to do, an action, such as "Next I'm starting the pull request". A sentence conditional on an event, such as "I'll push once the tests pass", is a promise to act after an event, above; a negative one, such as "I won't push yet", is not an announced action. It passes when a later tool call does the action or a background task the agent started is still running.

The user's decision of 2026-11-01 supersedes the promise check's Stop hook as approved on 2026-10-02, and items 8 and 10 of fleet-restart-at-login-every-open-question-combined-approval-walk-2026-10-22 (2026-10-23: the refusal line "Refused: you announced an action you have not done." and building the announced-action hook first); item 9 of that approval-walk, that a conditional or negative sentence is not raised as an announced action, stands. That decision concerns the promise check only; the Stop hook of item 6, which lists problem words, is not affected.
