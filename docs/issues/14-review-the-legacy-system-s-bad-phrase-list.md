# One problem-words system: a table of problem words and phrases, a checker that gives the reason for each hit, a promise check that reads the same table, and daily mining of transcripts for new rows

## Why

The user reads agents' messages cold, across many agents' terminals, and loses time to words he cannot pin down. On 2026-09-30, in the merge-lane-backlog agent-seat's approval-walk explain-skill-draft-2026-09-29-2, he directed a list of words agents should avoid, each with the reason and the word to write instead:

> "I have been thinking of having a 'bad' word list, an anti-glossary of sorts, words that should be avoided (and why). It, land, ... seem like good candidates"

He also named a second class, with a different reason and a different message to the agent:

> "agents saying they will remmember somethig, or will do something soon, but unless the todo soons are in a tasks list, or the remember somethings have some reminder or enforcmentt, those are 'bad' too - though for very different reasons - requiring very different 'error messages'."

He asked that the checker be mechanical and that each entry carry its replacement ("Is the style guide checker mechnical - if so good - I assume each word has the prefered alternative?"), and that the list be measured from the transcripts before the list is written ("we might want to review our jsonls for additional 'bad words'"). He approved filing the work ("y", 2026-09-30).

On 2026-10-05, at item 7 of the approval-walk cold-read-and-ask-the-user-rules-2026-10-05 (walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/cold-read-and-ask-the-user-rules-2026-10-05-minutes.md`), he approved ("y") the design's frame, which the items below carry out; rulings made before or after that date are dated where they appear. He said the page `docs/nedschorus-wiki/nedschorus-style-guide.md` is misnamed, since it lists problem words rather than guiding style; that the two classes above are one system with two kinds of message, a vague word getting a clearer word suggested and an unbacked promise getting the question whether a task backs the promise; that whatever reports a problem word flags it, says briefly why, and proposes, but never rewrites; that with code the list can be as long as needed; and that regular maintenance can look for more problem words: "maybe instead of a style guide this is really a guide to problem words and terms". What he approved: one problem-words system; the page renamed to `docs/nedschorus-wiki/nedschorus-problem-words-and-phrases.md`, together with its checker, which reads the page by path; one table with a "Why it is flagged" column and a "Check" column; promise phrases and glossary-term rows in the same table; each hit reported with its reason, together with the suggestion or the task question; regular maintenance rerunning the transcript count and proposing new rows; a cold-read-full-run, then an approval-walk, before building; and the dead-links companion, which makes md-drift-lint (`scripts/md-drift-lint.py`) apply git's record of a file rename, filed as a GHI of its own. GHI [A program that rewrites each Markdown citation of a renamed file to the file's new path, taking the new path from git's rename history](https://github.com/nedschorus/nedschorus/issues/3054) is that companion. On 2026-10-08 he set the maintenance rerun to daily: "If it's automated it can be daily."

The legacy system's list failed as text alone. The legacy list's page records that "under heavy context ... the model falls back to training priors", and the one class of wording the legacy system enforced at the moment of action, through its postal softener guard hook (under Supporting documents), is the class that held (the legacy GitHub issue nedlern/nedlern#1513, cited by this GHI's first version; that GitHub issue's title is not readable from the agent-seats' GitHub account). So this GHI builds the list and its enforcement together.

## What to build

1. **The page `docs/nedschorus-wiki/nedschorus-problem-words-and-phrases.md`**, renamed from `docs/nedschorus-wiki/nedschorus-style-guide.md` as item 5 says, holding one table, the project's one list of problem words and phrases. The list is one for the whole project, not one per system as the glossaries are (user, 2026-10-01). The table's heading becomes "## Problem words and phrases", and its columns become:

   | Column | What the cell holds |
   |---|---|
   | Word or phrase | the row's name, as the Word column holds it today |
   | Forms flagged | the forms that are found, each in a code span; a word row's forms are literal and also match with a capital first letter, as today; a promise row's forms are regular expressions, each in a code span that starts `re:`, compiled case-insensitively, with a `\|` written for each `|` the expression holds, because a bare `|` ends a Markdown table cell; the parser turns each `\|` back into `|` before compiling |
   | Forms not flagged | the forms that are skipped, as today |
   | Why it is flagged | one sentence of reason, such as "carries five project meanings, so a reader cannot tell which one the writer meant", or "a promise to act after an event, which nothing makes happen unless a task names the event" |
   | Check | for a word row, `suggest:` followed by the row's Write instead text of today, which the writer is shown; for a promise row, `ask:` followed by its kind of sentence, one of `promise_after_event`, `standing_rule` and `hold`, which picks the message GHI 940's idle sweep sends the writer when nothing backs the sentence; or `exempt: conditional_on_user`, for a phrase whose sentence is never raised because the user has the next move, such as "say the word and I'll …" |
   | Applies to | as today: files, messages to other agents, messages to the user; a document put to review, item 2's fourth place, counts as files; a promise row applies to messages to the user only |

   The table holds three kinds of row, each written in the same columns:
   - **Vague, overloaded or replaced words**, the rows the page has today, kept with their forms and their Write instead text, which moves into the Check column. Candidates already ruled or proposed, beyond the rows on the page: the legacy list's overloaded words and deceptive phrases, where the measurement shows agents still use them; and the status-inflation class, "a 100% fail indicator" (user-ruled 2026-07-22, as this GHI's first version records), phrases that declare a fresh thing established, such as "standing doctrine", with siblings such as "is now doctrine" and "established practice".
   - **Glossary-term rows**, as item 6 says.
   - **Promise phrases**, as item 3 says.

   A row is a promise row when its Check starts `ask:` or `exempt:`, and a word row when its Check starts `suggest:`. The parser that reads the table rejects, as malformed: a missing page, naming its path; a table whose header is not the six columns above; a row with a different number of cells; an empty Word or phrase or Forms flagged; a Check that starts with none of `suggest:`, `ask:` and `exempt:`; an `ask:` kind outside the three above; a word row with a `re:` form, or a promise row with a literal form; a `re:` form that does not compile; a word row whose Word or phrase is not among its forms, as today; an empty Why it is flagged; a promise row whose Applies to is not messages to the user only; and a promise row out of the kind order item 3 gives. Each error names the row.

   Each new row is the user's decision: item 7's mining proposes rows to him daily, and anyone else who proposes a row puts it to him in an approval-walk. The rows on the page today stay; the reason written for each of them goes to the user in one approval-walk before the pull request that adds the Why it is flagged column merges, because a change to a row of this table is never a cosmetic-change.

2. **The word checker**, today `scripts/style-guide-word-checker-nbd.py`: a script holding no list of its own, with no model in the loop, that reports each hit with where the hit is, the line or the words around it as today, the row's Why it is flagged text, and the row's Check text. The suggestion is a word ("merge" for "land"), the names to choose from (nc-head-commit or `HEAD` for "head"), or, where no single word fits, an instruction ("write the noun" for "it"). A script cannot tell every "that" used as a pronoun from a joining "that", so the checker flags candidates and the writer judges each one. Code and quoted text are exempt, as today. The checker reads only word rows, because item 3's ruling puts the promise check in the idle sweep alone.

   **No model other than the writer rewrites a flagged word; every hit goes back to the writer** (user-approved 2026-10-01, in the approval-walk glossary-names-for-ambiguous-project-words-2026-10-01; restated 2026-10-05). Only the writer knows which meaning it intended: bare "head" is an nc-head-commit or `HEAD`, and a rewriting model without the agent-session's context would guess. A guess shown to the user would also be text the writing agent never wrote and does not hold, so a sentence the user quotes back could not be found. The checker runs at four places, each through a Claude Code hook except the last:
   - **A Markdown file**: the PostToolUse hook on the Write and Edit tools, built today, checks the text just written and hands the agent each hit with its reason and suggestion.
   - **A message to another agent**: a PreToolUse hook on the SendMessage tool stops the first send of a message that holds a listed word, so the receiving agent never reads a listed word the writer has not judged. A send the agent repeats unchanged passes, because the writer judges each candidate: a word used in its ordinary English meaning, or in quoted text, stays. The hook's refusal text tells the agent this outright, in one instruction line: when each flagged word is used in its ordinary English meaning or inside a quotation, send the same message again unchanged and it goes through (user-approved 2026-10-02; the line in the refusal text user-directed the same day). The hook keeps a hash of each message it refused in a state file of the agent-seat's own, so it can tell an identical second send. A send made by a program's headless sender, such as the one GHI 940's idle sweep starts to deliver a message whose text code wrote, is not stopped, because no writer can judge its words and a refusal would fail the delivery.
   - **A message to the user**: a MessageDisplay hook marks the word on screen with its choices, such as "head (nc-head-commit or `HEAD`?)", without choosing one. The mark adds to the agent's words and removes none, and the transcript keeps the text without the mark, so a sentence the user quotes back, mark removed, is found in the transcript. A Stop hook tells the writing agent which listed words its message used. No hook can make the agent rewrite a message before the user reads the message, because the message is the model's own output.
   - **A document put to review**: a section of the cold-read-fast-read report, written by code with no model over the document the cold-read-fast-read reviews, placed beside the section the report already adds for bare GHI numbers in walk-documents (`nc-systems/cold-read/cold-read-fast-read.py`).

   When the page is missing or a row is malformed, each of the four places reports the parser's error and does not block: the two tool hooks let the write or the send through and print the error to the agent, the MessageDisplay hook shows the message unmarked and the Stop hook prints the error to the agent, and the cold-read-fast-read writes the error in place of its section. The Markdown edit hook already exits this way on any error, because a hook that blocked on a bad page would stop every agent's edits. The text each hook hands the agent follows CLAUDE.md's bullet on the text a program hands an agent.

   **Checking further places is not pursued** (user-ruled 2026-10-02): program messages outside the registered hooks, prompts, and message texts written out in documents are not checked, by pattern or by a fast model, until a listed word in one of them is seen causing a mistake, because a trial the agent-seat MD-skills ran on 2026-10-02, a pattern for dates, rulings and GHI numbers over the module-level string constants of all 152 programs and tests on main, found 16 false positives in 26 hits outside the hooks, and each false positive sends an agent to change text that was right. A Markdown file that holds such a prompt or message text is still checked by the first place when an agent writes the file. A test that fails on citations in the registered hooks' messages is built under GHI [Every refusal and warning a program hands an agent says why and what to do instead](https://github.com/nedschorus/nedschorus/issues/956): `scripts/registered-hook-messages-carry-no-citations-test.py`.

   **The MessageDisplay hook, measured 2026-10-01 on Claude Code 2.1.287** (`nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/merge-lane-backlog/message-display-hook-live-test-2026-10-01.md`): the hook runs before the text is shown, once per batch of completed lines. The screen showed only the hook's replacement and never the raw text, in an interactive test and in a headless test. The transcript, and what the model sees, keep the original text. The display waits for the hook: a hook that slept 3 seconds delayed the text by about 3 seconds, so the hook must be fast, and a test times it on a long message against the whole table. Claude Code's code also has a path that shows the raw text first and rewrites the text when the hook returns; that path did not run in the test, and what selects that path is not measured. If that path runs, the mark appears a moment after the word instead of with the word.

3. **The promise check, reading its phrases from the table.** The promise check is built as part of the idle sweep, a job that each minute looks for agent-seats that have stopped working and judges what to send them, of GHI [Tasks raise themselves when their due time passes or their prerequisite is met](https://github.com/nedschorus/nedschorus/issues/940). GHI 940's § Promises and announced actions says when the promise check runs, who judges, what backs each kind of sentence in detail, and what message the agent gets; this item keeps which sentences the promise check looks for, the rule for what backs each kind, and where the phrases are kept. A promise phrase in an agent's message (the measured forms: "I'll bring you X", "I'll report when…", "Noted", "I'll hold", "from now on", "going forward", "from here on", "I'll carry …", "I'll pick up …", "I won't … until …" and "I'll … when/once <an event>") passes only when the agent backed the promise with the trigger that will make it happen (user-approved 2026-10-02); the measured form "say the word and I'll …" is conditional on the user and is never raised. The principle: a rule names the trigger that enforces it, because a rule with no trigger depends on an agent remembering it.
   - **A promise to act later, or after an event**: passes when a task's `prerequisites` or `blockedBy` name the event, so GHI 940's due-task check, `scripts/agent-seat-due-task-raise-hook.py`, raises the task when the event happens. A task with neither does not pass, because nothing makes it fire.
   - **A standing rule** ("from now on…", "going forward", "from here on", "Noted"): passes only when backed by the hook or test that enforces it, or by a task to build one together with a proposal to the user. A memory entry never passes: nothing forces an agent to read the entry when the rule applies.
   - **A hold** ("I'll hold"): passes with a task whose `prerequisites` name what releases the hold.
   - **An announced action**: a sentence saying the agent is doing, or is about to do, an action, such as "Next I'm starting the pull request" or "I'm starting the PR 1633 work now", found by the announced-action patterns of `scripts/agent-seat-idle-sweep-verdicts-print.py`, which began as the phrase set at the top of `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/announced-action-not-executed-measurement-2026-10-19/measure_announced_actions.py`, or by the judge of GHI 940's idle sweep when the patterns miss the sentence. A sentence conditional on an event, such as "I'll push once the tests pass", is a promise to act after an event, above; a negative one, such as "I won't push yet", is not an announced action. What backs an announced action is as GHI 940's § Promises and announced actions says: a tool call that does the action, or a background task the agent started that is still running.

   The promise check runs on an agent-seat that GHI 940's idle sweep finds idle, over every message that ended one of its turns since the sweep last checked it, and raises each unbacked sentence once, with a message telling the agent to back the sentence or tell the user it takes the sentence back.

   **The table is the one list of promise phrases** (user-approved 2026-10-05). The phrases of `PROMISE_PHRASES` become rows of the table, one row for each measured form listed above, each with its `re:` forms and its Check, in the order that keeps today's first-match rule: `exempt: conditional_on_user` rows first, then `hold`, `standing_rule` and `promise_after_event` rows. The idle sweep reads the promise rows from the page each time the job runs, instead of holding its own copy, and tries them in table order. The idle sweep's existing tests pass unchanged against the table, which shows the rows match what `PROMISE_PHRASES` matched. A change to the promise phrases is then a change to a row, which the user approves like any other row and which item 7's daily mining can propose. The announced-action patterns and the sentence-classifying patterns stay in the idle sweep's code, and a sentence below the table names them and says why an announced action is flagged: they are not phrases a sentence holds but rules that combine lists of about a hundred verbs and their "-ing" forms with subjects such as "I'll" and "let me", or that decide a matched sentence's kind, as `RX_CONDITIONAL_ON_USER` makes any sentence the user has the next move in `conditional_on_user` whatever else it matches.

   Three constraints on how the idle sweep reads the table:
   - The idle sweep is not nice-but-dirty, and code that needs nice-but-dirty code is nice-but-dirty too, so the idle sweep does not import the word checker, whose file name ends in -nbd. The table's parser moves into a module without the -nbd suffix, with its own tests, which the checker and the idle sweep both import.
   - When the parser raises an error, the idle sweep skips the promise check for that run, leaves unchanged the time it last checked each agent-seat, so the next run that reads the table checks the messages this run skipped, writes the error where the job reports its failures, as GHI 940 says for the job's other failures, and runs its other rules, so a bad edit to the page never stops the wake of an idle agent-seat.
   - The build changes, in the same pull request as the move of the phrases, the comment above `PROMISE_PHRASES` in `scripts/agent-seat-idle-sweep-verdicts-print.py` and the sentence of GHI 940's § Promises and announced actions that says the job's module holds the one copy of each list, so that both name the table.

   Where the promise check runs is user-ruled 2026-11-01 (item 1.1 of reboot-test's approval-walk reboot-test-remote-control-never-connected-reconnect-2026-11-01, answered "A", the option that runs the check only in the idle sweep; walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/reboot-test-remote-control-never-connected-reconnect-2026-11-01-minutes.md`): only in GHI 940's idle sweep, with no Stop hook. This supersedes the promise check's Stop hook as approved on 2026-10-02, and items 8 and 10 of fleet-restart-at-login-every-open-question-combined-approval-walk-2026-10-22 (2026-10-23: the refusal line "Refused: you announced an action you have not done." and building the announced-action hook first); item 9 of that approval-walk, that a conditional or negative sentence is not raised as an announced action, stands. The ruling concerns the promise check only; item 2's Stop hook, which lists problem words, is not affected. The ruling of 2026-11-01 decided where the promise check runs, not where the promise phrases are kept; the sentence an edit of this GHI-MD added on 2026-11-01, that the job's module holds the one copy of each phrase list, had no user-ruling behind it and is replaced by this item.

6. **Glossary-term rows as a class.** A bare word that the project uses for several things, each of which a glossary names, gets a row whose Check suggests the glossary's name for each meaning, such as the `seat` row today, which suggests agent-seat, agent-session and cold-read-cell. Such a row does not forbid the word: written bare, the word keeps only its ordinary English meaning, and the row reminds the writer which name each project meaning takes. The rows the user approved for six such words on 2026-10-01, in the approval-walk glossary-names-for-ambiguous-project-words-2026-10-01, are on the page today: home, draft, walk, seat, head and drain. A word gets such a row in two ways: item 7's daily mining proposes it when it finds the bare word used for a glossary term's meaning; and an approval-walk that approves a new glossary term whose bare word already carries another project meaning also puts to the user the bare word's row, or the new term's place in the existing row.

7. **Daily mining of transcripts for new rows** (user-approved 2026-10-05; daily, 2026-10-08), as a job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058), run by `scripts/problem-words-and-phrases-daily-transcript-mining-new-row-proposals-nbd.py`. Its steps, divided by code-prompt-code:
   - **Code counts**, with no model, over the agent-session transcripts and cold-read-records written since the job's last run, or over the last 30 days on its first run: the words and phrases the user asked the meaning of, or said confused him; the words cold-read-cells quoted as unclear; the sentences that hold a future or commitment marker, such as "I'll", "once" or "until", and match no promise row; the bare words of glossary terms, as item 6 says; and the candidate phrases of item 1 that are not yet rows, such as "is now doctrine", which the job's state file holds from its first run. Code drops every candidate an existing row already flags, and every candidate the job's state file records as proposed and waiting for the user, approved, declined by the user, or judged not a problem by the model at a count it has not since doubled. Code keeps a running count per candidate in the job's state file, so a word that recurs over days rises.
   - **A model judges** the candidates whose count passed a threshold that code applies: whether each is a problem word or phrase, and, for each that is, the row it proposes, with its forms, its Why it is flagged sentence and its Check. When the model fails or returns nothing code can read, the job reports the failure as GHI 1058 says for its jobs' failures, and the candidates wait for the next run.
   - **Code checks** each proposed row with the table's parser and drops a row the parser rejects or whose forms match none of the candidate's sentences the count found.
   - **The user decides** each proposed row in the approval-walk of GHI 1058's section "How a daily job is handed to the user and tracked (decided)". Code then writes each approved row into the page, a promise row at the end of its kind's rows, and opens its pull request, records each declined row in the job's state file so that the row is not proposed again, keeps an approved row marked approved until its pull request merges, returns the row to the candidates when the pull request closes unmerged, reporting the failure as above when the pull request cannot be opened.

   The 2026-09-30 and 2026-10-02 measurement scripts under Supporting documents are where the counting code starts. GHI 1058's GHI-MD gains this job in an edit of its own.

## Supporting documents

- The measurement: `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/merge-lane-backlog/style-guide-word-count-2026-09-30.md`, with its script `style-guide-word-count-2026-09-30.py` beside it, written by a background agent started 2026-09-30: counts of each candidate word and promise phrase over 30 days of agent messages to the user, whether a task followed each promise, and the words the user himself asked about. Its headline, over 2026-08-31 to 2026-09-30 (266 agent-sessions, 21,991 agent messages the user sees, 3,949 of his typed messages):
  - Sentence-opening "It" appears in 15.4% of agent messages; "that" as a pronoun, by the script's heuristic, 163 times per 1,000 messages, "this" 84.
  - Overloaded words from the legacy list: "fix" 201 per 1,000 messages, "check" 171, "state" 76.
  - "land" and its forms 144 per 1,000 against 342 for "merge"; "or" 351, about a fifth of which is the approval-walk prompt "Y, N or D"; "draft" 75.
  - Bare project nouns the glossary defines only in hyphenated form: "walk" in 20.4% of messages, "seat" 18.0%, "head" 9.1%, "sweep" 8.3%.
  - 592 first-person promises; 47.0% were backed by a task, reminder or background job in the same response.
