# A small service on ned-box keeps one record of every agent-seat on both machines

This is a design. It proposes a small HTTP service on ned-box, in front of one SQLite database, that keeps one record of every agent-seat on both machines: which agent-seats exist, when each handoff-supervisor began and ended, how each agent-session ended where that was observed, which session-handoffs were written and consumed, and which restarts were attempted. Today four programs each answer part of that question from their own subset of about ten files, by their own rules. Nothing is installed or built yet. The user ruled every open point of this design in the approval-walk `agent-seat-database-on-ned-box-design-2026-10-02-3`, on 2026-10-03, and his rulings are written into the sections below. The next action is build-slice 1.

## The problem

An agent-seat's state is spread over about ten records, written by several programs, some writing more than one. Every line number below is on main at [2ba7cc17](https://github.com/nedschorus/nedschorus/tree/2ba7cc17765e6f03033311d1efd09c94fb63b5d1).

Four programs each answer part of "which agent-seats exist, and in what state" from these records, by their own rules:

- **The login restart** estimates when the machine stopped: from its own run log when an earlier run in the same boot recorded the stop ([`read_earlier_run_for_this_boot`, line 174](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L174)), and otherwise from the newest heartbeat written before the boot, reading a state file's modification time when its heartbeat is unreadable. It picks the agent-seats whose heartbeats fall within two heartbeat intervals, 20 seconds, of that stop ([line 114](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L114)), and only offers, rather than restarts, those whose files were written since the boot ([`select_seats_live_at_the_stop`, line 255](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L255)).
- **Recovery** combines the agent-seat's worktree, the agent-seat's own tmux socket and the default one older launches used, the lock's process identity and `lsof` ([`assess_seat`, line 667](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/recover-crashed-seats.py#L667)).
- **The handoff-supervisor** answers for its own agent-seat only: with no session-handoff and no exit record, it searches transcripts by date for an agent-session to resume, skipping small ones that this machinery started and that never did work.
- **The task viewer** names agent-seats from their task lists' directory names, removing the prefix `nedschorus-` and the suffix `-tasks` ([`seat_of`, line 211](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/seat-task-list-read.py#L211)); it lists task lists, not agent-seats' states.

Rules of this kind have failed. GHI [recover-crashed-seats.py: the six changes ruled 2026-09-02](https://github.com/nedschorus/nedschorus/issues/242) records that the heartbeat rule then in use would have taken a dead handoff-supervisor, whose heartbeat was 31 seconds old, for alive ([its GHI-MD, line 13](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/docs/issues/242-recover-crashed-seats-py-the-six-changes-ruled.md#L13)); that rule was replaced by the process check. The same GHI-MD records leftover shells taken for running agent-seats. GHI [The handoff-supervisor resumes a session that died without a handoff, instead of stopping the seat](https://github.com/nedschorus/nedschorus/issues/613) records an agent-seat that stayed dark until the user noticed. No single place answers "show me every agent-seat on both machines, and why each one that is down is down, where that is known".

## The design

One service, `agent-seat-database-service`, runs on ned-box and owns one SQLite database file, `~/.local/state/nedschorus/agent-seat-database.sqlite3` (a proposed path), with file permissions that let only `nedlern` read or write it. Every program that starts, supervises, hands off, restarts or recovers an agent-seat, on either machine, sends each **event** to the service. Once build-slice 4 lands, the programs that answer "which agent-seats exist" ask the service first, and read the files only when the service gives no valid answer. Callers never see the database's tables; only the service program, its tests and the backup job open the database file.

### The service

- **Standard library only.** The service is one Python program using `http.server` with `ThreadingHTTPServer`, and `sqlite3` with write-ahead logging, a bounded busy timeout and short transactions. ned-box's Python is 3.14, with SQLite 3.46.1. Nothing is installed with `pip`.
- **A narrow JSON API of named operations**, never SQL. Each request names an operation: record agent-seat created; record agent-seat seen, which the one-time fill of build-slice 3 sends; record agent-seat paused, resumed or retired (the glossary's retire-seat, and pausing, which the glossary keeps distinct from retiring); record machine booted, with the estimated stop of the boot before; record handoff-supervisor began; record handoff-supervisor ended; record agent-session ended, with its exit code; record session-handoff written; record session-handoff consumed; record restart attempted and its result; list agent-seats; get one agent-seat. A caller never sends SQL, so the schema can change inside the service without touching a caller.
- **Callers use `urllib`**, from Python's standard library, which works in every interpreter that runs these programs. The launchers are shell scripts, so they call a small Python helper rather than the service directly. The interpreters are Homebrew's Python on the Mac, whose LaunchAgent runs `/opt/homebrew/bin/python3` ([`install-restart-live-seats-at-login-launch-agent.py` line 52](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/install-restart-live-seats-at-login-launch-agent.py#L52)), `/usr/bin/python3` on ned-box ([`install-restart-live-seats-at-login-systemd-unit.py` line 63](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/install-restart-live-seats-at-login-systemd-unit.py#L63)), and Apple's Python 3.9, which some tests run under.

### Conditions the design keeps

1. **An agent-seat keeps working when ned-box cannot be reached.** The reason: a Mac agent-seat must not stop because ned-box is rebooting.
   - Every call to the service waits at most 2 seconds; with no answer, the event is queued. A handoff-supervisor sends from a background thread, so it never waits.
   - The 10-second heartbeat does not go to the service. It stays in the local state file for good, because the login restart's file rule needs it (see "What stays a file"). Only events go to the service.
   - Each machine keeps its outgoing events in one local SQLite file, `~/.local/state/nedschorus/agent-seat-events.sqlite`. Every event is first written there as a row; the row number is the machine's sequence number for that event, and a row whose `sent` column is empty is the queue. SQLite serializes the writers, so the project keeps no lock of its own: several programs on one machine can write and send at once without duplicate or missing numbers.
   - The service keeps every event in one table keyed by event ID, and ignores an event ID it already holds, so an event sent twice is stored once. The service computes an agent-seat's state from all of a machine's events in sequence-number order, not by clock time, so an event that arrives late still takes its proper place and a clock correction cannot reorder events.
   - A 2xx answer fills the event's `sent` column. A 400 or 422 answer marks the row rejected and prints why. Any other answer, or none, leaves the row in the queue.
   - A sent row stays in the local file until a backup holds it: every answer gives, for each machine, the highest sequence number in the service's newest successful backup, and a machine deletes sent rows only up to that number, so no clock is compared. So a restore loses nothing, however long ago the last backup ran.
   - A second table in the same file holds one row per agent-seat on that machine: its name, its ID, and whether it is retired. The launcher writes a new agent-seat's row; build-slice 3's fill command makes a UUID for, and writes the row of, each agent-seat that already exists; a program finds an agent-seat's ID by name among the agent-seats not retired; retiring marks the row and keeps it.
   - A scheduled job on each machine sends the queue every 10 minutes, so an idle agent-seat's events still arrive.
2. **Access stays on the LAN.** The service listens on port 8765 on ned-box's two LAN addresses, the wired 10.0.1.106 and the Wi-Fi 10.0.1.39, and on localhost, and nowhere else. ned-box's `ufw` firewall is active and admits the port from the LAN only; build-slice 2's install steps add the rule `sudo ufw allow from 10.0.1.0/24 to any port 8765 proto tcp comment 'agent-seat database service from LAN'`, matching the existing rules for ssh and file sharing. Callers name the service's host `ned-box.local`, which the LAN resolves and which follows an address change; on the Mac `ned-box` is only an ssh alias, which a Python program cannot resolve. Each machine has its own token in `~/.config/nedschorus/agent-seat-database-service.token` with mode 600, sent in every request's `Authorization: Bearer` header; the service reads the tokens it accepts from `~/.config/nedschorus/agent-seat-database-service-accepted-tokens` on ned-box, mode 600, and refuses a request without a known token with status 401. The reason: the record is the operating history of every agent-seat, and the LAN is the only network both machines share. Requests travel as plain HTTP; the design treats the LAN as trusted, since the project's failures come from accidents between cooperative agents, not from attackers.
3. **It starts at boot without `sudo`.** The service runs as a systemd user service of `nedlern`; lingering is already on for that user (`loginctl show-user nedlern -p Linger` printed `Linger=yes` on 2026-10-02), so the service starts at boot with nobody logged in. The unit starts after the network is online, so its addresses exist when it binds, and restarts 10 seconds after any failure.
4. **A nightly backup.** A scheduled job in the repository's table, `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, copies the database each night to `~/backups/agent-seat-database/` on ned-box, keeping 14 nightly copies, through SQLite's online backup (Python's `sqlite3.Connection.backup`), never a plain file copy, which can catch the file mid-write. The backups are not byproducts of the work, so they stay out of the log-store. A second scheduled job, on the Mac, copies the newest backup to the Mac each night over ssh, since only the Mac can reach the other machine, so a backup survives the loss of ned-box. A restore stops the service, puts a copy back, and has every machine send again every event it kept since that copy was taken (condition 1); the event IDs make the repeats harmless.
5. **The process check stays the proof of what is running.** The process check is the one recovery uses today: whether the process ID in the agent-seat's lock is that agent-seat's handoff-supervisor, by `ps`. The database records what happened; only the process check shows what runs now. A record that a handoff-supervisor began in the machine's current boot, with none that it ended, is a question for the process check; one from an earlier boot is certainly not running. ned-box identifies a boot by `/proc/sys/kernel/random/boot_id`. The Mac has no such file, so it identifies a boot by its boot time from `sysctl kern.boottime`, matched within 5 seconds, as the login restart already does (`BOOT_MATCH_TOLERANCE_SECONDS` in `scripts/restart-live-seats-at-login.py`), because a clock correction can shift that time; the service stores the first boot time it hears from the Mac as that boot's ID and maps a later time within 5 seconds to it.

### Alternatives considered

- **PostgreSQL on ned-box.** Mature, and built for writers on several machines; the user weighed it first. Set aside, by his ruling, because the write volume is a few events per agent-seat per hour, and because it is a server to install, back up and upgrade, with a Python driver outside the standard library for the service, or `psql`. The service's API means PostgreSQL can replace SQLite later without touching any caller.
- **One SQLite file on each machine**, each machine reading the other's with a query program over ssh. It needs no service. It was set aside because it splits the record of every agent-seat in two, so every reader on either machine would join two databases, one of them over ssh. A live SQLite database is never opened over a network share, such as the Mac's mount of ned-box's home, because its file locking is unreliable there.

### Schema

The table names live only inside the service; `agent_seat` and `agent_session` are also substrings of identifiers already on main, such as `agent_seat_working_directory`. Build-slice 2 settles the columns.

| Table, key | Columns |
|---|---|
| `event`, key `event_id` | machine, the sending machine's sequence number, operation, the event's own time, received at, body |
| `agent_seat`, key `seat_id`: a random UUID the launcher makes and keeps in the machine's local events file (condition 1), so a queued event can name an agent-seat the service has not seen yet | machine, seat name, seat directory, task-list name, created at, paused at, retired at, desired state and its reason; the seat name is unique per machine only among agent-seats not retired |
| `supervisor_run`, key `run_id`: one handoff-supervisor process | seat ID, boot ID, process ID and its start time, generation, began at, ended at, the restart attempt that started it |
| `agent_session`, key `(machine, session_id)`: one Claude Code session that a handoff-supervisor ran | seat ID, run ID, transcript path, predecessor session, launched at, ended at, exit code; its handoff-supervisor writes the end time and exit code |
| `handoff_event`, key the `event_id` of the event that recorded it, never the restart counter, which can repeat after a state file is lost | seat ID, restart counter, writer session, written at, next-step text, `dont-restart` reason, consumed by run, consumed at |
| `machine_boot`, key `(machine, boot_id)` | booted at, previous boot, stop estimated at and how the estimate was made |
| `restart_attempt`, key `attempt_id` | machine, boot, seat ID, why it was picked, action, began at, ended at, result; the attempt ID is passed to the launcher, which hands it to the handoff-supervisor it starts |

`machine` is `mac` or `ned-box`, always the machine the agent-seat runs on. There is no "agent-seat started" event: "handoff-supervisor began" says the same.

### What stays a file

- The heartbeat in the local state file, and the login restart's run log with its present use, stay: the login restart's file rule, which build-slice 4 keeps as the fallback for when ned-box is down, needs both, because after a reboot the process check finds nothing and only the old heartbeats show which agent-seats were running.
- The session-handoff file stays the session-handoff: the handoff-supervisor reads it locally, so a session-handoff works with ned-box down. The service records that it was written and consumed.
- Transcripts and task lists belong to Claude Code and stay its files; the database holds pointers to them.
- The files of an approval-walk, cold-read-records, test logs and GHI-MDs stay files: people read them whole.
- Test-run history, the daily memory-review marks and the daily overview-refresh reminder marks are later candidates, outside this design.
- Agent-seats of other runtimes, such as Codex, are outside this design; none runs today.

## The build-slices

Each build-slice is one pull request that leaves main working, followed where named by install steps the user runs or approves on ned-box. Build-slice 1 comes first, by the user's ruling: it changes no behaviour and makes every later build-slice smaller. A separate pull request from the cold-read-research seat, which moves the handoff-supervisor's lock onto an operating-system lock while keeping the process ID in the lock file, lands before build-slice 1.

1. **A shared reader over today's files.** One module holds the four rules above as named functions, reading the files as they are, and the four programs call those functions instead of their own copies. No behaviour changes: each program keeps its own rule, now in one place. The tests pin each rule's existing cases, which today's test suites for those programs already list.
2. **The service.** The pull request holds the service program, its schema, the systemd user unit file, the caller module with its local event queue, and the nightly backup job, with tests. The install steps, run after the merge: create the two tokens and the accepted-tokens file, enable the unit, and add the `ufw` rule from condition 2. No program sends events yet.
3. **Events sent.** The launchers, the handoff-supervisor, the handoff writer, the login restart, recovery and `scripts/resupervise-seat.py` send their events, queueing them when the service cannot be reached. The files still decide; the service only listens. The build-slice also adds one command, run once on each machine, that reads the records listed under "The problem" through build-slice 1's reader and sends an "agent-seat seen" event for every agent-seat: its worktree, task list, handoff-supervisor process if one runs, and last session-handoff. Pausing waits on that change: the parking marker's commands, when built under GHI [recover-crashed-seats.py: the six changes ruled 2026-09-02](https://github.com/nedschorus/nedschorus/issues/242) change 3, send "paused" and "resumed" events, and the retire steps in `docs/nedschorus-wiki/nedschorus-agent-seat-model.md` gain one command that sends "retired"; those steps are first checked for drift against today's records.
4. **Readers switch.** The shared reader from build-slice 1 asks the service, and reads the files when the service gives no valid answer: only a successful answer with valid JSON counts. The program's report names which it used, and each answer carries, per machine, the time of the newest event the service received, which the report shows. The switch lands only when every running handoff-supervisor on both machines runs build-slice 3's code, which alone sends "handoff-supervisor began", and both machines' queues are empty. A handoff-supervisor started before build-slice 3 keeps its old code and never sends that event, so after build-slice 3 merges both machines are rebooted at a quiet moment the user picks; the same fill command, run again, then confirms that every agent-seat's handoff-supervisor sent "began", and any agent-seat that did not come back is restarted with recovery. The process check stays.
5. **The whole-fleet view.** One command lists every agent-seat on both machines from the service, how to reach each, and why each one that is down is down where that was recorded, with any open tasks. Run on the Mac, the view shows both machines in full. Run on ned-box, it shows the Mac's agent-seats from the service only, marked "not checked: ned-box has no route that can check the Mac's processes". ned-box's one key for the Mac, used by `scripts/open-mac-window-from-ned-box.py`, is admitted for one forced command that opens an iTerm window, and nothing else. A stop with no recorded cause shows as "stopped, cause not recorded". With ned-box down, the view on the Mac shows the Mac's own agent-seats from its files and says the service did not answer.
6. **Remove what nothing reads.** Any record no program reads any more is removed. The files the build-slice 4 fallback reads stay, the login restart's run log and the heartbeat among them.
7. **Pull request head test runs.** The records `scripts/pull-request-head-test-run.py` writes for each pull request head, today appended under `flock` to a log in ned-box's log-store, move into a table on ned-box beside the service, so readers ask one place and the program keeps no lock of its own. The user approved this from a survey of the project's locks; it comes after the agent-seat build-slices.

## Rulings

The six-reviewer cold read of this design, cold-read-record `agent-seat-database-on-ned-box-design-2026-10-02-3`, found gaps that the user ruled on in the approval-walk of the same name on 2026-10-03, together with the design's open questions; its minutes are `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/agent-seat-database-on-ned-box-design-2026-10-02-3-minutes.md`. Every ruling is written into the sections above: event delivery and the queue (condition 1); the schema; the one-time fill and when readers may trust the service (build-slices 3 and 4); the heartbeat and the run log staying (What stays a file); the whole-fleet view (build-slice 5); running the service, its addresses, tokens and backups (conditions 2, 3 and 4); the Mac's boot ID (condition 5); pausing and retirement (build-slice 3); build-slice 1 first; and port 8765 with its `ufw` rule (condition 2). Applying the rulings found four more gaps, which he also ruled: sent events kept until a backup holds them, the reboot of both machines before readers switch, the local SQLite events file in place of a queue file and its lock, and the agent-seat table in that file (condition 1 and build-slice 4); and he added build-slice 7.
