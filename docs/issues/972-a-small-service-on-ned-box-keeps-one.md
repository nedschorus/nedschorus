# A small HTTP service with SQLite on ned-box keeps one record of every agent-seat on both machines

This is a design. It proposes a small HTTP service on ned-box, in front of the nc-shared-database, that keeps one record of every Claude Code agent-seat on both machines: which agent-seats exist, when each handoff-supervisor began and ended and how each agent-session ended, where each was observed, which session-handoffs were written and consumed, and which restarts were attempted. Today four programs each answer part of that question from their own subset of about ten files, by their own rules. ned-box is a required part of the design: every program reads and writes the record by calling the service, and a program that needs the service waits or stops while ned-box is down (condition 1). The user's rulings on this design, the latest of them on 2026-11-03, are written into the sections below and listed under "User-rulings". Build-slice 1 is merged; build-slice 2 is merged as PR [GHI 972 build-slice 2: the agent-seat database service, local events file, sender, backups and post-merge restart](https://github.com/nedschorus/nedschorus/pull/2027), and build-slice 2.1 removes the parts of it that the 2026-11-03 ruling makes unneeded.

## The problem

An agent-seat's state is spread over about ten records, written by several programs, some writing more than one. Every line number below is on main at [2ba7cc17](https://github.com/nedschorus/nedschorus/tree/2ba7cc17765e6f03033311d1efd09c94fb63b5d1).

Four programs each answer part of "which agent-seats exist, and in what state" from these records, by their own rules:

- **The login restart** estimates when the machine stopped: from its own run log when an earlier run in the same boot recorded the stop ([`read_earlier_run_for_this_boot`, line 174](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L174)), and otherwise from the newest heartbeat written before the boot, reading a state file's modification time when its heartbeat is unreadable. It picks the agent-seats whose heartbeats fall within two heartbeat intervals, 20 seconds, of that stop ([line 114](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L114)), and skips those whose files were written since the boot, since a handoff-supervisor has run for them since; when any agent-seat's files were written since the boot, it only offers, rather than restarts, the rest, because the newest heartbeat from before the boot may not mark the stop ([`select_seats_live_at_the_stop`, line 255](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L255)).
- **Recovery** combines the agent-seat's worktree, the agent-seat's own tmux socket and the default one older launches used, the lock's process identity and `lsof` ([`assess_seat`, line 667](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/recover-crashed-seats.py#L667)).
- **The handoff-supervisor** answers for its own agent-seat only: with no session-handoff and no exit record, it searches transcripts by date for an agent-session to resume, skipping small agent-sessions that a handoff-supervisor started and that never did work.
- **The task viewer** names agent-seats from their task lists' directory names, removing the prefix `nedschorus-` and the suffix `-tasks` ([`seat_of`, line 211](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/seat-task-list-read.py#L211)); it lists task lists, not agent-seats' states.

Rules of this kind have failed, or would have. GHI [recover-crashed-seats.py: the six changes ruled 2026-09-02](https://github.com/nedschorus/nedschorus/issues/242) records that the heartbeat rule then in use would have taken a dead handoff-supervisor, whose heartbeat was 31 seconds old, for alive ([its GHI-MD, line 13](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/docs/issues/242-recover-crashed-seats-py-the-six-changes-ruled.md#L13)); that rule was replaced by the process check. The same GHI-MD records leftover-shells taken for running agent-seats. GHI [The handoff-supervisor resumes a session that died without a handoff, instead of stopping the seat](https://github.com/nedschorus/nedschorus/issues/613) records an agent-seat that stayed dark until the user noticed. No single place answers "show me every agent-seat on both machines, and why each one that is down is down, where that is known".

## The design

One service, `nc-systems/nc-shared-database/nc-shared-database-service.py`, runs on ned-box and alone opens the nc-shared-database's file, `~/.local/state/nedschorus/nc-shared-database.sqlite3`, with file permissions that let only `nedlern` read or write it. Every program that starts or supervises an agent-seat, writes or consumes its session-handoff, or restarts or recovers it, on either machine, sends each **event** to the service by one HTTP call, and waits for the answer (condition 1). Once build-slice 4 merges, the programs that answer "which agent-seats exist" ask the service. Callers never see the database's tables; only the service program, its tests, the backup job and the restore command (condition 4) open the database file. The service's database is the project's one database. A later store that keeps any record no file or other store holds joins it, as tables of its own behind the service's operations, and keeps no SQLite file of its own; the standing user-rulings store of GHI 2118 joins it once the service runs. Only two kinds of SQLite file stay separate: a store whose whole contents a program can rebuild from files, such as a search index; and the files of a tool from outside the project, such as Codex.

### The service

- **Standard library only.** The service is one Python program using `http.server` with `ThreadingHTTPServer`, and `sqlite3` with write-ahead logging, a bounded busy timeout and short transactions. ned-box's Python is 3.14, with SQLite 3.46.1. Nothing is installed with `pip`.
- **A narrow JSON API of named operations**, never SQL. Each request names an operation: record agent-seat created; record agent-seat seen, which build-slice 3's fill command sends; record agent-seat paused or retired (the glossary's retire-seat, and pausing, which the glossary keeps distinct from retiring); record agent-seat parked, when the login restart sets an agent-seat aside, an operation separate from the user's pausing; record machine booted, with the estimated stop of the boot before; record handoff-supervisor began; record handoff-supervisor ended; record agent-session launched, with its session ID, transcript path and predecessor session, which the handoff-supervisor sends when it starts Claude Code; a launch that ends before any transcript exists is recorded as launched, then ended, with no transcript path; record agent-session ended, with its exit code; record session-handoff written; record session-handoff consumed; record restart attempted and its result; record heartbeat, which is not an event and is `POST /heartbeats`; list agent-seats; get one agent-seat. A caller never sends SQL, so the schema can change inside the service without touching a caller. Every 'record' operation is a `POST /events`; 'list agent-seats' is `GET /agent-seats`, with `?machine=` to list one machine's and `?name=` to find the agent-seat not retired that holds a name; 'get one agent-seat' is `GET /agent-seats/<seat ID>`. Requests and answers are JSON. The token travels in the `Authorization: Bearer` header (condition 2). The service answers 400 or 422 to an event it cannot parse or place, such as malformed JSON, no event ID, an unknown operation, keys or fields other than the operation's, an unknown machine or a seat ID it has no row for, and stores nothing.
- **Callers use `urllib`**, from Python's standard library, which works in every interpreter that runs these programs, through one caller module that build-slice 2.1 writes. The launchers are shell scripts, so they call a small Python helper rather than the service directly. The interpreters are Homebrew's Python on the Mac, whose LaunchAgent runs `/opt/homebrew/bin/python3` ([`install-restart-live-seats-at-login-launch-agent.py` line 52](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/install-restart-live-seats-at-login-launch-agent.py#L52)), `/usr/bin/python3` on ned-box ([`install-restart-live-seats-at-login-systemd-unit.py` line 63](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/install-restart-live-seats-at-login-systemd-unit.py#L63)), and Apple's Python 3.9, which some tests run under.

### Conditions the design keeps

1. **ned-box is required.** A one-shot program, such as a reader, a launcher, recovery or the fill command, reads or records an event by one call to the service on ned-box and, with no answer in 2 seconds, or a refused connection or any answer other than a success, 400, 422 or 401, prints that ned-box cannot be reached and exits 1. A handoff-supervisor waits for the service before each event it records, launching nothing meanwhile but still sending its heartbeat, calls again every 30 seconds, and logs once when it starts waiting and once when it stops. The reason: ned-box is already where the project's logs and most agent-seats live, and a record that every program writes straight to one place needs no queue, no resending and no second copy to reconcile.
   - The program that records an event makes its event ID, a random UUID, before the first call, and a handoff-supervisor that calls again sends the same ID. The service keeps every event in one table in which the event ID is unique, and answers an event ID it already holds with the answer it gave the first time, its sequence number and any seat ID included, so an event whose answer was lost is stored once. A handoff-supervisor makes its run ID, a random UUID, when it starts. `nc-systems/handoff/handoff-write-and-check-supervisor.py`, which writes the session-handoff file, puts the 'written' event's ID into that file, and the handoff-supervisor that consumes the file sends that ID in its 'consumed' event.
   - The service gives each event its sequence number as it stores it, from a column declared `INTEGER PRIMARY KEY AUTOINCREMENT`, and computes an agent-seat's state from its events in sequence-number order, not by clock time, so a clock correction cannot reorder events.
   - When the service answers 400, 422 or 401, the program prints the service's answer on a line opening FAILED; a one-shot program exits 1, and a handoff-supervisor logs the line, goes on without the event, and does not call again for it. For a 401, the line names the machine's token file and ned-box's accepted-tokens file, `~/.config/nedschorus/nc-shared-database-service-accepted-tokens` on ned-box, and says that the machine's token must be one line of the accepted-tokens file.
   - A program that acts and is killed before its call leaves no event; the files and the process check (condition 5) still show what happened.
   - Each handoff-supervisor sends its heartbeat to the service every 10 seconds, dropping a send that ned-box does not answer within 2 seconds; the service keeps the newest per agent-seat and shows an agent-seat as running while its newest heartbeat is under 20 seconds old, two heartbeat intervals, which the process check (condition 5) then confirms. A heartbeat is not an event: it has no event ID, and a dropped send is never sent again, so the agent-seat's heartbeat only ages until ned-box answers. After a reboot the login restart reopens the agent-seats whose last heartbeat came within 20 seconds of the newest heartbeat from that machine before its boot, skipping paused, parked and retired ones and those restarted since boot.
   - When the nc-shared-database service on ned-box does not answer, the login restart, `scripts/restart-live-seats-at-login.py`, waits, calling again every 30 seconds and allowing each call 2 seconds; it writes one line to its run log on its own machine when it starts waiting and one when it stops, and after 10 minutes of waiting it shows the user one notice on the Mac, as the agent-crash-watcher shows a failed-restart-notice; a notice it cannot show is written to its run log, and the wait goes on. Once the service answers, it reopens the agent-seats as it would have at once. It waits rather than exiting 1 because it runs once at boot or login, when nobody watches it, and without ned-box it has no list of agent-seats to reopen.
2. **Access stays on the LAN.** The service listens on port 8765 on every address; ned-box's `ufw` firewall admits the port from the LAN only, which is what keeps access on the LAN; build-slice 2's install steps add the rule `sudo ufw allow from 10.0.1.0/24 to any port 8765 proto tcp comment 'nc-shared-database service from LAN'`, matching the existing rules for ssh and file sharing. Callers name the service's host `ned-box.local`, which the LAN resolves and which follows an address change; on the Mac `ned-box` is only an ssh alias, which a Python program cannot resolve. Each machine has its own token in `~/.config/nedschorus/nc-shared-database-service.token` with mode 600, sent in every request's `Authorization: Bearer` header; the service reads the tokens it accepts from `~/.config/nedschorus/nc-shared-database-service-accepted-tokens` on ned-box, mode 600, and refuses a request without a known token with status 401. The reason: the record is the operating history of every agent-seat, and the LAN is the only network both machines share. Requests travel as plain HTTP; the design treats the LAN as trusted, since the project's failures come from accidents between cooperative agents, not from attackers.
3. **It starts at boot without `sudo`.** The service runs as a systemd user service of `nedlern`; lingering is already on for that user (`loginctl show-user nedlern -p Linger` printed `Linger=yes` on 2026-10-02), so the service starts at boot with nobody logged in. The unit restarts 10 seconds after any failure. At start, when its database file already exists, the service runs `PRAGMA quick_check` on it; when the check raises an error or returns any row but the single row `ok`, the service writes an alert that names the restore command and exits with a status the unit lists under `RestartPreventExitStatus=`, so the unit does not restart it, and the service stays stopped until the restore command starts it again.
4. **A nightly backup.** A scheduled job in the repository's table, `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, copies the database each night to `~/backups/nc-shared-database/` on ned-box, keeping 14 nightly copies, through SQLite's online backup (Python's `sqlite3.Connection.backup`), never a plain file copy, which can catch the file mid-write. The backup job checks each new copy with `PRAGMA integrity_check` and keeps the copy as a backup only when that integrity check passes. A copy that fails it is renamed to end in `.failed-integrity-check`, the older copies stay in place, and the job writes an alert naming the file, prints the failure and exits 1. An alert is one JSON file in `~/.local/state/nedschorus/user-alerts/pending/` on ned-box, which reaches the user as the next item of his approval-walk, as the alerts proposal, `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/fleet-restart-at-login/program-alerts-reach-user-as-walk-items-proposal-2026-10-26.md`, describes. The backups are not byproducts of the work, so they stay out of the log-store. A second scheduled job, on the Mac, copies the newest backup to the Mac each night over ssh, so a backup survives the loss of ned-box. A restore stops the service, puts a copy back and starts the service again; the events stored after that copy was made are lost to the record, and the fill command (build-slice 3), run again on each machine, records every agent-seat as it stands.
5. **The process check stays the test of what is running; when `ps` cannot run, the process check assumes the process is running and says so.** The process check is the one recovery uses today: whether the process ID in the agent-seat's lock is that agent-seat's handoff-supervisor, by `ps`. The database records what happened; only the process check shows what runs now. A record that a handoff-supervisor began in the machine's current boot, with none that it ended, is a question for the process check; one from an earlier boot is certainly not running. ned-box identifies a boot by `/proc/sys/kernel/random/boot_id`. The Mac identifies a boot by `sysctl kern.bootsessionuuid`, a random ID macOS makes at each boot, which a clock correction cannot change. Build-slice 3 first checks on the Mac that the value is present and changes at each boot.

### Alternatives considered

- **A local queue on each machine**, so that an agent-seat keeps working while ned-box cannot be reached: each program wrote its event to a local SQLite file, and a sender on each machine posted the file's rows to the service later. It was the design until 2026-11-03, and build-slice 2 built it. The user set it aside on 2026-11-03, because the queue alone needed a sender, a stuck-queue alert, a hold on unknown events, a resend after a restore and readers that fell back to files, while ned-box must be up for the project to work anyway.
- **The heartbeat kept in each local state file**, with the service asked only whether each agent-seat is paused, parked or retired. It was the design until 2026-11-04. The user set it aside, because the service then showed an agent-seat as running from 'began' without 'ended', so a handoff-supervisor killed without sending 'ended' still showed as running.
- **PostgreSQL on ned-box.** Mature, and built for writers on several machines; the user weighed it first. Set aside, by his user-ruling, because the write volume is a few events per agent-seat per hour, and because it is a server to install, back up and upgrade, with a Python driver outside the standard library for the service, or `psql`. The service's API means PostgreSQL can replace SQLite later without touching any caller.
- **One SQLite file on each machine**, each machine reading the other's with a query program over ssh. It needs no service. It was set aside because it splits the record of every agent-seat in two, so every reader on either machine would join two databases, one of them over ssh. A live SQLite database is never opened over a network share, such as the Mac's mount of ned-box's home, because its file locking is unreliable there.

### Schema

The table names live only inside the service; `agent_seat` and `agent_session` are also substrings of identifiers already on main, such as `agent_seat_working_directory`. Build-slice 2 settled the columns.

| Table, key | Columns |
|---|---|
| `event`, key `sequence`, the service's sequence number; `event_id` unique | machine, the machine the agent-seat runs on; operation, the event's own time, received at, body |
| `agent_seat`, key `seat_id`: a random UUID the service makes when it stores the agent-seat's 'created' or 'seen' event, and gives in its answer | machine, seat name, seat directory, task-list name, created at, paused at, parked at, retired at, last heartbeat at, kept by the service from the newest heartbeat only; a parked agent-seat stops being parked at its next 'handoff-supervisor began', 'paused' or 'retired' event, and a paused one stops being paused at its next 'handoff-supervisor began' or 'retired' event; the end of a pause clears `paused at`, and the end of a park clears `parked at`; the seat name is unique across both machines among agent-seats not retired, as the agent-seat model page requires; the service refuses 'record agent-seat created' for a name an agent-seat not retired already holds; a program finds an agent-seat's ID by its name among the agent-seats not retired, by asking the service |
| `supervisor_run`, key `run_id`: one handoff-supervisor process | seat ID, boot ID, process ID and its start time, handoff-supervisor generation, from its state file, began at, ended at, the restart attempt that started it |
| `agent_session`, key `(machine, session_id, run_id)`: one run of one Claude Code session under one handoff-supervisor run; a resumed session gets a row per run | seat ID, run ID, transcript path, predecessor session, launched at, ended at, exit code; its handoff-supervisor writes the end time and exit code |
| `handoff_event`, key the `event_id` of the event that recorded it, never the restart counter, which can repeat after a state file is lost | seat ID, restart counter, writer session, written at, next-step text, `dont-restart` reason, consumed by run, consumed at |
| `machine_boot`, key `(machine, boot_id)` | booted at, previous boot, stop estimated at and how the estimate was made |
| `restart_attempt`, key `attempt_id` | machine, boot, seat ID, why it was picked, action, began at, ended at, result; the attempt ID is passed to the launcher, which hands it to the handoff-supervisor it starts |

`machine` is `mac` or `ned-box`, always the machine the agent-seat runs on. There is no "agent-seat started" event: "handoff-supervisor began" says the same.

### What stays a file

- The login restart's run log stays, with its present use. The heartbeat leaves the local state file: it goes to the service (condition 1), which keeps the newest per agent-seat, and after a reboot those heartbeats show which agent-seats were running near the stop.
- The session-handoff file stays the session-handoff: the handoff-supervisor reads it whole, and people read it. The service records that it was written and consumed.
- Transcripts and task lists belong to Claude Code and stay its files; the database holds pointers to them.
- The files of an approval-walk, cold-read-records, test logs and GHI-MDs stay files: people read them whole.
- A file a Mac program writes that ned-box needs, such as the daily test run's record, stays where the program writes it. The every-minute mirror, `scripts/transcript-mirror-to-log-store.py`, which copies the Mac's transcripts to ned-box with rsync over ssh, also copies each Mac folder that holds such files, each listed in the mirror's table of sources with its place in the log-store. rsync copies only what ned-box lacks or holds out of date, so after an outage the mirror catches up by itself, and the daily test run no longer prints a command for someone to run by hand. No outbox and no shared copy function exist. Two facts the build meets: the mirror sends every source to one fixed directory, `agent-session-files-by-machine/`, so a source with its own place in the log-store is new; and its sources are paths under the home directory, while the daily test run writes its record under the temporary directory.
- Pull request test-run records stay one file per nc-head-commit; they take no lock.
- Test-run history, the daily memory-review marks and the daily overview-refresh reminder marks are later candidates, outside this design.
- Agent-seats run by an agent-binary other than `claude`, such as `codex`, are outside this design; none runs today.

## The build-slices

Each build-slice is one pull request that leaves main working, followed where named by install steps the user runs or approves on ned-box or the Mac. Build-slice 1 comes first, by the user-ruling: it changes no behaviour and makes every later build-slice smaller. A separate pull request from the cold-read-research seat, which moves the handoff-supervisor's lock onto an operating-system lock while keeping the process ID in the lock file, merges before build-slice 1.

1. **A shared reader over today's files.** One module, `nc-systems/handoff/agent-seat-state-records-reader.py`, holds the four rules above as named functions, reading the files as they are, and the other three programs call those functions instead of their own copies; the handoff-supervisor's own readers stay in `handoff-supervisor.py`, which the module loads and re-exports, because the handoff-supervisor does not load the module. No behaviour changes: each program keeps its own rule, now in one place. The tests pin each rule's existing cases, which today's nc-test-suites for those programs already list.
2. **The service.** Merged as PR [GHI 972 build-slice 2: the agent-seat database service, local events file, sender, backups and post-merge restart](https://github.com/nedschorus/nedschorus/pull/2027): the service program, its schema, the systemd user unit file, the caller module with its local events file, the sender command, the nightly backup job, the Mac's nightly job that copies the newest backup to the Mac, and the post-merge hook below, with tests. The install steps, run after the merge: create the two tokens and the accepted-tokens file, enable the unit, add the `ufw` rule from condition 2, and install the nightly backup job on ned-box and the nightly copy job on the Mac.
