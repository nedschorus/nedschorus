# A small HTTP service with SQLite on ned-box keeps one record of every agent-seat on both machines

This is a design. It proposes a small HTTP service on ned-box, in front of one SQLite database, that keeps one record of every Claude Code agent-seat on both machines: which agent-seats exist, when each handoff-supervisor began and ended and how each agent-session ended, where each was observed, which session-handoffs were written and consumed, and which restarts were attempted. Today four programs each answer part of that question from their own subset of about ten files, by their own rules. The user ruled every open point of this design in the approval-walk `agent-seat-database-on-ned-box-design-2026-10-02-3`, on 2026-10-03, and the defects a later cold read found in the approval-walk `ghi-972-seat-service-design-open-defects-2026-10-14`; his rulings are written into the sections below. Build-slice 1 is merged; the next action is build-slice 2.

## The problem

An agent-seat's state is spread over about ten records, written by several programs, some writing more than one. Every line number below is on main at [2ba7cc17](https://github.com/nedschorus/nedschorus/tree/2ba7cc17765e6f03033311d1efd09c94fb63b5d1).

Four programs each answer part of "which agent-seats exist, and in what state" from these records, by their own rules:

- **The login restart** estimates when the machine stopped: from its own run log when an earlier run in the same boot recorded the stop ([`read_earlier_run_for_this_boot`, line 174](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L174)), and otherwise from the newest heartbeat written before the boot, reading a state file's modification time when its heartbeat is unreadable. It picks the agent-seats whose heartbeats fall within two heartbeat intervals, 20 seconds, of that stop ([line 114](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L114)), and skips those whose files were written since the boot, since a handoff-supervisor has run for them since; when any agent-seat's files were written since the boot, it only offers, rather than restarts, the rest, because the newest heartbeat from before the boot may not mark the stop ([`select_seats_live_at_the_stop`, line 255](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/restart-live-seats-at-login.py#L255)).
- **Recovery** combines the agent-seat's worktree, the agent-seat's own tmux socket and the default one older launches used, the lock's process identity and `lsof` ([`assess_seat`, line 667](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/recover-crashed-seats.py#L667)).
- **The handoff-supervisor** answers for its own agent-seat only: with no session-handoff and no exit record, it searches transcripts by date for an agent-session to resume, skipping small agent-sessions that a handoff-supervisor started and that never did work.
- **The task viewer** names agent-seats from their task lists' directory names, removing the prefix `nedschorus-` and the suffix `-tasks` ([`seat_of`, line 211](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/seat-task-list-read.py#L211)); it lists task lists, not agent-seats' states.

Rules of this kind have failed. GHI [recover-crashed-seats.py: the six changes ruled 2026-09-02](https://github.com/nedschorus/nedschorus/issues/242) records that the heartbeat rule then in use would have taken a dead handoff-supervisor, whose heartbeat was 31 seconds old, for alive ([its GHI-MD, line 13](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/docs/issues/242-recover-crashed-seats-py-the-six-changes-ruled.md#L13)); that rule was replaced by the process check. The same GHI-MD records leftover shells taken for running agent-seats. GHI [The handoff-supervisor resumes a session that died without a handoff, instead of stopping the seat](https://github.com/nedschorus/nedschorus/issues/613) records an agent-seat that stayed dark until the user noticed. No single place answers "show me every agent-seat on both machines, and why each one that is down is down, where that is known".

## The design

One service, `agent-seat-database-service`, runs on ned-box and owns one SQLite database file, `~/.local/state/nedschorus/agent-seat-database.sqlite3` (a proposed path), with file permissions that let only `nedlern` read or write it. Every program that starts, supervises, hands off, restarts or recovers an agent-seat, on either machine, sends each **event** to the service. Once build-slice 4 lands, the programs that answer "which agent-seats exist" ask the service first, and read the files only when the service gives no valid answer. Callers never see the database's tables; only the service program, its tests and the backup job open the database file.

### The service

- **Standard library only.** The service is one Python program using `http.server` with `ThreadingHTTPServer`, and `sqlite3` with write-ahead logging, a bounded busy timeout and short transactions. ned-box's Python is 3.14, with SQLite 3.46.1. Nothing is installed with `pip`.
- **A narrow JSON API of named operations**, never SQL. Each request names an operation: record agent-seat created; record agent-seat seen, which the one-time fill of build-slice 3 sends; record agent-seat paused, resumed or retired (the glossary's retire-seat, and pausing, which the glossary keeps distinct from retiring); record agent-seat parked, when the login restart sets an agent-seat aside, an operation separate from the user's pausing; record machine booted, with the estimated stop of the boot before; record handoff-supervisor began; record handoff-supervisor ended; record agent-session launched, with its session ID, transcript path and predecessor session, which the handoff-supervisor sends when it starts Claude Code; a launch that ends before any transcript exists is recorded as launched, then ended, with no transcript path; record agent-session ended, with its exit code; record session-handoff written; record session-handoff consumed; record restart attempted and its result; list agent-seats; get one agent-seat. A caller never sends SQL, so the schema can change inside the service without touching a caller.
- **Callers use `urllib`**, from Python's standard library, which works in every interpreter that runs these programs. The launchers are shell scripts, so they call a small Python helper rather than the service directly. The interpreters are Homebrew's Python on the Mac, whose LaunchAgent runs `/opt/homebrew/bin/python3` ([`install-restart-live-seats-at-login-launch-agent.py` line 52](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/install-restart-live-seats-at-login-launch-agent.py#L52)), `/usr/bin/python3` on ned-box ([`install-restart-live-seats-at-login-systemd-unit.py` line 63](https://github.com/nedschorus/nedschorus/blob/2ba7cc17765e6f03033311d1efd09c94fb63b5d1/scripts/install-restart-live-seats-at-login-systemd-unit.py#L63)), and Apple's Python 3.9, which some tests run under.

### Conditions the design keeps

1. **An agent-seat keeps working when ned-box cannot be reached.** The reason: a Mac agent-seat must not stop because ned-box is rebooting.
   - Every call to the service waits at most 2 seconds; with no answer, the event is queued. A handoff-supervisor sends from a background thread, so it never waits.
   - The 10-second heartbeat does not go to the service. It stays in the local state file for good, because the login restart's file rule needs it (see "What stays a file"). Only events go to the service.
   - Each machine keeps its outgoing events in one local SQLite file, `~/.local/state/nedschorus/agent-seat-events.sqlite`. Every event is first written there as a row; the row number, from a column declared `INTEGER PRIMARY KEY AUTOINCREMENT` so that SQLite never reuses a number even after every row is deleted, is the machine's sequence number for that event, and a row whose `sent` and `rejected` columns are both empty is the queue. SQLite serializes the writers, so the project keeps no lock of its own: several programs on one machine can write and send at once without duplicate or missing numbers.
   - The service keeps every event in one table keyed by event ID, and ignores an event ID it already holds, so an event sent twice is stored once. The program that writes an event's row makes its event ID, a random UUID, in the same insert, so every resend carries the same ID. A handoff-supervisor makes its run ID, a random UUID, when it starts. `nc-systems/handoff/handoff-write-and-check-supervisor.py`, which writes the session-handoff file, puts the 'written' event's ID into that file, and the handoff-supervisor that consumes the file sends that ID in its 'consumed' event. The service computes an agent-seat's state from each sending machine's events in that machine's sequence-number order, not by clock time, so an event that arrives late still takes its proper place and a clock correction cannot reorder events.
   - A 2xx answer fills the event's `sent` column. A 400 or 422 answer fills the row's `rejected` column with the answer, which takes the row out of the queue, and the sending job reports the rejected row with the page described below for a stuck queue. A 401 leaves the row queued; that page reports it too. The page opens once for each newly rejected row, names the row and the service's answer, and says to fix the program that wrote it; the row stays in the local file for reading. Any other answer, or none, leaves the row in the queue.
   - A sent row stays in the local file until a backup holds it: every answer gives, for each machine, the highest sequence number in the service's newest successful backup, and a machine deletes sent rows only up to that number, so no clock is compared. So a restore from the newest backup loses nothing, however long ago that backup ran; a restore from an older copy loses the events sent after that copy and before the newest one.
   - A second table in the same file holds one row per agent-seat on that machine: its name, its ID, and whether it is retired. The launcher writes a new agent-seat's row on the machine the agent-seat will run on: `scripts/launch-claude-ubuntu` writes it through the command it runs on ned-box over ssh. Build-slice 3's fill command makes a UUID for, and writes the row of, each agent-seat that already exists; a program finds an agent-seat's ID by name among the agent-seats not retired; retiring marks the row and keeps it.
   - Each run, the sending job checks the local file with SQLite's `PRAGMA quick_check`. When that check fails, or SQLite reports the file corrupt to any program, the program that finds it renames the file, adding the time, and starts a new file. The program refills the new file's agent-seat table from the service ('list agent-seats', by machine). When the service cannot be reached, the program queues events with the agent-seat's name and no ID, and the sending job fills in the IDs from the service before it sends. Events in the renamed file that were not yet sent are lost to the record, unless a person recovers them from it. The page below reports the corruption and names the renamed file.
   - A scheduled job on each machine sends the queue every 10 minutes, so an idle agent-seat's events still arrive.
   - The 10-minute sending job on each machine checks two things after it sends: whether the oldest row still queued is more than one hour old, and whether the service answered 401. When either holds, it writes an HTML page saying which, on which machine, and what to do, opens it in the browser on the user's Mac, and, once the page has opened, records the condition and the time in a `page_shown` table of the machine's local events file; when the page cannot be opened, the job tries again on its next run. A condition clears when the queue empties or a send is answered with success; the page opens again only after its condition has cleared and come back. On the Mac the job skips the page when ned-box does not answer ssh, since a ned-box that is down is plain to see. For a 401, the page names the sending machine's token file and ned-box's accepted-tokens file, and says that the sending machine's token must be one line of the accepted-tokens file. On ned-box the job opens the page with `scripts/open-html-page-in-mac-browser-from-ned-box.py`; on the Mac, with the Mac's `open`. The page goes to the user until the maintenance agent-seat exists; routing it there then changes only who opens it.
2. **Access stays on the LAN.** The service listens on port 8765 on every address; ned-box's `ufw` firewall admits the port from the LAN only, which is what keeps access on the LAN; build-slice 2's install steps add the rule `sudo ufw allow from 10.0.1.0/24 to any port 8765 proto tcp comment 'agent-seat database service from LAN'`, matching the existing rules for ssh and file sharing. Callers name the service's host `ned-box.local`, which the LAN resolves and which follows an address change; on the Mac `ned-box` is only an ssh alias, which a Python program cannot resolve. Each machine has its own token in `~/.config/nedschorus/agent-seat-database-service.token` with mode 600, sent in every request's `Authorization: Bearer` header; the service reads the tokens it accepts from `~/.config/nedschorus/agent-seat-database-service-accepted-tokens` on ned-box, mode 600, and refuses a request without a known token with status 401. The reason: the record is the operating history of every agent-seat, and the LAN is the only network both machines share. Requests travel as plain HTTP; the design treats the LAN as trusted, since the project's failures come from accidents between cooperative agents, not from attackers.
3. **It starts at boot without `sudo`.** The service runs as a systemd user service of `nedlern`; lingering is already on for that user (`loginctl show-user nedlern -p Linger` printed `Linger=yes` on 2026-10-02), so the service starts at boot with nobody logged in. The unit restarts 10 seconds after any failure.
4. **A nightly backup.** A scheduled job in the repository's table, `nc-systems/general-tools/scheduled-jobs-on-each-machine.json`, copies the database each night to `~/backups/agent-seat-database/` on ned-box, keeping 14 nightly copies, through SQLite's online backup (Python's `sqlite3.Connection.backup`), never a plain file copy, which can catch the file mid-write. The backup job checks each new copy with `PRAGMA integrity_check` and keeps the copy only when the check passes; a failed check leaves the older copies in place, and the page condition 1 describes reports it, naming the file. The backups are not byproducts of the work, so they stay out of the log-store. A second scheduled job, on the Mac, copies the newest backup to the Mac each night over ssh, since the Mac can read ned-box's files over ssh, so a backup survives the loss of ned-box. A restore stops the service, puts a copy back, and has every machine send again every event it kept since that copy was taken (condition 1); the event IDs make the repeats harmless.
5. **The process check stays the test of what is running; when `ps` cannot run, the process check assumes the process is running and says so.** The process check is the one recovery uses today: whether the process ID in the agent-seat's lock is that agent-seat's handoff-supervisor, by `ps`. The database records what happened; only the process check shows what runs now. A record that a handoff-supervisor began in the machine's current boot, with none that it ended, is a question for the process check; one from an earlier boot is certainly not running. ned-box identifies a boot by `/proc/sys/kernel/random/boot_id`. The Mac identifies a boot by `sysctl kern.bootsessionuuid`, a random ID macOS makes at each boot, which a clock correction cannot change. Build-slice 3 first checks on the Mac that the value is present and changes at each boot.

### Alternatives considered

- **PostgreSQL on ned-box.** Mature, and built for writers on several machines; the user weighed it first. Set aside, by his ruling, because the write volume is a few events per agent-seat per hour, and because it is a server to install, back up and upgrade, with a Python driver outside the standard library for the service, or `psql`. The service's API means PostgreSQL can replace SQLite later without touching any caller.
- **One SQLite file on each machine**, each machine reading the other's with a query program over ssh. It needs no service. It was set aside because it splits the record of every agent-seat in two, so every reader on either machine would join two databases, one of them over ssh. A live SQLite database is never opened over a network share, such as the Mac's mount of ned-box's home, because its file locking is unreliable there.

### Schema

The table names live only inside the service; `agent_seat` and `agent_session` are also substrings of identifiers already on main, such as `agent_seat_working_directory`. Build-slice 2 settles the columns.

| Table, key | Columns |
|---|---|
| `event`, key `event_id` | sent_from, the machine that sent the event; machine, the machine the agent-seat runs on; the sending machine's sequence number, operation, the event's own time, received at, body |
| `agent_seat`, key `seat_id`: a random UUID the launcher makes and keeps in the machine's local events file (condition 1), so a queued event can name an agent-seat the service has not seen yet | machine, seat name, seat directory, task-list name, created at, paused at, retired at; the seat name is unique across both machines among agent-seats not retired, as the agent-seat model page requires; the service refuses 'record agent-seat created' for a name a live agent-seat already holds |
| `supervisor_run`, key `run_id`: one handoff-supervisor process | seat ID, boot ID, process ID and its start time, generation, began at, ended at, the restart attempt that started it |
| `agent_session`, key `(machine, session_id, run_id)`: one run of one Claude Code session under one handoff-supervisor run; a resumed session gets a row per run | seat ID, run ID, transcript path, predecessor session, launched at, ended at, exit code; its handoff-supervisor writes the end time and exit code |
| `handoff_event`, key the `event_id` of the event that recorded it, never the restart counter, which can repeat after a state file is lost | seat ID, restart counter, writer session, written at, next-step text, `dont-restart` reason, consumed by run, consumed at |
| `machine_boot`, key `(machine, boot_id)` | booted at, previous boot, stop estimated at and how the estimate was made |
| `restart_attempt`, key `attempt_id` | machine, boot, seat ID, why it was picked, action, began at, ended at, result; the attempt ID is passed to the launcher, which hands it to the handoff-supervisor it starts |

`machine` is `mac` or `ned-box`, always the machine the agent-seat runs on; `sent_from` is the machine that sent the event. There is no "agent-seat started" event: "handoff-supervisor began" says the same.

### What stays a file

- The heartbeat in the local state file, and the login restart's run log with its present use, stay: the login restart's file rule, which build-slice 4 keeps as the fallback for when ned-box is down, needs both, because after a reboot the process check finds nothing and only the old heartbeats show which agent-seats were running.
- The session-handoff file stays the session-handoff: the handoff-supervisor reads it locally, so a session-handoff works with ned-box down. The service records that it was written and consumed.
- Transcripts and task lists belong to Claude Code and stay its files; the database holds pointers to them.
- The files of an approval-walk, cold-read-records, test logs and GHI-MDs stay files: people read them whole.
- Pull request head test-run records stay one file per head; they take no lock.
- Test-run history, the daily memory-review marks and the daily overview-refresh reminder marks are later candidates, outside this design.
- Agent-seats of other runtimes, such as Codex, are outside this design; none runs today.

## The build-slices

Each build-slice is one pull request that leaves main working, followed where named by install steps the user runs or approves on ned-box. Build-slice 1 comes first, by the user's ruling: it changes no behaviour and makes every later build-slice smaller. A separate pull request from the cold-read-research seat, which moves the handoff-supervisor's lock onto an operating-system lock while keeping the process ID in the lock file, lands before build-slice 1.

1. **A shared reader over today's files.** One module, `nc-systems/handoff/agent-seat-state-records-reader.py`, holds the four rules above as named functions, reading the files as they are, and the four programs call those functions instead of their own copies. No behaviour changes: each program keeps its own rule, now in one place. The tests pin each rule's existing cases, which today's test suites for those programs already list.
2. **The service.** The pull request holds the service program, its schema, the systemd user unit file, the caller module with its local event queue, the nightly backup job, and the Mac's nightly job that copies the newest backup to the Mac, with tests. The install steps, run after the merge: create the two tokens and the accepted-tokens file, enable the unit, and add the `ufw` rule from condition 2. No program sends events yet.
3. **Events sent.** The launchers, the handoff-supervisor, the handoff writer, the login restart, recovery and `scripts/resupervise-seat.py` send their events, queueing them when the service cannot be reached. The build-slice adds the 10-minute sending job on each machine, with the page condition 1 describes. The files still decide; the service only listens. The build-slice also adds one command, run once on each machine, that reads the records listed under "The problem" through build-slice 1's reader and sends an "agent-seat seen" event for every agent-seat: its worktree, task list, handoff-supervisor process if one runs, and last session-handoff. Pause and resume events wait on GHI [recover-crashed-seats.py: the six changes ruled 2026-09-02](https://github.com/nedschorus/nedschorus/issues/242) change 3, which is not built; when the login restart parks an agent-seat under that change, it sends "parked", not "paused". The retire steps in `docs/nedschorus-wiki/nedschorus-agent-seat-model.md` gain one command that sends "retired"; those steps are first checked for drift against today's records.
4. **Readers switch.** The shared reader from build-slice 1 asks the service, and reads the files when the service gives no valid answer: only a successful answer with valid JSON counts. For an agent-seat of its own machine, a reader uses the service's answer only when its own machine's local events file holds no unsent row for that agent-seat, meaning a row whose `sent` and `rejected` columns are both empty; otherwise the reader reads that agent-seat's files, as readers did before build-slice 4. For the other machine's agent-seats, the reader uses the service's answer, which is all the reader has, and the reader's report shows when the service received the newest event from that machine, since the reader cannot see that machine's queue. The program's report names which it used, and each answer carries, per machine, the time of the newest event the service received, which the report shows. The switch lands only when every running handoff-supervisor on both machines runs build-slice 3's code, which alone sends "handoff-supervisor began", and both machines' queues are empty. A handoff-supervisor started before build-slice 3 keeps its old code and never sends that event, so after build-slice 3 merges both machines are rebooted at a quiet moment the user picks; the fill command reuses every ID it finds (condition 1) and, with `--confirm`, lists each agent-seat with no 'began' event since build-slice 3, and exits 1 when it lists any; readers switch only after it exits 0 on both machines, and any agent-seat that did not come back is restarted with recovery. The process check stays.
5. **The whole-fleet view.** One command lists every agent-seat on both machines from the service, how to reach each, and why each one that is down is down where that was recorded, with any open tasks. Run on the Mac, the view shows both machines in full. Run on ned-box, the view reads the Mac's open tasks from the Mac mirror's copy, `/home/nedlern/nedschorus-logs/transcripts/mac/tasks/`, and shows the time of the mirror's last complete pass beside them; it shows the Mac's agent-seats from the service only, marked "not checked: ned-box has no route that can check the Mac's processes". ned-box's one key for the Mac, used by `scripts/open-mac-window-from-ned-box.py`, is admitted for one forced command, `scripts/mac-request-from-ned-box-forced-command.py`, which accepts only the requests it lists. A stop with no recorded cause shows as "stopped, cause not recorded". With ned-box down, the view on the Mac shows the Mac's own agent-seats from its files and says the service did not answer.
6. **Remove what nothing reads.** The build-slice names each record it removes, and keeps any record people read, such as recovery's log. The files the build-slice 4 fallback reads stay, the login restart's run log and the heartbeat among them.
