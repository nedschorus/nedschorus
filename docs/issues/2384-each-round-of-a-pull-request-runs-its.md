# Each round of a pull request runs its test suites once, and a push reuses a passing test run of the same tree

## What is wrong

Today one round of a pull request, from the author's test run before the push to merge-lane-2's review, runs overlapping selections of the nc-test-suites up to three times:

1. The author's test run, which the CLAUDE.md bullet beginning "Before pushing" asks for: `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`.
2. The pre-push selective test run, `scripts/git-client-side-hooks-pre-push-selective-test-run.py`, which selects the same way again on the same files, within a 480-second budget (`DEFAULT_TIME_BUDGET_SECONDS`). It runs nothing when an earlier step of the hook refuses the push, or when it finds the machine's test lock held.
3. merge-lane-2's head test run, run by `scripts/merge-lane-pull-request-worktrees-reviewer-brief-codex-review-and-head-tests-run-without-merge.py`, which tests the pull request merged into main, the `pr<n>-merged` worktree, and selects since main's commit there, so it selects for the pull request's own changes.

Selecting since `origin/main` usually picks more nc-test-suites than selecting since the merge base, because it also selects for the files main changed since the branch started. Test runs started by authors, by hand or by the pre-push hook, averaged 81 nc-test-suites, and the pre-push runs stopped at the budget averaged 107, against 64 in head test runs.

Two independent analyses of the transcripts of every agent-seat and the runners' reports for 2026-10-31T00:00Z to 2026-11-02T00:00Z, one by Opus and one by Codex, measured this cost. The figures below are the Opus report's; the Codex report counts 17.58 hours over 175 push operations, and says its operations overlap one another.

- Pushes cost 18.0 agent-hours in the window and about 8 minutes of each round's critical path (168 pushes, median 8.1 minutes).
- 130 pre-push selective test runs (102 from authors' pushes, 28 from `scripts/ghi-issue-write.py`) stopped at the 480-second budget with no verdict: 17.2 machine-hours thrown away, and each of those pushes went through without the pre-push run's verdict.
- Running each round's nc-test-suites once would save about 78 pull-request hours and 63 agent-hours a week, and 60 machine-hours (Opus report, section 6, proposal 3).

The reports: `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/fleet-time-and-token-costs-2026-10-31-to-2026-11-02/opus/report.md` (section 2, "Retries and timeouts", and section 6, proposal 3) and `nedlern@ned-box:/home/nedlern/nedschorus-logs/analysis/fleet-time-and-token-costs-2026-10-31-to-2026-11-02/codex/report.md`.

A second count, over a longer window, made on 2026-11-02 from ned-box's transcripts under `~/.claude/projects/`: every Bash tool call whose command runs `git push`, in the foreground, from 2026-10-14 to 2026-11-02T18:31Z, each counted once by its tool call id. It leaves out the Mac, pushes run in the background, and the pushes `scripts/ghi-issue-write.py` makes itself.

- 1322 pushes; 186 of them took 480 to 492 seconds, the budget plus the hook's other steps.
- 159 pushes show the pre-push step's verdict in their output: 58 stopped at the budget (483 to 488 seconds), 100 passed (median 300 seconds; 99 took over two minutes), and 1 found the machine's test lock held and went through at once.
- 416 ended at 115 to 125 seconds with none of the hook's text, the Bash tool's default time limit of 120 seconds; what happened to those pushes is not in this data.

So a pre-push selective test run that finished took a median of about five minutes, and one that did not finish was stopped at eight and let the push through without its verdict.

## What the user decided

On 2026-11-02 at about 00:55Z, in agent-instructions-editor's agent-session on ned-box, the user decided, in his words: "Obviously running the same tests is stupid unless there's a reason to run a test. ... I would make all these changes, and I'd make them in the order of efficiency." His decision is recorded at line 35 of `/home/nedlern/agents/agent-instructions-editor/docs/walk/merge-lane-2-seat-brief-rewrite-without-history-2026-11-02-minutes.md` on ned-box, whose outcome reads in part "tests run once per change unless there is a reason". This change is second in the order he set, by hours saved, after taking the eight test suites that run without a sandbox off per-change test runs, GHI [Test suites that run without a sandbox leave per-change test runs and run apart, when their own files change or in a quiet gap](https://github.com/nedschorus/nedschorus/issues/2381).

So:

1. A push reuses a passing test run of the same tree instead of running the selection again.
2. The author's test run and the pre-push selective test run select since the merge base, as the head test run does.

Under the design below the pre-push selective test run no longer runs, so decision 2 applies to the author's test run, which the push program runs. The head test run selects since main's commit on the pull request merged into main, not since the merge base, but both select for the pull request's own changes.

On 2026-11-02 the user approved, as item 2 of the approval-walk ned-box-helper-speed-and-open-questions-2026-11-02, with his answer "A", the design below in outline: one push program runs the selected suites once, records the passing run with a fingerprint of the branch's files and the main commit the suites were chosen against, and pushes; it first rebases onto origin/main only if the branch was never pushed; the pre-push step's suite run is replaced by a pre-push step that refuses a push without a matching record and names the program to run, and the pre-push hook's other steps stay; the program logs each test run's time, and reports to the user a typical run over two minutes. The walk-document is `/home/nedlern/agents/ned-box-helper/docs/walk/ned-box-helper-speed-and-open-questions-2026-11-02.md` on ned-box, item 2, with its walk-minutes beside it. Two earlier decisions still hold: a pushed branch is never rebased (user-ruled 2026-09-15, item 4 of `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/keeping-branches-current-telling-and-rebase-minutes.md`), and a typical pre-push test run is timed, and its time goes back to the user when it is over two minutes (user-ruled 2026-10-05, item 7 of `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/nedschorus-where-agent-rules-live-decision-guide-draft-2026-10-05-minutes.md`).

The case against, as shown to the user: a mistake in the fingerprint could let an untested change through. merge-lane-2's head test run tests every pull request again, merged into main, before merging it, so such a change would most likely still be caught before it merges.

## Design

This design removes the second of the three test runs above: the push program runs the author's test run once and records it, and the pre-push hook checks the record instead of testing again. The head test run still tests each pull request again; whether it can reuse a passing result, which the title's "once" also needs, is listed under Deferred-decisions.

### The push program

`scripts/branch-rebase-if-never-pushed-selective-test-run-record-and-push.py` is how an agent pushes a branch other than main. The pre-push hook refuses a push of such a branch to origin, seat-branches included, unless a record of a passing test run of the pushed commit's files is on the machine, and only this program writes records. The hook does not check a branch deletion, a push to another remote, or a push whose record check fails rather than refusing, as the pre-push step below says. The program takes the branch's name on origin as an optional `--remote-branch <name>`, for a push from a detached HEAD or to another name, as step 8 of the fix-round program's subagent prompt, `git push origin HEAD:<branch>`, does. It runs these steps, each in code. A git command or file write in them that fails stops the program with a nonzero exit, printing the command and its error, and nothing is pushed.

1. It refuses, before anything else: a push to `main` on origin, whichever local branch it comes from; a detached HEAD without `--remote-branch`; a checkout with a rebase, merge, cherry-pick, revert or bisect in progress; and a checkout with a change git would test but not push, which is an uncommitted change to a tracked file, or a file git does not track and does not ignore. It leaves out, by name, the files that the fix-round and follow-up subagents write at a worktree's root before they push, `fix-round-answers-pull-request-<number>.md` for any number and `follow-up-pull-request-title-and-description.md`, because a branch cut before main's `.gitignore` listed them does not ignore them. The runner tests the checkout's files, uncommitted changes included, while a push sends a commit; refusing such a checkout makes the files tested the files of the commit pushed, so the record can name the commit's tree.
2. It runs `git fetch origin`.
3. When HEAD is a branch, `--remote-branch` is not given, and the branch was never pushed, it runs `git rebase origin/main`. "Never pushed" is decided by `head_state` of `scripts/checkout-freshness-catch-up.py`, which the program loads as `scripts/obsolete-file-edit-warning-hook.py` already does, so the Stop hook's rebase and this program use one rule. The program rebases only when `head_state` returns `unpushed`: a branch whose commits were pushed under another name, as a fix-round's local branch is, counts as pushed, and `unknown`, a state git cannot establish, stops the program. So do `behind-remote` and `diverged-from-remote`, before any test run, saying that the remote branch has commits this one lacks, so the agent builds on them or hand-merges them and runs the program again. A detached HEAD, or a push with `--remote-branch`, is never rebased: the callers that pass it, the fix-round subagent and `scripts/ghi-issue-write.py`, push a branch that is already pushed, or a detached worktree just cut from `origin/main`. When a rebase stops on a conflict, the program names the files that conflict, then runs `git rebase --abort`, and exits nonzero, saying that the agent resolves them in its own `git rebase origin/main` and runs the program again. A rebase that fails without a conflict, or an abort that fails, stops the program with git's message, saying whether a rebase is still in progress. A branch that was pushed is never rebased. A branch rebased here stays rebased whatever happens in the later steps: nobody else has it.
4. It sets the base to `git merge-base origin/main HEAD`, as decision 2 in the list above says, a list drawn from the user's words: the Opus report's proposal 3, which the user's words adopt, makes the author's test run select since the merge base. After step 3 the merge base of a never-pushed branch is the `origin/main` commit it was rebased onto, which is the "main commit the suites were chosen against" of the approved item.
5. When a passing record for this tree and base already exists, it skips steps 6 and 7 and says so in one line. This is the case of a push that failed after a passing test run, such as one stopped by the network, run again.
6. Otherwise it runs the runner beside it, `scripts/run-all-test-suites.py --checkout <top> --only-suites-whose-recorded-inputs-changed-since <base> --wait-for-lock-seconds <seconds>`, where `<top>` is `git rev-parse --show-toplevel` of the directory it is run from and `<seconds>` is the lock wait listed under Deferred-decisions, which is settled before the build writes this step, passing the runner's output through as it comes. There is no time budget: a slow test run finishes rather than being stopped. When the test run ends, passing or not, the program writes its seconds to the shared-log. Before it records a test run that exits 0, it checks that HEAD is still the commit it started with and that the checkout still has no change step 1 refuses; when either changed, it writes no record, says what changed, and stops nonzero, since the files tested may not be the commit's. A test run that exits 0 and passes that check is recorded. A test run that exits anything else writes no record and stops the program with the runner's exit status, after the runner's own lines saying what stopped it, such as each failed suite and its log, and nothing is pushed.
7. After a passing test run, it prints the two-minute report described below when it is due.
8. It runs `git push origin HEAD:refs/heads/<branch>`, with `-u` when `--remote-branch` is not given. A push that fails exits nonzero with what git printed, and is not tried again. The record stays, so running the program again pushes without testing again, unless main moved and step 3 rebases a never-pushed branch again, which changes its tree. When git rejects the push because the remote branch has commits this one lacks, the program adds that the agent builds on those commits or hand-merges them, then runs it again. Any other push that git refuses for a reason the record cannot change is the agent's to resolve from git's message, as it is today.

A test run can take longer than the 600 seconds Claude Code gives one foreground Bash command, so the program is run in the background, and its exit status read when it ends; so are `scripts/ghi-issue-write.py` and the follow-up program's `open-pull-request`, which run it. Its usage text, theirs, and every tool-message-to-agent that names one of the three say so.

Like the git hooks, the program is run as the reference-checkout's copy, `python3 ~/Projects/nedschorus/scripts/branch-rebase-if-never-pushed-selective-test-run-record-and-push.py`, a path that is the same on the Mac and on ned-box, because an nc-topic-branch cut before the program merged has no copy of its own, and the hook's refusal must name a command that works from every branch. The program tests the checkout it is run from, as the pre-push step does today.

### The record

A passing test run's record is one JSON file in `~/.cache/nedschorus-passing-selective-test-run-records/`, on the machine that ran it, outside every checkout, so that every worktree of that machine's clone, and the pre-push hook running from the reference-checkout, read the same directory. The file is named `<tree hash>-<base commit>.json`, from the fingerprint, which is the two values that name what was tested: the tree hash of the commit tested, `git rev-parse HEAD^{tree}`, which names every file of the commit, and the base commit the suites were selected against. The record also holds the commit, the branch, the machine, the start and end times, the test run's seconds, the number of suites run, and the runner's log directory, for a reader tracing a push. The program creates the directory when it is missing. A record is written to a temporary file with a name of its own in that directory and renamed into place, so a reader never sees half a record, and two agent-seats that record the same tree and base write the same name, the later rename replacing the earlier. Only a passing test run writes one. A missing directory, or a record that cannot be read as JSON, counts as no record; the two-minute report also leaves out a record without its seconds and end time.

The record's file name, its format, and the lookup that the program and the hook both use are in `scripts/passing-selective-test-run-record-common.py`.

The record gets a directory of its own, rather than the runner's recorded inputs, `~/.cache/nedschorus-test-suite-recorded-inputs`, or the run records beside the runner's lock file, because those belong to the runner and each holds one suite's inputs or one running process; a record here is about one tree and base, and serves every push of that tree and base on its machine.

### The pre-push step

`scripts/git-client-side-hooks-pre-push-selective-test-run.py` is replaced by `scripts/git-client-side-hooks-pre-push-passing-selective-test-run-record-check.py`, which runs no test. The hook pipes the pushed refs to the new step on stdin and passes it the hook's arguments, as it does to its other steps, in place of today's `</dev/null`. For each branch the hook already picks, a push to origin of a branch other than main, the new step reads the pushed commit's tree hash and its merge base with `origin/main`, and looks for the record with that name. It lets the push through with one line when every picked branch has its record. It refuses the whole push, exit 10, when any picked branch has none, naming each such branch: the refusal says that no passing selective test run of this commit's files is recorded on this machine, so the push is stopped, then gives, for each such branch, the command to run in the background in place of `git push`: the program by its reference-checkout path with `--remote-branch <branch>`, run from a checkout whose HEAD is that branch's commit, one branch per run. When `git worktree list --porcelain` shows a worktree with that commit checked out, the command starts with `cd <that worktree> &&`; otherwise the refusal says no worktree has it checked out.

The hook's other steps, the nc-mutation-testing worktree refusal, the refusal to rewrite or delete an open pull request's branch, and the conflict check with its revert check, stay as they are, and in the same order. The hook's failure handling stays too: a step that fails, rather than refusing, lets the push through and says so. For the new step, such as when git finds no merge base, that line says the record check did not run and why, and names no test command.

The pushed commit's merge base with `origin/main` stays the same when main moves on with commits of its own, so a record made before main moved still matches. It changes when main takes in commits of the branch itself, as when a pull request the branch is stacked on merges, and after a hand-merge of main into the branch. The hook then finds no record under the new base and refuses, and the program, run again, selects since the new base, tests, records and pushes. The hook's conflict check fetches origin before the record check runs, so such a change can arrive during the push itself; the same refusal and rerun apply.

### The two-minute report

After each passing test run, the program reads the seconds of the last 20 records on its machine, by the end time each holds, or of every record when there are fewer. When their median is over 120 seconds, it prints a line telling the agent to tell the user the median, the number of records it is taken from, and the record directory. The build does this unless the user picks another way under Deferred-decisions. The count above puts a typical finished pre-push test run at about 300 seconds, so the report is likely due from the first day.

### Steps that need judgment

None in the program: choosing the base, deciding whether to rebase, running the suites, writing and finding the record, and pushing are all code. An agent's judgment is used only where it is today: fixing a suite that the test run shows failing, resolving a rebase conflict, and resolving a push that git refuses.

### Tests

- The push program: it refuses `main`, a detached HEAD without `--remote-branch`, a git operation in progress, and each kind of change git would test but not push, and does not refuse the two named files; it rebases a never-pushed branch, stops on a branch behind or diverged from its remote branch, and leaves alone a pushed branch, a branch pushed under another name, and any push with `--remote-branch`; it stops on `unknown`; it aborts a rebase that conflicts and pushes nothing; a failing test run logs its seconds, writes no record and pushes nothing; a passing test run writes the record before the push, and writes none when HEAD or the checkout changed during it; a push that fails keeps the record, and a second invocation with the same tree and base pushes without a test run; the two-minute line appears when the median of the last 20 records, or of every record when there are fewer, is over 120 seconds, and not otherwise.
- The pre-push step: it refuses a pushed commit with no record, with a record of another tree, and with a record of another base, naming the command with `--remote-branch` for each branch; it lets through a commit whose record matches; the hook's other steps run as before.
- Each failure-handling line of both programs gets a test that causes the failure, as `CLAUDE.md` requires; after the merge, `scripts/scheduled-full-mutation-pass-of-merged-pull-requests-and-survivor-tasks-open.py` checks those tests by nc-mutation-testing in its nightly run.

## Deferred-decisions

- Who builds this, and when. This GHI-MD's first version gave the design to the agent-seat reboot-test, after the design of GHI 2381; the user approved the outline on 2026-11-02 in ned-box-helper's approval-walk. The agent-seat that builds it is settled before the build starts.
- The base. The approved item names "the main commit the suites were chosen against", and the user's 00:55Z decision 2 names the merge base. The two are the same commit for a never-pushed branch after step 3, and differ for a pushed branch that main has moved past; this design follows decision 2. If the user meant `origin/main` for a pushed branch too, step 4 and the pre-push step's lookup change together.
- How the two-minute report reaches the user without telling him on every push: the design prints it after every passing test run while the median stays over two minutes; once a day per machine, or once only, are the alternatives, and so is a notice the program shows the user itself rather than through the agent. The user decides; until he does, the build prints it as the design says.
- Whether merge-lane-2's head test run reuses a passing result for suites whose recorded inputs are identical, as the Opus report proposes. Without it, a round still runs its suites twice, once by the author and once in the head test run. Not part of this design.
- If pull request [Mutation testing: a quick pass before push on failure-handling lines, and a scheduled full pass that opens a task per survivor](https://github.com/nedschorus/nedschorus/pull/2147) merges first: whether the push program runs its quick pass too.
- How long the push program waits for the machine's test lock where the runner takes one, on a machine without nc-test-sandboxes such as the Mac: a number of seconds, or no limit. On ned-box, where suites run in nc-test-sandboxes, no lock is taken.
- What the push program does when the runner waits without end for CPU or memory to admit a suite, which the removed budget no longer stops; to be set from the first runs.
- What happens to the runner and the push when the push program itself is stopped mid-run, such as when its agent-session ends.
- Whether the record also names the runner's commit, so that a change to the reference-checkout's runner makes an older record stale; the head test run tests again before merge either way.
- Whether the fix-round program's `--check`, once it passes, runs the push program itself, so the fix-round's subagent cannot push out of order.
- Whether old records are ever removed. Each is a few hundred bytes; none is removed until the number of files shows a need.

## Why it matters

Each repeated selection holds CPU, admission slots and often the lock of the suites that run without a sandbox, so it delays the other agent-seats' test runs on the same machine at the time, as well as its own. A pre-push run that is stopped at its budget costs the time and still lets the push through without its verdict.
