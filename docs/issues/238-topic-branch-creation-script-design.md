**Vocabulary.** Agent-seat, agent-home, seat-branch, reference-checkout, nc-topic-branch and topic-worktree are used as `docs/nedschorus-wiki/nedschorus-glossary.md` defines them. The glossary's agent-home and seat-branch entries describe today, when each agent-home still stands on its seat-branch; the user-ruling above retires seat-branches, and the build that does so has not merged (see "While seat-branches still exist"). **The rule this implements**, restated here so the document stands alone: an ordinary nc-topic-branch starts at current `origin/main`, in a topic-worktree of its own in the managed area, rather than at whatever commit a checkout happens to stand on. Stacked work is the one exception, and it is not this script's case: see "What it deliberately does not do". This document says `origin/main`, the remote-tracking ref, rather than `main`: every worktree of the clone sees the local `main`, but only a git command run in the reference-checkout, such as a pull, moves it, and no agent works there, so the local `main` can stand far behind, while a fetch brings `origin/main` up to date.

## What this GHI covers: three pieces

A sentence of instruction is not a fix: agents are unreliable readers (user-ruled 2026-09-02, which is why this is filed separately from the pull-request skill that GHI [pull-request skill: how a change reaches main — durable-file disposition, the description, and topic-branch creation](https://github.com/nedschorus/nedschorus/issues/236) proposes; that skill has not been written, and this script does not depend on it). So the GHI has three mechanical pieces:

- **Piece 1, the topic-worktree script.** This document's subject, designed below, with the cases left open listed under "Deferred-decisions". Not built; it is built once the worktree cleaner's owner-file build has merged, as "The build order" says.
- **Piece 2, a check at `gh pr create`.** It detects the actual failure rather than trusting the rule was followed: refuse when the branch about to be filed carries commits that another open pull request's branch adds over `origin/main`, **unless the pull request declares that dependency**. The declaration is what distinguishes the two cases. Stacked work is legitimate: work that depends on an unmerged nc-topic-branch branches from that branch and necessarily carries its commits, and a check without the exemption would refuse exactly the case the rule permits. The project's code already reads one form of declaration: a pull request whose base branch is another open pull request's branch is stacked on it (`scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py`, which retargets such pull requests before it merges the one below them). Not designed; see "Where it sits in the code-prompt-code structure".
- **Piece 3, a session trailer stamped on commits before the push.** Filed as a check; built as a hook that stamps the trailer rather than checking for it. See below.

## The problem

A branch made without a start point is based on whatever commit the checkout running the command stands on. `git checkout -b <name>` does this and also moves that checkout onto the new branch, so the command that creates topic one leaves the checkout standing on topic one, and the same command typed for topic two bases topic two on topic one. `git worktree add -b <name> <path>` without a start point bases the new branch on the commit of the checkout it runs from too, without moving that checkout: run from an agent-home on its seat-branch, or from another topic-worktree, it bases the new branch on that checkout's commit (measured 2026-10-30 against throwaway repositories). The second pull request then contains both topics while its description names one, and if topic one is rejected its code rides into main inside topic two.

The ruled model removes the reason an agent-home ever held topic work, since every topic gets its own worktree, but it does not by itself choose the start point: the ruled command is right only because it names `origin/main`, and an agent typing it by hand can leave that argument off. The worktree location hook, not yet built, will refuse a `git worktree add` that makes a new branch outside the managed area (item 2a of approval-walk ghi-info-checkout-and-worktrees-the-cleaner-never-sees-2026-10-11, walk-minutes line 9, `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/ghi-info-checkout-and-worktrees-the-cleaner-never-sees-2026-10-11-minutes.md`, narrowed to new branches by item 5 of approval-walk md-skills-seat-open-decisions-2026-10-13, walk-minutes line 12, `nedlern@ned-box:/home/nedlern/agents/MD-skills/docs/walk/md-skills-seat-open-decisions-2026-10-13-minutes.md`). It checks the path only, never the start point.

Nothing detects a wrong start point automatically. The extra commits are visible from the moment the branch exists (`git log origin/main..HEAD` shows them locally, and the pull request's commit list shows them once filed), and main's protection requires an approving review, so the mistake is catchable. But catching it depends on a person looking, and the pull request's description will name one topic while its commits contain two.

**Near-miss, 2026-09-01.** The `reboot-test` agent-seat created four nc-topic-branches in a row in its agent-home, checking each out there in turn, filed as pull requests [Launchers: report only the update failure the launcher can actually see](https://github.com/nedschorus/nedschorus/pull/229), PR [launch-claude-mac: update the claude the seat will actually run](https://github.com/nedschorus/nedschorus/pull/230), PR [catch-up hook: a landed merge is an attention state, and stdout is one channel](https://github.com/nedschorus/nedschorus/pull/231), PR [Remove the Zero-Context Explanation output style](https://github.com/nedschorus/nedschorus/pull/232), naming `origin/main` explicitly on each. Each of the four depended on that argument: the first would have been based on the agent-seat's seat-branch, and each of the other three on its predecessor. The failure did not occur, and the margin was one argument, four times.

## What the script does

`python3 scripts/topic-worktree-from-origin-main-create.py <topic-name>`, run from a checkout's top directory, or by the script's absolute path from anywhere inside a checkout of the clone: the agent-home, a topic-worktree, or a subdirectory of either. `--help` prints the usage on stdout and exits 0, as `scripts/every-repository-program-help-option-test.py` requires of every program it does not exempt. Every git command runs in the current working directory and lets git find the repository from there; the script does not use its own file location, which is why running it by absolute path from an unrelated repository acts on that repository (see "Project identity is not checked").

**The worktree path.** The script finds the reference-checkout as the parent of the directory `git rev-parse --path-format=absolute --git-common-dir` prints, the way `main_checkout_of` in `scripts/clean-worktrees.py` does, and makes the topic-worktree at `<reference-checkout>/.claude/worktrees/<topic-name>`: the topic name used verbatim as the path below the managed area, as step 1 of GHI 1121's draft writes the command. Run from a linked worktree, that git command prints `<reference-checkout>/.git` (measured), so the path does not depend on where the caller stands, and no machine's home directory is written into the script. A topic name containing `/` makes nested directories in the managed area, which git accepts (measured) and which the cleaner's first condition in `classify`, that the managed area is among the worktree's parents, still counts as managed. A topic name may begin with `agent-`: the worktree location hook was once to refuse such names, because the cleaner treated `agent-` worktrees as subagents', and on 2026-10-28 the user approved dropping that refusal, since the ruled cleaner goes by a worktree's owner file, not its name (item 1.1.6 of approval-walk md-skills-seat-open-questions-from-item-2-carried-over-approval-walk-2026-10-28, `nedlern@ned-box:/home/nedlern/agents/MD-skills/docs/walk/md-skills-seat-open-questions-from-item-2-carried-over-approval-walk-2026-10-28.md`, approved 18:14 per its walk-minutes beside it). GHI 1121's draft row "Topic worktree" still says a topic name never begins with `agent-`; that clause predates the ruling.

The steps that change anything, in order:

1. `git fetch origin`
2. `git worktree add -b <topic-name> <reference-checkout>/.claude/worktrees/<topic-name> origin/main`
3. writing the owner file into the new topic-worktree (see "The owner file")

Rows 1 through 6 of the table under "Refusals" are checked before any step runs. Row 7 is the fetch failing, row 8 is a check made after a fetch that succeeded, and row 9 is the second step failing. The success line is printed last, after step 3. The fetch changes remote-tracking refs, tags it follows, and what comes with them, which the state guarantee treats separately; the second step creates the branch and the topic-worktree together.

The new branch's start point is `origin/main` by construction: `git worktree add -b` with an explicit start point does not consult the caller's HEAD. The command creates the new directory and the new branch and records the worktree in git's administrative files. Under git's default settings, because the start point is a remote-tracking branch, it also records `origin/main` as the new branch's upstream in the clone's config; so the first push must be `git push -u origin <topic-name>`, as step 4 of GHI 1121's draft writes it, which sets the branch's own upstream, while a plain `git push` is refused under git's default `push.default=simple`. The caller's HEAD, working tree, index and uncommitted changes stay as they were (measured), so uncommitted work in the caller's checkout does not move to the topic-worktree. A `post-checkout` hook, which git runs inside the new worktree, can write anything; the project installs none today. After a success the caller works in the topic-worktree, running git and test commands there, as step 1 of GHI 1121's draft says.

**The owner file.** On 2026-10-28 the user approved that the program that makes a worktree writes an owner file in it, naming the agent-seat for an agent-seat's worktree, and that the cleaner removes only a worktree holding an owner file: it keeps a worktree while its owner runs, unless its branch's pull request has merged or been closed and it holds no uncommitted or untracked file (item 1.1.2 of the 2026-10-28 approval-walk above, approved 14:23; its item 1.2, approved 2026-10-29 08:55, writes the rules into `nc-systems/handoff/handoff-uncommitted-work-snapshots-across-crashes-design.md`, which on main does not yet carry them). This script makes topic-worktrees, so it writes that owner file into each one it makes, as its step 3. The file's name and format, and how the script learns which agent-seat to name, belong to the cleaner's build and are listed under "Deferred-decisions".

**The build order.** On 2026-10-30 at 18:43 the user approved building this script after the worktree cleaner's owner-file build, the build that defines the owner file of item 1.1.2 of the 2026-10-28 approval-walk above, so that the script writes, from its first version, the owner file item 1.1.2 asks for (item 5.5 of that approval-walk, walk-minutes line 220, `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/md-skills-seat-open-questions-from-item-2-carried-over-approval-walk-2026-10-28-minutes.md`). The recommendation he approved, as the item was shown to him: "build the topic-worktree script after the cleaner's owner file." The alternative the item showed was to build the script now without the owner file and add the file later, which would catch worktrees started from the wrong commit sooner; the cost of the order chosen is that agents keep making topic-worktrees by hand until the script's pull request merges. Until the owner-file cleaner merges, today's cleaner can remove a new topic-worktree before its first commit, however the worktree was made: `classify` in `scripts/clean-worktrees.py` lets `--remove` delete a worktree in the managed area when its branch has no commit that `origin/main` lacks and no process has its working directory inside it, and, for a worktree whose name begins with `agent-`, only after an hour's quiet; it deletes the worktree with its uncommitted, untracked and ignored files, and it runs daily and at each session-handoff. An agent whose agent-session's working directory stays in its agent-home and who runs commands as `cd <worktree> && …` leaves no process with its working directory inside the worktree between its commands. It has happened: on 2026-10-24 and 2026-10-25 the cleaner removed two subagents' new topic-worktrees within 4 and 38 seconds of their creation, before either held an edit (cold-read-record `nedlern@ned-box:/home/nedlern/nedschorus-logs/cold-read-records/item-11.3-worktree-cleaner-removes-new-topic-worktrees-2026-10-27-2`, cited by item 1.1.3 of the 2026-10-28 approval-walk). The work-snapshot hook (`scripts/uncommitted-work-snapshot-hook.py`) keeps a copy of the tracked and untracked changes an Edit, Write or NotebookEdit call made there, which the handoff-supervisor lists in the initial-agent-instructions of the agent-seat's next agent-session once the worktree no longer holds them; of the ignored files, the cleaner first ships the walks in the worktree's `docs/walk/`, its cold-read-records and its sanity-check-records to the log-store, keeping the worktree when any of them fails to ship, and the rest are lost. The owner-file cleaner is to end this, for worktrees holding an owner file.

**While seat-branches still exist.** As of 2026-10-30 the agent-homes of prime-intellect, merge-lane-2 and MD-skills on ned-box stand on their seat-branches (checked with `git branch --show-current` in each). The build that detaches them at main is GHI 1121's Build item "Agent-homes detached at main", which MD-skills pilots on its own agent-home for a day before any other agent-home is detached (item 16 of the 2026-10-13 approval-walk, walk-minutes line 34). The script behaves the same before and after that build: it never checks out or moves the caller's branch and never uses it as a start point, and `git worktree add` works from a checkout on any branch or on none, so the seat-branch neither helps nor gets in the way. The script does not create, move or delete a seat-branch. The owner-file cleaner of items 1.1.2, 1.2 and 1.2.3 of the 2026-10-28 approval-walk has not merged either, so today's cleaner can remove a topic-worktree before its first commit, as "The build order" says.

An earlier draft of this document routed through the agent-seat's seat-branch: check it out, fast-forward it to main, then create the topic from there. That route was unsafe, and the ruled model has no use for it: `git merge --ff-only origin/main` does not refuse when the current branch is strictly ahead of `origin/main`. It answers "Already up to date" and exits 0, leaving stray commits in place for the next branch to inherit (measured 2026-09-02).

## The caller contract

**Exit status**: `0` success; `1` refusal (rows 2 through 9 below); `2` usage error (row 1); `3` an unexpected error, meaning the script's own traceback rather than a condition it anticipated. A refusal is an ordinary outcome rather than a crash, but it is nonzero so `&&` chains, and calling programs that check the exit status, stop. Exit 3 exists so that a crash is distinguishable from a refusal: an uncaught Python exception would otherwise exit 1 and impersonate one.

**After an exit 3, or a run that was killed or interrupted**, the branch and the topic-worktree may exist without the owner file, because each step may have finished before the end. The caller runs `git worktree list` and `git branch --list <topic-name>`, and, if the first lists the topic-worktree's path or the second lists the branch, tells the user what it found and the script's output, rather than running the script again, since a rerun with the same name is refused by row 4 or row 6. If neither exists after an exit 3, it tells the user the traceback, since a crash is a defect a rerun does not fix.

**Success**, one line on stdout, naming the worktree because the caller's next step is to work there:

```
<topic-name> created at <sha> (origin/main) in <worktree-path>
```

`<sha>` is the commit the new branch points to, read after the add, as `git rev-parse` prints it in full: 40 hex characters in a SHA-1 repository and 64 in a SHA-256 one, never abbreviated, so the line does not vary with `core.abbrev` or repository size. It is read from the new branch, not from `origin/main`, because another agent-session's fetch into the same clone can move `origin/main` after the add. `<worktree-path>` is absolute.

**Refusal**, on stderr: one line naming what is wrong; then the next action, each instruction on a line of its own with the condition it applies under, as `CLAUDE.md` asks of text a program hands an agent; then git's own message verbatim when git produced one, after a line saying git's message follows. Git's messages are frequently multi-line and are not reformatted or truncated, apart from the credential redaction under "Refusals". Where a row's fact involves git's message, the fact line names the git command that failed and its exit status, and git's message follows the next action. A command in a next action is printed with the reference-checkout's path and the topic name filled in, each argument quoted for the shell.

**Usage error**, on stderr: the usage line, then a next-action line. Nothing on stdout.

Stdout carries the success line, or the usage for `--help`, and nothing else; on any nonzero exit it is empty.

Subprocess output is captured, so git's messages appear only where this contract puts them. Capture does not cover authentication: depending on how the caller's environment is configured, git may use a credential helper, an askpass program, fail outright, or write a prompt straight to the terminal. The script sets `GIT_TERMINAL_PROMPT=0`, which stops git's own terminal prompt, so that an uncached credential git would have asked for on the terminal fails as a row 7 refusal. It does not stop an askpass program or ssh's own prompts for a passphrase or a host key, which can still wait; a timeout on the git commands is listed under "Deferred-decisions".

## Refusals

The table holds row 1, the usage error, and rows 2 through 9, the refusals, checked in this order. Every check before the fetch is local and cheap; the fetch is the first thing that touches the network.

| # | Condition | Fact reported | Next action |
| --- | --- | --- | --- |
| 1 | Not exactly one argument, or an argument other than a lone `--help` that begins with `-` (exit 2) | the usage line | pass exactly one topic name, and one that does not begin with `-` |
| 2 | Not inside a git checkout's working tree: `git rev-parse --is-inside-work-tree` does not print `true`, as in a bare repository | the working directory | run it from inside a checkout of the project |
| 3 | `git check-ref-format refs/heads/<name>` rejects the name | the name | see `git help check-ref-format` for the rules |
| 4 | A local branch of that name exists | the branch, its tip, and the worktree that has it checked out, if one does | pick another name; if that branch is an nc-topic-branch whose work you mean to carry on, work in the topic-worktree that has it checked out; if no worktree has it checked out, make one with `git worktree add <reference-checkout>/.claude/worktrees/<name> <name>` |
| 5 | The name and an existing `refs/heads/` ref cannot both exist, because one is a path prefix of the other | both names | pick a name where no existing branch is a slash-separated prefix of it, and it is not a slash-separated prefix of one |
| 6 | Something already exists at the worktree path, or `git worktree list` still registers a worktree there whose directory is gone | the path, and which of the two it is | pick another name; if a directory is there and you made it and it holds nothing you need, remove it; if a registration is left, `git worktree prune` removes it |
| 7 | `git fetch origin` fails | the command and its exit status, with git's message after the next action | check the network, the remote and the credentials; if git's message names a lock, tell the user, since a lock left by a git process that died does not clear by itself; otherwise, if you cannot fix the cause, tell the user git's message |
| 8 | No `origin/main` after a fetch that succeeded | how many `origin/*` refs exist, and up to ten of their names | check that `origin` is this project's remote |
| 9 | `git worktree add` fails for any other reason | the command and its exit status, and whether the branch and the worktree path exist after the failure, with git's message after the next action | if the fact line says neither exists, fix the cause git's message names, then run the script again; if either exists, tell the user git's message and the fact line, and remove nothing: another agent-session's run with the same name at the same moment leaves the same facts, and nothing tells the two apart |

Row 3 reports the name alone: `git check-ref-format` signals rejection through its exit status and prints nothing (measured: zero bytes on stderr), so there is no git message to pass on.

**Row 5 exists so that the refusal comes before the fetch.** Measured: with branch `foo` present, `git worktree add -b foo/bar <path> origin/main` fails with "cannot lock ref 'refs/heads/foo/bar': 'refs/heads/foo' exists", and creates no directory. The inverse fails the same way: with `baz/qux` present, plain `baz` cannot be created. Both names pass `check-ref-format` and neither exists as a branch, so rows 3 and 4 do not catch them. Git's own message names both branches, but without row 5 it arrives only after a network fetch, as row 9. The collision is between slash-separated path components, not string prefixes: with `foo` present, `foobar` creates without complaint. The row is detected by listing `refs/heads/` and comparing components.

**Row 6 exists because git leaves a branch behind.** Measured 2026-10-30 with git 2.53.0: when a non-empty directory already exists at the path, `git worktree add -b` exits 128 with "already exists" **after** creating the branch, so a rerun with the same name then fails at "a branch named ... already exists". Git refuses a path registered to a worktree whose directory is gone, "a missing but already registered worktree", at the same point, also leaving the branch behind (measured). The script checks the path on disk and in `git worktree list --porcelain` before running `git worktree add`, and refuses any existing file or directory there, empty or not, so that the refusal changes nothing.

Rows 4 and 5 consider local branches only. A name that exists solely as `origin/<name>` is created here without objection. When that remote branch holds commits `origin/main` lacks, the first push of the new branch is refused as a non-fast-forward; when its tip is already in `origin/main`, as for a merged branch whose remote copy was not deleted, the push fast-forwards it without complaint, and the new pull request reuses the old branch name. Accepted: refusing on remote names would block that ordinary reuse, and the fetch has just made the remote refs available for a caller who wants to look.

Row 8 reports a count and some names rather than the configured URL of `origin`. A remote URL can carry a token or password in its authority component, and this fact is printed to stderr and into agent transcripts. So before passing on git's message in any row, the script replaces the user-information part of every URL in it, the text between `://` and `@`, with `***`; that is the one change it makes to git's text.

**Row 9 is the catch-all.** It covers a branch ref that git cannot lock because a `.lock` file exists, left by a git process that died or held by one still running (measured with a left file: no branch and no directory are created), a full or read-only filesystem, and a `post-checkout` hook that exits nonzero (measured: `git worktree add` exits 1 **after** the branch and the topic-worktree exist, and the worktree is listed by `git worktree list`).

**The state guarantee.** On a refusal from rows 2 through 8, and from row 9 when the fact line says neither the branch nor the worktree path exists, this run has created no branch and nothing at the worktree path, and has not changed the caller's HEAD, working tree or index or any branch under `refs/heads/`. Other agent-sessions working in the same clone can change branches meanwhile; the guarantee is about this run's own effects. Row 9's other cases do not carry that guarantee, and the design does not pretend otherwise: after a failing hook the branch and the topic-worktree exist, and a filesystem that fills partway through can leave a partial directory. So after a row 9 failure the script checks whether `refs/heads/<name>` and the worktree path exist, separately, and says which in row 9's fact line, rather than promising nothing happened or leaving the caller to find out.

Refusals 7 through 9 follow the fetch, which does change repository state: remote-tracking refs under `refs/remotes/`, tags under `refs/tags/`, `FETCH_HEAD`, reflogs, and new objects. That is stated rather than hidden: it is not state a caller's work sits on. The `refs/heads/` half of the guarantee, and the claim that the fetch brings `origin/main` up to date, assume that `origin` has the conventional fetch refspec `+refs/heads/*:refs/remotes/origin/*`, which this project's clones use, and that `origin` has a `main` branch.

**Project identity is not checked.** Rows 2 and 8 establish a git checkout with an `origin/main`; they do not establish that it is *this* project. Run by an absolute path from inside an unrelated repository that has an `origin/main`, the script creates a branch and a worktree under that repository's `.claude/worktrees/` and reports success, and only the worktree path in the success line says which repository it happened in. Accepted rather than overlooked: the check would need a pinned remote URL or a marker file, and every agent-seat works in this one project. Reopen when an agent-seat works in two projects at once; the person to notice is whoever adds a second project to an agent-seat's seat-brief.

## What it deliberately does not do

- **Stacked work.** Work that builds on an unmerged nc-topic-branch must start at that branch, not at main. This script always uses `origin/main`, the scope the user approved, so that case is done by hand, once the parent branch has been pushed: `git fetch origin`, stopping if it fails, then `git worktree add -b <name> <reference-checkout>/.claude/worktrees/<name> origin/<parent-branch>`. Starting at `origin/<parent-branch>` takes the parent's pushed head, which also exists when the parent was made on the other machine or by another agent-seat. The worktree goes in the managed area like any other, because the worktree location hook will refuse a new branch's worktree outside it whatever its start point. A worktree made by hand gets no owner file from this script; "Deferred-decisions" lists what writes one. The pull request is opened with the parent branch as its base branch, `gh pr create --base <parent-branch>`, and its description says which pull request must merge first; when merge-lane-2 merges the parent's pull request, `scripts/merge-lane-pull-request-merge-through-merge-gate-with-stacked-pull-request-retarget.py` first retargets the open pull requests based on the parent's branch to the parent's own base branch. Nothing checks that a parent branch is not rewritten while another branch is built on it. No flag here: a flag invites use when the start point should have been main.
- **Committing, pushing, or opening a pull request.** One script, one job.
- **Removing the topic-worktree.** The cleaner removes topic-worktrees; this script only makes them.
- **Naming conventions.** `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md` says how a name is chosen and checked, and `CLAUDE.md` says to apply it. Whoever chooses the topic name applies that before calling this. The script enforces only git's own ref rules, which are mechanical (rows 3 and 5).

## Where it sits in the code-prompt-code structure

Code-prompt-code (CPC) is defined in `docs/nedschorus-wiki/nedschorus-glossary.md`, and `CLAUDE.md` states its rule: a step that needs no judgment goes in code, and a model is given only work that needs judgment.

This script is all code. It chooses among outcomes by facts it can read: its arguments, what is on disk, and what git reports. No outcome depends on judgment. The judgment stays with the caller: which topic to start, what to name it, whether the work is stacked.

Piece 2, a check at pull-request creation that refuses a branch carrying another open pull request's commits unless the pull request declares the dependency, would be code too; it is proposed in this GHI but not designed. Its mechanism is undecided and its design would be a separate document. Until it exists, this script is a convenience the caller can bypass by typing git directly, and the worktree location hook will not change that, since it checks the path and not the start point: the prevention the script offers is real but voluntary, and nothing makes it the only path.

## Value across gatekeeper activation

While the main-gatekeeper is dormant, agent-created nc-topic-branches are the ordinary way the agent-seats' work reaches main. One historical exception is on record: the gatekeeper's first live check-in landed commit `b24e376` on 2026-08-18, user-authorized, before main's protection was measured to require a review. The gate has been dormant since, and the PR process in `CLAUDE.md` — branch, pull request, merge-lane review — governs every agent change.

After activation the script has a narrower use. Per `nc-systems/main-gatekeeper/main-gatekeeper-design.md`, the gate builds each change in its own private workspace from main, so a caller creates no branch for an ordinary change; the gate opens the pull request, which means it creates that pull request's head branch itself. Two cases still need an agent-created nc-topic-branch: the gate's own source, since the gate refuses check-ins touching `nc-systems/main-gatekeeper/main-gatekeeper.py` (`gatekeeper-source-refused`) for as long as that refusal stands, which this script serves; and stacked work, which the gate's build-from-main design does not serve either, and which is made by hand, as "What it deliberately does not do" says.

## Testing

`scripts/topic-worktree-from-origin-main-create-test.py`, the nc-test-suite beside the script. Each case builds its own throwaway fixture: a bare repository as `origin`, a clone of it on `main` as the reference-checkout, and a linked worktree of that clone outside its `.claude/worktrees/` as the caller's checkout, standing in for an agent-home. Each case runs the script as a subprocess, as `nc-systems/main-gatekeeper/tests/main-gatekeeper-test.py` runs its program, and gives it a timeout, which that suite's ordinary helper does not; a case that times out fails. Nothing further about the structure of the new nc-test-suite is required here.

**The central case.** `origin/main` is at commit M; the caller's checkout stands on a branch whose tip is a different commit T. Run the script from the caller's checkout. Assert exit 0; the success line on stdout naming the new branch, M's full sha and the worktree path; that the new branch points to M and not T; that the topic-worktree exists at `<reference-checkout>/.claude/worktrees/<name>` with the new branch checked out; and that the caller's HEAD and branch tip are unchanged. The tips must differ or the assertion proves nothing about start point selection.

**The central case's mutant.** One case of the nc-test-suite runs a mutant, a deliberately broken variant of the script, to prove the central assertion can fail; it does not replace the nc-mutation-testing `CLAUDE.md` asks for on the script's failure-handling code. The script's worktree command is written so the start point is one element of its argument list, and the mutant is built by dropping that element, not by editing the script's text: the test imports the script's `worktree_add_command(name, path)` helper, checks that `origin/main` is one of the elements it returns, and then runs, as a subprocess, a short wrapper that loads the script as a module, replaces the helper with one that returns the original's list without `origin/main`, and calls the script's entry point. Deleting a list element cannot leave an empty argument, which a text substitution could, and the membership check fails loudly if a later edit renames or restructures the helper. Without a start point `git worktree add -b` bases the branch on the caller's HEAD (measured), so the mutant, run against a **freshly built fixture** under a fresh name, must exit 0 with a new branch that points to T: the mutant must fail the start point assertion rather than erroring, or it witnesses nothing about start point selection.

**The path case.** Run the script from inside a topic-worktree that an earlier invocation made, and from a subdirectory of the caller's checkout by the script's absolute path. Assert that each new topic-worktree is created under the reference-checkout's `.claude/worktrees/`, not under the checkout the script ran from.

**The `--help` case.** Assert exit 0, a line starting with "usage" on stdout, and that nothing was created.

**One case per row**, asserting the exit status (2 for row 1, 1 for rows 2 through 9), that stderr's first line names the fact and the lines after it the next action, and that stdout is empty. For rows 3 through 9, except row 9's hook case and its injected full-filesystem case, it also asserts that nothing exists at the worktree path that was not there before and that the caller's HEAD, branch tip, working tree and index and every ref under `refs/heads/` are as they were before the run, so that for row 4 the existing branch is still there and for every other row no branch of the name exists. Refs under `refs/remotes/` and `refs/tags/`, `FETCH_HEAD`, and the object store are excluded, per the state guarantee. Row 1 gets two cases, one for each of its conditions. Row 2 gets two cases, an empty directory that is not a checkout and a bare repository, each asserting exit 1, the message, and that the directory is unchanged. Row 4 gets two cases: the branch checked out in another worktree, asserting that the fact names that worktree; and the branch checked out nowhere, asserting that the next action names the `git worktree add` command. Row 5 gets both collision directions. Row 6 gets three cases, an empty directory, a non-empty one, and a registration whose directory was deleted, each asserting that no branch was created.

Rows 7 and 9 also assert that git's message survives after the fact and next-action lines, since truncating it is the failure the contract exists to prevent. Row 7 gets one more case, whose `origin` URL carries `user:token@`, asserting that `token` does not appear on stderr.

**Row 9's tested cases**: the `.lock` file, with the state assertions above; a `post-checkout` hook that exits nonzero, set through `core.hooksPath` in the fixture, asserting that the script exits 1, reports git's message, and says that the branch and the worktree path exist, with no claim that nothing changed; and, for the full-filesystem case, which cannot be caused in a fixture, an injected failure of `git worktree add` after which only the branch exists, asserting that the fact line says the branch exists and the path does not, so that the two facts are shown to be checked separately.

**The exit 3 case.** An injected exception after `git worktree add` succeeds, asserting exit 3, a traceback on stderr, and an empty stdout.

**One case that the caller's uncommitted work stays put**: a modified tracked file and an untracked file in the caller's checkout, asserting exit 0, that both are still in the caller's checkout with their content, and that the untracked file is absent from the new topic-worktree.

The owner file gets its cases when its name and format are settled.

## Deferred-decisions

- The owner file's name and format, and how the script learns which agent-seat to name in it, to be settled by the cleaner's build of item 1.1.2, which defines the file; with them, what the script does when it cannot write the file after `git worktree add` succeeded, and what writes an owner file into a worktree made by hand, such as a stacked-work worktree or the one row 4's next action makes, which the ruled cleaner otherwise leaves alone and lists in its daily report.
- What the caller does after a run that was killed or interrupted, as opposed to an exit 3, when neither the branch nor the topic-worktree exists: such a run leaves no traceback and may succeed when run again; to be settled when the script is built.
- What the script does when a git command that is not itself a row fails or prints what the script cannot parse: listing local branches for rows 4 and 5, `git worktree list --porcelain` for rows 4 and 6, and the `git rev-parse` after the add that fills `<sha>`; to be settled when the script is built.
- That a lone `--help` is answered before row 2 and before any git command, which `scripts/every-repository-program-help-option-test.py` needs, since it runs `--help` outside a checkout with `git` stubbed to fail; to be confirmed when the script is built.
- Exactly which text the credential redaction replaces in a message holding `://` and a later `@` that is not user-information, and how the row 7 test makes git print a URL that still carries its user-information; to be measured and settled when the script is built.
- Which condition wins when row 4's branch exists and row 6's path is occupied, and what row 6's next action says for a registration that `git worktree prune` does not remove, such as a locked one; to be settled when the script is built.
- How many times the caller reruns the script after row 9 before telling the user; to be settled when the script is built.
- What the stacked-work procedure does when its `git worktree add` fails or `origin/<parent-branch>` does not exist; to be settled when the script is built.
- Whether the script clears the variables that tell git which repository to use, such as `GIT_DIR` and `GIT_WORK_TREE`, inherited from its caller, and whether it refuses a checkout whose git directory was made with `--separate-git-dir`; to be settled when the script is built.
- Whether the start point is written as `refs/remotes/origin/main` rather than `origin/main`, so that a local branch or tag of that name cannot be chosen; to be settled when the script is built.
- How the owner-file cleaner finds a worktree's pull request, and so whether a topic-worktree this script makes under a name reused from a merged pull request's branch can be removed before its first edit; to be settled by the cleaner's build of item 1.1.2.
- What the script does when a directory above the worktree path, in the managed area, is a file or another worktree, as for `feature/parser` when `.claude/worktrees/feature` is a file or a worktree; a file there makes `git worktree add` fail as row 9, and whether git accepts a worktree nested inside another was not measured; to be settled when the script is built.
- How rows 4 to 6 compare names on the Mac, whose default filesystem ignores case, where a loose ref `refs/heads/Foo` and a new name `foo` collide on disk though their names differ; to be measured and settled when the script is built.
- The timeout on `git fetch origin` and on `git worktree add`, which can wait on an askpass program, an ssh prompt or a `post-checkout` hook, to be set from the durations of the script's first invocations.
- The mechanism of piece 2, the pull-request-creation check, which would need its own design document before anyone builds it.
