# Ask for the root cause at the moments a defect is fixed: fix pull requests, review fix-rounds, and code fixed a third time

## Problem

When an agent fixes a defect it usually fixes the case in front of it, and the same kind of defect returns elsewhere. CLAUDE.md now says to look for the root cause, but a standing instruction among many is easily lost in the middle of a fix, and no phrase reliably marks the moment: agents seldom write "root cause", and a defect can be fixed without the word "bug". The question has to arrive from outside the agent's memory, at the moment of the fix: from a program, or from the review every pull request already gets.

## The design

Four moments, each where the work happens: the first two ask the author for the root cause, the third shows the reviewer the earlier fixes to the lines a pull request changes, and the fourth makes sure a cause left in place is worked on.

1. **A pull request that fixes a defect.** Whether a pull request fixes a defect is a judgement: a test that fails on main and passes on the pull request's head commit marks a feature as often as a fix. So the judgement goes to the agent that already reads every pull request: the pull request reviewer instructions, `docs/agents/pr-reviewer-instructions.md`, ask whether the pull request fixes a defect, and if so whether its description carries, for each defect it fixes, a line, either `#root_cause <the reason the defect could happen at all, and what removes it>` or `#root_cause_not_fixed <why, and what the root cause is or that it was not found>`; the `#root_cause_not_fixed` line also carries `#follow_up` and a link, as item 4 says. A fix whose description lacks the line gets a finding that blocks the merge until the author adds it. The section "A pull request that fixes a defect" in `docs/agents/pr-reviewer-instructions.md` carries this; CLAUDE.md has no copy of the section, and CLAUDE.md's root-cause sentence tells authors where the line goes. Adding the line to the description settles the blocking finding without a new commit. Whether the reason given is the real root cause is the reviewer's to judge, not the program's.

   A root cause that lies in agent-instructions, such as a prompt, or in a design gets no blocking finding: the reviewer reports a finding that does not block and names that file as where the cause sits, and says nothing about its English. 2. **A review that carries findings.** The review that merge-lane-2 posts on a pull request with findings ends with one sentence asking the author, for each finding the author fixes, whether the finding is one case of a wider pattern, and to name the pattern in the fix commit's message. The author's forked subagent reads that review when it starts the fix-round, so the question arrives with the findings. A finding answered as not holding needs no such line.
3. **Code fixed a third time.** When two or more earlier merged pull requests whose description carries a `#root_cause` line, or its older `Root cause:` form, changed the same range of lines that a pull request changes, the reviewer's brief names the range and those pull requests in one fact line. Two earlier fixes to the same lines suggest each treated a symptom, and the reviewer, who otherwise sees one pull request at a time, judges whether this one does too. `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` builds the line from git, with no model: for each range of lines at the merge base that the pull request changes or deletes, `git log -L` along main's first parents finds the pull request merges that changed the range, and the merged pull requests' descriptions, which the program already reads from GitHub once per invocation, say which carry the line. `scripts/merge-gate.sh` prints no note about these lines: it runs at the merge, too late for the author to act on one, and it already makes every description say whether the pull request fixes a defect.    Part 3 finds code fixed repeatedly; it does not find process root causes, where a weak instruction let a defect through. design-to-main has the nearest mechanism: when a later step fails on an input that passed an earlier writer's input check, the failure shows which check that writer's checklist lacks, and whoever builds design-to-main adds it; the running machine does not (`docs/design-to-main/design-to-main-state-machine-design.md` § 4). design-to-main's build is paused, and design-to-main covers only work that goes through it.

4. **A cause left in place, after the merge.** A `#root_cause_not_fixed` line carries `#follow_up` and the full link to its follow-up: the issue or pull request that will fix the cause, or, when the cause is not known, an open issue that looks for it. `scripts/merge-gate.sh` refuses the line without that link, and refuses a link to an issue closed as not planned or a pull request closed without merging. After the merge, only the reviewer's brief reads the line again, `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` listing a merged pull request whose not-fixed line links to an issue that a later pull request closes; nothing makes anyone work the follow-up. Of the 27 not-fixed lines merged by 2026-10-15, written before a link was required, none linked work that would remove its cause, and twice an open issue for the cause existed and the fix still took five pull requests. Two things follow:
   - **The author is asked to fix the cause next.** `scripts/merge-gate.sh` prints, in its pass output, each `#follow_up` link to an issue in this repository that is still open. A link to an open pull request is not printed, because that work is already under way, and a link to another project is not printed, because that work is not ours. merge-lane-2 adds each printed issue to the message it sends the author when the pull request merges, and the author answers with one of: the pull request that fixes the cause; the agent-seat that will; "blocked on <link>"; or "needs the user: <why>". Only the last reaches the user.
   - **A follow-up closed without being done reaches the user.** A daily maintenance-job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058), the daily list of root-cause follow-ups closed without being done, reads the `#root_cause_not_fixed … #follow_up <link>` lines of merged pull requests' descriptions, and lists each follow-up they name that was closed without being done: an issue closed as not planned, or a pull request closed without merging. Nothing is posted on the follow-up. The not-fixed lines merged before the link was required carry no link, so the job cannot find their causes; the agent-seat cold-read-improvement checks them once, and brings those whose cause is still in the code to the user in one approval-walk.

## Not in scope

A root-cause analysis document, a template beyond the one line, or a separate reviewer. The line is the whole record; the commit message and the pull request carry any detail.
