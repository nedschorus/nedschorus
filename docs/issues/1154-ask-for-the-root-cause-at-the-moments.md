# Ask for the root cause at the moments a defect is fixed: fix pull requests, review fix-rounds, and code fixed a third time

## Problem

When an agent fixes a defect it usually fixes the case in front of it, and the same kind of defect returns elsewhere. CLAUDE.md now says to look for the root cause, but a standing instruction among many is easily lost in the middle of a fix, and no phrase reliably marks the moment: agents seldom write "root cause", and a defect can be fixed without the word "bug". The question has to arrive from outside the agent's memory, at the moment of the fix: from a program, or from the review every pull request already gets.

## The design

Four moments, each where the work happens: the first three ask the author for the root cause, and the fourth makes sure a cause left in place is worked on.

1. **A pull request that fixes a defect.** Whether a pull request fixes a defect is a judgement: a test that fails on main and passes on the pull request's head commit marks a feature as often as a fix. So the judgement goes to the agent that already reads every pull request: the pull request reviewer instructions, `docs/agents/pr-reviewer-instructions.md`, ask whether the pull request fixes a defect, and if so whether its description carries, for each defect it fixes, a line, either `#root_cause <the reason the defect could happen at all, and what removes it>` or `#root_cause_not_fixed <why, and what the root cause is or that it was not found>`; the `#root_cause_not_fixed` line also carries `#follow_up` and a link, as item 4 says. A fix whose description lacks the line gets a finding that blocks the merge until the author adds it. The section "A pull request that fixes a defect" in `docs/agents/pr-reviewer-instructions.md` carries this; CLAUDE.md has no copy of the section, and CLAUDE.md's root-cause sentence tells authors where the line goes. Adding the line to the description settles the blocking finding without a new commit. Whether the reason given is the real root cause is the reviewer's to judge, not the program's.
2. **A review that carries findings.** The review that merge-lane-2 posts on a pull request with findings ends with one sentence asking the author, for each finding the author fixes, whether the finding is one case of a wider pattern, and to name the pattern in the fix commit's message. The author's forked subagent reads that review when it starts the fix-round, so the question arrives with the findings. A finding answered as not holding needs no such line.
3. **Code fixed a third time.** A fix pull request is a merged pull request whose description carries a `#root_cause` or `#root_cause_not_fixed` line, or, written before the labels became hashtags, a `Root cause:` or `Root cause not fixed:` line; both forms are read. When a pull request changes lines that two earlier fix pull requests also changed, `scripts/merge-gate.sh` prints a note, without refusing the merge, naming those two pull requests and asking the author to add one of item 1's two lines to the pull request's description. Two earlier fixes to the same lines suggest each treated a symptom. Item 3 follows the changed lines back with `git log -L`.

   Part 3 waits until two things are true: at least 10 merged pull requests carry a `#root_cause` or `#root_cause_not_fixed` line, or the older `Root cause:` or `Root cause not fixed:` form of it, and the user has ruled on the report of the research into kinds of root cause (it lands in `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/cold-read-improvement/root-cause-kinds-research-2026-10-10/`). Part 3 does not fit in one function of `scripts/merge-gate.sh`: finding the earlier pull requests that changed the same lines takes one GitHub read per earlier commit, and its test needs a git repository with real line history. When both are true, check this design first: merge-lane-2 copies the `#root_cause` or `#root_cause_not_fixed` line, or its older form, into the merge commit's message as it merges, so the note can find earlier fixes in git history without reading GitHub.

   Part 3 finds code fixed repeatedly; it does not find process root causes, where a weak instruction let a defect through. design-to-main has the nearest mechanism: when a later step fails on an input that passed an earlier writer's input check, the failure shows which check that writer's checklist lacks, and whoever builds design-to-main adds it; the running machine does not (`docs/design-to-main/design-to-main-state-machine-design.md` § 4). design-to-main's build is paused, and design-to-main covers only work that goes through it.

4. **A cause left in place, after the merge.** A `#root_cause_not_fixed` line carries `#follow_up` and the full link to its follow-up: the issue or pull request that will fix the cause, or, when the cause is not known, an open issue that looks for it. `scripts/merge-gate.sh` refuses the line without that link, and refuses a link to an issue closed as not planned or a pull request closed without merging. After the merge, only the reviewer's brief reads the line again, `scripts/merge-lane-pull-request-reviewer-brief-compose-with-facts.py` listing a merged pull request whose not-fixed line links to an issue that a later pull request closes; nothing makes anyone work the follow-up. Of the 27 not-fixed lines merged by 2026-10-15, written before a link was required, none linked work that would remove its cause, and twice an open issue for the cause existed and the fix still took five pull requests. Two steps follow each such merge:
   - **A comment on the follow-up.** Right after merge-lane-2 merges the pull request, a program, the comment program, posts a comment on the follow-up that quotes the line, under the first line `#root_cause_follow_up from PR <number>:`, so whoever works the follow-up sees the cause. merge-lane-2 builds the comment program, since it runs the merge. If the comment cannot be posted, the comment program says why and exits nonzero, and the merge stands.
   - **The author is asked to fix the cause next.** `scripts/merge-gate.sh` prints, in its pass output, each `#follow_up` link to an issue in this repository that is still open. A link to an open pull request is not printed, because that work is already under way, and a link to another project is not printed, because that work is not ours. merge-lane-2 adds each printed issue to the message it sends the author when the pull request merges, and the author answers with one of: the pull request that fixes the cause; the agent-seat that will; "blocked on <link>"; or "needs the user: <why>". Only the last reaches the user. merge-lane-2's seat-brief, `nedlern@ned-box:/home/nedlern/agents/merge-lane-2/CLAUDE.local.md`, already says to send each issue `scripts/merge-gate.sh` lists, but `scripts/merge-gate.sh` does not print such a list yet: on main at commit b15d9fecf it checks each link and prints nothing for a link it accepts. GHI [Programs for sixteen merge-lane-2 seat-brief steps that need no judgment](https://github.com/nedschorus/nedschorus/issues/2608), idea 7, would have a program write that message.

   A follow-up closed without being done comes to the user through the thirty-third maintenance-job of GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedschorus/nedschorus/issues/1058), which finds the follow-up by the comment. The not-fixed lines merged before item 4 is built get no comment; the agent-seat cold-read-improvement checks them once, and brings those whose cause is still in the code to the user in one approval-walk.

   Three questions about the comment are open. The agent-seat cold-read-improvement puts them to the user:
   - Whether a program may post the comment at all. `.claude/guard-hooks/ghi-issue-write-hand-typed-gh-command-refusal.py` carries the user-ruling of 2026-09-24 that agents write no issue comments, because agents forget to read them, and says there will be no comment operation; item 26.3, which approved the comment, did not mention that ruling. One alternative needs no comment: the thirty-third maintenance-job of GHI 1058 finds follow-ups from the merged pull requests' `#root_cause_not_fixed` lines rather than from the comment.
   - What happens when the comment program fails. The approved text, item 26.3 of the approval-walk cited below, has merge-lane-2 post the comment by hand, but that hook refuses a hand-typed `gh issue comment` on this repository. And a follow-up whose comment failed is never found by the thirty-third maintenance-job of GHI 1058. The choices include: merge-lane-2 runs the comment program again instead of posting by hand; or the thirty-third job finds follow-ups from the merged pull requests' `#root_cause_not_fixed` lines rather than from the comment, so that a failed comment loses nothing.
   - Whether a follow-up in another repository than this one gets the comment. `scripts/merge-gate.sh` passes a link to another repository on GitHub when it can read the linked issue or pull request, and a comment there would be posted on another project's issue or pull request, where item 4's second step does not reach.

## Not in scope

A root-cause analysis document, a template beyond the one line and item 4's comment, or a separate reviewer. The line is the whole record, apart from item 4's comment on the follow-up; the commit message and the pull request carry any detail.
