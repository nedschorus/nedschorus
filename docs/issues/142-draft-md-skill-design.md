# draft-md: a draft, first or later, of technical writing for a reader with zero context ([nedschorus#142](https://github.com/nedschorus/nedschorus/issues/142))

Specification for the `draft-md` skill: how a draft — the first, or a revision after review — gets written, in this project, of technical writing in six forms — a design, a wiki page, a skill, a GitHub issue body, a pull-request description, a prompt for another agent — each read by a reader with zero context: an agent whose context window holds nothing from the conversation that produced the text, or a human in the same position. Training, the repository, and the internet are not context in this sense; the conversation is, and the reader has none of it. It is the pair document for issue 142, which commissions the skill; the skill does not exist yet and is drafted from this document. `draft-md` is the one drafting skill: it replaces an earlier, larger design that this file's own history carries under the same name, and the `md-write` skill that the founding plan (retired; `git show 615a230:docs/cross-project/nedschorus-founding-plan.md`) named as the drafting skill to build. The skill ends when the draft is written; what the session then does with the file is outside it. This document is for writers: it says nothing about how a draft is reviewed.

Vocabulary used throughout. A **runtime** is the agent program a session runs in — Claude Code or Codex. A **session** is one running agent conversation. A **seat** is a session with a standing role and its own worktree, named for the role: the prof seat owns issue 142; the merge-lane seat reviews and merges pull requests. A **fork** is a subagent that starts with a copy of the session's whole conversation up to the moment it is spawned — messages, tool results, and the files the session read included. A **form** is a kind of technical writing the skill drafts. It has two levels, and they do not count the same. A form **value** is what an invocation passes and what the file's `form:` front-matter field carries: one of `design`, `wiki page`, `skill`, `issue body`, `pull-request description`, `prompt` — six of them. A form **entry** is one of the paragraphs under "The forms" below, which says who the reader is and where the text goes — four of them, because `design`, `wiki page` and `skill` are all durable files in the repository and share one entry; `issue body`, `pull-request description` and `prompt` have an entry each. The **reader** is whoever will act on the text with zero context — nothing from the conversation that produced it in its context window; each form names its reader and what the reader does have. **Cold** describes a reader with zero context. A **pair document** is the Markdown half of a document-plus-issue pair, the shape the founding plan gives every durable design.

## The idea

A draft of technical writing in any of the forms — the first draft, or a revision — is written by a fork, not by the interactive session, wherever the runtime can fork. Claude Code can; Codex is unverified, and "The sequence" says what that costs. At the point where the text would be written, the session invokes `draft-md`; the skill fills the prompt's slots and spawns a fork; the fork writes under the prompt below, rereads its draft against the prompt's list and fixes what fails, reports one line, and ends. The skill ends there.

Why a fork: focus. The session is in the middle of a conversation — open questions, other tasks, the user's next message — and writes with all of that competing for its attention. The fork holds the same conversation, but its context ends with one job: write this text, for this reader, checked against this list. Nothing else is live. A second reason: the session's context grows by the fork's one-line report and not by the writing, so the session then reads the finished draft as a file, holding the design and never having watched the text form, and judges it from the design and the text rather than from having authored it.

What the session does with the file afterward is outside the skill; the session reads the file before it uses it, and reads its "Questions the writer could not settle" section first: it answers what the design settles and takes the rest to the user, and the answers come back through the revision path as a list of changes, which removes the section when it is empty. That section is transient and never travels with the text. A durable file keeps it while the questions are open, because the file stays in the repository where the answers will reach it. For every other form the file is handed onward as a unit — `ghi-write` takes an issue body with `--body-file`, the session opens a pull request with a description, an agent receives a prompt holding nothing else — so the section is answered and removed before the text is delivered, alongside the front-matter the session strips. The name is deliberately not "Open questions for the user", which is a standing section other documents keep; this one exists to be emptied. A writer that has just tried to obey the design word for word is the one who finds where it does not decide; that is why the fork records its questions instead of guessing silently or stopping.

What the skill never decides is disposition — whether the text revises a document that already exists or starts a new one. That belongs to the skill that lands the text, because a document's fate is settled where it arrives: `ghi-write` for an issue, and for a durable file the pull-request skill, once it exists, since a durable file reaches main through a pull request. The founding plan carries the vocabulary those skills use. `draft-md` receives a path and writes to it.

A revision is a draft too, and the fork matters more there: by then the conversation also holds the review reports, the walk, and the rulings, all competing for the session's attention. A revision needs three inputs a first draft does not — the existing file, the list of changes to make (after a walk, the dispositions: each names the passage and the ruling), and the rule that the fork changes what the list says and nothing else, except that a change one ruling forces elsewhere — a renamed term, a cross-reference — is made and named in the report. The prompt's list applies to the text the fork writes or changes, not to untouched text. The fork applies rulings already made — by the user at a walk, or by the session at triage, where the session sorts a review's findings into the ones it applies, the ones it declines, and the ones it takes to the user. The fork does not judge review findings itself.

What this document depends on that is not yet on main: the design notes at `docs/issues/142-draft-md-skill-design-notes.md`, not yet landed and written by another seat, which carry the decision history behind its rules. The reasons for the rules are stated here; the notes hold who ruled what and when.

## The problem

A writing agent holds the whole conversation in its context window and writes as if the reader held it too. The reader — another agent or a human with the text and whatever sources its form names, and no conversation — gets prose that leans on what was said in the room: contradictions, ambiguity, instructions wrong when obeyed literally, missing prerequisites, tasks with no stopping point, over-broad absolutes, incomplete mechanisms, unsearchable names, omitted words and premises — and conflation.

**Conflation** is one word used for two different but connected things ("disagree", "disagreeable"), or two different things over-simplified or over-condensed into one inconsistent thing — often because the wording is partly consistent. On the surface conflated text can appear fluent, but it is a serious logical error, and it causes nasty problems when the conflated text is turned into actions or instructions. There is no test for conflation. So the writer writes clear and complete sentences: do not over-condense, do not conflate. That is what item 11 of the prompt asks.

## The forms

Whatever the form, the fork writes one Markdown file at the path the invocation names, and reports that path; the session adapts the file to its destination — the body of an issue, the title and body of a pull request, the text handed to an agent. Every file the fork writes begins with front-matter carrying `form:`, whose value is the form the invocation named, so that whoever picks the file up knows what it is for without reading it. `form:` is the first field, with one exception: in a skill it sits inside `metadata:` and `name:` leads, because that is what Claude Code's skill loader expects. A durable file's home may require more fields, as its entry says. Where a form's text has a title line — a pull-request description does — the title line follows the front-matter rather than opening the file. When the destination is not a Markdown file in the repository — an issue, a pull request, a prompt handed to an agent — the session strips the front-matter as it adapts the file, since GitHub and the receiving agent would otherwise read it as text.

No file on main carries `form:` today, so the first revision of any existing document meets two rules at once: this one, and the rule that a revision changes what its list says and nothing else. The revision adds the front-matter block when the file lacks it, names that addition in its report, and changes nothing else that the list did not ask for. That converts the corpus a file at a time, at the moment someone is already editing the file, rather than in a sweep nobody asked for. The list in the prompt is the same for every form; what changes is who the reader is and what the reader has, where the file goes, and what the form's home already requires. The skill fills the prompt's `<form paragraph>` slot from the entry the invocation's form value selects — `design`, `wiki page` and `skill` all select the durable-file entry; `issue body`, `pull-request description` and `prompt` each select their own. Once the skill exists, its copy of these entries is the one that runs, and this document describes it.

**Durable Markdown file.** The reader is a future agent or human with the repository and the file. The file goes where its kind already lives; the common homes are a pair document at `docs/issues/<issue number>-<topic>-<genre>.md` — genre is the kind of document: design, plan, report and notes are the ones in steady use, and the suffix is the convention for new pair documents rather than a closed list, since most of the corpus predates it and ends in the word that described it best. One genre costs something to choose: a document whose name ends in `-report` (or `-log`, or `-capture`) is refused by the cold-read grid under [nedschorus#152](https://github.com/nedschorus/nedschorus/issues/152), which rules that a document recording what happened is not reviewable text — so naming a file `-report` takes it out of that review path deliberately, and nothing stops a person reading it. The issue is linked in the pair document's title line, a wiki page under `docs/wiki/`, and a skill at `.claude/skills/<name>/SKILL.md`; a kind not listed goes where the repository already keeps that kind. `docs/drafts/` is a home too, with one job: it stages text whose own home is guarded against agents writing to it, or whose home is not yet decided because no issue exists yet. Everything else is born at its home carrying `status: draft`, so the draft state is marked by the field rather than by the directory and the file never has to move — which is what keeps links to it from breaking. A pair document is one half of a document-plus-issue pair, so for a pair document the invocation carries the issue number; a wiki page or a skill has no issue. Those three homes carry the three durable form values: `design`, `wiki page`, `skill`. After `form:`, a design carries `status:` — free text; the values in use are draft, specification, ruled, and landed — so the reader knows whether to obey it or treat it as a draft, and `design-as-of: <date>`. A skill carries the `name:` and `description:` Claude Code requires, where the description is the only part of the skill the model sees when deciding whether to invoke it, so it says when to use the skill and when not to. In a skill, `form:` goes inside `metadata:`, the free-form map Claude Code accepts, because that map is the portable place for a field the tooling does not define: Claude Code allows it and the claude.ai upload path allows it. Keep the value a plain string — Claude Code does not act on the map's contents and drops a value that is not a map, so nothing should be built that needs the loader to preserve more. The description is written as the moment of use — "Use BEFORE writing …", naming what triggers the skill and what must not — because the model chooses skills by matching that moment, and false-trigger tests (near-misses that share the keywords) are how the wording is checked. `when_to_use:` adds context for that choice when the description alone is too short. `argument-hint:` and `arguments:` name what the invocation takes, so the skill can be invoked as a command without a dialogue. Both are Claude Code keys only: the claude.ai upload and the `package_skill.py` packaging path accept six fields and reject these two, so a skill written to this specification does not travel that way without dropping them. A wiki page carries `form:` only. The fork reports the path.

**GitHub issue body.** The reader is the seat that picks the issue up, cold. Whether and how the issue is filed is the `ghi-write` skill's (`.claude/skills/ghi-write/SKILL.md`): it searches existing issues first and edits a body rather than stacking comments. The file is a scratch file in the session's scratchpad directory, which the runtime names per session, at a path the skill chooses; `ghi-write` takes it with `--body-file`. The body passes `ghi-write`'s three tests: the subject is identifiable from the issue alone, the why is stated, and the next action is one a reader who was not in this conversation can take. The fork reports the path.

**Pull-request description.** The reader is the merge-lane seat, reviewing cold, and later anyone reading the merged change. The file is a scratch file, as for an issue body; its first line is the title, which names the one topic the pull request carries, and the rest is the body, which says what changed and why, what the change depends on that is not yet on main, what was deliberately left out, and — when the change is runnable — how to see it working. The session appends the attribution footer the runtime instructs it to add (a generated-with line and the session link); the fork does not write it. The session opens the pull request with the file. The fork reports the path.

**Prompt for another agent.** The reader is the agent that receives the prompt, holding nothing but the prompt and what the prompt tells it to read. A durable, reusable prompt lives in its skill's `prompts/` directory. That directory is guarded — the instruction-file guard described in `docs/agents/fleet-instructions.md` keeps agents from writing there until the user has reviewed the text — so a prompt is the one form that stages in `docs/drafts/` first and reaches its home when he has. A one-off prompt is a scratch file, as for an issue body. Every value the caller supplies is an angle-bracket slot, such as `<path>`, filled before the agent sees the prompt; the agent never fills one (the convention of the ghi-info design, `docs/issues/46-ghi-info-agent-design.md` § "Prompts"). The prompt states what the agent reports back and in what form, including what it says when nothing happened. Rulings and provenance about the prompt go in the prompt's governing document, not in the text the agent reads. The fork reports the path.

## The prompt

The list in the prompt is the writer's side of the defects named under "The problem" — the ones a reader with zero context meets — as things to do, one or two lines each, with what a durable artifact in this repository has to carry folded in, so that the prompt stands in one place and the fork receives it whole: the prompt names no other file of rules, because the fork holds nothing but the prompt. The skill fills the angle-bracket slots before the fork sees the prompt; the fork never fills one.

> You are writing <the form> at <path>. It covers: <one sentence>. You hold the design from this conversation; the reader has zero context — its context window holds nothing from this conversation. <When the invocation named a design file: "The design is also in <design file>."> <When revising: "The file exists at <path>. Make these changes and no others: <the list>. A change one of them forces elsewhere — a renamed term, a cross-reference — you make and name in your report."> <form paragraph: who the reader is and what the reader has, where the text goes, what its home requires>. The reader is an experienced software engineer, human or agent, who prefers standard SDLC terms. Everything the reader needs that the reader's sources, named above, do not supply is written in this text, where it is first needed.
>
> Draft by answering the reader's question: identify the question the text exists to answer, answer it as if a colleague asked — one concrete case first — and keep the sentences you would say. The answer, not the question, becomes the text. Use standard SDLC terms, and no coined vocabulary where a standard term exists. Where a reader stumbles on a sentence — what it means, or what it explains, recommends or dictates — expect every later reader to stumble in the same place: rewrite the sentence rather than assume it is clear because you wrote it. When the draft is written, reread it once per item below and fix what fails; then report.
>
> 1. **Opening.** The first paragraph names the text, its reader, and its purpose.
> 2. **Reasons.** Every rule or decision states why it exists, in one sentence; the reason is what lets the reader judge a case you did not anticipate.
> 3. **Stopping points.** A step is what you tell the reader to do. Every step you set states when it is done.
> 4. **Outputs.** When the text defines steps for an agent, each step says what it produces, including when nothing happened.
> 5. **Mechanisms.** A mechanism is what the text says the system does. For each mechanism, say what happens in every state it can reach, every failure, and every limit, or name the ones you leave out of scope.
> 6. **Absolutes.** "Never", "always", "every", "all", "cannot" can backfire in conditions you did not foresee. Before you write one, look for an exception; if you find one, name it or soften the wording.
> 7. **Names.** Use the repository's existing name for a thing. For a new name, grep inside files and glob for paths first; a collision or an ambiguity means a more explicit name. Make it multi-part and self-describing. Explain it where it first appears. One name per thing; if you change a name, say so once and use the new one after.
> 8. **Referents.** "It", "this", "that", "the change" may stand for something in the same sentence or the one before; otherwise name it.
> 9. **Explanations.** If you would have to explain a phrase to the reader, write the explanation in the phrase's place; a name explained where it first appears then stands on its own.
> 10. **Omissions.** Do not leave out a word, a step, or a premise because it is obvious to you. The test is whether the reader defined above can supply it. If a sentence only works with an unstated premise, state it.
> 11. **Conflation.** One word used for two different but connected things, or two different things over-condensed into one inconsistent statement that reads fluently because its wording is partly consistent. There is no test for it. Write clear and complete sentences: do not over-condense, do not conflate. When you reuse a word for something else, decide whether it is the same thing; if not, give the second thing its own name.
> 12. **Body.** One paragraph per line, no hard wraps. In a durable file, the body below the title line and front-matter holds instructions, their reasons, and examples — nothing about how it came to be: no dates, issue numbers, or who ruled. Two things this does not forbid. Ruling stamps already in the text — `(user-ruled <date>)`, and older blocks stamped `boss-ruled` — which a revision leaves exactly where it finds them; adding one to a sentence that binds is retired, because a rule binds by being in the document that governs, and a stamp on it is a second handle for other documents to cite it by. How a reviewer is told that something is already settled is a separate mechanism, being redesigned; no reviewer prompt mentions stamps today. And the transient questions section of item 14, which leaves when its questions are answered.
> 13. **Literal reading.** Read each instruction as a reader who obeys it word for word; if that reading is wrong, or two readings are possible, rewrite it.
> 14. **Questions.** Where the design or your sources do not settle something you need, choose the reading you think right and write under it; then record the question in a closing section, "Questions the writer could not settle" — what you had to decide, the reading you chose, and what would change under the other. Nobody can answer you while you write, so the question travels in the file, not in your report. Record an instruction on this list you could not carry out the same way, saying which and why: one reread per item is the limit, and an item you cannot satisfy is a question, not a silent pass.
> 15. **Accepted residuals.** Where the text records a review objection the user overrode — a risk accepted, a mitigation declined — write it at the decision point as the named block the founding plan defines: `Accepted residual (user-ruled <date>):` the objection in one line, why it is not a concern for this project, and the reopening trigger. One grep on `Accepted residual` has to return every such decision, which is why the block is written the same way every time.
>
> Report back, and keep it to the shape below. First line: the path you wrote, and the number of questions you recorded, 0 if none. For a revision, one line per change after it — its number, and either `applied` or `not applied` with the reason in a few words — and a line for any change you made that the list did not ask for, which one forced it. If you could not write the text at all, say why instead. Nothing else.

## The sequence

1. **Invoke.** The user or the session invokes `draft-md` with the form (one of the six `form:` values), the target path (for an issue body or a pull-request description, a scratch path the skill chooses), the one sentence the text covers, the issue number for a pair document, and, when the conversation does not hold the design, the path of the file that does; for a revision, the path of the existing file and the list of changes, numbered, each naming the passage and the change — the numbers are what the fork's report refers to. The skill fills the prompt's slots and spawns a fork.
2. **Write.** A first draft whose target path already holds a file is refused: the fork reports that the path is occupied and writes nothing, because overwriting a landed document is the one mistake this skill must not make silently, and revising it is what the revision path is for. The fork writes the draft — or applies the listed changes to the existing file — under the prompt, rereads what it wrote once per item and fixes what fails, reports one line (the path and the count of questions for the user), and ends. In Claude Code the fork is the Agent tool with `subagent_type: "fork"`, run in the background; its line arrives as the tool's completion notification, and the session does not poll for it. It is not the `context: fork` key a skill's front-matter can carry: that runs the skill's body in a subagent with no conversation history, which is the opposite of what this skill needs. On Codex, `spawn_agent` with `fork_turns: "all"` is reported to copy the conversation the same way; the first build verifies that before running the skill there, and until it does the skill runs on Claude Code only.
3. **Done.** The skill has nothing further.

A question is not a failure: it goes in the file's closing section and the report counts it. Two failures are reachable. The fork's report does not name a written file at the invoked path — it says why it could not write, or reports an error, a refusal, or an occupied path: the session invokes the skill once more, and if the second fork also fails, the session writes the text itself under the same prompt and says so where the text is delivered. The test is what the report says, not how many lines it runs to; a revision's report is several lines by design. The fork ends without reporting — a crash or a timeout, which the runtime reports as a failed task: the session treats it the same way. Text a fork returns beyond its one line is words about the process, not the draft, and stays in the session's context without harm.

How the skill gets invoked, by form. An issue body: the `ghi-write` skill invokes `draft-md` for the body before it files. A pull-request description: the pull-request skill, once it exists, invokes `draft-md` for the description. A durable file — design, wiki page, skill: a PreToolUse hook soft-blocks a write the session makes itself and names `draft-md` as the path; which tools it watches and how much written text trips it are set by its own design at `docs/issues/queue/draft-md-durable-file-write-hook.md`, not here, because the floor is to be settled by watching false triggers after the hook lands; a file the skill's fork has just written carries a marker with its content hash, so the same content is never asked for twice, and working material under `docs/issues/queue/` never triggers. The hook is built after the skill exists (its design is queued at `docs/issues/queue/draft-md-durable-file-write-hook.md`). A prompt for another agent: no trigger yet; the session invokes the skill by name.

## Testing the prompt

Nothing the research report (under "Where this lands") found measures whether a list like this changes what a writer produces, and the project has one asset that makes it measurable: transcripts in which the user has already found and named conflations, kept in `md-review-records/` on the machine the prof seat runs on (machine-local working material, gitignored). The experiment from that labelled set: for each labelled conflation, take the transcript up to just before the passage, regenerate the passage several times with and several times without the prompt's Conflation item, and let the user judge each regeneration for whether the same two things are again treated as one. The labels say where conflation occurred; the user's judgment of each regeneration is the measurement. The set grows as the user finds more; a run of the experiment names the set it used.
