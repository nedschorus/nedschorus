# Baseline timeout in mutation testing of a module with many dependent test suites is reported as failing suites

## What is wrong

`scripts/pull-request-mutation-testing-survivors.py` runs mutation testing with cosmic-ray on the lines a pull request changed. Its option `--mutant-timeout-seconds`, default 300 (`DEFAULT_MUTANT_TIMEOUT_SECONDS`), becomes the `timeout` of the cosmic-ray config that `cosmic_ray_config_text()` writes. cosmic-ray applies that timeout to the whole test command (`run_tests()` in cosmic-ray's `testing.py` waits on the command with `timeout=`), and the script's test command, built by `test_command_for()`, runs every test suite that depends on the module, one after another, from one script file. So the limit is on the whole chain of dependent suites, not on one suite, and a module that many suites depend on can need more than 300 seconds for the chain even when every suite passes.

The first place this shows is the baseline: `mutation_test_one_file()` runs `cosmic-ray baseline` on the unmutated code before any mutant. When the chain runs past the timeout, cosmic-ray records the baseline as killed, with the output `timeout`, and exits 1. The script then exits 2 with the message that the suites for the module "fail on the unmutated head, so no mutant can be judged", although no suite failed. The script already tells a timeout apart from a kill for a mutant (`TIMED_OUT_OUTPUT` in `outcomes_from_dump()`, printed as ERRORED with the advice to rerun), but not for the baseline.

## Reproduction


Under the default timeout of 300 seconds, the command exits 2. It prints `pull-request-mutation-testing-survivors: not run — the suites for nc-systems/general-tools/failed-command-agent-facing-message-rerun-once-then-stop-and-report-lines-common.py fail on the unmutated head, so no mutant can be judged`, then the list of suites, then cosmic-ray's log message `Baseline failed. Execution with no mutation gives those following errors:`, whose one error line is `>>> timeout`. The output of this test run, made on 2026-10-25 at main d6221151, is at `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/reboot-test/mutation-testing-survivors-baseline-timeout-2026-10-25/rerun-at-default-300-seconds-timeout.out`.

The agent-seat reboot-test ran the same command with `--mutant-timeout-seconds 2400` on ned-box on 2026-10-25. That test run exited 0, with 15 of 15 mutants killed, in about 25 minutes; its output is not in the log-store: `grep -rl "mutant-timeout-seconds 2400" /home/nedlern/nedschorus-logs` on ned-box on 2026-10-25 found no file. A test of cosmic-ray's own `baseline` with a timeout of 1 second and the test command `sleep 5`, on ned-box, exited 1, and `cosmic-ray dump` of its session file then showed the result killed, with the output `timeout`. The module the command mutates, `nc-systems/general-tools/failed-command-agent-facing-message-rerun-once-then-stop-and-report-lines-common.py`, has 71 dependent test suites.

## Why it matters

CLAUDE.md requires code that handles a failure to carry a test checked by mutation testing. For a module that many suites depend on, especially the shared `-common.py` modules, the script stops before any mutant under the default timeout, and its message sends the author looking for a failing suite that does not exist. An author who does not guess that the timeout is the cause falls back to hand-made mutants, as on pull request [git_failure_next_step_lines takes program only with the misspelt-name line](https://github.com/nedschorus/nedschorus/pull/1937). The script does exit 2 and say it did not run, so nothing passes silently; the cost is the missing mutation testing and the misleading message.

## Next action

Parts 1 to 4 below are built; see Outcome. What remains is to close this GHI once the edit that records the Outcome has merged and its edit-GHI rerun has finished.

Change `scripts/pull-request-mutation-testing-survivors.py`, its tests in `scripts/pull-request-mutation-testing-survivors-test.py`, and the project's test runner `scripts/run-all-test-suites.py` with its tests, in the parts below. The test of the whole change: the reproduction above, run on ned-box without `--mutant-timeout-seconds`, exits 0. Record that test run's exit code and the number of survivors it prints (mutants no suite killed) under a new heading, Outcome, in this GHI-MD, which is `docs/issues/<this GHI's number>-…` once filed, through the edit-GHI operation of `scripts/ghi-issue-write.py`. If it does not exit 0, record what it printed instead and leave this GHI open.

Two facts about cosmic-ray, from its source in `/tmp/cosmic-ray-venv` on ned-box (`run_tests()` in `cosmic_ray/testing.py`), shape the design. When the test command runs past cosmic-ray's own limit, the `timeout` key of the cosmic-ray config, cosmic-ray records the run as killed with the output `timeout`. When the test command exits nonzero, cosmic-ray records it as killed with the command's standard output as the output. Below, "cosmic-ray's limit" is that config key, and "a suite's limit" is the time limit the test runner gives each suite.

1. Teach the test file's fake cosmic-ray to produce a timed-out baseline, and add cases for Parts 2 and 4. The fake's `dump` command already prints the plan's `baseline_dump` for the baseline's session file whatever the plan's `baseline_exit` was, so a plan with `baseline_exit` 1 and a `baseline_dump` whose result is killed with the output `timeout`, or with the test runner's time-out line as its output, is a timed-out baseline; give the fake whatever else the cases need, such as a way to stand in for the test runner. Cases: (a) a baseline killed with the output `timeout` exits 2 with Part 2's message and without the word "fail"; (b) a baseline killed with the test runner's time-out line as its output exits 2 with Part 2's message naming the suite; (c) a mutant killed with that line as its output is reported as ERRORED with the suite named, not as killed.
2. Report a baseline timeout as a timeout. cosmic-ray writes the baseline's result to the session file given with `--session-file` before it exits 1, so when `cosmic-ray baseline` exits nonzero, read that session file with `cosmic-ray dump`, as the script already does when the baseline exits 0. When the baseline's result is killed with the output `timeout` (`TIMED_OUT_OUTPUT`), the script still exits 2, but its message says that the suites ran out of time on the unmutated code, gives cosmic-ray's limit in seconds, and says to rerun with a larger `--mutant-timeout-seconds`. When the output instead carries the test runner's time-out line, which Part 4 makes possible, the message names the suite that ran past its limit and gives that limit. Neither message says the suites fail. A baseline killed with any other output is a real failure and keeps today's message.
3. Give the test runner three options, each with cases in `scripts/run-all-test-suites-test.py`; their flag names are the implementer's, chosen by the project's naming page:
   - run only the suites named, instead of every suite in the checkout;
   - record nothing, so that a run on mutated code changes no suite's recorded times, which the runner reads to order suites and to set each suite's limit;
   - stop at the first failing suite, ending the suites running beside it, so a mutant that one suite kills does not wait for the rest.
4. Run each mutant's suites, and the baseline's, through the test runner in place of the shell script that `test_command_for()` writes today. The test command cosmic-ray runs becomes one run of `scripts/run-all-test-suites.py` on the scratch worktree, with Part 3's three options and the module's dependent suites. The runner runs the suites in parallel under its own admission control, gives each suite its own limit (the larger of 600 seconds and 4 times its last passing run, or 1800 seconds for a suite with no passing run; see "PER-SUITE TIMEOUT" in the runner's docstring), and, for a suite past its limit, prints the suite's line with `TIMEOUT after` (`why_suite_failed()` in the runner). The script runs the runner with `--checkout` set to the scratch worktree, where cosmic-ray has written the mutant. When a mutant's result is killed and its output carries that line, `outcomes_from_dump()` reports the mutant as ERRORED, naming the suite, and does not count it as killed; today it reports a mutant that ran past cosmic-ray's limit as ERRORED too, but without a suite, because cosmic-ray's output is only `timeout`. Because the runner stops at the first failing suite, the line names at most the one suite whose failure came first; when several lines carry `TIMEOUT after`, name each. cosmic-ray's limit then defaults to the longest of the suites' limits, which the script computes as the runner does (`suite_timeout_and_the_recorded_seconds_it_came_from()` in the runner), times the number of rounds of parallel runs (the number of suites divided by the number of suites the runner runs at once, rounded up), plus the runner's start-up time, measured on ned-box while building this, as a backstop, in place of the fixed `DEFAULT_MUTANT_TIMEOUT_SECONDS`; `--mutant-timeout-seconds`, when given, still sets cosmic-ray's limit; set below a suite's limit, it stops the runner first, and the result is Part 2's first message. Keep the runner's default `--lock-file`: on Linux with bwrap the runner takes no lock, and every run on the machine shares one admission through the directory beside that file, so a separate lock file would leave mutants' runs outside the machine's admission. Where suites run without test sandboxes (macOS, or Linux without bwrap), the runner takes an exclusive lock and a second run exits 3, so there a mutant's run is refused while another test run holds the lock; mutation testing there is outside this GHI. The mutation script runs each suite in the runner's signal sandbox today through its own shell script, which the runner already does for its suites, so the shell-script code in `test_command_for()` and its sandbox handling can go.

How the Python environment `/tmp/cosmic-ray-venv` is built is outside this GHI, as it is outside GHI [Mutation testing of a module with many dependent test suites fails before any mutant runs](https://github.com/nedschorus/nedschorus/issues/1939).

## Outcome

Built by pull request [Mutation testing survivors: run each mutant's suites through run-all-test-suites, and report a baseline timeout as a timeout](https://github.com/nedschorus/nedschorus/pull/2031), merged as 370464e5 on 2026-10-28, Parts 1 to 4 of the Next action above:

- `scripts/run-all-test-suites.py` gained `--only-suites-named`, `--leave-recorded-inputs-and-failure-history-unchanged` and `--stop-at-first-failing-suite` (Part 3), and reads its own `TIMEOUT after` lines with `run_all_test_suites_output_timed_out_suites_and_limits_parse()`.
- `scripts/pull-request-mutation-testing-survivors.py` runs the baseline and each mutant as one run of the test runner on the scratch worktree with those three options (Part 4). cosmic-ray's limit defaults, per file, to the longest suite limit times the runner's rounds, plus `TEST_SUITE_RUNNER_START_UP_SECONDS` of 5 seconds; `--mutant-timeout-seconds` still overrides it. A nonzero baseline is read with `cosmic-ray dump`: killed with `timeout` gives the message that the suites ran out of time, with cosmic-ray's limit, killed with the runner's `TIMEOUT after` line names the suite and its limit, and any other output keeps the message that the suites fail (Part 2). A mutant killed with a `TIMEOUT after` line is ERRORED, naming each suite, and a runner run that judged no suite is ERRORED, not killed.
- The script's shell-script chain went, and with it its per-suite sandbox prefixes, started-proof files, its own machine lock, admission slot, `nice` prefix and exit code 3, since the runner now does each per run.
- The fake cosmic-ray in `scripts/pull-request-mutation-testing-survivors-test.py` produces timed-out baselines and can run the test command, with cases (a) to (c) of Part 1 and two cases that run the real runner on fixture suites (Part 1).
