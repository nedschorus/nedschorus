# Wiki-agent: an interactive agent-seat that keeps the project wiki, `docs/nedsnodes-wiki/`, current

The wiki-agent is a planned agent-seat that is accountable for keeping the pages of the project wiki, `docs/nedsnodes-wiki/`, true; which files that charge includes, such as the project glossary or files outside the wiki, is open question 3. It runs the daily wiki check that GHI [Regular maintenance: the list of maintenance jobs, how often each runs, and how each reaches the user](https://github.com/nedsnodes/nedsnodes/issues/1058) plans, in one of the two ways open question 17 names, acts on requests from the user and from other agent-seats, and changes pages only through its own pull requests. This GHI-MD holds the three parts of its design that the user has decided, the rule that holds until it exists, and, under Deferred-decisions, the questions those parts leave open.

GHI [Hierarchical, cross-linked wiki, and a wiki-agent to build it and keep it current](https://github.com/nedsnodes/nedsnodes/issues/2709) says in its Next action: "Open questions 3 and 6 remain here; the wiki-agent's remaining questions are GHI 3950's." GHI 2709's open questions 3 and 6 ask what counts as an appropriate cross-link and which other wiki improvements belong to GHI 2709; neither is about the wiki-agent, and both stay in GHI 2709. This GHI-MD holds the wiki-agent's design and the wiki-agent's remaining questions. The wiki's new structure is not designed here: the user approved it on 2026-11-20, in item 2 of overall-cleanup's approval-walk overall-cleanup-wiki-structure-and-wiki-agent-questions-2026-11-20, whose walk-document and walk-minutes are cited below, as one pull request, which GHI 2709 calls the restructure, that puts the wiki pages in five folders by subject, shortens their names and adds a home page. GHI 2709 holds the restructure's plan.

## Why

Wiki pages drift out of date when no one is accountable for keeping them true, and an agent that acts on an out-of-date sentence acts on a false description; GHI 1058's section "Why" gives a case. The user's words of 2026-10-16, quoted in GHI 2709's section "The user's direction", ask for "a wiki-agent to do all that and keep it reasonably up to date". His remark of 2026-11-17, which decided nothing, led to item 4, and his answer to item 4, both cited below, makes the wiki-agent an agent-seat. GHI 1058 plans a daily wiki check as one of its maintenance-jobs, which fixes only obvious errors as PR 1052's rule defines one, while on 2026-11-19 the user gave overall-cleanup a wider rule for fixing wiki pages. Item 4 gives both the daily check and the work asked of it to one agent, under that one wider rule, so that an out-of-date sentence is not fixed when one agent finds it and sent to the user when the other does.

## Steps that need judgment

The judgment in the wiki-agent's wiki work is: whether a sentence on a page contradicts what one of Part 3's six sources shows, and what the fixed sentence says; which kind of change a change is, a fix under Part 3 or an obvious-error-fix it may make, or one that goes to the user; writing the text of a deletion, combination or reorganization that is a user-approved-change, such as a home page or the text that joins two pages; and what to do with a request. Besides these, it does the judgment work every agent-seat does, such as talking with the user, answering merge-lane-2's review in a fix-round, and writing its session-handoff. Steps that need no judgment, such as choosing the day's pages, recording which pages were checked, and moving a page and rewriting the links to it once the user has approved where it goes, are code, as `CLAUDE.md`'s code-prompt-code rule says and as GHI 1058's section "How the maintenance jobs run each night, and how often (decided)" has each maintenance-job's program do. Whether the wiki-agent itself does the daily wiki check's judgment, for which GHI 1058's job program would otherwise start a model of its own, is open question 17.

2. What the wiki-agent does with what goes to the user while GHI 1058's overseer agent-session is not built; GHI 1058's Next action builds it first.
3. Which files the wiki-agent keeps true: whether its charge includes the project glossary, which other agents change with the user's approval; the nc-architecture-overview pages, which /overview-write checks and GHI 1058's twenty-fourth job refreshes; and whether it also keeps true the proposed-improvements-or-changes-files that go with those pages, which sit outside the wiki under `nn-systems/<system>/docs/` and record proposals, so that a sentence in them may describe a change not yet made.
4. Where Part 3's rule stops: what the wiki-agent does when its six sources disagree with one another, such as a merged design that describes a plan not yet built while the code on main shows today's behavior; whether a sentence that states a rule or a user-ruling which a program does not follow is "an instruction that reality has made false" or goes to the user; and what it does when a sentence is shown wrong but more than one replacement fits, or when it cannot check a sentence because a machine or GitHub cannot be reached, both of which GHI 1058's second job sends to the user.
5. How the wiki-agent, and overall-cleanup until the wiki-agent exists, gets a fix under Part 3 past the instruction-file guard, `.claude/guard-hooks/instruction-file-guard.py`, which protects the wiki, without the user's approval for each. The guard already clears without asking the changes that `docs/nedsnodes-wiki/nedsnodes-which-changes-need-the-users-approval.md` excepts, such as an obvious-error-fix, a cosmetic-change, or removing whole sentences of prose; a fix under Part 3 that changes what a page directs, decides or plans is on that page's list of changes that need the user's approval, so the question is how Part 3's standing approval is recorded where the guard reads it, such as an exception added to that page.
6. Whether Part 3's rule also applies to other agents that change the wiki, which today may change a wiki page without asking only as `docs/nedsnodes-wiki/nedsnodes-which-changes-need-the-users-approval.md` allows.
7. Which of Part 3's limits code checks rather than the wiki-agent's judgment alone, such as a merge check that refuses a wiki pull request that deletes a page, combines pages or reorganizes the wiki without citing the user's approval, and a merge check that refuses a pull request of fixes under Part 3 whose description cites no file or command output for a fix.
8. How the wiki-agent learns that a page is out of date when the change is on the Mac, ned-box or GitHub, with no commit on main, given that the daily check reads only pages whose named repository files changed, for example whether a program checks each day every machine path, and every repository path, flag and section link, named on any page, before any model reads a page; and, if it runs on ned-box (open question 16), how it reads the Mac, which GHI 1058's section "How a daily job reads the Mac (decided)" has a daily job read through one read-only helper for each thing it reads, or whether it asks a Mac agent-seat.
9. Whether a request may also reach the wiki-agent as a filed GHI, besides from the user in its agent-session and from another agent-seat, which Part 1 decides; how it handles a request for a change that is neither a fix under Part 3 nor a deletion, combination or reorganization; and when a request counts as done and how the requester is told, such as by a request record that code advances when the request's pull request merges or closes.
10. Whether adding new text to a page, or renaming a page to a name no glossary lists, is a change the wiki-agent makes without asking, like a fix under Part 3, or one it brings to the user, like a deletion. `docs/nedsnodes-wiki/nedsnodes-which-changes-need-the-users-approval.md` already has creating a page need the user's approval, and lets an agent remove whole sentences or paragraphs of prose without asking.
11. How the wiki-agent groups its changes into pull requests: one pull request for each day's check, as GHI 1058's second job plans, or one per topic, as `CLAUDE.md`'s rule that each pull request is atomic may require; and how changes from requests are grouped.
12. How a deletion, combination or reorganization that comes from a request, rather than from the daily check, reaches the user: as a question queued for GHI 1058's overseer agent-session, as Part 1 has the daily check's findings go, or in an approval-walk of the wiki-agent's own.

How the wiki-agent avoids conflicting changes to the same page with the other maintenance-jobs that change wiki pages, such as GHI 1058's fifth job, which applies its cold-read-fast-read findings to documents including wiki pages, and its eighteenth job, which corrects the glossary; for example, whether a program lists the open pull requests that touch the same pages before a wiki pull request is opened.
