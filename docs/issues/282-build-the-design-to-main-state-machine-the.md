# Build the design-to-main state machine: the Python machine, its per-state agent-instructions, and the nine items the design defers to the build

The design-to-main state machine turns an approved design into code and tests and submits them to the gate that guards `main`. Its design was ruled by the user across six walks (2026-09-03 to 2026-09-08) and lands on `main` with PR [design-to-main state machine: the design as ruled in four walks, its glossary, and the walk files](https://github.com/nedschorus/nedschorus/pull/281): `docs/design-to-main/design-to-main-state-machine-design.md`, with its own glossary beside it. This issue is the build, step 1 of the AI-native architecture's build order, and it carries the design's section 11: what the design deliberately leaves to the build.

**Why.** The design is complete as a specification of states, transitions, counters and who talks to the user. It is not a program. The user ruled 2026-09-07 that the deferred items are captured here so that nothing the design defers is lost between the design landing and the build starting.

## Deferred to this build (the design's section 11)

Each is the builder's unless an owner is named.

1. **Resource limits per state**: time, tokens, retries, bounding every "to its own judgement" in the design; how long the machine waits for the user and what it does if he never answers.
2. **Provenance and attestation fields** on state-packages and state-exits beyond the state-package commit.
3. **The design's and the test-design's enumerated checks**, in the form of the design-contract's checks (section 5.3), and the file syntax the contract's program check reads.
4. **Where the machine runs**; how the invocation's conversation becomes `design-writing`'s; how the investigation's session reaches the user's Mac; how `submit-to-PR-gate` maps merge-lane's review and later the gatekeeper's answers onto its three verdicts.
5. **The machine is Python** (user-ruled 2026-09-07). Read PocketFlow's node and flow pages first (https://the-pocket.github.io/PocketFlow/core_abstraction/node.html): borrow the shape, not the dependency. The design's section 11 says why.
6. **The test runner** a test-design may name, and the result form of a prompt-based-test.
7. **The investigation report's required content**, beyond the placeholder in section 6.6. Still the build's: the tenth walk (2026-09-14) left it here.
8. **The per-state agent-instructions**, one per state that launches an agent, which the user reviews as standing agent-instructions. They draft in `docs/agents/queue/` and land in `docs/agents/` after their full cold read (user-ruled 2026-09-08).
9. **How a reviewer's own tests might be reused.** Evidence only, for now. The tenth walk's item 16 made every reviewer's own tests a rule of section 6.1 — each reviewer, the arbitrator included, writes and runs tests of its own to prove before it rules, under its evidence directory — so there is now something to reuse.
10. **One source for each fact, and the tooling that keeps the copies from drifting.** Not in section 11; found by the build. The design states one fact in up to five places (section 1's prose, 3.1's package table, 3.2's transition rows, 7's counter definitions) and `scripts/design-to-main/design-to-main-state-tables.py` holds the same machine as data; the tenth walk found section 7 and 3.2 disagreeing since they were written. **Ruled 2026-09-16, the eleventh walk** (minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/design-state-tables-source-of-truth-and-checker-minutes.md`): both copies stay hand-edited — section 3.2 is the source for what a transition *is*, the code for what it *does* — and tests bind them: a row-matcher pairing every 3.2 row to a `TRANSITION_TABLE` row by number, a names checker over the prose, and section 3.3's diagram generated from the code. First a prose PR adds a `Row` column to 3.2 (identifiers, never renumbered) and names the work-streams as orthogonal regions in 3.1. Then a scenario runner over the test fixture, so the user can script a run and read its trace — his "little game" — and a walk to play it. Rendering the prose from the code, proposed here before, is not adopted: the gap was a check, not a format.
11. **Whether the missing-`origin/main` refusal covers a recovered run.** Found by slice 1d (PR [design-to-main slice 1d: the ninth and tenth walks' code rulings](https://github.com/nedschorus/nedschorus/pull/381)). The ninth walk's item 10 words the refusal as firing at the invocation, and the build put it in `start()`, so a run recovered in a checkout that has since lost `origin/main` skips the check and still meets the raw `CalledProcessError` the ruling meant to remove. **Ruled 2026-09-16: leave it as worded.** A recovered run in a checkout without `origin/main` meets the raw `CalledProcessError` at its next step's instance count (reproduced: recovery discards the dead process's files as designed, then `git log origin/main..HEAD` fails). That is expected, not a defect: no checkout in this project has lost `origin/main`, and a guard against it would defend against nothing seen. Was GHI [design-to-main state machine: does the missing-origin/main refusal cover a run recovered in a checkout that lost the remote?](https://github.com/nedschorus/nedschorus/issues/382), closed 2026-09-15 as not planned in favour of this line.

Owned elsewhere, listed so the builder knows not to wait on them here:

- **What the gate's pull request carries**, the single candidate commit or the topic branch: the gatekeeper's, issue [main-gatekeeper — the single check-in gate (design: nc-systems/main-gatekeeper/main-gatekeeper-design.md)](https://github.com/nedschorus/nedschorus/issues/3). The run's record no longer depends on it (design section 9).
- **Which reviewers compose a cold-read run, and passing the user's rulings file to it**: the cold-read-research seat's. Until the cold-read run takes a rulings file, a writer's in-state cold read runs without them.
- **The repository layout** the component's directory follows: issue [Rationalize the repository layout: group components by owning system under nc-systems/, one built-in-process-planned document each, and a hook dispatcher](https://github.com/nedschorus/nedschorus/issues/224).

## Two test defects from 2026-09-29, as worked examples for the test-writing and test-review drafts

Two sets of tests written on 2026-09-29, outside design-to-main, were wrong in ways the drafts for `test-writing`, `test-design-writing` and `test-acceptance-by-agent` should teach against. The user ruled on 2026-09-29, at walk open-items-this-seat-holds-2026-09-24, item 16, that both go into this issue's text. The recommendation, at 19:51:41Z in the session transcript cited in the section above, was to add them "as worked examples for the test-writing and test-review instructions, so whoever finishes those drafts sees them". He answered "y" at 20:01:09Z. The drafts themselves are not changed here: whoever finishes them decides how each one states these lessons.

**1. A test must not reach a live service.** PR [A seat is not told to refresh an overview while an open pull request already changes it](https://github.com/nedschorus/nedschorus/pull/776) made the handoff supervisor ask GitHub, with `gh pr list`, whether an open pull request already changes an overview before telling a seat to refresh it. At its first head, ebcc21a1, five test cases that already existed in `nc-systems/handoff/tests/handoff-supervisor-test.py` reached the new call and ran the real `gh pr list` on every run. Their outcome hung on GitHub's answer rather than on the code: they passed because no real pull request touches the fixture's paths, and they still passed when GitHub stalled, so the calls checked nothing. With a stalled network the file took 192 s instead of 46 s: five timeouts of 30 s each. Both reviews of the first round blocked on it. The fix, 35458a07, put a fake `gh` that prints `[]` first on PATH for those five cases; a logging `gh` then recorded no calls, where it had recorded five.

None of the three drafts says a test must not reach a live service. Search receipt, 2026-09-29, on `main` at f3d0abd8: `grep -n -i -E 'network|internet|offline|github|fake|mock|stub|service' docs/agents/queue/design-to-main-test-writing-agent-instructions.md docs/agents/queue/design-to-main-test-design-writing-agent-instructions.md docs/agents/queue/design-to-main-test-acceptance-by-agent-agent-instructions.md` returns nothing. The test-writing draft's step 3, on a `flaky-test`, lists what can vary between runs inside a test, "a clock, a random value, a temporary path, an order the test-design does not fix, state an earlier run left behind", and a live service is not among them.

**2. A test that fails first must fail for the reason it claims.** PR [A recovered seat's supervisor runs from the reference clone, not from the checkout the recovery ran from](https://github.com/nedschorus/nedschorus/pull/778), merged as 45a77f90, gave `scripts/recover-crashed-seats.py` a `--checkout` option naming the checkout a recovered seat's launcher and supervisor come from. Its three new test cases in `scripts/recover-crashed-seats-test.py`, each named "CHECKOUT: …", failed against the program before the merge only because that program had no `--checkout` option: it exited 2 on the unknown argument before launching anything. One of the three runs only on the Mac, so off macOS two of them fail. Rerun on the Mac, 2026-09-29, with the test file at 45a77f90 against the program at 926d0324, the merge's first parent: exactly those three fail, each with exit code 2, no output and nothing launched. So failing first never showed the old bug, a supervisor launched from the recovery's own checkout. The fix itself was right, and the tests do pin the new behaviour: both reviews mutated the head, and putting back the supervisor from the program's own checkout fails the case that runs off macOS.

The test-acceptance-by-agent draft's step 3 already asks the question that catches this: "would it fail if the clause were violated". It catches it only if the reviewer asks why the test would fail, not only whether it would. That draft's reviewer never runs the tests under review, so the answer comes from reading the test against the code it replaces: a test that the old code rejects at its argument parser has not shown that it would fail on the old behaviour.
