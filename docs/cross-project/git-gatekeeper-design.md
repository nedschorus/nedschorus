## The job and the guarantee

One program, `scripts/git-gatekeeper.py`, is the only way any change reaches main. It holds the project's one **main-capable** credential (this section states the contract; the credential is dormant until it exists — see Implementation status). Agents — all of them, equally — invoke the program directly and never push to main themselves (branch pushes stay open to agent tokens — C4). One program, one credential, one door. No agent has a doorman or relay role in another agent's check-in path; choirmaster is simply the most frequent requester.

For each check-in request the program does exactly one of two things: **checks the work in**, or **refuses and teaches the fix**. (Informational subcommands — `status`, `cancel` — answer rather than check in; § The reply.)

On success, four things are guaranteed true:

1. The change is on main, pushed to GitHub.
2. The checks ran against exactly the content that was pushed.
3. The commit's trailer lines carry the whole machine-readable record (see § The trailer).
4. The requester has the answer: success plus the commit id (directly in the waiting form; a non-waiting caller collects the same answer via `status`).

On refusal, the reply always has three parts, like a well-built MCP tool — never a bare error code: the **named error** from the fixed catalog, the **specific facts** (which file, which check, which mismatch), and the **exact next action, written for an agent to execute**. The caller's files and main are untouched — a refusal changes no worktree content and lands nothing. Scoped exactly (2026-08-12): the base computation's fetch updates the caller's remote-tracking refs (metadata, never files); any invocation may sweep aged refusal records (§ States); a refused `--no-wait` request retains a JSON refusal record until read or expired (B4d); and a push whose acknowledgment was lost can leave the commit on main behind a `network-down` reply — resubmitting self-heals to `already-checked-in`.

**Records:** git history and the invoking session's ordinary transcript are the *only* durable records. No side files, no separate logs — the invocation is a normal tool call, already recorded where tool calls are recorded. (Transient, not a record: the B4d refusal record above, which exists only until collected or swept.)

**Resubmitting is always safe.** Same request, same answer (infrastructure weather aside: a `network-down` retry may answer `already-checked-in` where the first attempt reported failure — the self-healing working, not a contradiction); a fixed request digests differently and processes fresh; work that already went through answers `already-checked-in <commit>`. An agent that crashed or lost its connection never reconstructs what happened — it submits again and the program sorts it out. Refusals teach, retries are free: the loop self-heals, which is what near-perfect autonomous operation requires.

## The request and the reply

```
git-gatekeeper.py check-in
    --files <path> [<path> ...]
    --message "<one-line summary of what and why>"
    --import none | --import-commit <id> --import-source <path> --import-dest <path>
    --issue none | <issue-number>
    --agent <runtime/model>
    [--wait | --no-wait]          (default: --wait)
    [--repo <path>] [--remote <url>]   (test seams: hand the program a
                                        throwaway repository; identical
                                        under every user — C7)
    [--legacy-repo <dir>]              (the legacy checkout an import
                                        reads from; default
                                        ~/Projects/nedlern)
```

Field by field, with exact validation (all form validation is instant and synchronous in both modes; every refusal names its error and the fix):

1. **`--files`** — repository-relative paths, normalized: no absolute paths, no `..`, nothing under `.git/`, no duplicates, list non-empty. Path bytes are printable ASCII without whitespace and without the `->` sequence (the trailer separator) — violations refuse `malformed-field`; quoting grows in when a real import needs it. The new content of each path is read from the invoking agent's working copy — the program's only *content* read of that worktree (the advisory scan reads changed-file *names* from git status, never bytes — § Constructive guarantees). One exception: a declared import destination's bytes come from the legacy repository at the declared commit, never from the worktree — the caller need not, and should not, stage a hand-made copy (field 4). Per path the change is inferred: **added** (absent at base, present in worktree), **modified** (differs), **deleted** (present at base, absent in worktree). Refusals: `unknown-path` (in neither place — a typo), `unchanged-path` (declared but identical to base — declarations must be honest; an empty or malformed file list is `malformed-field`). No component of a declared path may be a symlink, on either side of the comparison — the caller's worktree refuses `malformed-field`, and a link carried in main's own tree refuses `base-tree-symlink`, which the caller cannot fix by resubmitting (ruled 2026-08-11 for the declared path itself, widened both ways 2026-08-12 after each direction was demonstrated reading and writing outside the repository). The gate reads and writes regular files only: a link's target can live outside the repository, and the security boundary does not follow it. (A separate `empty-change` code — "nothing differs at all" — was deleted 2026-08-10 as unreachable: the first unchanged path refuses `unchanged-path` before any aggregate check could run.) Accepted residual (ruled 2026-08-10): the comparison reads content only, ignoring the executable bit, so a permissions-only change (`chmod +x`, no byte changed) refuses as `unchanged-path`. Cosmetic here — most of the project's tracked scripts already carry the bit (twelve of fifteen at the 2026-08-12 count, `scripts/git-gatekeeper.py` itself among the three that do not, so normalizing its mode would be a permissions-only change the gate refuses as `unchanged-path`) — and a change that also touches bytes carries the bit along. Mode-awareness grows when a real need first arrives.
2. **`--message`** — the human-readable what-and-why; becomes the commit message body above the trailers. Required, non-empty (`malformed-field`, the facts naming the field — a dedicated `missing-message` code was folded in 2026-08-10 for consistency with every other field's emptiness). Intent lives with the author; it cannot be auto-filled.
3. **The base** — the exact commit id of the main state the work started from. Computed by the program, not declared (ruled 2026-08-10, replacing a caller-supplied `--base` field and its two hand-off refusals): the program runs `git merge-base HEAD origin/main`, after a fetch, in the caller's checkout — the same checkout it already reads declared content from — so every caller gets the exact right value deterministically, with no relay step to garble and no dependence on the cooperative tier being present. A failed fetch is tolerated: the computation proceeds against the last-known origin/main, degrading to a staler base, which the behind-main integration mechanism absorbs. The result is by construction a real commit on main. Accepted residual: a caller who refreshed from main mid-task (e.g. `git pull` after starting the work) presents a too-new fork point, weakening conflict detection for that request — a blind spot the previous design shared exactly, since its wrapper derived the value from the same repo state.
4. **`--import`** — `none`, or all three parts: the legacy commit id, the source path (must exist in the legacy repository at exactly that commit), and the destination (must appear in `--files`). Every import defect — incomplete triple, missing source, undeclared destination, unreadable legacy checkout — refuses as one code, `import-invalid`, whose facts and next-action text name the specific defect (four separate codes merged 2026-08-10: nothing machine-branches on refusal names, and the teaching text carries every distinction). A second import is inexpressible by construction — it is a second check-in. An explicit choice is required: `--import none` combined with any triple part, and omitting the import choice entirely — neither `--import none` nor the triple given — both refuse `import-invalid` (the built program behaves so; documented 2026-08-11).
5. **`--issue`** — `none` or a positive integer. Version 1 validates syntax only. The artifact-lifecycle rule (the founding plan's — `docs/cross-project/nedschorus-founding-plan.md` — standing rule for which work gets an issue and when) decides *upstream*, at the right granularity, which work has an issue; the gatekeeper only records the answer. `none` is honest for trivial work — an issue is never mandated per invocation (issues hold wanted things, not logs).
6. **`--agent`** — the runtime and model that produced the change (for example `claude-code/opus-5`), required and non-empty (`malformed-field`). Declared by the caller because the environment names the runtime but not the model, and the model is the half the fix ladder (the founding plan's escalation sequence for failed work — retry, stronger model, then the boss) needs ("who last wrote this" becomes one `git log` away). Cooperative class — recorded, not verified: the gatekeeper records what it is told and never guesses.
7. **Origin** — auto-filled from the session environment; recorded as `none` when absent, never blocking (a transcript-less caller is honest, not an error). Meaningful because our agents are long-lived: the session id points at a readable transcript of intent.
8. **The digest** — SHA-256 over: base id + sorted path list + each path's new bytes (deletions as a marker) + the import triple. Deliberately excluded: message, issue, mode, origin, agent, time — the digest identifies **the work**, so identical work resubmitted under different metadata still deduplicates. Canonical serialization (the built program's): each component length-prefixed under a NUL-framed field tag, so no crafted content can make two different requests read as one (length prefixes added 2026-08-12 — the original tag-only framing was collidable, Codex finding G25). Computed by the program; callers generate nothing. Scope, ruled 2026-08-10: this deduplication recognizes verbatim resubmits only — the same work against the same base. A request rebuilt after a refresh from main digests fresh; when that work is already checked in, its declared paths now match main (unless main has since moved them) and the answer is `unchanged-path`. Accepted residual: the situations that reach that answer are rare (a successor session with an imperfect handoff, duplicate work), and the refusal's text already names the operative fact.

**The reply.**

Every invocation prints exactly one JSON object on stdout: `{outcome, error?, facts?, next_action?, commit?, digest?, integrated_over?, advisory?, summary}`, where `summary` is the human-readable line — one format, not two (B1). The optional keys appear when earned: `integrated_over` on a race-losing check-in that integrated cleanly, `advisory` when the worktree differs beyond the declaration (both emitted by the built program today). Exit codes: **0** success and informational answers; **1** catalog refusal (the gatekeeper working); **2** program defect — distinct so loop counters and the audit never read a gatekeeper bug as a correct refusal. The contract covers the parser layer too (ruled 2026-08-11): a command-line-form error — unknown flag, missing argument, unknown subcommand — emits the same `malformed-field` teaching refusal as JSON, exit 1, never bare usage text with the defect code. Exactly two invocations are exempt, named here because the contract previously admitted no exceptions at all (ruled 2026-08-12): `--help`, the human lane, prints usage text and exits 0 — and agent-facing refusal text deliberately does not cite it; and `worker`, the internal re-entry the program makes into itself when detaching, which prints nothing because its reply channel is the workspace, and which is hidden from `--help` so the caller-facing surface matches the caller-facing contract.

- Waiting caller, success: `checked-in <commit-id>`, exit 0; when the race was lost and re-application was clean, the reply also carries `integrated_over: <n>`.
- Non-waiting caller: instant `accepted <digest> on <host>` once form is valid; the outcome is collected later with `status <digest>` (`next_action` says exactly that, and names the submitting host — the workspace is host-local, so the digest is handed out together with the machine it belongs to).
- Any refusal: the three-part teaching form, exit 1.
- `status <digest>` answers from what already exists (history plus the program's workspace): `checked-in <commit>`, `in-progress`, `abandoned` (workspace present, worker dead — resubmit safely), a retained B4d refusal record (returned once in the full three-part form, then swept), or `unknown` ("no trace; submit it" — always safe).
- `cancel <digest>` — see § States, crashes, cancel, and errors.

Naming note (ruled 2026-08-10): the single-word subcommands (`status`, `cancel`) are a deliberate exemption from the project's multi-part naming rule, not a violation. A subcommand never appears alone — it rides under the program's name, so the grepable name is `git-gatekeeper`, under which every invocation surfaces. The rule's failure mode, a search that cannot find the thing, cannot occur; renaming now would strand the built test suite for zero search benefit.
- The import record is read straight from history — `git log origin/main --grep "Gatekeeper-import: .*->"` (run after a fetch; the arrow appears only in real imports, so `Gatekeeper-import: none` lines do not match) lists every import: what was imported, from which legacy commit, to where, when. (An `imports` subcommand that formatted this into a table was built in slice 2 and deleted by ruling 2026-08-10: the trailer is the record, the git command is the view, and a per-call scratch clone bought no guarantee. The trailer replaces the retired entry-manifest row rule; `entry-manifest.md` remains as the founding-era historical record only.)

## The procedure

1. **Submit.** The agent invokes the program with the request and its mode choice.
2. **Instant screening — synchronous in both modes.** Form validation (above). The digest is computed and looked up in history right here: already present answers `already-checked-in <commit>` with no work done. A non-waiting caller gets `accepted <digest> on <host>` now; everything after runs identically either way. ("Instant" means synchronous and seconds-fast, not I/O-free: the built program creates the workspace clone during screening.)
3. **Build the candidate.** In the program's own private workspace (`<workspace-root>/<digest>/`) — never the agent's worktree — start from main *at the computed base* and apply exactly the declared changes. Unchanged files come from main, never from the agent's possibly-stale copies. A declared import happens here: copy from the legacy repository at the declared legacy commit; record the source for the trailer.
4. **Run the checks** (§ Constructive guarantees) against the candidate — the literal bytes that would become main.
5. **Commit.** The message, then the trailer lines.
6. **Push.** Happy path: main has not moved since the base; the push succeeds. Main moved: § Concurrent check-ins.
7. **Answer.** The waiting caller gets its line; the non-waiting caller's outcome now sits in history where `status` finds it. The workspace is deleted (B4d exception: a refused `--no-wait` request's workspace survives, holding only the refusal record, until `status` collects it or it expires — § States).

The requester's own working copy is never modified; the agent refreshes from main at its convenience.

## Constructive guarantees, the advisory, and the growth point

Most classic gate failures are made impossible by construction rather than detected:

- **Stray changes cannot enter** — at path granularity: the candidate is built *from* the declaration, so an edit in an undeclared path never reaches it. Within a *declared* path the worktree bytes ARE the declaration — a stray edit inside a declared file rides along; the guarantee is per-path, not per-edit.
- **The record cannot be missing** — the program writes the trailers itself.
- **The import record cannot lag** — written during candidate construction, same commit.
- **Duplicates cannot apply** — the digest screen runs at submit.

**One advisory (not a refusal):** if the agent's worktree contains modified or untracked files *beyond* the declared ones, the reply carries a note — "worktree also differs at `x`, `y`; confirm intentional" — because the likeliest cause is a forgotten declaration, and a forgotten *new* file arrives untracked (ruled 2026-08-11; `.gitignore`d files stay hidden). Unrelated work-in-progress in the same worktree is legitimate, so this never blocks.

In version 1, between screening and push, **no judgment refusal remains** — this stage is deterministic construction and recording; infrastructure failures (`workspace-io-error`, `network-down`) can still arise here and are safely resubmittable. In v1 the check set *is* construction itself, so guarantee 2 binds the checks that exist — construction — to the exact pushed bytes; it gains content as checks are added. That is the growth point, not a hole: when a test suite exists, the tests run here; when the boss gates an artifact class, its review-evidence check runs here (the request format grows its evidence field then, not before).

## The trailer

```
Gatekeeper-origin: <session-id> | none
Gatekeeper-agent: <runtime/model>
Gatekeeper-digest: <sha256-of-the-work>
Gatekeeper-import: none | <legacy-commit> <source-path> -> <destination-path>
Gatekeeper-issue: none | #<issue-number>
```

Four facts and a pointer; nothing else. The agent line (B6, boss-ruled 2026-07-31) names the runtime and model that produced the change, literal value, never omitted — the fix ladder's escalation needs to know what tier produced an artifact to know whether stronger models remain. The digest line is the **duplicate-detection key**, not provenance — it is what makes resubmission safe. The issue value is written in `#<n>` form deliberately: any commit reaching the default branch with `#<n>` in its message appears automatically in that issue's GitHub timeline, so **an issue collects all its check-ins with zero machinery**. The same collection is derivable offline (`git log --grep "Gatekeeper-issue: #<n>$"` — anchored, so `#1` never matches `#10`). Refusals and other responses are **never** auto-posted to issues — mechanical chatter stays in transcripts; a genuinely blocking outcome earns a judgment-written comment by the requesting agent (revision convention: comments are for genuinely new events).

## Concurrent check-ins

Everything rests on one property GitHub provides: **a push either wins cleanly or is rejected whole** — never partial, never interleaved. GitHub is the arbiter; exactly one request wins any race. No queue and no lock are built; check-ins run in parallel by default (boss ruling).

- **The winner** completes the procedure, unaware of the race.
- **The loser** — handled by the program, not the agent: fetch the new main, and first re-check the new tip for this request's digest — if the race's winner was this very work (a concurrent resubmit), the answer is `already-checked-in <commit>`, no rebuild (the built program does exactly this). Otherwise rebuild the candidate by re-applying the declared changes onto the new main. **Clean re-application** (the usual case — different paths): re-run the checks against the rebuilt candidate (version 1 re-runs everything; cheap while checks are fast) and push again; the reply notes "integrated over N newer commits." **Real conflict** (the new main touched the same path(s) this request changes — file granularity in the built program, so no silent lost update exists within a path): re-applying would require guessing the author's intent, and the program never guesses — refuse with `conflict`, naming the files, the intervening commits, and the next action: update from main, adjust, resubmit (the adjusted work digests fresh, correctly).
- A request submitted from a behind-main worktree is the same mechanism — being behind is just "main moved before we started."
- **Bounds, both named:** the retry loop is capped at five rounds, then `main-moving-too-fast` (refuse rather than spin). And the accepted gap, recorded: changes in *different* files that interact *semantically* pass silently until tests join the checks.
- **Deferred optimization, trigger named:** when checks become slow (a real test suite), re-validation narrows to checks whose inputs intersect what actually changed between bases (impact analysis), so trivial head movement — ledger marks, log commits — never invalidates a pending check-in (boss ruling). A merge queue (batch-validating several queued requests against the projected combined result) is the rung above that, if volume ever demands it.

## States, crashes, cancel, and errors

**States:** SCREENING (synchronous; only an unkeyed scratch clone on disk, nothing keyed by digest) → WORKING (candidate being built and checked, inside `<workspace-root>/<digest>/` — concretely `$XDG_STATE_HOME/nedschorus-gatekeeper/<digest>/`, default `~/.local/state/...` (B4a); once C2 lands this resolves in the *gatekeeper user's* environment — literal default `/home/nedschorus-gatekeeper/.local/state/nedschorus-gatekeeper/<digest>/`: outside every repository, discoverable from the digest alone *on the host that created it* (workspaces are host-local: nothing is shared between machines, so `status` and `cancel` answer only for requests submitted where they run — corrected 2026-08-13, the phrase previously read as though a digest were discoverable anywhere), holding the candidate clone, `worker.pid`, and the resolved request record (B4c: every environment-derived field, origin foremost, is resolved at screening into that record; the worker only reads it, never re-derives)) → PUSHING (atomic attempt, retry-capped) → **CHECKED-IN** or **REFUSED**. After either ending the workspace is deleted, with one exception (B4d): a refused `--no-wait` request keeps its workspace holding just the JSON refusal record; `status` returns it once, then sweeps. Expiry (ruled 2026-08-10): any gatekeeper invocation first sweeps refusal records older than 30 days — opportunistic, no daemon; a caller whose record aged out resubmits, the same recovery as every lost reason. Named residual (accepted): a caller whose `status` call collected the record but who crashed before reading the reply loses the reason — rare, recoverable by resubmit. Durable traces: a checked-in request is its commit on main; a refused waiting request deliberately leaves nothing.

**Crash recovery — one rule, not a procedure.** The whole pipeline has exactly two durable effects: the workspace directory, and the atomic push. A crash or lost connection at any moment therefore leaves one of two worlds that matter: the commit is on main, or it is not and a stale digest-keyed workspace remains. (A third, harmless leftover: a crash during screening strands an unkeyed `screening-*` scratch clone; the opportunistic expiry sweep clears those too.) Recovery is: **resubmit**. The program checks the digest against history — found means `already-checked-in <commit>`; absent means the leftover workspace is swept and the work runs fresh. No journal, no repair mode. `status` distinguishes WORKING from **abandoned** (workspace present, worker process dead) via the recorded process id, so a died-silently worker is a named, resubmittable state — never a forever-"in-progress". Residual (accepted): a recycled pid can masquerade as a live worker, and a pid check says nothing across machines; slice 4 records the worker's start-time beside the pid so `status` checks both.

**`cancel <digest>`** — in version 1's contract (boss ruling: the need arrives with slow checks, the machinery it needs already exists, and it is small; slice 4, BUILT 2026-08-12 — see Implementation status). Any agent may cancel; there is no permission machinery — cooperative model; the workflow simply does not teach cancel as a routine move (and the author may be gone; authorship grants no special judgment). Outcomes, exactly five (the fifth added 2026-08-12): digest already in history → `too-late — already-checked-in <commit>` (the remedy for a bad checked-in change is a **revert**: an ordinary check-in whose change undoes a previous one, through the same gate); live worker found → kill it, sweep the workspace, `cancelled`; a workspace with no live worker (an abandoned run, or a retained B4d refusal record) → sweep it, `cancelled`; nothing found *on this host* → `unknown-request` (workspaces are host-local; a request submitted from another machine is cancelled there, ruled 2026-08-12); the worker outlives SIGKILL → `cancel-failed`, naming the pid and what was tried, leaving the workspace in place and telling the caller the request may still reach main (ruled 2026-08-12 — the alternative was reporting a success that had not happened). The cancel-versus-push race resolves by the push's atomicity: kill the worker's process group — a recorded pid alone leaves an already-spawned `git push` child running (ruled 2026-08-11) — but the group **only** when the recorded pid leads one, since a waiting check-in records its own pid, whose group is the caller's harness (ruled 2026-08-12, after a demonstration killed a launcher and its unrelated siblings); then wait for it to exit, and ask history whether the digest made it. Every ending re-asks history and confirms the kill: the sequence used to run on the live-worker branch alone, so a worker that pushed and died was answered `cancelled — nothing reached main`. Cancel only makes sense before the check-in completes (boss ruling); after, revert.

**The error catalog** — every ending named, three-part teaching form:

- *Form (instant):* `malformed-field` (any missing, empty, or malformed field, named in facts — including a declared path passing through a symlink in the caller's worktree), `unknown-path`, `unchanged-path`, `import-invalid` (any import defect, named in facts), `base-tree-symlink` (main itself carries a link on the way to a declared path, added 2026-08-12: the caller cannot fix it by resubmitting, so it is named apart from `malformed-field` and its next action points at whoever maintains that path on main). (Collapsed 2026-08-10: `missing-message` and the unreachable `empty-change` folded into `malformed-field`; the four import codes merged; `unknown-base` / `base-not-on-main` retired with the `--base` field — the program computes the base, so no hand-off exists to validate.)
- *Integration:* `conflict`, `main-moving-too-fast`.
- *Infrastructure:* `push-auth-failed`, `network-down`, `workspace-io-error` — all safely resubmittable. Caller guidance: infrastructure refusals warrant bounded, backed-off retries at the caller's judgment; the gate never instructs unbounded resubmission.
- *Unbuilt surface:* `unbuilt-option` — dormant since slices 4 and 5 built (2026-08-12): no unbuilt option remains reachable. The name stays reserved for future growth points.
- *Cancel:* `cancel-failed` (added 2026-08-12) — the worker outlived SIGTERM and SIGKILL, so the gatekeeper neither stopped it nor knows the outcome. Named rather than forcing a false `cancelled`, which is what the program did before; the workspace is left in place and the caller is told the request may still reach main.
- *Answers, not errors:* `checked-in <commit>`, `already-checked-in <commit>`, `accepted <digest>`, `in-progress`, `abandoned`, `unknown`, `cancelled`, `too-late`, `unknown-request`.

**The autonomy standard, met:** no unnamed endings; every refusal teaches; resubmit always safe; nothing routes to the boss mechanically — he is consulted by agents' judgment, never by the machinery.

## The credential and enforcement

The dedicated-identity rung was **admitted early** (user-ruled 2026-08-09, exercising the trigger named below); the layout it replaces is recorded first because it is still the live state until the amendment is applied.

- **Branch protection, LIVE since 2026-07-21:** pushes to `main` restricted to the machine credential (`NedLern`) alone; enforce-admins on; force-push and deletion blocked. The org has two owners (`NedLern`; `NedLerner`, settings and emergency power, no push — caution: `NedLern` is a proper prefix of `NedLerner`, so substring searches conflate them; match anchored/whole names — and case-insensitively, because GitHub treats account names as case-insensitive for identity and the API returns the canonical login lowercase (`nedlern`), while this document and the audit's expected set spell it for a human reader), so either account can recover the org if the other is lost; a protection change by any owner is a deliberate, visible act, never a standing path. The boss never commits directly; a boss-originated change is drafted with an agent and checked in like any other. Issues need no repository *grant* beyond an authenticated GitHub account (the repository is public); the agent tokens nonetheless carry issues:write for the machinery (C4).
- **The layout amendment (ruled 2026-08-09, C1/C3 — applying it needs an org owner):** the pusher role moves to a **dedicated GitHub account** — a collaborator with write on this one repository, not admin, never an org owner — and protection's push restriction names it alone (the account's name is recorded here verbatim when the amendment is applied). Chosen over the App/CI form this section previously sketched: an App or CI job relocates the gate into CI, which this design scopes out; a plain account keeps the gate a local program. Blast radius of a stolen token: commits to this one repository, nothing else. Owner power stays with the user; "no agent ever holds it" is the C3 target state, true at amendment application — until then `NedLern` is both pusher and owner, the live-state exception recorded above.
- **The Unix-user boundary (C2) — where the enforcement actually lives:** GitHub restricts accounts, not processes, and on one machine every process of one Unix user reads the same credential files. So the main-capable credential is owned by a **dedicated Unix user**, unreadable by agent sessions, and agents invoke the program through a sudoers rule scoped to exactly it. That is the step at which "agents never push" becomes impossible rather than instructed; it also makes the gatekeeper literally an invocable service any agent on the box can call. The sudoers rule names a **root-owned copy of the program outside every checkout** (ruled 2026-08-10) — a rule pointing into a checkout would privilege whatever bytes an agent last wrote there. The copy keeps itself current from main automatically (no manual deploy step; a checked-in fix is live on the next call), which is safe because the gatekeeper's source joins the instruction-file class: changes reach main only with walked-approval evidence, enforced by the review-evidence check (slice 6). Activating the privileged lane therefore waits on slice 6. Working path: `/usr/local/lib/nedschorus-gatekeeper/git-gatekeeper.py`. Staleness of the deployed copy is fail-safe — a stale copy enforces the old contract and never runs bytes an agent planted in place directly — only walked-approved content from main; ownership, not freshness, carries the security guarantee, so a lag in self-update costs availability, never safety. Standing principle, project-wide: a deployed copy of anything keeps itself current from its source automatically rather than relying on a remembered deploy step.
- **Agent credentials are scoped (C4):** each agent host holds a fine-grained token for this repository only — contents read/write (branch pushes are open; the push-less ruling covers main alone), issues write — never a classic all-repository token, and never the `workflow` scope (capability-by-landing class, nedschorus#31). Issue work is **scoped, not gated**: no invariant like "one writer to main" exists there, so discipline lives at the skill and hook rung, not at a gate.
- **The cooperative tier (C6), above the boundary and never a substitute for it:** a PreToolUse hook rewrites `gh` calls seamlessly into their disciplined form (the same operation routed through the project's wrapper, argument-for-argument); a `git push` toward this repository's remote is denied with a *template* of the check-in invocation instead — files prefilled from the agent's own staging, the message left to the author, never a ready-to-run exact command — because a push carries none of the declaration, and auto-deriving all of it would gut the intentionality the `unchanged-path` refusal exists to force. The check-in skill front-loads the declaration (`--files` from the agent's own staging, message passed through verbatim; the base needs no front-loading — the program computes it), so the agent contributes only what it already does by training. Refusals teach, as the final tier.
- **Break-glass (C5) — an unlockable credential, never a standing ungated agent:** gate defects are recovered from the gate's own history — the program stays **one standard-library-only file** precisely so any historical version is directly runnable; a check-in the gate wrongly refuses uses a sudoers entry requiring the user's password, approved in the moment; credential expiry and protection misconfiguration are org-owner territory, the user's alone.
- **The test seams need no privileged-mode guard (C7 struck to zero, user-ruled 2026-08-10):** `--repo` and `--remote` exist so tests can hand the program throwaway repositories, and they behave identically under every user. The formerly planned refusals guarded nothing — a foreign GitHub remote dies at authentication because the credential is scoped to this one repository (C1), a non-GitHub remote (a local path) needs no credential and was never the protected asset, and refusing `--repo` would only move caller control to the working directory, not remove it. A hard-coded remote pin was considered as defense-in-depth against future credential misconfiguration and declined: the token's scope, set once by the user, is the guard.
- **The honest singleton statement (boss ruling), still true until C2 is installed:** branch protection restricts the *account*, not processes — anything running as that account, on any machine, can push. Process-level ordering needs no lock: the atomic push arbitrates. What remains procedural before C2 is only that agents *use the program* rather than raw `git push`.
- **CLAUDE.md is documentation, never enforcement (boss ruling; his rationale verbatim: a python script does not read it, and different machines may carry different copies).** The same is true of harness hooks: they configure a harness, and only cooperating harnesses read them — which is why C6 is a convenience tier and C2 is the boundary. No *guarantee* in this design depends on either (the convenience and token savings do). The raw-push residual is handled at the configuration level, not prevented per-commit: a standing **branch-protection audit** at each session recycle (riding the fast-handoff supervisor's cycle, which runs several times a day; ruled 2026-08-12, replacing the retired "handoff scrub" anchor) checks the live protection settings against this design, with **three named outcomes** — `protection-ok` / `protection-wrong` (differing settings named) / `audit-failed` (gh missing, unauthenticated, API error) — failing loudly as its own outcome, never a silent skip into green (B3c). **Coverage is credential-shaped, not schedule-shaped (recorded 2026-08-13):** the ride happens on every host, but only a host whose credential can read protection settings actually detects anything — today the Mac alone, since the Ubuntu seat's credential gets a 404 and the audit answers `audit-failed`. That answer is honest and blind at once, and a fleet where only one host detects drift is a thinner guarantee than "rides every session recycle" sounds. The gap closes with a credential that can read protection without being an owner's, which is C-work; until then the detector's real cadence is the Mac's recycles. (It also covers the sibling residual while it exists: an agent-held owner credential could deliberately edit protection — same catch; C3 removes that class by taking owner power out of agent hands entirely.) A second detector — a scan of main's history for trailer-less commits, filing `draft` issues — was in this design until 2026-08-10 and is deleted (ruled at the subtraction review): once C2/C3 apply, a trailer-less commit can arise only from break-glass (user-approved by password in the moment), a protection failure (this audit catches the hole at the configuration level, though not the commits that used it), or a gatekeeper defect. Before C2 applies, an authorized raw push leaves configuration green and goes undetected — an accepted gap, by the same no-consumer reasoning that deleted the scan, closed when C2 lands. A detector whose findings have no consuming machinery is logging cost without value.

## Acceptance tests

Build sequencing is owned by `docs/issues/3-git-gatekeeper-build-slice-plan.md` (five slices, with the test↔slice map; this section's original one-task framing is superseded by it, ruled 2026-08-10). What remains here is the contract's acceptance-test index:

T1 every form error refuses with its named error and no side effects · T2 happy path: the four success guarantees verified, trailer exact · T3 digest: identical resubmit answers `already-checked-in`; changed content digests fresh; metadata-only changes do not change the digest · T4 concurrent submissions (injected delay): winner clean, loser integrates over newer commits and succeeds · T5 conflict: same-path collision refuses with files + commits + next action · T6 retry cap: sustained head movement ends in `main-moving-too-fast`, never a spin · T7 crash recovery: worker killed mid-WORKING → `status` reports abandoned, resubmit sweeps and completes; killed after push → resubmit answers `already-checked-in` · T8 cancel: all four branches (two return `cancelled`); cancel-after-push answers `too-late` · T9 advisory: undeclared worktree changes noted, never blocking · T10 retired (2026-08-10): its subject, the `imports` subcommand, was deleted — the trailer's exactness is covered by T2's trailer assertion and T11's screening · T11 each import error class refuses correctly · T12 retired (2026-08-10): its subject, the trailer-absence audit, was deleted from the design; slice 5's audit acceptance is B3c's three branch-protection-audit outcomes.
