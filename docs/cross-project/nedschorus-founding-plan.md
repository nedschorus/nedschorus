- 100% manual edit-production pipeline; automation earned rung by rung (manual → script-you-run → automation). Python liberally, and light: python over prompts, python over bash; smallness kept by re-derivation, the single door, and earned complexity — not by the language.
- CLAUDE.md lines settled so far: the handoff pickup line; the transcript-archive pointer; commit-as-you-go with session id in every commit message; the zero-context-reader writing rule for durable artifacts (delivered inside every writing skill too); the check-in timing rule ([nedschorus#25](https://github.com/nedschorus/nedschorus/issues/25) — post-boot needs live as GHIs, not standing decisions; boss-ruled 2026-07-24).
- **Terminology (boss-ruled 2026-07-24, twice-extended):** use standard SDLC terms; never invent vocabulary. The check-in gate component class is the **gatekeeper**; this one, being git-specific, is the **git-gatekeeper** (other gatekeepers may exist later) — the former name "throat" is retired. The old system is **legacy**, never "quarry". The operation of getting a change onto main is a **check-in** (`git-gatekeeper.py check-in`) — the former "land"/"landing" is retired. The agent instruction file is called by its name, **CLAUDE.md** — the former "kernel" is retired (a kernel is an OS component). And the framing: NC is **not a rebuild** of the old system — it starts from its own requirements and cherry-picks pieces of nedlern that earn entry through the checkpoint.
- **Public-links policy (boss-ruled 2026-07-24, outer walk item 14):** this repository is public, and links in it are judged on usefulness and reliability only — there is no provenance-based quarantine class. Unofficial or leaked archives may be linked and used like any other source when they offer documentation or insight not available elsewhere; claims derived from them carry the normal reliability record (provenance varies, so: model, surface, version/date, extraction method, confidence); and unofficial extractions are never runtime contracts or dependencies — a reliability judgment about unversioned snapshots of a moving product, not a provenance one (accepted principle 4 of the pair-#9 notes).
- **The rewrite policy (boss-ruled 2026-07-24, outer walk item 13):** governs every legacy cherry-pick. At the moment work reads legacy material — an import crossing the checkpoint, or a build slice using legacy code as reference — the builder classifies exactly the legacy features that work touches, each into one of four classes: **preserve-feature** (the feature's contract survives, probably not its implementation — the implementation is re-derived unless the import record separately justifies keeping it; every preserve claim is named and test-pinned, so compatibility is demonstrated, not assumed), **update-feature** (the feature survives changed; the divergence is recorded so nobody later "fixes" NC back toward legacy behavior), **remove-feature** (the feature does not come along; a one-line reason is recorded — saying "defective" when that is the reason, so a removed defect cannot sneak back in via a later pick), **consider-feature** (not decidable now; blocks nothing; re-decided the moment work depends on it). No global inventory of legacy behavior is ever built — classification is per cherry-pick. The record lives in the slice plan's classification table or the entry-manifest line; a consider-feature that outlives its slice moves to [`legacy-feature-queue/`](#project-organization) — never a GHI, which is reserved for things we think we want. Default: **unexamined is never preserved** — silence about a legacy feature means NC does not have it; "legacy did it" is never a requirement without a recorded preserve-feature. Enforcement rung: discipline now; the `plan-rewrite-slice` skill ([nedschorus#16](https://github.com/nedschorus/nedschorus/issues/16)) embeds the procedure when built.
- The boss's review queue is **issues labeled `draft`** (boss-ruled 2026-07-24, renaming `boss-review`: a marker names the artifact's STATE, not the action owed — a queued issue IS a draft; the label is the issue-world's queue membership under the artifact-lifecycle rule, § Project organization) — same format as all issues, full-context walkable bodies, non-blocking by rule, no title/filename markers (the label is the single authority). The scrub step of each handoff states every queue's depth AND oldest item's age — the `draft` issue queue and the directory queues alike — so starvation is visible, not just volume (package-review item 9; drain procedure tracked on [nedschorus#24](https://github.com/nedschorus/nedschorus/issues/24)). When issue creation fails, the routed body is kept durably (committed) until an issue id exists — a routed suggestion is never lost to a failed API call.
- Boot-pack validation is boot-testing the delta with genuinely fresh subagents, not review alone. A fresh subagent's context floor (CLAUDE.md + prompt) is the measured boot state of every future reader.

## Project organization

The full preservation-and-placement design — what NC preserves (four
classes), where each class goes, how the rules become code and skills, and
the drift-prevention sweep — is the pair
[nedschorus#32](https://github.com/nedschorus/nedschorus/issues/32)
([docs/issues/32-preservation-and-placement.md](../issues/32-preservation-and-placement.md)),
boss-walked 2026-07-27/28; it graduates to a wiki page with subpages when
matured. This section holds the directory homes and the artifact-lifecycle
rule the pair builds on.

Five committed homes plus the shared place — no `docs/working/` ever exists:

1. **`docs/wiki/`** — permanent truth (Obsidian vault; `.obsidian/` gitignored, matching the legacy system's practice — config is per-vault, so the old wiki cannot be affected). Its `queue/` subdirectory holds wiki-bound doctrine awaiting the boss's drain (artifact-lifecycle rule, below).
2. **`docs/issues/<n>-<slug>.md`** — working material, one document per substantial issue; header carries the issue link only (the issue's open/closed state is the sole status authority). At issue close, the same commit disposes the document three ways (boss-ruled 2026-07-22, superseding the 2026-07-21 delete-or-promote form; pair #5's deletion stands as history): the DEFAULT is complete-and-archive — stamp frontmatter (`completed: <date>` + disposition) and move to `docs/issues/archived/`, so the active directory lists only open work; wiki PROMOTION is rare — only knowledge hard to reproduce by reading the files (a large system design, cross-cutting behavior no single file reveals), with `design-as-of:` frontmatter and the production-is-SSOT line; DELETE is nearly retired — only content that should not exist in the tree at all (the redaction class). Close is an ordered two-phase operation across two systems (package-review item 9): FIRST the disposing commit is checked in, THEN the issue closes referencing that commit. A failure between the phases leaves an open issue pointing at a disposed document — the visible half-state; recovery is finishing phase two (close the issue, referencing the commit), never re-opening the disposal. The reverse order is forbidden because its half-state — a closed issue with a live document — is invisible exactly where the status authority says nothing is pending. The choice between them (boss-ruled 2026-07-21): promote only distilled standing knowledge; an evidence archive or reference file DELETES, with the extracted decisions memorialized in their governing documents and a `git show <sha>:<path>` recovery pointer on the closing issue. The `queue/` subdirectory (`docs/issues/queue/`) holds pair-bound MDs awaiting the boss's drain (artifact-lifecycle rule, below).
3. **`handoff/`** — the numbered handoff series with transcripts.
4. **`docs/cross-project/`** — artifacts shared with the old system, including the founding documents (migrated here from the legacy system, frozen there at 78ed90f0).
5. **`nc-queue/`** — the tracked intake directory for boss-requested notes awaiting their initial walk (boss-ruled 2026-07-22). Every requested note is committed as `nc-queue/<YYYY-MM-DD>-<slug>.md`, and a note request is complete only when the file exists there. Queue commits are verbatim relays, never reviewed before being committed — the S1 residual class covers raw content on the public repository, and the drafting agent owns keeping do-not-publish material out (reopening trigger: a leak that costs something). At the note's initial walk the durable parts disperse to their homes — a GHI, an MD-GHI pair, a script, a REVISE on an existing artifact; the walk itself is never memorialized — and the dispersal commit MOVES the note to `nc-queue/archived/`, stamping frontmatter at that moment: `processed: <date>`, `dispositions: [<destinations>]`, `dropped-by: <author>` (boss-ruled 2026-07-22). An unwalked note expires at a 90-day TTL (boss-set), moved to `archived/` by the handoff scrub marked as expired; the scrub reports the queue root's count and oldest-note age at each handoff alongside the `draft`-issue numbers. Two dates, two homes: the DROP date is the filename date (set at creation — filesystem timestamps are never consulted; git does not preserve them), and the PROCESSED date is frontmatter. Unprocessed drops carry no frontmatter (verbatim capture, zero friction); frontmatter appears exactly at processing. The queue root empty means walks are caught up; `archived/` is the browsable processed history; git history additionally holds everything. Companion convention for LEDGER documents (pair docs, plans): a processed item is marked in place — `processed <date> → <outcome>` — with its body retained; documents dispose only at their ruled issue-close lifecycle. Frontmatter generally: a field exists only where a named consumer (a script or a reading pattern) uses it — no universal author/created stamps; git carries provenance.

6. **`legacy-feature-queue/`** — the decision queue for consider-features that outlive their slice (the rewrite policy, § Standing decisions). One file per feature, `legacy-feature-queue/<YYYY-MM-DD>-<slug>.md` — the date is when it was queued, giving the scrub its oldest-age without consulting filesystem timestamps (same convention as `nc-queue/`). Body: the feature in one paragraph, the legacy pin (SHA + path), the slice that hit it, why it is undecidable now, and what would decide it. Queued ONLY when still undecided at slice close — a consider-feature that resolves during its slice stays in the slice's classification table and never touches the queue, so every queue entry is a real open question. Drains by the standard four outcomes, and deciding IS the drain: promote to preserve-feature or update-feature (the GHI or slice-plan entry is minted then, when the feature becomes wanted), or remove-feature (file deleted, reason in the commit message). No TTL — a consider-feature blocks nothing; the scrub's depth + oldest-age report keeps starvation visible. The directory materializes in git at first use.

**The MD-GHI pair:** a request for a durable MD IS a request for a doc + issue pair (the boss's trigger word: "memorialize"). All NC-related GHIs — paired or issue-only — are filed on the nedschorus repository, never in the old system's tracker (boss-ruled 2026-07-22: NC context must not drown among the legacy system's thousands of issues). `md-write` searches existing pairs first, then disposes NEW / REVISE (default on subject match) / REPLACE (supersede, old issue closed same commit) / REMOVE; ambiguity goes to the `draft` issue queue, never blocks. Session provenance: MDs via commit messages; issues via a footer line. Revision convention (boss-ruled 2026-07-22): a clarification or revision to an issue or a pair document EDITS the artifact — the GHI body, the document — never a stacked clarifying comment; additive records multiply and conflict with what they meant to fix. Comments append only for genuinely new events (an instance outcome, a completion, a ruling challenge). Append-only audit surfaces (review clearances and their trailers) are the deliberate exception. Artifact-lifecycle rule (boss-ruled 2026-07-24; supersedes and absorbs the 2026-07-23 three-state artifact rule): **every artifact is either final at its home, or sitting in a named queue that states its destination — and every queue has a drain process.** No stateless piles, ever. Destination known up front → destination-rooted queue: wiki-bound doctrine in `docs/wiki/queue/`, pair-bound MDs in `docs/issues/queue/` — the same `queue` token everywhere, so one grep finds every queue. Destination decided only at the drain → decision queue: `nc-queue/` (boss notes) and `legacy-feature-queue/` (undecided legacy features). Draft GHIs carry the **`draft` label** — the issue-world's queue membership, symmetric with the directories. The drain is one process for all queues ([nedschorus#24](https://github.com/nedschorus/nedschorus/issues/24)): the boss walks a queue when he chooses; each item gets exactly one of four outcomes — **promote** (`git mv` to the destination; the move commit is the record), **edit** (revise, stays queued), **demote** (down to evidence/transient, attached to its pair or session), **drop** (deleted with the reason in the commit message — explicit, never silent rot). The handoff scrub step reports every queue's depth and oldest item; until the NC handoff skill is built, that reporting runs as discipline. Transient design/research MDs never enter these queues — they live and die attached to their pair or session. The absorbed three-state routing still governs write time: a queue drop needs NO GHI — the queue is its attention surface until the drain decides its fate, and minting a GHI at drop time front-runs the walk; the moment something is wanted as a feature, component, or commitment — any pending state — it gets a GHI (lean decision → issue-only; substantial working material → the MD-GHI pair: the MD carries the greppable substance, the GHI carries the walkable state); a bare MD with no GHI is legitimate only for final reference content awaiting nothing (operator notes beside code, wiki pages), and anything about it that later becomes pending gets a GHI then. Discriminator: the GHI carries state, the MD carries substance, the queue holds the not-yet-decided. Boss clarification 2026-07-25 (walk 17 cluster 2): **a committed doc is not an attention surface** — a backlog section or "captured research" note in a pair doc is a pile unless it is queued or carried by a GHI; anything task-shaped (an investigation, an evaluation, a build) gets a GHI even when small — lean bundled issues are fine; and agent-internal task lists are invisible to the boss until a review method exists ([nedschorus#28](https://github.com/nedschorus/nedschorus/issues/28) item 5), so nothing may live only there. Enforced at write time by `ghi-write`/`md-write` ([nedschorus#13](https://github.com/nedschorus/nedschorus/issues/13)).

**Accepted residuals (boss-ruled 2026-07-21):** when the boss overrides a review objection — accepts a risk, declines a mitigation — the artifact records it at the decision point as a named block: `Accepted residual (boss-ruled <date>):` the objection in one line, why it is not a concern for this project, and the reopening trigger (the evidence class that would legitimately re-raise it). Reviewer instructions carry the standing counterpart rule: a recorded accepted residual is re-flagged only with new evidence matching its trigger, filed as a separate RULING CHALLENGE, never as an ordinary finding. One grep on `Accepted residual` returns every such decision. The `md-write` and `d-review` skills embed both halves at build.

**Subsystem structure:** co-locate when free; subsystem subdirectories inside pinned roots at the second file; the subsystem token verbatim in every name (one grep returns the whole subsystem); a hygiene script (a git-gatekeeper check) verifies tokens and subdirectory moves — test-naming rules are enforced at writing time by the writing skills, not at the git-gatekeeper (claim corrected, package-review item 9) — placement itself stays the writer's judgment; a never-seen token routes to a `draft` issue.
