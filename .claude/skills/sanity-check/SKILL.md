# sanity-check

## When used

After the document's full /cold-read has run and the changes its findings produced are committed, and before its pull request opens, so that the changes the check produces are ordinary commits and not a fix round on a frozen-head. If the document's current text has had no full /cold-read, run one first. Only by a deliberate decision, yours or the user's: never wired into automation, and a revision of an already-checked document earns no automatic rerun. Only on a document that directs work, a design, a specification, a skill or a plan; never on one that only reports what happened. A full run is six sanity-check-cells, the three sanity-check-attacks with `claude` and the three with `codex`, each a full model run at xhigh reasoning effort taking tens of minutes; say so when you suggest it. A run can be smaller: `--attack` and `--runtime` select a subset, and without a sanity-check-request the two fresh-eyes cells are skipped.

## What to do

1. Read the runner's manual: `scripts/sanity-check-attacks.py --print requester`. It is authoritative for how the runner behaves. This skill repeats the parts you act on. The runner's manual calls an attack an audit; they are one thing.
2. Commit your work first: the cells read a copy of the last commit and see nothing that is uncommitted, and the runner refuses only a target or context document with uncommitted changes.
3. Write the sanity-check-request as the manual's section "Writing the problem statement" says. Its problem statement is extracted from the document's committed text at that commit: what the system must accomplish, never how the document does it, and none of the names the document coined. Its off-limits list must name the document's own paths. Save the file outside the worktree, in the session scratchpad the harness gives you; a run that launches a fresh-eyes cell saves a copy of it in the sanity-check-record, as `sanity-check-request.md`, and every run saves there what it printed before its closing `record:` line, as `sanity-check-run.log`.
4. Run `scripts/sanity-check-attacks.py --target <path> [--context <path> ...] --problem-statement <sanity-check-request path>` as a background task with its output redirected to a file in the session scratchpad. The flag is named for the statement but takes the whole request file. `--context` names documents a reader needs open beside the target; the cut and mechanization cells receive them, the fresh-eyes cells never do, since they read only what the request's read-first list names. The `--attack` values are cut, mechanization and fresh-eyes, the attack names without their suffix; the `--runtime` values are the two agent-binaries, `claude` and `codex`. Arm the Monitor tool on the runner's output for these lines. `saved:` means a report landed; read it now. `RETRYING:` means a cell's first launch saved no report and the runner is launching the cell once more, which needs nothing. `FAILED:` means a cell ended with no report; the line names the cause, and the lines under it say what to do next. `SKIPPED:` means a fresh-eyes cell had no request. `STOPPED:` means a signal ended the run before it finished; run the same command again for the reports the run did not save. `WARNING:` has seven sources: a model that could not run, a model that failed, and a model that produced no review, each of which the runner records and you note; a quoted span found in no tracked file, which you look for in git history or on the web before trusting the quote; a write to the review copy, the copy of the commit that the cells read, outside a cell's scratch directory, which the runner discards with the copy and you note; a stray write at a cell's own report path that the runner overwrote, which needs nothing; and a review copy the runner could not remove, which you delete at the path the warning names. `LEAK-WARNING:` names a coined design name found in the request or in an instruction file the CLIs inject, and the line it is on; a hit on the off-limits paths is expected and needs nothing, any other hit you weigh at triage. The cells read a copy of the commit, so you may keep working in the worktree while they run, but change neither the target nor a context document until the last rerun has ended, because a rerun reads the commit that is last when it starts and the runner refuses either document with uncommitted changes.
5. Reports land in the sanity-check-record, `sanity-check-records/<date>-<target-stem>/` (for a skill, `<date>-<skill directory>-SKILL/`), gitignored, one per cell that saved, named `<attack>-claude` or `<attack>-codex`. A rerun lands in a fresh directory with a `-2`, `-3` suffix, so one sanity-check can own several; all of them are its record. Read each report as it arrives and keep your judgments provisional until every launched cell has saved or failed. When a cell fails, the runner relaunches it once by itself, unless only the user can clear the cause or the cell timed out, and prints under the cell's `FAILED:` line what to do next: do that. An attack left with no report is unreviewed, and `finding-dispositions.md` says so.
6. Triage, after the run ends. Settle a hedged claim about code by reading the code. Compare the provenance lines: every report of one run names the same commit, and a rerun's reports name the commit that was last when the rerun started; if the target or a context document differs between those two commits, the rerun's report reviewed another text, and its findings are triaged apart from the first run's and never merged with them. Read a fresh-eyes report's last section, what it consulted, first: a disclosed off-limits read discounts that report's agreements with the original. Deduplicate the two reports for each attack: the same finding from both `claude` and `codex` is one finding, and where they disagree it is one finding carrying both readings. The attack prompts are `docs/agents/sanity-checker-cut-attack-prompt.md` and its mechanization and fresh-eyes siblings. Judge cut-attack and mechanization-attack findings by what their prompts ask for, which is more than deletion and more than code: a cut names what is lost and what elsewhere goes stale; a mechanization names a mechanism, which may constrain, externalize or verify rather than replace. The fresh-eyes-attack returns two independent designs, one from `claude` and one from `codex`; compare each with the original on its merits. A worry, trap or failure mode a fresh design raises that the original never addresses is a candidate finding; a substantive difference between the designs is a question, put to the user like a finding; the stronger parts of either can feed a best-of-both proposal, put to the user as a finding. Findings are candidate design changes, and none is applied without the user's ruling.
7. Put the surviving findings and questions to the user in an approval-walk with /walk-me-through (`.claude/skills/walk-me-through/`), one at a time, most important first. For each, propose the fix, not a restatement of the finding, and the user rules (user-ruled 2026-09-04, recorded on https://github.com/nedschorus/nedschorus/issues/263). Record every warning followed up, every failed cell, every finding or question set aside, with the reason, and every ruling the approval-walk produces, in `finding-dispositions.md` beside the reports: the approval-walk's walk-minutes are gitignored and nothing ships them, so the record is where a ruling survives. Triage is complete when every `WARNING:`, every followed-up `LEAK-WARNING:`, every finding and every question has been ruled on or set aside with a stated reason. Keep the sanity-check-record after the work it served lands: review records are logs (user-ruled 2026-08-25), and logs belong in the log-store on ned-box. The runner ships the record there when the run ends; after writing `finding-dispositions.md`, run `scripts/sanity-check-record-ship.py <record directory>` so it joins the reports there. A file already in the store whose content differs is refused rather than replaced, so ship the dispositions file once it is finished.
8. Commit the ruled changes on the topic branch, if any were ruled, and cite every sanity-check-record in the pull request description by its place in the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/sanity-check-records/<name>`.

## The user's review criteria

From the approval-walk of 2026-08-10, recorded in the sanity-checker brief: "asking to simplify is like asking to optimize without context." Name the criterion a finding is judged on. This project's criteria, in the order the cut and mechanization prompts apply them: simpler to operate, then simpler to understand, then simpler to build or maintain; mechanical guarantees over trained habit; a detector with no consumer is cost without value; never trade a deterministic script that does the job for probabilistic agent behavior.
