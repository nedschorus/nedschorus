# sanity-check

## When used

After the document's full /cold-read has run and the changes its findings produced are committed, and before its pull request opens, so that the changes the check produces are ordinary commits and not a fix round on a frozen head. If the document's current text has had no full /cold-read, run one first. Only by a deliberate decision, yours or the user's: never wired into automation, and a revision of an already-checked document earns no automatic rerun. Only on a document that directs work, a design, a specification, a skill or a plan; never on one that only reports what happened. A full run is six sanity-check-cells, the three sanity-check-attacks with `claude` and the three with `codex`, each a full model run at xhigh reasoning effort taking tens of minutes; say so when you suggest it. A run can be smaller: `--attack` selects a subset, and without a sanity-check-request the two fresh-eyes cells are skipped.

## What to do

1. Read the runner's manual: `scripts/sanity-check-attacks.py --print requester`. It is authoritative for how the runner behaves. This skill repeats the parts you act on. The runner's manual calls an attack an audit; they are one thing.
2. Commit the document and push the branch first. The provenance line each report opens with names the text the cells read, and on a dirty worktree it names a commit that does not; and the checkout-freshness Stop hook rebases a never-pushed branch onto main at every turn end, while a run spans many, so on an unpushed branch the later reports would read text the earlier ones did not.
3. Write the sanity-check-request as the manual's section "Writing the problem statement" says. Its problem statement is extracted from the document's committed text at that commit: what the system must accomplish, never how the document does it, and none of the names the document coined. Its off-limits list must name the document's own paths. Save the file outside the worktree, in the session scratchpad the harness gives you, and copy it and the runner's output into the sanity-check-record when the run ends, so a later reader can see what the fresh-eyes cells were asked and which warnings the run printed; the runner saves neither.
4. Run `scripts/sanity-check-attacks.py --target <path> [--context <path> ...] --problem-statement <sanity-check-request path>` as a background task with its output redirected to a file in the session scratchpad: a log growing under the sanity-check-record during the run is reported as a cell's write. The flag is named for the statement but takes the whole request file. `--context` names documents a reader needs open beside the target; the cut and mechanization cells receive them, the fresh-eyes cells never do, since they read only what the request's read-first list names. The `--attack` values are cut, mechanization and fresh-eyes, the attack names without their suffix. Arm the Monitor tool on the runner's output for these lines. `saved:` means a report landed; read it now. `FAILED:` means a cell produced no report, or produced text that is not one. `SKIPPED:` means a fresh-eyes cell had no request. `WARNING:` has six sources: a model that could not run, failed, or produced no review, which the runner records and you note; a quoted span found in no tracked file, which you look for in git history or on the web before trusting the quote; a cell that modified the worktree, which you inspect and, if the change is the cell's, revert; and a stray write at a cell's own report path that the runner overwrote, which needs nothing. `LEAK-WARNING:` names a coined design name found in the request or in an instruction file the CLIs inject; a hit on the off-limits paths is expected and needs nothing, any other hit you weigh at triage. While the run is in progress change nothing in the worktree, the sanity-check-record included: the write detector compares against a baseline and cannot tell your edit from a cell's.
5. Reports land in the sanity-check-record, `sanity-check-records/<date>-<target-stem>/`, gitignored, one per cell that saved, named `<attack>-<runtime>`. A rerun lands in a fresh directory with a `-2`, `-3` suffix, so one sanity-check can own several; all of them are its record. Read each report as it arrives and keep your judgments provisional until every launched cell has saved or failed. When a cell fails, rerun its attack alone once with `--attack`, which runs both runtimes again into a fresh `-2` directory; if it fails again, triage that attack from the other runtime's report, and if both runtimes failed, the attack is unreviewed and `finding-dispositions.md` says so.
6. Triage, after the run ends. Settle a hedged claim about code by reading the code. Compare the provenance lines: reports naming different commits mean the tree moved during the run. Read a fresh-eyes report's last section, what it consulted, first: a disclosed off-limits read discounts that report's agreements with the original. Deduplicate the two reports for each attack: the same finding from both runtimes is one finding, and where they disagree it is one finding carrying both readings. The attack prompts are `docs/agents/sanity-checker-cut-attack-prompt.md` and its mechanization and fresh-eyes siblings. Judge cut-attack and mechanization-attack findings by what their prompts ask for, which is more than deletion and more than code: a cut names what is lost and what elsewhere goes stale; a mechanization names a mechanism, which may constrain, externalize or verify rather than replace. The fresh-eyes-attack returns two independent designs, one per runtime; compare each with the original on its merits. A worry, trap or failure mode a fresh design raises that the original never addresses is a candidate finding; a substantive difference between the designs is a question, walked like a finding; the stronger parts of either can feed a best-of-both proposal, walked as a finding. Findings are candidate design changes, and none is applied without the user's ruling.
7. Walk the surviving findings and questions with /walk-me-through (`.claude/skills/walk-me-through/`), one at a time, most important first. For each, propose the fix, not a restatement of the finding, and the user rules (user-ruled 2026-09-04, recorded on https://github.com/nedschorus/nedschorus/issues/263). Record every warning followed up, every failed cell, every finding or question set aside, with the reason, and every ruling the walk produces, in `finding-dispositions.md` beside the reports: the walk's minutes are gitignored and nothing ships them, so the record is where a ruling survives. Triage is complete when every `WARNING:`, every followed-up `LEAK-WARNING:`, every finding and every question has been ruled on or set aside with a stated reason. Keep the sanity-check-record after the work it served lands: review records are logs (user-ruled 2026-08-25), and logs belong in the log-store on ned-box. The runner ships the record there when the run ends; after writing `finding-dispositions.md`, run `scripts/sanity-check-record-ship.py <record directory>` so it joins the reports there. A file already in the store whose content differs is refused rather than replaced, so ship the dispositions file once it is finished.
8. Commit the ruled changes on the topic-branch, if any were ruled, and cite every sanity-check-record in the pull request description by its place in the log-store, `nedlern@ned-box:/home/nedlern/nedschorus-logs/sanity-check-records/<name>`.

## The user's review criteria

From the walk of 2026-08-10, recorded in the sanity-checker brief: "asking to simplify is like asking to optimize without context." Name the criterion a finding is judged on. This project's criteria, in the order the cut and mechanization prompts apply them: simpler to operate, then simpler to understand, then simpler to build or maintain; mechanical guarantees over trained habit; a detector with no consumer is cost without value; never trade a deterministic script that does the job for probabilistic agent behavior.
