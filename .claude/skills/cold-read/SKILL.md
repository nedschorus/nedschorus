# cold-read

## What to do

1. If the user asks for a fast or quick cold-read, skip the full cold-read. If you are cold-reading the walk-me-through MD file, the session handoff, the PR description, an issue body, or CLAUDE.md, also skip the full cold-read. Wiki files, skills and their prompts, the files under `docs/agents/`, designs, test designs, and design contracts need a full cold-read. Everything else gets the fast read only.
2. Run `scripts/cold-read-fast-read.py --target <path>`. It writes a report at `docs/walk/<name>-suggestions.md` for a walk draft or at `cold-read-records/<date>-<name>/<name>-fast-read.md` for any other document, and prints the path. The report shows exactly how a fresh reader interprets this prose, what confused it, and what it thinks is missing from the document. If it prints FAILED, tell the user and stop.
3. Your job is to make sure this prose is correctly understood by a fresh reader. Revise the document accordingly. Fix what it misread, revise the text to resolve its issues, add what is missing. If you do not know how to resolve the fresh reader's problems, or how to fill in what is missing, stop and ask the user to walk through these issues. If this document is not getting a full cold-read, also stop here and run through your changes with the user. The fast read's own report is the record; there is nothing else to write.
4. If you are doing a full cold-read, continue.
5. Run `scripts/cold-read-grid.py --target <path>` as a background task, and arm a Monitor on its output that emits an event per `saved:`, `FAILED`, `STRAY WRITE:`, `WRITE CHECK DID NOT RUN:`, `FELL BACK:`, `RECOVERED:` and `TARGET CHANGED DURING RUN:` line. Each line is addressed to you: `saved:` means a finished review has landed and can be read now; `FAILED` means a cell produced no review, surfacing immediately instead of being discovered at the end (its line opens `FAILED (exit …)`, the one marker of the seven that carries no colon); `STRAY WRITE:` means a reviewer changed a file that was not its own report — inspect it and revert it before triage, which is ordinary cleanup for you rather than something to escalate; `WRITE CHECK DID NOT RUN:` means that check could not run at all for a cell, which is a failure to look rather than a clean result, so run `git status` yourself and revert any file a reviewer changed before you triage; `FELL BACK:` means a cell's first-choice model did not produce a report and names the model that actually wrote the one you are about to read, which needs no action beyond naming that model in `dispositions.md` if its report drives a change; `RECOVERED:` means the model wrote its report under the file name it was given but somewhere else under `cold-read-records/`, and the cell moved it into place — the review is intact, and the line is there so a model that put its report in the wrong directory is not invisible to you; a report written under some other name, or outside that directory, is not looked for and its cell reports `FAILED`; `TARGET CHANGED DURING RUN:` means the document's bytes differed between the moment the cells launched and the moment the last one finished, so the set was read against a document that moved under it and no report in it can be trusted to describe the file as it now stands — the script marks every report in the record directory with a `<!-- TARGET CHANGED DURING RUN: … -->` line and exits 3, and the right response is to stop editing the document and start a new cold-read run rather than to triage a set whose reports may review an earlier version of it. Keep your edits and keep the marked record directory; the new run reads the document as it now stands.
6. It launches six reviewers and saves their reviews to the `cold-read-records/` directory. The reviews exist to be triaged. Read each report as it arrives. Triage as you go, but keep your judgments provisional until every cell has reported or failed. These reports say what the cold readers think your prose means, which words they think are poorly chosen, and which phrases confused them. Those readers have the same context as the agent who is the final consumer of your prose. Do not dismiss a report as stupid or untrue: it is the truth of that reader, even if your own truth, with the context you got from the conversation with the user, seems to you the operative one. The only truth that matters is the one a future agent without your context will understand and act on, which is the cold reader's, not yours and not the user's. When every cell has reported or failed, rewrite the document to fix the issues they found; do not edit it while the cells are still running, because that invalidates every report in the run. When a cell fails, the script's closing text says whether to wait, to carry on, or to rerun that cell alone; follow it.
7. Ask the user before you reject a criticism, when you do not know how to address one, when addressing one would significantly expand a sentence or section, and when it would need a new section. A criticism that goes against a user ruling is not disposed of by that ruling: present the issue, the ruling, and your suggested fix, so the user can rule again. Record every finding you did not apply, with the reason, in `dispositions.md` beside the reports, and keep the record directory after the work it served lands. Commit the rewrite on the branch you cut from main for this change.
8. Then walk the user through all your findings and suggested changes with the walk-me-through skill.
