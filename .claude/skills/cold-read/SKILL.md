# cold-read

## What to do

1. Check the document's terms against the project glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`. Write every project-term as the glossary lists it. For each key-term the glossary does not list, propose it to the user as a project-term, all of them in one message, with a one-sentence definition each. Do not wait for the answer: continue to step 2. Until the user approves a proposed term, the document writes it as plain unhyphenated prose. A term he approves you add to the glossary as its own change; the document takes the hyphenated form in its next edit after that lands on main, never while cold-read-cells are running.
2. If the user asks for a fast or quick cold read, skip the cold-read-full-run. If the cold-read-target is a file under `docs/walk/`, the session-handoff, the PR description, an issue body, or CLAUDE.md, also skip the cold-read-full-run. Wiki files, skills and their prompts, the files under `docs/agents/`, designs, including a GHI-MD that is a design, test designs, and component-contracts need a cold-read-full-run, and so does a change to one of them, with one exception: a change of at most one sentence, or a mechanical one applied by search and replace, such as a rename or a path, gets the cold-read-fast-read instead. An issue body gets the cold-read-fast-read, as above. Neither a PR description nor an issue body is a file on disk, and `scripts/cold-read-fast-read.py` resolves `--target` and exits without launching anything unless it is one: save the text to a file in the session scratchpad and read that. A cold-read-fast-read asked for on a document that needs the cold-read-full-run does not finish that document's review, and the program says so on its own line and in its report. Everything else gets the cold-read-fast-read only.
3. Run `scripts/cold-read-fast-read.py --target <path>`. It prints the path it wrote. For a draft under `docs/walk/` the report is the suggestions file beside it; for anything else it is `fast-read.md` in a new directory under `cold-read-records/`, named for the document and the date, with `SKILL-<skill name>` for a skill and `-2`, `-3` for later reads the same day. The report shows how a fresh-reader interpreted this prose, what confused it, and what it thinks is missing from the document. If it prints a line opening FAILED, tell the user and stop.
4. Your job is to make sure this prose is correctly understood by a fresh-reader. Revise the document accordingly. Fix what it misread, revise the text to resolve its findings, add what is missing. If you do not know how to resolve the fresh-reader's problems, or how to fill in what is missing, stop and put those findings to the user in an approval-walk. If this document is not getting a cold-read-full-run, also stop here and take your changes through an approval-walk with the user. The cold-read-fast-read writes no report but its own; the cold-read-record also holds the frozen copy of the document it read. A draft under `docs/walk/` gets no cold-read-record, only the suggestions file.
5. If you are doing a cold-read-full-run, continue.
6. Run `scripts/cold-read-grid.py --target <path>` as a background task, and arm the Monitor tool on its output so that it emits an event per `saved:`, `RETRYING:`, `FAILED`, `AGENT-BINARY DOWN:`, `STRAY WRITE:`, `WRITE CHECK DID NOT RUN:`, `FELL BACK:`, `RECOVERED:` and `TARGET CHANGED DURING RUN:` line. Without the Monitor tool, read the file the background task writes to, as the run proceeds. Each line is addressed to you: `saved:` means a finished report has arrived and can be read now; `RETRYING:` means a cold-read-cell's first attempt produced no report and it is being relaunched once with the same model, which needs no action; `FAILED` means its retry produced no report either, so that report is absent, with the cause on the line (its line opens `FAILED (exit …)`, the one marker of the nine that carries no colon); `AGENT-BINARY DOWN:` means no cold-read-cell of that agent-binary can still produce a report: each has either arrived or is absent for one shared cause, which the closing text names for you to pass to the user, and reports from that agent-binary that arrived before it went down are still there to triage; `STRAY WRITE:` means a file outside a reviewer's own report changed while that reviewer ran; the cold-read-cell cannot tell who changed it, and you may have been editing in the same checkout, so inspect each file and revert only what the reviewer wrote, which is ordinary cleanup for you rather than something to escalate; `WRITE CHECK DID NOT RUN:` means that check could not run at all for a cold-read-cell, which is a failure to look rather than a clean result, so look yourself before you triage: `git status` tells you what changed but never who changed it, so read what it lists against the edits you know are your own, and revert only what you did not write; `FELL BACK:` means a cold-read-cell's first-choice model did not produce a report and names the model that actually wrote the one you are about to read, which needs no action beyond naming that model in `triage.md` if its report drives a change; `RECOVERED:` means the model wrote its report under the file name it was given but somewhere else under `cold-read-records/`, and the cold-read-cell moved it into place — the report is intact, and the line is there so a model that put its report in the wrong directory is not invisible to you; a report written under some other name, or outside that directory, is not looked for and its cold-read-cell reports `FAILED`; `TARGET CHANGED DURING RUN:` means the cold-read-target's bytes differed between the moment the cold-read-cells launched and the moment the last one finished, so the set was read against a document that changed under it and no report in it can be trusted to describe the file as it now stands — the script marks every report in the cold-read-record with a `<!-- TARGET CHANGED DURING RUN: … -->` line and exits 3, and the right response is to stop editing the document and start a new cold-read-full-run rather than to triage a set whose reports may review an earlier version of it. Keep your edits and keep the marked cold-read-record; the new run reads the cold-read-target as it now stands.
7. It launches six cold-read-cells and saves their reports to the `cold-read-records/` directory. The reports exist to be triaged. Read each report as it arrives. Triage as you go, but keep your judgments provisional until every cold-read-cell has reported or failed. If one cold-read-cell has neither reported nor failed after every other has finished, tell the user and triage what arrived. These reports say what the reviewers think your prose means, which words they think are poorly chosen, which phrases confused them, what defects they found, and which terms fail the tests in `.claude/skills/cold-read/prompts/terminology.md`. Those reviewers stand in for the fresh-reader who will have to act on your prose. Do not dismiss a report as stupid: it is what that reviewer reported understanding, and a fresh-reader without your context may understand it the same way. So favor the reviewer's reading of your words over your own sense of what you meant. A report can still get a fact wrong; record the correction in `triage.md`. If it's a misreading, rephrase your prose to make it unequivocal. If you are uncertain whether or how to clarify prose, ask the user. When every cold-read-cell has reported or failed, rewrite the document to fix the findings they raised; do not edit it while the cold-read-cells are still running, because that invalidates every report in the run. When a cold-read-cell fails, the script's closing text names it and its error; pass an error the user could fix to the user, and triage the reports that arrived unless the closing text says the cold-read-target changed.
8. Ask the user when you: reject a finding; do not know how to address it; your fix would add or remove more than a sentence; the fix is a new project-specific term that is not already a project-term. New proposed terms, whether coined by you or a reviewer, are ruled on by the user. He will accept it, reject it, or direct you to use a standard SDLC term. Record in `triage.md` what new term you proposed and what the user ruled. If he accepts it, add it to `docs/nedschorus-wiki/nedschorus-glossary.md`. If he directs you to a standard SDLC term, add that term to `docs/nedschorus-wiki/nedschorus-sdlc-terms.md`. Do not propose to rename, split or replace a project-term. Do not propose a new project-specific term that is already an SDLC-term. If the user has already ruled on a term, but the ruling was not to add it to the glossary or to the SDLC-terms file, you may present your suggested fix for him to re-rule on. Record every finding you did not apply, with the reason, in `triage.md` beside the reports. A finding about an input you cannot fix here — a document this one relies on — goes in `triage.md` too, with the reason it does not change your result; if you cannot establish that reason, it is a step 4 stop, not a `triage.md` entry. Commit the rewrite on the topic-branch you cut from main for this change.
9. Then take your committed changes and the findings you did not apply to the user in an approval-walk, with the /walk-me-through skill, naming the approval-walk after the cold-read-record; when it closes, write `docs/walk/<record>-dispositions.md`, one line per finding with what was ruled. Then, and not before, run `scripts/cold-read-record-ship.py <cold-read-record>` so the cold-read-record reaches the log-store on ned-box, and keep the directory after the work it served lands on main. It ships after this approval-walk rather than before it, because the approval-walk can overturn a decision already written into `triage.md`, and the store refuses a file it already holds with different bytes: ship last and what the store keeps is what the user ruled. The shipper prints `REFUSED:` when the store holds that file with different bytes, whose remedy it states itself — rename the local directory with a `-2` suffix and ship again — and `FAILED:` when ned-box cannot be reached, where the cold-read-record stays on disk and a later run finishes it; tell the user what it said, remedy included. A document that took the cold-read-full-run gets this approval-walk only; a document that stopped at step 4 gets its approval-walk there.
