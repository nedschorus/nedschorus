# cold-read

## What to do

1. Check the document's terms against the project glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`, and the system glossaries listed at its top. Write every project-term and system-term as its glossary lists it. For each key-term no glossary lists, propose it to the user as a project-term, or as a system-term when only one system uses it, all of them in one message, with a one-sentence definition each. Do not wait for the answer: continue to step 2. Until the user approves a proposed term, the document writes it as plain unhyphenated prose. A term he approves you add to its glossary as its own change; the document takes the hyphenated form in its next edit after that lands on main.
2. If the user asks for a fast or quick cold read, skip the cold-read-full-run. If the cold-read-target is a file under `docs/walk/`, the session-handoff, the PR description, an issue body, or CLAUDE.md, also skip the cold-read-full-run. Wiki files, skills and their prompts, the files under `docs/agents/`, designs, including a GHI-MD that is a design, test-designs, and design-contracts need a cold-read-full-run, and so does a change to one of them, except these changes, which get the cold-read-fast-read instead: a change of at most one sentence; a mechanical change applied by search and replace, such as a rename or a path; and a change that touches only the document's section headed `Deferred-decisions`. The rewrite that answers a cold-read-full-run, and the commit that carries out the user's rulings on it, get the cold-read-fast-read, run as step 3 says, unless the rewrite changes what the document decides beyond what the findings asked; then it gets another cold-read-full-run, counted toward the three. A change to a document gets at most three cold-read-full-runs before the user decides whether it gets more. `nc-systems/cold-read/cold-read-grid.py` counts them and refuses a fourth: at launch it prints a line such as "cold-read-full-run 2 of 3 for SKILL.md.", counting the runs of this document made since origin/main last took a change to it that saved at least one report, did not stop because its frozen-copy changed, and whose records reached the log-store or are in this checkout. State the count in the opening of the run's cold-read approval-walk, or in step 9's one line when the run has no approval-walk. When the grid refuses a fourth, bring the user, for each run it names, the number of findings that run's `triage.md` lists, in the log-store or in this checkout, or that the run has no `triage.md`, and ask whether to stop, run again, or change the document's design: on stop, the document gets no further cold-read-full-run and goes to the user to read as it stands; on run again, run the grid with `--user-ruled-cold-read-full-run-count-restart`, which starts the count again at 1 of 3; on change the design, make the change the user directs, then run the grid with that flag. Give the flag only on the first run after the user's ruling; the run it starts leaves a marker in its cold-read-record, and later runs count from it. When the grid prints `EARLIER COLD-READ-FULL-RUNS NOT COUNTED:` instead of a count, the run goes ahead uncounted: tell the user what the line says. An issue body gets the cold-read-fast-read, as above. Neither a PR description nor an issue body is a file on disk, and `nc-systems/cold-read/cold-read-fast-read.py` resolves `--target` and exits without launching anything unless it is one: save the text to a file in the session scratchpad and read that. A cold-read-fast-read asked for on a document that needs the cold-read-full-run does not finish that document's review, and the program says so on its own line and in its report. Everything else gets the cold-read-fast-read only.
3. Run `nc-systems/cold-read/cold-read-fast-read.py --target <path>`. It prints the path it wrote. For a draft under `docs/walk/` the report is the suggestions file beside it; for anything else it is `fast-read.md` in a new directory under `cold-read-records/`, named for the document and the date, with `SKILL-<skill name>` for a skill and `-2`, `-3` for later reads the same day. The report shows how a fresh-reader interpreted this prose, what confused it, and what it thinks is missing from the document. If it prints a line opening FAILED, tell the user and stop. If it prints a line opening `#cold_read_target_changed_during_run`, the document changed while the reviewer read it: triage the report against the copy the reviewer was given, whose sentences the report quotes, then carry each fix to the document as it now stands.
4. Your job is to make sure this prose is correctly understood by a fresh-reader. Revise the document accordingly. Fix what it misread, revise the text to resolve its findings, add what is missing. If you do not know how to resolve the fresh-reader's problems, or how to fill in what is missing, ask the user before going on. If this document is not getting a cold-read-full-run, commit the revision on the topic branch you cut from main for this change, or, for a text that is not a file in the repository, keep the revised file beside the original, and go to step 9; a draft under `docs/walk/` is the exception: apply its suggestions without asking the user and without recording them. The cold-read-fast-read writes no report but its own; the cold-read-record also holds the frozen-copy of the document it read. A draft under `docs/walk/` gets no cold-read-record, only the suggestions file.
5. If you are doing a cold-read-full-run, continue.
6. Run `nc-systems/cold-read/cold-read-grid.py --target <path>` as a background task, and arm the Monitor tool on its output so that it emits an event per `cold-read-full-run`, `EARLIER COLD-READ-FULL-RUNS NOT COUNTED:`, `saved:`, `RETRYING:`, `FAILED`, `AGENT-BINARY DOWN:`, `STRAY WRITE:`, `WRITE CHECK DID NOT RUN:`, `FELL BACK:`, `RECOVERED:`, `#frozen_copy_changed_during_run` and `#cold_read_target_changed_during_run` line. Without the Monitor tool, read the file the background task writes to, as the run proceeds. Each line is addressed to you: `cold-read-full-run` gives the count step 2 describes; `EARLIER COLD-READ-FULL-RUNS NOT COUNTED:` means the run went ahead uncounted, which step 2 says to tell the user; `saved:` means a finished report has arrived and can be read now; `RETRYING:` means a cold-read-cell's first attempt produced no report and it is being relaunched once with the same model, which needs no action; `FAILED` means its retry produced no report either, so that report is absent, with the cause on the line (its line opens `FAILED (exit …)`, one of the two markers that carry no colon); `AGENT-BINARY DOWN:` means no cold-read-cell of that agent-binary can still produce a report: each has either arrived or is absent for one shared cause, which the closing text names for you to pass to the user, and reports from that agent-binary that arrived before it went down are still there to triage; `STRAY WRITE:` means a file outside a reviewer's own report changed while that reviewer ran; the cold-read-cell cannot tell who changed it, and you may have been editing in the same checkout, so inspect each file and revert only what the reviewer wrote, which is ordinary cleanup for you rather than something to escalate; `WRITE CHECK DID NOT RUN:` means that check could not run at all for a cold-read-cell, which is a failure to look rather than a clean result, so look yourself before you triage: `git status` tells you what changed but never who changed it, so read what it lists against the edits you know are your own, revert only what a reviewer evidently wrote, and ask the user about any other change you did not make; `FELL BACK:` means a cold-read-cell's first-choice model did not produce a report and names the model that actually wrote the one you are about to read, which needs no action beyond naming that model in `triage.md` if its report drives a change; `RECOVERED:` means the model wrote its report under the file name it was given but somewhere else under `cold-read-records/`, and the cold-read-cell moved it into place — the report is intact, and the line is there so a model that put its report in the wrong directory is not invisible to you; a report written under some other name, or outside that directory, is not looked for, and its cold-read-cell is relaunched (`RETRYING:`), and reports `FAILED` if the retry does the same; `#frozen_copy_changed_during_run` means the frozen-copy that every cold-read-cell reads, under the cold-read-record's `target/`, changed after the cold-read-cells launched, so no report can say which text it reviewed — the script stops every cold-read-cell still running as soon as it sees the change, marks every report in the cold-read-record with a `<!-- #frozen_copy_changed_during_run … -->` line and exits 3, and the right response is to find what edited the frozen-copy and start a new cold-read-full-run. Keep the marked cold-read-record. A run stopped this way does not count toward the three, so the new run is never refused as a fourth; the third such stop in a row ends the attempt, and the closing text then says not to start a new run: tell the user, and ask whether to stop, to run again with `--user-ruled-cold-read-full-run-count-restart`, or to change the document's design first and then run again with that flag. `#cold_read_target_changed_during_run`, printed once when the run ends, means the cold-read-target itself was edited after the cold-read-cells launched; every report reviews the frozen-copy, which the line names, so nothing is stopped and the set stands: triage it against the frozen-copy, then carry each fix to the cold-read-target as it now stands. When both lines appear, the frozen-copy changed too, so `#frozen_copy_changed_during_run` decides and the set does not stand.
7. It launches six cold-read-cells and saves their reports to the `cold-read-records/` directory. The reports exist to be triaged. Read each report as it arrives. Triage as you go, but keep your judgments provisional until every cold-read-cell has reported or failed. If one cold-read-cell has neither reported nor failed after every other has finished, tell the user and triage what arrived. These reports say what the reviewers think your prose means, which words they think are poorly chosen, which phrases confused them, what defects they found, and which terms fail the tests in `.claude/skills/cold-read/prompts/terminology.md`. Those reviewers stand in for the fresh-reader who will have to act on your prose. Do not dismiss a report as stupid: it is what that reviewer reported understanding, and a fresh-reader without your context may understand it the same way. So favor the reviewer's reading of your words over your own sense of what you meant. A misreading that one reviewer reports is a problem even when the other reviewers read the passage correctly: the problem list is the union of the reports, not their intersection, because a passage that one careful reader in six misreads could be misread by future heavily loaded and distracted agents. A factual claim in a report is different: check it against its source, and when the report has the fact wrong, record the correction in `triage.md`. If it's a misreading, rephrase your prose to make it unequivocal. When you answer a finding by writing about what a program prints or does, first check what the program really prints or does. If you are uncertain whether or how to clarify prose, ask the user. When the document is a design of work not yet built, including a GHI-MD that is a design, you may defer a class (g) finding instead of fixing it — a finding, under class (g) of `.claude/skills/cold-read/prompts/defect-hunt.md`, that the design does not say what happens in a case its program, procedure or file will meet — when the design's build or later evidence will settle that case: add one line naming the case to the design's section headed `Deferred-decisions`, creating that section at the end of the design if it has none, and record the finding as deferred in the cold-read-record's `triage.md`. For example, a finding that the design never says how long a test run may take before it is stopped is deferred as the line "The test runs' time limit, to be set from the first runs' durations." The line stays until the build or the evidence settles the case; whoever settles it then removes the line and writes the decision into the design's body. A case is the user's to settle, not deferred this way, when its answer changes what the user sees or must do, such as whether a failed test run is retried silently or reported to the user; such a finding goes to the user under step 9, and the user may rule it into the design's deferred-decisions. A deferred finding does not go to the user under step 9. When every cold-read-cell has reported or failed, rewrite the document to fix the findings they raised. Every report cites lines of the frozen-copy, so read each finding against that copy before you apply it to the document. An edit to the document while the cold-read-cells are still running stops nothing, because they read the frozen-copy; never edit the frozen-copy itself, because that stops the run. When a cold-read-cell fails, the script's closing text names it and its error; pass an error the user could fix to the user, and triage the reports that arrived unless the closing text says the frozen-copy changed.
8. Ask the user when you do not know how to address a finding, or when the fix is a new project-specific term that is not already a project-term. New proposed terms, whether coined by you or a reviewer, are ruled on by the user. He will accept it, reject it, or direct you to use an SDLC-term. Record in `triage.md` what new term you proposed and what the user ruled. If he accepts it, add it to `docs/nedschorus-wiki/nedschorus-glossary.md`, or, for a term only one system uses, to that system's glossary, listed at the top of the project glossary. If he directs you to an SDLC-term, add that term to `docs/nedschorus-wiki/nedschorus-sdlc-terms.md`. Do not propose to rename, split or replace a project-term. Do not propose a new project-specific term that is already an SDLC-term. If the user has already ruled on a term, but the ruling was not to add it to the glossary or to the SDLC-terms file, you may present your suggested fix for him to re-rule on. Record every finding you declined, with the reason, in `triage.md` beside the reports. A finding about an input you cannot fix here — a document this one relies on — goes in `triage.md` too, with the reason it does not change your result; if you cannot establish that reason, it is a step 4 stop, not a `triage.md` entry. Commit the rewrite on the topic branch you cut from main for this change.
9. Then find what goes to the user: every change you applied that adds, alters or removes what a program or an agent does, must do or may do, or what the document decides or plans, and every finding you declined that would have made such a change. A finding step 7 deferred, and the line it added to `Deferred-decisions`, do not go to the user. A correction of past events, of a citation or a reference, or of spelling or punctuation that leaves a sentence's meaning unchanged, does not go to the user. When you cannot tell, it goes to the user. Then give one fresh-agent the diff of your committed rewrite and the declined findings with their reasons, and have it pick out what goes to the user by the same rule, without your list; whatever either of you picks goes to the user, and if the fresh-agent fails or returns nothing, say so in the approval-walk's opening, or in the one line when there is no approval-walk. Here the cold-read-record is the last cold-read-full-run's record when the document had one, and otherwise the cold-read-fast-read's; record the step 4 fast read's findings in that same `triage.md`. Take those to the user in one approval-walk with the /walk-me-through skill, named after the cold-read-record, opening with the one item that most alters what an agent will do, and its downside. Carry out the user's rulings in one commit on top: undo each change he rejects, apply each declined finding he accepts, and rewrite as he directs. If nothing goes to the user, there is no approval-walk: tell the user in one line how many changes you applied. Record every finding at the end of the cold-read-record's `triage.md`, creating the file if the run wrote none, one line each with what was applied, deferred, declined or ruled. Then, and not before, run `nc-systems/cold-read/cold-read-record-ship.py <cold-read-record>` so the cold-read-record reaches the log-store on ned-box, and keep the directory after the work it served lands on main. It ships last, so that what the store keeps is what the user ruled. The shipper prints `REFUSED:` when the store already holds one of the record's files, other than `triage.md`, with different bytes, whose remedy it states itself — rename the local directory with a `-2` suffix and ship again — and `FAILED:` when ned-box cannot be reached, where the cold-read-record stays on disk until you run the shipper on it again, or run `nc-systems/cold-read/cold-read-record-ship.py --all`; tell the user what it said, remedy included. Every document this skill reviews, except a draft under `docs/walk/`, goes through this step, whether it took the cold-read-full-run or stopped at step 4.
