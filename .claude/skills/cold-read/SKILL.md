# cold-read

## What to do

1. Check the document's terms against the project glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`, and the system glossaries listed at its top. Write every project-term and system-term as its glossary lists it. For each key-term no glossary lists, propose it to the user as a project-term, or as a system-term when only one system uses it, all of them in one message, with a one-sentence definition each. Do not wait for the answer: continue to step 2. Until the user approves a proposed term, the document writes it as plain unhyphenated prose. A term he approves you add to its glossary as its own change; the document takes the hyphenated form in its next edit after that lands on main, never while cold-read-cells are running.
2. If the user asks for a fast or quick cold read, skip the cold-read-full-run. If the cold-read-target is a file under `docs/walk/`, the session-handoff, the PR description, an issue body, or CLAUDE.md, also skip the cold-read-full-run. Wiki files, skills and their prompts, the files under `docs/agents/`, designs, including a GHI-MD that is a design, test designs, and design-contracts need a cold-read-full-run, and so does a change to one of them, except these changes, which get the cold-read-fast-read instead: a change of at most one sentence; a mechanical change applied by search and replace, such as a rename or a path; and a change that touches only the document's section headed `Deferred-decisions`. A change to a document gets at most three cold-read-full-runs before the user decides whether it gets more. `nc-systems/cold-read/cold-read-grid.py` counts them and refuses a fourth: its first line, such as "cold-read-full-run 2 of 3", counts the runs of this document made since origin/main last took a change to it, whose records reached the log-store or are in this checkout, and a run stopped by `TARGET CHANGED DURING RUN:` counts too. State the count in the opening of the run's cold-read approval-walk, or in step 9's one line when the run has no approval-walk. When the grid refuses a fourth, bring the user, for each run it names, the number of findings that run's `triage.md` in the log-store lists, or that the run has none, and ask whether to stop, run again, or change the document's design: on stop, the document gets no further cold-read-full-run and goes to the user to read as it stands; on run again, run the grid with `--user-ruled-another-cold-read-full-run`, which starts the count again at 1 of 3; on change the design, make the change the user directs, then run the grid with that flag. When the grid prints `COUNT NOT CHECKED:` instead of a count, the run goes ahead uncounted: tell the user what the line says. An issue body gets the cold-read-fast-read, as above. Neither a PR description nor an issue body is a file on disk, and `nc-systems/cold-read/cold-read-fast-read.py` resolves `--target` and exits without launching anything unless it is one: save the text to a file in the session scratchpad and read that. A cold-read-fast-read asked for on a document that needs the cold-read-full-run does not finish that document's review, and the program says so on its own line and in its report. Everything else gets the cold-read-fast-read only.
3. Run `nc-systems/cold-read/cold-read-fast-read.py --target <path>`. It prints the path it wrote. For a draft under `docs/walk/` the report is the suggestions file beside it; for anything else it is `fast-read.md` in a new directory under `cold-read-records/`, named for the document and the date, with `SKILL-<skill name>` for a skill and `-2`, `-3` for later reads the same day. The report shows how a fresh-reader interpreted this prose, what confused it, and what it thinks is missing from the document. If it prints a line opening FAILED, tell the user and stop.
4. Your job is to make sure this prose is correctly understood by a fresh-reader. Revise the document accordingly. Fix what it misread, revise the text to resolve its findings, add what is missing. If you do not know how to resolve the fresh-reader's problems, or how to fill in what is missing, stop and put those findings to the user in an approval-walk. If this document is not getting a cold-read-full-run, also stop here, and take your changes to the user as step 9 says, except for a draft under `docs/walk/`, whose suggestions you apply without asking the user and without recording them. The cold-read-fast-read writes no report but its own; the cold-read-record also holds the frozen copy of the document it read. A draft under `docs/walk/` gets no cold-read-record, only the suggestions file.
5. If you are doing a cold-read-full-run, continue.
6. Run `nc-systems/cold-read/cold-read-grid.py --target <path>` as a background task, and arm the Monitor tool on its output so that it emits an event per `saved:`, `RETRYING:`, `FAILED`, `AGENT-BINARY DOWN:`, `STRAY WRITE:`, `WRITE CHECK DID NOT RUN:`, `FELL BACK:`, `RECOVERED:` and `TARGET CHANGED DURING RUN:` line. Without the Monitor tool, read the file the background task writes to, as the run proceeds. Each line is addressed to you: `saved:` means a finished report has arrived and can be read now; `RETRYING:` means a cold-read-cell's first attempt produced no report and it is being relaunched once with the same model, which needs no action; `FAILED` means its retry produced no report either, so that report is absent, with the cause on the line (its line opens `FAILED (exit …)`, the one marker of the nine that carries no colon); `AGENT-BINARY DOWN:` means no cold-read-cell of that agent-binary can still produce a report: each has either arrived or is absent for one shared cause, which the closing text names for you to pass to the user, and reports from that agent-binary that arrived before it went down are still there to triage; `STRAY WRITE:` means a file outside a reviewer's own report changed while that reviewer ran; the cold-read-cell cannot tell who changed it, and you may have been editing in the same checkout, so inspect each file and revert only what the reviewer wrote, which is ordinary cleanup for you rather than something to escalate; `WRITE CHECK DID NOT RUN:` means that check could not run at all for a cold-read-cell, which is a failure to look rather than a clean result, so look yourself before you triage: `git status` tells you what changed but never who changed it, so read what it lists against the edits you know are your own, and revert only what you did not write; `FELL BACK:` means a cold-read-cell's first-choice model did not produce a report and names the model that actually wrote the one you are about to read, which needs no action beyond naming that model in `triage.md` if its report drives a change; `RECOVERED:` means the model wrote its report under the file name it was given but somewhere else under `cold-read-records/`, and the cold-read-cell moved it into place — the report is intact, and the line is there so a model that put its report in the wrong directory is not invisible to you; a report written under some other name, or outside that directory, is not looked for and its cold-read-cell reports `FAILED`; `TARGET CHANGED DURING RUN:` means the cold-read-target's bytes changed after the cold-read-cells launched, so the set was read against a document that changed under it and no report in it can be trusted to describe the file as it now stands — the script stops every cold-read-cell still running as soon as it sees the change, marks every report in the cold-read-record with a `<!-- TARGET CHANGED DURING RUN: … -->` line and exits 3, and the right response is to stop editing the document and start a new cold-read-full-run rather than to triage a set whose reports may review an earlier version of it. Keep your edits and keep the marked cold-read-record; the new run reads the cold-read-target as it now stands.
7. It launches six cold-read-cells and saves their reports to the `cold-read-records/` directory. The reports exist to be triaged. Read each report as it arrives. Triage as you go, but keep your judgments provisional until every cold-read-cell has reported or failed. If one cold-read-cell has neither reported nor failed after every other has finished, tell the user and triage what arrived. These reports say what the reviewers think your prose means, which words they think are poorly chosen, which phrases confused them, what defects they found, and which terms fail the tests in `.claude/skills/cold-read/prompts/terminology.md`. Those reviewers stand in for the fresh-reader who will have to act on your prose. Do not dismiss a report as stupid: it is what that reviewer reported understanding, and a fresh-reader without your context may understand it the same way. So favor the reviewer's reading of your words over your own sense of what you meant. A misreading that one reviewer reports is a problem even when the other reviewers read the passage correctly: the problem list is the union of the reports, not their intersection, because a passage that one careful reader in six misreads could be misread by future heavily loaded and distracted agents. A factual claim in a report is different: check it against its source, and when the report has the fact wrong, record the correction in `triage.md`. If it's a misreading, rephrase your prose to make it unequivocal. When you answer a finding by writing about what a program prints or does, first check what the program really prints or does. If you are uncertain whether or how to clarify prose, ask the user. When the document is a design of work not yet built, including a GHI-MD that is a design, you may defer a class (g) finding instead of fixing it — a finding, under class (g) of `.claude/skills/cold-read/prompts/defect-hunt.md`, that the design does not say what happens in a case its program, procedure or file will meet — when the design's build or later evidence will settle that case: add one line naming the case to the design's section headed `Deferred-decisions`, creating that section at the end of the design if it has none, and record the finding as deferred in the cold-read-record's `triage.md`. For example, a finding that the design never says how long a test run may take before it is stopped is deferred as the line "The test runs' time limit, to be set from the first runs' durations." The line stays until the build or the evidence settles the case; whoever settles it then removes the line and writes the decision into the design's body. A case is the user's to settle, not deferred this way, when its answer changes what the user sees or must do, such as whether a failed test run is retried silently or reported to the user; such a finding goes to the user under step 9, and the user may rule it into the design's deferred-decisions. A deferred finding does not go to the user under step 9. When every cold-read-cell has reported or failed, rewrite the document to fix the findings they raised; do not edit it while the cold-read-cells are still running, because that invalidates every report in the run. When a cold-read-cell fails, the script's closing text names it and its error; pass an error the user could fix to the user, and triage the reports that arrived unless the closing text says the cold-read-target changed.
8. Ask the user when you do not know how to address a finding, or when the fix is a new project-specific term that is not already a project-term. New proposed terms, whether coined by you or a reviewer, are ruled on by the user. He will accept it, reject it, or direct you to use a standard SDLC term. Record in `triage.md` what new term you proposed and what the user ruled. If he accepts it, add it to `docs/nedschorus-wiki/nedschorus-glossary.md`, or, for a term only one system uses, to that system's glossary, listed at the top of the project glossary. If he directs you to a standard SDLC term, add that term to `docs/nedschorus-wiki/nedschorus-sdlc-terms.md`. Do not propose to rename, split or replace a project-term. Do not propose a new project-specific term that is already an SDLC-term. If the user has already ruled on a term, but the ruling was not to add it to the glossary or to the SDLC-terms file, you may present your suggested fix for him to re-rule on. Record every finding you declined, with the reason, in `triage.md` beside the reports. A finding about an input you cannot fix here — a document this one relies on — goes in `triage.md` too, with the reason it does not change your result; if you cannot establish that reason, it is a step 4 stop, not a `triage.md` entry. Commit the rewrite on the topic branch you cut from main for this change.
9. Then find what goes to the user: every change you applied that adds, alters or removes what a program or an agent does, must do or may do, or what the document decides or plans, and every finding you declined that would have made such a change. A finding step 7 deferred, and the line it added to `Deferred-decisions`, do not go to the user. A correction of past events, of a citation or a reference, or of spelling or punctuation that leaves a sentence's meaning unchanged, does not go to the user. When you cannot tell, it goes to the user. Then give one fresh-agent the diff of your committed rewrite and the declined findings with their reasons, and have it pick out what goes to the user by the same rule, without your list; whatever either of you picks goes to the user, and if the fresh-agent returns no list, say so in the approval-walk's opening. Take those to the user in one approval-walk with the /walk-me-through skill, named after the cold-read-record, opening with the one item that most alters what an agent will do, and its downside. Carry out the user's rulings in one commit on top: undo each change he rejects, apply each declined finding he accepts, and rewrite as he directs. If nothing goes to the user, there is no approval-walk: tell the user in one line how many changes you applied. Record every finding at the end of the cold-read-record's `triage.md`, creating the file if the run wrote none, one line each with what was applied, deferred, declined or ruled. Then, and not before, run `nc-systems/cold-read/cold-read-record-ship.py <cold-read-record>` so the cold-read-record reaches the log-store on ned-box, and keep the directory after the work it served lands on main. It ships last, so that what the store keeps is what the user ruled. The shipper prints `REFUSED:` when the store already holds one of the record's files, other than `triage.md`, with different bytes, whose remedy it states itself — rename the local directory with a `-2` suffix and ship again — and `FAILED:` when ned-box cannot be reached, where the cold-read-record stays on disk and a later run finishes it; tell the user what it said, remedy included. Every document but a draft under `docs/walk/` gets this one approval-walk, whether it took the cold-read-full-run or stopped at step 4.
