name: d-review
description: Adversarially review a WRITTEN design, specification, or doctrine document before anything is built from it, and before it lands — a design pair doc, an architecture spec, a skill file, a CLAUDE.md or rule change. The document must already exist; this skill judges it, never co-writes it. Two modes: a design-soundness checklist for proposals (unvalidated assumptions, designed-vs-built conflation, discipline dressed as enforcement, dropped failure modes, over-complexity, unbounded growth, build-order risk, naming), and a sentence-level clarity review for doctrine and instruction files (isolated restatement plus adversarial-literal passes across capability tiers and runtimes). Not for code correctness, and not for reviewing an implementation against its design. Use when a document is about to be built from or landed, or when the boss says "d-review this" — his ask wins over the exclusions.

# Design review (d-review)

Review a written document before its content gets expensive: a finished design before anything is built from it, and doctrine before it binds readers. The document must exist and be complete enough to judge — reviewing is judging the written artifact, never co-writing it. **Review never creates — a finding explains, it does not prescribe (boss-ruled 2026-08-04):** a finding makes the defect fully understood — exactly what is wrong, under what conditions it does harm, and why — completely enough that the author can fix it without asking the reviewer anything. Designing the fix belongs to the author, and a reviewer who wants to propose an alternative design has left review — that is a create-design task, owned separately.

A design that reads as coherent can still rest on an unvalidated assumption, conflate designed with built, lean a load-bearing guarantee on agent discipline, or silently drop a failure mode — defects far cheaper to fix in the document than after the build. A shipped instruction file fails differently: one sentence that is ambiguous, self-contradictory, or literally wrong, which a sympathetic reader silently repairs and usually never reports. The fixed checklists below keep the review consistent instead of mood-dependent.

## Input and mode choice

Input: the path to the document — a pair doc (`docs/issues/<n>-<slug>.md`, an issue's companion document), a spec (`docs/cross-project/`), a skill file, CLAUDE.md, a rule page (paths relative to the repo root). If no target is given, ask which document to review. Pick the mode by what the document IS, not by the state of the system around it: a design nothing has been built from yet gets the soundness checklist; a doctrine or instruction file gets the clarity review; a document that is both — doctrine carrying designed mechanisms — gets both, in separate passes.

## Steps

Steps 1–4 and 6 apply in both modes; step 5 is discharged by the clarity matrix in mode 2.

1. **Read the whole document, in full — not a skim.** Identify the load-bearing claims: the statements the design depends on being true. Those get the hardest scrutiny.
2. **Write out your understanding of each mechanism, rule, and load-bearing claim — subtleties elucidated — before hunting defects:** edge behavior, boundary conditions, what is not covered, what it does to adjacent state; as exact as the document permits, with unresolved gaps listed as gaps rather than filled by guessing. A divergence between your written understanding and the document's words is a finding — after ruling out that you simply misread clear text: either the document permitted your misreading, or your correct model contradicts it. A live specimen of the cost of skipping this: a review once passed the confidently false sentence "uncommitted work has no copy outside the conversation" — a written-out model of the boundary collides with that class of sentence, since on this project's runtime, files on disk survive session restarts. Known limit: if the document and the reviewer are wrong the same way, no restatement reliably detects it; that is what step 4 and the independent passes are for. (This step is invoker-side preparation — in mode 2, the delegated restate cells do their paraphrasing separately and innocently.)
3. **Run the chosen mode's checklist.** Every finding names the specific location and explains the defect to fix-ready depth — what is wrong, when it does harm, why — never a vague concern, never a proposed fix, and **never a severity or importance rating** (boss-ruled 2026-08-04): a reviewer without context cannot rate importance, and an out-of-context rating anchors every later reader. A cell states only its own confidence — sure, or unsure and why. Coverage over self-censorship: report what you are unsure of, with the uncertainty stated; filtering is the synthesis's job.
4. **Spot-check the cheap, label the rest — load-bearing claims only (boss-ruled 2026-08-04: verifying everything is overreach).** When a load-bearing claim can be settled by one command or one file-read — a cited file exists, a quoted line matches, a commit landed — check it: designs' own existence labels are where they lie to themselves (the standing specimen: a backup script everyone believed ran, whose output directory had zero commits in the repository's history). When checking would be hard, laborious, or impossible, do not attempt it — mark the claim *unverified*, and let that label feed lens 7's measured-or-believed judgment; the label is the deliverable. Exhaustive mechanical checking belongs to code when it is worth doing at all, never to a reviewer's afternoon.
5. **Get independent passes.** One reader anchored in one context misses what fresh eyes catch, and an author reviewing their own text has the worst of it — the weak parts are already rationalized. Dispatch fresh subagents against the same document, spawned with nothing but the task (no session context rides along), on each available runtime. For a doctrine file, the clarity-review matrix below IS this step.
6. **Write the findings.** The invoker — the one agent holding full context — assigns each finding's severity here, and only here: HIGH = following the words does the wrong thing and the wrongness costs something real; MED = competent readers diverge; LOW = friction, likely recovered. An unconfirmed high-consequence finding is HIGH (unconfirmed), never buried. Order by severity, consequence breaking ties, each explained to fix-ready depth. Name what is solid where anything is — and say plainly when nothing is. End with one line: sound · sound-with-named-risks · not-ready-because-X, where X is the single blocking reason.

## Mode 1 — the design-soundness checklist

**Running it:** the lenses fan out — one focused agent per lens or per related group (grouping is the invoker's call), each handed the document and its question; the invoker synthesizes. No single reviewer walks the full lens set inside one context when delegation is available; with no subagent facility, one reviewer working the lenses serially is the accepted degraded mode. **A re-review always reads the whole document (boss-ruled 2026-08-04)** — design defects are global, and an edit collides with unedited text as often as with itself (measured: several of the first full-grid run's catches were changed-versus-unchanged conflicts). What scales with revision size is the reviewer count, never the text scope: a light revision may earn a single good-tier pass over the full document plus verification of each prior finding's fix; a heavy revision earns the full grid. The reviewable unit is the whole file — and doctrine and design files stay small and atomic partly so that whole-file review stays practical.

1. **Unvalidated runtime-boundary claims.** A load-bearing claim resting on first-principles reasoning about how the runtime behaves — what loads when, hook ordering, what a session can and cannot see — needs an empirical probe (or an authoritative contract that specifies the behavior), not assumption. Conversely, do not manufacture a probe for a fact true by construction — one that follows from the artifact's own definition, so its falsity would make the mechanism itself pointless. Demand probes for genuine unknowns; stake level is not the discriminator.
2. **EXISTS-vs-NEW honesty.** Anything labeled as existing that is only designed or proposed (or the reverse) is flagged — the biggest source of design confusion we have observed. Verify each label against ground truth (step 4).
3. **How each rule is backed — stated honestly.** Every load-bearing rule in a design is backed by something: an enforcement point (a gate, a check, a tool boundary) or a written instruction agents follow. The review checks that the document says which, truthfully: a claimed mechanism must actually exist (lens 2 verifies it), and a written instruction must be labeled as what it is. The finding is discipline presented as enforcement — a false claim about how the rule is backed. A design may freely specify what becomes code and what stays a written instruction; those are ordinary design decisions. Re-evaluating that split — "this prompt rule should be code," or the reverse — is a different problem set, out of this review's scope (boss-ruled 2026-08-04; the question lives per-candidate on [the what-can-code-check issue, nedschorus#42](https://github.com/nedschorus/nedschorus/issues/42)) — unless the code-versus-prompts choice is itself the subject of the document or section under review, in which case it is reviewed like any other design decision.
4. **Gaps and silently-dropped cases — enumerate, don't recall.** For each mechanism, walk the state space systematically: actor states (busy, idle, mid-turn, dead), dependency failures (the file it reads, the tool it runs, the channel it writes), concurrency (two sessions, re-entry, repeated firing) — and require the document to name or explicitly discard the reachable, consequential cells. The enumeration prompts the reviewer; it does not bind the document to a transcript of every cell. A reachable, relevant omission is a finding even when the happy path is flawless — the best catches live in cells the design's own story never visits.
5. **Over-complexity — what can be cut.** Machinery whose value does not justify its cost. Two named smells: *unnecessary tracked state* — state the design maintains that a state-agnostic mechanism would obviate; and a *compensating mechanism* — machinery papering over a gap that a simpler primitive would eliminate outright. The finding names the simpler mechanism that suffices — not as a proposal, but as the evidence that the machinery is over-complex.
6. **Internal consistency.** The document contradicting itself, its own stated principles, or the project's recorded rulings — the governing plan documents and issue bodies, which the lens agent is given alongside the document. Internal inconsistency is strong evidence of an unexamined call; confirm the exception is not deliberate before flagging.
7. **Reliability grounding.** Each load-bearing mechanism is measured (probe, canary, field observation), guaranteed (by definition or an authoritative contract — lens 1's by-construction class), or merely believed. Believed plus load-bearing is a named risk until measured.
8. **Build-order sanity.** Does the order remove the highest live risk first — ranked by probability times the cost of late discovery? Is the highest-value piece scheduled sensibly or buried behind lower-value work?
9. **Scale and growth.** Potentially unbounded data the design accumulates needs a stated bound — retention, archival, or the project's artifact-lifecycle rule that every accumulating store has a named home and a drain — plus a rough volume expectation. Unbounded growth with correctness-only thinking is a default blind spot; flag the missing bound even when the ceiling looks far off.
10. **Test-plan completeness — cooperative AND adversarial.** A plan that maps the design's own cells is necessary but, unless it includes generative techniques (fuzzing, property tests), only exercises what the design thought of. Where the designed thing has an executable surface, require a second, adversarial layer — load, scale, "what did we not anticipate" — that does not assume the design is right.
11. **Naming.** A name, for this lens, is an identifier that anything outside the document will use to find or invoke the thing (boss-scoped 2026-08-04): file and directory names; script, function, and command names; skill names; issue and test labels; defined terms other documents will cite. Ordinary prose vocabulary, one-off words, and local labels defined where they are used (a tier scheme, a severity scale) are not names and are out of this lens's scope. Every in-scope name must be self-documenting and greppable: full words a search matches verbatim, one shared token across a family of related names, no cryptic abbreviations, no bare sequence labels, and no bare numeric issue references in prose (the number must ride with a descriptive handle). Expect almost every truly self-documenting name to run two to five words (boss calibration 2026-08-03): a one-word name is a finding candidate by default when the word is generic or collides in context (`parser`, `data`, `manager`); domain-standard tokens (`README`, `checksum`, `SHA-256`) pass. A longer precise name beats a short ambiguous one, and ease of typing is not a constraint. A bad name in a design propagates into code, tests, and doctrine — flag it here, where the rename is still cheap.

## Mode 2 — the clarity review (doctrine and instruction files)

The failure mode is sentence-level: a reader who cannot follow a sentence without guessing, or two readers who follow it into different behavior. Two pass types, and **they run in SEPARATE agents — never one agent doing both**: a single agent doing one task first is primed for the second (a defect-hunt frame makes its restatement adversarial; a restatement frame makes its hunt post-hoc).

1. **Restatement pass — innocent, zero-charity.** The cell's prompt carries no review framing — only the paraphrase template and the target path, nothing else. The finding is not the paraphrase — it is the **divergence** between the paraphrase and the intended meaning. An innocent paraphrase often exposes ambiguity by misreading it.
2. **Defect-hunt pass — adversarial-literal.** A separate agent, told to find defects: flag every sentence that is self-contradictory, conflicts with another sentence, supports incompatible readings, is wrong when obeyed literally, is unexecutable by a zero-context reader — a reader with no project history whose entire context is the checkout's instruction file (CLAUDE.md / AGENTS.md), the document itself, and the files the document explicitly references by path — or demands work an agent cannot reasonably complete (unbounded verification or enumeration, current-world knowledge beyond training, control of another agent's internal state, labor with no stop rule). That last class is a candidate screen, not a verdict: agents mis-judge what agents can do, so the invoker decides which flags are genuine overreach. **A confusion flag is never dismissed as the reviewer's ignorance (boss-ruled 2026-08-04):** the reviewer's guaranteed context is the instruction floor plus the document, so a concept that confused them was missing from both — the remedy is one of three, chosen at triage: define it in the file, add the explicit path reference, or promote the definition to the instruction floor when many files share the concept. Plus absolutes broader than can hold (with the ordinary counterexample) and conditionals whose condition is a judgment call rather than an observable predicate. Each flag quotes the sentence, gives the readings or the conflict, and where the defect class permits, a case where obeying the words does the wrong thing — the what, when, and why of the defect, explained to fix-ready depth, with no proposed fix and no severity rating; the cell states only its own confidence.

**Running the cells.** Every tier-to-model assignment is an operator-set pinned value — the boss picks the models; agents apply the pinned picks and never substitute their own sense of the model landscape, which is months stale by construction (boss-ruled 2026-08-04). Claude-runtime cells are fresh subagents — good = the pinned top model at high effort, floor = the pinned floor model (Sonnet-class today), set per launch. Codex-runtime cells run through [`scripts/d-review-codex-cell.py`](../../../scripts/d-review-codex-cell.py) — one invocation per cell (`--cell restate|defect-hunt --tier good|floor --target <path>`), headless `codex exec`, read-only sandbox, the cell's final message on stdout. The templates in [`prompts/`](prompts/) are the single prompt source for BOTH runtimes' cells — one place to improve wording for both legs. The tier-to-model mapping and per-tier reasoning effort sit at the top of the script (authoritative; any ids quoted in prose are a snapshot), currently `gpt-5.6-sol` / `gpt-5.6-terra` at `xhigh`, boss-picked and live-verified 2026-08-03, pinned in the script so a cell does not depend on the machine-local Codex config.

**The matrix:** {restate, defect-hunt} × {good, floor} × {each available runtime} — with both runtimes available, as today, eight cells. *Good* is best at cross-rule contradictions. *Floor* is defined by capability — the lowest tier that actually reads the file, not the lowest tier that exists (a below-floor model flags mostly its own capability gaps); the framework's subagent default is the current instance. The full grid runs every time, and every cell reads the whole document. Pruning cells is a data question — which cells' findings survive context-aware triage, over tens of preserved reviews — decided by analysis of the records below, never by doctrine (boss-ruled 2026-08-04). (The clarity cells run on today's runtimes; a Codex *wrapper of this skill* — the runtime-parity question — is separate and arrives at companion admission.)

**The prompt is the lever.** Measured on a legacy doctrine-file review: seventeen findings under an adversarial-literal prompt against two under a charitably-worded one that silently repaired the defects being hunted. Force literal reading; forbid charity; keep the restate template free of review framing. The templates are the most leveraged text in the whole process — criticize them freely, in reviews and out of them; land changes deliberately (the context-holder rules on each, ideally micro-tested), never as silent drift (boss-ruled 2026-08-04).

**Synthesize — two roles, strictly split (boss-designed 2026-08-04).** First a **merge agent** — independent, one job, zero judgment — folds all cell reports into ONE file: hunt findings deduped (the same sentence flagged with the same complaint is one entry, all catching cells listed; the same sentence with different complaints stays adjacent entries), nothing dropped or filtered, uncertainty wording preserved verbatim, ordered by **document position — never by any cell's opinion or rating**: report order pollutes the author's judgment as their context fills, and document order is the one ordering that carries nobody's; it also puts every complaint about a passage in one place. The restatement reports merge alongside, aligned per section, so divergences sit next to the text they diverge about. Then the **author** reads that one file with full context — cells report observations, never importance (measured on the first full-grid run: the raw stream arrived pre-labeled "47 HIGH" by its cells, and the labels, not the content, framed the first triage) — assigns all severity at step 6, and plans the second pass. **Every review preserves its record** — the merged cell-attributed findings, the triage dispositions, and every cell's output, each file stamped with its provenance: runtime, exact model id, effort level, cell, tier (boss-required 2026-08-04 — tier names drift across model eras; pins do not; the Codex cell script stamps its own, Claude cell files are stamped when saved) — as a dated directory under `d-review-records/`, the data for the future which-cells-earn-their-keep analysis. Dedupe across cells — expect heavy overlap (first NedsChorus run, 2026-08-03: an under-scaled five-cell pass over a ~120-line skill returned 109 raw flags, ~35 distinct; the first full grid returned 191 raw, 110 distinct). The **author** compares restatements against intent — no one else holds the intended meaning, and a comparator without it watches a faithful paraphrase of broken text agree with the text and misses the defect. The two roles never mix: the cells generate the findings (the author never reviews their own text — that is step 5's warning), and the author, who holds the intent, takes the notes and rewrites — that is what review notes are for. A bad rewrite is caught by the next review round, not by restricting the author. Then findings as in step 6.

## When NOT to use

- Code correctness, or an implementation reviewed against its design — a code-review skill's lane (the review-change candidate owns it when built), not this one's.
- Routine re-review of long-shipped doctrine — run a deliberate consistency sweep instead; this skill gates changes, not the archive.
