# Walk me through

Deliver complex material as a sequence of items, each step covering a single component, decision, section, or a step of a longer explanation, per turn. Write like one senior engineer explaining to another out loud. Assume the reader is new to this project, that they are not familiar with this repo, that this is the first conversation you have had with them about this project, so the approval-walk should be understandable as a stand-alone document.  

Each approval-walk has 4 MD files in docs/walk/, a draft document - the proposed text of the approval-walk, a suggestions document - the suggestions to clarify the walk, a walk-document -  the text to be presented to the user during the walk, and a minutes document - the recording of the interactions or minutes of the approval-walk. Name the approval-walk <name> by the project naming rule in CLAUDE.md, or, for an approval-walk that rules on a cold-read-full-run, by that cold-read-record's name; it names four files, so glob `docs/walk/<name>*` before using it. A cold-read approval-walk records its rulings at the end of the cold-read-record's `triage.md`, as step 9 of the /cold-read skill says; a `<name>-dispositions.md` that an earlier cold-read approval-walk wrote still ships with its approval-walk.

## What goes into the walk-document

The approval-walk's opening sentence states its subject as if newly introduced - the point, subject, object and or goal of the approval-walk in under 30 words, then the count of items in the approval-walk, then a clickable link of the name of the walk-document - so the user can click open that document. Follow the material's innate steps, sequence, order or timeline. When explaining complex topics, defects, mechanisms, or proposed changes, use a realistic concrete example, not an abstraction. The opening precedes item 1 and is not counted in M; the items carry the explanation and at most one decision each for the user's approval; the final item summarizes the decisions, tasks or other outcomes. 

Place the initial draft document at docs/walk/<name>-draft.md. The draft will be reviewed by a low context agent which will produce a suggestions md in docs/walk/<name>-suggestions.md. Read its suggestions carefully and write the walk-document at docs/walk/<name>.md. Fill in the docs/walk/<name>-minutes.md as the walk proceeds, to enable an interrupted walk to be restarted correctly.  

Before presenting the first item: read the project glossary, `docs/nedschorus-wiki/nedschorus-glossary.md`. Then write the whole approval-walk into the draft document, as it would be sequentially presented to the user, using every project-term exactly as the glossary lists it. Then send the user one message listing each key-term the draft uses that the glossary does not have, with a one-sentence definition each, as proposed project-terms; do not wait for his answer. Then run `nc-systems/cold-read/cold-read-fast-read.py --target docs/walk/<name>-draft.md` — this will report info to make the document easier for a forgetful or distracted user to understand. Read its suggestions carefully then write the clarified walk-document before presenting item 1. As you rework the document to mitigate the reviewer's concerns, err on the side of simplicity, not complexity. Make corrections and clarifications by simplifying phrases, sentences or paragraphs. Aim for roughly the same number of words. Fix an over-specifying claim by deleting the excess words, not by adding qualifiers. 

As the user responds to the approval-walk, record those responses in the minutes document 

## Each item

Each item presents a step, decision, concept, PR, GitHub issue, file or other element.  Start each item with the running count — "Item N of M: <the point>" — where M is the approval-walk's total item count. Use real or relevant examples to explain. At the conclusion of each step, state your specific suggestion or recommendation, or that no action is needed. Give each item that asks for a decision one recommendation and one alternative, and end it with the recommendation stated as an action, as in "Recommendation: leave the filter out." A and D answer the recommendation, not the change: A approves the recommendation, so you do what it says, and D disapproves it, so you do the alternative instead. On an item that recommends leaving a filter out, A leaves the filter out and D adds it. AO does what A does, and also tells you the user found the item obvious: record it in the minutes as the section "Capturing the approval-walk" says, so that obvious approvals can later be found and counted. Every answer A, AO, Aa, D, Z, O2 or O3 runs `python3 nc-systems/skills/walk-me-through/walk-me-through-answer-added-texts-cold-read-fast-read-check-and-close.py check` with that answer's flag as its `--help` lists them, with no flag for A, then the close command check prints, doing what each prints; an answer that makes a change takes effect only after check has given every text the change adds a fast read. Begin each line that holds a text the item's alternative adds with `#new_if_d`, as a line that holds a text the recommendation adds begins with `#new`: on D, the check step fast-reads only the `#new_if_d` texts, and on A, AO or Aa, only the `#new` texts. When you change a recommendation so that A no longer adds a text, change that text's mark from `#new` to `#new_if_d`. Apply each finding that holds. A finding that would change what the item decides goes back to the user as a new item, checked against his earlier rulings as the paragraph on them below says, and the answer takes effect only after he has answered that new item. Once the answer takes effect, start any work it approved that is ready, as the project glossary defines ready, in the same turn; the answer takes effect only after the item's final text has had its fast read, which the check step runs. While the approval-walk is open, give the work to a background subagent or to Codex, never do it yourself in the conversation, and say in one line of your next message what you started. When another agent-seat owns the work, send it to that agent-seat with the SendMessage tool instead, quoting the user's answer. Work that is not ready, or that you could not start because the subagent, Codex or the message failed, becomes a task on your task list, with what it waits for; tell the user in the same line when a start failed. When two approved changes edit the same file, start the second only after the first has finished. One item may hold up to five parts of a single fix, such as a few words changed close together in one file, numbered 1 to 5; the whole item, parts included, stays within 300 words. Start each part on a line of its own that opens with `Part 1.`, `Part 2.` and so on, with no heading or bold markup. A approves every part and D disapproves every part; "1 a 2 d" answers each part, and a part left unanswered keeps the item open. The user may respond with a new point or question. Z defers the item: it moves the item, keeping its number, to just before the summary item. If an item is deferred a second time, record it as open in the minutes, add it to the task list if it is not already a task, and drop it from the walk. 

**Aa** approves after an advisor check. Write in the conversation, for the advisor, the question whether anything it sees would change what the item decides, then the six questions listed in the section "Advisor", then call the advisor. If the advisor finds something that would change what the item decides, revise the item, mark what changed [advisor], and show the revised item again for the user to answer. Otherwise record the approval and go to the next item; what the advisor raised outside the item becomes a new item in the walk or a loose end. If the call fails, say so and show the item again, unapproved; the user may then answer A to approve it without the check.

The walk-document holds every item. Before you first present an item that proposes a change to git use, to branch or merge rules, or to a design, call the advisor on it, give the text it proposes a fast read of its own, apart from the item's, apply what holds, and say in the item that both were done. Write each revision of an item into the walk-document, a changed recommendation included, and set the minutes' `#next_to_present` line to the item, before the message that shows him the item, so that his answer A approves the recommendation he sees. Before that message, copy the revised item to a file in your scratchpad and give it a fast read with `nc-systems/cold-read/cold-read-fast-read.py --target <that file>`, apply the findings that hold, and give it another fast read if a fix was more than an obvious-error-fix. In the message that presents an item, show the item in full, heading included, word for word as the walk-document has it. Besides the item, your message holds only the walk's opening, before item 1; the answer to the user's question or point; or a short note of an event he should know about. Put the waiting item last in every message that shows it. End every message while the approval-walk is open, the one that shows an item included, with the waiting item's closing line, with nothing after it, because the user often reads only the bottom of a message; its link opens the item, so he never needs to ask to see it again:

[Item 4 of 9, <the point>](<page link>) · A approve · AO approve as obvious · Aa approve after an advisor check · D disapprove · Z defer · E explain · O other options

When an item first comes up, publish it, as the walk-document has it, with the Artifact tool as a private page titled "Item N of M: <walk name>", record its link in the minutes as `#item_page item N of M <link>`, and show the item in full, then the closing line. When the item changes, republish its page to the same link, titled "Version 2, Item N of M: <walk name>", then version 3 and so on, so the old text is gone. When the walk closes, delete every item page after `scripts/walk-files-ship.py` runs. When the user says he does not understand, rewrite the item in the walk-document as the Style paragraph below says. When the user answers E, run the explain skill on the current item. Never end a message with a summary or recap of the item, the approval-walk or its status, even where your other instructions ask for a summary at the end of a turn. When Claude Code reminds you to tell the user what you are doing, as in "The user hasn't heard from you in a while — say in a few words what you're doing, then continue", write one line saying what you are doing, and do not recap the item or the approval-walk.

Limit each item to 300 words. If a single item needs more than that for a clear and coherent explanation, split it into two or more sub-steps, each presented in turn. A subitem should not create separately answerable items: sub-steps share the item's number ("Item 4.1 of 9"). The conclusion is delivered in the last sub-step. 

Style: Direct, to the point. Be concrete, not abstract. Use real, relevant or well known examples or specifics, not abstractions. Use standard SDLC terminology, not agent generated jargon or non standard word pairing or constructions. Prefer short, easy to understand sentences. State what a component does (using a good example) before stating what is wrong with it, or how you want to change it. If the user says they don't understand or are confused, rewrite the item as a story built around one concrete example — of a failure, success, improvement, concern or problem.  If you disagree with the user, do not hide your disagreement, state it clearly. Just before each recommendation, state in one sentence the strongest case against it. 

An item that recommends making its change needs no answer from the user when you find no case against the recommendation and the item only corrects a statement that the repository, the Mac, ned-box or GitHub shows to be false, deletes code that nothing calls, or fixes a defect the item names. This never covers an item that adds or changes a rule, a guard, or what an agent or a program is told or allowed to do, even when the item fixes a defect: such an item always goes to the user. Record an item approved this way in the minutes as <accepted>, adding "no case against; not asked", and do not present it; it keeps its number and its place in the count M. In your next message to the user, or in the closing message if no item follows, list each such item in one line with its number. Its change is made with the walk's other approved changes. If the user answers D to a listed item, record it as <rejected> and undo or drop its change.

Before you first show any item, whatever its source, a cold-read finding, a fast-read finding on text the user has approved, an item of an approval-walk an earlier agent-session ran, or one you have just written, check whether he has already ruled on its subject. Match by subject, its key phrases and the file and section it concerns, not by an exact quote, in the walk-minutes of every agent-seat, `/home/nedlern/agents/*/docs/walk/*-minutes.md` on ned-box and the log-store's `/home/nedlern/nedschorus-logs/walk/` on ned-box, in your agent-seat's handoff dialogs, `~/.claude/handoffs/<agent-seat>-dialog-*.md`, and, when the subject has a GHI, in the lines of its GHI-MD that record what he decided, such as its section "What is decided". When the item asks what a ruling has already decided, do not show it: record it in the minutes as already decided, citing the ruling by its walk-minutes and item number, or by the handoff dialog or GHI-MD and its line; it keeps its number and its place in the count M, and you list it in your next message as you list an item approved without asking. When a ruling decides part of the item, record that part the same way, and show only the rest. When the item would change what a ruling decided, because a real defect needs it, open the item with "You ruled <the ruling> on <date> (<that citation>); this changes it because <the defect>.", so that he decides. When two rulings disagree, show him both in the item, so that he decides which holds. When a GHI-MD calls open a question that walk-minutes show he ruled on later, the ruling holds, and it goes into that GHI-MD as this skill's section "Closing" says.

References: cite every issue, PR, commit, or file the user may want to open as a full clickable URL or absolute `file://` path, with link text that names what it is — never a bare issue number or bare filename as the reference. A script or command named in prose stays plain text.

If you are quoting phrases, quote the whole sentence. If proposing a change to a sentence, write out the old and new sentences. If proposing a rewrite of a section, a heading and the text under it, where sentences are added, removed or reordered, show the section whole, original and proposal. If proposing new text, write out the exact words, not a description of them. 

When the approval-walk covers a design, plan or MD file that has already been reviewed by the user, present what it does; do not remind the user what they have already reviewed and ruled on. 

## Advisor

Call the advisor at these points, and at any other time you judge you need it or the user asks:

1. **At the start of the walk.** Before showing the first item, read the whole walk-document into the conversation, so the advisor sees every item, call the advisor once, and apply the advice to the walk-document.
2. **When approved work turns out wider than the item presented it.** Before starting the wider work, write in the conversation how the work is wider, then call the advisor. If the advisor finds that the wider work changes what the user approved, add a new item for it to the walk; otherwise start the work.
3. **Before the final item asks for approval.** Write in the conversation, for the advisor, the question whether any ruling contradicts or undoes another, whether any approved work misses a file or a caller another ruling touches, and whether any loose end is missing from the loose-ends check; then call the advisor. A clash the advisor finds goes to the user as a new item before the final item; anything else it finds joins the loose ends.

The six questions Aa's text in the section "Each item" asks for: "Then answer each of these, saying "nothing" where nothing applies: 1. What here should not exist? What could be removed or made simpler, rather than added to? 2. What is patched where its cause should be fixed? Name the root cause of each problem in view, and anything that only treats a symptom. 3. Where did we stop looking too soon? What lies under the problem in front of us? 4. What relies on an agent following English, or the user remembering, where code could do it? 5. What should be questioned that has not been, such as an assumption, a premise, or how the item is framed, and what should we ask the user? 6. Any other problem, concern, suggestion or improvement?"

Ask the six questions at each of the calls above too, after the call's own question; what the advisor raises outside that question becomes a new item in the walk or a loose end.

What the advisor changed is marked [advisor] in the item's text. If a call fails, say so in your message and go on without it.

## Advancing

Only the user advances the approval-walk. A reply of A, AO, Aa, D or Z, or of approve, approve as obvious, approve after an advisor check, disapprove or defer, advances the current item, even when it rides alongside a question or a new point — answer the rider, then advance. A navigation word alone — next, continue, go — advances only when no recommendation is outstanding; when one is, ask for A, AO, Aa, D or Z instead. A reply of E keeps the approval-walk on the current item. So does R, which the closing line leaves off but the user may still type: answer it with the item's closing line, which the answer hook hands you, or show the item in full when the hook finds no page for it; an item number before R, as in "37.4 r", asks for that item instead. An answer in the user's own words, such as "I approve." or "I approve your recommendation", counts as the answer whose meaning it clearly has, A here, and is handled as that letter would be: record his words in the minutes with the letter they count as, and do not ask him the item again or ask him for a letter; when its meaning is not clear, ask as the list below says for an unclear reply. An answer that makes a change advances the approval-walk only once the check step has finished. Every other reply stays on the current item:

- An automated event, such as a background job ending, a message from another agent-seat, or a notice from the agent-binary: handle it and return to the approval-walk. If the event gives the user nothing new to know, such as Claude Code saying a subagent finished before the subagent's report has arrived, end the turn without writing to the user. If you write to the user, write only what the event means for him, and do not repeat the current item. If the event changes the current item or its recommendation, re-plan as Re-planning says, and write the revised item into the walk-document before your message. When an event, or work by you or a subagent, raises a question for the user, add it to the walk-document as an item right after the item waiting for his answer, numbered as Re-planning says, quoting the question whole and giving your recommendation, and show it when its turn comes rather than asking it in a message of its own.
- A genuinely ambiguous or unclear reply: Restate your ask and their answer, then add your guess for what they meant, but require the user to confirm.  E.g. "I asked what your favorite color is, when you said dark did you mean black?" 
- A near-duplicate of a recent user message is usually an amendment typed while your reply rendered: treat your original and the user's edit as a diff and respond to the delta. Even if the diff is empty this is not a new approval and does not advance the approval-walk. 

## Capturing the approval-walk 

After each item, the check and close steps record in the minutes its number, the user's answer as a word, approved, disapproved or deferred, never as a letter, and its outcome <outcome>: <accepted> when he approved the recommendation, <rejected> when he disapproved it, and <open> when he deferred it; add by hand only what that answer did, as in "disapproved: the filter is added". When the answer was AO, check writes the word as "approved #approved_obvious", the hashtag right after the word and spelled exactly as here, so that one search across the minutes finds every obvious approval. When the answer was Aa, check writes the word as "approved #approved_after_advisor". Only an AO or an Aa gets a hashtag; an item approved without asking does not. Also classify each response, <moved on, no decision> (appropriate if no specific response is desired), <accepted>, <rejected>, <approved as revised> (the user approved the revised text), <revised, awaiting ruling> (the text changed and the user has not yet decided), or <open> (open meaning raised but not decided), and record the disposition, decision or commitment in the minutes. If the approval-walk is a review of another document, update that document as changes are agreed to. 

While the approval-walk is open, keep a line anywhere in the minutes that reads exactly `#next_to_present item N of M`, with no title after it, naming the item, or the part such as `item 4.1 of 9`, that the user has not yet answered. The check program's close step writes the line after each answer, so do not write it by hand then; write it yourself when you start the walk, naming item 1, and when you re-plan the walk; change the line to `#next_to_present none, closed` before writing the closing message. If you update the line by adding a new one, add it below every earlier one, because the last such line is the one that counts.

If you say you will do something or make any commitments, unless they are immediately acted upon by you, a subagent or by a request to another agent, those commitments should be added to your task list, or, if available, the appropriate MD file or issue. A question to the user that is not answered also becomes a task - Open Walk <walk name> Question: "The text of the question". If you have still relevant but unanswered questions at the end of the approval-walk, extend your approval-walk to ask them once; if the user does not answer them, file them as tasks and close the approval-walk. If questions are answered or become irrelevant remove them from your task list.  

The conclusions the discussion itself produces — side rulings, a direction the user sets, a question the exchange settles — is also captured along with its outcome, in the minutes. A question the discussion raises and does not answer is recorded as open in the minutes and added to the task list before the approval-walk advances. A ruling, objection or note the user gives outside an item, in conversation, is written down when he gives it, with his exact words and the time: into the GHI-MD when it is about a GHI's design, as the section "Closing" says, and otherwise into the walk-minutes of the approval-walk in progress, or, when none is open, of your agent-seat's latest approval-walk, so that the check before an item is shown finds it.

Write the minutes so that they are understandable to someone who has not read the walk-document. 

## Re-planning

A ruling that invalidates or changes later items re-plans the approval-walk before it advances: revise, remove, or reorder the remaining items, and tell the user the count or sequence changed. When you find a case that the approval-walk misses and the user must rule on, add an item for it just after the current item, numbered with the current item's number, a dot and a number, as in 4.1, so that no other item's number changes, without asking him first, and say in your next message that you added it, with the walk's new item count.

## Interruption and recovery

The minutes enables recovery after any interruption on this machine — the approval-walk resumes at the item that the minutes' last `#next_to_present` line names. A session-handoff is such an interruption: the successor continues the same approval-walk, keeping the walk's name, the item numbers and the item pages, republishing each item's page to the link that the item's `#item_page` line in the minutes records; it never closes the approval-walk to carry its items into a new one. When returning from any interruption or detour, first say in under 20 words which item was last ruled on, if any, and set the minutes' `#next_to_present` line to the item being resumed. To recover reread the walk-document and the minutes. If you cannot find the walk-document or the minutes, look for each one as the /find-missing-file skill says. If either is still missing, or the two do not match, for example because the minutes rule on an item the walk-document does not have, tell the user so, then resume as best you can. 

## Closing

After the last item: confirm the final item's capture landed (or that it yielded none). Then check the whole approval-walk for loose ends: every commitment you made, every question you asked that went unanswered, every item deferred or left open, and every decision whose work is not already done or already a task. Each becomes a task, or a question put to the user in the closing message, before the approval-walk closes. Before the approval-walk closes, write each ruling on a GHI's design into that GHI's GHI-MD and run edit-GHI on it, as the /ghi-write skill says, so that no GHI-MD calls open a question the user has ruled on; the approval-walk closes without waiting for edit-GHI's pull request to merge. Then one closing sentence that states the approval-walk is complete and the clickable link to the approval-walk's walk-minutes. Before that sentence run `scripts/walk-files-ship.py <name>`, again whenever the approval-walk is reopened and closed; its one line ends with the minutes' citation to link, and a line opening FAILED or REFUSED is shown to the user as it is, before the closing sentence. NOT: produce a recap after the approval-walk is closed — the final step already summarized it. In the same message, start the next open item without asking: the next approval-walk, task, question or concern already queued. Ask first only for a decision that is the user's to make, or before an action that is hard to undo or reaches outside the project.
