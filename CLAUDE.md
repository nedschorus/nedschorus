# Nedschorus

- If you run into unexplained terms, read `docs/nedschorus-wiki/nedschorus-glossary.md`, which also lists the system glossaries. Use a glossary's term, spelled as the glossary spells it, and name a software-engineering concept by its SDLC-term. When a reader could confuse two meanings of a word where you use it, add the words that pick yours: "run mutation testing on the line", not "mutate the line".
- Read `docs/nedschorus-wiki/nedschorus-style-guide.md`.
- The project runs on two machines, each with its own clone: the user's Mac, and ned-box, the Ubuntu hub reached as `ssh nedlern@ned-box`, where most agent-seats run and the logs both machines use are kept. An agent-seat on the Mac keeps working when ned-box cannot be reached. When a program reports that ned-box cannot be reached or that its `claude` is logged out, tell the user what it said, remedy included, even when you can work around it.
- Logs go in the log-store on ned-box, never in the repository; cite a file there as `nedlern@ned-box:/home/nedlern/nedschorus-logs/<path>`, which works from either machine.
- Before you name a file, directory, script, branch or glossary term, or a function, class or constant used from other files, apply `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md`.
- Text a program hands an agent, such as a hook's refusal or an error message, says what was stopped and why, then gives each instruction on its own line with the condition it applies under, and the reason wherever the reason helps the agent act well. Comment code only with what the code cannot say, in as few lines as it takes: a reason, a constraint from outside the code, or a trap a reader would otherwise fall into. Standing instructions, which are this file, the seat-briefs and every `-instructions.md` and `-prompt.md` file, hold instructions, with a reason only where it helps. Program text, code comments and standing instructions carry no history or citations; history goes in the commit message and the pull request. A message to another agent-seat does carry its citations, because that agent-seat must verify claims it did not witness.
- In a file the instruction-file guard protects, you may fix an obvious error without asking the user first, and only these four count: a spelling, grammar or punctuation mistake; a link, path, file name, script name or flag that no longer exists or no longer works as the text says, when the one correct replacement is clear; a description of how things are that the repository, the Mac, ned-box or GitHub shows to be false, with that source named in the commit message; or a place that a change the user approved in this agent-session missed, fixed exactly as that change fixed the other places. An edit that changes what an agent or a program is told to do, or what a document decides, is not an obvious error, however obvious it looks. Tell the user what you fixed in your next message to him; a subagent tells the agent that dispatched it, which tells the user.
- Write each Markdown paragraph, list item and table row as one line, however long; break lines only where Markdown needs a break.
- Reviewing a pull request — **review scope: code findings block the merge; prose gets none, apart from the exceptions below.** Code needs PR reviewers. Prose is reviewed before the PR. This bullet is the "Review scope" section of `docs/agents/pr-reviewer-instructions.md` word for word: the file is pasted into every Claude reviewer's prompt, and the Codex reviewer reads this bullet. Change both together, or `scripts/pr-reviewer-instructions-copies-test.py` fails.
  - **Code is reviewed skeptically, hunting for defects, and its findings block the merge.** Review the code the pull request changes. If you notice that the change breaks other code, in the same file or another, that break is a finding too. A file of any type other than markdown is reviewed this way: source code, such as a script, a test or a hook; settings, such as `.claude/settings.json` or `.gitignore`; data, such as a JSON or YAML file a test reads; and any other file. A docstring is treated as code, and so is a comment that says what a piece of code does or why the code does it: a finding says where the docstring or the comment and the code it describes disagree. A comment that tells a program what to do, such as a script's `#!` first line or `# noqa`, is code. Every other comment, such as one that only cites a user-ruling or a pull request, is prose, and so are a message the code prints and a prompt the code hands to an agent. A pull request reviewer gives such a comment, message or prompt no finding, remark or question, with one exception: a finding may say that a message or a prompt names a file, a flag or a script that does not work as the message or the prompt says, such as a marker file a guard no longer reads, a flag the named script does not accept, or a script the message or the prompt places in this repository that is not there. Such a finding blocks the merge. Code that fills in the placeholders of a message or a prompt, or copies a prompt's text from another file, is code and is reviewed; the English of the message or the prompt is not. A finding about code may name a markdown file the change breaks, such as a `CLAUDE.md` line that quotes output the code no longer prints.
  - **A markdown file is prose, whole, the shell commands inside included.** A pull request reviewer says nothing about a markdown file, with two exceptions: a finding about code may name a markdown file the change breaks, as the code bullet above says; and when the pull request's description names a markdown file and asks for a review of the code or shell commands inside that file, review the ones the pull request changes as code and say nothing about the English around them.
  - **A file whose name ends with the -nbd suffix, just before any extension, is nice-but-dirty code, as the project glossary defines it, and only three kinds of finding on it block the merge.** Review the file as code, but a finding on it blocks the merge only when it shows one of these: the code damages other systems or data, or blocks other work; the code hides one of its own failures, reports one as success, or reports one where neither an agent nor the user will see it; or deleting the file, or reverting the pull request that added it, would leave something broken. A failing test still blocks. Every other finding on the file is advice, and does not block. A file without the suffix, which the pull request adds or changes, and which needs code from an -nbd file in order to work, is a finding that blocks: that file is nice-but-dirty too, so it must be renamed with the suffix, or stop depending on the -nbd file. A test whose only job is to test an -nbd file is named `<name>-nbd-test.py` and is exempt from this rule.
- Propose a guard, validation, retry or workaround only when two things hold: the failure has happened, as a citation from the user, an agent or a machine shows, or concrete evidence shows it is foreseeable within the next 30 days; and it would lose or damage work, stop work beyond the task that failed, or go unnoticed until it does one of those. Otherwise leave it out; in a review, raise a missing one as a question for the user, and an added one that fails these tests as a finding. When the cause is in this project's own code, settings or instructions, fix the cause instead, and where the fixed code can still fail, report it: print what failed and exit nonzero, or raise an error to a caller that does. Only a cause outside our control, such as an outside service, the operating system, the program the agent runs inside or the user's environment, earns a workaround; a retry is only for a passing fault, on an operation safe to repeat, with a limit on attempts. Show that what you add works with a test that reproduces the failure, injected where it cannot be caused for real. Three things need neither test: reporting a failure; rejecting malformed input where it enters a program; and a timeout sized to an operation the code already performs. Hardening against deliberate attackers is not needed.
- When you review or rewrite anything, look as hard for what could be simpler, smaller or gone as for what is broken, and report each as a finding of its own; in a pull request review such a finding does not block the merge unless the pull request adds what is not needed. When you find a problem, fix its root cause, the reason it could happen at all, not only the case in front of you; if you fix only the case, say why, and what the root cause is or that you could not find it. A pull request's description carries, for each defect it fixes, a line labelled `Root cause:` or `Root cause not fixed:`, or else the line `No defect fixed.`; `scripts/merge-gate.sh` refuses a description without one.
- Each pull request merges one topic branch and is atomic: it carries its tests and every test, caller, document or citation it would otherwise break, and nothing outside its topic. merge-lane-2 on ned-box reviews and merges every pull request. A head commit becomes a frozen-head the moment it is pushed, because its review is commissioned then: do not amend it or push small corrections one at a time, because either moves the head commit under a running review. When merge-lane-2 posts a changes-requested review on your pull request, dispatch a forked subagent at once for the fix-round: it fixes each blocking finding that holds, root cause included, changes nothing else but what keeps the pull request atomic, pushes at most one commit on top of the frozen-head, and tells merge-lane-2 with SendMessage the new head commit, or that it pushed nothing, and why it did not fix each finding it left. A defect you find yourself goes in the next fix-round, or after the merge in a new pull request; for a non-blocking finding merge-lane-2 sends you after the merge, open a new pull request or tell merge-lane-2 why not. When `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`, do what its report says.
- Before pushing, run `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`. Code that handles a failure, such as an `except` block or an exit-code check, gets a test that causes that failure, checked by mutation testing.
