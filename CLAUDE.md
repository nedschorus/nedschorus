# Nedschorus

- If you run into unexplained terms, this project's glossary is `docs/nedschorus-wiki/nedschorus-glossary.md`. A term used by one system alone is a system-term, defined in that system's own glossary; when the project glossary does not list a term, look in the glossary of the system whose files you are in. When you describe something a glossary names, use the glossary's term, spelled as the glossary spells it. Name a software-engineering concept by its SDLC-term, with its standard meaning; do not paraphrase it or substitute a coinage. Coin a project-term, a word with a meaning specific to this project, only when no SDLC-term fits, and propose it to the user first. A hyphenated phrase marks a project-term or a system-term; do not hyphenate a phrase that is not one.
- The project runs on two machines, each with its own clone: the user's Mac, and ned-box, an Ubuntu machine on the same LAN reached as `ssh nedlern@ned-box`, where the agent-seats run. When a program reports that ned-box cannot be reached or that its `claude` is logged out, tell the user what it said, remedy included, even when you can work around it.
- Logs — the byproducts of the work that are not the system, cold-read records first — live on ned-box in the log-store `/home/nedlern/nedschorus-logs/`, never in the repository; cite a file there as `nedlern@ned-box:/home/nedlern/nedschorus-logs/<path>`, the scp form, which works from either machine.
- Before telling anyone a file does not exist, run `scripts/locate-file-copies-across-machines.py <name>`; if it finds nothing, say where you looked, not that it does not exist.
- When creating or inventing names, for directories, file names, globals, functions, classes, scripts, and other names likely to be grepped, use explicit, clear and precise multi-part names. Check newly invented names in both your checkout and main: glob or grep your checkout, then `git fetch`, stopping if it fails, and `git ls-tree -r --name-only origin/main | grep -i <name>` for path names or `git grep -i <name> origin/main` for names in files. If these checks return collisions or ambiguity, choose a more explicit name, with 3 or 4 parts, not 1 or 2. If the thing you are naming already has a name in the project, use the existing name instead of inventing a new one.
- When you write the text a program hands an agent at the moment it must act, a hook's refusal or an error message, say what was stopped and why, then put each instruction on its own line with the condition it applies under. Give the reason wherever the reason helps the agent act well. Keep quotations of the user, rulings, dates and citations out of the text. Comment only what the code cannot say: a reason, a constraint from outside the code, or a trap a reader would otherwise fall into, in as few lines as it takes. History — incidents, review rounds, rulings, what was tried before — belongs in the commit message and the pull request, where `git log` and `git blame` find it.
- Standing instructions an agent reads before it acts — this file, the seat-briefs, and every `-instructions.md` and `-prompt.md` file — hold instructions, with a reason only where it helps an agent apply the instruction. Standing instructions carry no citations: no dates, rulings, walk or pull-request references, or accounts of what went wrong. A message to another seat does carry its citations, because that seat must verify a claim it did not witness.
- Never cite a pull request, GitHub issue, task, commit, seat or session by a bare number, hash, GUID or name. Write its ID-type and its name, and make it a clickable link when it can be opened: "PR [recover-crashed-seats: exit nonzero when any seat was not recovered](https://github.com/nedschorus/nedschorus/pull/426)", never "#426". Numbers mean almost nothing to the user; titles and links are what he reads and clicks.
- When you write to the user or to another agent, write the noun instead of "it", "its", "they" or "this", and instead of "that" used as a pronoun, unless the noun is in the same sentence and no other noun there could be meant. When "or" could mean one-or-the-other or one-or-both, write which. English lets these words point at more than one thing, and a reader without your context cannot ask which you meant. Code and quoted text are exempt.
- In Markdown, write each paragraph, list item and table row as one line, however long; break lines only where Markdown needs a break. Editors and browsers wrap long lines to the screen's width.
- Reviewing a pull request — **review scope: code blocks, prose does not.** Code needs reviewers; prose already has reviewers, including the user. This bullet is the "Review scope" section of `docs/agents/pr-reviewer-instructions.md` word for word: the file is pasted into every Claude reviewer's prompt, and the Codex reviewer reads this bullet. Change both together, or `scripts/pr-reviewer-instructions-copies-test.py` fails.
  - **Code is reviewed adversarially and blocks.** The class follows the CONTENT, not the file it sits in: `scripts/`, `.claude/hooks/`, `.claude/settings.json`, and every shell command, invocation, and code block embedded in any markdown file — commands inside skills included.
  - **Operative prose is gospel — not reviewed, not reported on at all.** `CLAUDE.md`, any `CLAUDE.local.md`, everything under `.claude/skills/`. Operative prose reaches the PR already cold-read and walked with the user; a reviewer improving settled instruction text is a regression.
  - **All other prose is silent — not a finding, not a remark, not a question.** `docs/` entire (designs and GHI-MDs included), `nc-queue/`, walk minutes, and provenance or recovery citations anywhere. Silent rather than non-blocking, because everything a reviewer writes gets read and "fixed" by another agent, and those fixes introduce defects. A citation written as a command is silent as prose and reviewable as a fact: its wording, its placement and whether it is needed are silent; whether it resolves is a blocking finding that states the command and what it returned. Check one by running it, and run only commands that read.
- Reviewer rule — before proposing a guard, validation, or robustness fix, name the behavior it defends against — something this project's cooperative, supervised agents actually did (cite it), or concretely will do. If you cannot name the behavior, raise it as a question for the user, not as a finding. Do not propose hardening against deliberate attackers: this fleet's failures are accidents between cooperative agents.
  - This rule does not cover reporting a failure. When a step can fail — a command exits nonzero, a file is missing, a remote machine does not answer — the program makes the failure visible to whoever acts on its output: it prints what failed and exits nonzero, or, inside a function, raises an error to a caller that does. Stopping at the failure is part of reporting it, not a guard. A finding that a failure goes unreported, or is reported as success, needs no cited behavior.
  - What the rule does cover is code that retries a failure, works around it, or tries to prevent it, whether the failure comes from an agent or from a machine, a network or an outside service. Propose that code only when you can cite the failure happening, or show it concretely will, and can say how you know the fix works: a test that reproduces the failure and passes with the fix.
- How a change reaches main: each pull request merges one topic branch — one feature or bugfix, which may take several logical changes — and is atomic. Atomic means self-contained: the pull request includes its tests and every test, caller, document or citation it would otherwise break, so main still works after the merge. Atomic also means not tangled: a change outside the topic goes on its own topic branch. Never extend an existing pull request with a second topic. Merges consolidate at the seat merge-lane-2 on ned-box: merge-lane-2 commissions an independent reviewer against the PR's head, reviews the code itself, and merges pinned to that head. A head is frozen the moment it is pushed, because that is when its review is commissioned. When you read a review of your pull request that carries findings, dispatch a forked subagent at once, before any other work — one that inherits your full context — so the fix proceeds alongside your own work instead of waiting behind it. The subagent checks each finding against the code, fixes the ones that hold, answers the ones that do not with the reason, and resubmits. A fix you find yourself goes the same way. The resubmission is one commit on top of the frozen head, pushed once and announced once; never an amend, and never a second push of small corrections, which moves the head under a running review.
  - A conflict is the one case a commit on top cannot clear — `scripts/branch-conflict-check.py` reports `VERDICT: CONFLICT`. First see what the conflict is with. If main has deleted or replaced what the branch changes, do not merge: close the pull request with a comment naming the commit or pull request on main that replaced the work, and carry what main still lacks on a new topic branch cut from current main.
  - Otherwise clear the conflict with a hand-merge, as that report says. If the resolution forces an edit beyond the conflicting lines, put that edit in one ordinary commit after the merge; this is the one exception to one commit on top. Push the merge and that commit once, and announce them once, naming the files you resolved in the merge's commit message and in the announcement.
- Before pushing, run only the test suites your change can affect: `python3 scripts/run-all-test-suites.py --only-suites-whose-recorded-inputs-changed-since origin/main`. A full run is not needed, because merge-lane-2 runs the same selection on the head merged onto main before merging, and `scripts/daily-full-test-run-of-main.py` runs every suite on main each night on both machines.
- Before saving or proposing a memory, check whether it is actually a task — something to do, removed when done. If so make it a task, not a memory; memory holds durable facts and every memory write requires the user's approval.
