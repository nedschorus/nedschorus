# Nedschorus

- If you run into unexplained terms, read `docs/nedschorus-wiki/nedschorus-glossary.md`, which also lists the system glossaries. Use a glossary's term, spelled as the glossary spells it, and name a software-engineering concept by its SDLC-term. When a reader could confuse two meanings of a word where you use it, add the words that pick yours: "run nc-mutation-testing on the line", not "mutate the line". A project-term, a system-term or a field of a structured output has one definition: a term's is in its glossary, and a field's is the `description` its JSON Schema gives it. Other text that explains the term or field points to that definition instead of defining it again.
- Read `docs/nedschorus-wiki/nedschorus-style-guide.md`.
- The project runs on two machines, each with its own clone: the user's Mac, and ned-box, the Ubuntu server reached as `ssh nedlern@ned-box`, which is the system's hub: most agent-seats run there, and the logs both machines use are kept there. When ned-box cannot be reached, or a program reports that ned-box's `claude` is logged out, tell the user what the failing command or program said, with its remedy if it gave one. Do not find another way to do a step that needs ned-box: leave that step until ned-box is fixed or the user says otherwise, and meanwhile carry on with work that does not need ned-box. The machines' setup, which commands run where, and how to link a ned-box file for the user are in `docs/nedschorus-wiki/nedschorus-mac-and-ned-box-machine-setup.md`.
- Logs go in the log-store on ned-box, never in the repository; cite a file there as `nedlern@ned-box:/home/nedlern/nedschorus-logs/<path>`, which works from either machine.
- Before you name a file, directory, script, branch or glossary term, or a function, class or constant used from other files, apply `docs/nedschorus-wiki/nedschorus-how-to-choose-a-name-for-files-code-and-glossary-terms.md`.
- Text a program hands an agent, such as a hook's refusal or an error message, says what was stopped and why, then gives each instruction on its own line with the condition it applies under, and the reason wherever the reason helps the agent act well. Comment code only with what the code cannot say, in as few lines as it takes: a reason, a constraint from outside the code, or a trap a reader would otherwise fall into. Standing instructions, which are this file, `AGENTS.md`, the seat-briefs, every `-instructions.md` and `-prompt.md` file, every skill's `SKILL.md`, and every agent definition in `.claude/agents/`, hold instructions, with a reason only where it helps. Program text, code comments and standing instructions carry no history or citations; history goes in the commit message and the pull request. A message to another agent-seat does carry its citations, because that agent-seat must verify claims it did not witness. When a sentence for a fresh-agent stays unclear after you rewrite it, add one example after it: a real case from this repository or from the task the sentence is for, which the sentence as written covers and which nothing else in the same text contradicts; when the example names a file or a command, check it against that file, or the command's help. When there is no such case, add none.
- In a file the instruction-file guard protects, you may make an obvious-error-fix in its prose, as the project glossary defines it, without asking the user first. When you are unsure that a mistake is an obvious-error, ask the user; a subagent asks the agent that dispatched it.
- Write each Markdown paragraph, list item and table row as one line, however long; break lines only where Markdown needs a break.
- Before reviewing a pull request, read `docs/agents/pr-reviewer-instructions.md` and follow it.
- Build code-prompt-code: a step that needs no judgment, such as sequencing, state, validation or a retry, goes in code, never in a prompt. A model is given only work that needs judgment. Each design document names the steps that need judgment. Code can be tested and runs the same way each time; a prompt is hard to test and can run differently each time.
- Propose a guard, validation, retry or workaround only when two things hold: the failure has happened, as a citation from the user, an agent or a machine shows, or concrete evidence shows it is foreseeable within the next 30 days; and it would lose or damage work, stop work beyond the task that failed, or go unnoticed until it does one of those. Otherwise leave it out. A failure whose harm can be noticed and undone, or whose work can simply be redone, does not lose or damage work. A warning or error message alone does not show that work was lost, damaged or stopped: before you cite one, look where the work would be, such as the recipient's transcript for a sent message, and cite what is missing, damaged or stopped there; when the work is there and whole, the message is no citation that the failure has happened. When the cause is in this project's own code, settings or instructions, fix the cause instead, and where the fixed code can still fail, report it: print what failed and exit nonzero, or raise an error to a caller that does. Only a cause outside our control, such as an outside service, the operating system, the program the agent runs inside or the user's environment, earns a workaround; a retry is only for a passing fault, on an operation safe to repeat, with a limit on attempts. Show that what you add works with a test that reproduces the failure, injected where it cannot be caused for real. Three things need neither test: reporting a failure; rejecting malformed input where it enters a program; and a timeout sized to an operation the code already performs. Hardening against deliberate attackers is not needed.
- When you review or rewrite anything, look as hard for what could be simpler, smaller or gone as for what is broken, and report each as a finding of its own. When you find a problem, fix its root cause, the reason it could happen at all, not only the case in front of you. Fix only the case when that fix would still be needed after the root cause is fixed, or to end an outage; then say why, and what the root cause is or that you could not find it. A pull request's description carries, for each defect it fixes, a `#root_cause` or `#root_cause_not_fixed` line, or else the line `#no_defect_fixed`; `scripts/merge-gate.sh` refuses a description without one.
- Each pull request merges one nc-topic-branch and is atomic: it carries its tests and every test, caller, document or citation it would otherwise break, and nothing outside its topic. Changes are one topic, and go in one pull request, when they run the same test suites, when a reviewer would check them the same way, or when one cannot land without another, such as moving every hook that reads Markdown onto one shared parser; a pull request is too big when a reader could not say in one sentence what it does, because its changes are unrelated or work at cross purposes. When one change in it fails review or its tests, move that change onto its own branch so the rest can merge. merge-lane-2 on ned-box reviews and merges every pull request. A pull request's nc-head-commit becomes a frozen-head when the pull request is marked ready, or, once it is ready, the moment the commit is pushed, because its review is commissioned then: do not amend it or push small corrections one at a time, because either moves the nc-head-commit under a running review. When merge-lane-2 posts a changes-requested review on your pull request, run `scripts/pull-request-fix-round-author-brief-from-blocking-findings-and-one-commit-every-finding-answered-check.py <pull request number>` at once in the pull request's checkout, and do what it prints: it tells you how to dispatch the forked subagent that runs the fix-round, gives the brief that subagent follows to its last step, the `--check`, the push and the message to merge-lane-2 included, and says how to clean up after it; if the program prints REFUSED or FAILED, do what that message says. A defect you find yourself goes in the next fix-round, or after the merge in a new pull request.
- Code that handles a failure, such as an `except` block or an exit-code check, gets a test that causes that failure.
