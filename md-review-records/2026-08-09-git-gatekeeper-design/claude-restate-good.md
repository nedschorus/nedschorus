## The job and the guarantee

1. **"One program, `scripts/git-gatekeeper.py`, is the only way any change reaches main."** — A single Python script at that path is the exclusive route to `main`; there is no other sanctioned path by which content gets onto that branch.
2. **"It holds the project's one push-capable credential."** — That program is the sole possessor of the single authentication secret that permits writing to the remote repository's `main`.
3. **"Agents — all of them, equally — invoke the program directly and never push themselves."** — Every AI agent working on this project, with no exceptions and no hierarchy among them, calls this program itself; no agent ever runs `git push` on its own.
4. **"One program, one credential, one door."** — A slogan restating the above: there is exactly one piece of software, exactly one secret, and exactly one entry point to `main`.
5. **"No agent has a doorman or relay role in another agent's check-in path; choirmaster is simply the most frequent requester."** — No agent acts as gatekeeper-by-proxy or forwarder for another agent's submission; in particular the agent named "choirmaster" holds no special position in the mechanism and merely happens to submit more often than others.
6. **"For each request the program does exactly one of two things: checks the work in, or refuses and teaches the fix."** — Every invocation ends in one of exactly two outcomes with no third possibility: either the submitted change is committed and pushed to `main`, or the program declines and, in declining, tells the caller what to do to make it succeed.
7. **"On success, four things are guaranteed true:"** — When the outcome is a successful check-in, the following four statements are promised to hold without exception.
8. **"1. The change is on main, pushed to GitHub."** — The commit exists both in the local `main` history and on the GitHub remote; success is not claimed for a merely local commit.
9. **"2. The checks ran against exactly the content that was pushed."** — Whatever validation the program performs was performed on the identical bytes that ended up on `main` — not on an earlier or different version of the content.
10. **"3. The commit's trailer lines carry the whole machine-readable record (see § The trailer)."** — All the structured metadata about the check-in is present in the `Key: value` lines at the bottom of the commit message, and those lines are the complete record — nothing structured is stored anywhere else. The exact lines are defined in the section titled "The trailer."
11. **"4. The requester has the answer: success plus the commit id."** — The calling agent receives back an explicit statement that it succeeded, together with the identifier of the commit that was created.
12. **"On refusal, the reply always has three parts, like a well-built MCP tool — never a bare error code: the named error from the fixed catalog, the specific facts (which file, which check, which mismatch), and the exact next action, written for an agent to execute."** — Whenever the program declines, its answer invariably contains three components, following the same quality standard applied to a well-designed Model Context Protocol tool response, and never consists merely of an error number or a terse code. The three are: (a) the error's name drawn from a closed, predefined list; (b) the concrete particulars of this instance — the file involved, the validation that failed, what did not match; and (c) the precise remedial step, phrased as something an AI agent can carry out directly rather than as advice for a human to interpret.
13. **"The repository is untouched — a refusal has no side effects at all."** — When a request is refused, nothing anywhere in the repository has been changed; the refusal leaves no partial commit, no altered file, no residue of any kind.
14. **"Records: git history and the invoking session's ordinary transcript are the only records."** — The sole places where evidence of check-in activity is kept are (a) the git commit history and (b) the normal conversation transcript of the agent session that made the call. Nothing else counts as, or is maintained as, a record.
15. **"No side files, no separate logs — the invocation is a normal tool call, already recorded where tool calls are recorded."** — The program does not write auxiliary bookkeeping files or its own log file, on the reasoning that calling it is just another tool invocation by an agent, and tool invocations are already captured in the session transcript.
16. **"Resubmitting is always safe."** — Sending the same request again can never cause harm, duplication, or corruption, under any circumstances.
17. **"Same request, same answer; a fixed request digests differently and processes fresh; work that already went through answers `already-checked-in <commit>`."** — Three cases: an identical resubmission produces the identical result; if the caller corrected the content, the content-hash ("digest") computed over it will differ, so the program treats it as new work and processes it normally; and if the exact work was already committed previously, the program replies with the outcome word `already-checked-in` followed by the identifier of the existing commit rather than committing a duplicate.
18. **"An agent that crashed or lost its connection never reconstructs what happened — it submits again and the program sorts it out."** — An agent that died mid-operation or was disconnected is not expected to investigate or infer the prior outcome; the prescribed recovery is simply to issue the same request again and let the program determine the correct response.
19. **"Refusals teach, retries are free: the loop self-heals, which is what near-perfect autonomous operation requires."** — Because every refusal contains instructions for fixing the problem and because repeating a request costs nothing and risks nothing, the agent's attempt-fail-fix-retry cycle recovers from errors without human intervention; the author asserts that this self-healing property is a precondition for agents operating autonomously at a very high reliability level.

## The request and the reply

1. **The command-line synopsis code block** — This shows the exact invocation form. The program is called with the subcommand `check-in`, plus: `--files` taking one or more path arguments; `--message` taking a single-line human summary stating both what changed and why; `--base` taking a commit identifier written out in full as forty hexadecimal characters; either `--import none` or the trio `--import-commit`/`--import-source`/`--import-dest` naming a commit id, a source path, and a destination path; either `--issue none` or `--issue` with an issue number; `--agent` taking a value formed as a runtime name and a model name joined by a slash; and optionally either `--wait` or `--no-wait`, where omitting both means `--wait`.
2. **"Field by field, with exact validation (all form validation is instant and synchronous in both modes; every refusal names its error and the fix):"** — What follows treats each argument individually and states precisely what makes it valid. Parenthetically: checking the well-formedness of the arguments always happens immediately and while the caller waits, regardless of whether the caller chose `--wait` or `--no-wait`; and each way a request can be rejected comes with the error's name and the corrective action.
3. **"`--files` — repository-relative paths, normalized: no absolute paths, no `..`, nothing under `.git/`, no duplicates, list non-empty."** — Each path given must be expressed relative to the repository root and in canonical form. Specifically prohibited: paths starting from the filesystem root; any path containing a parent-directory segment; any path inside git's own internal `.git` directory; the same path listed more than once; and supplying an empty list.
4. **"The new content of each path is read from the invoking agent's working copy — the program's only read of that worktree."** — For each declared path, the program obtains the intended new file content by reading that file out of the calling agent's own checkout of the repository, and this single read is the entire extent of the program's interaction with that checkout; it looks at nothing else there.
5. **"Per path the change is inferred: added (absent at base, present in worktree), modified (differs), deleted (present at base, absent in worktree)."** — The caller does not declare what kind of change each path represents; the program works it out by comparing the base commit against the agent's checkout: not in the base but present in the checkout means a new file; present in both but with different content means an edit; present in the base but missing from the checkout means a removal.
6. **"Refusals: `unknown-path` (in neither place — a typo), `unchanged-path` (declared but identical to base — declarations must be honest), `empty-change` (nothing differs at all)."** — Three named ways `--files` can be rejected: a declared path that exists neither in the base commit nor in the agent's checkout, whose likely cause is a mistyped name; a declared path whose content is byte-identical to the base, rejected on the principle that what a caller declares must accurately reflect what it actually changed; and a request in which no declared path differs from the base in any way.
7. **"`--message` — the human-readable what-and-why; becomes the commit message body above the trailers."** — This argument carries prose intended for a human reader, saying both what the change does and the reason for it; the program places that text as the main body of the commit message, positioned above the structured metadata lines.
8. **"Required, non-empty (`missing-message`)."** — The argument must be supplied and must contain text; omitting it or passing an empty string is refused with the named error `missing-message`.
9. **"Intent lives with the author; it cannot be auto-filled."** — The reason for a change is knowledge held only by whoever made it, so there is no way for the program to generate this text mechanically — which is the justification for requiring it.
10. **"`--base` — the full 40-character commit id of the main state the work started from."** — This argument identifies, by complete hexadecimal SHA-1 commit identifier, the particular snapshot of `main` that the agent had checked out when it began making its changes.
11. **"No abbreviations (short ids can turn ambiguous as history grows), no branch names (they move)."** — Shortened commit identifiers are not accepted, because a prefix that uniquely identifies a commit today may match two commits later as more commits accumulate; branch names are not accepted, because a branch name points at different commits over time and so does not pin down a fixed snapshot.
12. **"Must exist and be on main's history (`unknown-base` / `base-not-on-main`)."** — Two separate validations: the commit identifier must correspond to a commit that actually exists (otherwise `unknown-base`), and that commit must be an ancestor of the current `main` (otherwise `base-not-on-main`).
13. **"`--import` — `none`, or all three parts: the legacy commit id, the source path (must exist in the legacy repository at exactly that commit — `import-source-missing`; legacy checkout unreadable — `legacy-unreadable`), and the destination (must appear in `--files` — `import-dest-undeclared`)."** — The caller either states explicitly that this check-in imports nothing from the old system, or supplies all three pieces describing one import: which commit of the legacy repository the material comes from; which path within that legacy repository at that exact commit (if no such path exists there, the refusal is `import-source-missing`; if the legacy repository itself cannot be read at all, the refusal is `legacy-unreadable`); and where the material is being placed in this repository, which must be one of the paths already listed in `--files` (otherwise `import-dest-undeclared`).
14. **"One or two parts of three: `import-incomplete`."** — Supplying a partial import specification — one or two of the three required pieces — is refused under the name `import-incomplete`.
15. **"A second import is inexpressible by construction — it is a second check-in."** — The command syntax provides no way to describe two imports in a single request; this is deliberate, and the intended consequence is that importing two things means making two separate check-ins.
16. **"`--issue` — `none` or a positive integer."** — The value is either the literal word indicating no associated issue, or a whole number greater than zero identifying a GitHub issue.
17. **"Version 1 validates syntax only."** — In this first version, the program only checks that the value has the right form; it does not verify that an issue with that number exists or is relevant.
18. **"The artifact-lifecycle rule decides upstream, at the right granularity, which work has an issue; the gatekeeper only records the answer."** — A separate project rule governing how work items are tracked determines, earlier in the process and at whatever unit of work is appropriate, whether a given piece of work should have an issue; this program merely writes down whatever answer that rule produced and forms no judgment of its own.
19. **"`none` is honest for trivial work — an issue is never mandated per invocation (issues hold wanted things, not logs)."** — Declaring no issue is a legitimate and truthful answer for minor changes; the program never requires that every single check-in be attached to an issue, because in this project issues are meant to record things that are wanted or intended, not to serve as a running log of activity performed.
20. **"`--agent` — the runtime and model that produced the change (for example `claude-code/opus-5`), required and non-empty (`malformed-field`)."** — This argument names both the agent framework or harness in which the work was done and the specific language model that did it, joined in that two-part form; it must be present and non-empty, with an empty or badly shaped value refused as `malformed-field`.
21. **"Declared by the caller because the environment names the runtime but not the model, and the model is the half the fix ladder needs ('who last wrote this' becomes one `git log` away)."** — The caller must supply this rather than the program detecting it, because the process environment reveals which harness is running but not which model is in use; and the model is precisely the piece needed by the project's escalation procedure for fixing problems. The parenthetical states the payoff: determining which agent authored a given piece of work becomes a single `git log` query.
22. **"Cooperative class: the gatekeeper records what it is told and never guesses."** — This field belongs to a category of controls that depend on the caller telling the truth rather than being enforced; the program transcribes the declared value as given and never attempts to infer or substitute a value of its own.
23. **"Origin — auto-filled from the session environment; recorded as `none` when absent, never blocking (a transcript-less caller is honest, not an error)."** — This is not a command-line argument but a value the program obtains itself from the running session's environment, identifying the session. If no such value is available, the program records the literal `none` and proceeds; a missing session identity never causes a refusal, on the reasoning that a caller with no transcript is a legitimate situation truthfully reported, not a fault.
24. **"Meaningful because our agents are long-lived: the session id points at a readable transcript of intent."** — This field is worth recording because agent sessions in this project persist over long periods, so the session identifier serves as a pointer to a transcript that can actually be read later to discover why a change was made.
25. **"The digest — SHA-256 over: base id + sorted path list + each path's new bytes (deletions as a marker) + the import triple."** — The identifying hash is computed with the SHA-256 algorithm over a defined concatenation: the base commit identifier, the list of declared paths put in sorted order, the new content bytes of each path (with a deleted path represented by some sentinel value instead of content), and the three import fields.
26. **"Deliberately excluded: message, issue, mode, origin, agent, time — the digest identifies the work, so identical work resubmitted under different metadata still deduplicates."** — Intentionally left out of the hash input: the commit message, the issue number, the wait/no-wait choice, the session identifier, the agent declaration, and any timestamp. The rationale is that the hash is meant to be a fingerprint of the substantive change alone, with the effect that the same change resubmitted with, say, a different message or from a different session still hashes the same and is therefore recognized as a duplicate.
27. **"Computed by the program; callers generate nothing."** — The program calculates the hash itself; no calling agent ever has to compute or supply it.
28. **"The reply."** — A heading fragment announcing that the following text describes what the program sends back.
29. **"Every invocation prints exactly one JSON object on stdout: `{outcome, error?, facts?, next_action?, commit?, digest?, summary}`, where `summary` is the human-readable line — one format, not two (B1)."** — Regardless of outcome, each run of the program emits precisely one JSON object to standard output, with the listed fields — the fields marked with `?` being present only when applicable — and among them `summary` holds the prose sentence meant for a human to read. "One format, not two" means there is a single unified output shape covering both success and failure, rather than one machine format and a separate human format; this was decision item B1 in an earlier numbered list.
30. **"Exit codes: 0 success and informational answers; 1 catalog refusal (the gatekeeper working); 2 program defect — distinct so loop counters and the audit never read a gatekeeper bug as a correct refusal."** — The process exit status carries three distinguishable meanings: zero for successful check-ins and for purely informational responses; one for a refusal drawn from the defined error catalog, which represents the program functioning as designed; and two for a bug in the program itself. Two and one are kept separate specifically so that automated retry counters in agent loops, and the automated audit, cannot mistake a crash or internal defect for a legitimate, correctly-issued refusal.
31. **"Waiting caller, success: `checked-in <commit-id>`, exit 0; when the race was lost and re-application was clean, the reply also carries `integrated_over: <n>`."** — For a caller that chose to wait and whose submission succeeded, the outcome value is the word `checked-in` followed by the new commit's identifier, with exit status zero. Additionally, in the case where another check-in beat this one to `main` and this request's changes were successfully re-applied on top of the newer state, the reply includes a field naming the number of intervening commits it was integrated over.
32. **"Non-waiting caller: instant `accepted <digest>` once form is valid; the outcome is collected later with `status <digest>` (`next_action` says exactly that)."** — For a caller that chose not to wait, the program returns immediately — as soon as the arguments pass form validation — with the outcome word `accepted` and the computed digest; the actual result of the check-in is retrieved afterwards by running the `status` subcommand with that digest, and the reply's `next_action` field literally spells out that instruction.
33. **"Any refusal: the three-part teaching form, exit 1."** — Every refusal, of whatever kind, is delivered in the named-error/specific-facts/next-action structure described earlier, with exit status one.
34. **"`status <digest>` answers from what already exists (history plus the program's workspace): `checked-in <commit>`, `in-progress`, `abandoned` (workspace present, worker dead — resubmit safely), or `unknown` ('no trace; submit it' — always safe)."** — The `status` subcommand does not maintain its own database; it derives its answer entirely from two existing sources, the git commit history and the program's private scratch directory. It returns one of four results: the work is committed, with the commit id; the work is still being processed; a scratch directory for this digest exists but the process that was supposed to be working on it is no longer running, meaning the work stalled and can be safely resubmitted; or there is no evidence of this digest anywhere, in which case the advice is to simply submit the request, which is always a safe action.
35. **"`cancel <digest>` — see § States, crashes, cancel, and errors."** — The `cancel` subcommand, which takes a digest, is documented in the section titled "States, crashes, cancel, and errors" rather than here.
36. **"`imports` — prints the import table derived from history (every `Gatekeeper-import` trailer on main): what was imported, from which legacy commit, to where, when."** — The `imports` subcommand outputs a table it constructs on the fly by scanning `main`'s commit history for every commit carrying a `Gatekeeper-import` metadata line, and reports for each: the material imported, the legacy-repository commit it came from, its destination path here, and the date.
37. **"This derived view replaces the retired entry-manifest row rule; `entry-manifest.md` remains as the founding-era historical record only."** — Computing this table from history takes the place of the abolished practice of hand-appending a row to a manifest file for each import. The existing `entry-manifest.md` file is not deleted, but it now has no ongoing role — it is preserved solely as a historical artifact of the project's founding period.

## The procedure

1. **"1. Submit. The agent invokes the program with the request and its mode choice."** — Step one: the calling agent runs the program, passing the check-in request arguments together with its selection of waiting or not waiting.
2. **"2. Instant screening — synchronous in both modes."** — Step two, labelled: an immediate round of checking that happens while the caller is still blocked, whichever mode was chosen.
3. **"Form validation (above)."** — What that screening consists of first is the argument well-formedness checking already described in the previous section.
4. **"The digest is computed and looked up in history right here: already present answers `already-checked-in <commit>` with no work done."** — Also during this immediate phase, the program calculates the content hash and searches the commit history for it; if a commit already carries that hash, the program answers `already-checked-in` with that commit's identifier and stops, having performed no build, no checks, and no push.
5. **"A non-waiting caller gets `accepted <digest>` now; everything after runs identically either way."** — At this point in the sequence — and only at this point — the two modes diverge: a caller that asked not to wait receives its `accepted` acknowledgement and is released. From here on, the remaining steps are performed exactly the same way regardless of which mode was chosen.
6. **"3. Build the candidate. In the program's own private workspace (`<workspace-root>/<digest>/`) — never the agent's worktree — start from main at the declared base and apply exactly the declared changes."** — Step three: the program assembles the prospective new state of the repository ("the candidate"). It does this inside a directory it owns, located under a root directory and named by the digest, and never inside the calling agent's checkout. Construction begins from `main` as it stood at the commit the caller declared as its base, and then applies precisely the changes the caller declared — no more and no less.
7. **"Unchanged files come from main, never from the agent's possibly-stale copies."** — Every file that was not declared as changed is taken from `main` itself, rather than from the agent's checkout, whose copies of those files may be out of date.
8. **"A declared import happens here: copy from the legacy repository at the declared legacy commit; record the source for the trailer."** — If the request declared an import, this construction step is where it is performed: the material is copied out of the legacy repository as of the specified legacy commit, and the origin details are captured so they can be written into the commit's metadata lines.
9. **"4. Run the checks (§ Constructive guarantees) against the candidate — the literal bytes that would become main."** — Step four: whatever validations the program performs (described in the section on constructive guarantees) are run against the assembled candidate, which is the exact byte-for-byte content that is about to become `main`.
10. **"5. Commit. The message, then the trailer lines."** — Step five: create the git commit, whose message consists of the caller's prose message followed by the structured metadata lines.
11. **"6. Push. Happy path: main has not moved since the base; the push succeeds."** — Step six: push the commit to GitHub. In the normal case, no other commit has been added to `main` since the declared base, and the push is accepted.
12. **"Main moved: § Concurrent check-ins."** — If `main` did advance in the meantime, the handling is described in the section titled "Concurrent check-ins."
13. **"7. Answer. The waiting caller gets its line; the non-waiting caller's outcome now sits in history where `status` finds it."** — Step seven: report the result. A caller still waiting receives its reply directly. A caller that already left has no reply delivered to it; instead, the result is now recorded in the git history, which is where a later `status` query will read it from.
14. **"The workspace is deleted."** — The program's private scratch directory for this request is removed.
15. **"The requester's own working copy is never modified; the agent refreshes from main at its convenience."** — The program never writes to, updates, or otherwise alters the calling agent's checkout; bringing that checkout up to date with the new `main` is the agent's own business, done whenever it chooses.

## Constructive guarantees, the advisory, and the growth point

1. **"Most classic gate failures are made impossible by construction rather than detected:"** — Rather than adding checks that look for the well-known failure modes of code gates and report them, this design arranges its mechanics so those failures cannot occur in the first place; the following bullets list which ones.
2. **"Stray changes cannot enter — the candidate is built from the declaration; an undeclared edit never reaches it."** — Unintended modifications cannot slip into a commit, because the prospective commit is assembled starting from the caller's declared list; a file the caller did not declare is simply never copied from the agent's checkout, so its edits have no route in.
3. **"The record cannot be missing — the program writes the trailers itself."** — The structured metadata can never be absent or forgotten, because the program generates and inserts those lines rather than relying on the caller to include them.
4. **"The import record cannot lag — written during candidate construction, same commit."** — Documentation of an import can never fall behind the import itself, because the record is produced at the moment the material is copied in and lands in the very same commit.
5. **"Duplicates cannot apply — the digest screen runs at submit."** — The same work cannot be committed twice, because the hash lookup against history happens at submission time, before any work is done.
6. **"One advisory (not a refusal): if the agent's worktree contains modified files beyond the declared ones, the reply carries a note — 'worktree also differs at `x`, `y`; confirm intentional' — because the likeliest cause is a forgotten declaration."** — There is exactly one warning-type output, which does not stop the check-in: when the program observes that the agent's checkout has changes in files the caller did not declare, the reply includes a message naming those files and asking the caller to confirm the omission was deliberate, on the reasoning that the most probable explanation is that the caller meant to include them and forgot. (Note: this states the program observes the wider worktree state, which sits alongside the earlier statement that reading the declared paths is "the program's only read of that worktree"; I take the intended reading to be that it does not read other files' contents but does detect that they differ, though the text does not make the reconciliation explicit.)
7. **"Unrelated work-in-progress in the same worktree is legitimate, so this never blocks."** — Having other, unfinished, unrelated edits sitting in the same checkout is a normal and acceptable situation, which is why this observation is only a note and never causes a refusal.
8. **"In version 1, between screening and push, no refusal remains — this stage is deterministic construction and recording."** — In the current version, once a request has passed the initial screening, nothing in the subsequent build-and-check phase can reject it; that middle phase consists purely of mechanically assembling the candidate and writing down metadata, with no judgment or pass/fail gate in it.
9. **"That is the growth point, not a hole: when a test suite exists, the tests run here; when the boss gates an artifact class, its review-evidence check runs here (the request format grows its evidence field then, not before)."** — The author characterizes that empty middle phase as the designated place for future capability rather than as a design deficiency: once the project has an automated test suite, tests will execute at that point in the procedure; and if the project owner decides that some category of artifact requires proof of review, the check for that proof will also execute there — with the corresponding new command-line field for supplying the evidence being added at that time and deliberately not sooner.

## The trailer

1. **The trailer code block** — The literal format of the five metadata lines appended to each commit message: `Gatekeeper-origin` carrying either a session identifier or the word `none`; `Gatekeeper-agent` carrying the runtime/model pair; `Gatekeeper-digest` carrying the SHA-256 hash of the work; `Gatekeeper-import` carrying either `none` or a legacy commit id, a source path, an arrow, and a destination path; and `Gatekeeper-issue` carrying either `none` or a hash sign followed by an issue number.
2. **"Four facts and a pointer; nothing else."** — The trailer comprises exactly five items, understood as four pieces of factual record (agent, digest, import, issue) plus one reference to material stored elsewhere (the origin session id, which points at a transcript); no other lines are ever added.
3. **"The agent line (B6, boss-ruled 2026-07-31) names the runtime and model that produced the change, literal value, never omitted — the fix ladder's escalation needs to know what tier produced an artifact to know whether stronger models remain."** — The `Gatekeeper-agent` line, added by owner decision B6 on 2026-07-31, records the harness and model responsible for the change, written exactly as the caller supplied it and present on every commit without exception. The justification: the project's procedure for escalating a stubborn problem to progressively more capable models needs to know which capability tier already attempted a piece of work, in order to determine whether any more capable model is still available to try.
4. **"The digest line is the duplicate-detection key, not provenance — it is what makes resubmission safe."** — The `Gatekeeper-digest` line exists to serve as the lookup key by which the program recognizes work it has already committed; it is not there to attest to where the change came from or who made it. It is precisely this line that allows a resubmitted request to be identified and answered rather than re-applied.
5. **"The issue value is written in `#<n>` form deliberately: any commit reaching the default branch with `#<n>` in its message appears automatically in that issue's GitHub timeline, so an issue collects all its check-ins with zero machinery."** — Writing the issue number with a leading hash sign is a deliberate exploitation of a GitHub behavior: GitHub automatically cross-references a commit into an issue's activity timeline when that commit reaches the repository's default branch with a `#`-number reference in its message. The consequence is that every check-in belonging to an issue accumulates on that issue's page without the project having to build or run anything to make it happen.
6. **"The same collection is derivable offline (`git log --grep 'Gatekeeper-issue: #<n>'`)."** — The identical grouping of check-ins by issue can also be produced without GitHub, by running the shown `git log` search over the local history.
7. **"Refusals and other responses are never auto-posted to issues — mechanical chatter stays in transcripts; a genuinely blocking outcome earns a judgment-written comment by the requesting agent (revision convention: comments are for genuinely new events)."** — The program does not automatically write refusals, or any other program output, into GitHub issue comments. The reasoning is that routine machine-generated back-and-forth belongs in session transcripts, not on issues. When an outcome genuinely blocks progress, the appropriate response is a comment composed by the requesting agent using its own judgment about what is worth saying — following the project's established convention that issue comments should mark genuinely new developments rather than log activity.

## Concurrent check-ins

1. **"Everything rests on one property GitHub provides: a push either wins cleanly or is rejected whole — never partial, never interleaved."** — The entire concurrency design depends on a single guarantee from GitHub: a push is atomic — it either takes effect completely or is refused completely, and it can never land halfway or have its commits mixed in among another push's commits.
2. **"GitHub is the arbiter; exactly one request wins any race."** — GitHub itself decides the ordering when two requests compete, and its behavior guarantees that in any such competition precisely one of them succeeds.
3. **"No queue and no lock are built; check-ins run in parallel by default (boss ruling)."** — This design implements neither a serializing queue nor a mutual-exclusion lock; by owner decision, concurrent check-ins simply proceed simultaneously as the normal mode of operation.
4. **"The winner completes the procedure, unaware of the race."** — The request whose push is accepted follows the ordinary seven-step procedure to completion and has no knowledge that a competition occurred at all.
5. **"The loser — handled by the program, not the agent: fetch the new main; rebuild the candidate by re-applying the declared changes onto it."** — The request whose push was rejected is dealt with entirely inside the program, with no involvement from or notification to the calling agent: the program retrieves the updated `main`, then constructs a fresh candidate by applying its declared changes on top of that newer state.
6. **"Clean re-application (the usual case — different files): re-run the checks against the rebuilt candidate (version 1 re-runs everything; cheap while checks are fast) and push again; the reply notes 'integrated over N newer commits.'"** — When the re-application succeeds without contradiction — which is the typical situation because the competing requests usually touched different files — the program runs its checks again on the newly rebuilt candidate (in this first version, all checks are re-run without any attempt at selectivity, which is affordable as long as checks are quick) and attempts the push again; on success, the reply tells the caller how many newer commits its change was integrated on top of.
7. **"Real conflict (the new main touched the same content this request changes): re-applying would require guessing the author's intent, and the program never guesses — refuse with `conflict`, naming the files, the intervening commits, and the next action: update from main, adjust, resubmit (the adjusted work digests fresh, correctly)."** — When the commit that won the race modified the same content this request modifies, merging them automatically would mean the program inventing an answer about what the author meant, which it categorically will not do. Instead it refuses with the named error `conflict`, and in the three-part teaching form supplies: the conflicting files, the commits that arrived in between, and the instruction to bring the checkout up to date with `main`, resolve the difference by hand, and submit again — noting that because the resolved content differs, its hash will differ too, so the resubmission is correctly treated as new work rather than as a duplicate.
8. **"A request submitted from a behind-main worktree is the same mechanism — being behind is just 'main moved before we started.'"** — There is no separate handling for an agent whose checkout was already out of date when it submitted; that situation is the identical race case, differing only in that `main` advanced before the work began rather than during it.
9. **"Bounds, both named: the retry loop is capped at five rounds, then `main-moving-too-fast` (refuse rather than spin)."** — The design explicitly states its two limits. First: the fetch-rebuild-retry cycle is attempted at most five times; if the request loses the race five times over, the program stops and refuses with the named error `main-moving-too-fast`, on the principle that a bounded refusal is better than an unbounded loop.
10. **"And the accepted gap, recorded: changes in different files that interact semantically pass silently until tests join the checks."** — Second, an acknowledged and deliberately tolerated weakness, written down rather than hidden: two concurrent changes that touch different files but nonetheless break each other in meaning — not in text — will be integrated without complaint, and will continue to be until an automated test suite is added to the checks and can detect such breakage.
11. **"Deferred optimization, trigger named: when checks become slow (a real test suite), re-validation narrows to checks whose inputs intersect what actually changed between bases (impact analysis), so trivial head movement — ledger marks, log commits — never invalidates a pending check-in (boss ruling)."** — An improvement is postponed, with the condition for revisiting it stated in advance: once running the checks becomes expensive because a genuine test suite exists, the re-run after losing a race will be restricted to only those checks whose inputs overlap the files that actually changed between the old base and the new `main` — a technique called impact analysis. The purpose is that inconsequential advances of `main`, such as bookkeeping entries or log-only commits, will not force a full revalidation of a check-in already in flight. This is an owner decision.
12. **"A merge queue (batch-validating several queued requests against the projected combined result) is the rung above that, if volume ever demands it."** — The next escalation beyond impact analysis would be a merge queue — a mechanism that lines up several pending requests and validates them together against the state that would result from combining them — and it would be adopted only if the rate of check-ins ever grows enough to require it.

## States, crashes, cancel, and errors

1. **"States: SCREENING (synchronous, in memory, nothing on disk) → WORKING (candidate built and checked, inside `<workspace-root>/<digest>/` — concretely `$XDG_STATE_HOME/nedschorus-gatekeeper/<digest>/`, default `~/.local/state/...` (B4a): outside every repository, discoverable from the digest alone, holding the candidate clone, `worker.pid`, and the resolved request record (B4c: every environment-derived field, origin foremost, is resolved at screening into that record; the worker only reads it, never re-derives) → PUSHING (atomic attempt, retry-capped) → CHECKED-IN or REFUSED."** — A request passes through a defined sequence of conditions. SCREENING is the validation phase, performed while the caller waits, entirely in the program's memory, leaving no file anywhere. WORKING is the phase in which the candidate is assembled and validated, taking place in a directory named by the digest under a root directory; decision B4a fixed that root as the standard user state directory given by the `XDG_STATE_HOME` environment variable, under a subdirectory named for this project and program, defaulting to `~/.local/state/` when the variable is unset. Three properties are claimed for that location: it sits outside every git repository; it can be found knowing only the digest, with no index or registry needed; and it contains three things — a clone holding the candidate, a file recording the worker process's process id, and a record of the fully-resolved request. Decision B4c specifies that every field the program derives from its environment — with the session origin as the primary example — is determined during SCREENING and written into that record, so that the background worker only ever reads those values and never re-derives them for itself (which matters because the worker may run in a different environment than the original caller). PUSHING is the phase of attempting the push, which is all-or-nothing and limited to a bounded number of retries. The sequence terminates in exactly one of two final conditions: successfully committed, or refused.
2. **"After either ending the workspace is deleted, with one exception (B4d): a refused `--no-wait` request keeps its workspace holding just the JSON refusal record; `status` returns it once, then sweeps."** — Whichever of the two endings occurs, the scratch directory is removed, except in one situation established by decision B4d: when a request submitted in non-waiting mode is refused, its directory is kept, emptied of everything but the JSON object describing the refusal. This exception exists because such a caller has already been released and has no other way to learn the reason. The `status` command hands that record back on the first query and then deletes the directory.
3. **"Named residual (accepted): a caller crashing between sweep and read loses the reason — rare, recoverable by resubmit."** — A remaining imperfection is stated explicitly and consciously tolerated: if the caller dies after `status` has returned the refusal record and deleted it but before the caller has actually consumed it, the refusal reason is gone permanently. The design accepts this on the grounds that it is unlikely and that the caller can in any case recover by submitting the request again, which will reproduce the same refusal.
4. **"Durable traces: a checked-in request is its commit on main; a refused waiting request deliberately leaves nothing."** — What persists after the fact: a successful request's lasting evidence is simply its commit on `main`. A refused request from a caller that waited leaves no trace at all anywhere, and this absence is intentional rather than an oversight.
5. **"Crash recovery — one rule, not a procedure."** — The handling of crashes is deliberately expressed as a single rule to follow, rather than as a multi-step recovery routine that would have to be understood and executed correctly.
6. **"The whole pipeline has exactly two durable effects: the workspace directory, and the atomic push."** — Across its entire operation, the program makes only two changes that survive its own termination: creating the scratch directory, and pushing to GitHub.
7. **"A crash or lost connection at any moment therefore leaves one of two worlds: the commit is on main, or it is not and a stale workspace remains."** — Because there are only those two durable effects, a failure at any point whatsoever can only leave the system in one of two possible conditions: either the push already happened and the commit exists on `main`, or it did not and there is an orphaned scratch directory left behind.
8. **"Recovery is: resubmit."** — The complete recovery instruction, for either condition, is to issue the same request again.
9. **"The program checks the digest against history — found means `already-checked-in <commit>`; absent means the leftover workspace is swept and the work runs fresh."** — On that resubmission, the program looks up the hash in the commit history. If it finds it, the first condition held and it replies that the work is already committed, naming the commit. If it does not find it, the second condition held, so it deletes the orphaned directory and processes the request from the beginning.
10. **"No journal, no repair mode."** — The design contains no write-ahead log of intended operations and no dedicated repair or recovery subcommand; the resubmit rule replaces both.
11. **"`status` distinguishes WORKING from abandoned (workspace present, worker process dead) via the recorded process id, so a died-silently worker is a named, resubmittable state — never a forever-'in-progress'."** — The `status` command tells apart a request genuinely still being processed from one whose worker has died, by reading the recorded process id and checking whether that process is still alive; a directory with a dead worker is reported as `abandoned`. The point is that a worker that terminated without reporting anything produces an explicitly named result that the caller knows how to act on (resubmit), rather than leaving the request permanently reported as in progress.
12. **"`cancel <digest>` — built in version 1 (boss ruling: the need arrives with slow checks, the machinery it needs already exists, and it is three branches)."** — The cancel subcommand, which identifies its target by digest, is included in the first version rather than deferred. The owner's reasoning had three parts: the situation where cancelling matters will appear as soon as the checks take a long time; everything cancel requires — the workspace, the recorded process id — is already present for other reasons; and the implementation itself is trivially small, amounting to three conditional branches.
13. **"Any agent may cancel; there is no permission machinery — cooperative model; the workflow simply does not teach cancel as a routine move (and the author may be gone; authorship grants no special judgment)."** — No authorization is checked: any agent can cancel any pending request. There is no access-control mechanism at all, consistent with the design's general reliance on agents cooperating rather than being restricted. Misuse is discouraged instead by the documented workflow simply not presenting cancel as a normal thing to do. Two supporting reasons for not restricting cancel to the original submitter: that agent may no longer exist by then, and having authored a request confers no better judgment about whether it should be aborted.
14. **"Outcomes, exactly three: digest already in history → `too-late — already-checked-in <commit>` (the remedy for a bad landed change is a revert: an ordinary check-in whose change undoes a previous one, through the same gate); live worker found → kill it, sweep the workspace, `cancelled`; nothing found → `unknown-request`."** — Cancel can end in precisely three ways and no others. If the work is already committed, cancel answers `too-late` together with the already-committed result and its commit id — and the parenthetical explains the correct alternative in that case: reverse the change by making an ordinary new check-in whose content undoes the earlier one, submitted through this same program like any other change. If a worker process for that digest is running, cancel terminates it, deletes the scratch directory, and answers `cancelled`. If there is no trace of the digest at all, cancel answers `unknown-request`.
15. **"The cancel-versus-push race resolves by the push's atomicity: kill the worker, then ask history whether the digest made it."** — When a cancel arrives at the same moment the worker is pushing, the ambiguity is resolved using the fact that a push either fully happened or fully did not: the program first kills the worker, then consults the commit history to determine which side of that boundary things landed on, and answers accordingly.
16. **"Cancel only makes sense before the check-in completes (boss ruling); after, revert."** — By owner decision, cancelling is defined as meaningful only while a request is still in flight; once it has been committed, the appropriate action is not cancellation but a reverting check-in.
17. **"The error catalog — every ending named, three-part teaching form:"** — What follows is the complete, closed list of ways a request can end; the design's claim is that no ending is unnamed, and each is delivered in the named-error/facts/next-action structure.
18. **"Form (instant): `malformed-field`, `missing-message`, `unknown-path`, `unchanged-path`, `empty-change`, `unknown-base`, `base-not-on-main`, `import-incomplete`, `import-source-missing`, `import-dest-undeclared`, `legacy-unreadable`."** — Eleven refusals arising from argument validation, all issued immediately during screening: a badly-shaped field value; a missing or empty message; a declared path that exists nowhere; a declared path identical to the base; a request in which nothing differs; a base commit id that does not exist; a base commit that is not on `main`'s history; a partially-specified import; an import source path absent from the legacy repository at the given commit; an import destination not present in `--files`; and an unreadable legacy repository.
19. **"Integration: `conflict`, `main-moving-too-fast`."** — Two refusals arising from concurrency: overlapping content changes that the program will not merge by guessing, and exhaustion of the five-round retry limit.
20. **"Infrastructure: `push-auth-failed`, `network-down`, `workspace-io-error` — all safely resubmittable."** — Three refusals arising from the environment rather than from anything wrong with the request: credentials rejected by the remote, no network connectivity, and a filesystem read/write failure in the scratch directory. For all three, submitting the same request again once the underlying condition clears is safe and is the expected response.
21. **"Answers, not errors: `already-checked-in <commit>`, `accepted <digest>`, `cancelled`, `too-late`, `unknown-request`."** — Five outcome values that are catalogued alongside the errors but are classified as informational responses rather than refusals: work found already committed; a non-waiting submission acknowledged; a cancellation carried out; a cancellation arriving after completion; and a cancellation or query for a digest with no trace.
22. **"The autonomy standard, met: no unnamed endings; every refusal teaches; resubmit always safe; nothing routes to the boss mechanically — he is consulted by agents' judgment, never by the machinery."** — The design asserts it satisfies its own criterion for supporting autonomous operation, itemized as four properties: every possible way a request can end has a defined name; every refusal includes the corrective action; resubmission is unconditionally harmless; and no code path automatically escalates anything to the human owner — when he becomes involved, it is because an agent decided on its own judgment to consult him, never because the program routed something to him.

## The credential and enforcement

1. **"The dedicated-identity rung was admitted early (user-ruled 2026-08-09, exercising the trigger named below); the layout it replaces is recorded first because it is still the live state until the amendment is applied."** — An item that had been deliberately deferred to a later stage — giving the gatekeeper its own separate GitHub identity — has been pulled forward into the current design by a user decision on 2026-08-09, which invoked the very condition that the deferral list had specified as the signal for reinstating it. The section is ordered so that the older arrangement is described before the new one, because until the decided change is actually applied to GitHub, the older arrangement is what is really in force. ("Rung" I read as a step on a ladder of progressively stronger enforcement; "user-ruled" and "boss-ruled" appear to refer to the same person, though the document does not say so explicitly.)
2. **"Branch protection, LIVE since 2026-07-21: pushes to `main` restricted to the machine credential (`NedLern`) alone; enforce-admins on; force-push and deletion blocked."** — GitHub's branch-protection feature has actually been configured on the real repository since 2026-07-21, with these settings: only the account named `NedLern` — the account used by the machine rather than by a person — is permitted to push to `main`; the setting that makes protection rules apply to administrators as well as ordinary users is switched on; and both history-rewriting force-pushes and deletion of the branch are forbidden.
3. **"The org has two owners (`NedLern`; `NedLerner`, settings and emergency power, no push), so either account can recover the org if the other is lost; a protection change by any owner is a deliberate, visible act, never a standing path."** — The GitHub organization has exactly two accounts with owner privileges: `NedLern`, and `NedLerner`, the latter holding the ability to change settings and act in emergencies but not permitted to push. Having two exists so that if access to either account is lost, the other can still administer and recover the organization. Although an owner could in principle alter the protection settings, doing so requires a conscious action that is recorded and visible, so it does not constitute an ongoing open route around the gate.
4. **"The boss never commits directly; a boss-originated change is drafted with an agent and checked in like any other."** — The human owner does not make commits himself. When a change originates from him, it is written up in collaboration with an agent and then submitted through this program on the same terms as any other change.
5. **"Issues cost nothing: the repository is public, so opening and commenting needs no repository permission."** — Working with GitHub issues requires no grant of access, because the repository is publicly visible and GitHub allows any authenticated account to open issues and post comments on a public repository.
6. **"The layout amendment (ruled 2026-08-09, C1/C3 — applying it needs an org owner): the pusher role moves to a dedicated GitHub account — a collaborator with write on this one repository, not admin, never an org owner — and protection's push restriction names it alone."** — The change decided on 2026-08-09, recorded as items C1 and C3, whose implementation requires someone holding organization-owner rights to perform: the capability to push to `main` is transferred from the current machine account to a newly created GitHub account existing solely for this purpose, which is added as a collaborator with write access on this single repository — not granted administrative rights on it, and under no circumstances made an owner of the organization. The branch-protection push restriction is then updated to list that account and nothing else.
7. **"Chosen over the App/CI form this section previously sketched: an App or CI job relocates the gate into CI, which this design scopes out; a plain account keeps the gate a local program."** — This plain-account approach was selected in preference to the alternative previously outlined here, which would have used a GitHub App or a continuous-integration job as the pushing identity. The reason for rejecting that: implementing the pusher as an App or CI job would move the enforcement point into the CI system, and CI is explicitly outside this design's declared scope; using an ordinary account preserves the property that the gate is a program running locally on the machine.
8. **"Blast radius of a stolen token: commits to this one repository, nothing else."** — The consequence of the dedicated account's credential being compromised is bounded to what an attacker could do with write access to this single repository — make commits to it — and extends to no other repository, no organization settings, and nothing beyond.
9. **"Owner power stays with the user; no agent ever holds it."** — Organization-owner privileges remain exclusively with the human; no agent is ever given a credential carrying them.
10. **"The Unix-user boundary (C2) — where the enforcement actually lives: GitHub restricts accounts, not processes, and on one machine every process of one Unix user reads the same credential files."** — Decision item C2 identifies the point at which the restriction is genuinely enforced. The reasoning: GitHub's controls operate on the level of accounts, and it has no way to distinguish which program on a machine is using an account; and on a single machine, all processes running under one operating-system user account can read that user's credential files. So GitHub's restriction alone does not prevent an agent process from pushing, since it would be reading the same credential.
11. **"So the main-capable credential is owned by a dedicated Unix user, unreadable by agent sessions, and agents invoke the program through a sudoers rule scoped to exactly it."** — The remedy: the credential that can push to `main` is stored under a separate operating-system user account created for this purpose, with filesystem permissions that make it unreadable by the operating-system user under which agent sessions run. Agents reach the program via a `sudo` configuration entry that permits them to execute exactly this one program as that dedicated user and nothing else.
12. **"That is the step at which 'agents never push' becomes impossible rather than instructed; it also makes the gatekeeper literally an invocable service any agent on the box can call."** — This arrangement converts the rule that agents do not push from a documented instruction that agents are expected to obey into a technical impossibility, since they simply lack read access to the credential. A secondary consequence: the gatekeeper thereby becomes, in a literal technical sense, a service — a privileged executable that any agent on that machine can invoke.
13. **"Agent credentials are scoped (C4): each agent host holds a fine-grained token for this repository only — contents read/write (branch pushes are open; the push-less ruling covers main alone), issues write — never a classic all-repository token, and never the `workflow` scope (capability-by-landing class, nedschorus#31)."** — Decision C4: every machine running agents holds a GitHub fine-grained personal access token limited to this one repository, granting exactly two permissions — read and write on repository contents, and write on issues. The parenthetical clarifies that "contents write" does allow pushing to branches other than `main`; the prohibition on agents pushing applies only to `main`. Explicitly excluded: GitHub's older "classic" token type, which grants access across all repositories the account can reach; and the `workflow` permission, which allows modifying CI workflow definitions. That exclusion is attributed to a category of capability described on issue 31 of the nedschorus repository, whose name I read as covering capabilities an agent could grant itself simply by getting a change onto `main`.
14. **"Issue work is scoped, not gated: no invariant like 'one writer to main' exists there, so discipline lives at the skill and hook rung, not at a gate."** — Agents' interaction with GitHub issues is controlled by limiting what their tokens can reach, rather than by routing it through a gatekeeper program. The justification is that issues carry no correctness property analogous to "exactly one writer to `main`" that a gate would be protecting, so whatever consistency is wanted there is achieved through documented skills and harness hooks — the cooperative layers — instead of through an enforced chokepoint.
15. **"The cooperative tier (C6), above the boundary and never a substitute for it: a PreToolUse hook rewrites `gh` calls seamlessly into their disciplined form; a `git push` toward this repository's remote gets deny-with-exact-invocation instead — a push carries none of the declaration, and auto-deriving all of it would gut the intentionality the `unchanged-path` refusal exists to force."** — Decision C6 describes a layer of voluntary assistance that sits on top of the hard Unix-user boundary and is explicitly not offered as a replacement for it. It works through a harness hook that intercepts tool calls before they execute. For calls to the `gh` command-line tool, the hook silently rewrites them into the form the project's conventions require, so the agent notices nothing. For a `git push` aimed at this repository's remote, the hook takes the different approach of blocking the call and returning the exact gatekeeper invocation the agent should have used instead of rewriting it automatically. The reason for that difference: a `git push` command contains none of the information a check-in request requires — no message, no base, no issue, no agent declaration — and if the hook were to synthesize all of those automatically, it would destroy exactly the deliberateness that the `unchanged-path` refusal was designed to compel from callers.
16. **"The check-in skill front-loads the declaration (`--files` from the agent's own staging, `--base` computed as the merge-base, message passed through verbatim), so the agent contributes only what it already does by training."** — A documented skill for performing check-ins prepares most of the request in advance: the file list is taken from what the agent has already staged in git, the base commit is computed automatically as the merge-base against `main`, and the agent's own message text is passed along unchanged. The result is that the only thing the agent itself has to supply is the kind of thing it produces naturally anyway — a commit message — with the mechanical fields filled in for it.
17. **"Refusals teach, as the final tier."** — Below the rewriting hook and the skill, the last layer of the cooperative arrangement is the refusal mechanism itself: when everything above fails to keep an agent on the correct path, the program's teaching refusal corrects it.
18. **"Break-glass (C5) — an unlockable credential, never a standing ungated agent: gate defects are recovered from the gate's own history — the program stays one standard-library-only file precisely so any historical version is directly runnable; a landing the gate wrongly refuses uses a sudoers entry requiring the user's password, approved in the moment; credential expiry and protection misconfiguration are org-owner territory, the user's alone."** — Decision C5 defines the emergency-override arrangement, characterized as a credential that can be unlocked when needed rather than as any permanently-existing agent that bypasses the gate. It covers three distinct emergency situations. If the gatekeeper program itself is broken, recovery is by retrieving a working earlier version from the program's own git history — and this is why the program is kept as a single file depending on nothing beyond the Python standard library: any version checked out of history can be run directly without installing anything. If the gate incorrectly refuses a legitimate change, the change is pushed via a separate `sudo` configuration entry that demands the human's password, so the override happens only with his explicit real-time approval. And if the credential has expired or branch protection is misconfigured, resolution requires organization-owner privileges, which only the human has. (The word "landing" here is the retired vocabulary noted in the preamble; I read it as meaning a check-in.)
19. **"Privileged invocations refuse the test seams (C7): `--repo` and `--remote` exist so tests can hand the program throwaway repositories."** — Decision C7 concerns two command-line options whose purpose is to let the test suite point the program at disposable repositories created for testing rather than at the real one.
20. **"Run as the credential-holding user, they are refused and the remote is pinned to the canonical repository; tests run unprivileged and keep the seams."** — When the program is executed under the dedicated user that holds the `main`-pushing credential, those two options are rejected outright and the destination remote is forced to the real project repository, so the privileged mode cannot be aimed anywhere else. The test suite runs as an ordinary unprivileged user, where the options remain available and function normally.
21. **"The honest singleton statement (boss ruling), still true until C2 is installed: branch protection restricts the account, not processes — anything running as that account, on any machine, can push."** — A frank acknowledgement, made as an owner decision, of a limitation that remains real until the Unix-user separation of C2 is actually implemented: GitHub's protection constrains which account may push, and imposes no constraint on which program or process does the pushing, so any process anywhere that can authenticate as that account can push to `main`. ("Singleton" I read as the design's claim that there is exactly one pusher; the sentence states honestly how far that claim actually holds.)
22. **"Process-level ordering needs no lock: the atomic push arbitrates."** — Even though multiple processes may push, no locking mechanism is needed to sequence them, because the all-or-nothing nature of a push already determines a single winner in any conflict.
23. **"What remains procedural before C2 is only that agents use the program rather than raw `git push`."** — Until C2 is in place, exactly one element of the design still depends on agents voluntarily complying rather than being prevented: their choosing to call the gatekeeper program instead of running `git push` directly.
24. **"CLAUDE.md is documentation, never enforcement (boss ruling; his rationale verbatim: a python script does not read it, and different machines may carry different copies)."** — An owner decision holds that the `CLAUDE.md` instruction file can only ever inform behavior, never compel it. His reasoning is quoted directly: the gatekeeper is a Python program and does not read that file at all, and separate machines may hold different and divergent versions of it.
25. **"The same is true of harness hooks: they configure a harness, and only cooperating harnesses read them — which is why C6 is a convenience tier and C2 is the boundary."** — The identical limitation applies to the hooks described above: a hook is a setting belonging to a particular agent harness, and it has effect only when the process in question is running under a harness that reads and honors it. This is precisely the reason the hook layer of C6 is classified as a convenience rather than as protection, while the operating-system-user separation of C2 is the real enforcement boundary.
26. **"Nothing in this design depends on either."** — The design's guarantees are constructed so that none of them relies on `CLAUDE.md` or on harness hooks being present or obeyed.
27. **"The raw-push residual is detected, not prevented: a standing audit at each handoff scrub scans main for commits missing valid trailers and files a `draft` issue naming them, with three named outcomes — `protection-ok` / `protection-wrong` (differing settings named) / `audit-failed` (gh missing, unauthenticated, API error) — failing loudly as its own outcome, never a silent skip into green (B3c)."** — The remaining possibility of someone pushing directly rather than through the gate is handled after the fact rather than blocked in advance: a recurring automated check, run every time a session-handoff cleanup routine executes, examines `main` for any commit lacking properly-formed gatekeeper metadata lines and, if it finds any, opens a GitHub issue in draft state naming those commits. That audit is also required to report exactly one of three explicitly named results: the protection settings match what they should be; the protection settings differ, in which case the specific differing settings are named; or the audit could not be performed at all — because the `gh` command-line tool is not installed, because it is not authenticated, or because the GitHub API returned an error. Decision B3c requires that the inability-to-check case be surfaced as its own visible failure result, and specifically forbids treating an audit that could not run as if it had run and passed.
28. **"(The audit also covers the sibling residual while it exists: an agent-held owner credential could deliberately edit protection — same cooperative class, same catch; C3 removes that class by taking owner power out of agent hands entirely.)"** — The same audit additionally addresses a related weakness that exists under the current arrangement: because an agent presently holds a credential with organization-owner rights, an agent could in principle change the branch-protection settings itself. That weakness belongs to the same category as the raw-push weakness — prevented only by cooperation — and is caught by the same audit. Once decision C3 is implemented, that category of weakness disappears, because agents will no longer hold any owner-level credential at all.

## Relationship to the legacy design

1. **"The legacy system's `git-clean-slate-plan.md` (read-only reference, `~/Projects/nedlern/docs/working/proposed/`) designed the many-writer version of this problem."** — The predecessor project contains a design document at the given path — which this project may read but must not modify or execute — that addressed the same problem of controlling access to `main`, but in a setting where many parties wrote to the repository rather than a single one.
2. **"This design keeps only two of its ideas, re-derived: workflow rules expressed as CLAUDE.md documentation, and protection-as-lock reduced to one credential."** — Exactly two concepts from that earlier document survive into this one, and even those were arrived at independently here rather than copied: stating workflow rules as documentation in `CLAUDE.md`, and using GitHub's branch protection as a locking mechanism by narrowing push rights down to a single credential.
3. **"Never imported: the three GitHub Apps, the credential helper, per-agent branches, the PR pipeline for ordinary work, the parking states."** — Five elements of the legacy design were deliberately not carried over at any point: its three separate GitHub App integrations; its git credential-helper component; the practice of giving each agent its own branch; routing routine changes through pull requests; and its set of intermediate "parked" states for work in waiting.
4. **"The repo's git config is minimal and stated here, not imported: `user.name`/`user.email` for the machine identity, `useConfigOnly` so no global identity leaks in."** — This repository's git configuration is deliberately small and is specified in this document rather than copied from the legacy system. ## Build slice (choirmaster task 1)

1. **"The git config above + `git-gatekeeper.py` with `check-in`, `status`, `cancel`, `imports` + the CLAUDE.md workflow lines + tests:"** — A fragment enumerating the total deliverable of this unit of work, assigned as the first task for the choirmaster agent: the git configuration settings just described, the program itself implementing its four subcommands, the instruction lines to be added to `CLAUDE.md`, and an automated test suite — the tests being specified by the twelve items that follow.
2. **"T1 every form error refuses with its named error and no side effects"** — Test 1: for each of the argument-validation errors, verify the program refuses with the correct error name and that nothing anywhere was changed as a result.
3. **"T2 happy path: the four success guarantees verified, trailer exact"** — Test 2: for a normal successful check-in, verify all four of the promised success properties hold and that the commit's metadata lines match the specified format exactly.
4. **"T3 digest: identical resubmit answers `already-checked-in`; changed content digests fresh; metadata-only changes do not change the digest"** — Test 3: the hashing behavior in three respects — resubmitting identical work returns the already-committed answer; altering the content produces a different hash so the work is processed as new; and altering only metadata fields such as message or issue leaves the hash unchanged.
5. **"T4 concurrent submissions (injected delay): winner clean, loser integrates over newer commits and succeeds"** — Test 4: force a race by artificially inserting a delay so two submissions overlap, then verify that the winning one completes normally and the losing one re-applies its changes on top of the new `main` and ultimately succeeds.
6. **"T5 conflict: same-content collision refuses with files + commits + next action"** — Test 5: when the racing changes touch the same content, verify the loser is refused with the `conflict` error carrying the affected files, the intervening commits, and the corrective instruction.
7. **"T6 retry cap: sustained head movement ends in `main-moving-too-fast`, never a spin"** — Test 6: with `main` being advanced continuously so every retry loses, verify the program stops after its five rounds with the named refusal rather than looping indefinitely.
8. **"T7 crash recovery: worker killed mid-WORKING → `status` reports abandoned, resubmit sweeps and completes; killed after push → resubmit answers `already-checked-in`"** — Test 7: two crash scenarios. Killing the worker while it is building and checking the candidate should make `status` report the abandoned state, and a resubmission should delete the orphaned directory and carry the work through to completion. Killing the worker after the push has already gone through should make a resubmission report that the work is already committed.
9. **"T8 cancel: all three outcomes; cancel-after-push answers `too-late`"** — Test 8: exercise each of cancel's three defined results, with particular attention to the case where cancel arrives after a successful push, which must report `too-late`.
10. **"T9 advisory: undeclared worktree changes noted, never blocking"** — Test 9: when the agent's checkout contains changes to files not declared in the request, verify the reply mentions them and that the check-in nevertheless succeeds.
11. **"T10 `imports` derives the exact table from trailers"** — Test 10: verify the `imports` subcommand reconstructs precisely the expected table from the `Gatekeeper-import` metadata lines in history.
12. **"T11 each import error class refuses correctly"** — Test 11: verify each distinct way an import specification can be wrong produces its corresponding named refusal.
13. **"T12 a raw push (simulated) is caught by the trailer-absence audit"** — Test 12: simulate someone pushing to `main` directly rather than through the gate, and verify the audit detects that commit by noticing it has no valid metadata lines.
