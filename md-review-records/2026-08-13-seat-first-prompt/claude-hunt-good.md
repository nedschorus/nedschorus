## Findings, in document order

**1. Line 1 — "You have no context beyond this file; everything you need is reachable from here."**
Two problems. (a) Taken literally the first clause is false and the file itself disproves it: `CLAUDE.md` at the repository root is auto-loaded into every session in this project, and Step 3 line 19 tells the agent to read it as a *standing* rule set — so context beyond this file both exists and is required. An agent that believes the first clause will not reconcile what it was already handed against what this file says (see finding 12, where the two disagree). (b) "everything you need is reachable from here" is broader than holds. The briefs this file routes to require things no path in this file reaches: `doctrine-instructions.md` sends the agent to read GitHub issue #32, `skill-builder-instructions.md` to #24 and #18, `fleet-instructions.md` to check whether PR #57 merged — all of which need network access and a working `gh` credential that this file never mentions, never tells the agent how to test, and never says what to do about if absent. Harm: a seat whose `gh` auth is broken has been told, in its only zero-context document, that everything is reachable, so it will treat the failure as a local mistake rather than a launch defect worth reporting. Confidence: sure.

**2. Line 3 — "Your seat name is the name of your working directory. Run `pwd`: if it is `/home/nedlern/agents/<name>`, then `<name>` is your seat."**
The two sentences give different rules and the conditional has no else-branch. Sentence one says the seat name is the basename of the working directory, whatever the directory is. Sentence two only assigns a seat name when the working directory sits directly under `/home/nedlern/agents/`. So for any other `pwd` — a nested subdirectory, a hand-started session, a worktree elsewhere such as `.claude/worktrees/<something>` (a location this project actually uses; the guard script names `.claude/worktrees/` as an agent's isolated checkout) — sentence one yields a name and sentence two yields nothing, and the file never says which reading wins or what to do. Every later step depends on `<name>`: Step 2's branch check, the repair command, and the `docs/agents/<name>-instructions.md` path. Harm: an agent launched into an unexpected directory either invents a seat name from a basename that is not a seat, or stalls with no stated recovery. Note that the file *does* state a stop rule for the adjacent failure (line 21, no matching brief), which makes the silence here look like an oversight rather than a deliberate omission. Confidence: sure.

**3. Line 5 — "so `git rev-parse --show-toplevel` should answer with your own directory and `git branch --show-current` with your seat name."**
Two checks are prescribed but only one failure mode is handled. The remedy in line 7 is gated on "If it is *not* a checkout" — a home that *is* a checkout but fails the second check (wrong branch, detached HEAD, or a branch whose name differs from the seat name) passes that gate and falls through with no instruction at all. The file also never says what a detached HEAD would print (`git branch --show-current` outputs an empty string, not an error), so the agent has no stated way to distinguish "check failed" from "command returned nothing". This case is reachable: it is exactly what a partially-completed or interrupted launcher run leaves behind, and it is more dangerous than a missing checkout because everything looks superficially fine while commits land on the wrong branch. It also compounds finding 2: if the branch name and the directory basename disagree, the file has given two conflicting definitions of "your seat name" and no tiebreak. Confidence: sure.

**4. Line 7 — "you are running without any of them and cannot retrofit them by fixing the directory now" — followed immediately by "the repair is:" and a directory-fixing command.**
These contradict on their face. The sentence asserts that fixing the directory cannot restore the settings; the next sentence offers fixing the directory as "the repair". The intended distinction is presumably between *this* session (which cannot gain the settings) and a *future* session (which would), but the word "repair" is unqualified and the block is presented as the thing to do when the user says continue. Harm: an agent that runs the repair will reasonably believe it now has the status line, the recycle hook, and the instruction-file guard, when line 7's own claim is that it does not — and it will then rely on the guard (line 25) that is not loaded. **5. Lines 9–11 — the `git ... worktree add /home/nedlern/agents/<name> -b <name> origin/main` block.**
Wrong when obeyed literally in the situation that triggers it. The agent reached this block because Step 1's `pwd` returned `/home/nedlern/agents/<name>` — so that directory exists. `git worktree add` refuses an existing path unless it is empty: it fails with `fatal: '<path>' already exists`. Whatever put non-checkout content there (a partially-run launcher, a stray file, a session log) makes the command fail, and the file states no precondition, no check, and no alternative. Related unstated dependencies in the same command: that `/home/nedlern/Projects/nedschorus` exists on this box and is a git repository (the file never says so, and this is the zero-context document); and that `origin/main` is fetched and current — a stale `origin/main` silently branches the seat from an old commit, which is a quiet wrong answer rather than a visible failure. Confidence: sure that `worktree add` refuses a non-empty existing path; unsure how often the directory is non-empty in practice, but the file gives no way to find out.

**8. Line 13 — "git permits a branch in only one worktree at a time, which is what keeps seats from colliding".**
An absolute claim broader than it holds, offered as the load-bearing guarantee of seat isolation. Ordinary counterexamples: `git worktree add --force` overrides the check outright; a branch checked out in a worktree can simultaneously be checked out in a separate *clone* of the same repository, which git cannot see; and two seats operating in detached HEAD on the same commit collide freely. So the stated invariant is a convenience check inside one repository's worktree set, not a collision guarantee. Harm: an agent told this is "what keeps seats from colliding" will not check for a colliding seat before working, and will not report the collision when it happens. This also runs against the project's own instruction in `CLAUDE.md`: "absolute imperatives like 'always' or 'never' can backfire in unforeseen conditions. Use them cautiously." Confidence: sure.
