## 1. Your solution sketch

**Shape.** Two deterministic scripts and one tiny piece of model judgment. A turn-boundary hook measures context fill from the session's own transcript and, past a threshold, injects one instruction: "write your handoff note." A cron-run reaper script kills the session at a safe boundary and relaunches a fresh one in place, with an opening prompt assembled mechanically from the note, the task files, and (as fallback) the predecessor's transcript tail. The only model judgment in the whole loop is the dying session writing its note and the successor's first turn interpreting it. State between components is marker files in one machine-local directory; git stays the durable record for work products.

**Components.**

- **`fleet-launch` wrapper (script, genesis step).** Every fleet session — interactive or headless — starts through it. It records a registry entry per session (`~/.fleet/sessions/<id>.json`: PID, tmux pane if any, cwd, launch flags, model) and execs the CLI. This is what lets the reaper relaunch anything without a human remembering how it was started; successors are launched through the same wrapper, so the registry self-perpetuates.
- **Fill-check hook (script, runs at every turn boundary).** Reads the tail of the session's own JSONL transcript, computes current context size from the last assistant record's token usage, divides by a per-model window table. At a *soft* threshold (~50%) it injects, once, "checkpoint: commit WIP, update your task file." At the *hard* threshold (~70%) it injects "write a handoff note to `~/.fleet/handoff/<id>/note.md` using the template, then touch `note.done`; take no new work," and drops `handoff.requested`. Injecting via hook rather than relying on trained habit is the mechanical guarantee: a session cannot forget to hand off, because the instruction arrives from outside every turn until acted on. Thresholds are deliberately low — the point is recycling *before* degradation, and the note needs headroom to be written well.
- **Reaper (script, run by cron/systemd timer every minute; flock per session).** Not a daemon; a scan. For each registered session: if `handoff.requested` and `note.done` exist and the session is idle (last transcript record is a completed turn, no recent user input), kill and relaunch. If the note hasn't appeared after a grace period (session confused or hung), kill anyway — the fallback path covers it. The reaper is also the fleet watchdog for free: a session whose transcript hasn't moved in N minutes, or whose PID is gone, gets the same treatment. Interactive sessions are recycled in place with `tmux respawn-pane -k` so the boss's layout survives; headless ones are re-exec'd from registry flags.
- **Handoff note (model judgment #1).** A short template the dying session fills: current task and its exact state, next concrete step, gotchas, pointers (branch, PR, issue), and any background processes it started. It carries only the delta that isn't already in git, the task files, or the working tree — which, note, *survives the kill untouched*: the successor runs in the same directory, so uncommitted edits are never lost by the handoff itself. Push discipline (in CLAUDE.md, nudged by the soft-threshold checkpoint) covers machine loss, a separate risk.
- **Successor launch (script).** The reaper launches the fresh session — same id as the predecessor so the harness's task files carry over automatically (if probing shows same-id relaunch is unsafe, the fallback is a fresh id plus a deterministic copy of the task files; either way it's one script line, plus a lineage record `predecessor: <old-id>`). The opening prompt is assembled by template, not by a model: fixed orientation text ("you are the successor; questions are not an option in headless mode; trust git and the task file over the note where they disagree"), the note inline, and — if there is no note — the last N assistant text messages extracted deterministically from the predecessor's transcript, tool dumps stripped. Interpreting all that is model judgment #2, and the last.
- **Manual controls (files, not commands).** The boss's "recycle now" is touching `handoff.requested` — the same marker, same single code path as the automatic trigger. A `freeze` file (global or per session) disables recycling while debugging. Anything that can touch a file — ssh one-liner from the Mac, a synced folder — is a trigger; no typing into panes, ever.
- **Alerting.** The reaper pages the boss (push notification) only on genuine exceptions: successor fails to produce a transcript within M minutes of launch after K retries; loop guard trips (it refuses to recycle a session younger than X minutes/turns — a fresh session that's instantly "full" means a config problem, e.g. a bloated CLAUDE.md, not a recycling problem); transcript parse failure (fail *safe*: don't recycle, alert — a heavy session is degraded, a wrongly killed one is worse).

**Lifecycle (marker files are the state machine):** WORKING → `handoff.requested` (hook or boss) → `note.done` or grace expiry → KILLED (reaper, at idle boundary only) → RELAUNCHED (reaper, templated prompt) → successor's first turn reorients → WORKING. Every transition is a file appearing; every actor is restartable and idempotent because it re-derives its decisions from the transcript and markers on each run.

**Failure containment.** No note → transcript-tail fallback; cost is a few reorientation turns. Kill mid-flight → same class as a crash, which the system tolerates anyway; the working tree and `git status` tell the successor the truth. Launch fails → retry with backoff, then page; meanwhile the note, tasks, transcript, and working tree all persist, so recovery is one manual `fleet-launch`. Double-fire → flock. Stale or wrong note → successor instructed to trust durable state over the note. Cron dead → hook-side cross-check: if fill exceeds hard threshold by a wide margin and no reaper action has occurred, the hook pages. Nothing in the design prevents a botched handoff elaborately; everything makes a botched handoff a five-minute glitch.

## 2. The hard parts

Ranked by what I'd prototype first and what breaks at 2am:

1. **Kill/relaunch mechanics under the safety layer.** The stated fact is that *self*-kill is blocked; I'm assuming an external script's SIGTERM is not, and that `tmux respawn-pane -k` behaves. Experiment: launch a throwaway session, kill it externally, respawn in-pane, verify transcript integrity and no safety-layer interference — including whether a hook-descendant process counts as "self." Everything downstream depends on this.
2. **Same-id relaunch semantics.** Does launching with the predecessor's id append to or corrupt its transcript, or silently resurrect old context (which would recreate the rejected "resume" behavior)? Experiment: relaunch same id, inspect transcript files and first-turn context size. If dirty, switch to fresh-id-plus-task-file-copy.
3. **Hook injection actually reaching the model.** The design leans on the turn-boundary hook being able to put an instruction *in front of the session* — and on it firing for headless sessions. Experiment: canary hook, grep the transcript for the canary and the model's reaction.
4. **Context-fill arithmetic.** Which usage fields sum to "current context" (cache reads? cache creation?), and per-model window sizes. Wrong math fails silently in both directions: recycle storms or never-recycling. Experiment: track computed fill against the harness's own indicator across a full session.
5. **Note quality at 70% fill.** Does a heavy session write a usable note or boilerplate? At 2am nobody notices a bad note — the symptom is a successor that flails for ten turns, visible only in burned tokens. Test: forced handoffs mid-real-task, grade the successor's first five turns; also deliberately kill without a note to grade the fallback.
6. **Idle detection for interactive sessions.** Killing while the boss is mid-conversation or mid-keystroke is the one failure a human *will* notice and resent. Verifying "idle" from transcript timestamps alone may miss typed-but-unsent input. Experiment: probe what's observable about pending user input.
7. **The reaper not running.** Cron silently broken is the classic invisible failure; the hook-side cross-check alert is the mitigation, and it needs testing as deliberately as the happy path (disable cron, confirm the page arrives).

## 3. Late discoveries

Class-typical traps in session-recycling systems, cast wider than my sketch:

- **Permission and auth state doesn't survive.** The predecessor accumulated tool-permission grants interactively; the successor re-prompts — and a headless successor blocks *silently forever* on a permission dialog nobody sees. Fleet sessions need pre-approved permission settings on disk, discovered painfully otherwise.
- **Orphaned children.** Background processes the session started (dev servers, watchers, MCP servers, long builds) either die with the process group — successor doesn't know to restart them — or survive orphaned and hold ports/locks. The note template's "running background work" line is cheap now, expensive to retrofit.
- **Stale locks.** Kill lands while the session holds `git index.lock` or a package-manager lock; the successor's first command fails mysteriously. Turn-boundary-only killing helps but doesn't eliminate it; the successor's orientation text should mention stale-lock cleanup.
- **The successor asks a question as its first act** ("Should I continue where the predecessor left off?") and a headless session hangs on it indefinitely. The opening prompt must explicitly forbid asking.
- **External identity.** The predecessor claimed a GitHub issue, posted "working on it," or holds an address in an inter-agent messaging registry. Messages route to a dead session; the issue looks taken. Successors must reclaim identity, not just work.
- **Boilerplate-note decay.** Once notes are a ritual, they converge to template-satisfying mush with zero information. Without an occasional audit (or the successor rating the note it received), quality decays invisibly.
- **The wedged-but-light session.** Token fill isn't the only degradation: sessions get confused, loop, or stall well under threshold, and the boss ends up hand-recycling those — the "no human typing" goal quietly fails. A stall/error-rate trigger into the *same* recycle path is cheap at design time.
- **Disk fills.** Transcripts, notes, markers, and lineage accumulate; week six, the box runs out of disk at 2am. Rotation/GC is a one-liner now.
- **Version drift.** Transcript schema, usage-field semantics, and model window sizes all change under harness/model upgrades. Defensive parsing plus fail-safe-and-alert is the difference between "degraded" and "reaper kills everything."
- **Recycle economics.** Every handoff re-pays fixed orientation cost (CLAUDE.md, note, task file, repo re-reading). Threshold set too low turns the fleet into a machine for re-reading its own instructions. Measure orientation cost; set threshold so it amortizes.
- **Environment outside git and the note.** Activated virtualenvs, exported env vars, docker containers, `/tmp` state — the predecessor's implicit knowledge of them dies with it and nothing in the durable record mentions them.

## 4. Assumptions

Each of these the real design answered somehow; the answers may be load-bearing.

1. Interactive sessions live in tmux (or an equivalent addressable multiplexer) that a script can respawn panes in.
2. External processes may kill a session — the safety layer blocks only self-kill, and a hook-spawned descendant doesn't count as "self."
3. A launch wrapper is acceptable, i.e., it's fine to require that all fleet sessions be started through one recorded entry point (the single "remembered step," paid once at genesis).
4. A cron/systemd timer counts as "minimal standing infrastructure," not as the daemon the goals disfavor.
5. Relaunching under the predecessor's session id is safe (no transcript collision, no implicit context resurrection) — or, failing that, task files can be copied to a fresh id.
6. Turn-boundary hook output can inject text the model actually sees and acts on, and the hook fires for headless sessions too.
7. Transcript usage fields are sufficient to compute current context size, and the model→window mapping is small and maintainable.
8. The successor runs in the same working directory, and the working tree persisting through the kill is acceptable as the carrier of uncommitted work.
9. Headless sessions are long-runners worth recycling, not one-shot jobs that end naturally.
10. The harness's per-session task files genuinely reflect current work (kept current mechanically, not by agent diligence alone).
11. Tool-permission grants can be pre-configured on disk so successors don't re-prompt.
12. One box, one user account — the reaper and sessions share filesystem trust, and anyone who can touch the marker directory is allowed to trigger recycling.
13. The boss is reachable by push notification for the rare paged exception.
14. Fleet size is small (single digits to low tens), so a per-minute transcript scan is negligible load.
15. "Not dumber" is satisfiable by note + task file + transcript tail — i.e., no task in this fleet depends on long-range in-context memory that cannot be externalized (if one does, it needs an exemption flag, and none was mentioned).
