## Three kinds of checkout, one repository

1. **"All working copies on a machine are the same repository viewed at different branches, sharing one object store through git worktrees."** — On any one of the two machines, however many separate directories of project files exist, they are not independent clones. They are all views onto a single underlying repository, each one having a different branch checked out. They share a single `.git` object database — the store of commits, trees and blobs — because they are created as git *worktrees*, git's feature for attaching multiple working directories to one repository. So disk is not duplicated per directory, and a commit made in any of them is immediately present in the shared history.

2. **"**Git allows a branch to be checked out in only one worktree at a time**, which is the mechanism that keeps parallel agents from editing one branch's files: git refuses before they get the chance."** — A rule enforced by git itself: a given branch may be the checked-out branch of at most one worktree simultaneously. The document identifies this as the safeguard that prevents two agents running at the same time from both modifying the working files of a single branch. "Git refuses before they get the chance" = the protection is preventive rather than corrective — the attempt to create a second worktree on an already-checked-out branch fails with an error at that moment, so the situation where two agents are concurrently editing the same branch's files never comes into existence in the first place.

3. **"1. **The main checkout** — the machine's primary working copy, parked on `main`."** — Naming and defining the first of the three kinds. "The main checkout" is the coined name for the machine's principal repository directory. "Parked on `main`" = its checked-out branch is the trunk branch `main`, and it stays there — it is not switched to other branches.

4. **"This is what `git pull` updates, and what a session reads for the live `.claude/` machinery (hooks, settings)."** — Two roles for that directory. First, it is the directory that a `git pull` is normally aimed at, i.e. the thing you bring up to date when you want the machine to have the latest `main`. Second, when an agent session needs the currently-effective project configuration and automation — the contents of the `.claude/` directory, specifically hook scripts (programs the harness runs automatically around tool calls) and settings files — it reads them from this directory. "Live" = the versions actually in force, as opposed to copies sitting in some other worktree.

5. **"A stale main checkout means stale hooks, which is how the instruction-file guard's worktree bug outlived its fix by a day."** — Because hooks are read from the main checkout, if that checkout has not been pulled it holds old hook code, so the machine keeps executing the old behaviour. An instance is cited: there was a hook called the "instruction-file guard" (a guard that governs writes to instruction files, as I read the name) which had a defect involving worktrees; a fix for that defect was committed and merged, but because the main checkout was not updated, the defective behaviour continued to occur for a further day after the fix existed. "Outlived its fix by a day" = the bug kept manifesting for roughly 24 hours after it had already been repaired in the repository.

6. **"2. **Agent homes** — one permanent directory per named long-lived agent, each on that agent's own branch."** — The second kind. "Agent home" is the coined name for a directory that belongs to one specific, named agent that is intended to persist over time rather than being created for a single job. There is exactly one such directory per such agent, it is not deleted between uses ("permanent"), and each has a distinct branch checked out — the branch belonging to that agent.

7. **"Created by the launchers (as a plain directory) and made a checkout deliberately with `git worktree add` when the agent works on the repository."** — How an agent home comes into being, in two steps. Step one: the launcher scripts (the programs that start agents, named later in the document) create the directory, and at that point it is an ordinary empty/normal directory with no git relationship. Step two: only if and when that agent's work actually involves the nedschorus repository does someone explicitly run `git worktree add` to convert that location into a git worktree with a branch checked out. "Deliberately" signals this second step is a conscious, separate action rather than something that happens automatically.

8. **"3. **Task worktrees** — disposable, one per background job that edits files, each on its own branch, created by the harness when a session isolates itself and removed when the job ends."** — The third kind. "Task worktrees" are meant to be thrown away rather than kept. One is created for each background job that will modify files (jobs that only read do not get one, as I read it). Each such worktree has its own branch. They are created automatically by the Claude Code harness — not by a person or a launcher — at the moment a session opts into isolation, meaning it arranges to do its file edits in a separate directory and branch so as not to disturb others. When the job finishes, the worktree is deleted.

9. **"Their value leaves as pushed commits; the directory afterwards is litter."** — Everything worth keeping from a task worktree exits it in the form of git commits that have been pushed to the remote. Once that has happened, the directory itself holds nothing of further worth: "litter" = leftover debris that should be cleaned up, and by implication should not be treated as a place where anything valuable still resides.

## What crosses between machines, and what does not

1. **Section heading** — What follows sorts things into two categories: those that propagate from one machine to the other, and those that do not.

2. **"**Crosses:** git branches, once pushed, and through them every committed file."** — The only thing in the first category. Git branches move between the machines, but only after a push to the shared remote has made them available. "Through them every committed file" = anything that has been committed onto such a branch rides along with it, so file contents do cross — but only by virtue of being committed and pushed.

3. **"That is also the one real cross-machine collision surface — two clones pushing the same branch name fight over one remote ref, whatever the agents are called."** — Since branches are the only shared channel, they are also the only place where the two machines can genuinely interfere with each other. "Collision surface" = the area where conflicting simultaneous actions are possible. The specific conflict: if the Mac's clone and the box's clone each push a branch of the same name, both are writing to a single reference on the remote (one `refs/heads/<name>` on GitHub), so their pushes contend — one will overwrite or be rejected relative to the other. "Whatever the agents are called" = renaming or suffixing agents does not help here; the collision is about branch names on the remote, which is an entirely separate namespace from agent names.

4. **"**Does not cross:** worktrees and their directories, agent homes, handoff files, supervisor locks, tmux sessions, Claude credentials (each machine authenticates separately), and anything uncommitted."** — The second category, enumerated: git worktrees together with the directories holding them; the permanent per-agent home directories; the handoff markdown files; the exclusive locks held by the supervisor; the running tmux terminal sessions; the authentication credentials for Claude — with the parenthetical clarifying that each machine performs its own login and holds its own tokens, so being authenticated on one grants nothing on the other; and finally any file change that has not been committed to git, which by definition cannot travel because only committed-and-pushed material moves.

5. **"A pull on one machine tells the other nothing."** — Running `git pull` on one of the two computers has no effect whatsoever on the other computer's state, and conveys no information to it. Bringing one machine up to date leaves the other exactly as stale as it was.

6. **"**A consequence worth remembering:** pulling the main checkout does not update agent homes or task worktrees, because each sits on its own branch."** — A follow-on point the author flags as easy to forget, and note this one is about directories *within* a single machine, not about the two machines. Running a pull in the main checkout advances only the branch that checkout has out, namely `main`. It leaves the agent-home directories and the task worktrees untouched, for the stated reason that each of those has a different branch checked out, and pulling one branch does not alter another.

7. **"After a merge to `main`, the main checkout needs its own pull, and any long-lived agent branch needs `main` merged into it before that agent sees the change."** — The practical procedure that follows. Once a change has been merged into `main` on the remote: (a) the machine's main checkout will not reflect it until you explicitly run a pull there; and (b) for each persistent named agent working on its own branch, that agent's branch remains without the change until someone merges the updated `main` into that branch — only then does the agent, working in its own home directory, actually have the new material in its files.
