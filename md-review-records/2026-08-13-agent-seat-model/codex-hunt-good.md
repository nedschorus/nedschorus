1. “Ruled by the user 2026-08-14”; “Considered and declined 2026-08-14”; “Two cautions learned 2026-08-14”; “Its 2026-08-12 handoff was archived on 2026-08-14”; “verified 2026-08-14”. The checkout’s local date is 2026-08-13 in America/Los_Angeles, so these statements record rulings, observations, and completed actions on the following day. An agent may treat events that have not yet happened as settled evidence. Confidence: unsure — the records might use UTC, where it is already August 14, but the file never states a date convention.

2. “The test for whether two tasks belong to one seat is: does doing the first make the agent smarter about the second? If yes, same seat. If no, separate seats”. The test is order-dependent: A may inform B while B does not inform A. It is also non-transitive: A can inform B and B can inform C without A informing C, producing mutually impossible seat assignments. “Smarter” supplies no threshold or observable test. Finally, the “If no, separate seats” rule conflicts with `sidebar`, which deliberately collects unrelated off-topic tasks. These ambiguities can assign the same tasks differently depending on comparison order or interpretation. Confidence: sure.

3. “An agent with minimal, focused context is smarter than one carrying unrelated history.” This is an unrestricted comparative claim. An ordinary counterexample is an agent that successfully ignores irrelevant history and performs equally well; another is supposedly unrelated history that reveals a cross-cutting constraint. Taken as policy, the claim can cause useful context to be discarded merely because it was classified as unrelated. Confidence: sure.

4. “Idle agents are free. There is no cost to a seat nobody is using, so never merge two unrelated piles to keep a seat busy.” “Idle” can mean a defined but stopped seat or a running seat awaiting work; the file does not distinguish them. A running idle seat consumes one of the stated concurrency slots, while a stopped seat still carries a brief, namespace, branch, worktree, and handoff state that can become stale. The absolute “never” also conflicts with `sidebar`, whose purpose is to combine unrelated work, and with the later reuse model. Confidence: sure.

5. “The natural unit of work is a series of related tasks, then handoff-and-clear before the next series.” Neither the end of a “series” nor `handoff-and-clear` is defined. It is unclear whether “clear” means clearing conversation context, deleting a handoff, exiting the process, retiring the seat, or clearing its worktree. Because the sentence requires an action without identifying its target or completion condition, an agent cannot know when the series is finished or when it has complied. Confidence: sure.

6. “Seats are resumed weeks later”. This categorical statement conflicts with the later, weaker “can be resumed days or weeks later” and with the referenced `sidebar` brief, which says “Start clean” and “Do not write a handoff at the end of a conversation.” It can make an agent preserve continuity for a seat designed to be disposable. Confidence: sure.

7. “names must be recognisable in a session list without opening anything” conflicts with the introduced name “`ghi`”. The expansion appears only in the table description, which is unavailable in the session list; `ghi` is not self-documenting there. The dual-use names `gatekeeper` and `sanity-checker` also conflate a seat with the component or reviewer it owns. This is in tension with `CLAUDE.md`: “use explicit, clear and precise multi-part names” and, when ambiguous, “choose a more explicit name, with 3 or 4 parts, not 1 or 2.” Searches and session listings cannot reliably establish which entity a bare occurrence denotes. Confidence: sure.

8. “Seven seats are defined; two or three run at a time, five is the user’s maximum.” This supports incompatible readings: either the permitted running count is two or three, or four and five are also permitted because five is the maximum. No distinction such as normal count versus exceptional cap is supplied, so an agent cannot determine whether launching a fourth seat violates the model. Confidence: sure.

9. “A seat whose group is finished is simply exited; its name and handoff remain”. “Group is finished” has no completion criterion, particularly for open-ended queues and research. “Simply exited” also conflicts with the later retirement procedure, which requires archival and worktree/branch handling. The statement additionally conflicts with the referenced `sidebar` instruction, “Do not write a handoff at the end of a conversation”; a sidebar handoff therefore need not remain. Confidence: sure.

10. “A seat whose group is finished is simply exited; its name and handoff remain, so the thread can be resumed” and “the launcher will boot the next agent of that name” leave the identities of seat, thread, and agent unresolved. The seat appears both to be the exited entity and the persistent entity later occupied by a different agent. Later wording adds “stream” and “session” without defining their relationship. This matters when instructions say to exit, resume, or retire one of them: the literal target of the operation is unknown. Confidence: sure.

11. “`sanity-checker` | review quality: the sanity-checker reviewer and the md-review grid”. The same name denotes both the seat and one reviewer owned by the seat. A sentence or search result mentioning “sanity-checker” can therefore refer to the persistent work pile, a live agent, or the reviewer component. Confidence: sure.

12. “A coordinating seat has nothing to do while the user is the one choosing which two or three seats run”. “Nothing” is broader than the premise supports. Ordinary counterexamples within this document include detecting cross-seat dependencies, reconciling overlapping ownership, tracking the concurrency cap, and coordinating retirement or context transfer. A user choosing which seats run does not logically eliminate those activities. Confidence: sure.

13. “master agent”, “coordinating seat”, and “directing seat” are used in the same section without saying whether they are synonyms. A master can imply authority, a coordinator can imply routing, and a director can imply task assignment. The condition for revisiting the decision therefore does not identify which rejected mechanism would be reconsidered. Confidence: unsure — the author may intend ordinary-language synonyms, but their operational differences matter here.

14. “A seat is retired by exiting it” conflicts with “retiring a name has one required step: archive…” and “retire the stream first and archive second.” Exiting is variously described as the whole retirement operation, a precursor to retirement, and retirement of a differently named entity. An operator cannot tell whether a normal process exit retires the seat or merely suspends it. Confidence: sure.

15. “So retiring a name has one required step: archive `~/.claude/handoffs/<seat>-handoff.md`” conflicts with “freeing a name for reuse also means dealing with `~/agents/<seat>` and the branch it holds”. The latter identifies additional required work, so archival cannot be the one required step. Literal reliance on the first statement leaves the old worktree or branch occupying the reused name. Confidence: sure.

16. “its handoff file outlives it, and the launcher will boot the next agent of that name straight into it.” The referenced supervisor does not use an existing handoff as its initial prompt. It starts with `--first-prompt-file` when supplied, otherwise with “No handoff exists yet”; only after launching does it poll the handoff and compare its restart counter. Thus an existing handoff can be ignored, consumed only after an intervening launch, or rejected as already consumed. The promised direct resumption does not occur literally. Confidence: sure.

17. “rename it `<seat>-handoff-retired-<date>.md`”. The date format and behavior when that name already exists are unstated. More importantly, this name matches the referenced supervisor’s `<seat>-handoff-*.md` pruning glob. A later recycle can count retired archives among the two retained generations, delete older retired archives, or displace ordinary generation retention. The retirement store defines a reachable collision but neither states nor discards it. Confidence: sure.

18. “retiring a name has one required step: archive `~/.claude/handoffs/<seat>-handoff.md`”. The defined reuse procedure leaves the same seat’s supervisor state file intact. That state contains `consumed_counter` and `generation`; a reused seat whose new handoff counter begins below the old consumed counter will never trigger a recycle. Old dialog extracts, generation archives, and supervisor state also remain in the reused namespace. These are reachable consequences of the mechanism the file defines, not merely missing optional features. Confidence: sure.

19. “A launch that finds no handoff starts clean on the ordinary ignition prompt”. The referenced launcher/supervisor does not inspect handoff existence to choose its first prompt. The documented launch command always supplies `seat-first-prompt.md`, and a launch without that option uses the supervisor’s fixed no-handoff string even when a handoff exists. “ordinary ignition prompt” is also not defined or given a searchable path/name. Confidence: sure.

20. “A live stream keeps writing handoffs: archiving while its supervisor is still running only clears the file until the next recycle”. A live session does not necessarily write another handoff: it can stop without one, remain below the recycle threshold, or never recycle. The referenced supervisor explicitly exits when a session ends without a handoff. The absolute “keeps writing” can cause an operator to wait for an event that will not occur. Confidence: sure.

21. “retire the stream first and archive second.” No operation named “retire the stream” is defined, and “stream” is not mapped to the seat, agent process, tmux session, or supervisor. The file supplies neither an executable action nor an observable point at which this first step is complete. Confidence: sure.

22. “freeing a name for reuse also means dealing with `~/agents/<seat>` and the branch it holds, via `git worktree move` or `git worktree remove`”. The two commands do not have equivalent reuse effects. Moving a worktree leaves the seat branch checked out there, so the launcher cannot attach that branch to a new worktree of the same name. Removing a worktree leaves the branch itself intact, so a later launch resumes its old branch history rather than necessarily starting clean. The text neither distinguishes these outcomes nor accounts for dirty worktrees, unpushed commits, or branch retention. Confidence: sure.

23. “Its 2026-08-12 handoff was archived on 2026-08-14 so a future `choirmaster` starts fresh”. Archiving only the current handoff does not guarantee a fresh start: the old supervisor state, generated dialog/handoff archives, worktree, and branch remain relevant under the documented mechanisms. The stated result therefore does not follow from the stated action. Confidence: sure.

24. “When a new task arrives, put it in the seat whose existing context makes it cheapest”. “Put it in the seat” does not identify an operation: it could mean launch or attach to the seat, add the task to a brief, copy a handoff, create an issue, or merely tell the user. No durable store or completion signal is named. An agent responsible for “filing” cannot determine what artifact, if any, constitutes completion. Confidence: unsure — this may be intended as informal routing advice, but the section title presents it as a procedure.

25. “If it fits none of them, it either belongs in `sidebar` … or it is the seed of a seventh pile”. Seven seats, each with a pile in the table, have already been defined. A new pile would ordinarily be the eighth, unless `sidebar` is silently excluded from the pile count. The phrase supports both counting schemes. Confidence: sure.

26. “it either belongs in `sidebar` (a question, answered and forgotten) or it is the seed of a seventh pile”. The alternatives overlap: a question can expose a durable new topic and seed a pile. “Answered and forgotten” also conflicts with the later rule that decisions are recorded and with the referenced sidebar brief, which requires knowledge needed by a topic seat to be written where that seat will find it. The routing outcome changes depending on which sentence controls. Confidence: sure.

27. “One generic file serves every seat: the agent learns its own name from its working directory, so nothing needs substituting.” The immediately preceding command contains the required `<seat>` substitution. Read literally, leaving it unchanged causes the shell to interpret angle brackets as redirection rather than launch a seat. The sentence likely refers only to the contents of the prompt file, but it does not limit “nothing” that way. Confidence: sure.

28. “`--first-prompt-file` seeds only the first session; after the first recycle the seat’s own handoff takes over.” “First session” can mean the first session in the seat’s lifetime or the first session of each supervisor invocation; the actual supervisor implements the latter. After a stopped supervisor is relaunched, the first-prompt file is used again. After a recycle, the successor receives a dialog extract plus selected handoff fields, not the handoff itself; arbitrary handoff prose is ignored. This wording misstates both the lifetime boundary and the context source. Confidence: sure.

29. “each seat lives in `~/agents/<seat>` on the box”. The referenced launcher supports `NEDSCHORUS_AGENTS_ROOT`, which places a seat elsewhere, while the referenced first prompt recognizes only `/home/nedlern/agents/<name>`. The absolute path claim therefore fails for an explicitly supported launcher configuration and can prevent the agent from identifying its seat. Confidence: sure.

30. “on its own branch — which is what keeps two seats from touching the same files or racing each other’s pushes.” Separate branches do not prevent two seats from modifying the same repository-relative file and later producing a conflict. They also do not prevent races involving a reused branch name or pushes outside the stated convention. The physical worktree separation, not merely branch ownership, is doing part of the claimed work. Confidence: sure.

31. “The launcher creates that home as an empty directory, not a checkout; the first-prompt file has the agent make it one on its first run”. This directly contradicts both explicit references. `seat-first-prompt.md` says, “The launcher makes your home a checkout … before your session starts,” and instructs the agent to stop if it is not one. `launch-claude-ubuntu` creates the worktree before starting tmux because settings cannot be retrofitted after session start. Following the model literally boots the agent without required hooks and then tells it to perform a repair its prompt explicitly says is too late. Confidence: sure.

32. “Context on arrival: the supervisor reads `~/.claude/handoffs/<seat>-handoff.md` if one exists.” Under this heading, the sentence implies that the existing handoff becomes arrival context. The referenced supervisor first launches the session, then polls the file, and only acts when its counter exceeds stored state. An existing, already-consumed, malformed, or low-counter handoff provides no arrival context. Confidence: sure.

33. “copy that thread’s handoff to `~/.claude/handoffs/<seat>-handoff.md` before launching.” The copy can overwrite an existing destination without any stated treatment of that context. It also retains the source restart counter while the destination’s supervisor keeps its own consumed counter; if the copied counter is not greater, it is ignored. If it is greater, only recognized fields such as `next-step` influence the successor, not the source handoff’s full context. Thus the documented seeding procedure has reachable overwrite and non-seeding cases that are neither stated nor discarded. Confidence: sure.

34. “A forked session’s handoff describes where it ended, not where it forked.” The handoff format does not enforce this claim; it contains agent-authored fields, and an agent can describe the fork point, both points, or neither. An ordinary counterexample is a handoff written immediately after the fork, when the fork and end are the same. Treating the statement as guaranteed can send a successor to the wrong historical boundary. Confidence: sure.

35. “point the new seat at the `-dialog-` extract or the raw transcript instead”. `-dialog-` is only a filename fragment, not a defined artifact or path. The raw transcript’s location and session identifier are absent, as is the operation denoted by “point”: passing a file as the first prompt, mentioning it in a prompt, or copying it produce different behavior. A zero-context agent cannot locate the promised input or know how it is to be consumed. Confidence: sure.

36. “and say which part of the history matters.” No actor, communication channel, selection notation, or stopping boundary is identified. For a large transcript, “which part” might mean timestamps, turns, line ranges, topics, or a fork boundary; these are not interchangeable. The instruction requires judgment but supplies no executable way to attach that judgment to the transcript seeding operation. Confidence: sure.

37. “Nothing durable lives in a session.” This conflicts with the same file’s reliance on resumable threads, surviving handoffs, dialog extracts, and raw transcripts. An ordinary counterexample is a transcript retained on disk and later used as the source of continuation. If “durable” instead means only committed project artifacts, that narrower definition is not stated. Confidence: sure.

38. “decisions are recorded in the governing documents and issues.” “Governing documents” is an unexplained class with no membership rule or path. The file references several kinds of briefs and prompts but does not identify which are governing. A zero-context agent cannot determine the destination for a decision or verify that recording is complete. Confidence: sure.

39. “A seat can be exited at any time without loss once its work is pushed.” A pushed branch does not preserve unrecorded decisions, next-step context, running external work, machine-local state, or the supervisor counters required by this model. The file itself depends on a handoff for later resumption, so pushing work alone cannot establish “without loss.” Confidence: sure.
