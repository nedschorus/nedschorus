## ## The grouping rule

1. This is a bolded rule/heading stating the principle that tasks should be organized into groups according to whether they share context with one another, rather than being organized according to considerations of workload (e.g., balancing how much work each grouping/agent has to do).
2. The way to determine whether two given tasks should belong to the same "seat" (the same named agent grouping) is to ask: if the agent performs the first task, does that make the agent more knowledgeable, capable, or better-informed ("smarter") with respect to performing the second task?
3. If the answer to that test is yes, the two tasks should be assigned to the same seat; if the answer is no, they should be assigned to separate seats, and this separation should be maintained even in cases where doing so results in one of the seats having no active work to do (being idle).
4. The following bullet points explain the underlying reasoning held by the user, and this document exists in order to serve or implement that reasoning.
5. An agent that is given a minimal amount of context, focused specifically on the task at hand, performs more capably ("is smarter") than an agent that carries context or history from unrelated matters; the state of having irrelevant, conflicting, or excessive context ("confusion") is what carries a real cost, in contrast to an agent sitting unused, which does not carry a real cost.
6. A bolded assertion that agent seats which are not currently being used to perform any task do not incur any cost or penalty for being unused.
7. Because there is no cost to an idle seat, one should never combine two piles of work that are unrelated to each other merely for the purpose of ensuring that a given seat has something to do (keeping it occupied/"busy").
8. The natural or fundamental unit by which work should be organized is a sequence ("series") of tasks that are related to one another, followed by a transfer of context to a successor ("handoff") and a clearing of the current context, before the seat begins the next such series of related tasks.
9. Because agent seats may be revisited or resumed only after a gap of multiple weeks, it is a requirement that the names given to seats be identifiable/understandable ("recognisable") to a human simply by looking at a list of sessions, without that person needing to open or inspect any individual session to figure out what it is or was about.

2. A seat whose purpose is to coordinate other seats would have nothing productive to do, given that it is the user — not any coordinating agent — who is responsible for deciding which two or three seats are active at any given time.
3. 4. This decision (not to have a master/coordinating agent) should be reconsidered ("revisit") if a situation arises in the future where seats need to transfer work directly to one another without the user being involved in making that decision ("in the loop").

## ## Retiring a seat, and reusing its name

1. The process of retiring (deactivating/ending) a seat is accomplished by exiting it — however, the handoff file associated with that seat (which records context for continuation) continues to exist even after the seat itself is retired, and the launcher program will, if invoked again with that same seat name, start ("boot") a new agent directly into the context contained in that pre-existing handoff file, rather than starting fresh.
2. Therefore, if one wants to retire a seat's name so that name becomes available to be reused for a different, unrelated purpose, there is one mandatory action required: the existing handoff file, located at the path `~/.claude/handoffs/<seat>-handoff.md`, must be archived by renaming it to include the word "retired" and the date, following the pattern `<seat>-handoff-retired-<date>.md` — and this file must not be deleted, because these handoff files exist only on the local machine ("machine-local") and are not tracked in the git version control repository.
3. When a launch (start-up) of a seat occurs and no handoff file is found for that seat's name, the agent begins with no prior context ("starts clean"), following the standard/default startup prompt used for a new agent ("the ordinary ignition prompt") — and this clean start is the intended/desired behavior when a seat name is being reused for a new, different purpose.
4. There are two warnings or lessons that were learned by the user on 2026-08-14, introduced by this sentence.
5. The first warning, stated in bold, is that a "live stream" (an actively running agent session) continues to write/update its handoff file as it operates; therefore, if one archives (renames) the handoff file while the supervising process for that seat is still running, the archiving action will only be effective temporarily — until the next time the session's context gets cycled/refreshed ("recycle"), at which point a new handoff file will be written to the original location again. Because of this, the correct order of operations is to first stop/retire the running session (the stream), and only afterward archive its handoff file.
6. The second warning, also stated partly in bold, is that the working directory used by an agent seat (referred to as "the agent home") is actually a git worktree — a git mechanism that allows multiple working directories to be checked out from the same repository — and it is checked out on that particular seat's dedicated git branch; consequently, freeing up a seat's name so it can be reused also requires properly handling the directory at path `~/agents/<seat>` and the git branch it is checked out on, using the git commands `git worktree move` or `git worktream remove` (i.e., proper git worktree management commands), rather than simply deleting the directory with a generic file-removal command (`rm`).
7. The seat named `choirmaster` is offered as a real, currently-relevant example ("the live example") of this retirement-and-reuse process: the original, founding seat's body of work is currently in the process of being redistributed/reallocated out into the various topic-specific seats that were listed earlier in this document, and the user intends, at some point in the future, to reuse the name `choirmaster` again — but for a new purpose, that of a coordinating agent.

## ## Filing new work

1. When a task that has not been previously accounted for arrives, it should be assigned to whichever existing seat already has context that makes handling that task least costly/most efficient — and this determination should not be made by simply choosing whichever seat currently has the least work assigned to it (the "emptiest" seat).
2. If a new task does not fit into the scope of any of the existing seats, then one of two things should happen: either it belongs in the `sidebar` seat, described as a place for a single question that gets answered and is then not retained further ("forgotten"), or else it represents the beginning ("the seed") of a need for an eighth category of work requiring a new, seventh named seat to be defined — and the choice to create such a new seat is not something that should be decided automatically/by default, but rather is a decision that must be made by the user.
