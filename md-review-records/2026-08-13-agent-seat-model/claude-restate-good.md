## The grouping rule

1. **"Group tasks by shared context, not by workload."** — When deciding which tasks to assign to the same seat, the criterion is whether the tasks draw on the same background knowledge/state; the criterion is expressly *not* balancing how much work each seat has (i.e. do not load-balance).
2. **"The test for whether two tasks belong to one seat is: *does doing the first make the agent smarter about the second?*"** — The operational decision procedure is a single question about knowledge transfer: would having performed task A leave the agent better informed, and therefore better performing, when it comes to task B? "Smarter" here means better-informed for that specific second task, not generally more capable.
3. **"If yes, same seat."** — If the answer to that question is yes, both tasks are assigned to one and the same seat.
4. **"If no, separate seats — even when that leaves a seat idle."** — If the answer is no, the two tasks go to different seats, and this holds even in the case where the consequence is that one seat has nothing to do at all; idleness is not a reason to override the rule.
5. **"The user's reasoning, which this model exists to serve:"** — What follows is the user's own justification, and the document asserts that the whole seat model is in place precisely to carry out these stated aims — i.e. the reasons are the authority, and the rules are downstream of them.
6. **"An agent with minimal, focused context is smarter than one carrying unrelated history."** — An agent whose loaded context is small and confined to the topic at hand performs better than an agent whose context also contains material from unrelated earlier work; "history" means accumulated prior conversation/work in that session.
7. **"Confusion is the expensive failure, not idleness."** — Between the two failure modes — an agent that gets muddled because of mixed-together context, and an agent sitting unused — the one that actually costs something (in wasted effort, wrong output, rework) is the muddled agent; an unused agent is not counted as a real cost.
8. **"Idle agents are free."** — A seat that is doing nothing incurs no cost worth accounting for. I take "free" to mean cost-free in the user's accounting (attention, money, or both), stated as an absolute rather than as an approximation.
9. **"There is no cost to a seat nobody is using, so never merge two unrelated piles to keep a seat busy."** — Restating and drawing the consequence: since an unused seat costs nothing, one must not combine two unrelated bodies of work ("piles" = the accumulated set of tasks on a topic) into a single seat merely for the sake of giving that seat occupation. "Never" is used here as a strict prohibition.
10. **"The natural unit of work is a *series of related tasks*, then handoff-and-clear before the next series."** — The intended rhythm of work: a seat works through a run of mutually-related tasks; when that run is complete, the agent writes a handoff (a record for its successor) and the context is wiped, and only then does a new run of related tasks begin. "Handoff-and-clear" is a coined compound naming that two-step transition.
11. **"Seats are resumed weeks later, so **names must be recognisable in a session list** without opening anything."** — Because a seat may be picked up again after a long gap (weeks), the requirement follows that the seat's name alone, as it appears in a listing of sessions (e.g. a tmux or session-manager list), must be enough for the user to identify what that seat is about — without having to open the session, its handoff, or any file to find out.

## How many seats exist, and how many run

1. **"Seven seats are defined; **two or three run at a time**, five is the user's maximum."** — Three separate quantities: the total roster of named seats in this scheme is seven; in ordinary practice only two or three of them have live sessions simultaneously; and five simultaneous live seats is the ceiling the user has set — an upper bound not to be exceeded, not a target.
2. **"A seat whose group is finished is simply exited; its name and handoff remain, so the thread can be resumed days or weeks later when that topic comes back."** — When the body of related tasks ("group") belonging to a seat is completed, the action taken is just to end that session — no deletion, teardown, or ceremony. The seat's name stays part of the roster and its handoff file stays on disk, and because both persist, the continuous line of work on that topic ("thread") can be taken up again after a gap of days or weeks whenever that topic becomes relevant again.

## Why there is no master agent

1. **"Considered and declined 2026-08-14."** — The option of having a master/coordinating agent was actually evaluated and then rejected, on 2026-08-14 — i.e. this is a recorded negative decision, not an oversight.
2. **"A coordinating seat has nothing to do while the user is the one choosing which two or three seats run: today's evidence is that `choirmaster`, created as a directing seat, drifted into being an ordinary topic thread."** — The reason for the rejection: as long as the human user personally decides which seats are active, a seat whose job is coordination has no remaining function, because the coordinating decision has already been made by a person. The supporting observation, from the day the decision was made ("today" = 2026-08-14): the seat named `choirmaster` had been set up to direct other seats, and in practice it gradually stopped doing that and became just another seat working on a topic of its own — "drifted" implying this happened without anyone deciding it.
3. **"Revisit if seats ever need to hand work to each other without the user in the loop."** — The decision is conditional, not permanent: if a situation arises where seats must pass tasks between themselves with no human involved in the transfer, this rejection should be reconsidered at that point.

## Retiring a seat, and reusing its name

1. **"A seat is retired by exiting it — but its **handoff file outlives it**, and the launcher will boot the next agent of that name straight into it."** — The act of retiring a seat is just ending its session. However, the handoff file persists on disk after the session is gone, and as a consequence the launcher script, when next started with that same seat name, will start the new agent by loading that leftover handoff — so the new agent resumes the old work instead of starting fresh. "Boot ... straight into it" = launch it directly with that handoff as its starting context, with no intervening step.
2. **"So retiring a name has one required step: archive `~/.claude/handoffs/<seat>-handoff.md` (rename it `<seat>-handoff-retired-<date>.md`, do not delete — these files are machine-local and not in git)."** — Because of the previous sentence, freeing up a seat *name* obliges exactly one action: move the handoff file out of the way, by renaming it to a form that includes the word `retired` and the date. The instruction explicitly forbids deleting it, and gives the reason: these handoff files exist only on that one machine and are not tracked in version control, so a deletion would be unrecoverable.
3. **"A launch that finds no handoff starts clean on the ordinary ignition prompt, which is what a reused name should do."** — When the launcher looks for a handoff and finds none, it instead starts the agent with no prior context, using the standard opening prompt ("ignition prompt" = the default first prompt that starts a session from nothing); and that clean start is exactly the desired behaviour when a name is being put to a new use.
4. **"Two cautions learned 2026-08-14."** — Two warnings follow; "learned" indicates they were discovered empirically on 2026-08-14, presumably by encountering the problems.
5. **"A live stream keeps writing handoffs: archiving while its supervisor is still running only clears the file until the next recycle, so retire the stream first and archive second."** — "Stream" here means the ongoing succession of sessions that make up one seat's continuous life, and "supervisor" means the still-running process that manages that seat and writes its handoffs. The caution: while that process is alive it will write the handoff file again, so if you archive the file first, the file is only absent temporarily — it reappears at the next "recycle" (the automatic restart of the session when its context fills up). Therefore the order matters: end the running stream first, and only then archive the file.
6. **"And **the agent home is a git worktree on the seat's branch** — freeing a name for reuse also means dealing with `~/agents/<seat>` and the branch it holds, via `git worktree move` or `git worktree remove`, not `rm`."** — The second caution: the directory a seat works in is a git worktree, checked out on that seat's own branch. So making a name available for reuse involves more than the handoff file: the directory `~/agents/<seat>` and the branch checked out there must also be handled. And the handling must go through git's own worktree commands — `git worktree move` (relocate it) or `git worktree remove` (delete it properly) — rather than removing the directory with a plain filesystem `rm`, which would leave git's records inconsistent. ("Dealing with" is left unspecific as to which of move or remove is right in a given case.)
7. **"`choirmaster` is the live example: the founding seat's work is being redistributed into the topic seats above, and the user intends to reuse the name later for a coordinating agent."** — `choirmaster` is the concrete case currently in progress illustrating all of the above. It was the first seat to exist ("founding seat"), and its accumulated body of work is at this moment being parcelled out among the seven topic seats listed in the table earlier. Meanwhile the user plans to bring the name `choirmaster` back at some future point, for a coordinating agent of the kind the previous section declined to create now.
8. **"Its 2026-08-12 handoff was archived on 2026-08-14 so a future `choirmaster` starts fresh rather than resuming a stream that no longer exists."** — The handoff file `choirmaster` had written, dated 2026-08-12, was renamed/archived on 2026-08-14 — i.e. the required step from sentence 2 was actually carried out. The purpose: any later agent launched under the name `choirmaster` will begin with no context, instead of picking up a continuous line of work that has already been dissolved and redistributed.

## Filing new work

1. **"When a new task arrives, put it in the seat whose existing context makes it cheapest — not the emptiest seat."** — On receiving a new task, assign it to whichever seat already holds the background knowledge that makes that task least costly to do (cheapest in effort/tokens/ramp-up time), and expressly do not assign it to whichever seat currently has the least work on it — a restatement of the grouping rule applied to intake.
2. **"If it fits none of them, it either belongs in `sidebar` (a question, answered and forgotten) or it is the seed of a seventh pile, which is a decision for the user rather than a default."** — If the new task matches no existing seat's context, there are exactly two dispositions. Either it is a one-off question, which goes to `sidebar` and is answered and then deliberately not retained ("forgotten" = no ongoing thread is kept for it); or it is the first item of a genuinely new body of work, which would mean creating a new seat — and creating that new seat is something the user must decide, not something an agent may do automatically. On "a seventh pile": read literally this counts a new pile as the seventh, whereas the seat table lists seven seats already; I cannot tell from the text alone whether this means "an additional pile beyond the existing ones" (the numbering simply not having been updated) or whether the count of topic piles is intended to be six with `sidebar` excluded, making a new topic pile the seventh — I take the intended force to be "a further pile beyond those listed" under either reading.

## Mechanics every seat shares

1. **"Launch, from the Mac, in one line — the first-prompt file tells a zero-context agent everything, including how to find out which seat it is:"** — First shared mechanic: starting a seat. The command is issued from the user's Mac (not typed at the Ubuntu machine), and it is a single command line. The reason a single line suffices is that the referenced first-prompt file supplies a brand-new agent, which knows nothing at all, with all the information it needs — including instructions for determining its own seat identity, which it does not otherwise know. The command follows in the code block.
2. **The code block** — `~/Projects/nedschorus/scripts/launch-claude-ubuntu <seat> --first-prompt-file /home/nedlern/Projects/nedschorus/docs/agents/seat-first-prompt.md` — This is the literal invocation: run the launcher script `launch-claude-ubuntu`, giving the seat's name as its first argument (substituting the actual name for `<seat>`), and passing the option `--first-prompt-file` with the absolute path of the shared first-prompt document. The backslash is just a line continuation, so this is one command despite spanning two lines.
3. **"The path is a **box-side** path, since the supervisor reads the file on the box."** — The file path written in that command is to be interpreted as a location on the Ubuntu box's filesystem, not on the Mac — even though the command is typed on the Mac — because the process that actually opens and reads the file (the supervisor managing the session) runs on the box.
4. **"One generic file serves every seat: the agent learns its own name from its working directory, so nothing needs substituting."** — The same single first-prompt file is used unchanged for all seats; no per-seat variants and no templating are needed, because the agent determines which seat it is by inspecting the path of the directory it is running in (which is `~/agents/<seat>`).
5. **"`--first-prompt-file` seeds only the first session; after the first recycle the seat's own handoff takes over."** — That option supplies the starting context for the initial session only. Once the session has been recycled (restarted) for the first time, the starting context thereafter comes from the handoff that the seat itself has written, and the first-prompt file plays no further part.
6. **"Launching is attach-or-create — running the same name again attaches to the live agent rather than starting a second one."** — The launcher's behaviour is idempotent in this respect: if a session for that seat name is already running, invoking the launcher connects you to that existing session; if none is running, it creates one. So repeating the command cannot produce two concurrent agents sharing one seat name.
7. **"Home and branch: each seat lives in `~/agents/<seat>` on the box, on its own branch — which is what keeps two seats from touching the same files or racing each other's pushes."** — Second shared mechanic. Every seat has a fixed working directory on the Ubuntu box at `~/agents/` plus its name, and each of those directories is checked out on a branch belonging to that seat alone. This arrangement is the actual mechanism that prevents two seats from editing the same working-copy files and from pushing to the same branch simultaneously in a way where one push overwrites or conflicts with the other ("racing" = concurrent conflicting pushes).
8. **"The launcher creates that home as an **empty directory, not a checkout**; the first-prompt file has the agent make it one on its first run (`git worktree add` into an empty existing directory works, verified 2026-08-14)."** — What the launcher itself produces is merely an empty directory — it does not clone or check out a repository into it. Turning that empty directory into a git worktree ("make it one" = make it a checkout) is instead an instruction contained in the first-prompt file, carried out by the agent itself during its very first session. The parenthesis records a tested fact: running `git worktree add` targeting a directory that already exists and is empty succeeds rather than erroring, and this was confirmed by trial on 2026-08-14.
9. **"Context on arrival: the supervisor reads `~/.claude/handoffs/<seat>-handoff.md` if one exists."** — Third shared mechanic, concerning what an agent knows when it starts. The managing process looks for a handoff file at that path, named after the seat, and if such a file is present it reads it and thereby supplies the new agent's starting context; if absent, it does not.
10. **"To seed a seat from another thread's context, pass `--first-prompt-file <path>` to the launcher, or copy that thread's handoff to `~/.claude/handoffs/<seat>-handoff.md` before launching."** — If you want a seat to begin already knowing what some *other* line of work knew, there are two alternative methods: either launch it with `--first-prompt-file` pointing at a file containing that context, or place a copy of the other thread's handoff file at this seat's expected handoff path first, so that the mechanism in the previous sentence picks it up at launch.
11. **"A forked session's handoff describes where it ended, not where it forked."** — Fourth shared mechanic, stated as a warning about a specific failure. When a session has been forked (branched off from an earlier point in another session's history), the handoff that session writes reports its state at the moment it finished, which is not the same as its state at the point where the fork was taken — so using such a handoff will convey the later end-state, not the earlier branch point.
12. **"When the fork point is the subject, point the new seat at the `-dialog-` extract or the raw transcript instead, and say which part of the history matters."** — Consequently, in cases where what you actually care about is the situation at the fork point, do not use the handoff; instead direct the newly launched seat to one of two other sources — a file whose name contains `-dialog-` (an extracted record of the conversation) or the unprocessed session transcript — and additionally state explicitly which portion of that history is the relevant one, since these sources are long and undifferentiated.
13. **"Nothing durable lives in a session."** — Fifth shared mechanic, as a principle: no information of lasting value is to be held only inside a running session; a session is not a storage location.
14. **"Work is committed and pushed; decisions are recorded in the governing documents and issues."** — The two places durable things do live: code and file changes go into git commits that are pushed to the remote, and decisions that have been made go into the project's authoritative documents (such as this one) and into its tracked issues.
15. **"A seat can be exited at any time without loss once its work is pushed."** — Given the preceding, ending a seat's session carries no risk of losing anything — with the stated precondition that its work has already been pushed; the timing is otherwise unconstrained ("at any time").
