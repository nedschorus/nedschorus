## Frontmatter — `description`

1. This skill is meant to be loaded and followed *before* you perform any action that modifies a GitHub issue belonging to this project (the nedschorus repository) — where "modifies" covers four named cases: creating a brand-new issue, changing the text of an existing issue's body, adding a comment to an issue, and taking material that currently sits in one of the project's holding areas ("queue material") and turning it into issue content. "BEFORE" is capitalized to mean the skill must be consulted first, not after the write is drafted or performed.

2. There is a second, broader trigger: any time you are producing a new project artifact, or rewriting an existing one, and it is *possible* that the right place for that content is a GitHub issue, you must also load this skill — even though you have not yet decided to write to an issue. The stated reason is that deciding *where* a piece of content belongs ("routing") is itself one of the things this skill governs, so you cannot correctly decide "this doesn't belong in an issue" without first consulting the skill.

3. The skill does not apply when you are only consulting an issue — reading its contents, or mentioning/linking to it from somewhere else. Those are read-only acts and need no skill invocation.

## When Used

1. This restates the trigger conditions as a single list: invoke the skill before creating a new issue, before changing an existing issue's body text, before posting a comment on an issue, and before writing any project content whose eventual location — a GitHub issue, one of the queue directories, or a standalone Markdown file — has not yet been settled. I read "whose home ... is not yet decided" as meaning the destination is genuinely undetermined at the moment you start writing, not that it is merely unstated.

## What to do

1. **"Ask before filing."** Before you create an issue, you are required to perform a query step first; the querying is a precondition of the write, not an optional research step.

2. **"Put the subject to ghi-info by running `scripts/ghi-info-ask.py` with the question (add `--include-closed` when asking about precedent or absence); read the issues it returns and the pair documents they cite."** Take the topic you are about to write about, phrase it as a question, and pass that question to a component called "ghi-info" by executing the script `scripts/ghi-info-ask.py`. The `--include-closed` flag widens the search to include issues that have already been closed, and you should add it in two situations: when you want to know whether the project has previously ruled on or handled something similar ("precedent"), and when you want to establish that nothing on the subject exists at all ("absence") — both cases need closed issues in scope, because otherwise a closed issue would be invisible and you'd wrongly conclude nothing exists. Having received a list of issues back, you must actually read them, and you must also read the "pair documents" — the companion Markdown files — that those issues link to.

3. **"When an existing artifact covers the subject, edit that artifact — a revision of the existing issue is the default disposition, the same way md-write defaults to REVISE."** If your ask turns up something that already addresses your topic, the presumed correct action is to change that existing thing rather than create a new one. "Default disposition" means: revising is what happens unless you have a positive reason to do otherwise; it is the fallback outcome, not merely one option among equals. The comparison to "md-write defaults to REVISE" is an appeal to a sibling skill (for Markdown writing) that has the same built-in bias toward amending existing documents, invoking a consistency across the project's skills. I take "artifact" here to cover both issues and pair documents, though the second half of the sentence names only the issue case.

4. **"A failed ask never blocks the write: fall back to grepping the local mirror, then `gh` search, and proceed under these rules."** If the ask step does not work — the script is missing, errors out, or returns nothing usable — that failure must not stop you from doing the write you came to do. Instead you degrade to substitute methods in a stated order: first text-search a locally stored copy of the issue data ("the local mirror"), then use the GitHub CLI's search. Having done whatever substitute worked, you then continue on through the rest of the skill's rules as normal. "Never blocks" is a strong statement that the ask is a best-effort input, not a gate.

5. **"Route by state."** The heading rule for deciding where content goes: the deciding factor is whether the content has unresolved/pending status attached to it, rather than, say, its topic, size, or format.

6. **"Every artifact is either final at its home or in a named queue with a drain:"** A claim that the project admits only two conditions for any piece of written material — either it is finished and sitting in its permanent location, or it is parked in a queue that has an explicit identity and an explicit process for eventually emptying it ("a drain" = a defined procedure for taking things out of the queue and dispositioning them). The implied prohibition is that nothing may sit in an unnamed, un-drained limbo. The colon introduces the sub-bullets that follow as the elaboration.

7. **"Material whose disposition is not yet decided goes to its destination queue — `docs/wiki/queue/` for wiki-bound doctrine, `docs/issues/queue/` for pair-bound MDs, the `draft` label for queued issues — with no GHI."** Content whose fate you have not settled is placed in whichever queue matches the kind of thing it will eventually become: `docs/wiki/queue/` if it is general standing guidance headed for the wiki ("doctrine" = settled rules/principles of the project), `docs/issues/queue/` if it is a Markdown file that will eventually be paired with an issue, and — for something that will become an issue itself — the mechanism is applying the label `draft` rather than a directory. "With no GHI" means no GitHub issue is created for queued material. I note a tension I am not resolving: the third listed queue *is* a labeled GitHub issue, so "with no GHI" cannot literally apply to it. The two readings I can see are (a) "with no GHI" attaches only to the first two, directory-based queues, and the `draft` label is an exception where the issue itself serves as the queue slot; or (b) "GHI" here means a *real, non-draft* issue, so a `draft`-labeled issue is deemed not to count as one. I cannot tell which is intended.

8. **"Anything carrying pending state — a wanted feature or component, an open question, a commitment to act — gets a GHI: issue-only when the body stays under 500 words, an MD-GHI pair when substantial working material rides with it."** If a piece of content has something unfinished attached to it, it must get a GitHub issue. Three examples define "pending state": a feature or component someone wants built but which doesn't exist yet; a question that has been raised but not answered; and a promise or obligation to perform some action. The form the issue takes depends on volume: if everything fits in fewer than 500 words, a standalone issue with no companion file is enough; if there is a large body of supporting working material that needs to travel with it, you use the two-part arrangement of a Markdown file plus an issue (the "MD-GHI pair"). "Rides with it" = accompanies it as attached content rather than being separate work.

9. **"The body carries the summary, the pair MD the substance; the pair sequence is write the MD, land it, then cite it from the issue."** In the paired arrangement, the division of labor is: the issue's body text holds a condensed account, while the companion Markdown file holds the full detail. The ordering of operations is fixed at three steps: first author the Markdown file, second "land it" — which I read as commit and merge it to the main branch so it exists at a stable location — and only third create or update the issue so that it references that now-existing file. The point of the order is that the issue's citation should never point at a file that isn't there yet.

10. **"Final reference content awaiting nothing is a bare MD at its home."** Material that is complete, has no unresolved question or pending action attached, and exists to be consulted later gets no issue at all — it is simply a Markdown file stored in whatever directory is its proper permanent location. "Bare" = unaccompanied by an issue.

11. **"The discriminator: the GHI carries state, the MD carries substance, the queue holds the not-yet-decided."** A one-line statement of the test that separates the three destinations: use a GitHub issue when the thing to be recorded is a status that can change (open/pending/resolved); use a Markdown file when the thing to be recorded is content/detail; use a queue when what you have is neither yet, because the decision about which it is hasn't been made.

12. **"When the routing is genuinely ambiguous, file a `draft`-labeled issue and move on; ambiguity never blocks the write."** If, after applying the discriminator, you truly cannot tell which destination is right — "genuinely" signals this is for real uncertainty, not for skipping the analysis — then the prescribed escape hatch is to create an issue carrying the `draft` label and continue with your work rather than stalling. The second clause restates as a general principle that uncertainty about placement is never a valid reason to leave the content unwritten.

13. **"Revise by editing the body."** The heading rule for changing existing issues: the mechanism of revision is modifying the issue's body text in place.

14. **"A clarification, correction, or scope change edits the issue body, including fixes to references already in it."** Three kinds of change — making existing wording clearer, fixing something that was wrong, and altering what the issue covers — are all handled by rewriting the body. The "including" clause forecloses a likely exception: even if all you are doing is repairing a broken or wrong link/path that the body already contains, that too is a body edit, not a comment.

15. **"A comment is only for a genuinely new event — an instance outcome, or a challenge to a ruling."** Comments are restricted to a closed list of exactly two occasions, both of which are events that happened after the issue was written rather than improvements to what it says: (a) an "instance outcome" — the result of one particular occurrence of whatever the issue tracks; and (b) "a challenge to a ruling" — someone disputing a decision the issue records. "Genuinely new" excludes restating, elaborating, or amending existing content.

16. **"Completion is not a comment: record the outcome in the body, then close the issue with its reason."** Finishing the work an issue tracks is explicitly *not* one of the two comment-worthy events, notwithstanding that it is arguably a new event. The prescribed procedure instead has two steps in order: first edit the issue body so it states how things turned out, then perform the GitHub close action supplying a close reason.

17. **"A second issue is never filed where an edit to the first serves."** If modifying an existing issue would accomplish what you need, creating an additional issue is prohibited. The condition "where an edit ... serves" means: whenever an edit is sufficient — so a new issue is only permissible when an edit genuinely would not do the job.

18. **"(This overrides the default habit of stacking comments and new records; the edit history preserves the before/after.)"** A parenthetical giving the rationale and flagging that this rule contradicts an expected instinct. "The default habit of stacking comments and new records" names the ordinary practice — leaving a chain of comments and creating fresh issues for each development, so that the trail of what happened is visible. The counter-argument offered is that no information is lost by editing, because GitHub retains an edit history from which the prior and revised versions can both be recovered. I read "This overrides" as instructing you to abandon that instinct in favor of rules 14–17, and I read the intended audience of the warning as an agent (or person) who would otherwise reflexively comment.

19. **"Write for a zero-context reader."** Compose the issue for someone who arrives with no knowledge of the conversation, session, or circumstances that produced it.

20. **"Before submitting, check the three tests: the subject is identifiable from the issue alone; the why is stated; the next action is executable by a reader who was not in this conversation."** As a pre-submission checklist, verify three properties: (a) a reader can tell what the issue is *about* using only the issue itself — given the earlier summary/body split, I take "the issue alone" to include the material the body cites, so a paired issue passes if its summary body plus its cited Markdown file suffice; (b) the issue explains the reason or motivation, not just the requested change; and (c) whatever is supposed to happen next is described specifically enough that a person with no access to the originating discussion could actually carry it out.

21. **"Make every reference openable and every claim checked:"** A heading rule with two halves: anything the issue points at must actually be reachable by the reader, and any assertion the issue makes must be verified before it is written down. The colon introduces the three sub-rules.

22. **"A file reference must open from the reader's seat: full URLs for anything outside this repository; in-repo paths verified present on main before citing."** When you cite a file, it must be reachable by whoever reads the issue, not merely by you in your current working environment — "from the reader's seat" means judging the reference from the reader's position and access, not the author's. Two concrete consequences follow: for files not in this repository, give a complete URL rather than a bare path (a local path would be meaningless to the reader); and for files that are in this repository, confirm the file actually exists on the `main` branch before you cite it — because a path that only exists on your working branch or in your worktree will not resolve for the reader.

23. **"Run the cheap verifications before filing — a check one grep or one `gh` call answers is run now, so the body states what is, not what might be."** Any factual question you could settle with a single low-cost command — one text search, or one GitHub CLI invocation — must be settled before the issue is submitted rather than left as an assumption. "Cheap" is defined operationally as "answerable in one command." The purpose given is that the resulting issue text should assert established fact rather than conjecture or hedged guesses.

24. **"An absence claim carries its search receipt: the query and the scope that came up empty."** If your issue asserts that something does *not* exist — no prior issue, no existing document, no precedent — that assertion must be accompanied by evidence of the search that failed to find it: specifically, what exact search terms you used, and what body of material you searched over. "Search receipt" is a coined term for that recorded query-plus-scope proof, and the point is that a bare "nothing exists" is unfalsifiable to the reader unless they know what was actually looked at.

## How to do it

1. **"Ask: `scripts/ghi-info-ask.py "<question>"`; add `--include-closed` when asking about precedent or absence."** The literal command form for step 1's ask: run that script with your question as a quoted argument in place of `<question>`, and append the `--include-closed` flag in the two cases already named — when you are looking for prior handling of a similar matter, or when you are trying to establish that nothing exists.

2. **"When the ask fails, fall back in order: grep `ghi-mirror/` in the checkout (stale unless freshly regenerated), then `gh issue list --repo nedschorus/nedschorus --state all --search "<terms>"`, and grep the repository for pair documents on the subject."** If that script does not work, use these three substitutes in the sequence given: first, text-search the `ghi-mirror/` directory in your local working copy — with the caveat that this directory is a snapshot whose contents may be out of date relative to GitHub unless it was regenerated recently, so I take "(stale unless freshly regenerated)" as qualifying the reliability of the mirror's contents, warning you that a hit or a miss there may reflect an older state of the issues; second, query GitHub directly with the CLI, listing issues in the `nedschorus/nedschorus` repository across all states (open and closed, which is what `--state all` buys you) filtered by search terms; and third, search the repository's own files for companion Markdown documents on your topic, since a pair document may exist even where the issue search misses.

3. **"File: `gh issue create --repo nedschorus/nedschorus --title "<title>" --body-file <file>`."** To create a new issue, run the GitHub CLI's create command against the `nedschorus/nedschorus` repository, supplying the title inline as a quoted string and supplying the body by pointing at a file on disk rather than typing it into the command.

4. **"Edit: `gh issue edit <number> --repo nedschorus/nedschorus --body-file <file>`."** To change an existing issue's body, run the CLI's edit command with the issue's number, against the same repository, again passing the replacement body as a file. Note this replaces the body wholesale, so the file must contain the complete revised body, not just the change.

5. **"Close: after the body edit recording the outcome, `gh issue close <number> --repo nedschorus/nedschorus --reason "completed"` (or `"not planned"`)."** Closing is the second half of the two-step completion procedure from step 3: only once you have already edited the body to state how things turned out do you run the close command, giving the issue number, the repository, and an explicit reason — `completed` when the work was actually done, or `not planned` when the issue is being closed without doing it.

6. **"Comment (the two catalog events only): resubmit through the write tool `scripts/ghi-issue-write.py`'s comment verb naming the event kind; plain `gh issue comment` is denied by the write path."** Comments — permitted, per the parenthetical, only for the two entries in step 3's list, an instance outcome or a challenge to a ruling ("catalog" = that fixed enumerated set) — must be posted by invoking the project's own writing script `scripts/ghi-issue-write.py` using its `comment` subcommand, and you must declare which of the two event kinds the comment is. The final clause states that a direct `gh issue comment` invocation will be refused — I read "the write path" as the project's enforcement layer sitting between you and GitHub, most likely a permission/hook rule that rejects the raw CLI call so that comments cannot bypass the two-event catalog. I cannot tell with confidence what "resubmit" means here: it may presume you have already tried the plain `gh` command and been denied, so this is your retry through the sanctioned route; or "re-" may be doing no work and it simply means "submit it via the script."

7. **"Compose bodies in a file and pass `--body-file`; an inline `--body` with backticks is silently mangled by the shell."** Always write issue body text into a file and hand that file to the CLI, rather than passing the text directly on the command line. The reason given is a concrete failure mode: backtick characters in an inline `--body` argument are interpreted by the shell as command substitution, so the text that actually reaches GitHub is altered — and "silently" means nothing errors out, so you would not notice the corruption unless you inspected the result.

8. **"Queue routing: write the queue file under its destination directory, or add the `draft` label to the issue; the drain process is [nedschorus#24](https://github.com/nedschorus/nedschorus/issues/24)."** The mechanics of step 2's queue option: either place the Markdown file into whichever queue directory corresponds to its eventual destination, or, for issue-shaped material, apply the `draft` label to the issue. The final clause identifies where the procedure for eventually emptying those queues is documented — issue number 24 in the `nedschorus/nedschorus` repository, given as a full URL so a reader outside the repository can open it.
