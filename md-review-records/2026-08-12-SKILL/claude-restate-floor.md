# Frontmatter — description

1. This skill must be invoked prior to performing any write operation that affects a GitHub issue within this project's repository; the four listed cases — creating a brand-new issue, modifying the text of an existing issue's body, adding a comment to an issue, or moving material that is currently sitting in a queue into issue form — are given as instances covered by "any write that touches a GitHub issue."
2. Producing or modifying any project artifact (a file, document, or piece of content) for which it's possible that its proper home is an issue also requires invoking this skill first, and the stated reason is that deciding where something belongs (routing) is itself part of what this skill does.
3. This skill should not be invoked for actions that only read an existing issue's content or that cite/reference an issue without modifying it.

# When Used

1. This skill applies before four kinds of actions: filing a new issue, editing an existing issue's body text, adding a comment to an issue, or writing project material for which the correct destination — a GitHub issue, a queue, or a plain markdown file — has not yet been determined.

# What to do

1. The first instruction in this step is to perform the "ask" sub-step before filing anything.
2. Submit the topic/question to something called "ghi-info" by executing the script `scripts/ghi-info-ask.py` with the question as input (adding the `--include-closed` flag specifically when the question is about whether something similar has happened before, or about whether something is absent/doesn't exist); then read both the issues that this returns and any paired documents that those issues reference. (I read "put the subject to ghi-info" as "submit/pose the subject to ghi-info"; the phrasing is somewhat unusual and could alternatively be read as "hand the subject off to ghi-info's process," though the practical meaning seems the same either way.)
3. If it turns out an already-existing artifact already covers this subject, the instructed action is to edit that existing artifact rather than create a new one — revising the existing issue is described as the default choice, drawn as an analogy to another skill named "md-write," which apparently also defaults to a "REVISE" action in a similar situation.
4. If the "ask" step fails (i.e., running the script doesn't work or doesn't return usable results), that failure does not stop you from proceeding with filing/editing; instead you should fall back to first grepping a local mirror, then searching via `gh`, and then continue following the rules given in this document.

5. The instruction is to determine an artifact's destination based on what category of content it is ("state").
6. Every artifact falls into one of two overall situations: either it has reached a permanent/settled location ("final at its home"), or it currently sits in one of several specifically-named queues, each of which has an associated process for being emptied over time (a "drain"). (I flag "final at its home" as ambiguous: it could mean the artifact's content is complete/no-longer-changing, or merely that it has a stable, permanent address regardless of whether the situation it describes is still open — the latter reading fits better with a later bullet describing issues that carry "pending state" as one of these two situations.)
7. Material for which no decision about its ultimate destination has yet been made should be placed into whichever queue matches its type: wiki-oriented material not yet finalized goes into the `docs/wiki/queue/` directory, markdown material meant to be paired with an issue goes into `docs/issues/queue/`, and issues that are still undecided are marked with a `draft` label — and in all of these cases, no GitHub issue should be created for it yet.
8. Anything that represents an ongoing/unresolved status — examples given are a desired feature or component, a question that hasn't been answered, or a promise to take some future action — should be given a GitHub issue; specifically, it should be issue-only (no companion document) if the body text is fewer than 500 words, but should instead be an "MD-GHI pair" (a markdown file plus a linked issue) when there is a substantial amount of supporting working material involved.
9. In such a pair, the issue's body should contain a summary while the markdown document holds the detailed substantive content, and the required order of operations is: write the markdown file first, get it merged/committed ("land" it), and only then reference/link it from within the issue.
10. Reference content that is considered final and is not waiting on any further decision or action should simply be a plain markdown file placed at its permanent location, with no accompanying issue.
11. The rule used to decide between these categories is stated as: an issue is used for content representing status/state, a markdown document is used for substantive content, and a queue is used for anything whose routing hasn't been decided yet.
12. When it's genuinely unclear which category applies, the instructed fallback is to create an issue labeled `draft` and continue on, rather than letting the uncertainty prevent the write from happening.

13. The instruction is that revising something is generally accomplished by editing the body text of an issue (as opposed to, e.g., adding comments or filing new issues).
14. Any clarification of meaning, correction of an error, or change to an issue's intended scope should be made by editing the issue's body text directly, and this includes correcting references that are already present in that body.
15. A comment should be added only when something genuinely new has occurred, and this is narrowed to exactly two kinds of events: the outcome of a specific occurrence/instance, or someone disputing/challenging a previous ruling or decision.
16. When something reaches completion, that specific event does not count as one of the two comment-worthy events described above; instead, the outcome should be written into the issue's body (by editing it), and then the issue should be closed, with a reason given for the closure.
17. A new, separate issue should never be created in a situation where editing the existing issue would accomplish the same purpose.
18. This rule (prefer edits over comments/new issues) is stated to take precedence over what would otherwise be a natural/default tendency to keep appending comments and creating new records over time; the justification given is that an issue's edit history preserves a record of what it said before and after the change, which comments/new issues would not.

19. The instruction is to write issue content with the needs of a reader who has no prior context in mind.
20. Before an issue is submitted, it should be checked against three specific tests: whether the subject/topic can be identified using only the content of the issue itself; whether the issue states the reason/motivation behind it; and whether the next action to be taken is described clearly enough that it could be carried out by someone who was not present for the conversation or process that led to the issue being written.

21. The instruction is to ensure that every reference included is something a reader can actually open, and that every factual claim made has been checked/verified.
22. A reference to a file must be something the reader can open from wherever they are located: for anything located outside of this repository, a full URL must be given; for paths that are inside this repository, the path must be confirmed to actually exist on the `main` branch before it is cited.
23. Any verification that is cheap to perform — meaning something answerable with a single `grep` command or a single call to the `gh` CLI tool — should be carried out before filing, so that the resulting issue body describes things that have been confirmed to be true rather than things that are merely assumed or possible.
24. When an issue asserts that something is absent (does not exist, was not found, etc.), that claim must be accompanied by evidence of the search that was performed to establish this: specifically, what query was used and what scope was searched, noting that the search of that scope produced no results.

# How to do it

1. To perform the "ask" step, run the command `scripts/ghi-info-ask.py "<question>"`, and add the `--include-closed` flag specifically when the question concerns precedent (whether something similar has happened before) or absence (whether something doesn't exist).
2. If the ask script fails, fall back through the following steps in this specific order: first, search the `ghi-mirror/` directory in the local checkout using `grep` (noting that its contents are considered out-of-date/unreliable unless it has just recently been regenerated); second, run `gh issue list --repo nedschorus/nedschorus --state all --search "<terms>"`; and third, search (`grep`) the repository for paired markdown documents relevant to the subject.
3. To file a new issue, the command to run is `gh issue create --repo nedschorus/nedschorus --title "<title>" --body-file <file>` — that is, create the issue in the `nedschorus/nedschorus` repository, supplying a title directly and a body sourced from a file.
4. To edit an existing issue, the command to run is `gh issue edit <number> --repo nedschorus/nedschorus --body-file <file>` — that is, edit the issue with the given number in that repository, supplying the new body text from a file.
5. To close an issue, after having already performed the body edit that records the outcome (as described earlier), run `gh issue close <number> --repo nedschorus/nedschorus --reason "completed"` (or, alternatively, with the reason `"not planned"`).
6. For commenting — which, per the earlier rule, applies only to the two cataloged event types — the instructed method is to go through the "comment" verb/sub-command of the `scripts/ghi-issue-write.py` write tool, specifying which of the two event kinds applies; using the plain `gh issue comment` command directly is described as being blocked/rejected by "the write path." (I read "resubmit" as possibly implying a first attempt via the plain `gh` command gets denied and must then be redone through the correct tool, though it may simply mean "submit," full stop.)
7. Issue body text should be composed in a separate file and passed in using the `--body-file` option, rather than being passed inline with `--body`; the stated reason is that if the inline body text contains backtick characters, the shell will corrupt/alter it incorrectly without producing any visible error ("silently mangled").
8. For routing material to a queue, either write the queue file into its designated destination directory, or alternatively add the `draft` label to an issue; the process by which queued items are later processed and removed from the queue ("drained") is documented in, or tracked by, issue number 24 in the `nedschorus/nedschorus` repository on GitHub.
