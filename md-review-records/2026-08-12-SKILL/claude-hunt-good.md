## Findings

**1. Line 3 vs line 10 — the trigger is stated twice, with different scopes.**
Frontmatter: `"Creating or revising any project artifact that might belong in an issue also triggers it, because routing is part of the skill."` — When Used: `"or writing project material whose home (issue, queue, or MD) is not yet decided."` The frontmatter fires on any artifact that *might* belong in an issue, including one whose home is already settled as an MD; the body fires only when the home is *not yet decided*. An agent deciding whether to load this skill before writing a wiki MD gets opposite answers depending on which sentence it reads. Additionally "might belong in an issue" has no bound — almost any project artifact might. Sure.

**2. Lines 12 and 27 — `"## What to do"` and `"## How to do it"` are near-duplicate, non-self-documenting headings.** The split between them is not stated, and it is not observed: the ask command, its `--include-closed` flag, and its fallback ladder appear in both (line 14 and line 29). An agent looking for the authoritative form of a procedure cannot tell which section governs, and neither heading is greppable for anything specific. This also runs against CLAUDE.md line 7: `"use explicit, clear and precise multi-part names"` for `"section headings"`, `"with 3 or 4 parts, not 1 or 2"`. Sure on the duplication; sure that the headings are generic.

**3. Line 14 — `"1. Ask before filing."`** The step label scopes the ask to *filing*, but the skill governs edits, comments, and routing as well (line 3, line 10), and the step's own content ("When an existing artifact covers the subject, edit that artifact") is about the edit path. Literally obeyed, an agent editing an issue body skips step 1 entirely. Sure.

**4. Line 14 — `"Put the subject to ghi-info"`.** `ghi-info` is never defined in this file: not what it is (agent, service, index, script), not what it accepts, not what it returns beyond "issues". A reader with only this file cannot tell whether "the question" should be a natural-language sentence, keywords, or a subject line, and cannot judge whether a returned result set is complete. Sure.

**5. Line 14 (and line 29) — `"running scripts/ghi-info-ask.py"`.** This script does not exist in the checkout (`scripts/` contains handoff-*, launch-claude, md-review-*). Every invocation of step 1 as written fails. The file does anticipate failure — `"A failed ask never blocks the write"` plus the ladder — so the step remains completable, but the file never says the script is unbuilt, so an agent will spend a turn diagnosing a missing file as an environment problem rather than the expected state. Sure that the file is absent; the fallback ladder is what keeps this from being a dead end.

**6. Line 14 — `"read the issues it returns and the pair documents they cite"`.** No stopping point: no cap on how many issues, no rule on whether citations are followed transitively (a pair document that cites another issue that cites more documents), and no criterion for "enough read to proceed". On a broad subject this is unbounded work before a single write. Separately, `"pair documents"` is used here before anything named "pair" is introduced — the MD-GHI pair appears in step 2 (line 17), and even there the term "pair document" is never explicitly defined as the MD half. Sure on the missing stopping point; sure that the term precedes its explanation.

**7. Line 14 — `"When an existing artifact covers the subject, edit that artifact — a revision of the existing issue is the default disposition"`.** The first clause is about any covering artifact; the second silently narrows to an issue. When the covering artifact is a wiki MD or a queue file, the sentence gives an instruction ("edit that artifact") and then names a disposition that does not apply to it, and the file never says what the default disposition is for the non-issue case. Sure.

**8. Line 14 — `"the same way md-write defaults to REVISE"`.** `md-write` is named with no path, no description, and no statement of where its rules live; `REVISE` is an unexplained capitalized value from that other system. The analogy is the only justification given for the default disposition, and a reader who cannot resolve either name cannot check or apply it. Sure.

**9. Line 14 — `"A failed ask never blocks the write"`.** Absolute claim. The ordinary counterexample is a failure whose cause is shared with the write path: if the ask fails because `gh` is unauthenticated or the network is down, the *ask* does not block the write, but the write is blocked anyway by the same condition — the sentence as written invites an agent to conclude it can proceed when it cannot. This is arguable by design, since the ladder ending in "proceed under these rules" is precisely what makes the ask non-blocking; unsure for that reason. CLAUDE.md line 6 cautions: `"absolute imperatives like 'always' or 'never' can backfire in unforeseen conditions."`

**10. Line 14 vs line 29 — the fallback ladder has two different lengths.** Line 14: `"fall back to grepping the local mirror, then \`gh\` search, and proceed under these rules."` Line 29: `"fall back in order: grep \`ghi-mirror/\` in the checkout ... then \`gh issue list ...\`, and grep the repository for pair documents on the subject."` The step-1 version omits the third rung (grepping for pair documents), and names its first rung only as "the local mirror" — a term that is never defined and never tied to `ghi-mirror/` except by the reader's inference. An agent following step 1 alone does less searching than one following the How-to. Sure.

**11. Line 15 — `"Every artifact is either final at its home or in a named queue with a drain"`.** This binary excludes the case the very next bullets define: `"Anything carrying pending state — a wanted feature or component, an open question, a commitment to act — gets a GHI"` (line 17). An open issue carrying pending state is by definition not final, and it is not in a named queue (unless `draft`-labeled). The framing sentence therefore contradicts the list it introduces. Ordinary counterexample beyond that: an MD being drafted on a branch is neither final at its home nor in a queue. Sure.

**12. Line 16 — `"Material whose disposition is not yet decided goes to its destination queue — \`docs/wiki/queue/\` for wiki-bound doctrine, \`docs/issues/queue/\` for pair-bound MDs"`.** Circular as written: choosing between the wiki queue and the issues queue requires already knowing whether the material is wiki-bound doctrine or a pair-bound MD, which is the disposition decision the material is said not to have made yet. An agent holding genuinely undecided material has no rule for picking a queue. Sure.

**13. Line 16 — `"with no GHI"`, first use of `GHI`.** The acronym is never expanded anywhere in the file, and it carries the load of the central distinction (`"the GHI carries state, the MD carries substance"`, line 19). It is inferable from the frontmatter's "GitHub issue" and the skill name, but the file never states the expansion, and it is not obvious whether "GHI" means the issue itself or a broader record type. Sure that it is undefined; unsure whether the inference is reliable enough in practice.

**14. Line 16 — `"the \`draft\` label for queued issues — with no GHI."`** Self-contradictory: a `draft`-labeled issue *is* a GitHub issue, so the third listed queue violates the clause that closes the same sentence. Obeyed literally, an agent that routes undecided material to the `draft` label has both created a GHI and been told it created none. This also collides with line 19, `"file a \`draft\`-labeled issue and move on"`, which is the same act. Sure.

**15. Line 16 — `"wiki-bound doctrine"`.** "Doctrine" is used as a content category that determines routing, and is defined nowhere in the file; nothing distinguishes doctrine from the `"Final reference content"` of line 18, which routes to a bare MD instead. An agent holding a settled general rule cannot tell which of the two applies. Sure it is undefined; unsure how often the two categories actually collide.

**16. Line 17 — `"issue-only when the body stays under 500 words, an MD-GHI pair when substantial working material rides with it."`** Two independent criteria with no precedence, and they cross: a body under 500 words that carries substantial working material satisfies the first test and fails the second. The file also does not say what is counted (title? references? the summary body only, or the summary plus the MD?) or when the count is taken, given that the body is composed before filing. Two agents will route the same material differently. Sure.

**17. Line 17 — `"the pair sequence is write the MD, land it, then cite it from the issue."`** "Land it" is not defined. Line 23's `"verified present on main before citing"` suggests it means merged to main, but the file never says so, and it does not say by what route (direct commit, PR, another agent's merge) or what to do while the MD is written but not yet landed — which is the normal state of an agent working on a branch, and which blocks the third step of the sequence indefinitely. Unsure only about the intended meaning; sure the term is unexplained.

**18. Line 18 — `"Final reference content awaiting nothing is a bare MD at its home."`** "Its home" is never defined for an MD. The file names `docs/wiki/queue/` and `docs/issues/queue/` as queues, but no corresponding non-queue destinations, so an agent told to write a bare MD has no location rule and must invent one. Sure.

**19. Line 19 — `"When the routing is genuinely ambiguous, file a \`draft\`-labeled issue and move on; ambiguity never blocks the write."`** Two problems. First, this instructs the creation of an issue for undecided material, which line 16 classifies as queue material `"with no GHI"` — the same act described as both filing an issue and not creating a GHI. Second, `"never"` is broader than holds: line 14 makes an existing covering artifact the controlling case, so ambiguity about whether an existing issue already covers the subject does have to be resolved before writing, or the agent files the duplicate that line 20 forbids. Sure on the contradiction; sure on the counterexample.

**20. Line 20 — `"A comment is only for a genuinely new event — an instance outcome, or a challenge to a ruling."`** Both event kinds are undefined in this file. "Instance" is never given a referent (an instance of what — a recurring process, a rule application, a test run?), and "ruling" is never explained (who rules, where rulings are recorded, what distinguishes a challenge from a scope change, which line 20 routes to a body edit instead). Since the How-to requires `"naming the event kind"` (line 33), an agent must produce a value it cannot derive. Sure.

**21. Line 20 — `"Completion is not a comment: record the outcome in the body, then close the issue with its reason."`** This sits against `"an instance outcome"` in the previous sentence: one kind of outcome is a comment and another is a body edit, with no test to tell them apart. When an issue that tracked a repeated activity finishes, the agent cannot determine whether the final result is an instance outcome (comment) or a completion (body edit plus close). Sure.

**22. Line 20 — `"A second issue is never filed where an edit to the first serves."`** Circular: it forbids a second issue exactly when an edit "serves", and the file never says when an edit serves. As a decision rule it produces no decision. Taken as an absolute it also over-reaches: a closed issue whose subject recurs, or a distinct actionable task discovered inside a broad issue, are ordinary cases where a new issue is right — and the file's own line 17 (pending state gets a GHI) supports filing them. Sure.

**23. Line 20 — `"the edit history preserves the before/after"`.** Offered as the justification for preferring edits over comments, but stated without limits. GitHub's body edit history can be deleted by the editor or by users with write access, so the before/after is not guaranteed to survive; and the file's own toolchain cannot read it — every command in the How-to is `gh`, which offers no way to retrieve issue body edit history, so an agent following this skill can never recover what the sentence promises is preserved. Unsure on the exact reach of the API/CLI limitation; sure that the sentence states no limit of any kind.

**24. Line 21 — `"the subject is identifiable from the issue alone"`.** Conflicts with the pair model in line 17: `"The body carries the summary, the pair MD the substance"`. For an MD-GHI pair the substance is deliberately not in the issue, so a test demanding identifiability "from the issue alone" either fails every pair by construction, or "alone" silently includes what the issue cites — and the file never says which. An agent applying the test literally to a pair summary will keep expanding the body until it duplicates the MD, defeating the split. Sure.

**25. Line 21 vs CLAUDE.md line 5 — the zero-context test is defined in two places, with drift.** SKILL.md: `"Write for a zero-context reader. Before submitting, check the three tests: the subject is identifiable from the issue alone; the why is stated; the next action is executable by a reader who was not in this conversation."` CLAUDE.md: `"Write durable artifacts — committed files, issue bodies, commit messages — for a reader with zero context: the subject identifiable, the why stated, usable without the conversation that produced it."` The first two tests restate CLAUDE.md; the third narrows `"usable without the conversation"` (the whole artifact) to `"the next action is executable"` (one element), and the first adds the `"from the issue alone"` restriction CLAUDE.md does not have. An agent applying both has to reconcile a narrower and a broader form of the same rule. Unsure whether the divergence is intended; sure that the same rule is defined twice with different wording.

**26. Line 22 vs line 24 — `"Make every reference openable and every claim checked"` against `"Run the cheap verifications before filing — a check one grep or one \`gh\` call answers is run now"`.** The heading demands every claim be checked; the bullet under it limits checking to claims answerable by a single grep or a single `gh` call. A claim needing three calls is required by one sentence and excused by the next, and the file does not say what happens to it — whether it is verified anyway, hedged, or omitted. Sure.

**27. Line 23 — `"A file reference must open from the reader's seat: full URLs for anything outside this repository; in-repo paths verified present on main before citing."`** Two readings of "the reader's seat" that lead to different bodies. If the reader is on github.com — the natural seat for an issue reader, and the seat that motivates "full URLs for anything outside this repository" — a bare in-repo path is plain text there and does not open, so the rule's own second clause fails its first. If the reader has a checkout, bare paths open fine and the full-URL clause is what looks unnecessary. The file does not say which seat it means. Unsure which reading was intended; sure the sentence supports both.

**28. Line 29 — `"grep \`ghi-mirror/\` in the checkout (stale unless freshly regenerated)"`.** The parenthetical makes the mirror's usefulness conditional on regeneration, and the file never says how regeneration is performed, by whom, or how an agent determines whether the copy in hand is fresh. The rung is therefore usable only by someone who already knows a procedure this file does not contain. Sure.

**29. Line 29 — `"fall back in order: grep ... then \`gh issue list ...\`, and grep the repository for pair documents"`.** Supports two readings: run the rungs in sequence and stop at the first that returns something, or run all three because each covers material the others miss (the mirror is stale, `gh` search misses MDs, the MD grep misses issues). The cost and completeness of the ask differ substantially between the two, and step 1's shorter version (finding 10) does not settle it. Sure the ambiguity exists.

**30. An agent hitting a missing directory has no stated instruction — fall through to the next rung, or treat it as an error — and the ladder's meaning under "in order" (finding 29) determines the answer it cannot get. Sure the directory is missing; sure the absent case is unaddressed.

**31. Line 30 vs lines 16, 19, 35 — the `draft` label is required by three rules and has no command.** `"File: \`gh issue create --repo nedschorus/nedschorus --title \"<title>\" --body-file <file>\`"` carries no `--label`, while line 19 says to `"file a \`draft\`-labeled issue"` and line 35 says to `"add the \`draft\` label to the issue"`. The How-to gives an exact invocation for every other verb (file, edit, close, comment, ask), so its silence here reads as "no command needed" rather than "supply your own". The file also never states that a `draft` label exists in the repository or must be created. Unsure whether the omission is deliberate; sure the section is otherwise command-complete.

**32. Line 33 — `"Comment (the two catalog events only): resubmit through the write tool \`scripts/ghi-issue-write.py\`'s comment verb naming the event kind; plain \`gh issue comment\` is denied by the write path."`** Three defects in one line. (a) `scripts/ghi-issue-write.py` does not exist in the checkout, and this line — unlike the ask (line 14) — states no fallback, while simultaneously declaring the only other route denied. Commenting is therefore impossible for an agent following this file, and the file does not acknowledge the case; this is the one procedure here with no way to complete. (b) `"the write path"` names an enforcement mechanism that is never defined: it is not stated what denies the command (a hook, a permission rule, a wrapper), so an agent cannot tell whether the denial is advisory or hard, nor recognize the denial when it happens. (c) `"resubmit"` presupposes an earlier submission, implying the workflow is *attempt `gh issue comment`, get denied, then retry through the tool* — which contradicts the same sentence's statement that `gh issue comment` is denied and should not be used. Sure on all three.

**33. Line 34 — `"an inline \`--body\` with backticks is silently mangled by the shell."`** Stated without qualification, and false as written for the ordinary case of single-quoted arguments: in zsh and bash, `--body 'text with \`ticks\`'` passes backticks through untouched; the mangling happens under double quotes or no quotes, where the shell performs command substitution. An agent that trusts the sentence as universal learns a wrong model of its shell, and one that tests the single-quote case and finds it works may discard the whole (correct and useful) recommendation. Sure about the shell behavior.

**34. Line 34 — `"Compose bodies in a file and pass \`--body-file\`"`.** The file defines this mechanism but not where the composed file lives or what becomes of it: no directory, no naming rule, no statement of whether it should be deleted after filing or is itself a durable artifact. The reachable bad case is a scratch body file left inside `docs/` or committed to the repository. Unsure — this may be considered obvious enough to leave open — but the file gives commands precise enough elsewhere that the gap is noticeable.

**35. Line 35 — `"write the queue file under its destination directory, or add the \`draft\` label to the issue"`.** `"the issue"` has no antecedent. Queue routing (line 16) applies to material that is expressly not yet a GHI, so at the moment this instruction applies there is no issue to label; the definite article implies one already exists, and the file never says to create it first — the only place that does is line 19, which is scoped to the ambiguous-routing case, not to queue routing generally. Sure.
