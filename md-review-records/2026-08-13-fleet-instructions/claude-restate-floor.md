# Session-management facts, verified 2026-08-13 on Claude Code 2.1.231

Header meaning: a list of facts about managing Claude Code sessions, confirmed accurate as of 2026-08-13 using Claude Code version 2.1.231.

1. "Expensive to learn, easy to lose:" — Framing statement: the facts below took significant effort/trial to discover, but could easily be forgotten if not recorded — hence why they're written down here.
2. "**Job ids are not session ids.** `claude attach <id>` wants the 8-character job id (directory names under `~/.claude/jobs/`), not the session UUID." — Job ids and session ids are two distinct, non-interchangeable identifier types. The `claude attach <id>` command specifically requires the 8-character job id (which corresponds to a directory name under `~/.claude/jobs/`), not the (presumably longer/differently-formatted) session UUID.
3. "**`claude agents`** opens agent view: `Space` peeks without attaching, `Ctrl+R` renames, `Ctrl+T` pins against the ~1-hour idle reap, `Ctrl+X` stops, `Ctrl+S` groups by directory — which makes the shared-directory hazard visible." — Running `claude agents` opens an interface listing agents, with these keyboard shortcuts: Space lets you view an agent's session content without joining/attaching to it; Ctrl+R renames an agent; Ctrl+T protects an agent from an automatic cleanup process that otherwise removes sessions idle for about an hour; Ctrl+X stops/ends an agent's session; Ctrl+S groups the list by working directory, which is noted as useful because it reveals the risk of multiple sessions sharing one directory (referenced again in "Your standing invariant").
4. "It lists **only the machine it runs on**; the box needs `ssh nedlern@ned-box -t 'claude agents'`." — The `claude agents` command shows only agents on the same machine where it's run, not agents on other machines. To view agents on "the box" (the Ubuntu machine ned-box), one must run it remotely via the shown SSH command (with a pseudo-terminal allocated via `-t`, needed for its interactive interface to work over SSH).
5. "**Process uptime is not idle time.** A session showing 23 hours of `etime` may have been active a minute ago; check its transcript's modification time under `~/.claude/projects/`." — How long a process has been running (its elapsed time, `etime`) is not the same as how long it's been unused/idle. Example: a session with 23 hours of elapsed running time could still have been actively used as recently as one minute ago. To determine actual last-activity time, check the file-modification timestamp of its transcript file under `~/.claude/projects/` instead.
6. "Non-interactive SSH shells did not see `~/.local/bin` until `~/.bashrc` was fixed on 2026-08-13 to export PATH above its non-interactive early-return." — Previously, SSH sessions running a single non-interactive command couldn't find executables in `~/.local/bin` because it wasn't in their PATH in that context. This was fixed on 2026-08-13 by moving the line in `~/.bashrc` that exports/extends the PATH variable to a position before the point in that file where it checks for a non-interactive shell and exits early — meaning the PATH-exporting line was previously being skipped for non-interactive shells, and relocating it above that check ensures it now runs regardless.

# Your standing invariant

1. "**Two live sessions must never share a working directory.**" — An absolute rule: at no point should two currently-active agent sessions both be operating out of the same directory.
2. "Forks inherit the parent's directory along with its conversation; background jobs inherit the launching session's cwd." — Explaining two ways this rule could be violated if unmanaged: when a session is "forked" (spawned as a copy of an existing one), the new session starts with the same working directory as its parent, alongside inheriting its conversation history. Separately, when a background job is launched, it inherits the current working directory of whichever session started it.
3. "`EnterWorktree` relocates a running session correctly — the gap is the trigger, not the capability." — A tool called `EnterWorktree` exists and correctly relocates an already-running session to a different working directory (into a separate git worktree). The missing piece is not the ability to perform this relocation (which already works) but a reliable way to detect/trigger when it's needed — tying back to the unsolved detection problem described in "Your queue."
