## Session-management facts, verified 2026-08-13 on Claude Code 2.1.231

1. The section heading itself: the statements below are empirical facts about how Claude Code sessions behave, and they were checked and confirmed true on 2026-08-13 against that one specific version of the Claude Code CLI — the version and date being stated so a later reader knows the facts may not hold on other versions.
2. "Expensive to learn, easy to lose:" — A verbless preamble asserting that discovering these facts cost significant effort or time, and that they are the kind of knowledge that easily drops out of an agent's context and is forgotten; the combination is the justification for writing them down here.
3. "**Job ids are not session ids.** `claude attach <id>` wants the 8-character job id (directory names under `~/.claude/jobs/`), not the session UUID." — Two distinct identifier schemes exist and are easily confused. The `claude attach` subcommand's argument must be the job identifier, an 8-character string which can be found in practice as the names of the directories inside `~/.claude/jobs/`; passing the session's UUID instead will not work.
4. "**`claude agents`** opens agent view: `Space` peeks without attaching, `Ctrl+R` renames, `Ctrl+T` pins against the ~1-hour idle reap, `Ctrl+X` stops, `Ctrl+S` groups by directory — which makes the shared-directory hazard visible." — Running the command `claude agents` brings up an interactive listing of agent sessions, in which the following key bindings apply: Space displays a preview of the selected session's content without connecting to it; Ctrl+R renames the selected agent; Ctrl+T marks the selected session so it is exempt from the automatic cleanup that terminates sessions after roughly an hour of inactivity ("reap" = that automatic killing); Ctrl+X terminates the selected session; and Ctrl+S regroups the listing by working directory. The trailing clause says that last grouping is useful because it displays sessions sharing a directory together, making the condition the standing invariant forbids apparent at a glance.
5. "It lists **only the machine it runs on**; the box needs `ssh nedlern@ned-box -t 'claude agents'`." — The agent view shows sessions local to whichever machine the command executes on and no others; therefore to see the sessions on ned-box (the Ubuntu machine, "the box") from somewhere else — in practice from the Mac — you must run that exact ssh command, where the `-t` flag forces allocation of a terminal so the interactive view can render.
6. "**No side-by-side view exists.** Simultaneous views mean one terminal per session." — Claude Code offers no built-in feature for displaying two or more sessions next to each other in one view; consequently, if you want to watch several sessions at the same time, you must open a separate terminal (window or pane) for each one.
7. "**Process uptime is not idle time.** A session showing 23 hours of `etime` may have been active a minute ago; check its transcript's modification time under `~/.claude/projects/`." — How long a session's operating-system process has existed tells you nothing about how long it has been inactive. The example: a session that `ps` reports with an elapsed time (`etime`) of 23 hours could nevertheless have been doing work sixty seconds ago. The reliable way to establish when a session was last active is to look at the last-modified timestamp of that session's transcript file, which lives under the `~/.claude/projects/` directory tree.
8. "Non-interactive SSH shells did not see `~/.local/bin` until `~/.bashrc` was fixed on 2026-08-13 to export PATH above its non-interactive early-return." — Commands run over ssh in a non-interactive shell were unable to find executables installed in `~/.local/bin`, because `~/.bashrc` contains an early `return` that aborts the file when the shell is non-interactive, and the line adding that directory to PATH sat below that return. On 2026-08-13 the file was edited so the PATH export happens above the early return; the "until" construction means the defect existed before that date and is fixed as of it.

## Your standing invariant

1. The section heading itself: what follows is a condition this seat is charged with keeping true at all times — a continuously held property rather than a task to complete once.
2. "**Two live sessions must never share a working directory.**" — At no point should two Claude sessions that are both currently running have the same working directory; each running session must have a directory (checkout or worktree) of its own.
3. "Forks inherit the parent's directory along with its conversation; background jobs inherit the launching session's cwd." — The two known mechanisms by which the invariant gets violated: when a session is forked, the new session receives not only a copy of the parent's conversation but also the parent's working directory, so both then occupy it; and a job started in the background from a session runs with that session's current working directory, again producing two occupants of one directory.
4. "`EnterWorktree` relocates a running session correctly — the gap is the trigger, not the capability." — The `EnterWorktree` tool is able to move an already-running session into a separate worktree of its own, and it performs that move properly; so what is missing in the system is not any ability to remedy the violation but the mechanism that notices the violation has occurred and causes the remedy to be invoked — detection and firing, in other words, is the unbuilt part.
