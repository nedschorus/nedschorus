1. “**Your job is to answer the questions that belong to no topic seat.**” conflicts with the examples “how something in the harness works,” “what a command does,” and “checking a status.” The seat model assigns session and agent machinery to `fleet`, while commands and statuses can belong to other named piles. The document never establishes whether routing depends on subject ownership, required depth, or merely the absence of an available working agent. The same question can therefore be routed both to `sidebar` and to a topic seat. Confidence: sure.

2. “You exist so the user **never** has to ask an off-topic question of a working agent” is too broad. A question may concern an observation or decision recorded only in that working agent’s current conversation; this file itself also says questions needing another pile’s deep history should go to that seat. In those cases, `sidebar` cannot eliminate the need to consult the working agent. Confidence: sure.

3. “how something in **the harness** works” uses an undefined name. The referenced documents mention launchers, a supervisor, hooks, worktrees, and task isolation, but never identify which of these collectively constitute “the harness.” A cold reader cannot determine the term’s scope or route a harness question consistently. Confidence: sure.

4. “**Nothing durable is meant to live here**” supports incompatible meanings of “here”: the conversation, the seat’s persistent home and branch, or the repository. The latter two readings conflict with the later requirements to commit disk changes and record knowledge in issues or design files. An agent taking it literally could discard work that the same file requires it to preserve. Confidence: sure.

5. “that **costs nothing precisely because you were never holding anything**” is literally false and conflicts with the referenced seat model, which says an idle seat “is not literally free” because it retains a directory and branch and incurs retirement work. A live sidebar can also hold uncommitted changes or knowledge awaiting the durable treatment required later in this file. Confidence: sure.

6. “suggest a **restart** rather than accumulating” does not identify which project operation “restart” means. The seat model distinguishes recycling through a handoff, exiting and relaunching, pausing, and retiring, with materially different persistence behavior. The instruction only asks for a suggestion, but the user cannot tell which operation is being suggested or what context it will retain. Confidence: unsure because “restart” may be intended informally as opening a fresh conversation, but that reading is not stated and clashes with the project’s more specific lifecycle vocabulary.

7. “**you have no thread to carry**” is broader than the surrounding procedure permits. The same sentence requires a handoff when the user asks, and a conversation may be interrupted before its current question, disk work, or required knowledge recording is complete. In those reachable cases there is a thread to carry. Confidence: unsure because “thread” might mean a long-lived owned pile rather than any unfinished conversational context, but the file does not limit the term that way.

8. “If a question turns into **real project work**” leaves the controlling boundary undefined. The permitted examples already include running scripts and checking files, while the later rules contemplate disk changes, commits, pushes, issues, and design-file edits. A cold reader cannot tell which of those actions crosses from a “small errand” into “real project work,” causing either premature refusal or accidental adoption of a topic seat’s work. Confidence: sure.

9. “**name the seat it belongs to** … and let the user take it there, **where its context already lives**” assumes every project task belongs to exactly one existing seat with existing context. The referenced seat model expressly recognizes work that fits no seat and becomes the possible seed of a new pile; cross-cutting work can also fit several seats. The singular routing command is impossible in those cases, and the claim that relevant context already exists is false for novel work. Confidence: sure.

10. “`ghi`” is not self-documenting and is difficult to search as an unqualified three-letter string. This file neither expands it nor summarizes its domain. The seat model eventually associates it with GitHub-issue tooling, but even there the abbreviation is not explicitly expanded. Confidence: unsure because the required opening reference does provide enough surrounding description to infer its purpose and exposes `ghi-instructions.md` as a precise search target.

11. “**Your work is done when the user's question is answered. There is no larger completion criterion, and none is missing.**” conflicts with the next section. If the work changed disk, it is not complete until the required commit and push; if it produced knowledge needed by another seat, it is not complete until that knowledge is recorded. Those are completion criteria beyond merely answering the question. Confidence: sure.

12. “Ephemeral applies to your context, **never to the user's work**” is too broad. Temporary diagnostics, disposable scratch files, caches, and one-time command output are ordinary user-requested work for which ephemerality is intentional. Taken literally, the statement turns inherently temporary artifacts into durability obligations. Confidence: sure.

13. “**Anything you change on disk is committed and pushed**” cannot be obeyed literally. Disk changes can occur outside a Git repository, in ignored caches, temporary files, credentials, locks, generated output, or machine-local state that must not or cannot be committed. A push can also fail because of authentication, network, or remote-ref conflicts; no outcome is given for these reachable cases. Confidence: sure.

14. “Anything you learn that a topic seat will need is written **where that seat will find it — an issue, a queue document under `docs/issues/queue/`, or the relevant design file**” defines a knowledge-transfer mechanism without an addressing rule. The referenced material does not say which seats monitor which issues or queue documents, the queue files are not uniformly seat-named, and “the relevant design file” supplies neither an identity nor a discovery procedure. It also leaves information with no suitable existing issue, queue entry, or design file unhandled. An agent can write somewhere durable while still failing the stated requirement that the destination seat find it. Confidence: sure.

15. “**An answer that exists only in this conversation is lost the moment it closes**” conflates loss to a successor with literal destruction. The referenced seat model permits handoffs whose companion dialog preserves the conversation tail, and the user may retain the conversation itself. The claim also conflicts with the model’s description of `sidebar` questions as “answered and forgotten.” This can cause needless permanent recording of routine answers. Confidence: sure.

16. “which is **the one way this seat can do harm**” is an overbroad absolute. Ordinary counterexamples include giving a wrong answer, executing a destructive one-off script, exposing credentials, committing unsuitable generated files, pushing the wrong branch, or routing work to the wrong seat. Treating conversation-only answers as the sole hazard hides the other risks created by this file’s own permitted activities. Confidence: sure.

Neither this file, `CLAUDE.md`, nor the explicitly referenced documents define the identifier’s source, syntax, or where in a commit it must appear. “Session” is defined, but “session id” is not. A future agent cannot produce a conforming commit or verify one. Confidence: sure.

Nothing in this brief limits it to Ubuntu-launched instances. A Mac-launched `sidebar` would be instructed to misidentify its own machine and wrap box commands incorrectly. Confidence: sure.

Confidence: unsure because the standard Ubuntu first-prompt flow appears designed to create exactly this greeting situation, but the brief does not scope the instruction to that launch path.
