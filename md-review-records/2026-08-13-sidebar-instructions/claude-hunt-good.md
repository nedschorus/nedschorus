## Findings

**1. Line 3 — `"This seat is the deliberate exception to it: it owns no pile."`** (also line 20, `"deep history from another pile"`)
"Pile" is load-bearing vocabulary used twice and never expanded here. The pointer that precedes it is framed as `"Read [the seat model](agent-seat-model.md) for how seats work"` — a topical pointer, not a vocabulary pointer — so an agent that already believes it knows how seats work has no signal that it must read that file to learn a defined term. (The sibling briefs are explicit about this: `gatekeeper-instructions.md` says the seat model "defines the words used here — seat, pile, walked approval, instruction-class, slice, the C-numbers".) Harm: an agent guesses "pile" means something loose like "backlog" and mis-reads the whole exception clause on line 3. Confidence: sure the framing differs from siblings; unsure whether that rises to un-executable, since the definition is one click away.

**2. Line 5 — `"You exist so the user never has to ask an off-topic question of a working agent"`**
"Never" is broader than the mechanism can deliver. This seat's existence gives the user somewhere else to ask; it does not prevent him from asking a topic seat anything, and he routinely can and will. Harm: read literally as a guarantee, an agent may treat any off-topic question reaching another seat as a malfunction, or infer that it must intercept such questions — neither of which this file authorizes. This also sits against the project rule in `CLAUDE.md`: "absolute imperatives like 'always' or 'never' can backfire in unforeseen conditions. Use them cautiously." Confidence: sure.

**3. Line 5 vs line 9 — `"Your job is to answer the questions that belong to no topic seat."`** vs `"Small errands with no home: checking a status, reading a file, running a one-off script."`
The bolded job statement is scoped to *questions*; the scope section then admits *errands*, which are actions with no question attached. The two supply incompatible readings of what the seat is for, and the mismatch propagates: line 22's completion criterion is written only in terms of a question being answered. Harm: an agent asked to run a one-off script cannot tell whether that is in scope at all, and if it does the errand it has no stated point at which it is finished. Confidence: sure.

**4. Line 13 vs line 26 — `"The user exits and restarts you freely, and that costs nothing precisely because you were never holding anything."`** vs `"An answer that exists only in this conversation is lost the moment it closes"`
These contradict. Line 13 asserts restart is free because nothing is held; line 26 asserts that unwritten answers are held here and are destroyed on close. Both cannot be true of the same conversation. Harm: an agent that has internalized line 13 will accept a restart mid-thought without first writing down what line 26 obliges it to write, producing exactly the loss line 26 names as this seat's characteristic harm. Confidence: sure.

**5. Line 17 — `"Do not write a handoff at the end of a conversation."`**
The rule carves out exactly one exception — `"If the user asks you to hand off, do it"` — and thereby leaves the involuntary end unaddressed: a conversation that ends because context is exhausted or the session is recycled rather than because the user chose to stop. In that case the default ("do not") applies and nothing is written, even though line 26 may have material the agent was obliged to record. Harm: work that should have reached a topic seat dies with the session, and the agent has an explicit instruction telling it that is correct. Confidence: unsure — the file never mentions recycling, so this depends on a mechanism outside it; I flag it because the rule is stated as covering "the end of a conversation" generally.

**6. Line 18 — `"If a conversation here has grown long and wandered, say so and suggest a restart rather than accumulating."`**
No threshold and no measure for "long" or "wandered" — no turn count, token figure, topic-change count, or observable the agent can check. Harm: behaviour is arbitrary across agents; one suggests a restart after three exchanges, another never does, and neither is violating the instruction. Confidence: sure that the criterion is unmeasurable as written.

**7. Line 19 vs line 9 — `"If a question turns into real project work, do not adopt it"`** vs `"Small errands with no home: checking a status, reading a file, running a one-off script."`
"Real project work" is the sole boundary between the seat's job and what it must refuse, and it is undefined. It directly overlaps the errands line 9 explicitly grants: running a one-off script, reading a file, and checking a status are all plausibly "project work". Harm: two agents draw the line in different places — one refuses errands that belong here, another adopts a design task it should have routed — and the file supports both readings. Confidence: sure.

**8. Line 19 — `"name the seat it belongs to — `gatekeeper`, `sanity-checker`, `skill-builder`, `ghi`, `fleet`, or `doctrine` — and let the user take it there"`**
The list is closed and the instruction assumes a member always exists, but this seat is defined (line 5) as the home for questions that *belong to no topic seat*. The case where such a question turns into real project work is therefore both reachable and, by construction, likely — and in it the instruction cannot be obeyed: there is no seat to name, and the file offers no alternative disposition. Harm: the agent either forces a bad routing to satisfy the instruction, or stalls with no sanctioned move. (`agent-seat-model.md` line 82 does handle this case — work fitting no seat "is either a question for `sidebar` ... or the seed of a new pile, which is the user's decision" — but this file does not carry that route.) Confidence: sure.

**9. Line 19 — `` `ghi` `` and `` `fleet` `` in that same list**
Both are one-part, non-self-documenting names appearing here with no expansion. `ghi` in particular is an opaque three-letter token an agent cannot decode from this file; `fleet` does not say a fleet of what. **10. Line 22 — `"Your work is done when the user's question is answered. There is no larger completion criterion, and none is missing."`**
Contradicted by the next section. Line 26 imposes work that survives the answer: `"Anything you change on disk is committed and pushed"` and `"Anything you learn that a topic seat will need is written where that seat will find it"`. Those are larger completion obligations, so both sentences here are false as written — including the emphatic second clause that forecloses looking for one. Harm: an agent that answered a question and stops, citing line 22, leaves uncommitted disk changes and unrecorded findings behind, and line 22 tells it that is complete. Compounding it, the criterion covers only questions and so gives no stopping point at all for the errands line 9 admits (see finding 3). Confidence: sure.

**11. Line 26 — `"Anything you change on disk is committed and pushed like any other seat's work."`**
"Anything" is broader than can hold. Line 9 sanctions running a one-off script; scripts write logs, temp files, caches, and scratch output that should not be committed. Harm: taken literally the agent commits build artifacts and scratch files; taken with silent discretion the exception has no stated bounds and a real change can be dropped under the same discretion. Separately, this sentence names a push but no target: this seat holds no pile and is restarted freely, so which branch it pushes to — a per-seat branch, a shared one, a fresh one per conversation — is unstated, and line 28 only rules out `main`. Harm: the agent must invent a branch policy for a seat whose whole premise is that it accumulates nothing. Confidence: sure on both.
