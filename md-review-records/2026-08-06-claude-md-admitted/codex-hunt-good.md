1. “This repository is `~/Projects/nedschorus` (NC).” The location is true for this checkout but not inherently for the repository. A future clone or worktree elsewhere makes the statement literally false; `~` also depends on the executing user. This can direct commands toward a different checkout. Confidence: sure.

Confidence: sure about the searchability defect; unsure whether the naming-rule conflict was intended because “etc.” leaves its scope undefined.

3. “read anything there freely” is an absolute authorization broader than its apparent reference-only purpose. An ordinary counterexample is a symlink inside that directory pointing to unrelated material outside it, or an unrelated secret stored in the tree. “Anything” erases that boundary and can cause irrelevant or inappropriate inspection. Confidence: sure.

4. “NOT: write, commit, or run anything there.” “Run anything there” supports incompatible readings: execute files from that repository, execute any command with that directory as its working directory, or execute any command targeting it. Under the latter two readings, harmless reference inspection such as `git -C ~/Projects/nedlern status` or running `rg` from that directory is forbidden, conflicting with “read anything there freely.” The file provides no way to choose among these readings. Confidence: sure.

5. “Use standard SDLC terms.” Neither “SDLC” nor its supposedly standard vocabulary is defined. Different organizations and methodologies use incompatible names and boundaries for requirements, design, implementation, verification, release, deployment, and maintenance. An agent cannot determine which terminology satisfies this command, causing inconsistent artifacts. Confidence: sure.

6. “Write durable artifacts” can mean either that every task must produce an artifact or that artifacts should be durable only when something is written. “Durable” also has no stated lifetime, location, or persistence criterion. This matters for analysis-only or conversational tasks: one reading commands an unauthorized file write, while the other commands none. Confidence: sure.

7. “for a reader with zero context” is an impossible absolute and supplies no stopping point. Every artifact assumes some context, including language, repository access, file formats, and technical vocabulary. An agent can keep adding background indefinitely without reaching literal zero-context comprehensibility. Confidence: sure.

The requirement is also broader than ordinary durable artifacts: a lockfile, checksum manifest, preserved transcript, or raw measurement may be descriptive rather than actionable and may not contain an intrinsic “why.” This can force invented rationale or inappropriate instructions into factual records. Confidence: sure.

9. “Use them cautiously.” No observable behavior distinguishes cautious from incautious use, and no criterion identifies when an absolute is justified. Agents can obey this in mutually incompatible ways—from avoiding every absolute to using them whenever they have briefly considered exceptions. Confidence: sure.

10. “When creating or inventing names, for directories, file names, globals, functions, etc., use explicit, clear and precise multi-part names.” “Etc.” leaves the rule’s scope open, while “multi-part,” “explicit,” “clear,” and “precise” have no defined tests. The unconditional rule is also too broad: an ordinary counterexample is a local loop index named `i`, which can be clearer than a three-part substitute in a short loop, or an externally prescribed one-part entry point such as `main`. This can cause needless verbosity or violations of external interfaces. Confidence: sure.

11. “Check newly invented names with glob (for path names) or grep (for names in files).” This does not define an executable check. “Glob” may mean shell expansion, a library operation, or an unspecified search tool; neither it nor `grep` has a stated search root, pattern semantics, case policy, token boundaries, or treatment of hidden, ignored, binary, generated, and untracked files. These reachable limits permit both missed collisions and irrelevant substring matches. Confidence: sure.

12. “If these checks return collisions or ambiguity” is literally inaccurate. Glob and grep return matches, output, or status; they do not determine semantic ambiguity or namespace collisions. The same textual name can be valid in separate scopes, while a name with no textual match can still be ambiguous to readers. The file supplies no rule for converting search results into either condition. Confidence: sure.

The mechanism leaves no valid outcome when every suitable three- or four-part name remains ambiguous or collides, and it gives no recheck or stopping condition. Confidence: sure.
