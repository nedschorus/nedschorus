## Findings

**1. Line 3 — "This repository is `~/Projects/nedschorus`"**
Taken literally this is an identity claim about a filesystem location, and it is false in any checkout that isn't at that exact path: a clone under a different user account, a CI runner, a `git worktree`, or the same user working from a second copy. An agent that reads this as authoritative and finds itself in `/tmp/build/nedschorus` has no stated way to resolve the mismatch — is it in the wrong repo, or is the file stale? Harm lands when the agent either refuses to proceed or "corrects" its working directory to a path that doesn't exist. `~` also depends on which user's shell expands it, so the sentence's truth varies per invoking account. *Unsure* — if this file is only ever read by one agent on one machine, the claim holds; nothing in the file says that, which is itself the gap.

**2. Line 3 — "(NC)"**
An abbreviation is defined and then never used again anywhere in the file. A reader cannot tell whether "NC" is expected in artifacts the agent writes, whether it is a directory prefix, a commit-message tag, or merely an aside. Harm lands two ways: an agent may start emitting "NC" into filenames or prose on the theory that a defined abbreviation is meant to be used, or a later reader encountering "NC" elsewhere in the project cannot confirm from this file that it means this repository. Separately, "NC" is a two-character token: grepping for it returns matches inside unrelated words and hex, so it is not findable by search — which is exactly what line 7 ("use explicit, clear and precise multi-part names", "3 or 4 parts, not 1 or 2") forbids the agent from doing. The file introduces a name that its own rule would reject. Classes (i) and (a). *Sure.*

**3. Line 3 — "read anything there freely; NOT: write, commit, or run anything there."**
"Run" supports two incompatible readings and the file does not choose between them. Reading A: do not execute programs *that live in* nedlern (don't invoke its scripts or binaries). Reading B: do not execute any command *with nedlern as target or working directory*. Under Reading B the permission granted in the same sentence is unusable — `git log`, `git show`, `rg`, `ls`, and `find` are all commands run against that tree, and they are the ordinary means by which an agent "reads anything there freely." An agent that adopts Reading B is reduced to opening files one at a time by exact path it has no way to discover; an agent that adopts Reading A may execute a legacy build script that writes into the tree, which the prohibition plainly exists to prevent. Harm lands the moment an agent is asked to research anything in the legacy system: the two agents produce opposite behaviour from the same sentence. Classes (a) and (b). *Sure.*

**4. Line 3 — "NOT: write, commit, or run anything there."**
The prohibition enumerates three verbs and leaves reachable mutations unlisted: deleting a file, renaming or moving one, `git checkout` of a different branch, `git stash`, `git reset`, changing file permissions, or editing `.git/config`. None of these is literally "writing" a file or "committing," so a literal reader can perform all of them while believing it is honoring the rule. Whether they are covered depends entirely on which reading of "run" from finding 3 is in force — under Reading A they are all permitted. Harm lands when an agent tidies or re-points the legacy checkout and destroys the reference state the rule was written to protect. Class (g). *Unsure* — the intent is obvious to a human, but the enumeration is what a literal agent will apply.

**5. Line 4 — "Use standard SDLC terms."**
"Standard" has no referent: no glossary, no naming authority, no list, no example, and no source cited in the file. An agent cannot determine whether a candidate term qualifies, and cannot detect when it has violated the rule. The scope is also unstated — does this govern prose in documents, identifiers in code, directory names, commit messages, or all of them? Harm lands whenever an agent must choose a word and cannot tell whether the rule applies or whether its choice satisfies it; the rule then either does nothing or is invoked after the fact to reject arbitrary word choices. Class (d). *Sure* about "standard" and the missing scope. Separately and *unsure*: "SDLC" is itself an unexpanded acronym in a file whose line 5 demands artifacts be written "for a reader with zero context" — I mark this unsure because the acronym is common industry vocabulary a future agent will likely know, but the file holds itself to a stricter standard than it meets here.

**6. Line 4 vs line 7 — "Use standard SDLC terms." / "If the thing you are naming already has a name in the project, use the existing name instead of inventing a new one."**
These give opposite instructions in a case that will certainly arise: the project already uses a non-standard term for something. Line 4 directs the agent to the standard term; line 7 directs it to the existing project name. Nothing in the file says which rule wins. Harm lands when an agent renames an established project concept to a standard term (breaking searchability across existing artifacts), or when a different agent preserves a non-standard term and is judged against line 4. Class (a). *Unsure* — line 4 may be intended to govern vocabulary in prose and line 7 only identifiers, but the file draws no such boundary, and line 7's own list ("directories, file names, globals, functions, etc.") overlaps whatever line 4 covers.

**7. Line 5 — "Write durable artifacts for a reader with zero context"**
"Durable artifact" is not defined and its boundary is where the rule's cost lives. A commit message, a scratch file under `/tmp`, a test fixture, a code comment, a chat reply, and a design document are all plausibly in or out. Harm lands in both directions: an agent that reads the term broadly spends effort restating subject and rationale in throwaway output, and an agent that reads it narrowly ships a document that assumes the conversation. Because the rule states an obligation without a scope, no agent can confirm it has complied. Class (d). *Sure.*

**8. Line 5 — "actionable without the conversation that produced it"**
Applied literally to every durable artifact this is impossible for whole ordinary categories: a reference table, a glossary, a decision record of a path *not* taken, a test-run log, or a meeting summary is not actionable in any sense and cannot be made so without inventing actions that don't exist. Harm lands when an agent either pads such documents with fabricated next steps to satisfy the rule, or blocks on a document it cannot make actionable. The sentence's other two requirements — subject identifiable, why stated — apply cleanly to those categories; this third one does not. Class (c). *Sure.*

**9. Line 6 — "Absolute imperatives like 'always' or 'never' can backfire in unforeseen conditions. Use them cautiously."**
The addressee of "use" is not stated, and the two readings are incompatible. Reading A: when *you write* instructions or documents, avoid absolute imperatives. Reading B: when *you encounter* absolute imperatives, apply them cautiously — i.e. treat them as defeasible in unforeseen conditions. Reading B directly undermines line 3's "NOT: write, commit, or run anything there," which is an absolute prohibition in this same file: an agent holding Reading B is licensed to decide that its present situation is one of the "unforeseen conditions" in which the legacy-repo prohibition would backfire, and write there. Harm lands exactly in the case the prohibition exists for. Class (b). *Sure* that both readings are available; *unsure* which was meant, which is the defect.

**10. Line 6 — "Use them cautiously."**
No criterion is given for what caution consists of, so compliance is unverifiable and the instruction cannot be acted on differently from ignoring it. An agent cannot tell whether writing "never delete the ledger" is permitted caution or a violation. Harm lands when the rule is cited to reject an artifact after the fact, with no standard the author could have applied beforehand. Class (d). *Sure.*

**11. Line 7 — "When creating or inventing names, for directories, file names, globals, functions, etc., use explicit, clear and precise multi-part names. Check newly invented names with glob (for path names) or grep (for names in files)."**
The scope is universal and the "etc." leaves it open-ended, so taken literally the rule covers every identifier an agent creates — including local variables, loop indices, block-scoped temporaries, and parameter names. A loop counter would require a multi-part name and a repo-wide grep before it could be written. That is the ordinary counterexample: a three-line function would trigger several searches and produce identifiers like `outer_record_index_counter`. Harm lands as either wholesale abandonment of the rule (an agent that cannot obey it literally stops treating it as binding at all) or absurd output in routine code. Classes (c) and (f). *Sure.*

**12. Line 7 — "Check newly invented names with glob (for path names) or grep (for names in files)."**
The search scope is unstated. Is the check run over this repository only, or also over `~/Projects/nedlern`, which line 3 establishes as live reference material? Over tracked files only, or including `.git`, build output, and dependencies? The answer changes the result: a name that is clean in NC may collide in the legacy system, and line 3 gives no guidance on whether legacy collisions matter. Harm lands as inconsistent results between agents and as false confidence — an agent reports "no collisions" having searched a narrower tree than the next reader assumes. Class (d). *Sure.*

**13. Line 7 — "If these checks return collisions or ambiguity"**
"Collisions" is determinable from grep or glob output; "ambiguity" is not. Nothing in the file says what makes a name ambiguous, and no search result reports ambiguity. The condition that triggers the entire remedy clause therefore cannot be evaluated for half of its stated cases. Harm lands as arbitrary application: one agent renames because it feels the name is ambiguous, another does not, and neither can be shown wrong. Class (d). *Sure.*

**14. Line 7 — "choose a more explicit name, with 3 or 4 parts, not 1 or 2."**
The remedy has no termination condition. The rule says to re-choose on collision but does not say whether the new name is re-checked, and if it is, what happens when a 4-part name also collides — the ceiling of "3 or 4 parts" leaves no room to escalate further, so the agent is directed to a state it cannot satisfy and given no exit. Harm lands in a crowded namespace: the agent either loops re-checking names, or silently stops applying the rule after one attempt, with the file supporting neither behaviour explicitly. Class (e). *Sure.*

**15. Line 7 — "use explicit, clear and precise multi-part names" vs "with 3 or 4 parts, not 1 or 2"**
The part-count requirement appears only inside the remedy clause that follows a failed check, but the opening sentence states a general requirement with no count. Two readings: every invented name needs 3–4 parts from the start, or 2-part names are acceptable until a check fails. Harm lands as inconsistent naming across a codebase and as disagreement about whether an existing 2-part name violates the rule. Class (b). *Unsure* — the sequential reading is the more natural one, but the opening sentence's "multi-part" is unquantified and a reader may back-fill the "3 or 4" into it.
