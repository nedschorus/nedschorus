## 6. How to give a new agent someone else's handoff

1. **Section heading: "How to give a new agent someone else's handoff"** — This section explains the procedure for starting a new agent session with a handoff document that was written by and for a different agent name, rather than its own.

2. **"The supervisor reads `~/.claude/handoffs/<agent>-handoff.md`, where `<agent>` is the name passed to the launcher — so by default an agent only sees its own."** — The supervisor — the program that starts and oversees an agent session — looks for a handoff file whose name is constructed from the agent's name, in the `~/.claude/handoffs/` directory. The name substituted into that filename is exactly the agent name that was supplied as an argument to the launcher script. The consequence, introduced by the dash: because the filename is derived from the agent's own name, an agent started in the ordinary way is given only the handoff written under its own name and no other.

3. **"Two supported ways around that, both already built:"** — There exist two methods of circumventing that default, both of which are officially supported, and both of which have already been implemented and are available now (as opposed to being proposals).

4. **"**`--first-prompt-file <path>`** — the launcher passes it through to the supervisor, which reads that file as the new session's first prompt and then reverts to ordinary ignition."** — The first method is the launcher's `--first-prompt-file` option, which takes a filesystem path as its value. The launcher does not act on the option itself; it forwards it unchanged to the supervisor. The supervisor then takes the contents of the file at that path and submits them as the very first message of the new session. Having done so, it goes back to its normal startup sequence ("ordinary ignition" — the standard procedure for bringing a session up) for everything thereafter.

5. **"This is the intended mechanism for seeding a session from arbitrary context: point it at another thread's handoff, its dialog extract, or a purpose-written brief."** — This option is the designed-for way of starting a session with any body of prior context one chooses ("seeding," as seeding a process with initial material). Three example targets are given: the handoff belonging to a different thread; the `-dialog-` file holding that thread's conversation excerpt; or a document written specifically to brief this new session.

6. **"**Copy the handoff to the new name** — `cp ~/.claude/handoffs/<old>-handoff.md ~/.claude/handoffs/<new>-handoff.md` before launching `<new>`; its supervisor picks it up as if it were its own."** — The second method is to duplicate the existing handoff file under the filename that the new agent's name will produce, using the shell copy command shown, substituting the old agent's name and the new agent's name. This copy must be made before the new agent is launched. The result: the new agent's supervisor finds a file at exactly the path it expects and treats it as the new agent's own handoff, with no awareness that it originated elsewhere.

7. **"Either way, a handoff written by a *forked* session describes that session's state when it wrote the handoff, not the fork point."** — Whichever of the two methods is used, a caveat applies: when the handoff being reused was authored by a session that had itself been created as a fork of an earlier session, the handoff's account of "where things stand" refers to the moment the handoff was written, which is later than and different from the moment at which the fork was taken.

8. **"When the fork point is what matters, point the new session at the `-dialog-` extract or the transcript instead, and say in the first prompt which part of the history is the subject."** — In cases where the state at the moment of forking is the thing the new session needs, do not use the handoff; instead direct the new session at the conversation excerpt file or at the full transcript, both of which contain the history itself. Additionally, the first prompt given to the new session must state explicitly which portion of that history the new session is meant to be working on, since the file contains more history than is relevant.
