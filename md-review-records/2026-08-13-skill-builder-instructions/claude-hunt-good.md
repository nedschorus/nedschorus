# Findings

**1. Line 3 — "Your pile: **the candidate-skill queue.** Seven proposed skills" vs. line 19 "Plus [#24](…), the **queue-drain procedure**"**
The pile is defined by two mutually inconsistent statements. Line 3 defines it extensionally as seven candidate skills; line 19 adds an eighth item that is explicitly not a skill ("the review process that empties…"). An agent asked "what is in my pile?" gets seven or eight depending on which sentence it reads, and any per-item progress accounting ("the seventh build should be far cheaper than the first") silently excludes #24. Harm lands when the seat reports completion or hands off: #24 is either the most important item in the pile or not in the pile at all, and this file supports both. Sure.

**2. Line 3 — "each a build of the same shape, sharing one authoring checklist and one walk process … the seventh build should be far cheaper than the first"**
Two problems. First, it conflicts with the table's own descriptions: #19 is "filed as a d-review comparison question" (line 16), i.e. an open question, not a build; #17 is "read-only evidence-grounded design". If those are not builds of the same shape, the premise that unifies the seat is false for at least one row, and the agent cannot tell whether it is supposed to build `attack-artifact` or answer a question about it. Second, "the seventh build" asserts that all seven will be built, while line 37 says "Build nothing until he rules — the order is his call"; the user may rule that some are never built. Sure on the #19 conflict; sure on the asserted-seven tension.

**3. Line 7 — "Each has an issue carrying its state"**
"State" is named as the authoritative store for every item in the pile, but the file never says what states exist, where in the issue state lives (label, body field, latest comment, closed/open), how the agent reads it, or whether the agent is expected to update it after a build. It also does not say what to do when an issue and its queue document disagree — a reachable case, since three items have both. Harm: on resumption a fresh agent cannot determine which items are done, in progress, or rejected, which is precisely the information the seat needs to pick up where it left off. Sure.

**4. Lines 11–17 and 37 — the seven GitHub URLs, and "Read [#24](…) … and [#18](…)"**
Every substantive detail of the queue lives behind `https://github.com/nedschorus/nedschorus/issues/N`, and the mandated first action is to read two of them. The file never states how an agent on this machine reads a GitHub issue — no tool, no `gh` invocation, no note that network or GitHub credentials are available, and no fallback if they are not. The checkout's CLAUDE.md does not supply this either (it names only the gatekeeper/push lane). Harm: an agent with no network reaches its very first instruction and is blocked with nothing in the file telling it whether that is expected, fatal, or worked around. Sure that the file does not supply it; unsure how often the environment actually lacks access.

**5. Line 13 "a three-fix escalation stop", line 14 "a five-part finding gate", line 15 "baseline-vs-candidate A/B with trigger cases and raw-count reporting"**
These are capsule names for mechanisms that are never expanded here. #21 at least points to `docs/issues/queue/21-diagnose-failure-test-procedure.md`; #22 and #23 have no detail document and no riders file, so "five-part finding gate" and "raw-count reporting" are terminal dead ends in this file — the reader cannot learn what five parts, or what counts are raw as opposed to what. Harm: if the GitHub issue is thin or unreachable (see finding 4), the agent must invent the gate and will not know it invented it. Sure.

**6. Line 16 — "filed as a d-review comparison question"**
"d-review" appears once, is never defined, and sits thirteen lines from "md-review" (line 29), which is defined by use. A reader cannot tell whether "d-review" is a distinct project process, a typo for "md-review", or a document-review abbreviation. "Comparison question" compounds it: comparison of what against what is never said. Harm: #19 is the one row whose *disposition* (build it vs. answer it) hinges on this phrase, so the ambiguity blocks the only action the row calls for. Sure. (The term does occur elsewhere in the checkout, but this file gives no pointer, so it is unresolvable from the stated context.)

**7. Line 19 — "the review process that empties the wiki queue, the pair queue, and the draft-label issue queue"**
Three store names introduced, none defined: the reader is told none of what a "wiki queue" is, where the "pair queue" lives, or what a "draft-label" is. None of the three is the "candidate-skill queue" of line 3. Harm: the agent is told to read #24 early because it governs its work, but cannot tell from this file whether the drain touches its own pile at all. Sure.

**8. Line 19 — "It governs how the rest of this pile is worked, so read it early."**
This contradicts the preceding clause in the same sentence. #24 is described as emptying three named queues, none of which is this pile; then it is asserted to govern this pile. Either the description of #24's scope is wrong or the governance claim is. It also collides with the "How skills are built here" section (line 23), which names a *different* governing standard — the skill-authoring checklist. The file never says which one controls when they differ. Harm: two claimed governing procedures with no precedence rule means two agents can work the same pile by different rules and both be compliant. Sure.

**9. Line 3 / 5 / 7 / 19 — "queue" used for five different things**
"the candidate-skill queue" (3), the section heading "The queue" (5), "a queue document" (7), "the wiki queue, the pair queue, and the draft-label issue queue" (19), and "queue-drain procedure" (19) — plus the on-disk directory `docs/issues/queue/` the riders files live in. A bare "the queue" in this file or in any successor's writing has at least five referents. Harm: this is the word an agent will grep for to find its own work, and the grep is useless; a handoff sentence like "drain the queue" is unfollowable. This also sits badly against CLAUDE.md's naming rule ("If these checks return collisions or ambiguity, choose a more explicit name, with 3 or 4 parts, not 1 or 2"). Sure.

**10. Line 9–17 — table row order (#18, #20, #21, #22, #23, #19, #17)**
The rows are not in issue-number order and no ordering principle is stated, while ordering is the exact thing the first action asks the agent to reason about. A reader can equally conclude the table is a priority ranking, a rough grouping, or arbitrary. Harm: an agent proposing a build order may present the table's sequence as a recommendation that was never intended as one. Unsure — this is an inference from layout, and the ordering may be meaningful in a way the author simply did not write down.

**11. Line 23 — "Find the **skill-authoring checklist** under `docs/` and follow it"**
No path and no filename are given, only a directory root containing six subtrees. The file also states no criterion for recognising the right document, no branch for "not found," and no branch for "more than one candidate matches." Harm: the agent must guess, and a guess that lands on a superseded draft is indistinguishable from success — the instruction is "follow it", so a wrong hit propagates into every build the seat makes. (The document does exist, at `docs/wiki/queue/skill-authoring-checklist.md` — inside a queue directory, i.e. in material a drain procedure may move.) Sure.

**12. Line 23 — "reading two of them closely is the cheapest way to learn the house style"**
Four skills are listed and the agent is told to read "two", with no basis for choosing which two and no reason the number is two rather than one or four. Obeyed literally, the choice is arbitrary; the two chosen may both be atypical of the house style the sentence promises to teach. Unsure whether the author intended a binding count or a rough suggestion — which is itself the ambiguity.

**13. Line 27 — "A skill is instruction-class."**
The term is introduced in bold as the load-bearing premise of the rule that follows, and is never defined. The reader cannot tell whether "instruction-class" is a formal category with a defined membership test (which files are in it?), a label attached elsewhere, or shorthand for "counts as instructions." Harm: the agent cannot determine whether a *supporting* file it writes — a reference doc under the skill directory, a test fixture, an example — is instruction-class and therefore gated. Sure.

**14. Line 27 — "a `.walk-approved` marker quoting his approval, consumed by the one write it approves"**
The mechanism is asserted but not operable from this file: it does not say who creates the marker, where it lives (repo root? beside the target file? a fixed path?), what "quoting his approval" must literally contain to satisfy the hook, or where the `instruction-file-guard` hook is configured so a blocked agent can read the rule it tripped. Harm: the agent hits a mechanical block on the one action the seat exists to perform — writing a skill — with no stated way to produce the thing that unblocks it, and no stated failure behaviour if the marker is malformed or stale. Sure.

**15. Line 27 — "consumed by the one write it approves"**
A skill in this project is a directory, not a file — the four worked examples named on line 23 are directories (`.claude/skills/walk-me-through/` etc.), which means landing one skill is several writes. A marker that is consumed by *one* write therefore cannot cover a skill, yet the sentence presents it as the mechanism by which "a skill … lands". The file never says whether a separate walk and marker are needed per file, whether one approval can be re-used, or what happens to the remaining files after the first write consumes the marker. Harm: the agent gets one file through the gate and is then blocked mid-skill, with the repository left holding a partial skill. Sure.

**16. Lines 27, 29, 37 — "It lands only through the user's walk" / "a settled skill draft gets an md-review before it lands" / "a skill is walked before it lands"**
Three gates are attached to the same undefined verb "lands" and never ordered. Walk-then-md-review and md-review-then-walk are both consistent with this text, and they are not interchangeable: if md-review comes second and produces edits, those edits were not in the text the user approved, and the file says nothing about whether the `.walk-approved` marker survives them. Nor is "lands" ever defined — the checkout's CLAUDE.md adds a further step this file never mentions ("commit to the working branch, push it, and the user's Mac-side agent reviews and merges"), so the agent has no statement of what finishing a build actually consists of or when it may stop. Harm: the seat's terminal condition is undefined, and the most likely failure is a completed skill sitting unpushed or an approval invalidated by the review that was supposed to precede it. Sure.

**17. Lines 28–29 — "**Zero-context readability is the bar.** The user ruled 2026-08-11 that agents must understand their instructions cold" vs. CLAUDE.md line 5**
CLAUDE.md defines the standard as: "Write durable artifacts — committed files, issue bodies, commit messages — for a reader with zero context: the subject identifiable, the why stated, usable without the conversation that produced it." This file restates the same standard under a new name with a different scope (agents understanding *their instructions*, rather than a reader of *committed artifacts*) and a different justification (a dated user ruling rather than a project rule). The two are close enough to look like one rule and different enough to diverge: CLAUDE.md's version requires "the why stated", while line 28 of this file directs the opposite for skills — "Rationale asides get cut". An agent trying to satisfy both on a skill file receives contradictory guidance about whether to state the why. Sure the two definitions coexist; unsure whether the author considers the rationale-cutting rule an intentional carve-out, because the file does not say.

**18. Line 29 — "a settled skill draft gets an md-review"**
"Settled" is the trigger condition for the review step and has no criterion. Nothing states who declares a draft settled, or what evidence settles it, so the iteration loop before md-review has no stopping point — an agent can revise indefinitely, or call the first draft settled, and neither is contradicted by this file. Sure.

**19. Line 33 — "may add a reviewer to the md-review grid"**
"md-review grid" is undefined and unlocated: not a path, not a link, no statement of what a grid row or a "reviewer" is in it. Harm: this sentence is the boundary marker telling the agent what is *not* its business, and the agent cannot recognise the thing it must not touch. Sure. (The phrase exists elsewhere in the checkout, including in `docs/agents/agent-seat-model.md`, which line 3 does link — but this sentence gives no pointer, so from this file it is opaque.)

**20. Line 33 — "PRs #51 and #53 are its business."**
Bare numbers with no links, no repository named, and no statement of what they contain — in a file where all eight issue references carry full URLs, so the reader cannot even infer the same repo with confidence. Nor is any action attached: "are its business" does not say whether the agent should avoid touching them, read them for context, or expect its own work to conflict with them. Harm: a boundary that cannot be checked is not a boundary; the agent either ignores it or wastes effort guessing. Sure.

**21. Line 33 — "If a skill you are building would change how reviews are delivered, hand that part over rather than deciding it here."**
Two defects. (i) "Hand that part over" names no mechanism and no recipient address — comment on the issue, file a new issue, message the seat, leave a note? Nothing in this file says how one seat hands work to another, so the instruction cannot be executed as written. (ii) The rule collides with the pile itself: #22 `review-change` ("exact-revision defect-first review with a five-part finding gate"), #19 `attack-artifact` ("isolated adversarial review"), and #24 ("the review process that empties…") are review procedures. Building them *is* deciding how reviews are delivered. The file gives no test separating "review methodology owned by `sanity-checker`" from "review skills this seat builds", so the agent either hands over most of its own pile or ignores the rule. Sure.

**22. Line 11 "**flagged as the likely first build**" vs. line 37 "tell the user which skill you propose building first and why … the order is his call"**
The table pre-announces an answer to the question the first action asks the agent to form independently, with no attribution (flagged by whom, when, on what basis) and no statement of whether the flag binds. Two readings: the agent's proposal is a genuine judgement, or it is a rubber stamp on a decision already made. Harm: a fresh agent reports #18 as its recommendation on the strength of this line alone, and the user receives a recommendation with no reasoning behind it — the very thing the "and why" was meant to produce. Sure.

**23. Line 37 — "Build nothing until he rules"**
"Build" has no boundary here. Drafting a SKILL.md in the working tree, sketching a checklist, writing a test — an agent can read any of these as building or as preparation, and the file supports both. Given that the file elsewhere makes writing an instruction file mechanically gated (line 27), the intended line is probably "no writes to `.claude/skills/`", but that is not what the sentence says. Harm: either the agent idles when it could be preparing, or it produces artifacts the user considers pre-empting his ruling. Sure that the boundary is unstated; unsure which side the author intended.

**24. Line 37 — the file ends at the user's ruling**
The instruction sequence terminates with "Build nothing until he rules", and nothing states what happens next: no build procedure beyond "find the checklist and follow it", no statement of what the agent does after the ruling, no re-entry point for a later session that finds a ruling already made in a conversation it cannot see. Harm: this is a seat file meant to be read cold by a successor; a successor that arrives after the ruling has no instruction that applies to it, and the natural fallback is to re-ask a question the user has already answered. Sure.

clean sections: none — the intro (line 3), "The queue", "How skills are built here", "Related work you did not do", and "First action" each carry at least one finding.
