## Title block and lead (before the first `##` heading)

1. "How agents work with GitHub issues (GHIs) in nedschorus: a long-lived knowledge agent over the issue corpus, a script-maintained local mirror, a write-path tool with hooks that route raw writes through it, and the `ghi-write` skill carrying the judgment none of the machinery can." — This document's subject is the manner in which AI agents in the nedschorus project deal with GitHub issues (abbreviated GHIs throughout). It names the four parts of that arrangement: (a) an agent whose job is knowing things, which persists across many questions rather than being spun up per task, and whose subject matter is the whole set of issues taken together; (b) a copy of the issue data stored on the local machine, kept current by scripts rather than by any agent; (c) a piece of software that performs issue writes, together with hook configuration that intercepts unmediated `gh` command-line writes and redirects them into that piece of software; (d) a skill file named `ghi-write` that supplies the discretionary decision-making that no script, tool, or hook is capable of supplying.
2. "Decision trail: this file's design decisions were ruled 2026-08-07 (walk anchor with per-item dispositions: ghi-info-agent-plan-draft.md)" — Provenance statement: the design choices written in this file are not proposals; the user decided them on 7 August 2026. The document that served as the agenda for that walk, and which records what was decided for each individual item, is `ghi-info-agent-plan-draft.md` in the same directory.
3. "the rejected single-gate direction is preserved at ghi-gatekeeper-plan-draft.md" — There was an alternative design in which issue writes would pass through one single controlling gate; it was rejected. Rather than being deleted, that rejected design is still kept on disk at `ghi-gatekeeper-plan-draft.md`.
4. "The organizing idea: instead of building a vector or graph database of the GHIs, we use a modern agent — the corpus fits in its context window." — The single choice from which the rest of the design follows: the project does not build retrieval infrastructure over the issues (neither an embedding/similarity search store nor a database of issues-as-nodes-and-links). It instead relies on a current-generation LLM agent to do the retrieving and relating. The justification given is a size fact: all the issues together are small enough to be held in that model's context window simultaneously.
5. "Mechanical work never spends agent tokens: scripts fetch, format, measure, and filter for free" — Second organizing rule: any work that can be done by deterministic code is done by deterministic code and therefore consumes no model inference. The four named categories of such work are retrieving issue data from GitHub, arranging it into the file format, counting/measuring things such as lengths, and selecting subsets. "For free" means free in agent tokens (and by implication in money and latency of inference), not literally costless.
6. "the agent spends tokens only on judgment." — The corollary: model inference is reserved for decisions that require assessment or discretion, and nothing else.

## What ghi-info is

1. "The first build of the domain-knowledge-agent class defined in 26-dynamic-agent-team-model.md ("the GHIs" is that class's first listed domain)." — `ghi-info` is the first concrete instance to actually be constructed of a general category of agent — agents that own knowledge of one domain — where that category was specified in issue-pair MD file `26-dynamic-agent-team-model.md`. The parenthetical supports the choice of which one to build first: in that document's own list of domains such agents would cover, the GitHub issues appear first.
2. "It has three duties:" — `ghi-info`'s responsibilities are exactly three in number, enumerated below. (I read "duties" as the exhaustive list of what it is responsible for, which the later out-of-scope paragraph confirms.)
3. "**Answer asks.** Another agent, before filing or editing an issue, asks what it should read." — Duty one, named "answer asks": some other agent, at the point where it is about to create a new issue or modify an existing one, poses a question to `ghi-info`, and the substance of that question is which existing issues that other agent ought to go read first.
4. "The answer is a bare list — "read #13, #24, #31" — no why-lines, no summaries." — What comes back is only issue numbers, formatted as a short instruction to read them. Explicitly excluded: any accompanying line explaining why each issue was chosen, and any condensed restatement of what those issues say.
5. "Pointers fail visibly (a bad one costs one read); prose syntheses fail invisibly and make the agent a second author." — The rationale, framed as a comparison of failure modes. If `ghi-info` returns a mere reference and that reference is wrong, the mistake is detectable by the recipient the moment it opens the issue, and the total damage is the wasted effort of reading one issue. If instead `ghi-info` returns its own written summary of the issues and that summary is wrong, the recipient has no way to detect the error, because it never sees the original; and additionally `ghi-info` has thereby become a co-writer of whatever the recipient produces, inserting its own wording into a document it is not responsible for.
6. "Motivation lines are noise to an agent that will read what it is told." — A further reason to omit explanations: the recipient is an agent that will comply and read the referenced issues regardless, so text explaining why it should is content that adds nothing while consuming context.
7. "**Maintain the reference graph.** Cross-links between issues, and link integrity across the issue–MD boundary in both directions: every GHI→MD reference resolves; every pair MD backlinks its correct GHI(s)." — Duty two: `ghi-info` looks after the network of references. That comprises links from one issue to another, plus the correctness of links crossing between issues and markdown files in the repo, checked in both directions. The two directions are spelled out: every link written inside an issue that points at an MD file must point at a file that actually exists (and, I take it, at the right one); and every "pair MD" — the repo markdown document paired with a particular issue — must contain a link back to the issue or issues it belongs to, and that backlink must be to the correct issue.
8. "Cross-link edits are ghi-info's only write class." — The single category of modification `ghi-info` is permitted to make anywhere is adding/changing/removing cross-references. It writes nothing else.
9. "**Adjudicate writes.** The write-path tool (below) consults ghi-info with the actual draft body before an issue write lands." — Duty three: judging proposed writes. The mechanism is that the tool described later in this document sends `ghi-info` the full proposed text of the issue body — not a summary or a title, the real draft — and does so before the write reaches GitHub.
10. "Verdicts: **too similar** to an existing GHI (duplicate, overlapping, conflicting) — the write is refused with a reconsider-and-read reply" — `ghi-info` returns one of three rulings. Ruling one: the draft is too close to an issue that already exists — where "too close" covers the draft being the same issue, the draft partially covering the same ground, or the draft asserting something that contradicts the existing issue. Consequence: the write does not happen, and the writer is sent back a message telling it to think again and pointing it at what to read.
11. "**related but compatible** — the write proceeds, and the reply tells the writer which GHIs to familiarize itself with" — Ruling two: existing issues bear on the draft but do not conflict with or duplicate it. Consequence: the write goes through, and the writer additionally receives a list of issues it should read so as to be informed about the surrounding context.
12. "**unrelated** — plain write." — Ruling three: no existing issue bears on the draft. Consequence: the write happens with nothing added.
13. "Everything else is out of scope: ghi-info never decides routing (queue vs GHI vs pair vs bare MD — `ghi-write`'s judgment), never writes issue or MD substance, and answers only from the issue corpus — asked about the wiki or the code, it says so rather than guessing." — Beyond those three duties, `ghi-info` does nothing. Three specific exclusions: (a) it does not decide where a given piece of content should be recorded — the four candidate destinations being the project's queue, a GitHub issue, an issue-plus-MD pair, or a standalone MD file with no issue — because that decision belongs to the `ghi-write` skill; (b) it does not author the actual content of issues or of MD files; (c) its knowledge base is the issues only, so if someone asks it about the project wiki or about the source code, the correct response is to state that this is outside what it knows, rather than to produce a plausible answer from inference.
14. "For MD content that has drifted stale relative to its issue, and for issue bodies grown past the length limit while nobody was writing, ghi-info **flags and never fixes**: the repair belongs to the next agent with authoring context." — Two named defect types: an MD file whose content no longer matches the current state of its paired issue, and an issue body that has become longer than the allowed limit through accumulation rather than through any single write (so no write-time check caught it). For both, `ghi-info`'s action is limited to reporting the problem; it must not correct it. The reason: correcting either requires knowing the subject matter well enough to rewrite it, and that knowledge sits with whichever agent next works on that material for authoring reasons.

## The mirror

1. "A local MD mirror of the issue corpus, maintained entirely by script — the agent never fetches, paginates, or formats." — The mirror is a set of markdown files on the local machine that reproduce the content of all the issues. Keeping them current is done wholly by scripted code. Three things the agent consequently never does: call GitHub to retrieve data, work through multi-page API result sets, or convert raw data into the file format.
2. "GitHub is the source of truth; the mirror is derived data." — Where the two disagree, GitHub is right by definition. The mirror has no authority of its own and can always be thrown away and rebuilt from GitHub.
3. "**Two files, split by state**: `issues-open.md` — every open issue near-raw (number, title, labels, updated time, body, comments); `issues-closed.md` — one tiered line per closed issue." — The mirror consists of exactly two files, and the criterion dividing them is whether an issue is open or closed. The open file holds all currently-open issues with almost no processing applied — listing the fields kept: issue number, title, labels, the last-updated timestamp, the full body text, and the comments. The closed file holds one line per closed issue. "Tiered" is genuinely ambiguous to me: reading (a) is that the amount of detail packed into that one line varies by tier, e.g. more recently or more relevantly closed issues get a fuller line than old ones; reading (b) is that closed issues are sorted into tiers/groups and the line records which tier the issue is in. The later cuts-table phrase "mirror tiering answers it" (about old closed issues weighing on context) fits reading (a) better, so that is the reading I take.
4. "The split encodes the workflow default in the file layout: routine relatedness checks grep the open file only; the closed file joins in exactly two cases — an absence claim (a "no issue covers X" receipt is invalid unless both files were searched; was-tried-and-rejected lives in the closed file) and an explicit precedent hunt." — Putting open and closed issues in separate files is a way of building the normal behavior into the physical arrangement of the data rather than stating it as a rule. Normal behavior: when checking whether a new thing relates to existing issues, one searches only the open file. The closed file is searched in two situations and no others. Situation one: asserting that nothing exists on some topic — because a claim of the form "there is no issue covering X," offered as evidence, does not hold up unless both files were checked; the reason is that a topic that was raised and then dismissed will be recorded in a closed issue. Situation two: deliberately looking for what has been decided or attempted before on some matter.
5. "Closed GHIs are useful in perhaps one grep in fifty; the path, not an instruction, keeps them out of the other forty-nine." — An estimated frequency: roughly 2% of searches genuinely need closed issues. The design point: what keeps closed issues out of the remaining 98% of searches is the file path itself (searching the open file simply does not reach them), rather than a written instruction telling agents not to search them — the mechanism does the work instead of relying on compliance.
6. "**Home**: a gitignored conventional path in any checkout, regenerated by script on any machine." — Where the mirror files live: at a fixed, agreed-upon location relative to any clone of the repository, with that location listed in `.gitignore` so the files are never committed. On any given machine the files are produced by running the script.
7. "Derived churn never enters git history." — Because of the above: the constant changes to these generated files produce no commits, so the repository's history is not filled with them.
8. "**Delta refresh**: one `gh` search call (`updated:>` the mirror's newest entry) re-fetches changed issues and moves entries between the two files on state change." — Bringing the mirror up to date costs a single call to the GitHub CLI: a search whose filter is "updated after the most recent update timestamp already present in the mirror." That call returns the issues that have changed since then; those are re-downloaded and rewritten, and if an issue's open/closed state has changed, its entry is relocated from one mirror file to the other.
9. "Verified 2026-08-07 against the live repo: full pull of all 45 issues with bodies took 0.82 s (~109 KB); the `updated:>` filter returns exactly the issues touched since a timestamp." — Empirical check performed on 7 August 2026 against the actual repository, not a hypothetical. Two results: downloading every one of the 45 issues including full body text took 0.82 seconds and produced about 109 kilobytes of data; and the `updated:>` search filter behaves as assumed, returning precisely the set of issues modified after the given time (no extras, no omissions).
10. "A second feed — git log since last run — covers pair-MD edits, which touch no issue timestamp and are otherwise invisible." — There is an additional input to the refresh besides the GitHub search: the repository's commit log for commits since the previous refresh. This is needed because editing an issue's paired MD file changes nothing on GitHub, so the issue's updated timestamp does not move, and the GitHub-side feed would never reveal that the pair changed.
11. "**Currency made legible**: agents cannot infer what is relevant now versus before, so the mirror states it — each entry carries its updated time plus an activity-relative freshness (how much of the project has moved since this issue last did; project activity, not calendar time, is the aging clock)." — Premise: an LLM agent has no reliable sense of time and so cannot work out on its own whether a given issue is still current or has been overtaken. Response: rather than expect the agent to infer it, the mirror writes the information down explicitly. Every mirror entry therefore carries two things: the timestamp of the issue's last update, and a measure of freshness expressed relative to project activity — meaning a quantity capturing how much work has happened elsewhere in the project since this particular issue last changed. The parenthetical states the principle: staleness is measured in units of project progress, not in days elapsed, so an issue untouched for a month during a quiet period is not as stale as one untouched for a week during an active period.
12. "Supersession is an explicit marker naming the successor, written at change time by the agent that knows; the marker is a grep-able pattern, so two open issues claiming the same ground with neither naming the other is a mechanically flaggable defect." — When one issue replaces another, that fact is recorded as a distinct textual marker that identifies which issue is the replacement. It is written at the moment the supersession happens, by whichever agent is making the change, because that agent is the one that actually knows the relationship. Because the marker is a fixed text pattern that a search can find, it becomes possible for a script (with no judgment involved) to detect a specific defect: two issues both open, both covering the same subject, and neither containing a marker pointing at the other.

## The session

1. "**Seat**: the Ubuntu box (`~/agents/ghi-info` per the box convention), where agent workload is being consolidated." — Where `ghi-info` runs: on the project's Ubuntu machine, in a directory named for the agent under `~/agents/`, which is the existing naming convention on that machine for agent working directories. Stated reason: agent workloads generally are being moved onto that machine.
2. "Mac-side callers reach it over SSH, the path the launch-claude work built." — Agents or scripts running on the user's Mac invoke it remotely via SSH, using the remote-invocation mechanism that a previous piece of work in this project (referred to as "the launch-claude work") already built.
3. "**Lifecycle**: active only while taking a turn, otherwise exited — a session id, transcript, and the mirror persist; no process does." — `ghi-info` exists as a running program only for the duration of answering one question; when the answer is delivered, the process ends. What survives between questions is data on disk: the identifier used to resume the conversation, the recorded conversation transcript, and the mirror files. Nothing is left running.
4. "There is no idle state for a headless resume-per-question agent; idle describes a live waiting process (an interactive session, a watcher), which this is not." — A terminological clarification: it is a category error to speak of this agent being "idle." "Idle" properly applies to a process that is running and waiting for something — an interactive session waiting for a human to type, or a watcher waiting for an event. `ghi-info` runs without a terminal UI and starts fresh-from-transcript for each question, so between questions it is not waiting; it does not exist.
5. "**Context policy**: 100% open-focused." — The rule governing what goes into the agent's context window: it is oriented entirely toward currently-open issues.
6. "A cold start loads `issues-open.md` whole; closed issues enter a turn only by grep on demand." — When a new session begins with no prior transcript, the entire open-issues mirror file is read into context. Closed issues never get loaded wholesale; they appear in a turn only when a specific text search is run against the closed file because that particular question required it.
7. "**Recycling**: a resumed session's context drifts — the mirror updates every turn, but issues loaded while open linger in context after they close, and the agent cannot notice." — Naming the problem that motivates restarting sessions. When a session is resumed repeatedly, what it holds in context gradually diverges from reality. Specifically: the mirror files on disk are refreshed before each turn, but the text of an issue that was read into context back when it was open stays in context unchanged after that issue has since been closed, and there is nothing in the agent's inputs that would let it detect this — it will keep treating the issue as open.
8. "The wrapper therefore clears and reloads on the first of three script-observable triggers: a closes-since-session-birth counter passing its threshold; the stale-match rate from the answer post-check (below); transcript size." — Because of that, the wrapper script discards the accumulated session and starts a fresh one with newly loaded data. It does so as soon as any one of three conditions is met — three conditions all of which a script can evaluate without any agent judgment. Condition one: counting how many issues have been closed since the current session was created, and finding that count above a configured limit. Condition two: the proportion of answers found to contain pointers to closed issues, as measured by the check on outgoing answers described later. Condition three: the transcript having grown beyond some size.
9. "All three are config constants tuned in live use." — The three threshold values are settings, not hard-coded values, and the intent is to adjust them empirically once the system is running rather than to get them right in advance.
10. "Refreshing is fast and cheap — sub-second fetch, one load turn — so recycling errs eager: an eager recycle costs one cheap reload, a lazy one costs silently wrong answers." — Because starting over costs little (the data fetch takes under a second, and the reload occupies a single turn), the thresholds are deliberately set so that unnecessary recycles happen more often than missed ones. The asymmetry justifying that: recycling when you did not need to costs one inexpensive reload; failing to recycle when you should have produces answers that are wrong in a way nobody notices.

## The ask

1. "One wrapper script, run by any agent (and by `ghi-write` step 1)." — The interface for asking `ghi-info` a question is a single script. Any agent may run it. In particular, the first step of the `ghi-write` skill's procedure is to run it.
2. "In order: delta-refresh the mirror (free, so the agent always wakes current)" — First of the script's sequential steps: bring the mirror up to date. Since this costs no model tokens, there is no reason to skip it, so the agent's context is never built from stale files.
3. "resume by stored session id, or cold-start when none exists or a recycle trigger has fired" — Second step: continue the previous conversation using the saved session identifier. Two conditions divert to starting a brand-new session instead: there is no saved identifier (first ever run, or it was discarded), or one of the three recycle triggers described above has fired.
4. "prompt = the question, plus the changed-issue numbers since the last turn on resume" — Third step: construct the text sent to the agent. It consists of the asker's question; and, in the resume case only, additionally the numbers of the issues that have changed since the previous turn, so the agent is told explicitly which parts of what it already holds are out of date.
5. "**post-check the answer** — a returned pointer to a closed issue is filtered out with a note before the asker sees it (repairing the answer immediately; the rate of such filtered pointers is recycle trigger two)" — Fourth step: inspect the agent's output before returning it. If the answer references an issue that is in fact closed, that reference is removed and a note is put in its place, and this happens between the agent producing the answer and the asker receiving it. Two effects noted: the individual answer is corrected on the spot; and the frequency with which this filtering has to happen is exactly the "stale-match rate" that serves as the second recycle trigger.
6. "print the bare list." — Fifth step: emit the resulting list of issue numbers and nothing else.
7. "One overall timeout; a killed run is a named failure." — There is a single time limit applied to the whole invocation (rather than separate limits per stage). If the run exceeds it and is terminated, that outcome is reported as a specific, identified failure mode rather than being silently swallowed or reported as an empty answer.
8. "Auth is the box's long-lived token (interactive logins expire with no human to refresh them)." — Authentication to whatever services the script needs uses a long-lived token stored on the Ubuntu machine. Reason given: a credential obtained by a human logging in interactively will eventually expire, and since this runs unattended there is nobody present to log in again.
9. "The mechanics are proven, not hypothetical: nedsmessenger runs this exact pattern live (`~/Projects/nedsmessenger/adapter/adapter.py`, `ask_claude` — headless `claude -p --resume` per conversation, answer off the exit stream, watchdogs on stuck runs)." — The whole ask mechanism described above is not a speculative design; another project of the user's, nedsmessenger, already operates the same pattern in production. The specifics of that precedent: it lives in `adapter.py` in the `ask_claude` function; it invokes Claude Code non-interactively with `-p` and `--resume` once per conversation; it takes the answer from the output the process emits as it exits; and it has watchdog timers to handle runs that hang.
10. "**A failed ask never blocks a write.**" — Design rule: if the attempt to consult `ghi-info` does not succeed, that failure must not prevent the issue write from going ahead.
11. "The fallback ladder: ask → grep the mirror → `gh` search; then proceed under the ordinary rules." — The ordered set of degradations. First choice is asking `ghi-info`. If that fails, run a text search over the mirror files directly. If that fails too, run a GitHub search via the CLI. If all of them fail, carry on and write the issue following the normal conventions with no relatedness information at all.
12. "Bad pointers fail visibly; the missing-pointer residual is accepted under the cooperative posture." — Restating the earlier asymmetry and drawing the consequence for accuracy. Wrong references get caught because the recipient reads them. What is left over as unaddressed risk is the opposite error — relations that exist but were never pointed out — and the design consciously accepts that residual risk, on the grounds that the participants are cooperating agents rather than adversaries who must be constrained.
13. "Self-correction needs no feedback channel: a writer who finds a relation ghi-info missed adds the cross-link while editing, and the next delta refresh teaches the corpus." — There is no need to build a mechanism by which askers report back to `ghi-info` that its answer was incomplete. The system fixes itself through ordinary work: an agent that discovers a connection `ghi-info` failed to mention will write that connection into the issue as a cross-link in the course of the editing it was doing anyway; the next mirror refresh picks that edit up; and from then on the connection is present in the data `ghi-info` reads, so it will not be missed again.

## The write path

1. "Agents write issues with `gh` exactly as trained; the machinery makes the right thing happen without asking them to change:" — Agents are not asked to learn a new interface. They continue issuing GitHub CLI commands the way their training disposes them to. The interception machinery is what converts those ordinary commands into the desired behavior, so no change in agent habit is required.
2. "**Create and edit**: a PreToolUse hook rewrites the `gh issue create`/`edit` invocation into the project write tool (`updatedInput` — the rewrite-and-execute mechanics and the 600 s configurable command-hook timeout verified 2026-08-07 against https://code.claude.com/docs/en/hooks)." — For the two commands that create an issue and that modify an existing one: a hook that runs before the tool call executes replaces the intended command with an invocation of the project's own write tool. The technical means is the hook's `updatedInput` facility. Parenthetical verification note: on 7 August 2026, two things were checked against the official Claude Code hooks documentation — that a hook can indeed rewrite a call and have the rewritten version execute, and that command hooks have a 600-second timeout which is configurable.
3. "The tool runs the mechanical checks (body length; openable references), consults ghi-info with the draft body (the adjudication above), writes via `gh` internally, and replies in a form that cannot confuse an agent that believes it ran `gh`." — Four things the write tool does, in order. It performs the checks that require no judgment — specifically measuring the body's length and confirming that references in the body can actually be opened/resolved. It sends the draft body to `ghi-info` for the three-way verdict described in the duties section. It then performs the actual write by calling `gh` itself. And it returns output shaped so that the calling agent — which thinks it ran `gh` directly and never learned otherwise — is not thrown off by the response.
4. "Fail-open: ghi-info unreachable means the write proceeds unchecked." — The failure policy is permissive rather than restrictive: if `ghi-info` cannot be contacted, the tool does not refuse or wait; it completes the write without the similarity adjudication having happened.
5. "**Length and the lean-split**: no agent counts words — the tool measures the body after the write." — On enforcing body length. Agents are not asked to judge or count length themselves. The tool does the measurement, and it does so after the write has already been committed, not as a precondition for it.
6. "Over the limit, the writer is told immediately: keep a good summary in the body, move the substance to the linked pair MD (create or update it)." — If the measurement shows the body exceeds the limit, the writing agent is informed right away (in the same turn, so it can act while still holding the context). The instruction it receives is the remedy: leave a genuinely useful condensed version in the issue body, and relocate the detailed content into the MD file paired with that issue — creating that file if it does not yet exist, or adding to it if it does.
7. "The writer holds the authoring context, so the writer does the split; corpus breadth comes from asking ghi-info what to link." — Rationale for who performs the split: the agent that wrote the text is the one that understands it well enough to decide what is summary and what is detail. What that agent lacks — knowledge of the rest of the issue corpus — is supplied separately, by asking `ghi-info` which other issues the new material should link to.
8. "Issue bodies stay lean summaries-plus-links; the meat lives in grepable repo MDs — one kind of document, at two depths." — The resulting shape of the corpus. GitHub issue bodies are short: a summary plus references. The detailed content sits in markdown files in the repository, where it can be found with text search (which is the property that matters, as opposed to being on GitHub). The closing clause says these are not two different genres of writing; they are the same kind of prose document, differing only in how much detail each carries.
9. "**Comments**: `gh issue comment` is denied with a teaching reply, because a comment cannot be mechanically rewritten into the body edit the revision convention requires — where the content lands, and what it supersedes, only the commenting agent knows." — Attempts to add a comment to an issue are blocked, and the block returns a message that explains what to do instead rather than merely refusing. The reason this one cannot be silently rewritten like create/edit can: the project's convention is that new information should be folded into the issue body as a revision, and converting a comment into such a revision requires two judgments no script can make — which part of the body the new text belongs in, and which existing statement it replaces. Only the agent that wrote the comment knows those.
10. "The reply teaches both paths: integrate into the body by edit, or — for the genuinely new events the convention permits — resubmit through the tool's comment verb, which requires an event kind from the fixed catalog (instance outcome, completion, ruling challenge; growth only by explicit ruling)." — The refusal message presents two legitimate routes. Route one: edit the issue body to incorporate the content. Route two, applicable only when the content records an actual new occurrence (a case the revision convention does allow to be a comment rather than a body edit): resubmit it using the write tool's own comment operation, which will only accept it if the agent labels it with one of a closed list of event types. That list currently has three entries — the outcome of some particular instance of the thing the issue is about, a completion, and a challenge to a previous ruling — and the list is not to be extended except by an explicit decision from the user.
11. "One lost turn per attempt, accepted." — The acknowledged cost of denying rather than rewriting: each time an agent tries to comment, it wastes one turn discovering the denial and being told what to do. This cost is knowingly accepted rather than treated as a problem to solve.
12. "One catalog detail is open, deferred to the `ghi-write` walk: whether "completion" collapses into close-with-reason, so the catalog does not carry two spellings of one event." — One question about the event-kind list is not yet decided, and deciding it is postponed to the future review session covering the `ghi-write` skill. The question: whether the "completion" event kind should be eliminated on the grounds that it is the same thing as closing an issue with a completion reason — which is handled by the close mechanism below — so that the catalog would not contain two different ways of expressing the same event.
13. "**Close**: a state change with a reason (completed / not planned), not a comment; passes the hook untouched; the delta feed carries it." — Closing an issue is treated as changing the issue's state and supplying one of GitHub's two closure reasons, "completed" or "not planned"; it is explicitly not modeled as writing a comment. Because it is not a create/edit/comment, the hook does not intercept or rewrite it, and the command runs as issued. The mirror learns about the closure through the normal delta refresh, since closing moves the issue's updated timestamp.
14. "**Delete**: denied flat, close instead — the record is append-forward." — Deleting an issue is refused with no override path described here and no conditions; the substitute action is to close it. Justification: the issue corpus is a record that only ever grows forward in time, so information is superseded rather than removed.
15. "**Soft block, not hard**: every deny path carries the audited one-use override (the instruction-file guard pattern already live on main)." — Every refusal in this system is defeasible rather than absolute. Each one comes with a mechanism by which the agent can override the refusal once, with the override being recorded for later inspection. This is not a new invention: it is the same guard pattern already implemented and in use on the main branch for protecting instruction files.
16. "A hard block would make the tool a single point of failure for all issue writes — a tool bug or an unwrapped `gh` capability would halt the workflow exactly when the door is needed." — Why the refusals are not absolute: if they were, then every issue write in the project would depend on this one tool working correctly. Two named ways that dependency would bite: a defect in the tool itself, or an operation supported by `gh` that the tool does not implement. In either case, work would stop, and it would stop precisely in the circumstances where an escape hatch is most needed.
17. "Hardening trigger, named: the audit showing overrides used to dodge the tool rather than answer genuine breakage." — The condition under which this permissiveness would be tightened is stated in advance rather than left implicit: reviewing the override records and finding that agents are invoking overrides to avoid the tool's checks, as opposed to invoking them to get past real malfunctions.
18. "**Known holes, accepted**: the hook enumerates patterns (`gh issue …`); `gh api`, MCP tools, and creative quoting slip past under the cooperative threat model." — The interception is admitted to be incomplete, and this is accepted. The reason it is incomplete: the hook works by listing command patterns to match, so anything not on the list gets through. Three named ways through: calling the GitHub API directly via `gh api`, using GitHub MCP server tools instead of the CLI, and writing the command with unusual quoting so it does not match the pattern. These are tolerated because the threat model assumes cooperative agents that are not trying to evade the checks.
19. "The maintenance sweep catches what slips — an unchecked write still appears in the delta." — Writes that bypass the hook are not invisible. They still change the issue on GitHub, so the delta refresh picks them up, and the periodic maintenance pass over the corpus can therefore find and address them after the fact.

## The three-layer stack

1. "**`ghi-write` (skill)** — the up-front layer: fires when an agent is about to file or edit, and front-loads the right behavior (ask ghi-info, route by state, edit not duplicate, write lean) so the agent is never blocked into a retry." — Layer one is the `ghi-write` skill, and its position in the stack is before the action. It activates at the moment an agent is preparing to create or modify an issue, and it gets the correct behavior to happen in advance. Four behaviors it front-loads: consulting `ghi-info` first; choosing the right destination based on the current state of things; modifying an existing issue rather than creating a near-duplicate; and keeping the body short. The purpose of doing all this beforehand is that the agent then never runs into a refusal that forces it to redo the write.
2. "The efficient path." — This layer is the route through the system that wastes nothing.
3. "**Hook + tool** — the correctness backstop when the skill does not fire: a missed trigger costs efficiency (a late duplicate catch, one comment retry), never correctness." — Layer two, the hook and write tool together, exists to catch the cases where the skill failed to activate. Because the backstop is there, a failure of the skill to trigger has only a cost in wasted effort — examples: a duplicate is detected at write time instead of before, or a comment attempt costs one retry — and never results in a wrong outcome landing in the corpus.
4. "This layering is what lets the skill description stay firm rather than "pushy": undertriggering stopped being dangerous, so the pushy register's false-trigger test debt is never incurred." — A consequence for how the skill's description is written. Because a missed trigger is now merely inefficient, there is no need to write the description in the aggressive, insistent style ("pushy") that maximizes how often a skill fires; a plainly firm description suffices. And avoiding that style also avoids an associated cost: descriptions written in that insistent register fire on cases they should not, which would have obliged the project to build and maintain tests for those false triggers — an obligation ("debt") that is now never taken on.
5. "**CLAUDE.md** — ambient documentation only." — Layer three is the project's CLAUDE.md instruction file, and its role is limited to being background reference material that is always present in context. It is not relied on to cause behavior.
6. "Written conventions demonstrably lose to training (nedschorus#13 commissioned `ghi-write` because comment-stacking recurred despite the written rule); instructions that arrive at the moment of action do not." — A general claim with evidence: when a rule written in a documentation file conflicts with what a model's training inclines it to do, the training wins — and this has been observed, not merely supposed. The evidence: issue #13 in the nedschorus repository was the origin of the `ghi-write` skill, and the reason it was created was that agents kept piling up comments on issues even though a written rule forbade it. The final clause completes an ellipsis: instructions delivered at the moment the agent is acting — i.e. skills and tool replies — do *not* lose to training.

## Division of labor

(Each table row restated as one item; the columns are Work / Owner / Cost.)

1. "Fetch, format, delta-merge, state split | script | free" — Retrieving issue data from GitHub, rendering it into the mirror's markdown form, merging newly changed issues into the existing mirror, and placing each issue in the open or closed file according to its state: all four are done by scripted code, and therefore consume no agent tokens.
2. "Length measurement, reference checks | script (in the tool) | free" — Measuring issue body length and confirming that references resolve are also done by code — specifically by code inside the write tool rather than by a standalone mirror script — and likewise cost no agent tokens.
3. "Freshness numbers, supersession sweep, link-integrity scan | script | free" — Computing the activity-relative freshness values, searching the corpus for supersession markers (and thereby for the defect of two open issues on the same ground with no marker between them), and checking that all cross-boundary links resolve in both directions: all by script, no token cost.
4. "Answer post-check against closed file | script (in the wrapper) | free" — Checking a returned answer's issue pointers against the closed-issues file, and filtering out ones that are closed, is done by code in the wrapper script rather than by the agent, and costs no tokens.
5. "Which issues bear on a question; similarity verdicts | ghi-info | one model turn" — Two things require actual judgment and so are done by the `ghi-info` agent: deciding which existing issues are relevant to a posed question, and ruling on how similar a draft is to what already exists. The price of each is a single turn of model inference.
6. "Cross-link edits | ghi-info | its one write class" — Adding and adjusting cross-references between issues is `ghi-info`'s work, and the cost column notes that this is the only category of write it is allowed to perform.
7. "Routing, body substance, the lean-split rewrite | the writing agent (via `ghi-write`) | where the authoring context already is" — Deciding where content should go, composing the actual content of the issue, and performing the split of an over-long body into summary-plus-MD are all done by whichever agent is doing the writing, guided by the `ghi-write` skill. The cost column gives the justification rather than a price: that agent is already holding the understanding of the material needed to do these things, so assigning them there costs no extra context-building.

## Deliberately not in version 1

(Each table row restated as one item; the columns are Cut / Why / Grows back when.)

1. "Vector or graph database | The context window is the database | Never on current evidence" — Not building a similarity-search store or a link-graph store. Reason: the model's context window, holding the whole corpus at once, already performs the role such a database would play. Condition for reconsidering: none — on what is known today this will never be needed.
2. "GitHub MCP server as the write surface | Generic writes carrying none of our checks | Never — the tool is ours" — Not using GitHub's MCP server as the way writes reach GitHub. Reason: it offers general-purpose write operations that would carry out none of this project's specific checks. Condition for reconsidering: none, because the point of the write tool is precisely that it is the project's own and can enforce the project's rules.
3. "Hard block on raw `gh` writes | Single point of failure; absolutes backfire | The override audit shows dodging, not breakage" — Not making the interception absolute. Two reasons: it would concentrate all issue-writing on one component that could fail, and absolute rules produce bad outcomes in circumstances their author did not foresee. Condition for reconsidering: the override records showing that overrides are being used to evade the checks rather than to get past genuine malfunctions.
4. "GitHub-side purge of old closed issues | The weight lands on context and attention, not on GitHub; mirror tiering answers it | Mirror tiering no longer suffices" — Not deleting or archiving old closed issues on GitHub itself. Reason: the burden those issues impose is on what fills an agent's context window and on what readers have to sift through, not on GitHub's storage or performance; and that burden is already handled by giving closed issues graduated (tiered) treatment in the mirror. Condition for reconsidering: the mirror's tiering ceasing to be enough to keep that burden manageable.
5. "Multi-watchdog process supervision | One overall timeout suffices at one-question scale | The single timeout proves too blunt" — Not building several independent watchdog timers over the agent process. Reason: at the scale of one question per invocation, a single overall time limit is adequate. Condition for reconsidering: experience showing that one whole-run timeout is too coarse an instrument — for instance, it cannot distinguish among the failure modes that need distinguishing.
6. "Committed mirror | Derived churn would pollute the history the user reads | A cross-checkout grep need the per-machine regenerate cannot meet" — Not checking the mirror files into git. Reason: they change constantly and are generated, so committing them would fill the repository history with noise, and that history is something the user actually reads. Condition for reconsidering: a requirement to search the mirror across multiple checkouts that could not be satisfied by simply regenerating the files on each machine.

## Verify at build

1. "An issue's `updated` timestamp moves on close, reopen, and label changes as it does on body edits and comments (documented; untested here)." — To be confirmed when building: that GitHub advances an issue's last-updated timestamp not only for body edits and new comments but also when the issue is closed, reopened, or has its labels changed. The parenthetical states the current evidence level: GitHub's documentation says so, but this project has not itself tested it. It matters because the delta refresh depends entirely on that timestamp moving.
2. "`updatedInput` combined with `additionalContext` in one PreToolUse reply (undocumented combination)." — To be confirmed: whether a single PreToolUse hook response can both rewrite the tool call (`updatedInput`) and inject extra context for the agent (`additionalContext`) at the same time. Flagged because the documentation covers each separately but does not address using both together.
3. "Codex-side pre-tool hook equivalents (the runtime has hooks; field names unverified)." — To be confirmed: what the corresponding pre-tool-call hook mechanism is in Codex, the other agent runtime in use. It is known that Codex supports hooks at all; what is not known is the exact field names and response shape, i.e. whether the same rewrite technique is expressible there.
4. "The cross-reference timeline event as the backlink source for the graph (API shape)." — To be confirmed: whether GitHub's timeline event recording that one issue was cross-referenced from elsewhere can serve as the data source for building the backlink half of the reference graph. What specifically needs checking is the shape of that API — what fields it returns and whether they contain what the graph needs.
5. "`gh` output mimicry: the tool's reply format against what agents expect from `gh`." — To be confirmed: that the write tool's response text sufficiently resembles genuine `gh` output. The test is empirical against agent behavior — does an agent that believes it invoked `gh` interpret the tool's reply correctly, or does the difference confuse it.
6. "Whether the box's `gh` auth and the long-lived Claude token survive unattended operation (the box's auth has expired before)." — To be confirmed: that both credentials on the Ubuntu machine — the GitHub CLI's authentication and the long-lived Claude token — remain valid over extended periods with no human present to renew them. Flagged because this has already gone wrong: authentication on that machine has expired in the past.
