# Frontmatter

# Introduction (text before the first `##` heading)

1. This document concerns how agents work with GitHub issues (GHIs) in the nedschorus project, and the system described consists of four parts: a long-lived knowledge agent that operates over the corpus of issues; a local mirror of that corpus kept up to date by a script; a tool for writing issues, paired with hooks that redirect raw/direct write attempts through it; and a skill called `ghi-write` that supplies the judgment/decision-making that none of the other, purely mechanical components can supply.
2. A record of how these decisions were reached exists: the design decisions in this document were ruled on August 7, 2026, referencing a separate document (ghi-info-agent-plan-draft.md) that served as the base/anchor document for a walkthrough review session and that contains a disposition (decision) for each individual item; separately, an alternative approach that was considered and rejected — called "the single-gate direction" — has been kept, not deleted, in another document (ghi-gatekeeper-plan-draft.md) for reference.
3. The guiding idea behind the design is that, rather than building a vector database or graph database to index the GitHub issues, the design instead relies on a modern AI agent, because the entire corpus of issues is small enough to fit within that agent's context window (the amount of text it can hold and process at once).
4. Work that is purely mechanical (not requiring judgment) never consumes the agent's token budget: scripts handle fetching, formatting, measuring, and filtering, and this costs nothing in agent tokens; the agent's tokens are spent only on tasks that require judgment.

# What ghi-info is

1. ghi-info is the first implementation built of a general category of agent called the "domain-knowledge-agent" class, which is defined in a separate document (issue #26, "26-dynamic-agent-team-model.md"); within that defining document, "the GHIs" (GitHub issues) is listed as the first example domain this general class applies to.
2. ghi-info has three responsibilities.
3. (Duty 1 name) Answering requests/questions from other agents.
4. Before another agent files a new issue or edits an existing one, it first asks ghi-info which material it should read.
5. ghi-info's answer is only a plain, unadorned list of issue numbers (e.g., "read #13, #24, #31"), with no accompanying explanation of why each item was chosen and no summarization of the issues' contents.
6. If ghi-info gives simple pointers (issue numbers) and one turns out to be wrong, the failure is obvious and costs the requester only one wasted read; if instead ghi-info gave prose summaries and an error crept into that summary, the error would not be obviously detectable, and by producing summarized content ghi-info would effectively be creating its own version of that material, making it a second author of the content alongside the original writers — which is treated as undesirable.
7. Explaining why each issue is relevant would be unnecessary clutter, since the requesting agent is going to read the referenced issues anyway and doesn't need to be told in advance why they matter.
8. (Duty 2 name) Keeping the network of references between documents correct and up to date.
9. This duty covers links between issues themselves, and also the correctness of links crossing the boundary between issues and markdown files in both directions: every reference that points from an issue to a markdown file must actually resolve (the target must exist), and every markdown file paired with an issue must link back to the correct corresponding issue(s).
10. The only kind of write ghi-info itself is permitted to make is editing these cross-links; it makes no other kind of write.
11. (Duty 3 name) Judging/deciding on proposed writes before they happen.
12. A separate tool that handles the write process (described later) sends the actual draft text to ghi-info for review before the write is finalized.
13. ghi-info can render one of several verdicts. One is "too similar," meaning the draft is judged a duplicate of, overlapping with, or in conflict with an existing issue; in that case the write is rejected, and the reply tells the writer to reconsider and to go read the related existing issue(s).
14. Another verdict is "related but compatible," meaning the draft touches on related topics without conflicting; in that case the write proceeds, and the reply also tells the writer which existing issues it should read for context.
15. The third verdict is "unrelated," meaning there's no meaningful relationship to existing issues; in that case the write proceeds normally with no special annotation.
16. Anything not covered by these three duties is outside ghi-info's scope: it never decides how a piece of content should be routed (e.g., whether something becomes a queue item, a plain issue, an issue-plus-companion-document pair, or a standalone markdown document with no issue) — that decision belongs to the `ghi-write` skill's judgment; it never writes the substantive content of an issue or markdown file itself; and it answers questions only using the corpus of issues — if asked about the project wiki or the codebase, it explicitly says that's outside what it knows rather than guessing.
17. In two specific situations — a markdown document that has become stale relative to the issue it's paired with, and an issue body that has grown past the defined length limit because nobody happened to be actively writing it — ghi-info's behavior is only to flag/note the problem, never to fix it itself; the actual repair is left for whichever future agent has the contextual knowledge needed to author that content correctly.

# The mirror

1. There is a local copy, made of markdown files, of the full corpus of issues; it is kept up to date entirely by automated scripts, meaning the AI agent itself never retrieves data from GitHub, handles multi-page results, or formats the data into the mirror.
2. GitHub is treated as the authoritative source of the issue data; the local mirror is only a secondary, derived copy, not an independent record.
3. The mirror is split into two files according to issue state: `issues-open.md` contains every currently open issue in a nearly unprocessed form (its number, title, labels, last-updated time, full body, and comments); `issues-closed.md` contains, for each closed issue, a single condensed line that is itself structured with multiple levels/tiers of information (the exact meaning of "tiered" is not fully spelled out — it could mean a compact multi-level summary packed into one line, or a line whose detail level varies by some criterion; I read it as a single, information-dense summary line per closed issue, in contrast to the raw full content kept for open issues).
4. This two-file split is meant to encode the intended default workflow directly into the files' structure rather than relying on a written instruction: in routine checks for whether new content relates to existing issues, only the open-issues file is searched (via grep); the closed-issues file is brought in only in two specific situations — when someone wants to claim that "no issue covers X" (such a claim of absence is only valid if both files were searched, since information about ideas that were tried and then rejected lives in the closed file), and when someone is explicitly searching for precedent.
5. Closed issues are estimated to be useful in roughly only 1 out of every 50 searches, and the design keeps them out of the other 49 not through a written instruction telling agents to ignore them, but structurally, by virtue of being in a file that isn't searched by default.
6. The mirror's storage location follows an established path convention, exists in any local checkout of the repository, is excluded from git tracking (gitignored), and can be regenerated by running the maintenance script on any machine.
7. Because the mirror is derived, regenerable data rather than something git tracks, the frequent changes it undergoes as it's kept current never get recorded in the git commit history.
8. The mirror is refreshed incrementally via a single call to the `gh` command-line tool's search feature, using a filter (`updated:>`) set to the timestamp of the mirror's most recently updated entry; this retrieves only issues changed since that point, and as part of processing, moves entries between the open and closed files whenever an issue's state changes.
9. This was verified against the live repository on August 7, 2026: fetching all 45 issues in full, including bodies, took 0.82 seconds and produced about 109 kilobytes of data; and it was confirmed that the `updated:>` filter returns exactly the issues that changed since a given timestamp, no more and no fewer.
10. There is a second update source, separate from the `gh` search call: checking the git commit log for changes since the last refresh, which is needed to detect edits to "pair" markdown files (companion documents), because such edits don't change any issue's timestamp and would otherwise go completely undetected.
11. The design deliberately makes "currency" (how up to date something is) explicit/readable rather than something to be inferred, because agents cannot reliably infer on their own what information is currently relevant versus outdated; accordingly, each mirror entry states both its last-updated time and a measure of "activity-relative freshness" — how much overall project activity has occurred since that issue was last updated — with the amount of project activity, not literal calendar time, serving as the measure of how "old" an entry is considered.
12. When one issue supersedes another, that relationship is recorded via an explicit marker naming the successor issue, written at the moment the supersession happens by whichever agent knows about it; because this marker follows a consistent, searchable text pattern, it becomes possible to automatically detect a specific defect: two open issues covering the same ground where neither one's text names the other, which can be automatically flagged as a problem.

# The session

1. ghi-info's host location ("seat") is a specific Ubuntu machine, at the path `~/agents/ghi-info`, following an established naming convention referred to as "the box convention"; this machine is where agent workload generally is being centralized.
2. Callers running on Mac machines reach ghi-info (on the Ubuntu machine) via SSH, using a connection pathway that was previously built by earlier work referred to as "the launch-claude work."
3. ghi-info's process is only actively running while it is in the middle of handling one turn; at all other times it has fully exited (is not running); what persists between these active periods is a session identifier, a transcript, and the mirror — but no actual running process persists.
4. This headless, resume-per-question agent has no "idle" state in the sense that word usually carries; "idle" normally describes a process that stays alive while waiting (like an open interactive session or a background watcher), and this agent is not that, since it fully exits and restarts per question rather than staying alive between them.
5. The policy governing what ghi-info loads into its working context is entirely centered on open issues.
6. When ghi-info starts a fresh session with no prior context, it loads the full contents of `issues-open.md`; closed issues only enter a given turn's context when specifically searched for via grep, as needed.
7. The problem being addressed by "recycling" (discarding and restarting context) is that a resumed session's context becomes progressively less accurate over time: even though the mirror itself is refreshed every turn, any issue that was loaded into context while open remains present in that context after it closes, and the agent has no way of noticing this has happened.
8. To address this, the wrapper script clears and reloads the context based on whichever of three script-detectable conditions occurs first: a count of issues that have closed since the session began exceeding a configured threshold; the rate of stale matches detected by the answer post-check (described later); or the size of the transcript reaching a threshold.
9. The specific threshold values for all three triggers are configuration settings that will be tuned based on real-world usage.
10. Because refreshing context is fast (under one second to fetch) and low-cost (one turn to load), the triggers are deliberately biased toward firing too early rather than too late: an unnecessary early recycle only costs one cheap reload, whereas recycling too late risks the agent giving wrong answers without any indication something is wrong — and the latter is judged the worse outcome.

# The ask

1. There is a single wrapper script that can be run by any agent, and which is also invoked as the first step of the `ghi-write` skill's process.
2. The script's steps run in this order. First, it triggers an incremental (delta) refresh of the mirror, which costs nothing in agent tokens, ensuring the agent always starts with current information.
3. Second, it resumes the previous session using a stored session ID if one exists and no recycle trigger has fired; otherwise it starts a fresh session.
4. Third, the prompt sent to the agent is the caller's question, plus — when resuming a session — the list of issue numbers that changed since the previous turn.
5. Fourth, the produced answer is checked afterward: if it contains a pointer to an issue that is actually closed (indicating stale context), that pointer is removed and a note is added before the requester ever sees the answer, correcting the answer immediately; how often this filtering happens is used as the second of the three recycle triggers mentioned earlier.
6. Fifth, the script prints the plain list as its final output.
7. There is a single overall time limit on the whole operation, and if a run has to be forcibly killed for exceeding it, that is recorded as a specific, identified type of failure.
8. Authentication is done using a long-lived token belonging to the Ubuntu machine rather than an interactive login, because interactive logins expire and there's no human present to renew them in this automated context.
9. This overall approach is not merely theoretical — it is already proven, because a separate project called nedsmessenger runs this exact same pattern live in production: specifically, a function called `ask_claude` in a file at `~/Projects/nedsmessenger/adapter/adapter.py` invokes Claude headlessly using `claude -p --resume` for each conversation, extracts the answer from the process's exit output, and includes watchdog mechanisms that detect and handle runs that get stuck.
10. It is a stated rule that if the process of asking ghi-info fails for any reason, that failure must never prevent a write from proceeding.
11. There is a defined fallback sequence: first try asking ghi-info; if that fails, fall back to directly grepping the mirror; if that also fails, fall back further to a live `gh` search; after this sequence, the process continues under the normal rules regardless of which level was reached.
12. If a given pointer/reference turns out wrong, that failure is obvious and visible; there remains a residual risk that some relevant pointer is simply omitted entirely, and this risk is accepted as tolerable under what's called the "cooperative posture" (the assumption that agents act in good faith, so the design doesn't try to catch every possible gap).
13. The system can correct itself over time without any dedicated error-reporting mechanism back to ghi-info: if a writing agent discovers a relationship ghi-info failed to surface, it simply adds the cross-link itself while editing, and the next delta refresh picks that addition up and incorporates it into the mirror.

# The write path

1. Agents continue to write issues using `gh` exactly the way they were originally trained, with no change required of them; instead, the underlying machinery ensures the correct outcome happens automatically without needing the agents to alter their behavior.
2. For the create and edit actions: a hook that runs before a tool executes (a "PreToolUse hook") intercepts any `gh issue create` or `gh issue edit` invocation and redirects it to the project's own custom write tool instead, using a mechanism called `updatedInput`; the mechanics of this rewrite-then-execute behavior, and the fact that command hooks have a configurable timeout defaulting to 600 seconds, were confirmed on August 7, 2026 against the cited documentation.
3. Once invoked in place of the original call, the write tool performs mechanical checks (body length; whether references can actually be opened), sends the draft content to ghi-info for the adjudication process described earlier, performs the actual write internally via `gh`, and replies in a format indistinguishable from a genuine `gh` response, so as not to confuse an agent that believes it called `gh` directly.
4. The system is "fail-open": if ghi-info cannot be reached, the write proceeds anyway without having gone through the adjudication check.
5. Regarding body length and the practice of splitting overlong content (the "lean-split"): agents never count words themselves — the tool measures the body's length automatically after the write happens.
6. If the body exceeds the length limit, the writer is immediately told to keep a good summary in the body and move the more substantial content into the linked companion markdown document, either creating or updating it as needed.
7. Because the writing agent is the one that holds the necessary understanding of what it's writing, that same agent is the one who performs the actual split between issue body and companion document; any broader knowledge of what else in the corpus this content should link to comes from asking ghi-info.
8. The intended end state is that issue bodies stay concise — a summary plus links — while the detailed substance lives in searchable markdown files in the repository; the issue and its companion document are conceptually one document expressed at two different levels of detail.
9. Regarding comments: any attempt to use `gh issue comment` is blocked, with a response designed to teach rather than merely refuse, because a comment cannot be automatically converted into the kind of body edit the project's revision convention requires — since only the commenting agent actually knows where the content belongs and what it supersedes.
10. The blocking response explains two alternative paths: integrate the intended content into the body via an edit, or — for genuinely new events the convention actually permits as separate entries — resubmit through the tool's dedicated comment action, which requires specifying an event type from a fixed, predefined list (instance outcome, completion, ruling challenge), a list that can only be expanded through an explicit deliberate ruling.
11. Each time this denial happens, it costs the agent one wasted turn to retry via one of the taught alternatives, and this cost is considered acceptable.
12. One question about this fixed event-type list remains open and has been deliberately deferred to a future walkthrough of the `ghi-write` skill: whether the "completion" category should be merged into the "close with reason" mechanism, so the list doesn't end up with two different terms representing the same underlying event.
13. Closing an issue is treated as a state change accompanied by a reason (either "completed" or "not planned"), not as a type of comment; this action is not intercepted or modified by the hook, and the delta-refresh feed will reflect it on its next run.
14. Deleting an issue is unconditionally forbidden; closing should be done instead, following the principle that the historical record should only ever grow by appending new information, never by erasing past entries.
15. The blocking mechanisms throughout are "soft" rather than "hard": every situation where a write is denied comes with a single-use override that gets logged for auditing, following an existing pattern (the "instruction-file guard pattern") already deployed on the main branch.
16. If the block were instead hard and unoverridable, this write tool would become a single point of failure for every issue write in the system — meaning a bug in the tool, or a GitHub capability the tool doesn't yet support, would halt the entire workflow exactly when bypassing the tool would be most necessary.
17. A specific condition is defined that would trigger reconsidering this soft-block approach: if audit logs of override usage show agents using overrides to routinely evade the tool's checks rather than only in cases of genuine tool malfunction, that pattern would be the signal to make the blocks harder.
18. There are known, consciously accepted gaps in this design: because the hook works by matching a specific list of command patterns (like commands starting with `gh issue`), other approaches — using `gh api` directly, using MCP tools, or using unusual/creative quoting — could bypass the hook's detection; this is accepted under the assumption that agents are acting cooperatively rather than adversarially, so the design doesn't need to defend against deliberate evasion.
19. Even so, any write that bypasses the hook this way will still be caught later by a periodic maintenance sweep, because such a write still shows up in the delta-refresh feed regardless of which path it took.

# The three-layer stack

1. The first layer is the `ghi-write` skill, called the "up-front" layer because it activates before an agent acts — specifically when an agent is about to file or edit an issue — and it proactively instills the correct behavior in advance (asking ghi-info, routing appropriately, editing rather than duplicating, writing leanly) so the agent never ends up blocked and forced to retry.
2. This layer represents the efficient way of getting things right in the first place.
3. The second layer is the combination of the hook and the write tool, serving as a correctness safety net for cases where the skill fails to activate; in such cases, the missed activation only costs some efficiency (for example, a duplicate caught later than ideal, or one retry after a denied comment), but never results in an actual correctness failure, because this layer still catches it.
4. This safety-net layer is what allows the `ghi-write` skill's own trigger description to remain firm but not aggressively insistent ("pushy"): because the skill failing to fire is no longer dangerous given the backstop, the extra testing burden that would come with a more aggressively worded description (checking for cases where it fires when it shouldn't) never has to be paid.
5. The third layer is the CLAUDE.md documentation file, which serves only as background reference material.
6. There is demonstrated evidence that merely written conventions are less reliable than an agent's trained default behavior when the two conflict — as shown by GitHub issue #13 in the nedschorus repository, which led to the creation of the `ghi-write` skill because agents kept stacking comments repeatedly despite a written rule against it — whereas instructions delivered at the exact moment of action do not suffer this same failure.

# Division of labor

1. Fetching issue data, formatting it, merging in incremental changes, and splitting entries by state (open/closed) are all done by script, at no cost in agent tokens.
2. Measuring body length and checking that references are openable are done by a script component embedded in the write tool, at no agent-token cost.
3. Computing freshness numbers, scanning for supersession markers, and scanning for link integrity are all done by script, at no agent-token cost.
4. Checking answers against the closed-issues file (filtering stale pointers) is done by a script component within the wrapper script, at no agent-token cost.
5. Determining which issues bear on a given question, and rendering similarity verdicts for write adjudication, are done by ghi-info, and each such determination costs one model turn.
6. Editing cross-links is done by ghi-info, and is, as stated earlier, the only class of write ghi-info itself performs.
7. Deciding on routing, writing the substantive body content, and performing the lean-split rewrite are all done by the writing agent, guided by the `ghi-write` skill; the stated rationale is that this is where the necessary authoring context already resides.

# Deliberately not in version 1

1. Building a vector or graph database is deliberately excluded from this first version, because the agent's context window itself effectively serves as the database; based on currently available evidence, this component is expected to never be needed.
2. Using a GitHub MCP server as the interface for writes is deliberately excluded, because such generic writes would carry none of this design's custom checks; this is expected to never be reconsidered, since the write tool is a custom asset belonging to this project.
3. A hard, non-overridable block on raw `gh` writes is deliberately excluded, because it would create a single point of failure and because absolute/rigid rules tend to backfire in unforeseen situations; this would only be reconsidered if the override-usage audit shows agents using overrides to evade the tool's checks rather than only in cases of genuine tool breakage.
4. Deleting old closed issues on GitHub's side is deliberately excluded, because the actual burden of old issues falls on the agent's context and attention rather than on GitHub itself, and the mirror's tiered file structure already addresses that burden; this would only be reconsidered if the mirror's tiering stops being sufficient.
5. Building a system of multiple watchdog processes for supervision is deliberately excluded, because a single overall timeout is sufficient at the current scale of one question at a time; this would only be reconsidered if the single timeout proves too imprecise in practice.
6. Committing the mirror to git is deliberately excluded, because the mirror's frequent, derived changes would clutter the git history that the user reads; this would only be reconsidered if a need arises to grep across multiple separate local checkouts at once — a need the current per-machine regeneration approach cannot meet.

# Verify at build

1. One item to verify when this design is actually built: the assumption that a GitHub issue's "updated" timestamp changes not just on body edits and comments but also on closing, reopening, and label changes; this is documented but has not been tested as part of this design work.
2. Another item to verify: whether `updatedInput` can be combined with `additionalContext` within a single PreToolUse hook reply, since this particular combination is undocumented.
3. Another item to verify: whether and how an equivalent to a pre-tool hook exists on the "Codex" side (a different runtime/system), given that this runtime is known to have hooks but the exact field names used have not been confirmed.
4. Another item to verify: the exact API response shape for using GitHub's cross-reference timeline event as the data source for backlinks in the reference graph.
5. Another item to verify: whether the write tool's reply format actually mimics what agents expect from a genuine `gh` response, so the substitution described in "the write path" is transparent to the calling agent.
6. Another item to verify: whether the Ubuntu machine's `gh` authentication and the long-lived Claude token both remain valid through unattended operation over time, flagged as a concern because the machine's authentication has expired unexpectedly in the past.
