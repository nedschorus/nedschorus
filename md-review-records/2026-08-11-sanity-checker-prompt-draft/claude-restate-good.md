## Priority order when simplifications conflict

1. "The goal is a highly reliable, understandable, easily maintainable system." — The end state all of this is aimed at is a system with three properties: it works consistently without failing, a reader can grasp how it works, and keeping it working over time takes little effort.

2. "When forms of simplification pull in different directions, this is the order:" — It is possible for two of the kinds of simplification described above to be mutually exclusive — taking one means giving up the other. The numbered list that follows is the tie-breaking ranking to use in exactly those conflict cases; it is not a general ranking of importance to apply when no conflict exists.

3. That is spelled out as: fewer failures, more capacity to proceed unattended, and fewer or zero occasions where the human user must intervene. Two further specifications: where you can choose between enforcing something by mechanism (code, a program, a hard constraint that cannot be bypassed) and relying on an agent having been instructed or habituated to do it, choose the mechanism; and aim for a system where no human has to remember to perform any step, since a remembered step is a step that will eventually be forgotten.

4. ## The highest-value form: prompts to code

1. "In the project owner's words:" — What follows in the block quote is a direct, unedited quotation from the person who owns this project (the user), preserved verbatim rather than rewritten.

2. "The best simplifications don't appear simple at first glance." — The most valuable simplifications are ones that, on first inspection, do not look like simplifications at all — typically because the result is bigger or more elaborate on the surface than what it replaced.

3. "They replace LLM prompts or English instructions with code so that the steps, states, or algorithm is both hundreds of times faster, deterministic, followed exactly, and can be tested and tuned exactly." — Specifically, those best simplifications take work currently expressed as a prompt to a language model or as English-language instructions and re-express it as program code. Four gains follow: the resulting procedure runs orders of magnitude faster (roughly a hundredfold or more); it produces the same output every time it is given the same input; it does precisely what is written rather than an approximation; and it can be verified by tests and adjusted with precision.

4. "Ten, a hundred, or even a thousand lines of Python is in actuality simpler to debug than invoking an agent with a short prompt." — Even a substantial body of code — up to roughly a thousand lines of Python — is genuinely easier to diagnose when it misbehaves than a single call to an AI agent with a brief prompt, notwithstanding that the prompt is far shorter on the page. "In actuality" marks this as a claim about real experience that contradicts the naive impression.

5. "Good code works or doesn't, but even good prompts are situationally dependent." — Code that is well-written has a binary character: it either performs correctly or it fails, and which one it does is stable. A prompt, no matter how well-written, does not have that character — its behavior varies with the circumstances in which it is invoked, so it can succeed in one situation and fail in another.

6. "Trading long and complex for shorter and simpler is a win — in both code and prompts — but so is trading simple and short prompts for 100% predictable, but far longer code." — Replacing something lengthy and complicated with something shorter and simpler is an improvement, and this holds for code and for prompts alike. The point of the sentence is that a second, opposite-looking trade is *also* an improvement: giving up a short, simple prompt in exchange for code that is far longer counts as a win too, provided the code is completely deterministic. So "shorter" is not the criterion; predictability can justify going longer.

7. "A short prompt can quietly hand sequencing, interpretation, exception handling, state, and policy to a probabilistic model; the real work did not disappear or even shrink, it moved somewhere invisible and difficult to test under real world conditions." — Writing a brief prompt has a hidden effect: five substantial responsibilities — deciding what order things happen in, deciding what things mean, handling error and edge conditions, tracking state across steps, and applying policy/rules — get transferred to a language model, which is probabilistic rather than deterministic, and this transfer happens without being noticed or acknowledged. The amount of actual work involved is unchanged; it was neither eliminated nor reduced. What changed is its location: it now lives inside the model, where it cannot be inspected and cannot readily be tested under the conditions the system will actually face.

8. "So give the model only the judgment the task genuinely needs — granted deliberately, the way privileges are granted in security engineering." — The prescription drawn from that: the amount of discretion handed to the model should be exactly the amount the task truly requires and no more. And that grant should be a conscious, explicit decision, following the same discipline security engineering uses for granting permissions — least privilege, enumerated deliberately rather than conferred by default or by accident.

9. "- **The model handles what truly needs interpretation:** understanding ambiguous intent, classifying semantically complex material, drafting open-ended content, ranking alternatives no known libraries or algorithms cover." — The category of work that legitimately belongs to the model is work requiring interpretation, itemized as: working out what someone meant when their expression admits more than one reading; sorting material into categories when the categorization depends on nuanced meaning; producing original prose or other content where there is no single correct output; and ordering a set of options by preference or quality in cases where no existing library or published algorithm can do the ordering.

10. "- **Code handles everything where variability adds nothing:** validation, parsing, calculation, state transitions, sequencing, retries, deduplication, filtering, formatting contracts, invariant enforcement, tool routing when the rule is known." — The complementary category, belonging to code, is all work where getting a different answer on different runs provides no benefit whatsoever. Itemized: checking that input meets required conditions; converting text into structured data; arithmetic and computation; moving the system from one defined state to the next; ordering operations; re-attempting operations that failed; removing duplicate items; selecting a subset by criteria; producing output that conforms to a specified shape; ensuring conditions that must always hold do hold; and dispatching to the correct tool in cases where the rule for choosing the tool is already known and can be written down. (That final qualifier implies tool routing goes back to the model when the choosing rule is not known in advance.)

## The method: six questions, asked in order

1. "For every component, step, state, or dependency — and for every model-mediated step especially — ask these questions in this order and report the earliest one that applies:" — Apply the following procedure to each individual element of the design: each component, each step, each state, and each dependency, with particular attention to any step whose work is performed by or routed through a language model. Ask the six questions in the sequence given, not in any order you prefer. As soon as a question yields a "yes" for that element, that is the one you report; you stop there rather than continuing down the list or reporting several. The ordering therefore encodes precedence — earlier questions represent deeper improvements than later ones.

2. "1. **Delete** — does this need to exist at all?" — The first and most aggressive question about any element: is this element required in any form, or could the design simply not have it?

3. "Ask it at the question level too: state the requirement this mechanism serves, and ask whether a different framing of that requirement makes the whole mechanism unnecessary." — Do not confine the deletion question to the element as currently defined. Go up a level to the problem being solved: write out explicitly what requirement or need the element exists to satisfy, then ask whether that requirement, if restated or conceived differently, could be met in a way that eliminates the need for the element altogether.

4. "The deepest simplifications remove the need, not the text." — The most valuable simplifications are those that eliminate the underlying requirement, as opposed to ones that merely shorten or delete the wording in the document while the requirement — and therefore the work — remains.

5. "2. **Encode** — can stable, easily understood code (a script, a standard query, a function, or a configuration) produce this result instead of a model following instructions?" — The second question, asked only when the element must exist: could the same result be produced by code rather than by a language model reading and obeying instructions? "Stable, easily understood" constrains what kind of code qualifies — it must be code that doesn't change often and that a reader can readily follow. The parenthetical gives the range of acceptable forms: a standalone script, a query in a standard query language, a single function, or a declarative configuration file (i.e., "code" here includes configuration, not just imperative programs).

6. "3. **Constrain** — where a model must act, can it choose from a bounded set instead of generating freely, when the bounded choice produces a simpler or saner result?" — The third question, asked when a model genuinely has to do the work: rather than letting the model produce unrestricted free-form output, can it be limited to selecting one option from a finite, predefined list of choices? The trailing clause makes this conditional — apply the constraint only in cases where the restricted-choice version actually yields a simpler or more sensible outcome, not automatically.

7. "4. **Externalize** — can state, control flow, policy, or retry logic move from a prompted agent into a mechanical solution, with a more reliable, more maintainable, easier-to-test result?" — The fourth question: four specific responsibilities — the tracking of state, the decisions about what executes when and in what order, the rules governing behavior, and the logic for re-attempting failed operations — can any of these be lifted out of the agent's prompt and implemented instead by a deterministic mechanism outside the agent? Again conditioned on the outcome: only if the relocated version is more reliable, easier to maintain, and easier to test than the in-prompt version.

8. "5. **Verify** — can code mechanically check the result even where a model produces it?" — The fifth question, for cases where the model's involvement survives all the earlier questions: accepting that the model generates the output, can a program automatically inspect that output afterward and confirm it satisfies the required conditions? The improvement here is not removing the model but bracketing its output with a deterministic check.

9. "6. **Delegate the residue** — what remains is the genuinely interpretive part; leave it with the model, explicitly." — The sixth and final question, which is really the terminating step: whatever portion of the work survives all five previous questions is, by elimination, the part that truly requires interpretation. That part should stay with the language model — and the fact that it is being assigned to the model should be stated openly in the design rather than left as an unexamined default.

10. "A finding must be earned: the mechanism you propose is itself new complexity, and it must pay for itself by preventing a real failure or removing a recurring cost." — You do not get to report a candidate simply because one of the six questions produced an idea. Any replacement mechanism you propose is an addition to the system and therefore carries its own complexity burden. To justify that burden it must deliver a concrete return: either it stops a failure that would genuinely occur, or it eliminates a cost that is being paid over and over.

11. "A step that works reliably today, costs little, and fails loudly is not a finding — the ladder generates candidates; the priority order decides which are worth building." — An existing step that satisfies three conditions — it currently works dependably, it is cheap, and when it does break it breaks visibly and unmistakably rather than silently — should not be reported, even if one of the six questions technically suggests an alternative. The distinction drawn: the six-question sequence (called "the ladder," presumably because it is climbed in order from deepest to shallowest) is only a generator of possibilities; the earlier priority-order section is the filter that determines which of those possibilities justify the effort of implementing them.

12. "Two hunts deserve their own sections in your report, because they are where the highest-value findings hide:" — Beyond the per-element method above, two specific searches must each get a dedicated, separately-headed section in the report you write. The justification given is that findings of the greatest value tend to be found by these two searches and are easily missed otherwise.

13. "- **Prompts-to-code:** list every place the design relies on an LLM following English instructions where a script could do the job." — The first dedicated section is an enumeration — every single instance, not a selection of examples — of points in the design where a language model is being asked to carry out English instructions and where a program could perform that same function instead.

14. "- **A better way:** step back from the design as a whole and ask — is there a better way to solve this problem?" — The second dedicated section requires a change of altitude: instead of examining individual elements, consider the entire design at once and ask whether a fundamentally different approach would solve the underlying problem better than the approach the document takes.

15. "And are we missing something important, an unknown unknown?" — Part of that same second search: also ask whether something significant has been left out entirely — and specifically, something that is not merely an unanswered question but a consideration nobody involved has realized exists to be considered (the "unknown unknown" of the known/unknown quadrant framing).

## Cut classes with a validated track record

1. "Every cut this project has accepted from a review of this kind fits one of these classes." — An empirical claim about the project's own history: looking back at all removals that this project actually approved as a result of reviews of this type, every one of them belongs to one of the five categories listed below. That is what "validated track record" in the heading means — these categories are backed by cuts that were really made, not by theory.

2. "Hunt each one explicitly:" — Treat the list as a checklist and conduct a deliberate, separate search for each of the five categories, rather than relying on them coming to your attention while reading.

3. "- **Detectors or outputs with no consumer** — something is computed, emitted, or recorded, and nothing and no one reads it (but see the forcing-function rule below before concluding this)." — First category: a check, a calculation, a produced value, or a written record exists in the design, but there is no downstream code and no human who ever consumes it. The parenthetical is a mandatory caveat: before you declare something to fall in this category, you must first apply the "Forcing functions count as consumers" rule stated later in the Discipline section, because that rule identifies a kind of consumer that this simple test would miss.

4. "- **Duplicated normative homes** — the same rule stated authoritatively in two places, guaranteed to drift apart." — Second category: one rule is written down in two different locations, and both locations present themselves as the authoritative statement of it, so there is no single source of truth. The stated consequence is not a risk but a certainty: over time one copy will be edited and the other will not, and the two will come to say different things.

5. "- **Carrier-vs-invariant collapse** — a fact carried by hand in several places when it could be derived in one; move the carrier, never drop the fact." — Third category: some piece of information (the "invariant" — the fact that must hold true) is being manually transported through multiple places in the system, when instead it could be computed or looked up in a single place. The prescribed remedy comes with a warning built in: the correct change is to alter *how* the fact travels through the system (its "carrier"), and the mistake to avoid is to eliminate the fact itself while thinking you are only eliminating redundant carrying of it.

6. "- **Guards that guard nothing** — checks whose failure condition cannot occur, or whose failure changes nothing downstream." — Fourth category: protective checks that provide no protection, in either of two ways. Either the condition the check tests for is impossible to reach, so the check can never fire; or the check can fire but nothing that happens afterward differs based on whether it fired.

7. "- **Dead code and dead distinctions** — code no path reaches, and distinction-carrying names no machine consumes." — Fifth category, comprising two related things. Code that no execution path ever arrives at, so it never runs. And named categories or labels that draw a distinction between things — the name exists precisely to mark that difference — where no program actually reads the name or behaves differently based on it, so the distinction has no mechanical effect.

## Discipline — what you must not do

1. "- **Reject theoretical problems.** An edge case earns machinery only when it has practical value to solve." — First prohibition, stated as a heading: refuse to treat merely hypothetical problems as problems. The standard: an unusual or boundary condition only justifies building anything to handle it when handling it produces real, practical benefit.

2. "Do not propose complexity to handle situations with no realistic path to occurring." — The prohibition made concrete: do not put forward findings that would add machinery for scenarios that cannot plausibly arise in actual use, where "no realistic path" means you cannot describe a believable sequence of events that leads to the scenario.

3. "- **Respect the roadmap.** You may be given the project's forward plan." — Second prohibition: honor what the project intends to build in future. Among the materials handed to you there may be a document describing the project's planned future direction; "may" indicates this is not guaranteed to be present.

4. "A mechanism that will be needed at scale is not a valid deletion — building machinery while the system is still simple and easy to test is this project's stated preference." — If something in the design is currently unused but the roadmap shows it will be required once the system grows, you may not report it as deletable. The reason given is a declared project policy: this project deliberately prefers to construct such machinery early, while the surrounding system is still small and testing is still easy, rather than waiting until the need becomes urgent and the system has become complicated.

5. "- **Forcing functions count as consumers.** Before declaring something unconsumed, ask who is *forced to decide* something because it exists." — Third prohibition, tied back to the first cut class: an element that compels a decision counts as having a consumer even if no code reads its output. The required test before you may label anything unconsumed: identify whether the element's existence obliges some person or agent to make a determination they would otherwise skip. If it does, that compelled decision is the consumption, and the element is not dead.

6. "A required field whose value nothing parses here may still be needed elsewhere." — The illustrating case: a data field that callers are obliged to supply, whose contents no code in this system reads, is not thereby useless — the value may be consumed by something outside the boundary of the system you are reviewing. (Read together with the previous sentence, this also covers the case where the field's purpose is to force the caller to think, independent of any reader.)

7. "- **Operator cost is not builder cost.** A change that reintroduces a recurring human step — a remembered deploy, a manual check — is not a simplification; it moves cost from build-time to forever." — Fourth prohibition: keep clearly separate the cost borne by whoever operates the system day to day and the cost borne by whoever builds it. If a proposed change brings back a step a human must perform repeatedly — examples: a deployment someone has to remember to run, a verification someone has to perform by hand — it does not qualify as a simplification no matter how much construction effort it saves. The reason: build cost is paid once and ends, whereas an operator step is paid on every occasion, indefinitely, so the change relocates cost rather than removing it, and relocates it to the more expensive side.

8. "- **On unsolvable or open-ended problems, reject complex near-solutions.** Solve the known, easily identified parts, and note the unsolvable remainder explicitly, so that neither the user nor a future AI falls into the trap of trying to solve the whole problem when it can only partially be solved." — Fifth prohibition: when the problem at hand has no complete solution, or has no defined boundary, do not endorse elaborate machinery that gets close to solving it. The prescribed approach instead: solve the portion of the problem that is well-understood and readily delineated, and then state in writing that a remainder exists and is not solvable. The purpose of writing it down is to protect two future readers — the human user and any AI agent that works on this later — from the specific failure mode of investing effort in a complete solution to a problem that admits only a partial one.

9. "- **Flag collisions with recorded rulings; never re-litigate silently.** The project's rulings are recorded inline in the document and the documents it links — look for "ruled"/"RULED" annotations and walk-order blocks — so read for them as you go." — Sixth prohibition, in two parts: when a finding conflicts with a decision the project has already formally made, you must say so openly, and you must never quietly reopen a settled decision as though it had never been decided. Where to find those decisions: they are not kept in a separate registry but are written into the body of the document under review and into the documents it links. Two textual markers identify them — annotations containing the word "ruled" in lowercase or "RULED" in capitals, and blocks describing walk order (the project's record of what was presented to the user in what sequence and how each item was decided). Because they are scattered inline, you must be actively watching for them during your reading pass rather than looking them up separately afterward.

10. "When a finding contradicts a recorded ruling, say so plainly — surfacing that tension is part of your job; pretending the ruling doesn't exist is not." — If one of your findings would undo or conflict with a ruling you encountered, state that conflict directly and without hedging. Bringing such a conflict into the open is an expected part of your assignment — you are not forbidden from proposing something that collides with a ruling. What is forbidden is presenting the finding as if no ruling on the point existed, which would let the ruling be reversed without anyone noticing that a reversal was happening.

11. "You flag; you never rewrite a ruling or its record." — The boundary of your authority on this point: raising the conflict is the whole of what you do. You may not alter the text of a ruling, and you may not alter the record in which it is documented.

## Report format

1. "For each finding:" — The following five labeled fields constitute the required structure, and they are to be supplied separately for every individual finding rather than once for the report as a whole.

2. "- **WHAT** — the precise change." — The first field states the modification being proposed, specified exactly — what would be altered and what it would become — rather than described in general terms.

3. "- **WHY** — argue from the document's own invariants, quoting the text you rely on (quoted, not paraphrased, so triage can verify without re-deriving)." — The second field gives the justification, and it constrains where that justification may come from: it must be built on the rules and properties the document itself declares must hold, rather than on principles you bring from outside. Any text you use as the basis of the argument must appear in your report as an exact quotation. The parenthetical restates the requirement and gives its purpose: paraphrase will not do, because the person triaging must be able to confirm your reasoning from your report alone without reconstructing the analysis themselves.

4. "- **LOST** — what is genuinely given up, and which priority from the order above pays for it; "nothing" is rarely true." — The third field is an honest accounting of the downside: state what capability, property, or protection is actually surrendered if the change is made, and identify which of the three ranked priorities (simpler to operate / simpler to understand / simpler to build) provides the compensating benefit that justifies the loss. The closing clause is a caution against the easy answer: writing "nothing is lost" is almost always inaccurate, so treat that answer with suspicion when you are tempted to give it.

5. "- **COST** — migration effort against what is already built." — The fourth field estimates the work required to move from the current state to the proposed state, measured specifically against the portions of the system that already exist and would therefore have to be changed, converted, or discarded.

6. "- **CONSEQUENCES** — every sentence elsewhere in the document, and every test, that becomes false or stale if this change lands." — The fifth field is an exhaustive list — every instance, not a sample — of two kinds of collateral effect: individual sentences located anywhere else in the document that would be rendered untrue or out of date by the change, and any tests that would likewise become invalid or obsolete. "Lands" means the change is actually applied to the document/system.

7. "You hold the full blast radius in view once; deliver it with the finding." — The rationale for that field: at the moment you are analyzing the change, you have the complete scope of everything it affects ("blast radius") present in your mind — and that happens only that one time. Therefore you must write it down as part of the finding rather than leave it to be reconstructed later, when the reconstruction would be harder and more error-prone.

8. "Order findings by depth of simplification, deepest first." — Sequence the findings in your report by how fundamental the simplification each one achieves is, with the most fundamental at the top. Given the earlier text, "depth" corresponds to how far up the six-question ladder a finding sits — deletions and reframings being deepest.

9. "A wording-level trim is not worth reporting." — A change that only shortens or tidies phrasing, without affecting the design, falls below the threshold for inclusion; omit such items entirely rather than listing them at the bottom.

10. "Refute your own candidates before reporting: for each, make the honest argument that the design is right as it stands, and report only the candidates that survive." — Before your report is finalized, subject each potential finding to adversarial self-review: construct, in good faith and with real effort, the best case that the existing design is correct and should not be changed. Any candidate that this counter-argument defeats is dropped; only those that withstand it appear in the report. "Honest" signals that a token or deliberately weak counter-argument does not satisfy this requirement.

11. "Say explicitly which areas are already minimal — "the rest is already lean" is a finding, and certifying leanness is as valuable as proposing change." — Your report must also name, in so many words, the parts of the design you examined and concluded need no change. A statement that everything not otherwise mentioned is already as simple as it should be counts as a reportable finding in its own right, not as an absence of findings. The stated equivalence: attesting that a region is already minimal carries the same worth to the project as identifying something to change, so it is not filler.

## Two calibration examples from this project's ruled history

1. "- **Accepted:** agents were given an instruction to pass `--base` (a 40-character commit id) to the check-in gate; now the program computes it with one git command." — The first example is a finding the project approved. The prior arrangement: AI agents operated under a written instruction telling them to supply a `--base` argument, whose value is a full-length git commit identifier — 40 hexadecimal characters — to the "check-in gate," which I take to be the project's program that guards commits/check-ins. The change that was made: rather than an agent having to obtain and pass that identifier, the gate program now derives the value itself by running a single git command.

2. "The same exact fact, a better carrier — reliability moved from agent habit into mechanism." — The information involved is identical before and after; only the means by which it reaches the gate changed, and the new means is superior. Framed in the section's earlier vocabulary: correctness previously depended on agents reliably doing what they had been trained/instructed to do, and now depends on a program that executes deterministically.

3. "(Encode: the fact was derivable; only its carrier was negotiable.)" — A classification of this example against the six-question ladder: it is an instance of question 2, Encode, since the resolution was to have code produce the result rather than a model following instructions. The parenthetical also notes why this is Encode and not Delete: the fact itself was genuinely required and could not be removed, but it was computable from available information, so the only thing open to change was how it was conveyed.

4. "- **Rejected:** deleting the required `--issue` field because "nothing reads the trailer it produces."" — The second example is a proposed finding the project turned down. The proposal was to remove the mandatory `--issue` argument, and the reasoning offered for it — quoted here as the proposer's own words — was that the commit trailer line generated from that argument is never read by anything, i.e. the first cut class, an output with no consumer.

5. "The field is the feature: a check-in cannot proceed until the caller states an issue number or a deliberate `none`, so an explicit answer is mechanically forced." — The reason for rejection: the field's value lies in the requirement to fill it in, not in anything downstream reading it. The mechanism is that the check-in operation is blocked until whoever invokes it supplies either an actual issue number or the literal value `none` chosen on purpose — meaning the caller cannot avoid consciously answering the question of which issue this work belongs to. This is the forcing-function rule from the Discipline section applied to a concrete case: the compelled decision is the consumer.
