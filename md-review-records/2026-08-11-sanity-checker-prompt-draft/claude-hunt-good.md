**2. L3 — "The name \"sanity-checker\" is the user's ruled candidate (2026-08-11, refined the same day from \"sanity reviewer\")"**
"ruled candidate" supports two incompatible readings: a name the user has ruled *on* (decided, not to be changed), or a name still holding candidate status (proposed, open). The rest of the file uses "ruled"/"rulings" to mean settled decisions (L78, L94), which pushes toward "decided" — but then "candidate" is contradictory. Harm: a later agent either renames a settled name or refuses to rename an open one, and L78's "never re-litigate silently" makes the wrong guess costly. Confidence: sure that it is ambiguous.

**3. L5 — "Everything below the rule is the prompt itself, written for a reviewer with zero context beyond what it names."**

Harm: whoever extracts the prompt into a skill will ship it believing it is self-contained, and the reviewer will silently guess at the missing project facts. Confidence: sure.

**4. L5 — "below the rule"**
"the rule" here means the horizontal rule at L7, but this file uses "rule" and its cognates throughout in the normative sense — "the forcing-function rule" (L65), "the same rule stated authoritatively in two places" (L66), "rulings", "ruled" (L78, L94). Harm is small but real: an agent asked to extract "the prompt itself" needs an unambiguous boundary marker, and this is the only sentence that sets it. Confidence: unsure — context makes the intended reading likely, but the boundary is load-bearing enough that the collision is worth noting.

**5. L11 — "write nothing — your only output is the report described at the end"**

Harm: a literal-minded reviewer either refuses to produce output, or (worse) reads "write nothing" as satisfied by not touching files and concludes it may write anything else — including the records that the very next clause forbids. Harm: on any real design doc with a link web, one reviewer reads two files and another reads forty, and neither knows which behaviour was intended; an unreachable link either aborts the review or is skipped silently, and the report gives triage no way to tell which happened. **9. L11 — "the requesting agent triages your findings and walks them with the user, and only the findings he accepts reach the document"**

**10. L20 — "looking for attempts to solve NP complete problems, like detecting every way a computer can edit a file"**
The example is not NP-complete and is not even a member of NP. NP-completeness is a property of decision problems with polynomially checkable certificates; "detect every way a computer can edit a file" is an open-ended enumeration over an unbounded space, closer to undecidable-or-ill-posed than to NP-complete. Obeyed literally, this instruction tells the reviewer to hunt for a complexity class that will essentially never appear in an MD design doc, and the one worked example teaches the wrong classification test. Harm: the reviewer either finds nothing under this heading, or applies the label to any problem that merely feels hard, so the bullet stops discriminating. Confidence: sure.

**11. L20 — "In the case of guarding a file from edits, simply backing up that file, then checking if it has been altered."**
Two problems. First, the sentence has no main clause — it is a fragment, so what the reviewer is being told to do with the backup-and-compare idea (propose it? recognise it?) is not stated. Second, taken literally the advice does not do what the clause says: backing up and later comparing *detects* an alteration after the fact, it does not *guard* against one, and the sentence stops before saying what happens when the comparison fails (restore? report? abort?). Harm: the reviewer proposes detect-only mechanisms as replacements for prevention requirements, and the design silently loses a guarantee it was written to hold. Confidence: sure.

**12. L22 — "every change you propose must leave the system better — simpler or more autonomous, safer or more testable, and saner or more reliable"**
The conjunctions make this a three-way AND: a proposal must improve on all three pairs simultaneously. That is stricter than the rest of the file and contradicts it. L26 states that "forms of simplification pull in different directions" and builds a whole priority order to resolve those conflicts — but if every change must improve all three pairs at once, no conflict can ever arise and the priority order is dead. It also contradicts L86, which requires each finding to state what is "genuinely given up" and notes "'nothing' is rarely true": a change that gives something up is by definition not better on every axis. Harm: a reviewer applying L22 literally reports almost nothing; a reviewer applying L26/L86 reports things L22 forbids. Confidence: sure.

**13. L18 vs. L30 — "but not at the expense of reliability and testability" / "welcome, but never at the expense of reliability or testability"**
The same normative rule is stated authoritatively in two places, with different conjunctions — "reliability **and** testability" versus "reliability **or** testability". Read strictly these differ: the first forbids only changes that cost both, the second forbids changes that cost either. This is precisely the "Duplicated normative homes — the same rule stated authoritatively in two places, guaranteed to drift apart" failure the file itself lists at L66, and the drift has already happened. Harm: a reviewer citing the weaker form admits a maintainability win that costs testability; one citing the stronger form rejects it. Confidence: sure.

**14. L26–L30 vs. L86 — the priority order has no entry for safety**

A finding whose loss is a safety loss, or whose payoff is a safety gain, has no priority to name — the mechanism is defined but a reachable case falls outside it, and the file neither adds the case nor says safety is deliberately excluded. Harm: the LOST field gets filled with the nearest-fitting wrong priority, and safety-vs-understandability conflicts have no documented resolution. Confidence: sure.

**19. L41 vs. L54 — "Code handles everything where variability adds nothing: validation, parsing, calculation, …"**

Harm: two rules, opposite verdicts, same input; report contents become reviewer-dependent, and triage cannot tell whether an omitted candidate was judged unearned or simply missed. Confidence: sure.

**20. L45 — "ask these questions in this order and report the earliest one that applies"**
Three problems, all of which bite in normal use.
(a) "the earliest one that applies" is unconditional and contradicts L54 ("A finding must be earned… is not a finding"), L90 ("A wording-level trim is not worth reporting"), and L92 ("report only the candidates that survive"). L45 says report; those three say withhold.
(b) Question 6, "Delegate the residue — what remains is the genuinely interpretive part; leave it with the model, explicitly", always applies to any model-mediated step once 1–5 have failed. So obeyed literally, L45 emits a finding for *every* component, step, state, and dependency in the document — the report never contains fewer entries than the design has parts.
(c) "applies" is itself ambiguous: it can mean the question is *applicable* to this item, or that the answer to it is *yes*. Under the first reading question 1 always applies to everything and questions 2–6 are unreachable.
Harm: the report's size and contents are determined by which reading the reviewer picks, and the WHAT/WHY/LOST/COST/CONSEQUENCES format at L84–L88 is unfillable for a bare "delegate the residue" entry — there is no change, nothing lost, and no migration cost. Confidence: sure.

**24. L58 — "list every place the design relies on an LLM following English instructions where a script could do the job"**

Harm: on a document describing an agent-mediated process, this yields a list the length of the process, and the reviewer has no stopping point. Confidence: sure the two instructions pull against each other; unsure only whether L54 is meant to be read as governing L58 (nothing in the text says it does).

**25. L59 — "And are we missing something important, an unknown unknown?"**

**27. L67 — "move the carrier, never drop the fact"**
