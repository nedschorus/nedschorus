## How the user judges a proposal

1. **"Recorded from many walks, because proposals that ignore these come back:"** — The criteria in the following list were compiled by observing repeated approval walks with the user. The reason for recording them: proposals that fail to satisfy them get rejected and returned for rework ("come back"), so satisfying them up front avoids that.

2. **"**State the axis.**"** — An instruction: when proposing something, explicitly name the dimension along which you are claiming improvement, and by implication what you are trading away on other dimensions.

3. **"\"Simplify\" without an axis is \"optimize\" without an axis."** — An analogy justifying the previous instruction: claiming a change "simplifies" something is as empty as claiming it "optimizes" something, because both words describe improvement along an unspecified dimension; simpler for whom, or in what respect, must be stated for the claim to have content.

4. **"This project's axis: simple-to-operate over simple-to-build; mechanical guarantees over trained habit; deterministic code over LLM prompts wherever the choice exists."** — The project's own settled preferences on three such dimensions, each stated as A preferred to B: prefer a system that is easy to run and use over one that is easy to construct; prefer correctness enforced by machinery that cannot be skipped over correctness that depends on an agent or person having learned to behave a certain way; and prefer implementing behaviour as deterministic program code rather than as instructions in a prompt to a language model, in every case where both are viable options.

5. **"Machinery with no consumer gets cut."** — Any built component whose output nothing reads or acts upon will be removed from a proposal. "Consumer" I read as a downstream reader or actor — code, process, or person — that uses what the machinery produces.

6. **"Logging is cheap; the machinery to act on logs is the real cost."** — An illustration of the previous point: emitting log records costs little, so the presence of logging is not the expensive part; the expense lies in whatever must be built to read those logs and do something with them. I read the implied caution as: don't count logging as a benefit unless something will actually consume it.

7. **"**A deterministic script is not traded for probabilistic agent behaviour**, even when the script is longer."** — A standing rule: do not propose replacing an existing deterministic script with an agent performing the same job by inference, whose results vary between runs. The concessive clause pre-empts the usual argument for such a trade — that the script has more lines of code — and declares that length is not sufficient reason.

8. **"A forcing function counts as a consumer."** — A qualification of criterion 5: if the effect of some machinery is to compel a person or agent to do something (a "forcing function"), that effect qualifies as a legitimate consumer of its output, so the machinery is not cut for lack of one.

9. **"A required field nothing parses can still earn its place by forcing an explicit answer."** — The illustration: a mandatory field in a form or template that no program ever reads is nevertheless justified, because requiring it compels whoever fills it in to state an answer explicitly rather than leaving the matter unconsidered. The human act of answering is the consumption.

10. **"**Absolutes in instructions can backfire.**"** — Writing instructions in unconditional terms can produce bad outcomes, presumably in situations the author did not anticipate where the unconditional rule is wrong.

11. **"CLAUDE.md says to use \"always\" and \"never\" cautiously; that applies to what you write as much as to what you review."** — There is an existing rule in `CLAUDE.md` calling for restraint in the use of the words "always" and "never."
