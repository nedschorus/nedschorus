# Agent-session reincarnation — the handoff-system

**What this document is.** The handoff-system is built, tested, and passed its trial; the scripts and their nc-test-suites are the normative description of what it does. This document carries only what code cannot: the user-rulings and their reasons, the verified facts about Claude Code the design rests on, the known holes, and the pinned commit at the end; the one exception is the session-handoff file format, which two programs share. It was cut down to that charter on 2026-08-12 (user-ruled: there is no utility in prose that documents what is better understood by reading the code — mechanism prose drifts). The full text from before that cut, mechanism descriptions included, is kept at `git show db917b5:md-review-records/2026-08-12-fast-handoff-sanity-check/reviewed-fast-handoff-design.md`; the superseded design of 2026-07-22 to 2026-07-24 is at `git show e178e67:docs/cross-project/fast-handoff-design.md`.

**Where the system's current parts are described.** `docs/nedschorus-wiki/nedschorus-handoff-architecture-overview.md`, the handoff-system's nc-architecture-overview, names the parts as they now stand and how they fit together; this document is the ledger of user-rulings.

## The problem

Many interactive agent-sessions run with little attention from the user. Each agent-session is to be replaced by a fresh one before its context grows heavy — the work is mostly sequential, so old turns are disposable — without the user typing into each tmux pane. **Compaction is rejected** for this: it summarizes uniformly when value is non-uniform, and it is slow. **`claude --continue` and `claude --resume` are rejected for this replacement**: they restore the context being shed. (`claude --resume` is used for a different case, an agent-session that died without a session-handoff; see the user-ruling of 2026-09-21.) Every relaunch at a session-handoff is a fresh agent-session — a new session id, a context window holding none of the predecessor's conversation, and CLAUDE.md and the hooks reloaded from disk.

## The components

Each script's module docstring says what it does and why it is built that way; each has a `…-test.py` nc-test-suite stating what must keep passing. The nc-architecture-overview describes the system's parts; these are the ones this document refers to.

- `scripts/handoff-context-threshold-hook.py`, the threshold hook — a `Stop` hook that reads the context used from the agent-session's own transcript and tells the agent to run the /handoff skill when the context used reaches the reincarnation threshold, `--threshold-used-percentage`, or when the context used plus the tokens the agent-session's compactions dropped reaches a second, higher threshold, `--threshold-used-plus-compaction-dropped-percentage`. While a subagent or a background Bash task of the agent-session is still in flight and the context used is below the ceiling, the hook instead says the session-handoff is deferred: until the subagent finishes, or until the background Bash task finishes or outlives its wait (next section). It also defers, up to the ceiling, when its scan of the transcript for work in flight cannot read every record, since it then cannot tell what is running; the context used comes from the newest assistant record, read before that scan. Subagents raise `SubagentStop`, not `Stop`, so the threshold hook never fires for them.
- `.claude/skills/handoff/SKILL.md`, the /handoff skill — the agent writes the next step, runs the writer script, and does what the writer script reports. Its decisions were approved in an approval-walk and merged on 2026-08-06; the outcome of each item is at `git show 9f8cc38:docs/drafts/handoff-skill-draft.md`.
- `nc-systems/handoff/handoff-write-and-check-supervisor.py`, the writer script — fills every field a machine can compute, removes from the agent-seat's task list each completed task whose log-store copy has the same bytes as the task's file, unless the completed task and an open task are linked, in either direction, through the `blocks` or `blockedBy` list of either, or the next step names the completed task's id or subject, writes the session-handoff, and reports whether a handoff-supervisor is watching.
- `nc-systems/handoff/handoff-supervisor.py`, the handoff-supervisor — one per agent-seat on each machine, guarded by a lock per agent-seat on that machine: it waits for a session-handoff, kills the agent-session, runs the extractor, and launches the successor with initial-agent-instructions. Tasks need no carrying: every agent-session of an agent-seat on one machine opens the one task list the launcher selects by setting `CLAUDE_CODE_TASK_LIST_ID`, and a handoff-supervisor started with that variable unset or empty refuses to start and names the launchers that set it.
- `scripts/handoff-extract-conversation.py`, the extractor — writes the conversation-tail, verbatim, holding the user's and the agent's turns only. When the conversation-tail leaves turns out, or the agent-session dispatched a subagent, it also writes the complete dialog, `<seat>-dialog-NNNN-complete.md`, which holds every turn and what each subagent the agent-session dispatched was asked and what it reported.
- `scripts/log-store-session-dialogs-refresh-nbd.py`, the session dialogs refresh — every 10 minutes on ned-box, writes the complete filtered dialog of each agent-session transcript in the log-store whose transcript has changed since, subagent prompts and reports included, to `nedlern@ned-box:/home/nedlern/nedschorus-logs/session-dialogs/<machine>/<project-key>/<session-id>-dialog-complete.md`, replacing the earlier file, so a running agent-session's dialog is on ned-box whether or not the agent-session has ended.

## What a reincarnate-seat kills, and how work survives it

A reincarnate-seat kills the agent-session, and the agent-session's subagents die with it: a subagent runs inside the process the handoff-supervisor terminates, and no field of the session-handoff can carry a running one across. On 2026-08-27 an agent-seat dispatched a builder subagent at 20:38; the threshold hook fired at 20:43 at the threshold then set, 50%, the session-handoff was written, the handoff-supervisor killed the agent-session, and the subagent died four minutes into its job.

**The handoff-deferral makes that rare, and it is the one exception to recording subagents rather than waiting for them (user-ruled 2026-08-27).** The threshold hook holds the reincarnate-seat while any subagent started with the Agent tool is in flight, up to `--ceiling-used-percentage`; at the ceiling it fires whatever is still running, because an agent-session waiting on a subagent that does not finish runs out of context instead of being replaced, which loses more. The 2026-08-23 user-ruling that a reincarnate-seat records its subagents rather than waiting for them (PR [The handoff records the subagents a session spawned](https://github.com/nedschorus/nedschorus/pull/153)) governs everything else. The handoff-deferral postpones the kill; it does not do away with it. A subagent still dies at the ceiling, when the agent-session crashes, and on any exit the hook is not there to see.

**The session-handoff is held for a background Bash task too, up to a wall-clock wait (user-ruled 2026-09-14; the wait raised to 75 minutes, user-ruled 2026-09-16).** The handoff-deferral at first saw only subagents. On 2026-09-14 agent-session 831c08ee handed off at 50% while an invocation of the cold-read grid, `nc-systems/cold-read/cold-read-grid.py`, which launches six cold-read-cells (reviewers), ran as a background Bash task; the hook found nothing in flight, the reincarnate-seat killed the grid and its six cold-read-cells 12.7 minutes in, and five of the six reports were lost, because a cold-read-cell writes its report as its last act. The hook now counts a background Bash task as in flight while it is younger than `--background-task-wait-minutes` and no completion notification names it, judging each task's wait on its own; past that wait the task is presumed stuck or open-ended and holds nothing, because the transcript carries no process id, the Bash tool does not enforce its `timeout` on a background task, and the task's output file stays empty when the command redirects its own standard output, as the grid's does. The wait was first set to 30 minutes: the user offered 15 as an example, 15 would have killed the grid invocation this was built for, and across 365 finished background tasks on the Mac the 90th percentile was 20 minutes and the 95th 31, with grid invocations at 8 to 27. On 2026-09-16 the user raised it to 75 minutes, because the grid now relaunches a failed cold-read-cell once, which makes a grid invocation with a late failure run longer. Monitors started with the Monitor tool still do not hold the session-handoff: a monitor watches work that runs elsewhere. The ceiling bounds this wait as it bounds the wait for subagents.

**So the prompt of a subagent given a job longer than one step says how the work survives a kill.** A fresh subagent starts with only CLAUDE.md and its prompt, and a fork knows nothing its commissioning agent-session learned after forking it, so both requirements go in that prompt: commit after each step, and keep a report file rewritten after each step rather than composed at the end. A kill then costs the step in progress and nothing before it, and whoever picks the job up reads the commits and the report instead of reconstructing intent from an absence.

**Subagents, forks included, are the default way to dispatch work.** They report back on their own, the handoff-deferral protects them, the spawned-subagent-roster in the session-handoff names those still working when a reincarnate-seat kills them, and their output reaches the commissioning agent-session without anyone watching a tmux pane.

**A detached headless agent-session is the explicit exception**, for an unattended job measured in hours rather than one that fits in an agent-session's remaining context. It buys freedom from being replaced at a reincarnate-seat and pays in tracking, so a prompt that chooses it names that cost where its reader will meet it:

- **No completion notification.** Nothing wakes the commissioning agent-session when the job ends; someone goes and looks.
- **Its own permission mode**, fixed at launch rather than inherited from the agent-session that dispatched it.
- **Nobody notices when it is stuck.** Detecting a stuck or waiting agent-session is the open gap in GHI [Console text-insertion + stuck/waiting-state detection (operator tooling; captured from the comms backlog)](https://github.com/nedschorus/nedschorus/issues/27), so a headless job that stalls stalls quietly.
- **The spawned-subagent-roster does not list it.** That roster is read from the transcript's records of Agent-tool spawns, and a detached agent-session leaves no such record; the extractor also drops the Bash call that launched it from the conversation-tail, so the successor is not told the job exists unless the next step says so.

## The session-handoff file format

The session-handoff is a short list of `key: value` lines, written whole: the writer script writes it to a `.partial` file and renames that file, so no reader ever sees it half-written. The handoff-supervisor reads those lines into fields, and the first occurrence of a key wins. The writer script's `write_handoff_file` writes every field; this section gives the two whose form takes more than a line to state: the verbatim next step and the spawned-subagent-roster.

### The verbatim next step

The `next-step` field is always one line: the writer script collapses its whitespace, because a multi-line value would otherwise be cut at its first line by the reader. When the agent's next step has more than one non-blank line, the writer script also writes a second field, `next-step-verbatim`, carrying the text with its line breaks, and writes it LAST:

    written-at: 2026-08-19T17:04:11Z
    next-step: FIRST ACTION: run the suite and read the three failures. THEN: fix only the locale case; leave the other two for the design approval-walk on docs/issues/45-remote-named-agent-launch-and-reattach.md@3406ac3.
    restart-counter: 7
    written-in: /Users/el/agents/git-infra
    written-by-session: 5b66b6d0-0000-4000-8000-000000000000
    next-step-verbatim: <<END-OF-NEXT-STEP
    FIRST ACTION: run the suite and read the three failures.
    THEN: fix only the locale case; leave the other two for the
    design approval-walk on docs/issues/45-remote-named-agent-launch-and-reattach.md@3406ac3.
    END-OF-NEXT-STEP

The opening delimiter is `<<END-OF-NEXT-STEP`, on the `next-step-verbatim:` line. The terminator is `END-OF-NEXT-STEP` alone, with no `<<`, on a line by itself. The lines between them are the value.

**The terminator is matched as an exact line**, by both the writer script and the handoff-supervisor: no leading or trailing whitespace is tolerated, and the writer script refuses on the same exact comparison the handoff-supervisor uses to end a block. This makes an indented lookalike — a terminator indented inside a list item, say — ordinary content rather than the end of the block: the writer script writes it, the handoff-supervisor keeps it, and the two cannot disagree about where a block ends. A terminator that is not indented ends the block even inside a fenced code block, so the writer script refuses it. The cost is that a hand-written terminator with trailing whitespace does not end the block; that falls into the unterminated case below, which falls back to the one-line `next-step` and says so, rather than silently dropping content.

Writing the block last, after every computed field, is what makes it safe for a reader that knows the block: a content line that happens to look like `key: value` cannot shadow a real field, because the real fields come before it and the first occurrence of a key wins.

Rules both ends follow:

- **The writer script adds `next-step-verbatim` only when the next step has more than one non-blank line**, and always writes `next-step`. A next step of one non-blank line, with or without blank lines around it, produces no `next-step-verbatim` field.
- **Content between the delimiters is verbatim** — no indentation added or stripped, no whitespace collapsed, and no trailing whitespace removed from the last line. A trailing double space is a Markdown hard break, so the handoff-supervisor must pass the block on exactly as parsed; emptiness may be tested on a stripped copy, but the value passed on is never the stripped one. The one exception: blank lines before the first non-blank line and after the last are not written; blank lines between them are kept.
- **The writer script's refusal of an empty next step is applied to the collapsed `next-step` value**, before any block is considered. A next step that is only whitespace is therefore refused, rather than written as an empty block.
- **The writer script refuses a next step of more than one non-blank line that contains a line equal to the terminator**, naming that line. As with its refusal of an empty next step, a writer script that cannot represent what it was given says so, rather than writing a file that reads back as something else. A one-line next step equal to the terminator is written as `next-step` only, where it is ordinary text.
- **The handoff-supervisor uses `next-step-verbatim` when it is present, terminated and not blank**, and `next-step` otherwise. An unterminated block is a damaged session-handoff: the handoff-supervisor falls back to `next-step`, which the writer script always writes, and says in the initial-agent-instructions that the verbatim block was unterminated, so the successor knows it received the one-line form. A terminated block that is blank falls back to `next-step` with no such note. A hand-written `next-step-verbatim:` line without the opening delimiter is an ordinary field, and its value is passed on as the next step.
- **Only `next-step-verbatim` takes the block form.** A `<<` in any other value, `next-step` included, is ordinary text.

**Compatibility, and why the delimiter is not on the `next-step:` line.** A handoff-supervisor is a long-running process, so one started before an upgrade reads session-handoffs written after it. Such a handoff-supervisor reads `next-step` as before and ignores `next-step-verbatim` as an unknown key, and its successor gets the one-line next step, which is a degradation, not a failure. It does read each content line of the block that looks like `key: value` as a field, and the rule that the first occurrence of a key wins protects only the fields the writer script wrote: a content line such as `dont-restart: …` or `spawned-subagent-1: …`, in a session-handoff that has no such field, becomes that field for this older handoff-supervisor. A handoff-supervisor that knows the block, reading a session-handoff without one, uses `next-step`, so nothing needs migrating; and in a hand-written file, `next-step` is whatever its line says. Had the delimiter gone on the `next-step:` line, an older handoff-supervisor would have started its successor with the delimiter string as its entire instruction, silently.

### The spawned-subagent-roster

The writer script records each subagent still working when the session-handoff is written — one whose last event in the transcript is its spawn, a resume, or an interim task-notification, which Claude Code sends when a subagent's turn ends while background work of its own is still running — as one numbered field carrying the agent id and the job's description:

    spawned-subagent-1: a309071aa3681d280 "Fix ignored-path write blind spot"

The fields are numbered from 1 in spawn order rather than repeated, because the reader takes the first occurrence of a key, and a repeated `spawned-subagent:` would lose every subagent but the first. They are written with the computed fields, before any verbatim block. A subagent whose last event is a final task-notification, whatever its status (`completed`, `failed`, `killed` or `stopped`), is not recorded, and an agent-session with no subagent still working writes no such field; a handoff-supervisor that predates the field ignores it as an unknown key. When the writer script cannot read the transcript, it writes no roster and tells the agent to name its subagents in the next step. When the roster is not empty, the handoff-supervisor's initial-agent-instructions name each entry and say: "You may need to re-commission similar agents. If you need more context, the dead agents' full transcripts are at `<predecessor-session-dir>/subagents/agent-<id>.jsonl`."

Why the roster records only working subagents, and says so little (user-ruled 2026-08-29 and 2026-08-30): ended subagents are left out because "Completed is junk. If someting is completed its on main or minimally in the worktree. Neither I or the next agent cares what is completed", and failed ones because "presumably the prior agent had a chance to restart, and if that worked it would have restarted." The successor is told only what it needs at its start: "like tuning a claude.md file we should only put in the stuff that they need to know at their start. The rest they can look up if they need to." A dead subagent cannot be resumed by its id from a successor — on 2026-08-29 a successor's SendMessage to a predecessor's subagent id was refused with "No transcript found", because the id resolves only within its own agent-session, while resuming within one agent-session works — so the successor re-commissions a new agent instead. Under the same principle of telling the successor only what it needs at its start, the initial-agent-instructions do not say that a dead subagent cannot be resumed.

## User-rulings

Dated decisions and their reasons — the part of the design a reader cannot recover from code. Where a later user-ruling replaced part of an earlier one, the entry says what each user-ruling decided and when; the earlier text is in git history.

- **Git is the long-term record and the source that work is restored from after a problem (user-ruled 2026-08-02).** Session-handoffs are operational, kept on their agent-seat's machine, never committed, and disposable; the Mac's are also copied to the log-store by `scripts/transcript-mirror-to-log-store.py`. File and repository state travel by committing as work goes and by the queues, not by session-handoff.
- **The successor is not dumber than the predecessor (user-ruled 2026-08-02).** Carry information, not interpretation: dialog goes verbatim; no distillation, rewriting, or correction ceremony.
- **Gaps cost more than over-capture (user-ruled 2026-08-02).** Dialog is small next to what an agent-session reads and writes, which is what makes frequent reincarnate-seats safe.
- **Moving an agent-seat between machines is in scope (user-ruled 2026-10-28, replacing the 2026-08-02 ruling that it was not).** Agent-seats run on the Mac and on ned-box, and may later run as cloud agents; moving one seamlessly between them is the subject of GHI [Moving an agent-seat to the other machine in one handoff that stops it on the old machine and starts it on the new one without restart prompts](https://github.com/nedschorus/nedschorus/issues/1129).
- **The agent supplies only the next step and whether the user is to be asked before a relaunch; the writer script fills every field a machine can compute (user-ruled 2026-08-06).** The agent gives the second with `--dont-restart` (/handoff skill, step 2). Hand-written fields asked the agent to do arithmetic and left silent truncation possible; each of the writer script's mechanisms (the next step read from a file rather than an argument, the whitespace collapse, the restart counter taken from the larger of the file's and the consumed value, the refusal of an empty next step) answers a failure that hand-written fields allowed.
- **The retiring agent exercises no judgment over which dialog its successor receives (user-ruled 2026-08-06).** The extractor's word floor sets where the conversation-tail starts — the floor's value and its sizing rationale are in the extractor — extended back to the nearest user prompt; `--boundary-quote` survives as a manual override only.
- **The next step is an instruction to act on, not a summary, and every pointer in it carries a pin** (path, or repository and GitHub issue number) so the successor resolves what the predecessor meant. Canonical location: the /handoff skill (2026-08-06).
- **The /handoff skill runs one script that does everything best done by script (user-ruled 2026-08-06).** Writing the session-handoff and reporting whether a handoff-supervisor is watching are one command because they are one decision: a session-handoff nobody is watching must not stop the agent working, and an agent that runs only half of a two-step procedure would stop anyway.
- **No program scans the machine for agent-sessions to supervise (user-ruled 2026-08-06), and a launcher, not the writer script, starts each handoff-supervisor (user-ruled 2026-08-14).** On 2026-08-06 the writer script was made to start a detached handoff-supervisor, which adopted the running agent-session, whenever none was watching. On 2026-08-14 the user decided that replacing an agent-session works only where there is a terminal to launch the successor on: a successor inherits its handoff-supervisor's standard input and output, and a detached handoff-supervisor's output is a log file, so every successor such a handoff-supervisor launched died at its first need for input. The commit that carried out that user-ruling, db49f1ed8, also removed the writer script's starting of handoff-supervisors. A handoff-supervisor now runs as the command of its agent-seat's tmux pane, started by `scripts/launch-claude-mac`, `scripts/launch-claude-ubuntu`, `scripts/recover-crashed-seats.py` or `scripts/resupervise-seat.py`; when none is watching, the writer script says so and gives the `scripts/resupervise-seat.py` command that relaunches the agent-seat under one. A lock per agent-seat on each machine refuses a second handoff-supervisor for that agent-seat on that machine (two would double-kill and double-launch); nothing stops the same agent-seat name running on the other machine too.
- **The threshold hook takes the context used from the transcript, and only from the transcript (user-ruled 2026-08-12).** The status-line relay — a second source of the figure for the context used, carried by the status line, which only interactive agent-sessions run — was cut: its sole remaining use was an agent-session whose first turn had not ended, before which the `Stop` hook never runs. The status-line renderer survives as `scripts/session-statusline-command.py`, outside this system.
- **The threshold hook fires at the threshold unconditionally (user-ruled 2026-08-12).** Its test for a running handoff-supervisor was cut, because staying silent could only turn a dead handoff-supervisor into an agent-session that is never replaced. When the user-ruling was made, the writer script then started a handoff-supervisor that adopted the agent-session; since 2026-08-14 it instead reports that none is watching and gives the relaunch command (the user-ruling "No program scans the machine…" above). *Unconditionally* here excluded the test for a running handoff-supervisor, which was the condition then in question. Conditions added since: the handoff-deferral (user-ruled 2026-08-27, extended 2026-09-14), which postpones the firing rather than cancelling it; the second threshold, which adds the tokens compactions dropped (user-ruled 2026-10-24); and the variable `NEDSCHORUS_SESSION_REINCARNATION_OWNED_BY_CALLER`, which `scripts/ghi-guide-agent-ask.py` sets for its own agent-sessions and which silences the hook. The hook also asks only once per agent-session until a compaction.
- **The reincarnation threshold is a third of the context window (user-ruled 2026-10-21).** `--threshold-used-percentage` defaults to 33, down from 50, to try replacing agent-sessions earlier; the ceiling stays at 65.
- **The queue-status line is printed on the handoff-supervisor's console only (user-ruled 2026-08-12; changed 2026-08-29).** On 2026-08-12 the line, each queue's depth and oldest item, was added to every successor's initial-agent-instructions with the instruction to surface anything rotting, to meet the duty in GHI [What NC preserves, where it goes, how that is codified, and how it is kept from drifting — design pair (destination: wiki page with subpages)](https://github.com/nedschorus/nedschorus/issues/32) to keep rotting queue items visible to the user. On 2026-08-29 the user removed it from the initial-agent-instructions: "Also useless is the reminder there are files in the queues. Thats what queues are for." The console print stays, for a watched tmux pane or the handoff-supervisor's log.
- **Record the subagents, do not wait for them (user-ruled 2026-08-23; narrowed 2026-08-29 and 2026-08-30).** Subagents die with the agent-session that spawned them, and apart from the handoff-deferral below, that stays the policy: killing and re-commissioning them is cheaper than waiting for them before a reincarnate-seat. What was missing is that nothing told the successor they had existed. On 2026-08-23 the merge-lane commissioned a subagent that built PR [codex review cells launch with the shared memory store disabled](https://github.com/nedschorus/nedschorus/pull/150); it completed at 21:31:18Z and sat idle, still the owner of that pull request's unanswered review findings, and the agent-session was killed at 22:08:12Z. The successor found the orphaned work only because the retiring agent happened to write a sentence about it, and re-commissioned a new fixer at 22:25:28Z. Prose is the faculty least to be relied on when an agent-session is replaced, so the writer script derives the roster from the transcript instead. The 2026-08-29 narrowing to working subagents, the 2026-08-30 wording of what the successor is told, and the user's reasons are in "The spawned-subagent-roster" above. The case of a subagent that has ended but still owns work, as this one did, is carried instead by the agent-seat's task list, which every agent-session of the agent-seat opens (PR [Bind each seat's task list to its NAME (CLAUDE_CODE_TASK_LIST_ID), so a recycled seat resumes the same list](https://github.com/nedschorus/nedschorus/pull/141)), and by the rule that an unanswered question to the user goes on the task list (`.claude/skills/walk-me-through/SKILL.md`), and the user accepts what remains: "theyd find out when or if that mattered". Liveness is not inferred from unmatched tool_use and tool_result pairs, because a spawn's result arrives at spawn time (Verified facts below).
- **A reincarnate-seat waits for the agent-session's running subagents, up to a ceiling (user-ruled 2026-08-27; extended to background Bash tasks, user-ruled 2026-09-14).** The threshold hook defers while any subagent is in flight, saying so once rather than at every turn's end: the subagent's completion notification wakes the agent-session by itself, and a hook that refused the stop each time would drive an idle agent-session into a new turn at every turn's end for as long as the subagent ran. `--ceiling-used-percentage` (default 65) bounds the wait. This is the single exception to the 2026-08-23 user-ruling to record subagents rather than wait for them; the loss that bought it, the wait for background Bash tasks and its 75-minute default, and what a subagent's prompt owes a job longer than one step are in "What a reincarnate-seat kills, and how work survives it".
- **A compacted agent-session also counts the tokens its compactions dropped (user-ruled 2026-10-24).** Claude Code compacts an agent-session whose context used is 200,000 tokens or more after about 54 idle minutes, cutting its context to a few tens of thousands of tokens; the fleet-restart-at-login agent-seat's agent-session of 2026-10-14 was compacted eight times in a week and never reached the threshold (evidence: `nedlern@ned-box:/home/nedlern/nedschorus-logs/seats/fleet-restart-at-login/compaction-timing-research-2026-10-24.md`). So the threshold hook also fires when the context used plus the newest compaction record's `cumulativeDroppedTokens` reaches 40% of the context window, set by `--threshold-used-plus-compaction-dropped-percentage`. The handoff-deferral holds both triggers, and the ceiling measures the context used alone.
- **No scheduled canary re-runs (user-ruled 2026-08-12).** Carrying tasks across agent-sessions rests on undocumented Claude Code behaviour, and the user does not care about the risk of a Claude Code upgrade breaking it. Since copying tasks into a new task list was removed (complexity-sweep approval-walk, item 18, 2026-10-03, walk-minutes `nedlern@ned-box:/home/nedlern/nedschorus-logs/walk/complexity-sweep-findings-2026-10-02-minutes.md`), the task-list id the launcher sets, `CLAUDE_CODE_TASK_LIST_ID`, is the only carrier of tasks across generations. Nothing detects a task-list id that stops working: the successor sees an empty task list, which looks like one with nothing to do. The handoff-supervisor nc-test-suite's `--canary` cases, once the diagnosis, were removed after PR [~/.claude.json presets: a file that is not UTF-8 is reported as not valid JSON, the handoff-supervisor uses the shared remedy, and the canaries skip with a reason](https://github.com/nedschorus/nedschorus/pull/1458), so no diagnosis for it remains in the repository. This user-ruling covers only Claude Code's carrying of the task list, and no other scheduled test (item 3 of approval-walk md-skills-seat-open-questions-carried-over-approval-walk-2026-10-27, walk-minutes `nedlern@ned-box:/home/nedlern/agents/MD-skills/docs/walk/md-skills-seat-open-questions-carried-over-approval-walk-2026-10-27-minutes.md`).
- **The initial-agent-instructions carry no task count and no elapsed time (user-ruled 2026-08-30).** The line "Confirm N task(s) are visible to you" was cut: the task list is a standing tool, and the count line is junk. The initial-agent-instructions' elapsed-time phrase, composed when the handoff-supervisor wrote it, which read "0 minutes ago" even when the successor started much later, was replaced by the session-handoff's `written-at` time and the instruction to calculate the gap from `date` and apply wariness in proportion.
- **An agent-session that ends without a session-handoff, other than by exiting cleanly, is resumed, not left dark (user-ruled 2026-09-21).** Specified in GHI [The handoff-supervisor resumes a session that died without a handoff, instead of stopping the seat](https://github.com/nedschorus/nedschorus/issues/613). Bought by a dark agent-seat: on 2026-09-21 the MD-skills agent-seat finished a turn cleanly at 21:49:00Z, sat idle 4m41s, and was terminated at about 21:53:47Z with exit code 143; its handoff-supervisor — alive, last heartbeat 21:53:41Z — wrote the exit record and stopped exactly as then designed, and the agent-seat sat dark beside an intact 6.4 MB transcript until the user happened to look. The handoff-supervisor can know how an agent-session died but never who killed it (POSIX does not tell a parent who sent a signal, and the agent-session's last output goes to the terminal it inherited, which it needs because it is interactive), so the choice is made on `process.returncode` alone: `0` stops, because a clean exit is a decision rather than a crash; `143` or `-15` (SIGTERM), `137` or `-9` (SIGKILL) and any other non-zero status resume; `None` stops — Python's value when the handoff-supervisor has no exit code, which happens only for an agent-session it adopted rather than launched, and no entry point now starts an adoption — because there is no basis for resuming. Two limits hold every resume. First, a budget of one resume that produces no new work (one, user-ruled 2026-09-22, where the GHI could be read both as two resumes and as no third launch: what makes a resume fail fails the same way on the next try), reset when the resumed agent-session adds a substantive turn — an assistant message with text or a tool call — and not merely when its transcript grows, since the resume prompt itself grows it (`claude --resume` reuses the session id in place, so the work goes into the same transcript). Second, the existing refusal to launch without a terminal, since a resumed agent-session needs a terminal exactly as a successor does. A resume keeps the session id and the generation: it is one conversation continuing, not a reincarnate-seat. Every path on which the handoff-supervisor stops after its agent-session has exited writes the exit record, so `scripts/recover-crashed-seats.py` remains the fallback unchanged.
- **The writer script prunes completed tasks from the agent-seat's task list (user-ruled 2026-10-13).** Claude Code lists every completed task in each task reminder and removes completed tasks only when every task in the list is completed, which seldom happens to a standing list, since it keeps gaining tasks: on 2026-10-13 the Mac's cold-read-research agent-seat's list held 25 completed tasks of 66, and ned-box's eight lists 194 of 441. Before it writes the session-handoff, the writer script removes each completed task whose log-store copy, made by `scripts/transcript-mirror-to-log-store.py`, has the same bytes, keeps one linked to an open task in either direction or that the next step names by id or subject, first raises `.highwatermark` — the file in the task-list folder from which Claude Code numbers a new task — to the highest task id, so that no new task takes a removed task's id, and reports any failure in one line without stopping the session-handoff. The user's answers of 2026-10-13: keep linked tasks rather than rewrite the links; take no task-list lock and do not re-read a file before deleting it, since no clash has been seen; one failure line in the old agent-session's output is enough; report a task list whose folder is missing, so that a move of Claude Code's task storage does not stop the prune silently.
- **Architecture-overview refreshes are drafted for the user, shown in an approval-walk, and reminded once a day (user-ruled 2026-10-01 and 2026-10-27).** A refresh of a system's nc-architecture-overview is drafted in `docs/nedschorus-wiki/queue/` under a `-draft` name and shown to the user as an item of an approval-walk before it replaces the nc-architecture-overview, since a message outside an approval-walk tends to be skipped; the reminder to refresh an nc-architecture-overview comes once a day per nc-architecture-overview.

## The reincarnate-seat trial — passed 2026-08-06

Four generations of a headless essay-writing agent, with three reincarnate-seats triggered automatically and no human input, met every pass criterion (full account in the text kept from before the 2026-08-12 cut). What it proved that no unit test could: for a headless agent-session, exiting after writing the session-handoff is the normal case, and the handoff-supervisor reads it correctly; the clean-stop path works; raising the threshold during the trial does not disturb the cycle; and a successor challenges inconsistent state unprompted.

## Known holes

- The task-list id the launcher sets, `CLAUDE_CODE_TASK_LIST_ID`, rests on undocumented Claude Code behaviour, and nothing detects its failure (accepted risk, user-ruled 2026-08-12).
- Dialog older than the conversation-tail's word floor is not in the conversation-tail; the successor finds it, when it needs it, in the complete dialog, in the log-store's session dialogs, or in the transcript, and committing as work goes keeps file state out of the dialog. A running thread of conversation longer than the word floor is handed over in part, and the conversation-tail's header counts the turns left behind.
- A handoff-supervisor is a process per agent-seat; if it dies, nothing replaces its agent-session at the next threshold. At that threshold the writer script reports that no handoff-supervisor is watching and gives the `scripts/resupervise-seat.py` command, and `nc-systems/handoff/handoff-supervisor.py --check --agent <name>` reports liveness on demand. On ned-box, if the agent-session dies too without a session-handoff, the agent-crash-watcher, `nc-systems/handoff/handoff-agent-seat-died-without-session-handoff-restart-watcher.py`, restarts the agent-seat, and tells the user instead when a session-handoff is waiting.
