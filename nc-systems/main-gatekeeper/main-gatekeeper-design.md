## The job and the guarantee

One program, `nc-systems/main-gatekeeper/main-gatekeeper.py`, is the only way an agent's change is submitted for main. The program builds the change, checks it, and opens a pull request; merge-lane reviews the pull request, checks the merge result and merges it (§ Check-in through a pull request). Two exceptions are named: a change to the gate's own source goes by an ordinary pull request until build-slice 7 (§ The error catalog, *Scope*), and agents on the Mac cannot reach a gate that runs on ned-box (§ Open, C8). A live gate opens its pull requests from its own GitHub account, `ned-git-gatekeeper`, which can open a pull request and cannot write main (§ The credential and enforcement). Because that account opens them, merge-lane-2, which approves as `ned-review-merge`, can approve every gate pull request, its own check-ins included: GitHub forbids an account to approve a pull request it opened, and until build-slice 10 moves the program onto `ned-git-gatekeeper` the program runs on its caller's credential, so the caller's account would open the pull request. That is one reason the gate stays dormant until build-slice 10. Agents — all of them, equally — invoke the program directly and never push to main themselves (branch pushes stay open to agent tokens — C4). No agent has a doorman or relay role in another agent's check-in path.

For each check-in request the program does exactly one of two things: **submits the work for main**, by opening a pull request, or **refuses and teaches the fix**. (`status` answers questions about a request and `cancel` withdraws one; § The reply.)

When the pull request merges, four things are true:

1. The change is on main, merged by merge-lane from the gate's pull request.
2. The checks ran against exactly the candidate commit the pull request carries, and merge-lane checked the merge result, the candidate combined with the main it joined, before merging (§ Concurrent check-ins).
3. The candidate commit's trailer lines carry the whole machine-readable record (§ The trailer).
4. The requester can learn the outcome: the check-in answers `in-review` with the pull request, and `status` answers `checked-in` with the candidate commit once the pull request merges.

On refusal, the reply always has three parts, like a well-built MCP tool — never a bare error code: the **named error** from the fixed catalog, the **specific facts** (which file, which check, which mismatch), and the **exact next action, written for an agent to execute**. The caller's files and main are untouched — a refusal changes no worktree content and lands nothing. Scoped exactly (2026-08-12): the base computation's fetch updates the caller's remote-tracking refs (metadata, never files); any invocation may sweep aged refusal records (§ States); a refused `--no-wait` request retains a JSON refusal record until read or expired (B4d); and a GitHub operation whose acknowledgement was lost can leave a pushed branch or an open pull request behind a `network-down` reply — resubmitting finds the pull request and answers `in-review`.

**Records:** git history, the gate's pull requests on GitHub, and the invoking agent-session's ordinary transcript are the *only* durable records. No side files, no separate logs — the invocation is a normal tool call, already recorded where tool calls are recorded. (Transient, not a record: the B4d refusal record above, which exists only until collected or swept.)

**Resubmitting is always safe: a check-in is idempotent.** A resubmit of the same work gets the request's current state back: `already-checked-in <commit>` once its pull request has merged, `in-review <pull request>` while the pull request is open (with one exception: a `network-down` retry may find the work further along than the first attempt reported, which is the self-healing working, not a contradiction). A corrected request digests differently and processes fresh. An agent that crashed or lost its connection never reconstructs what happened — it submits again and the program sorts it out. Refusals teach, retries are free: the loop self-heals, which is what near-perfect autonomous operation requires.

## The request and the reply

```
main-gatekeeper.py check-in
    --files <path> [<path> ...]
    --message "<one-line summary of what and why>"
    --import none | --import-commit <id> --import-source <path> --import-dest <path>
    --issue none | <issue-number>
    --agent <runtime/model>
    [--wait | --no-wait]          (default: --wait)
    [--repo <path>] [--remote <url>]   (test seams: hand the program a
                                        throwaway repository; identical
                                        under every user — C7)
    [--legacy-repo <dir>]              (the legacy checkout an import
                                        reads from; default
                                        ~/Projects/nedlern)
```

Field by field, with exact validation (all form validation is instant and synchronous in both modes; every refusal names its error and the fix):

1. **`--files`** — repository-relative paths, normalized: no absolute paths, no `..`, nothing under `.git/`, no duplicates, list non-empty. Path bytes are printable ASCII without whitespace and without the `->` sequence (the trailer separator) — violations refuse `malformed-field`; quoting grows in when a real import needs it. The new content of each path is read from the invoking agent's working copy — the program's only *content* read of that worktree (the advisory scan reads changed-file *names* from git status, never bytes — § Constructive guarantees). One exception: a declared import destination's bytes come from the legacy repository at the declared commit, never from the worktree — the caller need not, and should not, stage a hand-made copy (field 4). Per path the change is inferred: **added** (absent at base, present in worktree), **modified** (differs), **deleted** (present at base, absent in worktree). Refusals: `unknown-path` (in neither place — a typo), `unchanged-path` (declared but identical to base — declarations must be honest; an empty or malformed file list is `malformed-field`). No component of a declared path may be a symlink, on either side of the comparison — the caller's worktree refuses `malformed-field`, and a link carried in main's own tree refuses `base-tree-symlink`, which the caller cannot fix by resubmitting (ruled 2026-08-11 for the declared path itself, widened both ways 2026-08-12 after each direction was demonstrated reading and writing outside the repository). No check-in can remove such a link either, because every declaration that passes through the link is refused; whoever maintains that path removes the link by an ordinary pull request. The gate reads and writes regular files only: a link's target can live outside the repository, and the security boundary does not follow it. (A separate `empty-change` code — "nothing differs at all" — was deleted 2026-08-10 as unreachable: the first unchanged path refuses `unchanged-path` before any aggregate check could run.) Accepted residual (ruled 2026-08-10): the gate reads and writes bytes only, never a file's mode. A permissions-only change (`chmod +x`, no byte changed) refuses as `unchanged-path`, and a change that also touches bytes does not carry the caller's executable bit either: the candidate keeps the mode main already has, and a new file gets the clone's default. A mode change therefore goes by an ordinary pull request. Mode-awareness grows when a real need first arrives.
2. **`--message`** — the human-readable what-and-why; becomes the commit message body above the commit trailers. Required, non-empty (`malformed-field`, the facts naming the field — a dedicated `missing-message` code was folded in 2026-08-10 for consistency with every other field's emptiness). One line: a line break refuses `malformed-field`, because the gate writes its commit trailers after the message and a second line could fake one, for example `Gatekeeper-issue: #42` (ruled 2026-10-02; not built). Intent lives with the author; it cannot be auto-filled.
3. **The base** — the exact commit id of the main state the work started from. Computed by the program, not declared (ruled 2026-08-10, replacing a caller-supplied `--base` field and the two refusals that validated it): the program runs `git merge-base HEAD origin/main`, after a fetch, in the caller's checkout — the same checkout it already reads declared content from — so every caller's base is computed the same way, with no relay step to garble and no dependence on the cooperative tier being present. A failed fetch is tolerated: the computation proceeds against the last-known `origin/main`, giving an older base, which the re-application rules of § Concurrent check-ins absorb. When the checkout has no `origin/main` that shares history with HEAD, the request refuses `malformed-field`, naming the fix. The result is by construction a real commit on main. `--remote` changes only where the candidate is built and published, never where the base comes from: the base is always the caller's `origin/main`, so `--remote` must name a repository that holds the base commit. Accepted residual: a caller who refreshed from main mid-task (e.g. `git pull` after starting the work) presents a too-new fork point, weakening conflict detection for that request — a blind spot the earlier design shared exactly, since its wrapper script derived the value from the same repository state.
4. **`--import`** — `none`, or all three parts: the legacy commit id, the source path (must exist in the legacy repository at exactly that commit), and the destination (must appear in `--files`). Every import defect — incomplete triple, missing source, undeclared destination, unreadable legacy checkout — refuses as one code, `import-invalid`, whose facts and next-action text name the specific defect (four separate codes merged 2026-08-10: nothing machine-branches on refusal names, and the teaching text carries every distinction). A malformed import argument — an unrecognized `--import` value, a commit id that is not a full 40-character id, unsafe path text — refuses `malformed-field`, like every other malformed field. The gate checks only that the source exists at that commit, not that it is a regular file: a folder imports git's listing of the folder, and a symlink imports the link's target path as text, so an import names a regular file. A second import is inexpressible by construction — it is a second check-in. An explicit choice is required: `--import none` combined with any triple part, and omitting the import choice entirely — neither `--import none` nor the triple given — both refuse `import-invalid` (the built program behaves so; documented 2026-08-11).
5. **`--issue`** — `none` or a positive integer. Version 1 validates syntax only. Which work has an issue is decided *upstream*, by the agent and the user, at the right granularity; the gate only records the answer. `none` is honest for trivial work — an issue is never mandated per invocation (issues hold wanted things, not logs).
6. **`--agent`** — the runtime and model that produced the change (for example `claude-code/opus-5`), required, non-empty and one line (`malformed-field`; the line-break refusal is ruled 2026-10-02 and not built, as for `--message`). Declared by the caller because the environment names the runtime but not the model, and the model is the half the escalation path for failed work — retry, stronger model, then the user — needs ("who last wrote this" becomes one `git log` away). When several models, or a person and a model, wrote parts of the change, the value names the agent that submits it. Recorded, not verified: the gate records what it is told and never guesses.
7. **Origin** — auto-filled from the agent-session's environment; recorded as `none` when absent, never blocking (a transcript-less caller is honest, not an error). Meaningful because our agents are long-lived: the session id points at a readable transcript of intent.
8. **The digest** — SHA-256 over: base id + sorted path list + each path's new bytes (deletions as a marker) + the import triple. Deliberately excluded: message, issue, mode, origin, agent, time — the digest identifies **the work**, so identical work resubmitted under different metadata still deduplicates. Canonical serialization (the built program's): each component length-prefixed under a NUL-framed field tag, so no crafted content can make two different requests read as one (length prefixes added 2026-08-12, after a reviewer showed the original tag-only framing collidable). Computed by the program; callers generate nothing. Scope, ruled 2026-08-10: this deduplication recognizes verbatim resubmits only — the same work against the same base. A request rebuilt after a refresh from main digests fresh; when that work is already checked in, its declared paths now match main (unless main has since moved them) and the answer is `unchanged-path`. For a declared deletion the answer is `unknown-path` instead, because the deleted path is now in neither place, and that refusal's text calls it a typo: a caller who resubmits a deletion after refreshing checks `git log origin/main` for the path before reading the refusal as a typo. Accepted residual: the situations that reach that answer are rare (a successor session with an imperfect handoff, duplicate work), and the refusal's text already names the operative fact.

**The reply.**

Every invocation that runs to completion prints exactly one JSON object on stdout: `{outcome, error?, facts?, next_action?, commit?, digest?, pull_request?, merge_commit?, integrated_over?, advisory?, summary}`, where `summary` is the human-readable line — one format, not two (B1). An invocation killed before it finishes — a waiting check-in stopped by `cancel`, or a crash — prints nothing, and its caller asks `status`. The optional keys appear when earned: `pull_request` once the request has a pull request, and `merge_commit` beside `commit` once the pull request has merged (designed 2026-10-02 for build-slice 7, not built); `integrated_over` on a race-losing check-in that integrated cleanly, which build-slice 7 retires (§ Concurrent check-ins); `advisory` when the worktree differs beyond the declaration. Exit codes: **0** success and informational answers, `in-review` and `changes-requested` included; **1** catalog refusal (the gate working), and `closed-unmerged`, because nothing reached main; **2** program defect — distinct so loop counters and the audit never read a gate bug as a correct refusal. The contract covers the parser layer too (ruled 2026-08-11): a command-line-form error — unknown flag, missing argument, unknown subcommand — emits the same `malformed-field` teaching refusal as JSON, exit 1, never bare usage text with the defect code. Exactly two invocations are exempt, named here because the contract previously admitted no exceptions at all (ruled 2026-08-12): `--help`, for a person reading at a terminal, prints usage text and exits 0 — and agent-facing refusal text deliberately does not cite it; and `worker`, the internal re-entry the program makes into itself when detaching, which prints nothing because its reply channel is the workspace, and which is hidden from `--help` so the caller-facing surface matches the caller-facing contract. The `audit` subcommand (§ The credential and enforcement) is not exempt: it prints one JSON object whose outcome is one of its three named outcomes.

- Waiting caller: `in-review <pull request>` once the pull request is open, exit 0 (§ Check-in through a pull request).
- Non-waiting caller: instant `accepted <digest> on <host>` once form is valid; the outcome is collected later with `status <digest>` (`next_action` says exactly that, and names the submitting host — the workspace is host-local, so the digest is handed out together with the machine it belongs to).
- Any refusal: the three-part teaching form, exit 1.
- `status <digest>` answers from what already exists — main's history, the gate's pull requests on GitHub, and the program's workspace: `checked-in <commit>`, `in-review <pull request>`, `changes-requested <pull request>`, `closed-unmerged <pull request>`, `in-progress`, `abandoned` (workspace present, worker dead — resubmit safely), a retained B4d refusal record (returned once in the full three-part form, then swept), or `unknown` ("no trace; submit it" — always safe). For a request whose pull request is open the answer comes from GitHub, so any machine can give it; before the pull request opens, only the submitting machine knows the request.
- `cancel <digest>` — see § States, crashes, cancel, and errors.

Naming note (ruled 2026-08-10): the single-word subcommands (`status`, `cancel`, `audit`, and the internal `worker`) are a deliberate exemption from the project's multi-part naming rule, not a violation. A subcommand never appears alone — it is typed after the program's name, so the searchable name is `main-gatekeeper`, under which every invocation surfaces. The single-word answer and refusal names (`accepted`, `cancelled`, `conflict`, `unknown` and the rest) stay as they are too (ruled 2026-10-02): they are the built interface, and the tests pin them. Renaming now would strand the built test suite for no search benefit. New names added since 2026-10-02 are multi-part.
- The import record is read straight from history — `git log origin/main --grep "Gatekeeper-import: .*->"` (run after a fetch; the arrow appears only in real import trailers, so `Gatekeeper-import: none` lines do not match — though a commit message that quotes the trailer's format in prose can, so read each matching commit's trailer, not only the list) lists every import: what was imported, from which legacy commit, to where, when. (An `imports` subcommand that formatted this into a table was built in build-slice 2 and deleted by ruling 2026-08-10: the trailer is the record, the git command is the view, and a per-call scratch clone bought no guarantee. The trailer replaces the retired entry-manifest row rule; `entry-manifest.md` remains as the founding-era historical record only.)

## The procedure

1. **Submit.** The agent invokes the program with the request and its mode choice.
2. **Screening — synchronous in both modes.** Form validation (above). The digest is computed and looked up right here: in main's history, where it answers `already-checked-in <commit>` with no work done, and among the gate's open pull requests, where it answers `in-review <pull request>`. A non-waiting caller gets `accepted <digest> on <host>` now; everything after runs identically either way. (Screening fetches and creates the `screening-*` scratch clone, so it takes as long as those take — usually seconds, longer on a slow network.)
3. **Build the candidate.** In the program's own private workspace (`<workspace-root>/<digest>/`) — never the agent's worktree — start from main *at the computed base* and apply exactly the declared changes. Unchanged files come from main, never from the agent's possibly-stale copies. A declared import happens here: copy from the legacy repository at the declared legacy commit; record the source for the trailer.
4. **Run the checks** (§ Constructive guarantees) against the candidate — the literal bytes that would become main.
5. **Commit.** The message, then the trailer lines.
6. **Publish.** Push the candidate commit to the request's own branch, `main-gatekeeper-request/<digest>`, and open a pull request from it (§ Check-in through a pull request). The built program still pushes to main directly until build-slice 7.
7. **Answer.** The waiting caller gets `in-review <pull request>`; the non-waiting caller finds the same answer with `status`. The workspace is deleted (B4d exception: a refused `--no-wait` request's workspace survives, holding only the refusal record, until `status` collects it or it expires — § States).
8. **Review and merge.** merge-lane reviews the pull request, checks the merge result, and merges it; `status` then answers `checked-in <commit>`.

The requester's own working copy is never modified; the agent refreshes from main at its convenience.

## Constructive guarantees, the advisory, and the extension point

Most classic gate failures are made impossible by construction rather than detected:

- **Stray changes cannot enter** — at path granularity: the candidate is built *from* the declaration, so an edit in an undeclared path never reaches it. Within a *declared* path the worktree bytes ARE the declaration — a stray edit inside a declared file rides along; the guarantee is per-path, not per-edit.
- **The record cannot be missing** — the program writes the trailers itself.
- **The import record cannot lag** — written during candidate construction, same commit.
- **Duplicates cannot apply** — the digest screen runs at submit.

**One advisory (not a refusal):** if the agent's worktree contains modified, deleted or untracked files *beyond* the declared ones, the reply carries a note — "worktree also differs at `x`, `y`; confirm intentional" — because the likeliest cause is a forgotten declaration, and a forgotten *new* file arrives untracked (ruled 2026-08-11; `.gitignore`d files stay hidden). Unrelated work-in-progress in the same worktree is legitimate, so this never blocks.

In version 1, between screening and publication, **no judgment refusal remains** — this stage is deterministic construction and recording; infrastructure failures (`workspace-io-error`, `network-down`) can still arise here and are safely resubmittable. In version 1 the checks *are* construction itself, so guarantee 2 binds the checks that exist — construction — to the exact bytes the pull request carries; it gains content as checks are added. That is the gate's extension point, the place where new checks are added as they come to exist, not a hole: when a test suite exists, the tests run here. (A review-evidence check for instruction-bearing text was designed for this place and ruled not to be built, § Resolved.)

## The trailer

```
Gatekeeper-origin: <session-id> | none
Gatekeeper-agent: <runtime/model>
Gatekeeper-digest: <sha256-of-the-work>
Gatekeeper-import: none | <legacy-commit> <source-path> -> <destination-path>
Gatekeeper-issue: none | #<issue-number>
```

Four facts and a pointer; nothing else. **What `Gatekeeper-origin` names when work is delegated (measured and ruled 2026-08-14):** a subagent inherits its parent's environment unchanged — `CLAUDE_CODE_SESSION_ID` is the *parent's* id inside a spawned agent, verified by probing one — so a check-in submitted by a subagent already records the supervising session, and the subagent itself is recorded nowhere. That is the wanted default: the supervising agent-session's transcript is the one worth opening, and it contains the delegation. The accepted cost, named so a reader is not misled: a commit can name a supervising session while a subagent wrote every line, and `Gatekeeper-agent` carries whatever runtime/model that subagent declared, so a weaker tier's work can sit under a stronger tier's session id. Recovery is on that machine only — the subagent's transcript sits at `~/.claude/projects/<project>/<parent-session-id>/subagents/agent-<id>.jsonl` beside a `.meta.json` carrying `agentType`, `description` and `spawnDepth` — and nothing in git points at it. No trailer is added: a `Gatekeeper-subagent` line would need the harness to export a spawned-agent identifier, which it does not. The reopening trigger recorded on 2026-08-14 — subagent-written check-ins becoming common — has fired, because subagents now do most of this project's work; the trailer stays out only because the harness still exports no identifier, and § Open lists the question. The agent line (B6, user-ruled 2026-07-31) names the runtime and model that produced the change, literal value, never omitted — the escalation path needs to know which model produced an artifact to know whether stronger models remain. The digest line is the **idempotency key**, not provenance — it is what makes resubmission safe. The issue value is written in `#<n>` form deliberately: any commit reaching the default branch with `#<n>` in its message appears automatically in that issue's GitHub timeline, so **an issue collects all its check-ins with zero machinery**. A candidate commit pushed to its request's branch may appear on the issue's page before it merges, and stays there if the pull request is closed unmerged; the listing links the pull request, so the issue's page shows the attempt and its outcome (accepted 2026-10-02). The same collection is derivable offline (`git log --grep "Gatekeeper-issue: #<n>$"` — anchored, so `#1` never matches `#10`). Refusals and other responses are **never** auto-posted to issues — mechanical chatter stays in transcripts; a genuinely blocking outcome earns a judgment-written comment by the requesting agent (revision convention: comments are for genuinely new events). The gate's own pull requests are the one exception: `cancel` comments on the pull request it closes, so the reviewer sees why it closed.

## Concurrent check-ins

Each request publishes to its own branch, so two check-ins never race to push: both pull requests open, and merge-lane merges them one at a time (§ Check-in through a pull request). Before merging each gate pull request, merge-lane checks the merge result — the candidate commit combined with the main it would join — so main never holds a combination nobody checked. When that check fails, merge-lane closes the pull request and says why, and the caller updates from main and checks in again. No queue and no lock are built; check-ins run in parallel by default (user ruling).

- **At a resubmit, the re-application rules apply.** A request whose base main has passed is rebuilt by re-applying the declared changes onto the new main. **Clean re-application** (the usual case — different paths): the checks run again on the rebuilt candidate. **Same-path collision** (main changed a path this request changes — file granularity in the built program, so no silent lost update exists within a path): re-applying would require guessing the author's intent, and the program never guesses — it refuses `conflict`, naming the files, the intervening commits, and the next action: update from main, adjust, resubmit (the adjusted work digests fresh, correctly).
- A request submitted from a behind-main worktree is the same mechanism — being behind is just "main moved before we started."
- **The built program still pushes to main directly**, so until build-slice 7 its race works as designed on 2026-07-24: GitHub accepts one push whole and rejects the other; the loser re-checks the new tip for its own digest (a concurrent resubmit of the same work answers `already-checked-in`), re-applies its changes and pushes again, up to five rounds, then refuses `main-moving-too-fast` rather than spin; a clean re-application reports `integrated_over: <n>`. Build-slice 7 retires the push race, the five-round cap, `main-moving-too-fast` and `integrated_over`, because a push to the request's own branch has nothing to race.
- **Semantic clashes:** changes in *different* files that interact *semantically* are caught by merge-lane's check of the merge result — once checks exist that can catch them (§ Open, the check battery). Until then they pass, as they always have.
- **Deferred optimization, trigger named:** when checks become slow (a real test suite), re-validation narrows to the checks whose inputs intersect what actually changed between bases (impact analysis), so head movement that no check reads does not invalidate a pending check-in (user ruling). A merge queue — checking several queued pull requests against their combined result, as GitHub's merge queue does — is the next step up, if volume ever demands it.

## States, crashes, cancel, and errors

**States:** SCREENING (synchronous; only an unkeyed scratch clone on disk, nothing keyed by digest) → WORKING (candidate being built and checked, inside `<workspace-root>/<digest>/` — concretely `$XDG_STATE_HOME/nedschorus-gatekeeper/<digest>/`, default `~/.local/state/...` (B4a); once C2 lands this resolves in the *gatekeeper user's* environment — literal default `/home/nedschorus-gatekeeper/.local/state/nedschorus-gatekeeper/<digest>/`: outside every repository, discoverable from the digest alone *on the host that created it* (workspaces are host-local: nothing is shared between machines, so `status` and `cancel` answer only for requests submitted where they run — corrected 2026-08-13, the phrase previously read as though a digest were discoverable anywhere), holding the candidate clone, `worker.pid`, and the resolved request record (B4c: every environment-derived field, origin foremost, is resolved at screening into that record; the worker only reads it, never re-derives)) → PUBLISHING (push the request's own branch and open its pull request; until build-slice 7, PUSHING to main, an atomic attempt capped at five rounds) → IN-REVIEW (the pull request is open; merge-lane reviews it) → **CHECKED-IN** (merged), **CLOSED-UNMERGED** (closed without merging), or **REFUSED** (refused before publication). The workspace is deleted once the pull request is open or the request is refused, with one exception (B4d): a refused `--no-wait` request keeps its workspace holding just the JSON refusal record; `status` returns it once, then sweeps. Expiry (ruled 2026-08-10): any invocation of the gate first sweeps refusal records older than 30 days, and `screening-*` scratch clones and dead-worker workspaces older than a day — opportunistic, no daemon; a caller whose record aged out resubmits, the same recovery as every lost reason. Named residual (accepted): a caller whose `status` call collected the record but who crashed before reading the reply loses the reason — rare, recoverable by resubmit. Durable traces: a checked-in request is its candidate commit on main; a request in review, or closed unmerged, is its pull request on GitHub; a refused waiting request deliberately leaves nothing.

**Crash recovery — one rule, not a procedure.** The pipeline's durable effects are the workspace directory, the request's branch on GitHub, its pull request, and — through merge-lane — the merge. A crash or lost connection can stop the pipeline between any two of them: for example, the branch is pushed and the pull request never opened. (A harmless leftover: a crash during screening strands an unkeyed `screening-*` scratch clone, which the expiry sweep clears.) Recovery is: **resubmit**. The program checks the digest against main's history (found: `already-checked-in <commit>`), then against the gate's open pull requests (found: `in-review <pull request>`); otherwise a leftover workspace whose worker is dead is swept and the work runs fresh — a live worker answers `in-progress` instead — and the request's branch is replaced, which the gate does only when no pull request from that branch is open (§ Check-in through a pull request). No journal, no repair mode. `status` distinguishes WORKING from **abandoned** (workspace present, worker process dead) via the recorded process id, so a died-silently worker is a named, resubmittable state — never a forever-"in-progress". Residual (accepted): a recycled pid can masquerade as a live worker, and a pid check says nothing across machines; build-slice 4 records the worker's start-time beside the pid so `status` checks both.

**`cancel <digest>`** — in version 1's contract (user ruling: the need arrives with slow checks, the machinery it needs already exists, and it is small; build-slice 4, built 2026-08-12 — see the build-slice plan). Any agent may cancel; there is no permission machinery — cooperative model; the workflow simply does not teach cancel as a routine move (and the author may be gone; authorship grants no special judgment). Outcomes, exactly five (the fifth added 2026-08-12): digest already in history → `too-late — already-checked-in <commit>` (the remedy for a bad checked-in change is a **revert**: an ordinary check-in whose change undoes a previous one, through the same gate); live worker found → kill it, sweep the workspace, `cancelled`; a workspace with no live worker (an abandoned run, or a retained B4d refusal record) → sweep it, `cancelled`; nothing found *on this host* → `unknown-request` (workspaces are host-local; a request submitted from another machine is cancelled there, ruled 2026-08-12); the worker outlives SIGKILL → `cancel-failed`, naming the pid and what was tried, leaving the workspace in place and telling the caller the request may still reach main (ruled 2026-08-12 — the alternative was reporting a success that had not happened). The cancel-versus-push race resolves by the push's atomicity: kill the worker's process group — a recorded pid alone leaves an already-spawned `git push` child running (ruled 2026-08-11) — but the group **only** when the recorded pid leads one, since a waiting check-in records its own pid, whose group is the caller's harness (ruled 2026-08-12, after a demonstration killed a launcher and its unrelated siblings). When the recorded pid leads no group — a waiting check-in — cancel signals that one process alone, and a `git push` it already started can still finish; so cancel waits for the process to exit and then asks history whether the digest made it, and answers what history shows. Once the pull request is open, cancel works on the pull request instead (§ Check-in through a pull request). Every ending re-asks history and confirms the kill: the sequence used to run on the live-worker branch alone, so a worker that pushed and died was answered `cancelled — nothing reached main`. Cancel only makes sense before the check-in completes (user ruling); after, revert.

**The error catalog** — every ending named, three-part teaching form:

- *Form (instant):* `malformed-field` (any missing, empty, or malformed field, named in facts — including a declared path passing through a symlink in the caller's worktree), `unknown-path`, `unchanged-path`, `import-invalid` (any import defect, named in facts), `base-tree-symlink` (main itself carries a link on the way to a declared path, added 2026-08-12: the caller cannot fix it by resubmitting, so it is named apart from `malformed-field` and its next action points at whoever maintains that path on main). (Collapsed 2026-08-10: `missing-message` and the unreachable `empty-change` folded into `malformed-field`; the four import codes merged; `unknown-base` / `base-not-on-main` retired with the `--base` field — the program computes the base, so no hand-off exists to validate.)
- *Integration:* `conflict`, `main-moving-too-fast` (retires at build-slice 7, § Concurrent check-ins).
- *Scope:* `gatekeeper-source-refused` (added 2026-08-17) — the declared paths include `nc-systems/main-gatekeeper/main-gatekeeper.py`, the gate's own source, which the gate does not check in. Facts name the offending path; the next action points at the pull-request lane, where the change is reviewed before merge. Not a defect and not resubmittable as-is: resubmitting the same request refuses identically, by design. The reasoning is in § The credential and enforcement — the deployed copy updates itself from main, so the gate declining to check in its own source is what keeps a reviewer between an agent and the running gate. **Retires at build-slice 7 (ruled 2026-10-02):** once the gate opens pull requests that merge-lane reviews, a change to the gate's source gets the same review through the gate as through an ordinary pull request, so the refusal adds a detour and no safety. Until then the built gate pushes to main directly, and the refusal stays.
- *Infrastructure:* `push-auth-failed`, `network-down`, `workspace-io-error`, and `pull-request-operation-refused` (designed 2026-10-02 for build-slice 7, not built) — GitHub refused an operation on the request's branch or pull request, naming which: pushing the branch, opening, closing, or deleting the branch — all safely resubmittable. Caller guidance: these refusals warrant bounded, backed-off retries at the caller's judgment; the gate never instructs unbounded resubmission.
- *Unbuilt surface:* `unbuilt-option` — dormant since build-slices 4 and 5 built (2026-08-12): no unbuilt option remains reachable. The name stays reserved for future extension points.
- *Cancel:* `cancel-failed` (added 2026-08-12) — the worker outlived SIGTERM and SIGKILL, so the gate neither stopped it nor knows the outcome. Named rather than forcing a false `cancelled`, which is what the program did before; the workspace is left in place and the caller is told the request may still reach main. Designed 2026-10-02 for build-slice 7, not built: `cancel-pull-request-not-closed` (GitHub refused to close the pull request, so the request may still merge) and `cancel-branch-not-deleted` (the pull request is closed and its branch remains); `cancel` is safe to repeat, and running it again finishes the job.
- *Answers, not errors:* `checked-in <commit>`, `already-checked-in <commit>`, `accepted <digest> on <host>`, `in-progress`, `abandoned`, `unknown`, `cancelled`, `too-late`, `unknown-request`; and, designed 2026-10-02 for build-slice 7, not built: `in-review <pull request>`, `changes-requested <pull request>`, `closed-unmerged <pull request>`.
- *Audit:* `protection-ok`, `protection-wrong`, `audit-failed` — the three outcomes of the `audit` subcommand (§ The credential and enforcement).

**The autonomy standard, met:** no unnamed endings; every refusal teaches; resubmit always safe; nothing routes to the user mechanically — he is consulted by agents' judgment, never by the machinery.

## Check-in through a pull request (designed 2026-10-01)

Build-slice 7 makes the gate open a pull request instead of pushing to main (ruled 2026-08-29). On 2026-10-02 this design replaced the push design: the sections above were rewritten to match this section, and where they still describe a push to main, they describe the built program until build-slice 7.

- **Where a request lives while its pull request is open.** The gate pushes its candidate commit to a branch of the request's own, `main-gatekeeper-request/<digest>`, opens a pull request from that branch, and deletes the workspace. The open pull request is the request's record, so `status` and `cancel` answer for it from any machine. A new state, IN-REVIEW, follows PUSHING, which now pushes the branch and opens the pull request. The endings become CHECKED-IN when the pull request merges, CLOSED-UNMERGED when it is closed without merging, and REFUSED as before. The digest screen asks two questions in order: is the digest in main's history (`already-checked-in <commit>`), and is a pull request from the digest's branch open (`in-review <pull request>`). A resubmit during review therefore opens no second pull request. A closed pull request does not count, so a resubmit after a cancel or a closing opens a new one.
- **A request's branch, from push to deletion.** The gate owns each request's branch, and replaces the branch only when no pull request from it is open. "The request's pull request" means the most recent pull request from that branch. GitHub allows one open pull request per branch, so of two identical check-ins racing, one opens the pull request and the other answers `in-review` with its link. `cancel` is safe to repeat: a failed close and a failed branch deletion are each their own outcome (§ The error catalog), and running `cancel` again finishes the job. Before opening a pull request, the gate's reply lists any open gate pull request that declares the same files, so a duplicate is visible; the list never blocks the check-in.
- **What a waiting caller gets.** Both modes end before review. `--wait` returns once the pull request is open, with `in-review <pull request>`, or with a refusal if screening or the checks refused. `--no-wait` still returns `accepted <digest> on <host>` after screening. Afterwards the caller asks `status <digest>`, which reads the pull request on GitHub and answers `in-review <pull request>`; `changes-requested <pull request>` when merge-lane's review asked for changes; `checked-in <commit>`; or `closed-unmerged <pull request>`. The review's findings stay on the pull request; `status` points to them and does not copy them.
- **Following up a request in review.** The calling agent records the pull request's link as a task in its agent-seat's task list, so a successor agent-session finds the pull request; merge-lane closes nothing on a timer. A daily job that relaunches every agent-seat that has open tasks and is not running is GHI [Relaunch stopped agent-seats with open tasks daily](https://github.com/nedschorus/nedschorus/issues/936).
- **Which commit is reported.** `checked-in <commit>` and `already-checked-in <commit>` name the same commit: the gate's candidate commit, which carries the trailer and joins main's history through the merge. The facts also name the merge commit and the pull request.
- **Cancel once the pull request is open.** `cancel <digest>` closes the pull request with a comment saying it was cancelled, deletes its branch, and asks GitHub again. GitHub settles the race the push used to settle: a merged pull request cannot be closed. So if the merge got there first, the answer is `too-late — already-checked-in <commit>`, and the remedy is a revert, as before.
- **Two check-ins at once.** merge-lane merges one pull request at a time, so merge-lane orders them; the gate keeps no queue and no lock. Each pull request merges as a merge commit, so a pull request whose base main has since passed still merges when git can combine the two. Before merging, merge-lane checks the merge result (ruled 2026-10-02), and when that check fails, merge-lane closes the pull request and says why. The per-file staleness report (build-slice 8) shows the reviewer which of the request's files main changed since its base, and is never a refusal. When git cannot combine them, merge-lane closes the pull request and says why; the caller updates from main and resubmits, and the re-application rules of § Concurrent check-ins, the `conflict` refusal included, apply at that resubmit. The gate never moves the branch of an open pull request, because merge-lane reviews a frozen head.
- **Correcting a request in review.** Every correction starts with `cancel`, which closes the old pull request; a closed pull request does not block the resubmit, so the corrected request then opens a new pull request for merge-lane to review. This holds for a correction to the message, the issue or the agent field too, which leaves the digest unchanged: without the cancel, that resubmit would answer `in-review` with the old pull request. CLAUDE.md's fix-round and hand-merge rules do not apply to pull requests the gate opens; CLAUDE.md is to say so when the gate activates (the build-slice plan's note on the CLAUDE.md edit owed at activation).

## Resolved

- Which artifact classes are gated on approved-by-walk evidence — the first class was designated (user-ruled 2026-08-04): instruction-bearing text (CLAUDE.md files, skills with their prompt templates, injected system prompts, the wiki), whose check-ins were to require approved-by-walk evidence — a requirement withdrawn with build-slice 6 on 2026-08-17 (next bullet); class definition, procedure, and guards on GHI [Review-system design requirements learned from the legacy gate — dormant until a class of work first requires review](https://github.com/nedschorus/nedschorus/issues/31). The check itself was build-slice 6, scheduled 2026-08-10 as a prerequisite of privileged-lane activation, and is not built.
- **The approved-by-walk evidence format, and build-slice 6 with it — designed, then ruled NOT to be built (user-ruled 2026-08-17).** The format was designed against a forgery threat: an agent fabricating the user's approval in order to land an instruction-bearing change. That threat was tested against the project's own record — 360 session transcripts on both machines searched for writes of the `.walk-approved` marker, 61 writes found — and **no fabricated approval exists**. One defect class was found, twice: a marker mixed the user's words with an agent's framing and marked neither. In one case the user had approved by selecting an option rather than speaking, so the agent, having no words of his to record, wrote a summary of its own proposal into the slot reserved for his voice. Nothing was forged; the *record* lost its ability to show where the approval came from. Against that, the format's benefit in ordinary use is thin — when the user instructs an agent to submit a change, his approval is already the instruction, so the evidence field records what has already happened rather than preventing anything — while its cost is that no instruction-bearing change could ever land unattended. The user judged the trade not worth taking; the deciding standard was that machinery is not built merely because an earlier ruling implied it. Consequences carried into § The credential and enforcement rather than left implied: C2's activation reasoning is restated honestly, the gate refuses check-ins touching its own source, and the owner's account stays on main's push allow-list so the pull-request lane survives activation. Full reasoning, including one alternative considered and withdrawn (read-only file modes, which fail because permissions do not travel through git): `docs/issues/3-slice-6-review-evidence-not-built.md`.
